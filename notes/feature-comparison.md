# 功能比较方案

本文件只维护全仓比较思路、证据口径、输出格式和模块入口。比较对象、领域维度与范围由各模块 prompt 自行维护；本文件及模块 prompt 均不保存某次比较的结论或评分，不替代架构契约、ADR 或 roadmap。

## 使用方式

将以下任务指令交给执行者，并指定模块；未指定时比较Kernel 与 Viz 两个方案入口。先读取对应模块 prompt，再按其对象、维度和边界执行。可以限定能力子集，但必须在报告中列明覆盖与排除范围。

> 按本文件执行功能比较。模块：`Kernel / Viz（Data、Plot、Chart、Table） / 全部`；能力子集：`全部或明确列出`。读取当前仓库与外部官方资料，按模块配置比较，用表格和最多五条简要总结反馈。只生成分析报告，不修改代码、架构、ADR 或 roadmap，不自动执行性能、压力、基准或 LLM 测试。结果写入已被 Git 忽略的 `notes/reports/feature-comparison/<YYYY-MM-DD>-<module>-<short-commit>.md`；全部模块分别出报告，聊天中给出文件链接与简要总结。

## 执行与证据口径

1. 记录日期、当前分支、完整 commit、工作区是否有未提交改动及其对结论的影响；从实际 manifest 读取包版本，不复用历史报告中的版本、数量或“尚未实现”结论。
2. 阅读模块及相邻 owner 的 AGENTS、公开入口、schema、实现和相关测试，追踪输入到最终输出的闭环。需要设计背景时先按仓库 ADR 检索规则定位，再阅读命中文档。设计获批、测试存在或类型存在都不能单独证明功能已实现。
3. 外部框架优先使用官方文档、公开 API、官方示例和源码；记录版本或 commit、访问日期及链接。无法确定版本或获得资料时写明限制，不能凭印象补齐。历史报告只提供检索线索，不能直接当作当前证据。
4. 调研时按下表区分能力状态，报告用 10 分制呈现，评分依据与必要限制集中到表格最后的备注栏。同一功能区分“内置完成度”和“公开扩展能力”；不把理论可编程性、可替换 renderer 或可写 adapter 当作已经交付的支持。
5. 各项目按其定位比较共同问题，不按 Retikz 的 API 形状评判。原生无需中间层即可解决的问题，不因没有同名 IR 或 registry 扣分。产品交互、底座机制、作者体验分别评价。
6. 当前能力、已批准设计与建议分开；分别给 Retikz 现状与规划打分；规划指 roadmap 与明确长期计划完成后的预期程度，不是理论架构上限；按统一规则计算分类均分与总均分。评分是有证据支持的主观判断，不是精确测量。性能与包体积仅引用注明环境、工作负载、配置、版本和方法的可比数据；否则不打分。运行任何性能测试须另获当次授权。
7. 输出前复核关键结论与来源、模块边界、支持状态和未验证项，确认报告路径被 `git check-ignore` 覆盖。报告不 stage / commit；同路径已存在时使用时间后缀保留旧结果。

| 状态           | 判定条件                                                     |
| -------------- | ------------------------------------------------------------ |
| 内置支持       | 当前版本有可用公开入口与完整输出链路，注明范围限制           |
| 公开扩展可实现 | 有稳定公开扩展契约和实现证据或可核验示例，注明所需工作       |
| 需自行开发     | 只有通用原语或自定义代码的可能性，没有现成闭环，不计作已支持 |
| 不支持         | 有明确边界或实现证据；仅未检索到不能直接判定不支持           |
| 不适用         | 不属于项目定位或本次比较范围，说明原因                       |
| 未验证         | 证据不足、版本不明或未完成核验                               |

## 报告格式

报告以一张评分表和表后最多五条重要发现为主；确有需要时按主题拆表。外部框架列只放分数，不逐框架展开；Retikz 分为“Retikz 现状”和“Retikz 规划”两列分数。表格备注尽量简短，通常用一句话说明 Retikz 现状与该项最高分者的主要能力差距，并点明参照对象；规划已明确弥补差距时可简述。并列最高可选代表或写“并列最高者”；Retikz 同分或领先时如实说明，不强造差距。最高分只在已核验的有效分数中确定，规划分不作为已交付标杆；缺少可比证据时注明“差距待核验”，仅 Retikz 有分数不代表领先。重要发现、跨项结论与较长解释在表后列表给出，详细证据放折叠区或附件，不挤进单元格。

### 基线与评分口径

表前用两三行说明日期、模块、Retikz 版本 / commit、工作区影响与验证范围。外部版本和来源放备注或折叠的资料区，不另写长篇介绍。

**10 分制**：1–2 缺失或很弱，3–4 有限，5–6 基本可用，7–8 较完整，9–10 领先或标杆。按同一行的具体能力评价，不因为接口形态不同扣分；证据不足或不适用写 `—`，原因放备注，不能把未知打成低分。

### 评分表

| 分类     | 比较项              | 框架 A     | 框架 B     | Retikz 现状 | Retikz 规划 | 备注                     |
| -------- | ------------------- | ---------- | ---------- | ----------- | ----------- | ------------------------ |
| 能力类别 | 比较维度            | 1–10 或 —  | 1–10 或 —  | 1–10 或 —   | 1–10 或 —   | 当前能力、规划依据与限制 |
|          | 其他维度            | 1–10 或 —  | 1–10 或 —  | 1–10 或 —   | 1–10 或 —   | 必要说明                 |
|          | **能力类别 · 均分** | **均分**   | **均分**   | **均分**    | **均分**    | 有效分数平均             |
|          | **总均分**          | **总均分** | **总均分** | **总均分**  | **总均分**  | 有效分类数 / 全部分类数  |

同一分类只在首行填写名称，后续行留空；每类末尾增加“分类名 · 均分”，分类汇总后增加“总均分”，其下增加“能力完备性”。汇总值加粗，保留一位小数。分类均分按有效分数作算术平均，总均分按有效分类均分等权计算；使用未舍入值计算后再显示一位小数。`—` 不计作零分，整类无有效分数时不参与总均分。备注注明未评分原因，以及总均分的有效分类数 / 全部分类数；覆盖范围不同的总均分只供概览，不作严格排名。

不追加逐框架分析、重复的能力状态表或完整差距表。详细证据可放折叠区或同目录的 ignored 证据附件，主报告只保留必要链接。

### 简要总结

表后用最多五条列表说明重要发现，包括 Retikz 的优势、主要短板、规划缺口与优先建议，不重复逐行备注。建议不是开发承诺；注明关键未验证范围，不将覆盖范围不同的总均分作为不同定位项目的严格排名。总均分备注可简写“覆盖见表后”，具体有效分类数与有效项数列于表后或折叠资料区。

规划评分口径：先核对源码，roadmap 中已实现的项目计入现状，不重复加分。规划分保留现状基线，仅按尚未交付且有明确目标的 roadmap / 长期计划调整；没有新增计划时与现状相同，目标过泛或无法判断时写 `—`。候选方向须标为条件性预期，不能当作确定承诺。现状和规划分别计算分类均分与总均分。

规划评分前必须实际阅读所属模块的 roadmap、相关架构设计及命中 ADR 全文，并核对当前源码；备注或证据区列出具体文档、状态、目标与未实现部分。不得仅凭标题、用户提到的方向、通用经验或理论可扩展性猜测规划能力和分数。文档缺失、目标不明确或旧设计与当前架构冲突且未解决时，对受影响规划项写 `—` 并说明缺口；没有新增目标且现状证据充分的项目可维持现状分。

在“总均分”下一行增加“能力完备性”，格式为 `已实现项数/全部比较项数 → x.x/10`，计算公式为已实现项数 ÷ 全部比较项数 × 10，各项等权。按证据逐项判断是否已有可用能力闭环，不按评分阈值或有无评分机械计数；能力已实现但缺性能实测分仍可计入。明确缺失、仅有理论可扩展性或需另行开发闭环的项目不计入；未核验项保留在分母、不计入分子，因此有未知项时须标明“已确认下限”，不能据此认定其余均不支持。规划列以已实现能力为基线，再并入有 roadmap 与架构设计依据的新增闭环，去重计数，标注为目标覆盖而非已交付。详细计数依据放折叠区。
