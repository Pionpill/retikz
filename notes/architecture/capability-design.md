# 能力完备检测设计

> 本文只定义 retikz 的“能力完备检测”概念、适用模块和执行方式。各模块自己的完备标准、检查项和落地细节，写在对应模块的设计文档 / ADR / roadmap 中。

---

## 1. 背景

“图灵完备”对 retikz 有启发，但不能直接照搬。图灵完备判断的是计算模型；retikz 需要判断的是表达模型：

> 一个核心功能模块是否具备表达某类能力的完整闭环。

这里的“完备”不是指一次内置所有能力，也不是 API 数量越多越好，而是指模块具备清晰的能力边界、扩展机制和端到端消费路径。新增能力时，应先判断它属于哪个模块，再检查该模块是否已经具备承载它的完整链路。

---

## 2. 核心概念

能力完备检测回答三个问题：

1. **归属**：这个能力应该属于哪个核心模块？
2. **闭环**：这个模块是否能从 schema / contract / provider 到 compile / lowering / docs / tests 形成完整链路？
3. **边界**：如果不能闭环，是该补当前模块、下沉到更底层模块，还是明确不在范围？

不满足闭环的实现只能算局部实现，不能算模块能力。常见风险包括：

- 高层封装绕过底层表达能力。
- 内置能力可用，但自定义能力不能走同一机制。
- 有 schema，但没有 registry / provider / pipeline 消费。
- 能画出来，但不能持久化、测试、文档化或被 AI 稳定生成。
- 某个模块私造了本该属于更底层模块的 IR、几何、renderer 或数据语义。

---

## 3. 需要做完备检测的模块

完备检测只用于核心功能模块，不用于 `chart` 这类体验封装层。

当前至少包括：

| 模块 | 完备方向 | 说明 |
| --- | --- | --- |
| `@retikz/core` | Graphic / Drawing Complete | 检测任意静态图形语义是否能落到统一图形基座。 |
| `@retikz/plot` | Visualization Complete | 检测任意数据可视化语义是否能落到统一数据映射管线。 |

未来新增同级核心模块时，也必须定义自己的完备方向。例如 table、geo、data 等模块如果成为独立核心层，应各自说明它们的能力边界和闭环标准。

`chart`、React / Vanilla 组件层、preset、demo 和文档示例不定义自己的完备目标。它们只能消费核心模块已经具备的完备能力；如果它们需要底层无法表达的新语义，应先回到对应核心模块补能力。

---

## 4. 怎么做

每个核心模块都应维护自己的完备检测文档或 ADR 小节，至少包含：

1. **模块使命**：该模块追求什么类型的完备性。
2. **能力边界**：什么能力属于本模块，什么应下沉或上移。
3. **能力链路**：一个能力从声明、扩展、实现到消费要经过哪些环节。
4. **准入标准**：新增能力进入本模块前必须回答的问题。
5. **不完备处理**：遇到缺口时，是补模块能力、补底层能力，还是记录为不支持。

新增核心能力的 ADR 应加入“完备性检查”小节：

```md
## 完备性检查

- 所属核心模块：
- 对该模块完备目标的影响：
- 是否需要下沉到更底层模块：
- 是否形成 schema / contract / provider / pipeline / tests / docs 闭环：
- 内置与自定义是否同机制：
- 本轮不做的能力及原因：
```

实现阶段按这个检查结果执行。若发现能力放错层，应先调整设计；若发现闭环缺失，应补齐对应环节或明确延期原因，不能用局部补丁绕过。

---

## 5. 与其它设计文档的关系

本文是总纲，不替代子模块设计。

- `core-design.md` 负责 core 的具体架构原则。
- `packages/viz/_notes/architecture/plot-design.md` 负责 plot 的具体图形语法与管线。
- 各模块 roadmap / ADR 负责把完备检测拆成具体阶段和任务。

后续如果某个模块需要更细的检查表，应写在该模块自己的 architecture notes 或 ADR 中，不扩写本文。
