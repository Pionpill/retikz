# AI 语义评测设计

> **状态：分层方向已确认，尚未按此组织落地。** 当前 `apps/eval` 是集中式实验工具；本文确定长期职责，不表示包内评测或统一发现机制已经实现。
>
> 关联：[`IR JSON-Schema 产物设计`](./schema-design.md) · [`Bench 与开发者性能实验室设计`](./bench-design.md)

## 1. 定位

retikz 的 AI 友好性不仅是 schema 合法、API 可调用，还包括 LLM 能否理解能力边界、选择正确表达，并组合能力完成真实绘图任务。

语义评测采用“用例就近、执行集中、与普通单测分开运行”的原则。包内测“这项能力会不会用”，跨包测“这些能力能不能组合起来完成任务”。

## 2. 检查层次

| 层次       | 核心问题                             | 典型检查                                                                |
| ---------- | ------------------------------------ | ----------------------------------------------------------------------- |
| 普通单测   | 实现是否遵守确定性契约               | schema 接受与拒绝、默认值、解析与编译结果                               |
| 能力级评测 | LLM 能否理解并正确使用某项能力       | 根据意图选择正确 `kind`，区分相近字段，生成符合 schema 且语义正确的输入 |
| 任务级评测 | LLM 能否组合多项能力完成真实绘图任务 | 绘制包含分组、分支和标签的流程图，检查关系、内容与最终表达              |

能力级与任务级评测分别类比单元测试和集成测试，但不继承普通单测的确定性假设。模型输出会波动，评测结果需要保留运行条件与失败证据。

“schema 是否好理解”应通过选择准确率、必要字段遗漏率、语义错误等可观察行为衡量，不以模型自述“容易理解”作为通过依据。schema 能否解析由普通单测保证；LLM 能否根据 schema 正确表达意图由能力级评测验证。

## 3. 归属与执行

### 包内能力级评测

能力所属包维护自己的评测用例与判定要求，与实现和公开契约一起演进。用例按语义能力组织，不按每个私有函数、展示变体或 demo 建立一套评测。

包内使用独立 `evals/` 表达评测用途，与 `src/`、`tests/` 区分；不以含义宽泛的 `_llm` 混放评测、提示词工具和 Agent 指令。评测资产不进入发布包，也不让产品运行时依赖评测设施。

### 统一评测平台与跨包任务集

`apps/eval` 同时承担两个职责：

- **统一执行平台**：运行包内与跨包评测，集中管理模型接入、运行上下文、调用预算、结果记录与比较报告。
- **跨包任务集**：维护面向真实用户目标的绘图任务，验证多项能力组合后的整体效果，不复制包内的全部细粒度检查。

用例靠近能力不意味着执行设施也分散。功能包负责“什么算正确”，平台负责“怎样运行和比较”；各包不各自维护模型 SDK、鉴权、重试与报告系统。普通单测默认不调用模型，模型评测由独立入口显式运行。

## 4. 判定原则

语义检查不等于 LLM 判分。能通过程序确认的事实优先使用确定性检查；LLM 只补充难以完全形式化的理解与表达质量判断。

| 判定面     | 主要证据                                               |
| ---------- | ------------------------------------------------------ |
| 可执行性   | 输出解析、schema、编译与引用合法性                     |
| 语义正确性 | 高层 IR 或公开语义产物中的关系方向、分组归属与数据映射 |
| 表达质量   | 最终图形的几何与视觉结果，必要时增加视觉 LLM 评审      |

文字、图元或箭头存在不等于语义正确。例如要求 A 指向 B，仅检查 A、B 和一支箭头无法排除方向反转。判定应围绕任务要求，不强制结果与某份标准 IR 的 ID、数组顺序或布局完全相同。

评测上下文应对应真实使用者可获得的 schema、文档或示例；期望答案与隐藏判定要求不作为额外提示泄露给生成模型。比较模型或版本时记录并控制上下文、生成参数、判定规则及重复次数，区分模型生成失败、库执行失败和评测设施失败，不以单次总分掩盖错误来源。

## 5. 用例收敛

每个长期用例应保护一个明确的语义失败模式，优先代表性能力、关键组合与真实回归，不按配色、措辞或展示形式无限枚举。

同一语义要求可同时检查参考输入与模型生成结果，用于区分能力实现问题和模型使用问题。检查器本身需要少量已知正确与已知错误的样本校准，尤其要确认反向关系、遗漏内容等错误确实会失败；模型评分应附具体证据，而不是只有总分。

稳定用例与判定要求纳入版本管理；运行报告、生成产物与临时探索默认放在现有 ignored 目录。普通单测继续承担确定性回归守卫，语义评测不替代它，也不因模型单次波动默认阻断普通单测流程。

## 6. 同类实践参考

- [Evalite](https://github.com/mattpocock/evalite)：以 `*.eval.ts`、数据、任务与评分器组织 TypeScript 评测，提供接近单测的书写方式。
- [DeepEval](https://github.com/confident-ai/deepeval)：将语义判定与测试式断言结合，支持 LLM 应用评测。
- [Pydantic Evals](https://ai.pydantic.dev/evals/)：分离用例、被测任务与评估器，组合确定性检查和 LLM judge。
- [Promptfoo](https://github.com/promptfoo/promptfoo)：集中编排任务、模型和断言，比较不同运行配置。

以上用于参考组织原则，不决定 Retikz 必须依赖某个框架；具体接入与执行契约另行设计。
