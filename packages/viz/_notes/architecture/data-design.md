# Data 数据模型与外部计算契约设计

> **状态：整体设计草案。** 本文确定数据接入、模型与计算执行的长期边界；外部执行契约尚未实现，具体 API、协议格式和交付计划由后续 ADR 决定。能力归属遵循 [Data 能力完备设计](./data-capability-complete.md) 与 [全仓能力设计](../../../../notes/architecture/capability-design.md)。

## 1. 目标与接入方式

`@retikz/data` 为 Plot、Table 等宿主提供统一的数据模型与计算语义。用户可以独立使用模型能力，选择由 Retikz 或第三方引擎处理数据；使用 Retikz 可视化不要求把数据库全量明细交给前端，也不要求在后端运行 Retikz 的计算实现。

| 接入方式              | 计算声明         | 计算执行                       | 宿主收到的内容                 |
| --------------------- | ---------------- | ------------------------------ | ------------------------------ |
| 原始数据直接接入      | 无分析计算声明   | 无分析计算                     | 原始行与对应数据模型           |
| 第三方处理后接入      | 应用或第三方声明 | 第三方引擎                     | 处理后的行与结果数据模型       |
| Data 处理后接入       | Data transform   | Retikz 本地实现                | 处理后的数据视图，可选 lineage |
| Data 声明并由外部执行 | Data transform   | 实现外部计算契约的引擎 adapter | 经契约校验的结果与可选 lineage |

前两种具有相同的宿主接入形态；宿主消费当前结果，不需要知道结果此前是否经过计算。第三、四种共享计算语义与输出模型，区别在于执行位置和实现。上述分类是使用方式，不引入必须配置的模式枚举。

“直接接入”指不执行分析变换，仍需完成字段解析、值归一化，以及宿主的比例尺、布局与绘图计算。可用功能由输入结果是否满足宿主需求决定。

## 2. 数据模型与结果边界

数据模型描述当前数据集的逻辑字段、测量类型、解析格式与类别顺序；数据引用只标识宿主注入的数据集，实际数据保持在可视化 IR 之外。模型不描述数据库连接、业务实体、权限或查询实现。

每个处理阶段都对应自己的结果模型。变换保留、增加或替换字段的语义复用现有 Definition 的 output model，不能把源表模型直接当作聚合后结果的模型。字段类型证据由模型、Definition 或有效观测建立，不仅凭引擎返回的字段名推断。

外部计算可以只交付授权范围内的绘图结果。分组键与结果粒度属于结果身份的必要语义；只有消费方需要区分完整、分页或抽样结果时，才附带相应范围信息。查询引用、数据版本和回查句柄按消费需求提供，不重复保存可推导的索引或缓存 key。

模型与结果校验不能证明查询在业务上完整或统计上正确。引擎和宿主负责执行语义与数据范围；Plot 等宿主只基于收到的结果推断视觉范围，需要全局比例尺或完整类别时由宿主显式提供。

## 3. 职责划分

| Owner               | 拥有的责任                                                                                                        |
| ------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `@retikz/data`      | 模型与字段语义、transform / statistics 声明、输出模型推导、执行能力与结果校验契约、通用 lineage；提供本地计算实现 |
| 外部引擎 adapter    | 声明支持的操作与语义，将 Data 计划编译为目标 DSL / SQL 或引擎调用，并把结果适配为 Data 可消费的形态               |
| 应用或服务宿主      | 数据源与查询授权、连接与凭据、请求调度、取消与过期结果处理、缓存，以及结果向可视化模块的注入                      |
| Plot / Table 等宿主 | 消费已准备的数据与模型，完成自己的视觉语义、布局、定位与 lowering                                                 |

Data 拥有引擎无关的协议，不拥有 SQL 方言、数据库驱动、分布式调度或业务数据源 SDK。adapter 的具体包组织后续决定，Data 不反向依赖引擎。依赖 Plot 视觉语义的变换仍由 Plot 拥有，不因可外部执行而迁入 Data。

## 4. 外部计算契约

```text
数据引用与输入模型 + 有序 Data operations
  -> 根据 Definition 推导输出模型与语义要求
  -> 核对目标 adapter 的执行能力
  -> 编译为目标 DSL / SQL 或引擎调用
  -> 执行并接收结果
  -> 校验结果结构与类型，建立可消费的数据视图
  -> 注入 Plot / Table 等宿主
```

契约围绕三个部分组织，先确定语义，不预先固定序列化格式或 API 名称：

- **计算计划**：JSON-safe 的数据引用、输入模型与有序 operations，复用现有 schema / Definition 语义，不建立另一套 SQL 专用 Data IR。数据源的实际绑定由宿主完成。
- **执行能力**：adapter 明确声明支持的操作、配置与语义约束。内置与自定义 operation 使用同一匹配机制；自定义 JavaScript 回调不因可注册就自动具有外部表示，缺少明确外部实现的能力只能本地执行。
- **执行结果**：返回可适配的数据、实际输出结构及必要运行信息。Data 在外部结果入口依据预期输出模型校验一次，再交由既有宿主路径消费；不另建平行可视化 IR 或渲染路径。

跨引擎执行必须保留操作顺序，并明确空值、数值与时间、分组、排序及统计语义。不能等价表达的操作、配置或类型在执行前明确失败；结果缺字段、类型不符或无法安全适配时在交付宿主前失败，不能静默丢字段或改写计算含义。

外部执行允许异步完成，绘图继续消费已完成的结果。协议不把网络请求嵌入现有同步 transform 回调或 Plot lowering。宿主负责请求与结果的对应关系，避免过期结果覆盖当前视图。

执行位置由宿主显式选择，不自动回退到前端，不隐式下载全量数据补算。将计划拆成远程与本地两段需要另行明确中间模型、数据范围与语义，不作为本设计的默认执行行为。

## 5. 溯源与数据保密

来源标记与运行链路均按需启用，不是使用数据模型或绘图的前提。本地行级来源继续沿用现有 provenance；外部结果只能记录引擎确实提供的来源证据，不能把结果行序号伪装成数据库明细来源。

远程聚合可以通过查询引用、数据版本、分组键或不透明回查句柄关联来源。Plot 负责在这些信息上补充图元语义；数据库内部 lineage 由引擎提供。协议不要求传输明细、SQL 文本或凭据；是否允许回查及返回什么数据由服务端授权，声明中的数据引用或 metadata 不构成权限。

## 6. 当前基础与后续设计

当前已有数据引用与模型、字段映射与归一化、可省略的 transform、本地 Definition / registry / pipeline、输出字段模型，以及可选 provenance / lineage。前三种方式可以组合现有能力使用；普通 Plot 接入仍会执行字段准备，不支持直接跳过整个 Data 处理路径。

第四种仍缺少统一的执行能力声明、计划编译与异步结果交付契约。后续 ADR 应细化跨引擎语义、输出结构与类型校验、失败行为、扩展机制及宿主接入，并用同一组可观察输入输出与反例验证本地和外部实现的一致性。具体计划不进入本文。

## 7. 成熟设计参考

- [Substrait](https://substrait.io/)：以跨语言计算计划连接不同执行引擎，支持 [自定义扩展](https://substrait.io/extensions/)。借鉴计算语义与执行实现分离，以及显式描述扩展语义的方式；不直接将完整关系代数系统纳入 Data。
- [Apache Arrow](https://arrow.apache.org/docs/format/Columnar.html)：区分数据类型、内存表示与传输格式。借鉴结果模型与物理载体分离；协议不强制使用 Arrow，也不把它视为计算计划。

现有行数组继续作为可用的宿主输入。是否增加 Substrait、Arrow 或特定 SQL adapter，由具体需求与后续 ADR 决定，不为潜在引擎预建配置层。
