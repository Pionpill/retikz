# Showcase 文档写法

## 核心原则

Showcase 的目标是展示和解释功能，让读者理解“这个能力解决什么、如何阅读结果、应观察什么”。真实数据或真实使用场景是达成目标的手段，不是文档主角；数据背景只讲到足以理解功能。入口和基础示例还必须优先服务最广泛的读者，不以特定行业兴趣作为理解前提。

先读 [`docs-doc-principle`](../docs-doc-principle/SKILL.md) 和当前页型 skill。使用 controls 或多文件数据时，再按 principle 加载 `docs-doc-control` 与 ComponentPreview 契约，不在本 skill 重复页面结构和预览规则。

## 展示尺寸

Showcase 的完整 demo 默认设置 `preview.size: 'xxl'`，让读者能直接阅读成品的结构、数据和编码。只有内容本身简短且更小尺寸不会损失可读性时，才降低档位；示例选择缩略卡片不受此约束。

## 成品基础用法

成品或复合组件页的首个 example 默认是“基础用法”。只传可运行的必要配置，不使用 controls 或 presets；根组件已经提供完整配置入口时，统一在根组件传入数据与配置，不额外展开等价 declarations。

基础用法的 description 必须说明这是最简配置、可以切换到 IR 查看配置项，以及配置简单时只需在根组件传递。最简 authoring 仍须保留成品原生支持的 `title`、`subtitle`、`source` 或等价叙事元信息；出现可见文案时按语言拆分 demo，共享语言无关的数据文件。数据型基础示例应使用独立于后续进阶示例的静态数据；Chart Point 一类图表默认使用约 100 行记录，只映射该图型的必要数据角色，不引入 series、facet、颜色分组等进阶逻辑。类别逐项占用独立行或列时，以真实预览中图元和标签不重叠的最小充分样本为准。

## 先定功能，再选载体

写 demo 前先用一句话定义读者收获：

> 读者通过观察 `<结果>`，理解 `<功能能力>`。

再选择最能暴露该能力语义的载体：

| Showcase 类型                              | 默认载体                       |
| ------------------------------------------ | ------------------------------ |
| 图表、表格、统计等数据型成品               | 可追溯的真实数据               |
| Diagram、Notation、Standard 等非数据型成品 | 可识别的真实使用场景           |
| 底层几何、错误边界、固定解释图             | 为单一机制构造的最小数据或场景 |

真实不等于庞大。截取能展示功能的最小充分样本，优先提交静态快照，不让文档依赖运行时远程请求。确认数据允许随仓库分发；需要时记录许可或访问时间。

### 基础示例优先普遍性

入门页、主 Preview 和默认候选优先选择人口、地理、时间、年龄或预期寿命、收入、教育、气候、公共健康等普遍议题。数据主题应满足：无需行业知识即可理解，指标能用一句话解释，单位熟悉或能就近说明，关系不会因文化背景而失去意义。

汽车、证券、专业医疗、专业体育等领域数据只有在功能本身属于该领域，或作为后续进阶变体时使用，不作为跨模块基础能力的默认入口。涉及年龄、收入等个人属性时，优先使用合法公开的国家、地区或时间聚合数据；不要为了“贴近生活”引入隐私、代表性或敏感推断问题。

## 数据与场景契约

- 使用有业务语义的字段名、类别和单位，不用整齐的 `x / y / value` 序列代替真实关系
- 选择能显露目标能力的数据特征，如相关性、分组重叠、异常值、密度、排序、缺失值或层级关系；不要让多个编码只是重复同一信息
- 保留理解功能所需的上下文，同时删除与功能无关的字段和背景介绍
- 公开采样、筛选、清洗、去重、缺失值处理、单位换算和派生字段；这些处理不得改变要展示的关系
- 合成、模拟或人工构造的数据必须如实标注，不得包装成真实观测数据

## 外层功能说明与图内叙事

Showcase 外层的 `title`、`description` 和 `preview.caption` 只说明本例要展示的能力、编码和可观察的交互，不用具体数据主题命名。例如使用“颜色与对数变换”，而不是“收入与预期寿命”。

具体场景的主题、范围、单位、时间、数据处理和来源属于成品自身的 `title`、`subtitle`、`source`。当 Chart 或其它成品具备这些原生能力时，必须在成品内部渲染；能力尚未提供时，不以 Showcase 外层文案替代。

## 成品叙事元信息

一个离开正文仍能读懂的成品至少回答三件事：

| 元信息     | 内容                                 |
| ---------- | ------------------------------------ |
| `title`    | 主题、问题或读者可观察的结论         |
| `subtitle` | 范围、时间、样本、单位或方法         |
| `source`   | 数据集或场景出处，以及影响理解的处理 |

被展示的组件具备原生 `title`、`subtitle`、`source` 或等价能力时，必须通过组件自身渲染，不能只写在外围 MDX、caption 或 Preview 标题里。组件没有该能力时，才由页面承载，并明确这不是组件原生输出。

## 示例

展示 Scatter 的位置与颜色编码时，可使用 Gapminder 或同等权威来源的国家级公共指标静态快照：

- 功能目标：比较两个连续变量，读取整体关系、大洲重叠和异常国家，颜色只表达大洲或地区
- `title`：人均收入越高，预期寿命通常越长
- `subtitle`：同一年各国样本；横轴为人均收入，纵轴为出生时预期寿命，颜色表示大洲；收入使用对数尺度
- `source`：Gapminder 或 World Bank 公共指标；注明数据年份、指标口径、地区映射、缺失值处理和快照版本

这里只解释足以读图的数据语义；数据集历史不扩写成正文主线。

## 完成检查

- 不看数据说明时，读者仍能说出本例展示的功能
- 基础示例无需特定行业知识或个人兴趣即可理解
- 数据或场景能触发该功能的关键语义，不只是让成品“有内容”
- 标题、副标题和来源能让成品独立成立，并优先走组件原生能力
- 来源可追溯，所有影响理解的数据处理已公开，模拟数据已明确标注
- zh / en 的功能结论、范围、单位和来源语义一致

## 常见错误

- 点、行或节点能渲染，就把示例当成功能展示完成
- 用汽车、金融或其它领域内部指标作为基础能力的默认入口
- 为了讲数据背景，把 Showcase 写成数据集介绍文章
- 用少量整齐样本制造完美趋势、完全分组或重复编码
- `source` 只写“公开数据”或“示例数据”，无法追溯和复现
- 组件已有叙事元信息能力，却只在外围正文补标题和来源
- demo 运行时请求第三方数据，导致构建、测试和离线阅读不稳定
