# Docs Figure Logic

本 skill 用于给“功能如何实现”配叙述性逻辑图。先读 [`docs-figure-contract`](../docs-figure-contract/SKILL.md)，本文只补充实现逻辑图的风格方法：如何抽象节点、组织箭头、处理 path label、区分 stroke / fill、安排布局。

## 目标

逻辑说明图要像论文里的概念图：结构清楚、排版规整、标签短、箭头语义稳定、颜色克制。不要蒸馏具体模板，不要把某张图的节点数量、形状组合或代码结构照搬下来；要蒸馏可复用的绘图语言：细描边、同色浅填充、灰色主线、少量语义色、贴边短 label、宽松网格布局。

一张好逻辑图回答三个问题：

- 入口是什么？
- 中间经过哪些稳定角色？
- 输出、反馈或副作用在哪里？

不要把所有实现细节画进去。图只保留解释当前小节所需的主链路、关键分支和一两个约束点。

## 工作流

1. 读正文目标：明确这张图要解释的一个机制，而不是整个模块。
2. 读相关代码：找入口、核心状态 / IR、转换步骤、注册 / provider、输出边界。
3. 抽象角色：把文件名和函数名归并成读者能理解的稳定角色，如 `Input`、`Spec`、`Registry`、`Compiler`、`Scene`。
4. 规划主链：先确定唯一阅读方向，再放辅助分支、状态或源码注释。
5. 固定视觉编码：同一页内相同角色使用相同节点、箭头、颜色和 label 规则。
6. 写 demo：用 retikz 自绘，遵守 `docs-figure-contract`。
7. 回看正文：图前后文字要解释图中每个非显然节点。

## 节点风格

节点优先表达“角色”，不是文件、函数或临时变量。

| 节点类型     | stroke / fill                                     | 使用方式                                                                 |
| ------------ | ------------------------------------------------- | ------------------------------------------------------------------------ |
| 主流程角色   | 语义色 stroke + 同色低透明 fill                   | 用于处理阶段、核心数据结构、稳定边界；节点标题短而具体。                 |
| 当前强调角色 | P2 色 stroke + 同色低透明 fill                    | 只标出正文正在解释的一个关键节点；后续强调色按 contract 的 P2 顺序调用。 |
| 辅助角色     | `gray` / `lightgray` stroke + 同色低透明 fill     | 用于默认值、配置、缓存、源码位置、旁路输入；不抢主链路。                 |
| 分组边界     | `lightgray` 虚线 stroke + 无填充或极浅灰透明 fill | 用于 layer、runtime、adapter 等范围框；只框范围，不当作独立步骤。        |
| 纯文本注释   | `stroke="none"`、`fill="none"`                    | 用于文件路径、约束、短注释；文字用 `gray`。                              |

彩色节点的 fill 必须来自 stroke 的同色系弱化：降低 opacity / saturation / lightness 后形成浅底，而不是换成无关背景色。节点内部文字分两级即可：标题用默认色，补充说明用 `gray` 和更小字号。不要在一个节点里塞三行以上解释；放不下说明时，拆成正文。

节点形状承担语义：圆角矩形表示处理或组件，圆 / 小圆表示抽象单元或操作点，菱形表示判断，圆柱表示存储，虚线外框表示分组边界。不要只靠文字区分不同角色。

## 箭头风格

箭头只表达可命名的关系。每条箭头都必须能用一句话说清楚。

- 主数据流 / 控制流：细灰色实线 `arrow="->"`，沿主阅读方向排列；箭头头部小，不抢节点。
- 密集结构连接：使用浅灰细实线，可省略箭头头部，让布局暗示方向。
- 辅助输入 / 依赖：灰色或语义色虚线，进入主节点侧边，不穿过主链。
- 反馈回路：从图外侧绕回状态节点，避免横穿主流程；只有反馈是机制核心时才画。
- 强调路径：用 P2 色细线表达特殊语义，如参数更新、异常 retry、梯度回传；一张图通常只强调一条路径或一类回路。
- 禁止无语义连线：装饰线、重复箭头、为了对称而加的箭头都删掉。

箭头颜色跟随语义，而不是跟随节点外观：主链默认灰色，辅助线退后，彩色线只用于读者必须区分的通信、依赖、异常或反馈语义。危险 / 成功语义才使用 `red` / `green`。

## Path Label

path label 是“关系名”，不是解释句。

- 优先写动词、短名词或数学符号：`parse`、`resolve`、`features`、`retry`、`θ`、`∇θ`、`ŷ`。
- 只给关键边加 label；如果每条边都需要 label，说明节点命名或图形结构不够清楚。
- label 用小字号，贴近路径中段或转折后留白处；中性路径用 `gray`，彩色语义路径的 label 跟随 path 色。
- label 不压线、不压节点、不和箭头头部争位置；必要时把路径改成折线给 label 留空间。
- 同一图内 label 的位置规则一致：主链 label 多放在线上方，辅助线 label 放在线旁或下方。
- label 不加背景框，不放进节点里；需要被强调的中间语义可以实体化成小节点。

不要把文件路径、函数全名、完整条件表达式写进 path label。这些信息放灰色注释或正文。

## Stroke / Fill 区分

逻辑图主要靠同色 stroke / fill、线型和位置表达结构。fill 不是装饰色块，而是 stroke 色的低透明浅底。

- 主节点默认有浅 fill：`fill = stroke color + low opacity`，让节点形成柔和面。
- 中性节点用 `gray` / `lightgray` 的浅 fill，视觉层级低于彩色语义节点。
- 分组或背景区域优先用虚线浅灰边框，可无填充或极浅灰透明 fill。
- 强调用 stroke、path stroke 或同色浅 fill，不用高饱和 fill。
- `stroke="none"` 只给纯文本和无需边界的注释使用；有角色边界的节点必须保留 stroke。
- 同一语义不要同时改 stroke、fill、字体颜色和线型；一次只改一两个维度。

## 布局规则

布局先保证阅读顺序，再追求紧凑。

- 只保留一个主阅读方向：左到右或上到下。
- 主节点落在同一条水平 / 垂直基线上，间距相等。
- 辅助输入放主链上方或下方，状态 / 输出放主链末端附近。
- 回路和旁路沿外侧走线，不从节点之间穿插。
- 同层主节点控制在 3-5 个；超过 5 个时合并为组或只画关键边界。
- 文字 label 与节点保持固定间距，不靠手感贴边。
- 页面宽度不足时优先改成纵向主链，而不是缩小字体。

## 抽象规则

- 用稳定概念命名节点，不用临时变量名。
- 文件路径只放在第二行或灰色注释中，不要抢主链路。
- 如果两个阶段只是实现细节连续调用，合并成一个节点。
- 如果一个节点既是数据又是处理器，拆开或在正文说明；不要让一个标记承担两个概念。
- 如果辅助分支无法解释当前段落，删掉它。

## 逻辑图检查

画完后逐项检查：

- 删除任一节点后，图是否仍能说明当前小节？如果能，删掉它。
- 每条箭头是否能用一句话解释？不能就删或改。
- 是否只有一个主要阅读方向？
- path label 是否短、少、位置稳定？
- stroke / fill 是否有清晰分工，而不是装饰？
- 是否有且只有一个主强调点？
- 正文是否解释了图里的缩写、边界和反馈？
- 是否仍遵守 `docs-figure-contract` 的 `hideCode`、id 连线、响应式和验证规则？
