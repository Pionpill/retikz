# 原理页共同写法

## 共同写作要求

- 先用通俗语言建立含义，再引入概念、数据结构与函数，最后解释关键分支；不靠后文或源码链接补齐基础逻辑
- 新概念首次出现时用“名称：通俗职能与作用”的列表集中介绍，再说明协作关系；只引入当前小节所需概念，解释不依赖尚未说明的术语
- 解释关键决策与中间数据，不逐行翻译实现；接口、默认值与分支以当前源码为准，不以 ADR 计划替代
- 区分初始化与逐次执行、同步数据流与异步生命周期；涉及缓存时说明作用域及跳过的处理，涉及错误时说明终止范围、部分结果与重试语义，没有的机制不强凑
- 每个机制小节就近放 `SourceLinks`，独立 H3 也有自身入口；链接指向入口、关键分支或产物契约，标签说明阅读重点，不只链接 demo 或全部堆在页尾

## 配图与源码锚点

配图遵循 [figure-contract](../../docs-doc-principle/references/figure-contract.md) 与 [figure-logic](../../docs-doc-principle/references/figure-logic.md)。难以用文字理解的分支、转换、时序、层级与协作关系就近配局部图：先解释含义，再用图表达关系，图后收束结论。每图只回答一个问题，不按章节数凑图或为单个定义添加装饰图。

默认按“具体问题 → 实例效果图 / demo → 对照图中元素逐步解释 → Flow 实现流程”组织。图前说明看什么，图后沿同一个例子说明为什么；空间、方向、比例或状态差异必须在图上可见，不能只在文字中声称。读者仍看不懂时，优先补可观察的对照和读图步骤，不继续增加术语或抽象流程框。

内部函数、类型与对象只是实现锚点，不意味着公开导出，不进入公共 API 表，也不为展示源码修改 export。图中成员名使用可搜索的准确拼写，下一行解释作用；长名称移至就近正文，不编造缩写。区分数据与动作，不把同一次调用重复画成两步。
