# 实现原理页

## 定位与分工

面向已读用法与前置概念、准备理解内部逻辑或结合源码阅读的读者。固定底层难度，适用于包、组件和独立进阶专题。名称、难度与 URL 按 [页型词典](../docs-doc-principle/references/page-contract.md)：完整原理页使用 `mechanism` 与“实现原理 / Implementation”，具体进阶专题使用准确的任务名，如文字测量，不另写“运行原理”“技术原理”等同义页型。

先读 `docs-doc-principle`；配图复用 `docs-figure-contract` 与 `docs-figure-logic`；局部修改按 `docs-doc-review` 自审，新建、重写或大范围重构后按通则派遣 1 个 fresh、只读 Luna 做读者视角评审，仅看文档与页面内图示，不读项目规范或源码，并直接提出理解上的质疑。不重复安装教程、完整 API 签名或 schema 字典。概念心智模型归 `docs-doc-concept`，设计取舍真源归 ADR。

## 固定骨架

1. 开篇：简述阅读前提并链接前置页，明确追踪对象、一次执行的范围、输入、输出和停止边界
2. `## 整体流程`：简图建立输入到输出的完整主线，用稳定语义命名阶段，不展开函数清单
3. 按主线顺序展开阶段 H2：每节解释一次有意义的数据变化，不按源码目录或 helper 数量分章
4. 必要的跨阶段机制：仅在不能就近解释时独立成节，说明它与主线的接入点
5. `## 完整实现流程`：详细图沿用总览阶段，补关键代码成员、数据产物和必要分支；图后给简短源码阅读顺序
6. `## 延伸阅读`：用 LinkedSections 链接相关主题，不在流程图后散列另一种收尾导航

原理主线的整体流程与完整实现流程固定，中间阶段数量与标题服从真实机制。进阶专题聚焦自身执行范围，不重复整个包的调用链。简单主链保持紧凑；复杂支路在所属阶段局部展开，末图仍是可读的源码导览，不是完整调用图。

## 阶段讲解

从读者视角循序渐进：先用通俗语言讲清基础逻辑，再引入概念名称、数据结构和相关函数，最后展开关键分支与实现细节。“已读前置文档”不等于熟悉内部模型；本页主线依赖的概念应在首次使用前简要建立含义，不能靠后文、源码链接或函数名让读者自行补齐。例如先说明 selection 是“声明想观察哪些对象及其选项的规则”，再解释谁解析它、何时匹配实例。

每节应让读者知道输入是什么、何时由谁触发、关键处理及其原因、产物交给谁。这些是检查项，不强制拆成固定 H3。必要时补充不变量、失败结果与停止条件。

新概念首次出现时，先用列表逐项写“名称：通俗职能与作用”，再解释它们如何协作、对应哪些函数；一组相关概念集中介绍，不埋在长段落里。只介绍当前阶段需要的概念，不前置整页术语表；列表中的解释不得依赖尚未说明的新术语。

- 选一个最小实例贯穿主线，展示各阶段真正变化的字段；不反复倾倒完整对象
- 区分初始化、每次调用、每个对象和批次完成；同步数据流、异步生命周期与依赖关系不能混成连续执行
- 缓存说明命中后跳过哪些阶段及其作用域；错误说明终止范围、是否有部分结果、是否重试；没有的机制不强凑
- 解释影响理解的关键决策和中间数据，不逐行翻译实现；接口、默认值与分支以当前源码为准，不以 ADR 的计划状态替代
- 每个机制小节就近放 `SourceLinks`，独立 H3 机制也有自身入口；链接指向入口、关键分支或产物契约，标签写清进去看什么，不只链接 demo 或全部堆在页尾

## 图与内部标识符

总览图回答“整体如何走”，详细图回答“沿哪些成员读实现”。阶段名称与阅读方向应能对应，第二张图必须增加源码定位或时序信息，不只重复第一张图。

首尾流程图不能代替正文配图。实现原理涉及理解门槛较高的内部机制，应在讲解中穿插局部逻辑图：关键分支、阶段间数据转换、调用时序，以及容易混淆的概念职责、层级或协作关系，必须在对应段落就近配图，不以连续文字或函数清单代替。先用通俗文字或概念列表建立含义，再用图说明关系，图后收束结论；每图只解释一个问题，不按章节数凑图，也不为单个定义添加装饰图。具体绘制遵循 `docs-figure-contract` 与 `docs-figure-logic`。

内部函数、类型与对象可作为实现锚点出现，必须明确是内部成员，不意味着公开导出，也不进入公共 API 表。节点或边上的成员名保持可搜索的准确拼写，下一行简要解释作用；不为展示源码修改包的 export。

数据对象与处理动作要区分；函数可作阶段节点，也可作转换边的两行 label，按真实关系选择，不把同一次调用重复画成两步。长名称放不下时调整布局或移至就近正文，不能缩写成源码中不存在的名字。

## 完稿检查

- 只看首图能否说清输入、输出与职责边界；正文顺序是否与它一致
- 是否能沿同一个实例读完，而不需要提前理解后面的阶段
- 是否先解释概念再使用；是否存在只列术语、函数职责或源码链接，却未讲清基础逻辑的段落
- 正文是否就近配图解释关键逻辑与概念关系，而非只在首尾放图；图是否补充关系或时序信息，而非重复文字
- 初始化与逐次执行、筛选与最终匹配、局部失败与整体失败是否区分
- 每节源码是否直接支撑解释，内部成员是否与公共 API 分开
- 末图是否覆盖主线终点，并让读者知道从哪个入口开始读
- zh/en 的阶段、例子、图与链接是否一致；按文档通则执行静态检查及真实页面验证
