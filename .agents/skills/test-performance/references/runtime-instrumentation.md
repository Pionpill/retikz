# 渐进式运行时插桩

用于已授权范围内的性能诊断与优化；采样、预算、优化轮次及报告遵循 [主 skill](../SKILL.md)。目标是在真实调用链中定位可行动的成本来源，而不是通过阅读代码猜测热点。Vitest / Tinybench 负责基准统计，profiler 与插桩负责成本归因，最终无插桩对照负责验证收益。

## 运行前固定边界

- 固定目标场景、输入规模、首次执行 / 缓存复用状态、正确性不变量、计时边界、消费预算与采样协议；记录源码及参与依赖、fixture、配置和运行环境身份
- 保存无插桩原实现基线；复用既有结果前核对可比性。原实现与候选使用相同运行器，不把切换加载器、构建模式或输入带来的变化算作优化收益
- 诊断开始前在已有 ignored plan / report 中记录诊断运行上限与停止条件；已有计划有约束时沿用，否则默认最多 6 轮诊断运行，每轮包含一次当前观测方案的受影响场景集合。计数与计时分开跑分别计轮，不因上下文恢复重置。达到上限且证据不足时交付未定位项，不盲改或无限细分
- 用户已要求自主诊断并优化时，范围内的插桩、细分、修复和验证连续执行，仅汇报进度和最终结果；范围扩大、公开契约变化、用户改动冲突或外部阻塞按仓库规则处理。此模式不授权 commit / push / publish，也不授权放宽预算或更新基线

## 临时代码隔离

1. 按主 skill 的 Worktree 隔离与合回规则，必须在任务专用隔离 worktree 的真实源码上插桩，可使用 detached worktree，不为实验提交或推送。新 worktree 不自动包含 dirty / untracked 内容；按明确文件清单重建所需有效快照，并核对源码、依赖解析和配置与原场景一致，不能误测 HEAD 或另一工作区的依赖
2. 插桩前保存受影响文件快照与原始 diff，分别记录插桩改动和优化改动；小范围也不例外回到原工作区插桩。不得用整文件恢复、hard reset 或盲目反向 patch 清除与用户工作或优化重叠的修改
3. 不把函数复制到 ignored 目录作为真实流程的替代测量；副本仅用于算法实验，结论必须回到真实入口验证。临时 runner、trace、补丁、清单与报告使用已有 ignored 目录；临时 Vitest case 遵循 `tests/_scratch/` 与 `pnpm temp:test` 规则
4. 创建实验 worktree 前记录原工作区路径、原分支与有效源码快照。任务完成后交付撤除探针后的最终差异与验证结果，保留 worktree 等待用户确认处理完成；确认后必须将已验证的最终改动合回原工作区的原分支，不能仅留在实验 worktree 或报告中。没有有效改动时明确报告无改动可合回
5. 合回前核对原分支与用户新增改动，仅应用相对实验初始有效快照的优化差异，不重放原有 dirty 内容或整文件覆盖。默认以未提交改动合回，不自动 stage / commit / push；原分支已切换或有无法安全合并的冲突时保留实验结果并报告阻塞，不擅自切换分支或覆盖用户工作
6. 合回后检查 diff、探针清理状态及必要的受影响验证；有效源码与被测快照不同则在隔离 worktree 补齐性能验证，不能沿用实验收益结论。用户确认完成、最终改动已合回、证据已保存且没有未迁移的有效改动后才清理实验 worktree，不强制删除未知内容；失败退出也须撤除实验中的临时探针并报告未合回项

## 渐进定位

1. **粗定位**：可先用 Node / V8 CPU profiler 采样调用栈；已有明确阶段边界时也可先插桩。初次只设 3–5 个语义区域，例如准备、遍历、计算、组装、提交，另记完整操作耗时
2. **细分热点**：按累计成本、调用次数和对完整操作的贡献选择主要区域，继续按职责拆分；不是按代码行数机械二分。保留父级与完整操作观测，避免局部优化掩盖成本转移；多个热点分别跟踪
3. **检验假设**：区分单次昂贵、重复调用、缓存未命中、命中后仍做全量工作、分配 / GC、等待及运行器开销。用调用次数、输入量、访问量和缓存计数支持解释，不以一个耗时占比断言根因
4. **形成修复目标**：只有定位到具体区段、实际负载下的成本与可验证机制后才实施候选；源码阅读用于解释测量与选择方案。已能行动、开销过大或达到诊断上限时停止细分，明确记录证据强度与未解释成本

一次细分诊断不算优化轮；实施或替换候选并进行验证才计入主 skill 的最多 3 轮优化。不得用“继续诊断”规避优化轮次限制。

## 记录与测量约束

- 优先复用 Node `perf_hooks` 的 `performance.now()`、mark / measure 或 profiler；不先建设通用追踪框架，不向公开 IR / API 增加诊断字段，不引入未获授权的工具依赖
- 每个区域记录稳定名称、父区域、源码位置、调用次数、累计耗时与按相同粒度计算的分布；同时保存完整操作样本、输入规模、缓存 / 访问计数、运行及源码指纹。预热与正式测量分离
- 同步嵌套区域按实际调用配对计算 inclusive / self time；仅扣除不重叠的直接子区间，不相减父子区域各自的 P50 等汇总统计量，也不重复累加重叠成本。递归、并发和异步需要独立调用标识或轨道；不能把跨 `await` 的墙钟时间解释为 CPU 时间
- 高频循环优先包围整段计时，细粒度计数与计时必要时分开运行；热路径不输出日志、不写文件、不序列化、不捕获调用栈。内存聚合后在计时区间外导出，清理 mark / measure 或限制缓冲，避免记录自身持续增长
- 比较无探针与粗探针完整操作耗时，检查排序和分布是否被观测明显改变；扰动影响判断时减少探针或改用采样。不得扣除估算探针开销后宣称得到精确延迟；插桩运行只用于诊断，不替代验收基准
- Vitest 模块运行器可能引入导出 getter 等额外成本。核对安装版本、真实模块解析路径与当前产物；必要时用原生 Node ESM 复核。跨运行器结果单独报告，不能直接作为代码前后收益
- 墙钟计时包含 GC、调度与等待；CPU 热点用采样交叉验证，疑似分配 / GC 问题再选择对应运行时工具，不凭时间差直接归因

## 修复与最终验收

1. 保存“现象 → 区段 / 调用链 → 测量证据 → 机制假设 → 候选修复 → 正确性风险”，优先消除已测成本，不扩大到无证据的顺手优化
2. 按主 skill 执行候选与功能验证；删除所有临时探针、包装与诊断 import 后，才运行同条件原实现 / 候选对照，核对最终源码与被测快照一致。初次成本和后续复用、受益与可能退化场景分别报告
3. 波动使结论不明确时，在已授权运行范围内交错复测原实现与候选；仍不明确则不认定收益。按主 skill 保留有效候选、撤回无收益 / 退化项，不用局部插桩收益代替完整流程改善
4. 最终中文报告链接原始数据并列出热点细分路径、确认原因与未验证假设、修复内容、无插桩 P50 对比、辅助均值与预算状态（不展示 P90）、功能验证、保留 / 撤回项、探针清理状态及剩余问题。未运行或未解决如实说明，不把阶段定位包装为根因已确认

## 工具参考

- [Node perf_hooks](https://nodejs.org/api/perf_hooks.html)：语义区域计时、函数观测与直方图；observer 本身也有成本
- [Node inspector](https://nodejs.org/api/inspector.html)：V8 CPU profiler，可生成 CPU profile
- [Vitest 模块运行器开销](https://vitest.dev/guide/benchmarking#module-runner-overhead)：基准环境的可比性限制
- [speedscope](https://github.com/jlfwong/speedscope)：CPU profile 可视化，不负责采集或自动修复
- [Perfetto Trace JSON](https://perfetto.dev/docs/getting-started/other-formats) 与 [AI 分析流程](https://perfetto.dev/docs/getting-started/using-ai)：区域 / 计数轨迹及 SQL 分析；Node 侧仍需生成适配轨迹，不假定其录制器直接支持本机 Windows / Node 场景

工具按定位需要选用，不要求全部安装或每次同时采集；简单区域统计足够时不强制引入 trace 平台。
