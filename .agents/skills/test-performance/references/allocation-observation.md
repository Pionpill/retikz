# 单次分配观察

- 算法内存列记录“估算单次分配”：V8采样估计的本用例正式累计分配字节数 / 实际调用次数，按 B/op、KiB/op、MiB/op 展示。不得用 worker 的 `heapUsed` / RSS、结束堆总量或其除以轮次冒充单次成本；GC前后存活差值也不等于累计分配量
- 通过共享命令的 `--memory` 及 `defineBenchmark` 接入：命令在运行时注入 projects，全部耗时场景先完成，再在独立 project 重新 setup 执行分配阶段；使用 `sequence.groupOrder` 串行分组，不在耗时采样期间启用 profiler 或强制GC。输入、fixture、hooks、断言和报告不进入分配调用栈
- 分配协议由共享 `allocationSampling` 提供：10次预热+100次正式调用，最后一次预热用32KiB间隔粗采样，选择最低128B、目标约4096样本的正式间隔，不额外增加探测调用。开启包含 minor/major GC 已回收对象的采样选项；在停止采样前回收一次，仍统计完整分配，不只统计存活结果。只累计 `runAllocationOperation` 调用子树
- 分配归因边界须验证连续短场景经过JIT后仍可辨识；当前共享工具用仅分配阶段的Proxy apply边界保留调用栈，输入和驱动分配位于边界之外。不能把被内联丢失的标记当作零分配或正常采样不足
- JSON保存估算总字节、正式调用数、预热调用数、有效分配样本数与实际间隔；B/op按需计算。少于16个有效样本显示“无法可靠估计”，不是零分配；API不可用单列，不伪造数值，被测函数异常仍须失败
- reference档保持包括预热、探测和验证在内总共3次算法调用，跳过额外分配阶段；报告分别核对耗时与分配调用数，不将两阶段混作一次100轮，也不对参考档做外推
- 内存观察线统一由共享脚本提供，单次分配超过16MiB且采样充分时给黄色“建议复测”，不在各包单独配置、不从首次实测倒推阈值、不阻断功能、耗时预算或进程退出。本指标仅覆盖JS堆对象分配，不覆盖外部缓冲区、原生或GPU内存；累计分配不等于峰值、常驻占用或泄漏，不自动启动快照分析或算法优化
- 内存接入不自动授权迁移既有耗时预算指标；发现存量判定不符合P50规则时单独确认。未获授权时保留并明确标注原指标，不隐藏旧判定或声称已采用P50
