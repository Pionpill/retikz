# Weave 全量 / 增量编译临时对比

## 触发与产物

仅在用户主动要求比较 Weave 编译性能、生成临时对比报告时执行。目标是评估 Kernel 元素首次编译成本与更新复用收益；暂不生成正式性能单测或 `*.bench.ts`，不新增 package scripts、CI、预算、基线或集成性能应用。

脚本、原始 JSON、报告生成器、中文 Markdown 报告及必要的临时配置，放入已有 gitignore 覆盖的新目录，例如 `notes/reports/<task>/`。先用 `git check-ignore` 确认，不 stage / commit。优先复用现有采样与统计工具；不为一次实验扩展公共测试框架。

运行授权限于明确的比较范围；不自动授权生产代码优化、阶段级 profiling、扩大规模或重复整轮实验。编写本参考文档不触发运行。

## 对比边界

使用当前公开 API，执行前核对入口与参数。以下名称描述本次确立的调用方式，API 演进时跟随实际契约调整并记录：

| 阶段     | Core 全量                   | Weave                                                    |
| -------- | --------------------------- | -------------------------------------------------------- |
| 首次编译 | `compileToScene(scene)`     | 创建 `ReconcilerSession` 并 `mount(scene)`               |
| 更新     | `compileToScene(nextScene)` | 持久会话 `update(WeaveBatch)`，分别测量 `auto` 与 `full` |

- “首屏”仅指首次编译到完整 Scene 就绪，不是浏览器首次绘制；预热后的首次编译不代表冷启动
- 区分 Core 无状态全量编译与 Weave 强制全量批次更新，两者不能统称同一个 full 基线；不得用 `replace(nextScene)` 冒充增量更新
- 只含 Kernel Node、Scope、Path，不含 Composite、文本测量、异步加载、React / Vanilla adapter、宿主 target、DOM 或 SVG / Canvas 渲染
- 首次 Weave 计时包含会话创建与 mount，dispose 在计时外；更新各模式保持独立持久会话
- 输入、批次、预期结果构造与断言在计时外，保留并消费返回结果；计入各实现正常的内部计算与分配
- 记录实际 observers、trace、captureProvenance 等选项；未显式开启来源捕获不等于 Weave 内部没有来源信息构建成本
- 实际元素编译次数通过独立、计时外的 trace 验证；先核对计数字段语义，不将 `visited` 当遍历总数或将复用次数当未触及节点数

## 固定场景

每个场景使用 **N = 100 / 1,000 / 5,000** 个 Node，不套用算法单元基准的百万规模。输入确定、无随机 ID、无文本。

| 场景                          | 结构                                                              | 更新                                                                          |
| ----------------------------- | ----------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| 独立 Node                     | N 个固定尺寸矩形，网格排列                                        | 中间 Node 的 x 坐标移动 3 个单位                                              |
| Scope + Node + Path，局部更新 | 一个 localNamespace Scope，含 N 个相同 Node 与 N−1 条相邻节点连线 | 中间 Node 的 x 坐标移动 3 个单位                                              |
| Scope + Node + Path，范围更新 | 同上                                                              | 切换 Scope 的 `defaults.node.style.fill`，影响全部 N 个 Node，不替换 children |

首次编译仅测两种不同结构。Scope 场景总元素数为 **2N**，包含 Scope；报告同时解释 Node 数与总元素数。该结构只代表一种拓扑，不将其结果推广为所有 Scope / Path 行为。

## 采样与正确性

1. 每个计时单元固定 **10 次预热 + 100 次正式测量**，串行执行，不并发启动构建、测试或性能链路，不因运行慢自动减少轮次
2. 更新在 A/B 两个真实状态之间交替，避免重复相同输入；每轮轮换 Core / auto / full 顺序。首次编译沿用 Core → mount 顺序，报告披露 JIT、GC 与顺序偏差
3. 默认自然 GC，记录 CPU 绑定、系统负载隔离等实际条件，不将未控制的条件写成已隔离
4. 首次编译至少在首轮预热和最后正式样本校验；更新至少在前两轮预热、最后两轮正式样本校验，覆盖 A/B 两态
5. 以 Core 输出为 oracle，对完整输出的 JSON 值做深相等比较；普通对象与 null-prototype 对象的原型差异不算 Scene 内容差异，不删去有意义的字段或错误来使断言通过
6. 默认矩阵共 **39 个计时单元**：首次 2 结构 × 3 规模 × 2 模式，更新 3 场景 × 3 规模 × 3 模式。发布完整报告前确认每单元都有 100 个正式样本，正确性检查与计时外编译次数验证完成
7. 失败或中断保留原始记录，标注未完成范围；不填造缺失值，不将不同运行的部分数据拼成一份完整结果

实验可使用 `tsx` 加载当前源码，但须记录 loader 与命令，不称为原生 ESM 生产产物基线。记录源码提交、相关未提交改动、Node、OS、CPU、内存与采样配置。临时脚本按适用范围格式化、类型检查；工具跳过 ignored 文件时如实报告，不能记为 lint 通过。

## 中文报告结构

按以下顺序生成，表格数据从同一份原始 JSON 计算：

1. **结论**：同时呈现收益、首次成本和更新退化，不仅挑选最快场景
2. **测量边界与方法**：调用入口、计时包含 / 排除项、预热、顺序、正确性与计数方法
3. **环境**：采样时间、源码 SHA、相关 dirty 状态、OS / CPU / 内存 / Node、runner / loader、实际选项、GC 与负载限制
4. **场景**：输入结构、修改方式、N 与总元素数定义
5. **首次编译 P50 表**：场景、Node 数、Core、Weave mount、mount / Core 倍数
6. **更新 P50 表**：场景 / 修改、Node 数、Core 全量、Weave full、Weave auto、Core / auto 加速比、auto / full 实际编译元素数
7. **解释与限制**：编译次数减少不等于整体复杂度降低；该实验不能推导 FPS、绘制耗时或跨机器性能门槛。未做 profiling 时，不把源码推测当已验证耗时归因
8. **完整统计**：每计时单元的正式样本数、均值、P50、P90、最小值、最大值；分位数采用最近秩法，表格注明时间单位，JSON 保留毫秒原始样本
9. **复现入口**：相对链接到执行脚本、原始 JSON、报告生成器与必要配置，给出工作目录及准确的执行 / 生成报告命令

Core / auto 大于 1 表示 auto 更快；mount / Core 大于 1 表示首次 Weave 更慢。自然 GC 与单次本机运行的 P90 只描述本次样本分布，不代表跨运行置信区间。历史实测数字不写成固定预期。

## 重点评估方向

每次报告都评估以下三项，区分实测现象、待验证原因与优化目标；需要新增埋点或 profiling 时另行取得诊断授权。

| 方向               | 必须观察                                                                | 获准诊断后重点检查                                                                                                                                  |
| ------------------ | ----------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| 首次构建成本       | mount / Core 倍数及其随 N 增长的趋势，分别比较独立 Node 与 Scope + Path | 建树、注册表、依赖记录及来源信息是否存在重复工作；区分必要建树成本与可消除开销，不直接把总耗时差归因于某个环节                                      |
| Scope 失效范围     | 局部 Node 修改与 Scope 范围修改的 auto / full 编译数和耗时              | 追踪 Node → Scope → 消费者的失效链，检查 context / compile 来源、依赖粒度、变化比较与传播停止条件；细粒度不足是候选原因，不能仅凭全量重编译断言根因 |
| 单节点更新外围成本 | 固定只改一个 Node 时，实际编译数、总耗时与加速比如何随 N 变化           | 排查全树遍历、集合复制、索引重建和完整 Scene 组装等成本；即使只编译一个元素，也不能据此认定整次更新接近常数复杂度                                   |

大规模独立 Node 的单点更新以相对 Core 全量 **10 倍以上加速**作为用户期望的优化目标，报告实际差距；它不是已实现保证，也不自动成为所有场景的硬门槛。Scope 默认样式变化本就可能影响全部子节点，应与单点变化造成的过度失效分开评价。

默认诊断顺序为：独立 Node 单点更新的外围成本 → Scope 失效扩散 → 首次构建成本，先区分“处理范围过大”与“重新编译过多”。仅有三个规模的总耗时不能证明具体复杂度或瓶颈归属。

## 完成检查

- 核对矩阵、样本数、完整输出一致性、编译次数、比值方向、单位及复现链接
- 报告脚本检查与实验实际完成范围，明确失败、缺口和可信度限制
