# 单元性能基准

以真实消费场景决定输入规模，测量完整且可解释的工作负载。性能报告始终生成，耗时门槛按场景选择；规模上限、采样次数和耗时上限是三个独立概念。

## Weave 临时对比入口

仅在用户主动要求 Weave 全量 / 增量编译性能对比或临时报告时，读取 [Weave 编译性能对比](references/weave-comparison.md)。该流程测量无渲染后端的首次编译与批次更新，脚本、原始数据和报告均放 ignored 目录；暂不生成正式性能单测、bench 用例或 CI 门槛。场景、规模与报告格式以该参考文档为准，不套用下文包级算法的默认规模与接入方式。普通功能开发、验证或仅修改本 skill 不触发性能运行。

## 接入与边界

- 开始性能测试前确认：“得到结果后是否自动诊断并优化？默认不自动优化。”同时说明包、用例、预算、验证范围和轮次上限；当前任务已明确授权时不重复询问。未获明确同意按关闭处理，不阻塞已授权的测试与报告
- 开启自动优化后，授权覆盖[优化闭环](references/optimization-cycle.md)前两阶段的源码诊断、临时插桩、范围内实现、验证、对比及保留/撤回决策；结果出来后连续执行，不再逐阶段或逐轮审批。第三阶段仅授权研究并生成方案，实施须人工确认；不自动授权扩大范围、改变公开契约/预算/基线、调度 agent 或 Git 操作
- 获准自动优化即按 [长任务状态与恢复](../flow-long-task/SKILL.md) 管理连续执行，不因此把任务规模升级为大型。初始计划记录授权和停止条件；中间脚本、插桩快照、原始样本、候选、对比及决策统一保存在 ignored `notes/plans/<task>/` 或就近 `_notes/plans/<task>/`，维护 `TASK_STATE.md` 的阶段、累计轮次和恢复入口；正式报告仍放 reports 目录

- 先读目标包的公开入口、现有基准、实际消费代码及就近规则；正确性契约复用 [test-contract](../test-contract/SKILL.md)
- 优先使用现有 Vitest / Tinybench 链路；包内 `benchmarks/` 与 `tests/` 同级，用例为 `*.bench.ts`。采样、执行辅助和报告工具复用根目录 [scripts/benchmarks](../../../scripts/benchmarks)，不在每个包复制 reporting 实现
- 包内 `benchmarks/` 的辅助文件统一加 `_` 前缀，如 `_budgets.ts`、`_workloads.ts`，便于排序并与 `*.bench.ts` 用例区分；此约定不扩展到顶层共享脚本或生产源码
- 参考 [Math 基准](../../../packages/kernel/math/benchmarks) 的接入方式；不复用应用集成基准作为单元性能测试架构，不默认向包 README 添加 bench 说明
- 独立 bench 配置只承载基准特有的发现范围、运行环境、产物入口与 reporter，不要求所有包机械新增一份配置
- 性能运行需有当前任务针对范围的授权，不能混入默认功能测试。默认串行运行，避免其它构建、测试或服务负载干扰；遵循根规则的 stage / commit 边界
- 用 Vitest 做多文件性能对照时，基线与候选须从相同的历史结果缓存状态启动，并固定文件执行顺序；分别记录启动时的缓存状态和实际执行顺序，不以命令行文件列表代替运行记录

### 共享运行命令

准备目标包当前加载策略所需的构建产物后，从仓库根目录运行：

```bash
pnpm bench --workspace packages/kernel/math          # 仅耗时
pnpm bench --workspace packages/kernel/math --memory # 耗时完成后独立采样单次分配
```

- `--workspace` 选择包目录，可追加 bench 文件过滤词；不按包名决定是否记录内存。默认关闭，只有 `--memory` 开启；包配置不声明测量阶段或内存观察线
- 共享命令保持串行，不运行功能测试，不自动构建或改写包的产物入口、别名和加载策略；包现有直接 Vitest 入口仅测耗时
- reporter 按本次命令注入的运行模式检查分配元数据；耗时模式隐藏全部内存列、提示和说明。JSON 记录 `allocationEnabled`；当前报告为 v5，历史报告不回写，不能直接作为当前版本基线

## Worktree 隔离与合回

- 所有性能测试任务，包括基准编写、已有基准运行、临时对比、插桩诊断及优化验证，统一在任务专用的隔离 Git worktree 中处理，不在原工作区执行；仅编辑本 skill / reference 不触发实验 worktree 或性能运行
- 开始前记录原工作区、原分支和有效源码快照；新 worktree 不自动包含 dirty / untracked 内容，须按任务清单重建必要内容并核对依赖、配置及真实执行路径。已有本任务隔离 worktree 可复用，不重复嵌套创建
- 在已授权范围内自主完成测量、诊断与修复；完成后撤除探针，交付结果、验证证据和拟合回的差异，保留 worktree，等待用户确认处理完成后才合回原分支。任务执行授权不等于提前获得最终合回确认
- 用户确认后，将已验证的最终测试及优化改动合回原工作区的原分支，默认保持未提交，不自动 stage / commit / push。仅迁回相对实验初始有效快照的任务差异，保护原有及新增用户改动；分支切换或无法安全合并的冲突交人工，不擅自覆盖
- 合回后核对差异及受影响验证；源码与被测快照不一致时，在隔离 worktree 补齐性能验证，不直接沿用收益结论。确认改动已合回、ignored 报告等证据已保存且无遗漏后才清理实验 worktree；无可合回改动也须在用户确认完成并保存报告后清理
- 插桩细节见 [渐进式运行时插桩](references/runtime-instrumentation.md)，临时报告仍按 ignored 产物规则保存，不纳入提交

## 模块与调用方的职责

- 操作 owner 或计时边界变化时，同步核对基准、fixture、预算和报告归属；边界变化后的结果不直接沿用旧基线比较，不为迁移机械新增场景
- 分阶段复用收益与实际驱动收益分别举证：底层消费有效 prepared 不证明驱动已接入或完整更新提速；流程测量须包含其拥有的准备、比较、资源恢复及提交成本
- 先按公开契约确定模块拥有的一次完整操作：该次操作内部的遍历、计算、分配及可复用准备属于本模块；调用方的重复调度、跨调用复用、缓存失效与生命周期管理属于调用方，应在其所属模块评测
- 纯算法每个计时样本只调用一次算法，按输入点数、顶点数、精度等真实参数扩容；不通过外包循环制造调用量，不加入调用方的缓存/未缓存对比。统计采样的重复执行不属于工作负载规模
- 若模块公开契约本身拥有批处理或缓存能力，可在该模块测量一次完整的对应操作；不能为压低报告耗时把调用方策略下沉到不拥有该职责的底层模块
- 诊断与优化建议先标明责任归属，再评估内部算法或调用方策略。超限不自动意味着底层应增加缓存；也不能因复杂度高而放宽真实输入需求
- 单次预算按本操作的消费需求重新判断，不沿用或直接均摊旧批量预算；修改计时边界后的结果不能与旧批量结果直接比较

## 工作负载与覆盖

- 默认采用代表性覆盖，不逐方法、逐参数穷举；固定成本操作保留典型输入，仅在参数改变计算路径时拆分场景。可扩容算法保留常用规模和一个上限参考档，发现热点后再增加细分基准；正确性边界交给功能测试，不为增加性能用例数量重复覆盖
- 分别识别单实体复杂度与实体数量两个扩容维度；前者测内部算法，后者仅在拥有批处理职责的调用方测调度与组装，结果不能互相替代。获准测量有状态流程时，覆盖首次执行、真实变化与等值更新，更新计时包含该操作的完整提交，不只测缓存内部

首次采样前列出“公开算法 → 实际调用场景与频率 → 输入形态与规模 → 输出不变量 → 常规/参考档 → P50 警告/错误上限与依据”，并将预算写入模块配置。常规场景不得缺省预算；缺少确切业务数据时明确需求假设并给出初始预算，仅报告限于明确的参考档或用户确认的例外。要求全覆盖时逐一核对公开函数及 namespace 成员，常量、类型不算算法；清单放已有 ignored plan 目录。

- 可扩容点集通常用 **1k / 10k / 100k / 1M**；10k、100k 是业务重点，1M 只是上限参考，不能推导为所有算法的业务需求
- 上限结合复杂度及消费者判断：Plot 过点曲线以约 100k 点为重点；最小外接圆的有序输入可能放大嵌套循环，应使用更小规模，不盲跑百万
- 区分输入规模与精度：多边形命中扩容顶点数，曲线弧长扩容采样精度；固定控制点数的贝塞尔曲线不把查询次数标成曲线规模
- 常数规模算法使用固定代表性输入；覆盖均匀/非均匀间距、重复/共线点、命中/未命中等执行分支，分别列出，不混为一次循环；不按无意义参数组合膨胀 case

设计或执行基准时按[采样协议与例外](references/sampling-protocol.md)。

## 计时边界与运行环境

- 跨包测量记录实际执行入口及参与计算的 workspace 源码或产物身份；调用包指纹与全仓 dirty 标记不足以区分依赖改动。工具未覆盖时在报告补充参与包与快照证据，证据不足不归因单项收益，也不据此宣称工具已支持跨包指纹
- 算法单元基准默认在 Node.js 中执行，优先测当前源码构建的原生 ESM 公开入口。构建不计入算法耗时；避开开发加载器的导出 getter 包装等额外开销，不能用陈旧产物
- 输入构造、随机数据生成、预期值计算与断言放在计时区间外；fixture 确定且可复现，测量过程中不逐轮增长或修改成另一种负载
- 保留并消费返回结果，防止只测无可观察结果的空工作；用独立已知答案、几何不变量或已有功能测试校验，不仅断言“不抛错”
- 计时包含该次操作自身的计算与分配；短算法可能接近计时与调度开销，应报告可信度限制，不通过增加外部调用批量掩盖精度限制，也不扣除估算开销声称精确延迟
- 本机适合开发探索和同环境对比；稳定回归门槛优先在固定机器或专用 runner 上执行。共享 CI 可生成报告，但未经稳定性验证不设置严格耗时阻断
- 记录 Node、Vitest、OS、CPU、runner、源码/产物及 fixture/配置指纹。环境、输入或计时方式不同，不直接做回归判断，也不将跨机器差异解释为代码收益
- 对照运行按实际源码指纹确认原实现与候选身份，不依赖运行名称；最终保留源码须与已验证快照一致。多个优化一起测量只能报告组合收益，未经消融实验不将总收益归给单项

## 报告与门槛

需要观察分配时按[单次分配观察](references/allocation-observation.md)。

### 耗时报告

- 生成报告前核对共享 reporter 的实际比较、预算判定与展示是否已采用本规则；旧工具仍用 P90 或 mean 判定时须先适配，不能仅隐藏列而沿用旧判定。历史报告不回写，跨指标旧结论不直接比较；预算数值不因指标切换自动调整

- 报告按运行前配置的消费预算独立显示是否达标，统一评价常规档 P50；消费预算与历史回归基线、CI 阻断独立，缺少历史数据或不启用阻断不构成免设预算的理由
- 不用一次本机结果自动生成“稳定上限”，也不把 100k 输入规模上限写成耗时预算。基线须由人工选择，比较前检查环境和工作负载可比性
- 性能标准以实际消费需求和交互时间预算为准，不按算法复杂度或当前实测速度放宽；即使算法复杂度高，达不到实际需求仍判定为性能问题。配置记录消费依据，未发现消费者时明确标注假设场景，不把假设写成已验证业务上限
- 标记阈值由 LLM 在首次采样前结合消费需求、输入规模、本模块的一次完整操作及运行环境判断，写入各模块配置；报告按配置确定性判定，🟡 表示警告、🔴 表示错误，仅报告例外必须记录原因。禁止根据本次实测耗时倒推保证通过的上限
- 阈值参考点：**16.6ms** 约为 60Hz 的一帧预算，同步工作占满该预算有帧卡顿风险；**200ms** 作为用户明显感知卡顿的参考。两者不作为所有算法的统一硬阈值；帧内还需给编译、布局、渲染留出时间，批量耗时不能直接等同于一次交互阻塞，其余阈值由 LLM 按用例判断
- 保存中文 Markdown 与原始 JSON；使用已有 ignored 报告目录，每次生成新目录，失败也保留，不覆盖基线
- 场景维度及标题由模块提供，按级联拆列，重复父级仅首行显示；其后保留状态、样本数、均值、P50、上限、备注。不合并耗时列、不依赖单元格 HTML 换行；验收状态、级别与原因放备注，有内容才显示
- 样本数是正式计时记录数量，不包含预热，也不是输入点数或批内操作数；达到 1k / 1M 时分别以一位小数 K / M 显示，JSON 保留原始数量
- 耗时按原始值选单位：小于 1ms 用 μs，小于 1s 用 ms，其余用 s，四舍五入保留一位小数；JSON 与预算保持毫秒。显示小数位不等于测量精度
- P50 与均值只使用正式样本计算；P50 作为前后对比、回归判断和优化验收的基准，均值仅作辅助统计。报告正文、表格及摘要不展示 P90，也不用 P99 替代；原始样本保留以便复核，三个参考样本不用于稳定分布结论
- JSON 保存每个场景实际采样选项、总调用次数及统计数据，不能用全局默认配置冒充覆盖后的配置。报告标出参考档、单次操作边界与输入规模含义

报告后按授权范围读取[诊断、优化与停止条件](references/optimization-cycle.md)。

## 完成检查

- 性能优化需验证其适用边界与代价：同时检查预期受益和可能退化的负载，保持前后测量条件可比，分别报告收益、退化及正确性验证结果；不能以局部提速推导整体收益

1. 用例对应实际消费场景，规模和特殊上限有理由；常规场景已在采样前配置预算，参考档或获准例外记录仅报告原因；全覆盖要求无遗漏
2. 固定轮次及参考档调用上限已实测，输入构造和断言未混入计时
3. 按受影响范围格式化、lint、类型检查、功能验证，再串行运行获授权的性能用例
4. 阅读生成的 Markdown / JSON，核对样本、单位、状态、实际配置与运行错误；“测试通过”不等于“性能达标”
5. 汇报报告路径、验证范围和可信度限制；仅完成 skill 编写时，不声称采样实现已调整或基准已重跑
6. 测试前确认自动优化选项，默认关闭；开启后按源码 → 插桩 → 机制顺序及长任务状态连续推进，达标即停，机制新方案交人工决定。关闭时才保留报告后的诊断/实施审批；核对 plans 中间产物、阶段轮次、最终报告及实际授权一致
