# 单元性能基准

以真实消费场景决定输入规模，测量完整且可解释的工作负载。性能报告始终生成，耗时门槛按场景选择；规模上限、采样次数和耗时上限是三个独立概念。

## 接入与边界

- 先读目标包的公开入口、现有基准、实际消费代码及就近规则；正确性契约复用 [test-contract](../test-contract/SKILL.md)
- 优先使用现有 Vitest / Tinybench 链路；包内 `benchmarks/` 与 `tests/` 同级，用例为 `*.bench.ts`。采样、执行辅助和报告工具复用根目录 [scripts/benchmarks](../../../scripts/benchmarks)，不在每个包复制 reporting 实现
- 包内 `benchmarks/` 的辅助文件统一加 `_` 前缀，如 `_budgets.ts`、`_workloads.ts`，便于排序并与 `*.bench.ts` 用例区分；此约定不扩展到顶层共享脚本或生产源码
- 参考 [Math 基准](../../../packages/kernel/math/benchmarks) 的接入方式；不复用应用集成基准作为单元性能测试架构，不默认向包 README 添加 bench 说明
- 独立 bench 配置只承载基准特有的发现范围、运行环境、产物入口与 reporter，不要求所有包机械新增一份配置
- 性能运行需有当前任务针对范围的授权，不能混入默认功能测试。默认串行运行，避免其它构建、测试或服务负载干扰；遵循根规则的 stage / commit 边界

## 工作负载与覆盖

先列出“公开算法 → 实际调用场景 → 输入形态 → 规模 → 输出不变量 → 常规/参考档”。要求全覆盖时逐一核对公开函数及 namespace 成员，常量、类型不算算法；清单放已有 ignored plan 目录。

- 可扩容点集通常用 **1k / 10k / 100k / 1M**；10k、100k 是业务重点，1M 只是上限参考，不能推导为所有算法的业务需求
- 上限结合复杂度及消费者判断：Plot 过点曲线以约 100k 点为重点；最小外接圆的有序输入可能放大嵌套循环，应使用更小规模，不盲跑百万
- 区分不同维度：曲线输入点数、弧长近似采样精度、查询次数、操作批量不是同一个量。多边形顶点数和查询数分别扩容，避免无依据的 100k × 100k
- 常数规模算法可按 1k / 10k / 100k 次操作组成一批，用变化的确定性输入；场景名注明 `operations=N`。这时一条耗时记录对应整批，不能将整批 P90 除以 N 冒充单次操作 P90
- 覆盖会影响执行路径的代表性形态，如均匀/非均匀间距、重复/共线点、命中/未命中、缓存/未缓存；不按无意义参数组合膨胀 case

## 固定采样轮次

本项目约定：

| 档位                     |  预热 | 正式测量 | 用途                                           |
| ------------------------ | ----: | -------: | ---------------------------------------------- |
| 常规档，包括业务重点规模 | 10 轮 |   100 轮 | 均值、P50、P90；P99 仅供观察                   |
| 百万等超业务规模参考档   |  0 轮 |     3 轮 | 大致耗时与可完成性，不作为稳定分位数或门槛依据 |

Vitest / Tinybench 配置意图：

```ts
// 常规档：关闭时间驱动，固定预热与正式轮次
{ time: 0, iterations: 100, warmup: true, warmupTime: 0, warmupIterations: 10 }

// 参考档：实际算法计算总次数不得超过 3 次
{ time: 0, iterations: 3, warmup: false, warmupTime: 0, warmupIterations: 0 }
```

- `time > 0` 与 `iterations` 通常是共同满足的最低条件，不能把 iterations 当成上限；短算法可能因此产生数百万样本
- 对同步算法显式设置注册选项 `async: false`，避免自动探测额外执行。参考档不得在计时前另算一次完整规模“预期结果”；包括探测、预热、校验在内的实际计算总数必须受限
- 核对安装版本与共享 helper 的真实行为，以计数器和保留样本验证：常规档正式样本 100、总调用 110；参考档样本与总调用都为 3。计数用于验证测量协议，不替代算法正确性断言
- 100 次是默认起点，不保证 P99 稳定；最近秩法下 P90 为第 90 个、P99 为第 99 个排序值。确需研究尾部的少数场景可明确增加到 1,000 次，不擅自全局扩大
- 固定预热 10 次不保证 JIT 已稳定；有重复运行漂移证据时再调整具体场景，并记录实际配置
- 接入时检查 [sampling.ts](../../../scripts/benchmarks/sampling.ts) 是否符合上述约定；发现差异应在获授权的实现任务中修正并验证，不能把 skill 中的目标配置当作已运行事实

## 计时边界与运行环境

- 算法单元基准默认在 Node.js 中执行，优先测当前源码构建的原生 ESM 公开入口。构建不计入算法耗时；避开开发加载器的导出 getter 包装等额外开销，不能用陈旧产物
- 输入构造、随机数据生成、预期值计算与断言放在计时区间外；fixture 确定且可复现，测量过程中不逐轮增长或修改成另一种负载
- 保留并消费返回结果，防止只测无可观察结果的空工作；用独立已知答案、几何不变量或已有功能测试校验，不仅断言“不抛错”
- 批量测试包括循环、调用、算法自身分配及结果保存的成本，报告应说明；不要扣除估算开销后声称得到精确单调用延迟
- 本机适合开发探索和同环境对比；稳定回归门槛优先在固定机器或专用 runner 上执行。共享 CI 可生成报告，但未经稳定性验证不设置严格耗时阻断
- 记录 Node、Vitest、OS、CPU、runner、源码/产物及 fixture/配置指纹。环境、输入或计时方式不同，不直接做回归判断，也不将跨机器差异解释为代码收益

## 报告与门槛

- 无预期：仅报告，显示执行是否成功。有预期：按场景显式配置绝对上限或相对基线，独立显示是否达标；优先选择常规档 P90
- 不用一次本机结果自动生成“稳定上限”，也不把 100k 输入规模上限写成耗时预算。基线须由人工选择，比较前检查环境和工作负载可比性
- 性能标准以实际消费需求和交互时间预算为准，不按算法复杂度或当前实测速度放宽；即使算法复杂度高，达不到实际需求仍判定为性能问题。配置记录消费依据，未发现消费者时明确标注假设场景，不把假设写成已验证业务上限
- 标记阈值由 LLM 结合调用场景、输入规模、单次或批量耗时及运行环境判断，写入各模块配置；报告按配置确定性判定，🟡 表示警告、🔴 表示错误，未配置时仅报告
- 阈值参考点：**16.6ms** 约为 60Hz 的一帧预算，同步工作占满该预算有帧卡顿风险；**200ms** 作为用户明显感知卡顿的参考。两者不作为所有算法的统一硬阈值；帧内还需给编译、布局、渲染留出时间，批量耗时不能直接等同于一次交互阻塞，其余阈值由 LLM 按用例判断
- 保存中文 Markdown 与原始 JSON；使用已有 ignored 报告目录，每次生成新目录，失败也保留，不覆盖基线
- 表格保留独立列：**场景、状态、样本数、均值（μs）、P50（μs）、P90（μs）、P99（μs）、上限、备注**。不合并耗时列、不依赖单元格 HTML 换行；验收状态、级别与原因放备注，有内容才显示
- 样本数是正式计时记录数量，不包含预热，也不是输入点数或批内操作数；达到 1k / 1M 时分别以一位小数 K / M 显示，JSON 保留原始数量
- 耗时展示为微秒并保留三位小数、四舍五入；JSON 与预算保持毫秒。显示小数位不等于测量精度，高分辨率时钟也不保证每条纳秒级结果可靠
- 均值、P50 与最近秩 P90/P99 使用正式样本计算；三个参考样本的高分位数接近最大观察值，不代表可靠尾延迟
- JSON 保存每个场景实际采样选项、总调用次数及统计数据，不能用全局默认配置冒充覆盖后的配置。报告标出参考档及批量耗时语义

## 报告后的 AI 诊断

1. 性能报告生成并核对后，向用户询问“是否进行 AI 诊断？”，说明拟诊断的包、重点用例，以及是否包含临时埋点和限定范围的性能重跑；获得明确授权后才开始。生成报告的授权不等于诊断授权，诊断也不等于实施优化
2. **测试用例复核**：先不看算法实现，从重点结果中的错误、警告入手，结合用例、预算依据和已知消费需求检查上限、输入规模、形态及调用频率是否合理。区分真实需求、假设场景和不符合实际消费方式的负载；不能仅凭耗时高或暂未找到消费者就认定场景不成立，也不能为消除红黄标记放宽标准。给出用例或上限调整建议及证据
3. **代码优化分析**：结合报告检查相关源码与调用链，定位算法、重复计算、分配、代码逻辑及整体方案的优化空间；必要时调研强相关的成熟开源方案，记录来源、适用条件和差异。建议说明预期收益、正确性风险与验证方式，未实测的收益明确标为假设
4. **继续深挖**：单一总耗时不足以定位时，在授权范围内使用临时埋点、分阶段计时或 profiler 拆分成本，串行重跑受影响用例。记录埋点开销与计时边界，区分诊断测量和原始基准，不直接混作同一基线；不擅自扩大规模、轮次或全量重跑，结束后撤除临时埋点
5. **重新出具报告**：诊断完成后，在已有 ignored 报告目录生成独立的中文诊断报告，链接原性能报告及有重跑时的新报告；包含重点结果表（最后一列为说明）、用例/上限复核、源码证据、细分测量、调整方案、验证计划及待人工决策项。区分已确认原因、推测和未验证内容；没有重跑则明确沿用原测量，不生成或宣称新的性能结果
6. **人工决策**：交付诊断报告与具体调整方案后，询问用户是否实施及实施哪些项。未经批准不修改正式算法、用例或预算，不自动更新基线；临时诊断埋点不能作为生产优化保留

## 完成检查

1. 用例对应实际消费场景，规模和特殊上限有理由；全覆盖要求无遗漏
2. 固定轮次及参考档调用上限已实测，输入构造和断言未混入计时
3. 按受影响范围格式化、lint、类型检查、功能验证，再串行运行获授权的性能用例
4. 阅读生成的 Markdown / JSON，核对样本、单位、状态、实际配置与运行错误；“测试通过”不等于“性能达标”
5. 汇报报告路径、验证范围和可信度限制；仅完成 skill 编写时，不声称采样实现已调整或基准已重跑
6. 生成性能报告后询问是否授权 AI 诊断；已完成诊断则交付独立报告和调整方案，等待人工决定是否实施优化
