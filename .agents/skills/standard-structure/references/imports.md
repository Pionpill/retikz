# 模块导入导出

## 导入导出

- 导出范围按实际生产需求收敛：仅同文件使用的成员不 `export`；内部跨文件使用的成员只保留模块级导出；包根与公开子路径仅暴露必要的 API 和配套契约。不得无依据导出内部实现，也不得仅为功能测试或性能测试新增导出、扩大 barrel 或包根公共面。
- 包根、owner 及子模块 barrel 均按当前入口的可见性选择导出形式：转导出与来源模块的全部导出完全一致时，直接用 `export *`，不重复列举成员；仅部分 API 需要暴露、其余仅供内部复用时用 `export { ... }` 精选导出，类型使用对应的 `export type *` / `export type { ... }`。不按目录层级强制某一种形式。
- 包根或子路径是否属于包外公共入口，由 `package.json` 的显式 `exports` 映射、包内规范或 public-surface 测试确定；字符串形式视为根 `.` 映射，通配符映射不单独证明每个匹配文件都是稳定 API，单个源码文件存在也不构成公共入口。包内跨模块可见不等于包外公开。
- 包根 `index.ts` 的每项导出都须审查公开必要性、契约稳定性及消费方影响；使用 `export *` 时也须逐项核对来源模块，防止内部新增导出自动扩大公共面。内部复用不构成包外公开依据，避免后续实现调整迫使消费方修改代码或升级适配。
- 不需要公开的模块不得进入向上 barrel；owner 内通过相邻路径或私有子 barrel 导入，不得为测试或复用便利转发到包根。
- 包内跨 owner 的消费方从拥有者 barrel 导入；包外消费方使用 package root 或 `exports` 声明的 facade / 稳定子路径。不要从非拥有者模块转手 export 其它层内容。
- 从祖先目录访问其他 owner 时，也必须止于目标 owner 的根 barrel，不得继续深入私有子模块；模块根入口供包内跨 owner 使用，包根入口独立裁剪包外 API，不自动转发内部复用符号。同 owner 内允许直接引用内部文件，避免经自身 barrel 形成循环依赖。
- 包外导入只能使用 package root 或 `package.json` `exports` 声明的稳定子路径，不得访问未声明的源码文件。包内跨 owner 导入必须经目标 owner 或稳定二级 owner 的 barrel；稳定二级 owner 必须具有独立职责、自己的 `index.ts`，并有包内规范或已验证的跨 owner / 公共使用依据，不能仅因目录存在而成立。同 owner 内部可从相邻模块导入，不要为了追求包根入口而制造自引用或循环依赖。无论哪种情况都不得跨 owner 进入实现文件；若缺少稳定 barrel，应先补充边界或重新判断所有权。
- 同一文件中同 kind（type 或 value）且同 source 的 named import 必须合并为一条；不同符号的 type/value 导入保持分离。同名符号同时用于值和类型时只保留普通 import，不重复 import type；仅用于类型时使用 import type。
- 内部尽量避免 import / export `as` 重命名；公共 facade 仅在稳定公共名称或冲突隔离确有需要时建立别名，不建立兼容旧 API 的迁移别名、fallback 或双轨实现。
- 主题内部可相邻导入；模块外避免 deep import 到 `constants.ts` / `schema.ts` 等私有文件。

## 公开导出收敛

- 分两层判断：先确认每项导出的真实消费方，再判断公开必要性。其他包的生产代码消费视为有效依据；包内消费只证明内部导出必要，不自动证明包根或公开子路径必要。
- 仅测试、基准或 Docs 消费时，区分用户实际调用的公开能力与内部实现展示；扩展作者的 `defineXxx` 示例可证明公开用途，公共面存在性断言、Schema 展示注册和性能测试本身不能证明。
- 无直接生产消费时，沿当前公开入口、扩展契约和已确认设计判断具体用途；保留调用者需要构造或命名的输入、产物及配套类型，不以“未来可能有用”保留内部步骤、派生表或空别名。零 import 不等于无公开用途。
- 消费统计追踪模块解析、别名、转导出链、命名空间访问与实际词法引用；同名命中、未使用的 import、纯 barrel 转发和文档词项仅作线索。类型还须追踪公开签名及中间类型；`IRXxx` 的 `z.infer` 引用不代表对应 runtime Schema 必须从包根导出。
- 报告逐项记录消费位置、类别、保留或收敛理由；无直接消费时补充具体用途依据，区分移除根转导出、保留内部导出与删除声明。仅扫描仓内时不得声称仓外无人使用；测试和 Docs 迁移随实际收敛同步处理。

收敛公开导出、递归 schema 或公开签名关联类型时，验证源码消费及生成声明的依赖闭包；复用受影响包的声明构建与既有产物入口检查，按 [发布验证](../../package-publish/references/validation.md) 选择必要范围。不可验证时明确缺口，不以源码 `tsc --noEmit` 通过替代发布面可用性，不新增独立类型测试或用 `tsc` emit 污染源码。

## 测试访问例外

- 上述导入边界约束生产源码；仓库内测试可深层导入因生产代码跨文件使用而已导出的内部成员，无需经包根或公开子路径转发。此例外不适用于生产消费方。
- 完全未导出的实现通过其消费方验证，不为直接测试增加导出或测试专用访问入口；测试需求不得反向决定生产 API 的公开范围。
