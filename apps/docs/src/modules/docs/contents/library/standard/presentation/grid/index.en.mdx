## Basic usage

### Basic grid

You define a grid with `bounds` and `line`; spacing, alignment, styles, and major lines are configured inside that one property:

- `bounds` accepts unordered `start` and `end` Cartesian corners, or a center `position` with `width` and `height`
- `start` and `end` are sorted independently on x and y during lowering, so reversed and equal coordinates are valid; corner positions must be Cartesian `Position` values
- centered `position` is the geometric center and accepts `Position` or `PolarPosition`; Core resolves PolarPosition, while the grid itself remains Cartesian
- `line` may be omitted or set to `true` to enable both directions with default spacing `10`; `false` disables all grid lines while leaving `border` independent
- a shared `line` object applies one `GridLineInput` to both directions; `{ vertical, horizontal }` configures each direction independently
- each `GridLineInput` accepts positive `spacing`, an optional scalar `origin`, `includeBoundary`, ordinary-line `style`, and periodic `major` settings
- `origin` uses scene coordinates for corner bounds and center-local coordinates for centered bounds
- `border` can be configured independently and remains available when `line` is `false`

The grid below covers `[20, 20]` through `[260, 150]` and emits a line every 20 user units in both directions.

<ComponentPreview files="grid-basic" size="sm" />

`line.origin` follows the bounds form. Corner bounds use scene coordinates and default to the normalized start; centered bounds use center-local coordinates and default to `[-width / 2, -height / 2]`. Set `line: { origin: 0 }` in a centered configuration to align both lattices through the geometric center. Direction-specific configurations can use different scalar origins. Core resolves the center `PolarPosition`.

## Errors and limitations

Spacing must be positive, major.every a positive integer, and dimensions and border padding nonnegative. Corner bounds may be reversed or coincident. Center positioning does not create a polar grid. Direct IR without GridDefinition reports COMPOSITE_NOT_REGISTERED.

## Implementation

<ComponentAlert
  type="tip"
  title="Optional for everyday use"
  description="You only need this lowering model when working with Grid IR directly or debugging compile diagnostics."
/>

Grid IR does not become a renderer primitive. Corner bounds are normalized independently on both axes; centered bounds are expanded in a center-local rectangle. Standard normalizes the shared or direction-specific `line` input, enumerates each lattice, applies ordinary and major styles, and assembles Core `Path` nodes in border order.

Centered bounds additionally use an existing Core `Scope` to carry the center translation. Cartesian Position, recursive PolarPosition, and node references are therefore resolved by Core Scene compilation; Standard does not add a second position resolver, and this is not a polar grid.

The figure follows this deterministic transformation from left to right. Grid's responsibility ends once the output reaches `Core Path[]` or a positioned `Scope`.

<ComponentPreview files="grid-lowering" hideCode size="xs" />

Each grid line becomes a `move + line` path, while the border becomes a closed path. Core's existing compiler and renderers consume the result, so renderers never need to recognize Grid.

A handwritten `IRGrid` without a loaded definition is never silently interpreted: Core emits `COMPOSITE_NOT_REGISTERED` and skips it. Standard therefore remains dynamically loaded by capability without changing compilation for other figures.
