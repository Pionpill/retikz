Arrow extensions build on Core's basic arrows and add more optional content:

| Package          | Provided content                                                                        |
| ---------------- | --------------------------------------------------------------------------------------- |
| `core`           | `normal`, `open`, `stealth`, `openStealth`, `circle`, `openCircle`                      |
| `standard/arrow` | `diamond`, `openDiamond`, `kite`, `openKite`, `square`, `openSquare`, `bar`, `crowFoot` |

## Usage

This page supports two import styles:

- Import specific Definitions on demand, such as `DiamondArrowDefinition`, and pass only the official extensions used by the figure to `Layout` or `compile`
- Use the complete official extension set through `StandardArrowDefinitions`, which includes every Standard Definition from this subpath; use `StandardArrowProviders` when assembling a provider graph

Both styles explicitly assemble capabilities for the current figure. Importing the package does not register arrows globally.

### React usage

Import the Standard Definitions a figure actually uses from `@retikz/standard/arrow` and pass them to the React `Layout` `arrows` prop. Core arrows need no extra injection; the subpath import does not register Standard arrows globally.

```tsx
import { Draw, Layout } from '@retikz/react';
import { DiamondArrowDefinition, OpenDiamondArrowDefinition } from '@retikz/standard/arrow';

<Layout arrows={[DiamondArrowDefinition, OpenDiamondArrowDefinition]}>
  <Draw
    way={[
      [0, 0],
      [160, 0],
    ]}
    arrow="->"
    arrowDetail={{ end: { shape: 'openDiamond' } }}
  />
</Layout>;
```

### Vanilla usage

With `@retikz/vanilla`, put the same Definition in `compile.arrows`. `input` can be an existing Core IR or Vanilla plain spec; `mount` accepts the same `compile` configuration.

```ts
import { renderToSvgString } from '@retikz/vanilla';
import { DiamondArrowDefinition, OpenDiamondArrowDefinition } from '@retikz/standard/arrow';

const svg = renderToSvgString(input, {
  compile: {
    arrows: [DiamondArrowDefinition, OpenDiamondArrowDefinition],
  },
});
```

Path IR stores only an arrow name and JSON-safe configuration. If the name has no built-in or injected Definition, Core fails explicitly at lookup and lists the available entries instead of substituting a default arrow.

### Diamond arrows

`diamond` and `openDiamond` use flat 2:1 proportions and provide filled and hollow endpoints. The solid form uses arrow fill, while the open form is stroke-only.

<ComponentPreview files="diamond-arrows" size="sm" />

### Kite arrows

`kite` and `openKite` place their shoulders at one quarter of the default length, producing an asymmetric contour stretched toward the tip. They share Diamond's solid/open paint rules but are not symmetric diamonds; inject `KiteArrowDefinition` or `OpenKiteArrowDefinition` on demand.

### Square arrows

`square` and `openSquare` have equal default length and width, while explicit `length` and `width` can still stretch them independently. The open form moves its contour inside the marker bounds before stroking instead of reusing the solid outer edge; their Definitions are `SquareArrowDefinition` and `OpenSquareArrowDefinition`.

All three families reuse Core's marker host, start/end placement, path shrink, and `arrowDetail` visual parameters. Explicit `length` and `width` only stretch the frozen default local contours.

### Bar endpoint

`bar` draws an open line perpendicular to the path tangent at the authored endpoint. It inherits the path stroke, but its name does not impose domain meanings such as “blocked” or “inhibited”; consumers assign those meanings.

<ComponentPreview files="bar-arrow" size="sm" />

The path body overlaps the marker contact edge by half of its own stroke width, then the marker paints over the joint. This avoids antialiasing seams without letting the line pass through the bar. `length` controls marker size along the path, `width` controls the bar span, and `lineWidth` controls the marker stroke.

### Crow-foot endpoint

`crowFoot` explicitly draws three open rays from the path contact point. Relationship diagrams may use it for multiplicity, but Standard defines only reusable geometry and does not bind it to cardinality.

<ComponentPreview files="crow-foot-arrow" size="sm" />

All three rays belong to the marker, and the path body shrinks to the junction. `length`, `width`, `lineWidth`, `color`, and `opacity` continue to use Core's `arrowDetail` contract; start, end, reversed routes, and double endpoints share the same placement algorithm.
