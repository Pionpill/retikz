Standard 扩展不会自动注册。使用形状、箭头、裁剪或 Path kind 时，先从对应子入口导入 Definition，再传给 React `Layout` 或 Vanilla 的编译入口。

## 如何使用

有两种导入方式。图形只需要少量能力时按需导入；希望一次使用官方扩展包的全部内容时，使用对应的 `StandardXxxDefinitions` 集合。

### 方式一：按需导入具体 Definition

只导入当前图真正使用的 Definition，并传入对应的 compile option：

```tsx
import { Layout } from '@retikz/react';
import { DiamondArrowDefinition } from '@retikz/standard/arrow';
import { CircleClipDefinition, CircleClipShapeDefinition } from '@retikz/standard/clip';
import { RibbonPathKindDefinition } from '@retikz/standard/ribbon';
import { CrossShapeDefinition } from '@retikz/standard/shape';

<Layout
  shapes={[CrossShapeDefinition]}
  arrows={[DiamondArrowDefinition]}
  clips={[CircleClipDefinition]}
  clipShapes={[CircleClipShapeDefinition]}
  pathKinds={[RibbonPathKindDefinition]}
>
  {/* 图形内容 */}
</Layout>;
```

Vanilla 使用同一组 Definition：

```ts
import { renderToSvgString } from '@retikz/vanilla';
import { DiamondArrowDefinition } from '@retikz/standard/arrow';
import { CircleClipDefinition, CircleClipShapeDefinition } from '@retikz/standard/clip';
import { RibbonPathKindDefinition } from '@retikz/standard/ribbon';
import { CrossShapeDefinition } from '@retikz/standard/shape';

const svg = renderToSvgString(input, {
  compile: {
    shapes: [CrossShapeDefinition],
    arrows: [DiamondArrowDefinition],
    clips: [CircleClipDefinition],
    clipShapes: [CircleClipShapeDefinition],
    pathKinds: [RibbonPathKindDefinition],
  },
});
```

### 方式二：使用官方完整 Definition 集合

如果当前图可以直接使用某个官方扩展包的全部内容，可以导入集合：

```tsx
import { Layout } from '@retikz/react';
import { StandardArrowDefinitions } from '@retikz/standard/arrow';
import { StandardClipDefinitions, StandardClipShapeDefinitions } from '@retikz/standard/clip';
import { StandardShapeDefinitions } from '@retikz/standard/shape';

<Layout
  shapes={StandardShapeDefinitions}
  arrows={StandardArrowDefinitions}
  clips={StandardClipDefinitions}
  clipShapes={StandardClipShapeDefinitions}
>
  {/* 图形内容 */}
</Layout>;
```

Vanilla 只需要把同样的集合传给 `compile`：

```ts
import { renderToSvgString } from '@retikz/vanilla';
import { StandardArrowDefinitions } from '@retikz/standard/arrow';
import { StandardClipDefinitions, StandardClipShapeDefinitions } from '@retikz/standard/clip';
import { StandardShapeDefinitions } from '@retikz/standard/shape';

const svg = renderToSvgString(input, {
  compile: {
    shapes: StandardShapeDefinitions,
    arrows: StandardArrowDefinitions,
    clips: StandardClipDefinitions,
    clipShapes: StandardClipShapeDefinitions,
  },
});
```

| 方式                       | 适合场景                                                                              |
| -------------------------- | ------------------------------------------------------------------------------------- |
| 具体 Definition            | 只装载当前图使用的能力                                                                |
| `RibbonPathKindDefinition` | Ribbon 只有一个直接 Path kind Definition，没有完整的 `StandardRibbonDefinitions` 集合 |
| `StandardXxxDefinitions`   | 快速使用对应官方扩展包的全部 Definition                                               |

裁剪是两级能力：`clips` 解析 authored operation，`clipShapes` 把解析后的几何降低为 canonical path。按需装载时必须为实际 kind 提供两级 Definition；完整集合也必须成对传入。

如果是 adapter 在编译前组装 provider graph，则使用对应的 `StandardShapeProviders`、`StandardArrowProviders` 或 `StandardClipProviders`，Ribbon 则使用 `createRibbonProviderContribution()`。`StandardClipProviders` 同时包含 operation 与 shape provider，但仍只是 catalog；resolver 只物化 roots 可达闭包。Provider 用于装配 Definition，不直接替代 `Layout` 或 `compile` 的 `shapes`、`arrows`、`clips`、`clipShapes`、`pathKinds` 数组。

## 内部编译逻辑

两种 Definition 导入方式最后都会进入 Core 的同一条编译路径：

<ComponentPreview files="capability-loading-flow" hideCode size="xs" />

图中左侧的单个 Definition 和完整集合只是两种装载入口；它们会汇入同一条 Core 编译路径。provider graph 负责在编译前组织 Definition，IR 只在消费阶段按名称查找已经装载的能力。

- 直接传入 Definition 时，Core 将它们放入对应的 `shapes`、`arrows`、`clips`、`clipShapes` 或 `pathKinds` registry
- 使用 Provider 时，adapter 先收集 `CoreProviderContribution`（例如 `createRibbonProviderContribution()`），Core 的 `resolveCoreProviderDependencies()` 解析依赖，再把结果按能力分组为普通 compile options
- Standard 只提供 Definition 和 Provider，不维护全局注册表，也不创建第二套 lookup 规则

直接 Definition 输入就是最终的 compile option 值；provider contribution 则是声明 roots、dependencies 与 runtime 数据集的闭包。Core 先解析 contribution，再产出同一套普通的 `pathKinds`（或其它能力）数组。

## 持久化与限制

IR 只保存图形数据，例如节点的 `shape: 'cross'`、路径中的箭头名称或 Path kind 名。Definition、Provider 和 maker 属于运行时装配内容，不会写入 IR、Scene 或持久化 JSON。

导入 Standard 子入口也不会自动影响其他编译调用。每次编译都应显式传入当前图需要的 Definition 或集合；如果 IR 引用了未装载的能力，Core 会在 registry lookup 时报告错误。重复注册同一个 key 或 provider key 时，Core 也会明确拒绝冲突。
