---
title: 能力装载
description: 通过直接 CompileOptions 注入或 adapter 的 provider graph 装配 Standard 可选能力，同时始终复用 Core 的 registry 与 compile。
---

持久化 IR 只保存 JSON-safe 数据，Definition 中包含运行时逻辑，必须在编译前装配。本页区分两条明确路径：直接 IR 宿主传入完整 Definition 集合；React、Vanilla 和 Tier 2 authoring 由 adapter 声明 provider contribution，再由 Core 解析本次所需的闭包。

Standard 不提供全局注册、preset、bundle 或隐式全集。可选 shape、arrow、clip 与 path generator 仅从各自的 `@retikz/standard/<capability>` 子入口导入；`@retikz/standard` 根入口只保留 composites，不聚合这些 Definition。

## 直接 Definition 注入

直接编译、恢复持久化 IR 或已经掌握完整依赖集合的宿主，应把每个 Definition 放入对应的 Core compile option：

```ts
import { compileToScene } from '@retikz/core';
import { DiamondArrowDefinition } from '@retikz/standard/arrow';
import { CompoundClipDefinition } from '@retikz/standard/clip';
import { ParabolaPathGeneratorDefinition } from '@retikz/standard/path-generator';
import { CrossShapeDefinition } from '@retikz/standard/shape';

const result = compileToScene(scene, {
  shapes: [CrossShapeDefinition],
  arrows: [DiamondArrowDefinition],
  clips: [CompoundClipDefinition],
  pathGenerators: [ParabolaPathGeneratorDefinition],
});
```

React 的 `<Layout>` 也暴露相同的 `shapes`、`arrows`、`clips` 和 `pathGenerators` 入口。调用方仅传入当前图真正使用的项；这不是动态 import，也不改变其他编译调用的 registry。

## adapter 的 provider graph

React、Vanilla 和第一方 Tier 2 在 authoring 阶段可声明 `CoreProviderContribution`。一个 contribution 由实际需要的 roots 和静态携带的 providers 组成；普通 provider key 使用 `capability + name`，composite key 使用 `namespace + type`。

Core 的 `resolveCoreProviderDependencies()` 统一处理 roots、传递依赖和与显式 definitions 的合并，然后产生 `shapes`、`arrows`、`clips`、`pathGenerators`、`composites` 等普通 compile options。Standard 子入口只提供静态 Definition 或 provider；它不实现合并、去重、lookup 或第二套 registry。

## 执行与持久化边界

1. 直接宿主显式传入 Definition，或 adapter 为已创作的能力声明 contribution
2. Core 在 compile 前解析本次 roots 的 dependency-first 闭包，并检查缺失、循环和冲突
3. Core 将结果与宿主的显式 definitions 合并到对应 compile options
4. Core 使用唯一 registry 校验 IR、查找 Definition 并生成 Scene 与诊断

provider、maker 和 dataset 只存在于 authoring 与编译装配阶段。它们不得进入 IR、Scene、artifact、manifest 或持久化 JSON。

## 错误与限制

| 情况                                        | 结果                                                   |
| ------------------------------------------- | ------------------------------------------------------ |
| root 或传递依赖缺少 provider                | Core resolver 在 maker 与 compile 前报告完整依赖链     |
| 同一 provider key 的 maker 或有序依赖不同   | Core resolver 明确失败，不采用 first-wins 或 last-wins |
| provider 结果与显式 Definition 使用相同 key | 相同 Definition 对象可去重；不同对象明确失败           |
| IR 引用未装配的可选能力                     | 对应 Core registry lookup 明确失败并报告可用项         |
| 将 Definition 或 provider 写入持久化 JSON   | 不允许；JSON 只保存 schema 定义的数据                  |
