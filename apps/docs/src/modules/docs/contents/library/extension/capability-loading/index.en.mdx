Extension definitions are not registered automatically. Import them from the `@retikz/extension` root and pass them to React `Layout` or the Vanilla compilation entry.

## How to use

There are two import styles. Import individual Definitions when the figure needs only a few capabilities; use the matching `ExtensionXxxDefinitions` collection when you want the complete official extension set for a capability family.

### Style one: import individual Definitions

Import only the Definitions used by the current figure and pass them to the matching compile options:

```tsx
import { Layout } from '@retikz/react';
import {
  DiamondArrowDefinition,
  CircleClipDefinition,
  RibbonPathKindDefinition,
  CrossShapeDefinition,
} from '@retikz/extension';

<Layout
  extensions={{
    shapes: [CrossShapeDefinition],
    arrows: [DiamondArrowDefinition],
    clips: [CircleClipDefinition],
    pathKinds: [RibbonPathKindDefinition],
  }}
>
  {/* Figure content */}
</Layout>;
```

Vanilla uses the same Definitions:

```ts
import { renderToSvgString } from '@retikz/vanilla';
import {
  DiamondArrowDefinition,
  CircleClipDefinition,
  RibbonPathKindDefinition,
  CrossShapeDefinition,
} from '@retikz/extension';

const svg = renderToSvgString(input, {
  compile: {
    shapes: [CrossShapeDefinition],
    arrows: [DiamondArrowDefinition],
    clips: [CircleClipDefinition],
    pathKinds: [RibbonPathKindDefinition],
  },
});
```

### Style two: use the complete official Definition collections

When the figure can use every official extension in a capability family, import its collection:

```tsx
import { Layout } from '@retikz/react';
import { ExtensionArrowDefinitions, ExtensionClipDefinitions, ExtensionShapeDefinitions } from '@retikz/extension';

<Layout
  extensions={{ shapes: ExtensionShapeDefinitions, arrows: ExtensionArrowDefinitions, clips: ExtensionClipDefinitions }}
>
  {/* Figure content */}
</Layout>;
```

Vanilla passes the same collections to `compile`:

```ts
import { renderToSvgString } from '@retikz/vanilla';
import { ExtensionArrowDefinitions, ExtensionClipDefinitions, ExtensionShapeDefinitions } from '@retikz/extension';

const svg = renderToSvgString(input, {
  compile: {
    shapes: ExtensionShapeDefinitions,
    arrows: ExtensionArrowDefinitions,
    clips: ExtensionClipDefinitions,
  },
});
```

| Style                      | Use it when                                                                                                         |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| Individual Definition      | The figure uses only selected capabilities                                                                          |
| `RibbonPathKindDefinition` | Ribbon needs one direct Path kind Definition; Ribbon does not export a full `ExtensionRibbonDefinitions` collection |
| `ExtensionXxxDefinitions`  | The figure can use every Definition in a family                                                                     |

Clipping uses one complete Definition. Every item in `clips` owns its spec schema, shape schema, resolve, and lowering stages. On-demand loading passes the actual `XxxClipDefinition`; the complete family needs only `ExtensionClipDefinitions`.

When an adapter assembles a provider graph before compilation, use the matching `ExtensionShapeProviders`, `ExtensionArrowProviders`, or `ExtensionClipProviders`, and use `createRibbonProviderContribution()` for Ribbon. `ExtensionClipProviders` contains five complete clip providers but remains a catalog; the resolver materializes only the root-reachable closure. Providers assemble Definitions; they do not replace the `shapes`, `arrows`, `clips`, or `pathKinds` arrays accepted by `Layout` or `compile`.

## How compilation works internally

Both Definition styles end up in the same Core compilation path:

<ComponentPreview files="capability-loading-flow" hideCode size="xs" />

The individual Definition and complete collection on the left are simply two assembly inputs; both converge on the same Core compilation path. The provider graph organizes Definitions before compilation, while the IR only looks up already assembled capabilities by name during consumption.

- With direct Definitions, Core places them in the corresponding `shapes`, `arrows`, `clips`, or `pathKinds` registry
- With Providers, an adapter collects `CoreProviderContribution` (for example, `createRibbonProviderContribution()`); Core's `resolveCoreProviderDependencies()` resolves dependencies and groups the results into ordinary compile options
- Extension supplies Definitions and Providers only. It does not maintain a global registry or a second lookup rule

Direct Definition input is the final compile option value. A provider contribution is a closure that declares roots, dependencies, and runtime datasets; Core resolves that contribution before producing the same ordinary `pathKinds` (or other capability) array.

## Persistence and limits

IR stores figure data such as a node's `shape: 'cross'`, an arrow name, or a Path kind name. Definitions, Providers, and makers are runtime assembly values; they never enter IR, Scene, or persisted JSON.

Importing a Extension root entry also has no effect on other compilations. Each compilation should explicitly receive the Definitions or collections it needs. If the IR refers to an unloaded capability, Core reports an error during registry lookup. Conflicting duplicate Definition or provider keys are also rejected explicitly.
