Layout schemas persist container and item configuration. Definitions, the Core compile context, and adapters are runtime objects. Layout owns generic layout solving, while Core proposes two-axis conditions to children, isolates probe candidates, replays selected candidates, and publishes typed artifacts.

> This page covers Definition loading and execution rather than schema fields. See [Contract - Input](/library/layout/reference/contract-input) for persisted configuration and [Contract - Artifact](/library/layout/reference/contract-artifact) for solved results.

## Loading definitions

| Granularity    | Public entry                                                              | Purpose                                                   |
| -------------- | ------------------------------------------------------------------------- | --------------------------------------------------------- |
| One definition | `FlexLayoutDefinition`, `GridLayoutDefinition`, `OverlayLayoutDefinition` | Register one layout composite with Core                   |
| React          | `FlexLayout`, `GridLayout`, `OverlayLayout`, `LayoutItem`                 | Build canonical IR and contribute definitions to `Layout` |
| Vanilla        | `LayoutInputEmbedAdapters`                                                | Recognize all three embeds in Scene, mount, or SSR hosts  |

Pass one or more of the three layout Definitions directly in `CompileOptions.composites`. React and Vanilla adapters produce the same Layout IR and contribute the same Definitions; their adapter convenience arrays do not become Core compile presets.

## One layout transaction

A layout container is a Core layout-aware composite. One compilation proceeds through these deterministic stages:

1. **Parse input**: Core resolves the definition by `namespace` and `type`, then validates canonical IR with its schema.
2. **Probe children**: the container calls `layoutChild` for minimum, natural, ranged, or exact candidates. Results carry the parent-resolved `slotSize`, real `allocationBounds`, `visualBounds`, and available alignment guides.
3. **Solve the container**: Layout solvers use container rules, available space, and probe measurements to resolve tracks, lines, slots, and translations.
4. **Replay selected candidates**: each child replays only its selected candidate. Discarded probes publish no primitives, resources, namespaces, or artifacts.
5. **Publish results**: Core wraps the Layout value in an occurrence-aware composite artifact and returns it with the final Scene.

Fixed geometry may refuse a smaller slot, so `slotSize` and real `allocationBounds` remain distinct. Containers do not guess another main-axis distribution after refusal. Determinate undersizing is represented through overflow and visible bounds, while invalid or unsolvable configuration fails loudly.

Nested layouts remain in the same Core compilation. An inner container receives the outer proposal as an ordinary child. Every composite occurrence publishes an artifact with a local key space, without relying on a public id as an instance selector.

## Direct Core usage

```ts
import { compileToScene } from '@retikz/core';
import {
  FlexLayoutArtifactSchema,
  FlexLayoutDefinition,
  GridLayoutDefinition,
  OverlayLayoutDefinition,
} from '@retikz/layout';

const output = compileToScene(scene, {
  composites: [FlexLayoutDefinition, GridLayoutDefinition, OverlayLayoutDefinition],
});
const envelope = output.artifacts.find(
  artifact => artifact.kind === 'composite' && artifact.namespace === 'layout' && artifact.type === 'flexLayout',
);
const artifact = FlexLayoutArtifactSchema.parse(envelope?.value);
```

Hosts that need one container may put only that Definition in `compile.composites`; add the other Definitions when the figure uses the complete family. `occurrence.sourcePath` and `occurrence.expansionPath` distinguish nested or repeated instances. Parse `value` with the matching `XxxLayoutArtifactSchema`.

## React

The three `@retikz/layout-react` containers are embeddable Tier 2 components. Their direct children must be `LayoutItem` elements with the matching `kind`. Fragments and arrays flatten transparently, but ordinary JSX nodes cannot bypass item semantics.

Every `LayoutItem` requires exactly one of `children` or `ir` and must produce exactly one `IRChild`. React `itemKey` becomes canonical JSON `key`; it never reads React's reserved `key`. Nested Layout containers may contribute the same family, while external datasets or foreign Tier 2 runtime contributions remain the outer host's responsibility.

React containers start no local compilation and perform no DOM measurement. They contribute IR and definitions to the outer `Layout`, which compiles and renders the complete tree. Observe artifacts through the outer host.

## Vanilla

`flexLayout()`, `gridLayout()`, and `overlayLayout()` return `InputEmbed` values. Scene, mount, or SSR hosts need the matching adapter; use `LayoutInputEmbedAdapters` for the complete family.

Each adapter calls the same `createXxxLayout()` factory as direct authoring and contributes the layout Definitions required by its family. Vanilla therefore shares schemas, definitions, solvers, and artifact semantics with direct Core compilation and React.

## Layout Inspector

Layout Inspector is an optional runtime development capability. It never enters Layout IR or changes typed layout artifacts. `@retikz/layout/inspect` owns the three Inspector Definitions, option schemas, and presets. `@retikz/layout-react/inspect` and `@retikz/layout-vanilla/inspect` own host wiring. Base Layout entries do not depend on `@retikz/inspect`.

Flex, Grid, and Overlay Inspectors read final typed artifacts observed by Core and return ordinary Core Path, Node, and pattern-paint children. `@retikz/inspect` compiles those children as isolated fragments and maps them to ordinary Render readonly layers. SVG paints a `pointer-events="none"` group after the primary figure. Canvas paints after the primary bitmap without adding auxiliary primitives to hit testing. Only the primary Scene determines the viewBox, primary resources, animation, and normal interaction.

### Color, pattern, and line style

The overlay uses three independent visual channels instead of overloading color with both geometry class and nesting depth:

| Channel    | Meaning                 | Rule                                                                                                                                                                   |
| ---------- | ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Color      | Final layout occurrence | Inspect assigns `colorScope` in final request order and supplies a regular color from the nine-color cycle plus the fixed warning color through `InspectionAppearance` |
| Pattern    | Spacing semantics       | Layout uses ordinary `lines` pattern paints: margin and fixed gaps use `-45°` `/`, padding uses `45°` `\`, size is 12, and line width is 1; none adds a base fill      |
| Line style | Geometry class          | Container, content, item boxes, Flex lines, Grid tracks/cells/spans, Overlay placements, and alignment guides are dashed; anchor crosshairs are solid                  |

Regular auxiliary content from one occurrence shares a color. Nested containers receive colors from their own final occurrences. The palette repeats from the tenth occurrence, so color is a quick ownership cue; the occurrence locator remains the exact identity. Overflow warnings are ordinary translucent fills, and labels are ordinary Nodes.

Paint order is spacing hatch / boundary underlay → family structure → box outline → overflow warning → guide/anchor → label. `bounds.content` and `bounds.slot` control only their outlines; `spacing.padding` and `spacing.margin` independently control both texture and boundary. Margin, padding, and fixed gaps use independent dashed lines for their boundaries. A ring outlines only its outer and inner perimeter, never the seams between its hatch pieces. `distributedSpace` shows only the dashed perimeter of unused content and keeps its interior transparent. If a spacing boundary is already fully covered by a content or slot outline, Flex line, or Grid track, that segment is painted once; enabling any category alone still keeps its complete visible boundary.

### Three selection scopes

| Scope            | React                                                              | Vanilla                                                                  | Meaning                                                |
| ---------------- | ------------------------------------------------------------------ | ------------------------------------------------------------------------ | ------------------------------------------------------ |
| Whole figure     | `LayoutInspectLayout request={...}`                                | Figure `createInspectionVanillaAuthoring(...)`                           | Select all matching occurrences by Inspector key       |
| Authored subtree | `LayoutInspectScope request={...}`                                 | Scope `createInspectionVanillaAuthoring(...)`                            | Select authored descendants of that Scope              |
| One container    | `InspectFlexLayout` / `InspectGridLayout` / `InspectOverlayLayout` | `inspectFlexLayout()` / `inspectGridLayout()` / `inspectOverlayLayout()` | Select one occurrence without selecting nested layouts |

React requires `LayoutInspectLayout`, which hosts a registry preloaded with all three Definitions. Vanilla passes `createLayoutInspectionVanillaDriver()` as the render or mount `compileDriver`. `LayoutInspectScope request={false}` and `createLayoutInspectionBarrier()` are hard barriers that descendants cannot cross.

Requests for one Inspector resolve in scene → outer subtree → inner subtree → self order, with declaration order breaking ties. Object-valued `bounds` and `spacing` merge individual fields; switching between a boolean and an object replaces the whole group with the later value. A request value of `false` disables the current layer but a deeper request may enable it again. With all requests omitted, the observer captures no layout output and creates no readonly layers.

A request value of `true` uses one full canonical profile: container, content, slot, allocation, padding, margin, overflow, and alignment guides are on; visual bounds and labels are off. Object values override only explicit fields, so `{ spacing: { padding: false } }` disables only padding texture.

The docs playground “Recommended” profile is intentionally smaller: Flex shows the content outline, Flex line regions, and fixed gaps; Grid shows the content outline, track bounds, and fixed gaps; Overlay shows only the content outline. “All” enables every detail, “Off” changes only the master switch, and Reset returns to Recommended.

Flex enables `lines`, `gaps`, and `distributedSpace` by default. Grid enables `tracks`, `gaps`, `distributedSpace`, and `spans`, while `cells` stays off. Overlay enables `placements` and `anchors`, while `stacking` stays off.

For Flex and Grid, `gaps` controls resolved authored gaps and `distributedSpace` controls positive free space introduced by `justifyContent` or `alignContent`. Fixed gaps use `/`, opposite the padding hatch; distributed space keeps a transparent interior and contributes only uncovered dashed perimeter segments. The inspector consumes resolved `artifact.spacing` segments and does not classify every empty interval between slots or tracks as a gap.

Each `InspectXxxLayout` accepts only `false`, `true`, or its corresponding sparse option object. Unknown keys and invalid types fail loudly. Inspect admits selection and sparse inputs before Core traversal, then merges and resolves complete options after final occurrences settle. A Layout Inspector reads only same-compile typed artifacts and returns ordinary Core children. A retained update commits the primary frame, artifacts, and readonly layers atomically; failure publishes no partial frame.
