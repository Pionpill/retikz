A line chart with a title contains text, a plotting area, and a container. Chart knows where the title belongs and which fields define the line plot. Layout components allocate space, and Core compiles text and geometry into a Scene. This page follows the data exchanged between those packages until the final primitives enter the Scene.

Start with the declarations, IR, and Scene introduced in [Rendering Pipeline](/kernel/components/runtime-mechanics/rendering-pipeline). This page covers composition across packages. For Core's isolated probes, resource replay, and references, see [Composite Compilation](/kernel/packages/core/composite-compilation).

## Overall flow

The example uses three records: `(1, 2)`, `(2, 4)`, and `(3, 3)`, with the title “Observations” and an outer Chart size of 480 × 320. The following figure uses a real ConnectedScatterChart. Core handles both the title and axis text; Plot computes point positions from the data and available plotting area, then connects them in ascending x order.

The following objects travel between the components:

- **Source IR**: serializable input describing this chart, including its line type, field mappings, and title.
- **Definition**: a registered Core capability with an input schema and compilation callback.
- **Size proposal**: a parent's request to lay out a child under particular size requirements.
- **Layout result**: the child's allocated size, bounds, and compiled result available for submission.

Arrows show the main processing order. Layout recursively enters child components and receives their size feedback.

## Input and definitions

After React or Vanilla receives authored input, an adapter turns it into high-level component Source IR and contributes the capabilities needed for compilation. Core needs to know what to compile and which Definition will handle it.

Providers declare dependencies between capabilities and create Definitions. In this example, Chart depends on Surface, FlexLayout, and Plot. Vanilla collects the providers, and Core assembles their definitions in dependency order for use during child traversal.

| Handoff     | Example content                                    | Consumer             |
| ----------- | -------------------------------------------------- | -------------------- |
| Source IR   | Chart configuration, field mappings, and title     | Chart Definition     |
| Datasets    | The three records shown in the chart               | Plot data processing |
| Definitions | Chart, Surface, FlexLayout, Plot, and dependencies | Core traversal       |

With these definitions ready, Core can invoke compilation capabilities through the component structure. Size allocation and geometry generation happen during the compilation that follows.

## Component expansion

When Core reaches the Chart declaration, it calls the matching Definition. Chart resolves the theme, field mappings, and line recipe into a complete Plot declaration, then arranges the title and plotting area.

With a title present, `resolveChartPresentation` creates a Surface containing a vertical FlexLayout. Inside it, the title becomes a regular text Node, while Plot becomes a layout item with `grow: 1` and `min: 0`. The title supplies its text size; Plot participates in remaining-space allocation. Optional subtitle, note, and source regions occupy fixed slots. This example only has a title and Plot.

The figure shows the child declarations generated by Chart. Edges mean containment, with layout-item wrapper fields omitted. They do not represent React DOM nesting or separate canvases produced by each layer.

<ComponentPreview files="composition-tree" hideCode type="illustration" size="md" />

Surface owns general container behavior such as background and padding. FlexLayout owns child arrangement and space allocation. Plot owns scales, coordinates, marks, and axes. These capabilities come from Standard, Layout, and Plot respectively and cooperate through the same Core composite contract.

If `presentation` is omitted entirely, Surface wraps Plot directly without a FlexLayout. The structure shown here belongs to the current Chart implementation; other high-level components can use different structures.

Themes follow the same ownership boundaries. Chart resolves its presentation defaults and generates title styles; Plot consumes plotting-area and mark theme settings; Core processes the resulting Node and Path declarations. Explicit title styles override the corresponding presentation defaults.

## Layout cooperation

After creating child declarations, each child needs an allocation. A parent sends size requirements through a proposal, receives the child's layout result, and uses it to determine placement. Each axis can request an intrinsic size, an exact size, or a bounded range. This example follows exact proposals.

Chart explicitly sets `layout.width: 480` and `layout.height: 320`, so it proposes 480 × 320 to Surface. For an axis without an authored Chart dimension, it instead accepts an exact parent proposal or clamps its preferred size to the parent's range.

The example also explicitly sets padding to 16 on every side. Surface therefore passes a 448 × 288 content area to FlexLayout: `480 - 16 - 16` by `320 - 16 - 16`. This only subtracts container padding; Plot has not yet allocated space for its axes or other internal elements.

| Layer      | Requirement received             | Handoff to children                                   |
| ---------- | -------------------------------- | ----------------------------------------------------- |
| Chart      | Explicit outer size of 480 × 320 | Exact size proposal for Surface                       |
| Surface    | 480 × 320 with padding 16        | 448 × 288 content area for FlexLayout                 |
| FlexLayout | Content area, title, and Plot    | Child proposals and final translations                |
| Plot       | Its allocated width and height   | Core declarations for axes, points, and other content |

FlexLayout queries child size contributions, distributes space according to layout rules, and obtains child results under the final proposals. Core measures the title. Plot accepts its allocation and reserves internal space for axes, legends, and other elements. The 448 × 288 area therefore belongs to all Flex content; it is not the line coordinate range. Text height and the final plotting area also depend on fonts, themes, and axis configuration.

The title sits above Plot. If its actual occupied height increases while the outer height stays fixed and the content still fits, Plot has less height available. This feedback happens within one compilation. For scheduling across updates, see [Incremental Updates](/kernel/components/runtime-mechanics/incremental-updates).

After layout returns, FlexLayout translates each child into place; Surface then positions the content inside its padding. Insufficient space has explicit failure boundaries. For example, Surface fails if its exact proposed width is smaller than the sum of left and right padding. A size proposal does not guarantee that all content can fit.

## Compilation output

Once Plot has a size, its scales and coordinates map the three records to point positions, connecting them in ascending x order and producing Core Scope, Node, and Path declarations. It compiles these through Core and returns the selected child layout result. The title Node follows Core's text and node compilation path as well.

Each layer submits its selected child result through `replay`. FlexLayout adds child translations. Surface adds the padding translation and any required background, border, or clipping. Chart returns the whole container result. These results enter one Scene, whose primitives, group transforms, and resources are consumed by Render.

Allocation bounds guide parent layout, while visible bounds describe drawn content. They can differ: Plot reports its entire allocated region to its parent, but the line path covers only part of it. This distinction helps explain whether empty space was reserved by layout or simply contains no data points.

Core provides recursive compilation, measurement, and result submission. Chart, Surface, FlexLayout, and Plot choose their own structures and layout policies. New high-level components can use a composite Definition in the same way.
