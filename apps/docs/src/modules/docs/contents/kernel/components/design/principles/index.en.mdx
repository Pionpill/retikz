retikz separates describing a drawing, supplying capabilities, and executing output. Authors express intent as IR, Core compiles IR into a backend-neutral Scene, and renderers only execute that Scene. React, Vanilla, LLMs, and multiple rendering backends can therefore share one set of drawing semantics.

## Architecture at a glance

Start with two stable artifacts: **IR is the description boundary, and Scene is the execution boundary**. React JSX and Vanilla `InputScene` data converge through one normalization flow, while validated external IR enters compilation directly. Core outputs Scene rather than SVG strings, DOM objects, or Canvas pixels.

Solid arrows show data flow: author input becomes IR, `compileToScene` creates Scene and typed artifacts together, and a renderer emits the Scene as SVG or Canvas. The secondary nodes below show optional supporting capabilities: `@retikz/tex` enters compilation as a lowerer, while `@retikz/inspect` reads the final compilation result to produce read-only helper content. Dashed arrows distinguish these supporting relationships from the main data flow; neither creates a special IR or renderer branch.

See [Layers · Packages](/kernel/components/design/layers#packages) for all nine Kernel packages and their responsibilities. The figure shows the main input-to-rendering path, not every dependency.

## Built-ins and extensions share one path

Extensible capabilities do not use a built-in switch followed by an extension patch. Each capability begins with an `XxxDefinition` protocol. Built-in items and custom items created with `defineXxx(...)` enter one effective registry, after which compile looks up and consumes both through the same key path.

<ComponentPreview files="principles-registry" size="md" hideCode />

“Built-ins and extensions are first-class” means three concrete things:

1. **One protocol**: both satisfy the same Definition, with no hidden fields reserved for built-ins.
2. **One registry**: `BUILTIN_*` and `options.xxx` become one `ReadonlyMap` at the start of each compile call.
3. **One consumer path**: resolvers, diagnostics, and compile consumers do not branch on where a key came from.

Built-ins register first and custom items follow. Registry construction rejects empty and duplicate keys. When a consumer later encounters an unknown key, that capability's contract determines whether to throw or warn and skip. First-class therefore means the same protocol and execution path, not that a custom item can silently override a built-in. See [Extension Mechanisms](/kernel/reference/runtime/extensions) for extension families, injection points, and failure semantics.

## Capability ownership

Capabilities that only change authoring notation without adding drawing semantics belong to [Sugar](/kernel/components/design/sugar). Equivalent expressions and expansion constraints are explained there.

Once the overall framework is clear, decide whether a request changes authoring ergonomics, shared drawing semantics, a high-level domain model, a replaceable compile strategy, or backend runtime behavior. Design from that first owner.

<ComponentPreview files="principles-placement" size="lg" hideCode />

Each arrow points to the first owner, while the second line in the node shows common implementation anchors; this does not mean only one package can change. One capability may need authoring, contract, compile, and runtime wiring, but each semantic layer has one source of truth.

| Request signal                 | First owner             | Boundary failure                       |
| ------------------------------ | ----------------------- | -------------------------------------- |
| Friendlier JSX / InputScene    | React / Vanilla adapter | Adapters produce different geometry    |
| Shared drawing semantics       | `@retikz/core`          | Adapter / renderer repeats layout      |
| High-level domain model        | Domain composite        | Chart / domain fields enter core IR    |
| Pure geometry and numeric work | `@retikz/math`          | Math depends on schema or runtime      |
| SVG / Canvas execution         | `@retikz/render`        | DOM / Canvas objects enter Scene       |
| Optional lowering such as TeX  | Dedicated lowerer       | Heavy dependency becomes core-required |

The central constraint is that upper packages obtain foundations from `@retikz/foundation`, `@retikz/core`, or `@retikz/math`. Adapters may change authoring and domain packages may preserve high-level IR, but neither may create parallel IR, rendering semantics, or geometry foundations.

## Capability completeness

Rendering one built-in example does not make a capability complete. Every long-lived capability must answer four groups of questions:

| Axis            | Required answer                                                                 | Action when missing                 |
| --------------- | ------------------------------------------------------------------------------- | ----------------------------------- |
| Problem / owner | What root problem is solved, who owns it, and what remains outside the scope?   | Reassign ownership or narrow scope  |
| Internal model  | Can IR, pure computation, and compile express it without host special cases?    | Move down a shared contract         |
| Extension       | Do built-ins and custom items share Definition, registry, resolver, and errors? | Complete one extension path         |
| End-to-end loop | Are input, compile, Scene, renderer, adapters, tests, and docs connected?       | Record the missing links explicitly |

When a subpackage lacks a capability, first decide whether the need is composition, an extension gap in the current domain, or a missing shared foundation. Keep only composition in the caller; add a domain contract for the second case or move the foundation to its true owner for the third.
