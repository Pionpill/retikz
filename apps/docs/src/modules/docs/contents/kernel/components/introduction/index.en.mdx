Kernel is the general drawing foundation of retikz: use nodes, named coordinates, and paths for flowcharts, geometry illustrations, and relationship diagrams. Author with React or Vanilla and render to SVG or Canvas. Start with Plot for statistical data mappings and grammar of graphics, or Standard for reusable composite components.

## Core Concepts

This diagram does one small thing: it places two named nodes, then uses one arrowed `Draw` to connect them. It shows retikz's basic flow: place reusable points first, then stitch primitives together with path relationships.

retikz's beginner mental model has two layers: first describe **what each primitive is**, then describe **the connections and geometry between primitives**. A `Node` is a visible object, while `Draw` connects objects through named references.

## An AI-Friendly Shared Format

<ComponentPreview files="/about/blog/core-philosophy/pipeline" hideCode />

React, Vanilla, and AI-generated input all normalize to the same IR. Because IR is ordinary JSON, it can be validated with a schema, persisted, transported, and edited before SVG, Canvas, or another renderer uses it.

The benefits of one shared format are straightforward:

- You maintain saving, editing, and rendering around one IR contract.
- You do not maintain separate figure formats for JSX, AI output, and each renderer.
- The same figure data can be reused across authoring surfaces and runtimes.

Continue with [Layers](/kernel/components/design/layers) to see how IR becomes Scene and how the packages work together. Use [Architecture](/kernel/components/design/principles) when deciding which layer should own a capability.

React / Vanilla notation or AI-generated declarations form IR, which compiles into Scene: drawing results with positions and styles already resolved. A renderer then displays those results.

## General Primitives, Arbitrary Composition

retikz uses a small set of components with explicit responsibilities. They can be used directly or combined through nesting, named references, and authoring conveniences.

| Concern                    | Common components                              | Responsibility                                                                    |
| -------------------------- | ---------------------------------------------- | --------------------------------------------------------------------------------- |
| **Canvas and groups**      | `<Layout>` `<Scope>`                           | Host the figure, group local primitives, and apply styles or transforms           |
| **Objects and points**     | `<Node>` `<Coordinate>`                        | Describe visible objects or named coordinates used for positioning and references |
| **Path relationships**     | `<Path>` `<Step>`                              | Precisely describe a path and its line, curve, or arc actions                     |
| **Authoring conveniences** | `<Draw>` `<Arc>` `<Circle>` `<Rectangle>` etc. | Combine base primitives through concise parameters without adding new semantics   |

## Relation to TikZ

<Comparison target="tikz" title="Relation to TikZ">

retikz's naming, path actions, and anchor model are direct tributes to LaTeX's TikZ package.

| Aspect        | LaTeX TikZ      | retikz                 |
| ------------- | --------------- | ---------------------- |
| Runtime       | LaTeX compiler  | Browser / Node         |
| Syntax        | `\node` `\draw` | `<Node>` `<Draw>`      |
| Output        | PDF / SVG       | SVG / Canvas           |
| Interactivity | None            | React / runtime events |
| Persistence   | `.tex` source   | JSON IR                |

You do not need to know TikZ to use retikz. retikz borrows naming vocabulary (node / path / anchor / step), while figures can be described with React components or a Vanilla `InputScene`.
