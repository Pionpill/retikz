## 隐式根作用域

给一组子图元统一设置样式时，`rootScope` 并不是另一套样式系统。Layout 会按需把 JSX children 包进一层普通 Scope，让它们沿用 Scope 的继承与覆盖规则。

例如，下面的根配置等价于在 Layout 内手写一层 `<Scope defaults={{ node: { style: { fill: 'lightblue' } } }}>` 包住这些节点：

```tsx
<Layout rootScope={{ defaults: { node: { style: { fill: 'lightblue' } } } }}>
  <Node id="a" position={[0, 0]}>
    A
  </Node>
  <Node id="b" position={[80, 0]} style={{ fill: 'orange' }}>
    B
  </Node>
</Layout>
```

A 继承浅蓝填充，B 的显式填充覆盖默认值。这里的 **defaults** 是给未显式配置的后代图元提供默认值，不是强制重写每个节点的属性；`rootScope.style` 则向后代提供 `fill / stroke / opacity` 等通用绘图样式。

包装与否取决于是否存在有效覆盖，而不是有没有传入 `rootScope` 这个对象：

- **无有效覆盖**：不传、传 `{}`，或只传 `style: {}`、`defaults: {}` 等空覆盖时，直接使用原 children，不增加合成 Scope。
- **有有效覆盖**：有实际样式、默认值或有效的 `defaults.reset` 时，包装一层普通 Scope，沿用既有继承规则。`reset` 为 `true` 或非空通道列表时表示切断相应的外层样式继承；`false` 或空列表本身不触发包装。
- **直接传入 ir**：使用 IR 已描述的完整子图，忽略同时传入的 children 和 `rootScope`。要改变其中的作用域，应修改 IR 本身；宿主 CSS `style` 仍然生效。

**这层合成 Scope 不是局部命名空间。** `rootScope` 只接收 `style / defaults`；需要 `localNamespace` 时，应在子图中显式使用 Scope，命名与引用机制见 [Scope 用法](/kernel/components/scope/usage)。

## 自动视窗

没有指定 `viewBox` 时，Layout 的视窗不是由页面容器尺寸决定的，而是由绘图内容的布局边界决定的。这里的“布局边界”是各图元贡献的最左、最上、最右、最下范围合并得到的包围框，不只是节点中心点的范围；它在编译时得到，不是渲染后再读取 DOM 像素。

先选择视窗来源：Layout 的 `viewBox` prop 优先，其次是输入 IR 中的 `viewBox`；两者都没有，才根据内容自动计算。显式视窗直接决定坐标窗口，不再按内容追加自动留白。

自动计算只需要理解两步：合并内容边界，再向四边扩展 padding。当前默认 padding 为 10 个绘图单位，不是宿主 CSS 的 `padding`。Core 编译选项支持配置它，但 Layout 当前没有暴露这个 prop；需要自行控制取景留白时，用显式 `viewBox`。

<ComponentPreview files="layout-auto-viewport" size="xs" hideCode />

假设内容边界为 `x: 20, y: 30, width: 80, height: 40`，默认留白后得到 `x: 10, y: 20, width: 100, height: 60`。一般地，边界为 `(x, y, w, h)`、留白为 `p` 时：

$$
(x', y', w', h') = (x-p,\ y-p,\ w+2p,\ h+2p)
$$

若没有任何内容边界，则直接使用 `{ x: 0, y: 0, width: 100, height: 100 }`，不再在这个兜底范围外加 padding。

因此，移动或增删图元可能连带改变自动视窗。若要在多次更新之间比较相同坐标位置，应显式固定 `viewBox`；仅固定 `width / height` 不能固定取景范围。

## 视窗与显示尺寸

`viewBox` 决定“看哪一段绘图坐标”，`width / height` 决定“这个窗口在页面上占多大”。先确定视窗，再以它的宽高作为显示尺寸的推导依据；反过来，修改显示尺寸不会改写节点坐标，也不会重新定义视窗。

<ComponentPreview files="layout-viewbox-resolution" size="md" hideCode />

以 `viewBox={{ x: 0, y: 0, width: 200, height: 100 }}` 为例，内部宽高比是 2:1：

| 尺寸配置                      | 宿主尺寸    | 推导方式         |
| ----------------------------- | ----------- | ---------------- |
| 不传宽高                      | 200 × 100   | 使用视窗宽高     |
| 只传 `width={400}`            | 400 × 200   | 按比例补齐另一轴 |
| 传 `width={400} height={300}` | 400 × 300   | 保留两轴显式值   |
| 只传 `width="100%"`           | 100% × auto | 留给浏览器排版   |

两轴都给时，Layout 不会把 `400 × 300` 改成 `400 × 200`。宿主尺寸与内部内容怎样适配属于 SVG / Canvas 的呈现行为，不能把宿主尺寸推导理解成重新布局图元。

SVG 和 Canvas 共用这套显示尺寸计算。CSS 字符串不会被当作绘图坐标解析。

## 主题与局部覆盖

`theme`、`rootScope` 和宿主 `style` 都可能影响外观，但不是同一个配置对象的三层优先级：

| 配置                         | 作用位置                     | 用来决定什么               |
| ---------------------------- | ---------------------------- | -------------------------- |
| `theme`                      | Scene 及消费主题的 Composite | 主题风格与明暗模式         |
| `rootScope.style / defaults` | JSX 子图的根作用域           | 绘图样式与图元默认值       |
| `style`                      | SVG / Canvas 宿主            | 页面 CSS，如背景与最大宽度 |

**Composite** 是接收高层描述、再展开为基础图元的组合能力。Layout 把主题写入 Scene，供这些能力读取；它不会把主题选择器直接转换成每个普通 Node 的填充色。具体主题如何生成图元样式由消费它的能力决定。

主题也不只影响 Composite：当图元使用数值颜色（按主色比例派生颜色）时，`mode` 会参与颜色计算；显式的 `'orange'` 等字符串颜色则保持原值。因此不能将“切换主题”理解为统一替换所有图元样式。

同一份主题内部才存在明确的覆盖顺序：继承自 ThemeProvider 的主题、输入场景的主题、Layout 的 `theme`，按此顺序逐字段合并。后面只覆盖显式提供的 `style / mode`，省略字段继续继承，不把前面的整个主题清空。

<ComponentPreview files="layout-theme-overlays" size="xs" hideCode />

例如 Provider 提供 `{ style: 'clean', mode: 'dark' }`，Layout 只传 `{ mode: 'light' }`，最终仍保留 `style: 'clean'`，仅将明暗模式改为 `light`。嵌套 ThemeProvider 也使用相同的字段合并规则。

当 Composite 与 `rootScope` 一起使用时，要看它展开后实际写了什么。例如，根 Scope 默认填充是浅蓝色，而某个 Composite 根据主题生成了显式 `style.fill: 'orange'` 的 Node，那么这个 Node 显示橙色；若它在同一作用域下生成的 Node 没写 fill，则继承浅蓝色。主题不是绕开 Scope 的覆盖开关，最终仍由生成图元的显式属性与作用域继承共同决定。

若要确定普通 Node 的填充色，用节点属性或 `rootScope`；若要限制整幅图在页面上的最大宽度，用宿主 `style={{ maxWidth: '100%' }}`。这些选择对应不同作用位置，不应靠反复切换主题来试探。
