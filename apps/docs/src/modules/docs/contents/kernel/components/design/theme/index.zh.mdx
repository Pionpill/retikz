---

一组图形需要保持共同风格时，可以传递主题环境，而不必在每个对象上重复指定颜色。Theme 描述环境，图元样式描述最终画法；两者不是同一条通道。

## 主题与样式

下图中的组合负责读取主题，把它转换成节点、路径等基础图元的明确样式。渲染器只执行结果，不重新解释主题。

<ComponentPreview files="theme-flow" size="xs" hideCode />

| 内容     | 职责               | 消费者     |
| -------- | ------------------ | ---------- |
| style    | 选择视觉风格       | 主题解析器 |
| mode     | 选择浅色或深色环境 | 主题解析器 |
| colors   | 共享语义色与分类色 | Composite  |
| 图元样式 | 明确填充、描边等   | renderer   |

因此，切换主题不保证手写 Node、Path 自动换色。它们的显式样式仍然有效；只有消费主题的组合才会把环境变成可见差异。

## 公共主题

Kernel 通过 Core 提供默认中性配色，支持 `light` 与 `dark` 两种模式。没有继承或显式选择风格时使用这套基线；根环境默认是 `light`，不需要填写 `style: 'neutral'`。

| 公共内容           | 作用                   |
| ------------------ | ---------------------- |
| `semantic.error`   | 错误                   |
| `semantic.success` | 成功                   |
| `semantic.warning` | 警告                   |
| `semantic.guide`   | 低强调辅助内容         |
| `categorical`      | 区分不同类别的非空色板 |

默认分类色板有 16 色，明暗模式保持类别索引与色相顺序一致，调整明度与饱和度。它只提供可复用的颜色，不规定图表、表格或流程图如何分配这些颜色。

## 数据结构

主题分为两份不同用途的数据：`IRTheme` 保存作者选择，`ResolvedTheme` 是编译当前位置供组合读取的有效环境。

| 数据                  | 字段                       | 含义                       |
| --------------------- | -------------------------- | -------------------------- |
| `IRTheme`             | `style?`、`mode?`          | 稀疏选择，省略字段沿用外层 |
| `ResolvedTheme`       | `style?`、`mode`、`colors` | 继承和风格解析后的只读结果 |
| `ResolvedThemeColors` | `semantic`、`categorical`  | 共享语义色与当前分类色板   |

下面只展示数据形状；`Color` 代表 CSS 颜色字符串，不是新增的公开类型：

```text
IRTheme
  style?: string
  mode?: 'light' | 'dark'

ResolvedTheme
  style?: string
  mode: 'light' | 'dark'
  colors
    semantic: { error: Color, success: Color, warning: Color, guide: Color }
    categorical: 非空 Color 数组
```

`colors` 不写入 `IRTheme`，而是由当前模式和风格解析器生成。自定义风格可逐项覆盖语义色；显式提供分类色板时整体替换默认色板，不要求仍为 16 色。风格定义中的 `resolve` 函数属于运行环境，不进入可持久化 IR。

## 继承

IRScene 是可保存的根绘图声明，Scope 是其中的局部分组；编译后的 Scene 才是渲染器消费的结果。主题按字段从外向内继承：内层只指定 mode 时，仍沿用外层 style；只指定 style 时，仍沿用外层 mode。

例如，根环境是“学术／浅色”，一个子组只改为“深色”，它得到的仍是“学术／深色”，不会重置成另一种风格。主题的继承也不等于节点样式默认值的继承。

## 组合上下文

下面保留扩展作者需要的上下文约束。expand 是把高层对象展开成基础实体的分支，compile 是需要测量与布局反馈的分支；接口详见[复合](/kernel/components/design/composite)。

`expand(node, context)` 与布局感知 `compile(node, context)` 都能读取冻结的 `context.theme`。其中 `mode` 和 `colors` 始终有值，`style` 可以缺省：Core 从默认 light 基线开始，按 IRScene → 外层 Scope → 内层 Scope 逐字段继承 selector，再由默认 palette 或当前 style resolver 生成 `colors`。`colors` 是 detached/frozen 的 Core shared view，固定提供 `semantic.error/success/warning/guide` 与非空 `categorical` palette，不是 Core 图元的隐式样式。

## 消费与边界

style resolver 是按风格名称生成颜色或领域默认值的解析器。probe 是测量子内容的试探编译，replay 则复用已选中的结果；复用时保留原主题，才能保持测量与最终结果一致。detached/frozen 表示这份颜色数据与输入隔离且只读，组合不能通过修改它影响其它对象。

Composite 负责把 shared `colors` 与自己 style resolver 生成的领域 token、palette 或其它默认映射为已经物化的正式 IR。Core 不解释 Tier 2 token，也不拥有 Plot、Chart、Table 的具体 token；Core primitive 与 renderer 也不解释 Theme。普通输出 Scope 与 `context.scope({ theme }, children)` 可以建立更内层环境；replay child 则保留 probe 时已经解析的 Theme，不会在提交位置被重新解释。自定义 style 必须同时注入 Core 与实际消费它的 Tier 2 resolver；任一 registry 缺失该名称都会 fail-loud。

这意味着主题可以随图形声明保存，但自定义风格的实现仍由运行环境提供。缺少实现应暴露配置错误，而不是悄悄换一种风格。
