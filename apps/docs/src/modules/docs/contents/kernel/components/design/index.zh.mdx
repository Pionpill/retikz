同一张图可以由 React 组件书写、保存为 JSON，再交给不同后端显示。设计理念解释这些入口为什么能够协作，以及新增能力时怎样保持一致。了解基础概念与核心概念后即可阅读本总览，不需要先认识源码目录或编译函数。

## 表达、声明与结果

Node、Path 等是基础图元；复合组件（composite）保留高层数据，再展开为基础图元。文中的“对象”泛指图形声明中的实体，并非另一种图元类型。

作者写图的方式称为 DSL，例如 JSX 组件或 Vanilla 的函数调用。可保存的图形声明称为 IR，它保留对象、位置与关系；编译后的 Scene 则包含已经确定的绘制结果。renderer 是执行这些结果、输出 SVG 或 Canvas 的渲染器。

下图重点看中间的 IR 与 Scene：前者支持保存和编辑，后者连接渲染后端。不同写法共享声明和结果，因而不需要各自维护一套几何规则。

## 用一张柱状图理解取舍

假设要保存一张柱状图。可以保存每根柱子的基础图元，也可以保留数据数组与图表配置，在编译时生成柱子。后者保留了“这是图表”的高层意图，属于复合模型；它仍复用基础图元的布局与渲染。

如果只是把一段常见路径写得更短，而没有保留新的高层对象，则属于语法糖。两者都能让书写更方便，但应该保留什么声明不同，不能仅凭代码更短来判断。

主题解决的是另一个问题：多个组件怎样共享风格与颜色环境。真正消费主题的组件把环境转换成图元样式；已经显式指定的 Node / Path 样式不会因为存在主题而自动被替换。

## 从设计问题选择入口

先通过分层理解共同的数据边界，再判断自己的问题是书写便利、高层模型，还是风格共享。架构页把这些选择放回包职责中，帮助确定哪一层应负责实现。

这里讨论“为什么这样分工”。需要跟踪一次调用、检查测量结果或研究主题继承的内部过程时，再进入[内部机制](/kernel/components/internals)。设计理念不把内部执行顺序变成普通绘图的使用前提。
