`contour` is a built-in Node shape that takes an **arbitrary closed vertex ring**: give it a ring of points (`params.points`) and the node's boundary is the closed contour through those points. It runs on the same contour engine as `polygon` / `star`; the only difference is where the vertices come from — `polygon` derives a regular polygon from a side count, while `contour` takes the points you give directly. See [Shapes](/kernel/components/shapes) for the full definition.

One thing sets it apart from the other shapes: it is **a Node shape only**, with no sugar drawing component. To draw an arbitrary closed outline, use [`<Path>`](/kernel/components/draw/path) with `line` steps; `contour` solves a different problem — making that arbitrary contour **still a connectable node** (other lines can target it by id and snap to its boundary).

## As a node shape

Set `shape={{ type: 'contour', params: { points } }}` on `<Node>` and the node is bounded by the closed contour through those points.

### Usage

```tsx
import { Node } from '@retikz/react';
```

```tsx
<Node
  shape={{
    type: 'contour',
    params: {
      points: [
        [-30, 44],
        [30, 30],
        [30, -44],
        [-30, -44],
      ],
      cornerRadius: 8,
    },
  }}
  fill="steelblue"
/>
```

### Examples

`points` is a ring of **local-frame vertices** (at least 3, implicitly closed, with straight edges). You **do not need to pre-center** them — core normalizes by the center of the points' axis-aligned bounding box (AABB) and aligns the node's `position` to that center. The two nodes below use the same shape, but the right one's points are all shifted by a fixed offset: after auto-centering they render identically.

<ComponentPreview files="node-contour" size="sm" />

`cornerRadius` rounds **every vertex** uniformly (user units); omitted / `0` = sharp corners, clamped per corner to the largest non-self-intersecting radius — reusing the same fillet engine as `polygon` / `roundedCorners`.

#### Connectable

The key value of `contour` is that it is **still a Node**: another `<Path>` / `<Draw>` can target it by id, and the endpoint snaps via `boundaryPoint` to the exact intersection on the contour edge (ray ∩ contour), not the bounding box.

### API Reference

| `shape`                       | Boundary                                                               | Parameters                      |
| ----------------------------- | ---------------------------------------------------------------------- | ------------------------------- |
| `{ type: 'contour', params }` | The closed contour through `points` (auto-centered on the AABB center) | `points` (≥3) / `cornerRadius?` |

| Parameter      | Type                           | Default | Description                                                                                                                                  |
| -------------- | ------------------------------ | ------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `points`       | `Array<[number, number]>` (≥3) | —       | Closed local-frame vertex ring (any origin; core auto-centers on the AABB center), implicitly closed, straight edges                         |
| `cornerRadius` | `number` (≥0)                  | —       | Uniform per-vertex fillet radius (user units); omitted / `0` = sharp corners, clamped per corner to the largest non-self-intersecting radius |

## How it works

This section focuses only on the vertex normalization and attachment resolution owned by `contour`. See [Architecture Principles](/kernel/concepts/design/principles) for the full JSX → IR (intermediate representation) → Scene pipeline.

### How any local origin is normalized to the node position

Read the figure from left to right: the same `points` ring sheds the caller's choice of local origin, then becomes a world-space contour centered on `Node.position`.

<ComponentPreview files="contour-normalization" size="xs" hideCode />

Core first computes the AABB center `c` of `points`, then rewrites each vertex as `pᵢ - c`. This removes only a translation of the full ring; it does not change edge lengths, angles, or concavity. The centered ring is then projected into world space around `Node.position`.

Translating every input point by the same amount therefore cannot change the final shape. Rendering and attachment intersection both consume the same normalized contour segments, so the visible boundary and automatic connections do not derive separate geometry.

### Why automatic attachment and standard direction names differ

The top row follows the real contour; the bottom row shows the fallback for standard direction names. Both start from the same node geometry, but they answer different questions.

<ComponentPreview files="contour-attachment" size="sm" hideCode />

When a path targets the node id automatically, the compiler already knows the direction from which the line approaches. `boundaryPoint` can cast a ray from the node center and intersect the sharp or filleted contour. Numeric angle anchors also provide an explicit direction and use the real contour.

Standard direction names such as `top` / `right` ask for a fixed canonical point; they do not carry the incoming direction of a particular line. An arbitrary concave or convex ring may have several local extremes in the same direction, so `contour` avoids inventing named points. Only after the shape lookup has no result does the compiler use the circumscribing AABB's rectangle direction point. `center` always remains the node center and is unaffected by this fallback.
