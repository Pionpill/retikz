## 文字测量与边框尺寸

节点边框需要先容纳正文，再满足形状和最小尺寸约束：

- **文字框**：折行后每行文字占据的范围
- **内容框**：在文字框四周加入 `padding`，为文字留出空间
- **视觉边框**：形状包住内容框后的轮廓，`minimumSize` 为它设置尺寸下限

普通正文在浏览器中通过 Canvas `measureText` 按实际字体、字号和字重测量宽度，再按 `maxTextWidth` 折行（西文按词，中文按字）。文字框取折行后的最大行宽，高度为行数乘以 `lineHeight`（默认字号的 1.2 倍），因此包含行间留白；字形的上升与下降高度用于安排基线。没有浏览器测量器时使用平均字宽估算；公式与混排则按各片段的度量对齐基线。

下图跟踪同一个 Hello 节点。中间加入 padding，边框扩大；右侧再加标签，边框保持不变。

<ComponentPreview files="node-size-states" size="md" type="illustration" hideCode />

字体、折行阈值和内边距都会改变需要容纳的内容；`minimumSize` 只能扩大边框，不能把文字压小。`scale` 在计算过程中同时作用于字体、间距和形状参数；`rotate` 再改变最终边框的朝向。

### 标签不参与边框尺寸计算

上图右侧的 label 是独立附属文字。它需要已经确定的节点边框来计算附着位置，因此不反过来参与节点形状的尺寸计算。

标签有自己的文字框。编译器根据标签旋转后的框和 `distance` 计算中心位置，使视觉框与节点边界保持指定净距。这一结果同时用于文字、引线和视框收集：节点边框不变，自动 viewBox 仍会包含外侧标签。

`Node.scale` 不缩放 `distance`；外层 Scope 的缩放则会一起变换节点、标签和间距。这解释了两种缩放看起来不同的原因。

## 视觉形状与连接几何

`shape` 决定画出来的轮廓，也拥有形状专属锚点；`boundary` 则只在解析自动连线端点、标准方位锚点和数字角度锚点时参与。`boundary` 省略或写成 `'shape'` 时，两条几何路径才重合。

下面三个 Q 的可见圆形和连线方向相同。中间改用矩形连接面，右侧再增加 margin；比较线端的位置，圆形本身始终不变。灰色点线是教学辅助边界。

<ComponentPreview files="connection-surfaces" size="md" type="illustration" hideCode />

| 引用方式                                    | 实际采用的几何              |
| ------------------------------------------- | --------------------------- |
| 自动连线、`.top`、`.30`                     | `boundary`，再外扩 `margin` |
| 形状专属锚点（如 `tip-0`）                  | 视觉 `shape`                |
| `{ anchor: { side, fraction } }` 边上比例点 | 视觉 `shape`                |

因此，`margin` 会外推连接端点与标准 border anchor，并扩大节点布局占位，却不会重画视觉形状。形状专属锚点与边上比例点保持在原轮廓上；某个 shape 没实现标准方位锚点时，core 会回退到它的外接矩形。

规则连接面先按 `fit` 求矩形，再应用 `gap`；自动端点、数字角度和标准命名 anchor 会共享这一结果。Core 的 ellipse / polygon，以及已注入的 star / contour，都会提供 贴合形状的 `tight` 外包轮廓；rectangle 的 `tight` 与 `bounds` 一致，已注入的 Sector 按 bounds 处理。自定义 shape 若未实现 `connectionEnvelope`，`tight` 会安全回退到 bounds，并产生一次结构化 warning。

## 命名引用与登记顺序

`id` 把一个已经完成布局的对象变成后续定位与连接可查询的几何句柄。编译器维护的是一组命名表；绘制图元与登记引用是两件事，因此没有 `id` 的 Node 仍会绘制。

### 命名表保存布局记录

命名表由 `NamespaceStack` 管理。它的 `frames` 是一个数组，每项是 `Map<string, NamespaceEntry>`；数组末项是当前栈顶，`register` 只写入这一项。下面把栈中的一个 Map 和键 `a` 对应的记录展开。图中的 `a` 已完成布局：中心为 `[40, 0]`，矩形宽 60、高 32，margin 为 0。

<ComponentPreview files="namespace-storage" size="xxl" type="illustration" hideCode />

Map 的 key 是 `id`，value 包含 `layout` 和 `state`。`layout` 是已解析的 `NodeLayout`：保存矩形、形状定义、连接面、margin 等几何信息，也包含文字等布局结果。图中只展示引用所需的字段，不表示完整对象或内存布局。

遍历到 Node 时，编译器先解析位置、计算正文与形状布局，再把布局投影到全局坐标；带 `id` 时才把这一结果写入当前 Map，状态为 `resolved`。Coordinate 使用同一张表，但保存的是零宽高几何记录。命名表是本次编译的运行时状态，不写回可持久化 IR。

### 定位即时查询，路径延迟消费

查询 `a` 时，`lookupEntry` 从栈顶 Map 向栈底依次查找，命中后立即返回条目。定位解析器读取这份布局的几何视图：取中心可以得到 `[40, 0]`，取无旋转矩形的 `right` 锚点则得到 `[70, 0]`。自动贴边连接还需要另一端的方向，才能求出连接面上的交点；不是查到 id 就总返回同一个点。

下图使用同一作用域内的声明数组 `[Path(a, b), Node a, Node b]`。路径写在两个节点之前，但遍历到它时只入队，不立刻查询端点。

<ComponentPreview files="namespace-consumption" size="xxl" type="illustration" hideCode />

- **Node / Coordinate 定位**：遍历到该对象时立即查询，使用当时已经登记的条目；不会等待后面的声明，也不能靠互相引用形成定位循环。存储的几何使用全局坐标，定位结果会按当前 Scope 的变换转换回局部坐标。
- **Path / Draw 端点**：先在图元序列中留下占位，同时把路径、作用域变换、样式和占位位置存入待处理队列。当前作用域子节点登记完成后，再查询命名表、解析端点并回填原占位，因而既支持后声明的同级节点，也保留原有绘制顺序。

例如，把 `Node b` 写在 `Node a` 前面，同时让 `b.position` 引用 `a`，定位无法获得尚未登记的 `a`；把 `Path(a, b)` 写在它们前面则可在收尾时解析。这个等待边界是当前作用域，并非等整棵图的所有未来声明都完成。

### Scope 控制条目的可见范围

普通 Scope 不创建新的命名表：它的子节点继续写入当前 Map。`localNamespace` 为 true 时才 `pushFrame()`，子节点写入新的栈顶 Map；查询先找内层，再找外层，所以内层可以引用外部节点，同名条目则遮蔽外层条目。

图中外层已有 `a`、`b`，局部 Scope `group` 内再定义 `a`、`c`。内层查询 `a` 命中局部条目，查询 `b` 才继续向外查找。离开 `group` 后局部 Map 出栈，外部重新看到原来的 `a`，看不到 `c`；局部条目不会合并进外层 Map。

<ComponentPreview files="namespace-scope" size="xxl" type="illustration" hideCode />

`group` 自己的 id 属于父 frame，不与局部子节点一起消失。进入 Scope 前先登记 `scope-placeholder`；子树布局完成后，用真实包围盒替换为 `resolved` 条目，再处理该 Scope 的待解析路径，最后弹出局部 frame。因此外部可以引用已闭合的 `group`，即使其内部 id 不可见；内部 Node 的锚点定位不能使用尚未闭合的祖先 Scope 包围盒。已闭合的空 Scope 是合法的零尺寸目标，与“尚未完成”不同。

同一 frame 内重复登记相同 id 会覆盖旧条目并产生诊断；跨 frame 的同名遮蔽不属于同表重复。Scope 的几何变换和命名隔离也是独立的：变换影响保存和消费的几何，只有 `localNamespace` 决定是否建立新的 Map。

## 行归一化与优先级

`<Text>` 是一个返回 `null` 的标记组件，本身不创建 DOM 或图形。只有 `<Node>` 收集 children 时会识别这个标记，并把不同 JSX 输入归一到同一份 `Node.text` 契约：

例如 `<Node>A<Text fill="red">B</Text>C</Node>` 会产生三行：第一行 A、第二行红色 B、第三行 C。对应文本输入如下；若同时提供 `text="X"`，最终只采用 X。

```ts
['A', { text: 'B', fill: 'red' }, 'C'];
```

<ComponentPreview files="text-normalization" size="xs" type="flow" hideCode />

显式 `text` prop 优先；只要它存在，children 就不再参与文本收集。没有 `text` prop 时，适配层按 JSX 顺序递归读取字符串、数字、数组、Fragment 与 `<Text>`：

| 输入            | 归一规则                                     | `Node.text` 结果 |
| --------------- | -------------------------------------------- | ---------------- |
| 字符串 / 数字   | 相邻内容拼接，按 Node 文本规则处理 `\n`      | 普通字符串行     |
| 无样式 `<Text>` | 先结束当前普通行，再把自身作为独立一行       | 普通字符串行     |
| 有样式 `<Text>` | 先结束当前普通行，再保留当前行的样式覆盖字段 | IRLine 对象行    |

这也解释了两个边界：`<Text>` 只能在 `<Node>` 内生效，而且它表达的是一整行，不是行内 span。

## 自动对比色计算

归一完成后，每一行沿同一套颜色优先级进入 Core。`<Text fill>` 是显式行色，直接覆盖 Node 默认；没有 `fill` 的行才继承 `Node.style.textColor`。下面只展开该值为 `contrast` 时的背景判断：

<ComponentPreview files="text-contrast-flow" size="sm" type="flow" hideCode />

当 Node 使用 `NodeTextColor.Contrast` 时，Core 在样式级联后读取最终 `fill`。只有静态且有效不透明度为 1 的颜色参与黑白文字与背景的对比度计算（WCAG 相对明度），并解析成 `#000000` 或 `#ffffff`；缺省、半透明、gradient、`var()` 等无法闭合求值的背景使用固定 `currentColor`，同时发出 `TEXT_AUTO_CONTRAST_UNRESOLVED`。Node 的整体 `opacity` 不参与背景判断。

## 坐标点的登记与输出

本节只放大 `<Coordinate>` 如何在 compile 中成为可引用的几何句柄；完整的 JSX → IR → Scene 管线见[架构](/kernel/components/design/principles)。

### 先登记，再引用

图中从左到右展示一个坐标点从位置输入到可被引用的过程。查询只读取已经登记的 id，登记完成后，后续节点和路径才能使用它。

<ComponentPreview files="coordinate-resolution-flow" size="xs" type="flow" hideCode />

Coordinate 的 `position` 会立即解析。若它依赖另一个 id，该 id 必须已经在当前可见命名空间中登记；引用同一层里后定义的 Node / Coordinate 会直接报错。位置解析成功后，编译器把结果投影到全局坐标，保存成一条只有中心坐标的零尺寸几何记录，再按 `id` 登记。

Node / Coordinate 的定位引用同样在遍历时解析，因此只看得到已登记的 id。Path 则先排队，等当前 Scope 的 children 完成登记后再解析端点，所以同一作用域里的 path 可以引用写在它后面的 Coordinate。`localNamespace` 带来的可见范围仍遵循 [Scope 的命名空间规则](/kernel/components/scope/mechanism#命名空间与-id-冲突)。

### 零尺寸记录与渲染输出

这里的“零尺寸”表示记录的宽为 0、高为 0，因此也常简写为 **0×0**。它只保存 Coordinate 的中心坐标，没有面积或可见内容，边界也退化到中心；这是一条供编译器定位和连线引用的内部几何记录，不是 Scene 图元。这样既能复用 Node 的 id 查询与 anchor 解析机制，又不会让纯引用点进入渲染输出或自动画布范围。

- **不画任何图元**——没有形状、没有文字，渲染产物里完全不出现。
- **不撑大画布**——远处的 coordinate 不会让最终 viewBox 自动变大；必须有实际 `<Node>` / `<Path>` 落在那片区域，画布才覆盖过去（调试定位时常踩这点）。
- **命名 / 角度 anchor 退化为中心**——因为宽和高都是 0，各方向的边界都和中心重合，所以 `hub.top` / `hub.bottom` / `hub.30` 都等于中心点；需要方向 anchor 就改用 `<Node>`。
- **边上比例点会报错**——`{ anchor: { side, fraction } }` 需要一条真实边，而零尺寸记录只有中心点，没有可取样的边。

矩形不会为了外接内容额外放大半轴，所以边界正好包住「文字 + padding」。同一份 `cornerRadius` 参数既参与矩形绘制，也参与朝目标方向求边界交点；这就是圆角节点的连线会落在圆弧上，而不是落在已被磨掉的尖角上的原因。

因此 `<Rectangle>` 的结果是纯 Path 图形；矩形 `<Node>` 则保留 id、方位 anchor 与边界求交能力。需要装文字并连接时，应选择 `<Node>`。

### 多边形的内容外接与连接轮廓

沿主链看，Node 的内容尺寸先决定多边形要包住什么，再由 shape 参数决定用什么正多边形去包；上下两条输出表示同一套轮廓规则同时服务渲染与自动连接：

<ComponentPreview files="polygon-node-flow" size="lg" hideCode type="illustration" />

文字与 `padding` 先形成内容内框；`polygon` 形状实现再根据 `sides` 与 `rotate` 求出能完整外接这个内框的最小外接圆半径。所有顶点仍落在同一个圆上，所以长文本只会把正多边形整体放大，不会把它拉伸成不规则多边形。

`cornerRadius` 不改变外接尺寸，而是在顶点环生成后应用倒角。同一套顶点与倒角规则既输出 Scene path，也用于从节点中心朝目标方向求边界交点，因此自动连接会落在圆角弧上。标准方位 anchor（`top`、`bottom` 等）仍取外接矩形；它们不等同于任意方向上的真实轮廓交点。

`shape="diamond"` 只改变入口写法：编译器会先把它归一为 `polygon{ sides:4, rotate:0 }`，再进入完全相同的 provider 主链。对象形式 `{ type:'diamond', params:{ aspectRatio } }` 也走这条主链，其中 `aspectRatio` 表示最终轮廓的宽 / 高；缺省或设为 `1` 时等价于原有正菱形。扁菱形固定使用 0° / 90° / 180° / 270° 四个顶点方向，并由同一套顶点参与渲染、边界交点和连接面计算。

### 自定义形状的解析

图中橙色是 JSON 数据，蓝色是运行时能力。两者在 compile 阶段按 shape 名汇合：registry 先合并内置与自定义定义，再校验 params，最后由同一份 definition 生成 Scene 图元与连接几何。

<ComponentPreview files="custom-shape-flow" size="sm" hideCode type="illustration" />

执行顺序如下：

1. 解析 `node.shape`；`circle` / `diamond` preset 先归一为真实 provider 名和 params
2. 在统一 shape registry 中查找定义；内置项与自定义项不分两条消费路径
3. 依次通过 JSON object 护栏与 definition 的 `paramsSchema`
4. Node 布局调用 `circumscribe`，连接与 anchor 调用几何函数，规则连接面可调用 `connectionEnvelope`，绘制调用 `emit`
