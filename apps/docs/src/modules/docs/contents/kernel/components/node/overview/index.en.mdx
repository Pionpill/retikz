## Usage

```tsx
import { Node } from '@retikz/react';
```

```tsx
<Node id="a" position={[0, 0]}>
  Label
</Node>
```

Use Node when you need a visible subject, text, or a real boundary. Use [Coordinate](/kernel/components/node/coordinate) when only an invisible reference point is needed.

## Examples

### Basic

<ComponentPreview files="node-basic" size="xs" />

A Node keeps position, content, and shape boundary in one declaration. Flowchart nodes usually need only the default rectangle; plain text can remove `stroke` / `fill`; add `minimumSize` only when the box must stay stable.

### Positioning

The five center/point placement forms of `position` are Cartesian, polar, directional relative, referent offset, and fractional-between. Switch the input kind and adjust its parameters to see the same `q` move around the fixed reference nodes `a` and `b`.

<ComponentPreview files="node-position" size="md" />

Referenced ids must be declared first. Directional placement inherits its default distance from `<Layout nodeDistance>`, while `fraction: 0.5` is the midpoint for `between`. See the full input union in the [API Reference](#positioning), or use [Coordinate](/kernel/components/node/coordinate) for invisible helper points.

Node also supports a sixth form that depends on its real measured size: anchor-to-anchor placement. Use the panel to switch both standard anchors and adjust offset, target margin, both rotations, and the current Node's scale; asymmetric padding and all of those geometry inputs are laid out first.

<ComponentPreview
  files="node-anchor-position"
  size="md"

Both `target.anchor` and `selfAnchor` default to `center`. The target must be an already-laid-out Node, Coordinate, or Scope; undefined, later, self, and still-open ancestor Scope references throw immediately.

### Shapes

A node's visual contour and connection endpoints have three independent controls: `shape` selects what is drawn, `boundary` selects the surface used for automatic clipping, and an endpoint `anchor` selects a named attachment point. Change A and B independently to see how the same edge resolves at both ends.

<ComponentPreview files={['node-shape-connection', 'node-shape-connection-boundary.ts']} size="md" />

With no `anchor`, the edge clips automatically toward the opposite endpoint. Standard named anchors such as `top` and `right` resolve against `boundary`; `center` connects directly to the node center. Shape-specific anchors still belong to the visual `shape`; see each shape page for their names.

`shape` has two forms: shapes without required parameters accept a bare string, while parametric shapes such as `polygon`, `sector`, and `star` require `{ type, params }`. Core provides `rectangle` / `ellipse` / `polygon` by default and exposes `circle` / `diamond` as basic presets; optional Node shapes such as `sector` / `star` must first be injected through `<Layout shapes>` or `CompileOptions.shapes`. By size source, they divide into text-container shapes that wrap "text + padding" and geometric shapes sized by radii or angles. A Sector with `innerRadius === outerRadius` is the open-arc state.

See each shape page for its parameters and shape-specific anchors:

| shape             | form                                       | docs                                                         |
| ----------------- | ------------------------------------------ | ------------------------------------------------------------ |
| rectangle         | default / `'rectangle'`                    | [Rectangle](/kernel/components/shapes/rectangle)             |
| circle / ellipse  | `'circle'` / `'ellipse'`                   | [Circle / Ellipse](/kernel/components/shapes/circle-ellipse) |
| sector            | `{ type:'sector', params }`                | [Arc / Sector](/kernel/components/shapes/arc-sector)         |
| polygon / diamond | `{ type:'polygon', params }` / `'diamond'` | [Polygon](/kernel/components/shapes/polygon)                 |
| star              | `{ type:'star', params }`                  | [Star](/kernel/components/shapes/star)                       |

`shape` also accepts names registered through `<Layout shapes>` / `CompileOptions.shapes`; parametric registered shapes continue to use `{ type, params }`. See [Custom Shapes](/kernel/components/shapes/custom-shape).

`boundary` defaults to `'shape'` and can also use `'circle'`, `'rectangle'`, `'ellipse'`, or a registered connection surface. It changes only automatic endpoints and standard anchors, never the node footprint or visual contour. All three built-in alternatives accept `{ fit, gap }`: `fit: 'tight'` (the default) uses the visual shape's safe envelope for a closer fit, while `fit: 'bounds'` encloses its visual AABB; `gap` then adjusts the radius or half-axes outward (positive) or inward (negative). Rectangle produces the same result for both fit modes.

Switch A and B between fit modes and drag `gap` in the playground; the light dotted contour is the actual connection surface. A negative gap may cross the visual shape, but this usually makes graphConnectors cover the node and is not recommended. Compilation fails if it reduces either effective half-axis to zero or below. An individual edge can override the node default in its endpoint object. See [Custom Boundaries](/kernel/components/node/custom-boundary) for registration and [Path](/kernel/components/draw/path) for endpoint syntax.

### Size & transforms

Size and transforms share one node geometry: padding expands the content box, minimumSize sets a floor, and scale / rotate alter the final border. Margin leaves the node appearance unchanged and makes connecting paths stop early. Adjust the same `q` while the edge provides a border reference.

- Inner: `padding={N}` or `padding={{ default, x, y, left, right, top, bottom }}`
- Outer: `margin={N}` or `margin={{ default, x, y, left, right, top, bottom }}`
- `cornerRadius` — corner radius. `rectangle` / `polygon` / `star` / `sector` support rounding (`ellipse` and the like do not) via their params: `shape={{ type:'polygon', params:{ sides:6, cornerRadius:8 } }}`, and likewise for `star` / `sector` / `rectangle`. The top-level `cornerRadius` only affects the `rectangle` shape (default or explicit `'rectangle'`), and only merges when params don't already set `cornerRadius` (params wins when both are set)
- `minimumSize` — floor the bbox without shrinking natural text width
- `scale` — uniform / per-axis scale; affects bbox, font size, padding, and path attachment
- `rotate` — rotate around the node center; attached paths follow the rotated border

### Text

Enter multiple lines directly in the panel. Newlines create hard lines, while line 1, line 2, and line 3 onward can each change color, emphasis, and opacity. The same scene also compares `shape`, `align`, `lineHeight`, and `maxTextWidth` without moving the node or camera.

<ComponentPreview files="node-text" size="lg" />

- `text` accepts a string or a LineSpec array; `'\n'` creates hard breaks, while the array form gives each line independent styles
- `align` controls horizontal alignment within the block and `lineHeight` controls spacing; both are block-level properties
- `maxTextWidth` is a wrap threshold, not a fixed paragraph width; Western text wraps by word, CJK by character, and unbreakable tokens overflow as a whole
- Each line can override `fill` / `opacity` / `font`; [`<Text>` children](/kernel/components/node/text) express the same structure in JSX
- Changing `shape` keeps the shape-specific circumscription rules around the multiline content

`text` wins over `children` whenever both are supplied. Block-level `font` is `{ family?, size?, weight?, style? }`; the other shared visual properties remain in the [styling playground](#styling) at the end of this page.

#### Automatic black-or-white contrast

Set `textColor` to `NodeTextColor.Contrast` and Core selects pure black or white, whichever has higher contrast against the Node's final static opaque `fill`. The keyword resolves after style cascading and independently for each Node, so it can also live in `Scope.nodeDefault`.

<ComponentPreview files="node-auto-contrast" size="sm" />

```tsx
import { NodeTextColor } from '@retikz/core';

<Node fill="#1e293b" textColor={NodeTextColor.Contrast}>
  Status
</Node>;
```

- Core statically supports CSS named colors, 3/4/6/8-digit hex, and legacy / modern `rgb()` and `hsl()`; it never reads DOM styles, theme variables, or page pixels
- Translucent / missing fills, `fillOpacity < 1`, gradients, patterns, images, `var()`, and `currentColor` use the fixed `currentColor` fallback and emit `TEXT_AUTO_CONTRAST_UNRESOLVED`
- Per-line / run `fill`, explicit label colors, and `labelDefault` still win. The keyword affects only body text, labels, and pins that ultimately inherit the Node text color

### Node labels

`label` attaches extra text to the node border. Single object or array form; `position` accepts the 8-direction enum (default `'top'`), `'center'`, a numeric angle, or a `{ boundary, fraction }` proportional boundary point; `placement` chooses whether the label is offset outside or inside the attachment point and defaults to `'outside'`; `'center'` draws the label directly at the node center with no collision avoidance; `font` / `textColor` inherit from the node when omitted, and `opacity` controls the label's own opacity (0..1, multiplied with the node `opacity`).

The playground below focuses on one label and combines named directions, numeric angles, boundary fractions, inside / outside placement, rotation, text style, and leader lines.

<ComponentPreview files="node-label" size="md" />

To attach multiple labels, place the same object form in an array:

```tsx
<Node
  label={[
    { text: 'status', position: 'top' },
    { text: 'owner', position: 'bottom' },
  ]}
/>
```

`distance` is the net gap, along the placement direction, between the node boundary and the **rotated label visual box**. It defaults to `12`; `0` makes the visual box touch the boundary. `placement: 'inside'` turns the direction inward and preserves the same gap on the inner side. Rectangle nodes can also use `position: { boundary, fraction }` to attach to a proportional point on a specific side. `position: 'center'` always uses the final node rectangle center and ignores `placement` and `distance`.

- `boundary` accepts `'top'` / `'right'` / `'bottom'` / `'left'`
- `fraction` is the 0..1 proportional position on that side and defaults to `0.5`
- `placement: 'inside'` cannot be combined with `pin`; keep labels outside when a leader line is needed

`label.rotate` spins the label text around **its own center**: `'radial'` follows the direction defined by `position`, using the selected side's outward normal for a boundary-fraction position; `'tangent'` is its tangent (radial + 90°), and a number is an explicit angle in degrees. `placement: 'inside'` reverses only the label offset, not this orientation. `keepUpright` flips it 180° when it would otherwise read upside-down. Rotation changes the visual box projection along the placement direction, so the compiler adjusts the label center to preserve the same `distance` gap.

`label.pin` adds a **leader line** from the node border to the label: `pin: true` is a default thin solid line (inherits the label color); `pin: { stroke, strokeWidth, dashPattern, dashOffset }` customizes it; omitted / `false` = no leader. Its endpoint is the exact intersection of the placement ray and the rotated visual box, with no hidden padding; the preceding box geometry still owns label placement.

### Stacking order (zIndex)

By default stacking = declaration order (SVG only honors paint order). `zIndex` overrides it explicitly: higher draws on top, omitted = 0, ties keep declaration order; effective only among siblings at the same level (same scope / top level). The example always declares a → b → c and only changes their levels through the controls. `<Path>` / `<Scope>` support `zIndex` too (a scope's `zIndex` positions the whole group among its siblings without affecting the relative stacking inside it).

Font, color, opacity, strokes, and `IRPaintSpec` are shared visual properties across primitives; they do not change Node's naming, positioning, or connection semantics. Use the playground for common appearance choices and the [API Reference](#visual-style-api) for the complete field list.

### From props to a referenceable node

The compiler first resolves the style-inherited `position`, content, and geometry props into one Node layout. That layout serves two outputs: shape, text, and labels become Scene primitives, while `id`, anchors, and the connection boundary become named geometry that `<Path>` / `<Draw>` can query.

<ComponentPreview files="node-layout-flow" size="md" hideCode />

Node sizing converges in a fixed order: text is measured and wrapped first; `padding` forms the content box; the shape definition computes a visual circumscribed box from that box and its params; then `minimumSize` applies a floor. `scale` affects fonts, spacing, and shape params from the start, while `rotate` is attached to the resolved geometry.

Anchor placement runs only after that provisional layout exists. It resolves both anchors and translates the whole Node; opt-in `nodeLayout` artifacts, id registration, Scene output, Scope bbox, and automatic viewBox observe only the final translated geometry.

`label` does not participate in visual shape sizing. Labels are laid out as separate attached primitives, so they do not enlarge the node border, but their extents join `margin` and shadow when the automatic viewBox is collected. The compiler resolves each label visual box in one measurement phase, then uses the final node rectangle, rotated box, and `distance` to resolve its center offset without remeasuring after the rectangle is known. The same box geometry drives the text baseline, pin endpoint, and viewBox. `Node.scale` does not scale the user-unit `distance`; an outer `Scope` transform scales the node, label, and gap together.

### Visual shape vs connection geometry

`shape` owns the rendered contour and shape-specific anchors. `boundary` participates only when resolving automatic path endpoints, standard directional anchors, and numeric-angle anchors. The two geometry paths coincide only when `boundary` is omitted or set to `'shape'`.

| Reference form                        | Geometry used                    |
| ------------------------------------- | -------------------------------- |
| Automatic endpoint, `.top`, or `.30`  | `boundary`, expanded by `margin` |
| Shape-specific anchor such as `tip-0` | Visual `shape`                   |
| `{ side, fraction }` edge point       | Visual `shape`                   |

As a result, `margin` pushes connection endpoints and standard border anchors outward and expands the node's layout footprint, but never redraws the visual shape. Shape-specific anchors and edge points stay on the original contour. If a shape does not implement a standard directional anchor, core falls back to its bounding rectangle.

A regular connection surface first derives its rectangle from `fit`, then applies `gap`; automatic endpoints, numeric-angle anchors, and standard named anchors share that resolved result. Core ellipse and polygon, along with injected star and contour shapes, provide shape-aware `tight` envelopes. Rectangle gives the same result for `tight` and `bounds`, while injected Sector uses bounds in this release. If a custom shape omits `connectionEnvelope`, `tight` safely falls back to bounds and emits one structured warning.

### Why named positioning is order-sensitive

Node positioning resolves immediately when traversal reaches that node: the compiler queries the current namespace first, then registers the node's `id` only after its layout is known. A `position` that refers to a later Node / Coordinate / Scope therefore fails, and cyclic positioning cannot resolve. Anchor placement may target a previously closed Scope; targeting an ancestor Scope whose bbox is still being computed throws as an incomplete layout. A closed empty Scope is still a valid target even though its layout is 0×0.

Path / Draw endpoints use a different phase. A path first reserves its drawing-order slot, then resolves only after every Node and Coordinate in the current scope has registered. Path endpoints can therefore refer to later sibling nodes.

### margin vs padding

|           | Affects                                     | Visual effect                                                                                                                 |
| --------- | ------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `padding` | Distance from text to border                | Visible shape grows                                                                                                           |
| `margin`  | Outer offset around the connection boundary | Visible shape unchanged; all border anchors and path endpoints move out by `margin`, and the node footprint includes `margin` |

`padding` grows the node itself; `margin` leaves the visible shape untouched but pushes the node's connection/reference boundary outward (including explicit anchors like `.top`) and reserves that much extra space in layout. `margin` defaults to 0, so unset means zero effect.
