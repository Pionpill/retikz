## Implicit root scope

When applying shared styling to a set of children, `rootScope` does not introduce another styling system. Layout conditionally wraps JSX children in an ordinary Scope, reusing its inheritance and override rules.

For example, the following root configuration is equivalent to placing a `<Scope defaults={{ node: { style: { fill: 'lightblue' } } }}>` around these nodes inside Layout:

```tsx
<Layout rootScope={{ defaults: { node: { style: { fill: 'lightblue' } } } }}>
  <Node id="a" position={[0, 0]}>
    A
  </Node>
  <Node id="b" position={[80, 0]} style={{ fill: 'orange' }}>
    B
  </Node>
</Layout>
```

A inherits the light-blue fill; B's explicit fill overrides the default. **defaults** supplies values that descendants have not set explicitly, rather than forcibly rewriting each node. `rootScope.style` supplies general drawing styles such as `fill / stroke / opacity` to descendants.

Wrapping depends on whether the configuration contributes an override, not merely whether the `rootScope` object exists:

- **No effective override**: when omitted, `{}`, or limited to empty overrides such as `style: {}` and `defaults: {}`, use the original children without adding a synthetic Scope.
- **Effective override**: actual styles, defaults, or an effective `defaults.reset` wrap the children in an ordinary Scope and reuse its inheritance rules. A `reset` of `true` or a nonempty channel list cuts the corresponding outer style inheritance; `false` or an empty list alone does not trigger wrapping.
- **ir supplied**: use the complete child structure described by IR, ignoring any children and `rootScope` supplied alongside it. Change the IR itself to change its scopes; host CSS `style` remains applicable.

**The synthetic Scope is not a local namespace.** `rootScope` only accepts `style / defaults`. Use an explicit Scope inside the drawing for `localNamespace`; see [Scope usage](/kernel/components/scope/usage) for naming and references.

## Automatic viewport

Without `viewBox`, the viewport comes from the drawing's layout bounds, not the size of its page container. Layout bounds combine the leftmost, topmost, rightmost, and bottommost extents contributed by drawing elements, not just node centers. They are computed during compilation, not measured from rendered DOM pixels.

Layout first chooses a viewport source: its `viewBox` prop takes precedence over the input IR's `viewBox`. Only when both are absent does it compute a range from the content. An explicit viewport directly sets the coordinate window without automatic content padding.

Automatic sizing has two steps: combine content bounds, then expand all four sides by padding. The current default is 10 drawing units. This is not host CSS `padding`. Core compile options can configure it, but Layout currently exposes no such prop; use an explicit `viewBox` to control the viewed margin yourself.

<ComponentPreview files="layout-auto-viewport" size="xs" hideCode />

For content bounds `x: 20, y: 30, width: 80, height: 40`, default padding gives `x: 10, y: 20, width: 100, height: 60`. In general, bounds `(x, y, w, h)` and padding `p` produce:

$$
(x', y', w', h') = (x-p,\ y-p,\ w+2p,\ h+2p)
$$

If no content bounds exist, the result is directly `{ x: 0, y: 0, width: 100, height: 100 }`, without padding that fallback range again.

Moving, adding, or removing elements can therefore change the automatic viewport. Set an explicit `viewBox` to compare positions within the same coordinate window across updates; fixing `width / height` alone does not fix the viewed range.

## Viewport and display size

`viewBox` selects which drawing coordinates are visible; `width / height` determines how much page space that window occupies. The viewport is determined first; its dimensions then provide the basis for deriving display size. Changing display size in the other direction neither rewrites node coordinates nor redefines the viewport.

<ComponentPreview files="layout-viewbox-resolution" size="md" hideCode />

For `viewBox={{ x: 0, y: 0, width: 200, height: 100 }}`, the internal aspect ratio is 2:1:

| Size configuration         | Host size   | Derivation                           |
| -------------------------- | ----------- | ------------------------------------ |
| Neither dimension          | 200 × 100   | Use viewport dimensions              |
| Only `width={400}`         | 400 × 200   | Derive the other axis proportionally |
| `width={400} height={300}` | 400 × 300   | Keep both explicit values            |
| Only `width="100%"`        | 100% × auto | Let the browser lay it out           |

With both dimensions supplied, Layout does not change `400 × 300` to `400 × 200`. Fitting internal content into that host belongs to SVG / Canvas presentation; host sizing is not a new layout of drawing elements.

SVG and Canvas share this display-size calculation. CSS strings are not parsed as drawing coordinates.

## Themes and local overrides

`theme`, `rootScope`, and host `style` can all affect appearance, but they are not three priority levels of one configuration object:

| Configuration                | Applied to                       | Controls                                       |
| ---------------------------- | -------------------------------- | ---------------------------------------------- |
| `theme`                      | Scene and theme-aware Composites | Theme style and light/dark mode                |
| `rootScope.style / defaults` | Root scope of JSX children       | Drawing styles and element defaults            |
| `style`                      | SVG / Canvas host                | Page CSS, such as background and maximum width |

A **Composite** accepts a high-level description and expands it into basic drawing elements. Layout writes the theme into Scene for these capabilities to consume; it does not directly turn a theme selector into every ordinary Node's fill color. Each consuming capability determines how the theme produces element styles.

Themes also affect more than Composites: for numeric colors (colors derived as a proportion of the master color), `mode` participates in color resolution. Explicit string colors such as `'orange'` retain their values. Changing the theme is therefore not a blanket replacement of all element styles.

Within the theme itself, the order is explicit: the theme inherited from ThemeProvider, the input scene's theme, then Layout's `theme`. Merge them field by field: later layers override only the `style / mode` they supply, while omitted fields remain inherited rather than clearing the entire earlier theme.

<ComponentPreview files="layout-theme-overlays" size="xs" hideCode />

For example, if the Provider supplies `{ style: 'clean', mode: 'dark' }` and Layout supplies only `{ mode: 'light' }`, the result keeps `style: 'clean'` and changes only the mode to `light`. Nested ThemeProviders use the same field-wise merge.

When a Composite is used with `rootScope`, the result depends on what it actually emits. Suppose the root Scope supplies a light-blue default fill. If a Composite uses the theme to emit a Node with explicit `style.fill: 'orange'`, that Node is orange. If it emits a Node in the same scope without a fill, the Node inherits light blue. Theme selection does not bypass scope rules: emitted properties and inherited styles still determine the result together.

To set an ordinary Node's fill, use its own property or `rootScope`. To constrain the drawing's maximum page width, use host `style={{ maxWidth: '100%' }}`. These target different layers; repeatedly changing the theme is not a substitute for choosing the appropriate configuration.
