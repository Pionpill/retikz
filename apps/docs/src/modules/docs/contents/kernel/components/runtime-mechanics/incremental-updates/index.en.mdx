When node A changes from orange to blue, what needs to run again? This page follows a Vanilla DOM retained update: Vanilla prepares input, a Reconciler session invokes Core, Render prepares and commits the drawing, and the new result is published only after success. React subscribes to processing results and displays them with its own host commit boundary.

First read the IR, Scene and package roles in the [rendering pipeline](/kernel/components/runtime-mechanics/rendering-pipeline). For one compilation, see [Core compilation](/kernel/packages/core/compilation).

## Overall flow

The example has two root nodes, A and B, with unique ids. The second input changes only A's `style.fill`, but still submits a complete document containing both nodes. The layout below places the results side by side for comparison.

Ordinary React and Vanilla input updates use complete replacement. Reconciler batches require explicit operations on the current basic-element tree. Both return complete compilation output. Reusing element compilation state and updating part of a host are decisions made at different layers.

## Input preparation

React converts component declarations into `InputScene`, which Vanilla normalizes into `IRScene`; existing IR enters processing directly. `prepareProcessingInput` also prepares compilation configuration and Composite inputs. The controller owns a `ReconcilerSession`, calling `mount` initially and `replace` for ordinary subsequent input.

This path does not use the generic Runtime package's Source / Computation registry graph. `replace` explicitly rebuilds compilation output; it does not promise to skip compilation for equal document contents. Configuration-only changes can use `updateTarget` to retain compilation output.

## Compilation and reuse

Complete replacement selects a compilation entry by input kind. Basic elements build a Weave tree and use Core element compilation. Documents containing Composites use Core full preparation, preserving probes, instance inputs, artifacts and spatial handles.

<ComponentPreview files="update-reuse" size="md" hideCode type="flow" />

Weave retains input, context, compiled state and dependencies. `ReconcilerSession.update(batch, expected)` applies a `WeaveBatch` to an existing basic-element tree. `expected` must be the current session result; stale results are rejected. Composite scenes do not support this entry, and empty batches retain the current result.

Batches recompute affected elements from final inputs and reuse valid products. Context follows declaration structure and invalidation follows dependencies; a Scope change can recompute its whole subtree. Name indexing and output assembly can still traverse the tree, so local compilation does not imply local total update cost. Ordinary React and Vanilla input updates do not yet use this batch entry.

## Host commits

Vanilla DOM connects a renderer through `createRetainedRenderTarget`, combining host commits with `ProcessingResult` publication in the session's output target. The target prepares a new frame and configuration. Changed compilation output produces `replaceScene`; configuration-only updates produce an empty-operation Patch. This integration does not derive per-primitive Patches automatically from complete-result differences.

Scene snapshots record primitive identities, owners and topology from compilation provenance for Render validation and hydration. These identities are not Weave batch node addresses and do not guarantee local host updates.

React Layout subscribes to a successfully published `ProcessingResult` before constructing host output. Reconciler target rollback guarantees do not cover React's own commit cycle.

## Failure handling

Preparation retains the previous result. The session prepares its output target, then commits candidate Weave state and the target. It publishes the new result only after both succeed. Complete replacement uses a new tree, leaving the previous tree in place until publication.

<ComponentPreview files="update-commit" size="lg" hideCode type="flow" />

On commit failure, the session rolls back the target before restoring candidate Weave state. Successful recovery leaves the previous result readable. Failed recovery puts the session into the broken state, blocking normal reads and writes until disposal. A preparation function that fails before returning its commit token must clean up resources it already acquired.

Warning callbacks, tracing and commit-token cleanup failures after publication are recorded as diagnostics and do not undo the published revision. Vanilla notifies subscribers only of successfully published processing results; React retains the last successful result when an update fails.

## Complete implementation flow

This diagram locates an ordinary Vanilla DOM input replacement. Member names are source-reading anchors, not APIs an application must call one by one.

<ComponentPreview files="update-implementation" size="lg" hideCode type="flow" />

Start at `prepareProcessingInput` and the controller, then follow `ReconcilerSession.replace` through the Weave / Composite branches. `publish` prepares and commits the target; the Render target materializes candidate output as a host frame. The session then publishes its result and the controller notifies subscribers.
