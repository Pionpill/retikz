Once a drawing is visible, which work must run again when node A changes from orange to blue? This page follows a retained update across packages: the adapter submits new input, Runtime schedules computation, Reconciler prepares new compilation state, and the host displays the committed result. Complete input replacement currently recompiles the drawing. Weave retains inputs, results and relations for subsequent local scheduling.

Start with [Rendering Pipeline](/kernel/components/runtime-mechanics/rendering-pipeline) for IR, Scene and package responsibilities. This page covers state passed between compilations. See [Core compilation](/kernel/packages/core/compilation) for geometry within one pass, and [Runtime](/kernel/packages/runtime) for the general transaction machinery.

## Input updates

React components, Vanilla DSL and existing IR all converge at Vanilla's processing entry point. They reach a complete `IRScene` in different ways:

| Input form       | How it reaches complete IR                                                              |
| ---------------- | --------------------------------------------------------------------------------------- |
| React components | Layout collects declarations into `InputScene`, which Vanilla normalizes into `IRScene` |
| Vanilla DSL      | The caller supplies `InputScene`, which Vanilla normalizes into `IRScene`               |
| Existing IR      | The complete `IRScene` is used directly, without input normalization                    |

In the retained mode discussed here, Vanilla submits the complete IR to Runtime. The packages then cooperate with these responsibilities:

| Package    | Responsibility during an update                                                                                                                                                                                                           |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Vanilla    | Coordinates input preparation and pipeline assembly: normalizes authoring input, prepares IR, compile options and Composite inputs, wires Runtime and Reconciler computations, manages controller lifecycles and submits subsequent input |
| Runtime    | Provides general update scheduling and transactions: manages snapshots and revisions, selects computations by dependency, invokes incremental or full entry points, and coordinates commits and rollback                                  |
| Reconciler | Builds Weave and name relations, assigns runtime identities, calls Core, and assembles Scene snapshots and Patches                                                                                                                        |
| Core       | Performs one static compilation from `IRScene` and context to Scene and other [compilation output](/kernel/packages/core/compilation-output), with optional provenance                                                                    |

Runtime determines when to invoke which computations; Reconciler chooses what to recompute, and Core performs the compilation. Compile options, Composite inputs and related information travel through their own contracts rather than all being placed inside IR. In static mode, Vanilla arranges one complete compilation without this Runtime incremental transaction.

Even when only A's fill changes, an ordinary input update still delivers the complete IR containing A and B. Later stages prepare a new basic-element tree or a complete Composite result. This discussion follows a later update with stable controller configuration and compile options. Changing controller configuration involves its lifecycle.

Three objects matter here:

- Source: the owner of an input category, defining how to capture, read and compare values. Core documents use `CoreSourceDefinition`.
- Snapshot: the input held by a Source at a revision. A revision identifies a committed version.
- ChangeSet: optional hints identifying changes. The complete next snapshot still provides the actual values.

The Reconciler Source copies and freezes JSON on capture and compares its structure. Creating a new JavaScript object with identical content therefore does not, by itself, trigger Reconciler compilation. Vanilla's ordinary input update currently submits complete Sources without automatically generating a Reconciler ChangeSet for every edit.

In the color example, the next snapshot still contains A and B, with only A's `style.fill` changed. Callers integrating with Runtime directly can also provide a ChangeSet. Reconciler checks those hints against the previous and next snapshots. Missing hints are normal; inconsistent hints produce a diagnostic and trigger full fallback.

## Scheduling computation

Runtime receives an update with `baseRevision`, checks that it targets the current version, and prepares candidate Sources. A candidate is new state that has not been published; the committed state remains available while calculations run. If no Source actually changes, Runtime skips computations and participants and keeps its own revision.

Otherwise, Runtime selects computations through declared dependencies. A **Computation** reads Sources and produces a result; Reconciler integrates through `createCoreComputation`. Runtime knows which inputs affect it, while Reconciler decides how to compile the drawing again.

The initial computation executes the full `run` path. On later updates, the default incremental strategy allows `update` to inspect the previous result and candidate snapshots. It can return incremental output or request full fallback. A forced full strategy invokes `run` directly. General Runtime computations can also return bailout to retain their result; Reconciler currently requests fallback to prepare a complete candidate result.

Vanilla also wires Composite input and invalidation Sources into Reconciler. Changes to these dependencies can require compilation even when the IR is unchanged. If Composite definition topology becomes incompatible, Vanilla prepares a new retained state and replaces the old state only after success. This definition topology describes the registered capabilities; it is distinct from the Scene primitive hierarchy discussed below.

## Compilation state and identity

Reconciler retains drawing provenance and identity for each version. Weave also holds basic-element inputs, Core state and direct relations. Identity alone does not imply compilation reuse. Three kinds of information connect them:

- Semantic identity identifies the IR object that produced primitives. A's identity path includes `root / node / A`.
- Primitive identity identifies a particular emission from that object. A Node with text can produce a group containing a shape and text, so Node ids and primitives do not have a simple one-to-one relationship.
- Scene topology records primitive identity, semantic owner, parent, order and location in the primitive tree, allowing outputs to be matched across versions.

Core records the relationship between declarations, namespaces and emitted primitives during one compilation. Reconciler combines that provenance with the candidate revision to construct identities through Runtime. An author-supplied `id` is retained in IR and contributes to identity generation. The complete runtime identity consists of a domain identifier, `owner`, and an array of path segments, `path`. For a Core document, `owner` is `@retikz/core/document`.

For node A in this example, identity is built in successive layers: author id → semantic identity → primitive identity. One declaration can produce several primitives, so a single semantic identity can lead to multiple distinct primitive identities. Slashes in the table separate the segments of the `path` array.

| Level              | How it is generated                                                                                                                                                          |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Author id          | The example declares the node with `id: 'A'`                                                                                                                                 |
| Semantic identity  | Reconciler appends the node type and a valid unique id to the parent's identity path; root node A receives `root / node / A`                                                 |
| Primitive identity | Reconciler appends `emission`, the output role and its emission ordinal to the semantic identity path; A's first node group is `root / node / A / emission / node:group / 0` |

For anonymous, duplicate-id or compiler-generated objects, among other cases, Reconciler builds a semantic identity from a path containing the candidate revision, object kind and position index, then derives primitive identities from it. These identities apply only to the current candidate version and do not promise reuse across updates. Duplicate ids are detected within the compilation namespace.

For a node with stable identity such as A, Reconciler can still match its primitives across versions when its fill changes, provided that the parent identity, object type, id and other identity components remain stable. Stable identity establishes correspondence. Complete replacement still recompiles the input; local reuse requires the subsequent scheduler.

### Weave compilation

For basic-element input, Weave builds a declaration tree. The root owns the environment and lookup indexes; nodes retain their own input, effective context and Core compilation state. Scope prepares context before compiling children and its envelope. Path runs when references in its container are ready. Name reads establish direct relations, but cross-batch invalidation propagation is not yet implemented.

<ComponentPreview files="update-reuse" size="xl" hideCode type="flow" />

| Input                              | Current preparation path                                                     |
| ---------------------------------- | ---------------------------------------------------------------------------- |
| Node, Coordinate, Path and Scope   | Build Weave, call Core element compilation and assemble complete output      |
| Contains Composite                 | Core full preparation, retaining probes, instance inputs and attached output |
| ChangeSet disagrees with snapshots | Record a diagnostic, then prepare from the actual complete input             |

Even when only A changes color, the current update prepares a new tree containing both A and B. Failure retains the previous result. Successful updates produce one exclusive `replaceScene`; the presence of a Patch does not imply local computation.

## Display commits

Reconciler's **SceneRuntimeSnapshot** contains the complete Scene, revision and topology. A **ScenePatch** contains `baseRevision`, `nextRevision` and operations. Current updates carry a complete replacement snapshot; the Patch contract still allows future scheduling to describe local operations. Consumers must pair the Patch with its correct previous version.

In Vanilla DOM retained mounting, Render receives the compilation result and Patch for the update, applies local updates or full replacement according to backend capabilities, and coordinates with Runtime as a **Participant** to commit or roll back the rendering work. When preparing rendering operations, Render validates revisions and consistency between the Patch and target snapshot. An unsupported local operation can become `replaceScene`; an invalid Patch is rejected.

Whether Reconciler avoids geometry work and whether a backend updates locally are separate decisions. SVG and Canvas consume the same Scene contract, while each backend determines how to perform DOM changes or Canvas drawing.

React Layout follows another path. The Vanilla controller commits a `ProcessingResult`, then React subscribes to it. The SVG host builds a description tree from the complete result, while the Canvas host consumes a frame. Render Participant rollback guarantees do not extend directly to React's own commit cycle.

## Failure handling

Consider the Vanilla DOM transaction path. Finishing computation does not publish the next version. Participants first prepare, then commit and provide candidate reads. Runtime publishes Sources, computation results and the revision together only after those steps succeed.

<ComponentPreview files="update-commit" size="lg" hideCode type="flow" />

A failure before publication cleans up candidates and rolls back prepared participants in reverse order. Successful rollback preserves the previous committed state. If rollback itself fails, Runtime becomes broken and blocks normal reads and writes; the host can no longer be assumed to have recovered. Initialization has no previous successful frame, so failure throws from creation.

Observer or cleanup failures after publication become diagnostics and do not revoke the published version. Vanilla subscriber exceptions likewise do not roll back completed updates. React Layout retains its last successful result when a subsequent controller update fails and forwards diagnostics. A compilation failure therefore does not replace its current display input with an incomplete result.
