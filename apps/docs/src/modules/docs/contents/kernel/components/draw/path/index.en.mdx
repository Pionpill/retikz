## Usage

```tsx
import { Path, Step } from '@retikz/react';
```

```tsx
<Path stroke="currentColor">
  <Step kind="move" to="a" />
  <Step kind="line" to="b" />
</Path>
```

`<Draw>` compiles down to `<Path>` and covers everyday step / fold / curve / arc connections; but `<Path>` additionally exposes element-level capabilities — `color` / `rotate` / `scale` / `marks` / `id` / `meta` / `animations` — that `<Draw>` does not. Reach for `<Draw>`'s single-line `way` array for everyday connections, and `<Path>` when you need an explicit Step sequence, multiple `move`s, per-segment mixing of `kind` / label / control points, or any of those Path-only capabilities:

|                                                                       | `<Draw>`                | `<Path>` + `<Step>`                              |
| --------------------------------------------------------------------- | ----------------------- | ------------------------------------------------ |
| Form                                                                  | Single-line `way` array | Container + child nodes                          |
| step / curve / fold / arc                                             | Yes                     | Yes                                              |
| `color` / `rotate` / `scale` / `marks` / `id` / `meta` / `animations` | Not exposed             | Yes                                              |
| Use when                                                              | 90% of connection cases | Explicit Step sequence, element-level capability |

### Path and Step

`<Path>` requires `<Step>` children (at least 2); if the first isn't `move`, the compiler coerces it to `move`:

```tsx
<Path>
  <Step kind="move" to={...} />     {/* First: must be move */}
  <Step kind="line" to={...} />     {/* Then any number of line / move / step */}
  ...
</Path>
```

`<Step>` supports thirteen kinds — `move` / `line` for straight segments, `fold` for the right-angle fold, `cycle` to close back, `curve` / `cubic` for Bezier curves, `bend` as the arc shorthand (with out/in angles and self-loops), `smooth` for a smooth curve through a list of points, `generator` for injected custom path generators, `arc` / `circlePath` / `ellipsePath` for arcs / full circles / full ellipses centered on the cursor, and `rectangle` for a diagonal rectangle. See [Step](/kernel/components/draw/step) and [path generators](/kernel/components/draw/path-generator) for details.

### Path labels and stroke gaps

`<Path label>` samples on the whole Path, while `<Step label>` samples only on its owning Step. When an unfilled built-in `stroke` Path has canonical `side: 'center'`, Core removes real stroke geometry beneath the text rather than painting a backdrop. `sloped: true` with no `side` also canonicalizes to `center`.

With the upper-left and lower-right nodes fixed, switch the connection route, `side`, and the label position from 0 to 1 to observe sampling and gaps on the same host Path. “Automatic center” omits `side` and enables only `sloped`, so it still follows the centered-label default gap rule.

When `interrupt` is omitted, only that unfilled built-in Stroke + centered combination gets an automatic gap. `interrupt: false` forces a continuous stroke; `interrupt: true` can also gap a non-centered label.

Any effective `fill` — including `fill="transparent"` or `fillOpacity={0}` — disables the automatic gap, and `interrupt: true` then fails loudly. Any explicit boolean on Ribbon, a custom Path kind, or another non-built-in Stroke host also fails loudly. The gap does not move labels, marks, dash phase, or endpoint arrows, and does not avoid label / arrow or mark collisions.

Sampling a curve at a parameter, inverting distance, and taking a shape-preserving slice belong to the [`@retikz/math` curve-segment algorithms](/kernel/packages/base/math-algorithms#curve-slicing). They operate on plain geometry only; Core still decides label interruption, gap clearance, and Path output.

### Endpoints and connections

#### Arrows

`arrow` picks direction (`'->'` / `'<-'` / `'<->'` / `'none'`), `arrowDetail` owns visual shape / size / color fields, and `arrowPlacement` uses a normalized `[0,1]` ratio to move an arrow from its existing default to final-visual-back alignment at the logical endpoint, with shared and `start` / `end` overrides. All three are equivalent on `<Path>` and `<Draw>`. See **[Arrow](/kernel/components/draw/arrow)** for the `0 / 0.5 / 1` comparison, failure boundaries, and complete API.

#### Endpoint connection surface

When an endpoint references a node (the `{ id }` object form, or an id inside a way), you can add a `boundary` field to override the target node's [`boundary`](/kernel/components/node/overview#visual-shape-vs-connection-geometry) (connection surface) **for that endpoint only**. It takes the same forms as the node's `boundary`: `'shape'` (the visual shape itself) / `'circle'` (a true circle) / any registered shape name / `{ type, params }`.

```tsx
<Path arrow="->">
  <Step kind="move" to="a" />
  <Step kind="line" to={{ id: 'star', boundary: { type: 'circle', params: { fit: 'tight', gap: 8 } } }} />
</Path>
```

`circle`, `rectangle`, and `ellipse` share `fit: 'tight' | 'bounds'` plus a signed `gap`. They default to shape-aware `tight` and `gap: 0`. Both fit values are equivalent for `rectangle`; a negative gap contracts inward but may cross the visual shape.

`boundary` only applies where a connection surface is meaningful: endpoint auto-clip (no explicit `anchor`) and that endpoint's standard direction / angle anchor. In direction-less reference contexts — `between` endpoints, an `offset` `of`, a node center — it is a no-op. A node's default connection surface lives on [`<Node boundary>`](/kernel/components/node/overview#visual-shape-vs-connection-geometry); the endpoint `boundary` is the per-edge override.

The five-pointed star below has no node `boundary`. The panel starts on the circle boundary, so you can compare `tight` with `bounds` and adjust `gap` immediately; switch back to the star outline to compare the real shape surface. The light dotted outline is the current circle boundary and updates with the real endpoint.

### Styling

Set `strokeWidth` directly or use the semantic `thickness` presets from `ultraThin` through `ultraThick`; an explicit `strokeWidth` wins. `dashOffset` shifts only the dash rhythm's origin. `lineCap` / `lineJoin` shape endpoints and corners, while `opacity` / `fillOpacity` / `strokeOpacity` are three composable channels.

<ComponentPreview files="path-style" size="sm" />

#### Gradient stroke

Besides a plain color string, `stroke` accepts an `IRPaint`. Linear / radial gradients, patterns, and images enter the same paint resource table; `dashPattern`, `dashOffset`, `lineCap`, `strokeOpacity`, and other stroke styles still apply to the line itself. Adjust the linear-gradient angle and three color stops in the panel to inspect their distribution along one path.

<ComponentPreview files="path-stroke-paint" size="sm" />

If a gradient-stroked path also has arrows, give `arrowDetail.color` or the endpoint `color` an explicit solid color; marker geometry cannot inherit a resource-backed stroke.

#### Stacking order (zIndex)

By default stacking = declaration order. `zIndex` overrides it explicitly: higher draws on top, omitted = 0, ties keep declaration order; effective only among siblings at the same level (same scope / top level). The two filled rectangles below are declared dodgerblue-then-red; move the blue path's `zIndex` through negative, zero, and positive values to compare the overlap order.

### Curves and transforms

#### Out / in angles and self-loops

Besides the symmetric `bendDirection` + `bendAngle`, `<Step kind="bend">` accepts `outAngle` / `inAngle` for the start out-angle and end in-angle to draw asymmetric curves; `looseness` tunes the control-point distance (default ≈1). **out/in take precedence over `bendDirection`.** When `from == to` (same node / same coordinate) it degenerates into a **self-loop** — the prime use case for out/in (a state-machine self transition), which a symmetric bend cannot draw. Switch between a self-loop and a two-endpoint connection in the panel, then use the dotted direction guides to tune both angles and looseness.

<ComponentPreview files="path-outin-loop" size="md" />

#### Control-point inspection

After installing `@retikz/inspect`, use `InspectLayout` and `InspectPath` to select this Path occurrence at runtime. The built-in stroke Path Inspector reads quadratic and cubic control points from final settled commands and emits ordinary Path handles and Node markers; `labels` adds control-point identifiers. Selection never enters Core IR and does not change primary bounds, resources, hit testing, or animation. See [`@retikz/inspect`](/kernel/packages/extension/inspect) for registry and host wiring.

<ComponentPreview files="path-inspector" size="sm" />

#### Whole-path transform (rotate / scale)

`rotate` (degrees) / `scale` (a number for uniform, or `{ x, y }` for non-uniform) transform the whole path around its **bounding-box center**, sparing a wrapping `<Scope transforms>` for a single path. The order is a hard contract: path endpoints resolve first, arrow shrink is computed on the **untransformed** geometry, then everything is wrapped in a group — so arrow direction follows the transform correctly without misalignment. The dotted path preserves the original geometry while the panel's rotation and two-axis scale affect only the solid path for direct comparison.

<ComponentPreview files="path-transform" size="sm" />

#### Mid-path marks

`marks` places directional marks along the path: each `{ pos, mark }` has `pos ∈ [0, 1]` (out-of-range rejected by the schema), and `mark` is initially `{ kind: 'arrow', shape, ... }` (a registered arrow name + visual subset, see [Custom Arrows](/kernel/components/draw/custom-arrow)), **oriented by the tangent at that point** (not a fixed direction). Lines, Béziers, and arcs are all tangent-oriented. Their size **scales with `strokeWidth`**, just like endpoint arrows: the thicker the line, the larger the mark. Move both position controls to watch the marks follow the local tangent as they travel along the path.

<ComponentPreview files="path-marks" size="xs" />

#### Rounded corners (roundedCorners)

`roundedCorners` rounds every **line↔line joint** of the path with a tangent arc of the same radius — handy for flowcharts, routing, and polyline connections where you want soft corners instead of sharp ones. Omitted = sharp corners everywhere (behavior unchanged). The first / last endpoint stays sharp; a joint whose neighbor is a curve / arc / Bézier / fold stays sharp too. When the radius is too large it is **clamped per joint** to what the adjacent segment lengths allow. After a `cycle` close, the closing joint is rounded as well.

<ComponentPreview files="path-rounded-corners" size="sm" />

`roundedCorners` changes the **path geometry** — it pulls the joint vertices back and inserts a tangent arc, so it affects the bounding box, arc length, path-level `marks` normalization, and connection-point resolution. This is distinct from `lineJoin`, which only styles the **stroke render** while the path centerline stays a sharp fold. The panel shows `lineJoin` above and geometric rounding below so you can drag the radius and compare them directly. (Note: continuous step `label`s retain their existing step-local sampling; interrupted labels sample final rounded geometry so the gap aligns with the visible stroke.)

### Why endpoints can refer forward

The compiler does not emit primitives as soon as it reaches a `<Path>`. It queues the path and leaves an ordering placeholder when output stays at the current level. It continues registering `<Node>` and `<Coordinate>` ids, then resolves `Step.to`, control points, and connection boundaries after the current scope has been scanned. Ordinary scopes backfill the placeholder; see the [`<Scope>` deep dive](/kernel/components/layout/scope#how-it-works) for transformed-scope projection.

As a result, path endpoints can refer to an id declared later in the same scope without changing paint order. This is a contract of deferred path emission only: `Node.position` and scope transforms are still resolved when the compiler reaches them, so not every id reference supports forward declarations.

### How kind selects whole-path output

`kind` is not a renderer switch. It names the provider that compiles the whole Path and defaults to `stroke`. Core's Path host first accepts an open `kind` string and JSON-safe `kindOptions`; during compilation, the shared registry resolves a definition and that definition's complete subject schema validates the Path. The provider can then reuse standard stroke emission or return custom Scene primitives directly.

The figure stops at the Path responsibility boundary: the input remains one `<Path>`, while every provider branch returns renderer-agnostic Scene primitives.

<ComponentPreview files="path-kind-pipeline" size="sm" hideCode />

The built-in `stroke` kind and external kinds use the same registry and collision rules. Core does not auto-register optional capabilities, and renderers do not need to understand custom kinds. See [Custom Paths](/kernel/components/draw/custom-path) to own the whole path, or [Path Generators](/kernel/components/draw/path-generator) to extend one step. For a band-shaped relation, load the optional Standard [Ribbon Path kind](/library/standard/extension/ribbon).

### How stroke materializes geometry

The default stroke path first resolves relative targets, node references, and generators into path commands (`PathCommand`: materialized move / line / arc geometry). `roundedCorners` then rewrites those commands. Labels still sample the uncut logical path; a compatible `interrupt` projects the text visual box, removes only stroke geometry, and emits path fragments that retain command form and the original logical owner. Marks, endpoint arrows, and dash phase still follow the logical path, then `rotate` / `scale` wrap the main path, labels, and marks in one group.
