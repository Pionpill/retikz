title: Path
description: Path is the Kernel path container for stroked or filled paths and variable-width ribbons.

## Usage

```tsx
import { Path, Step } from '@retikz/react';
```

```tsx
<Path stroke="currentColor">
  <Step kind="move" to="a" />
  <Step kind="line" to="b" />
</Path>
```

`<Draw>` compiles down to `<Path>` and covers everyday step / fold / curve / arc connections; but `<Path>` additionally exposes element-level capabilities — `color` / `rotate` / `scale` / `marks` / `id` / `meta` / `animations` — that `<Draw>` does not. Reach for `<Draw>`'s single-line `way` array for everyday connections, and `<Path>` when you need an explicit Step sequence, multiple `move`s, per-segment mixing of `kind` / label / control points, or any of those Path-only capabilities:

|                                                                       | `<Draw>`                | `<Path>` + `<Step>`                              |
| --------------------------------------------------------------------- | ----------------------- | ------------------------------------------------ |
| Form                                                                  | Single-line `way` array | Container + child nodes                          |
| step / curve / fold / arc                                             | Yes                     | Yes                                              |
| `color` / `rotate` / `scale` / `marks` / `id` / `meta` / `animations` | Not exposed             | Yes                                              |
| Use when                                                              | 90% of connection cases | Explicit Step sequence, element-level capability |

## Composition

`<Path>` requires `<Step>` children (at least 2); if the first isn't `move`, the compiler coerces it to `move`:

```tsx
<Path>
  <Step kind="move" to={...} />     {/* First: must be move */}
  <Step kind="line" to={...} />     {/* Then any number of line / move / step */}
  ...
</Path>
```

`<Step>` supports thirteen kinds — `move` / `line` for straight segments, `fold` for the right-angle fold, `cycle` to close back, `curve` / `cubic` for Bezier curves, `bend` as the arc shorthand (with out/in angles and self-loops), `smooth` for a smooth curve through a list of points, `generator` for built-in or custom path generators, `arc` / `circlePath` / `ellipsePath` for arcs / full circles / full ellipses centered on the cursor, and `rectangle` for a diagonal rectangle. See [Step](/kernel/components/draw/step) and [path generators](/kernel/components/extend/path-generator) for details.

### Arrows

`arrow` picks direction (`'->'` / `'<-'` / `'<->'` / `'none'`); `arrowDetail` is a single object covering every visual spec (shape / scale / length / width / color / fill / opacity / lineWidth) plus optional `start` / `end` sub-objects for per-end overrides. The full reference — eight built-in shapes, per-end merge semantics, color / sizing / opacity, and the complete API table — lives on the **[Arrow](/kernel/components/draw/arrow)** page.

### Endpoint connection surface

When an endpoint references a node (the `{ id }` object form, or an id inside a way), you can add a `boundary` field to override the target node's [`boundary`](/kernel/components/node/overview#connection-surface-boundary) (connection surface) **for that endpoint only**. It takes the same forms as the node's `boundary`: `'shape'` (the visual shape itself) / `'circle'` (a true circle) / any registered shape name / `{ type, params }`.

```tsx
<Path arrow="->">
  <Step kind="move" to="a" />
  <Step kind="line" to={{ id: 'star', boundary: 'shape' }} />
</Path>
```

`boundary` only applies where a connection surface is meaningful: endpoint auto-clip (no explicit `anchor`) and that endpoint's standard direction / angle anchor. In direction-less reference contexts — `between` endpoints, an `offset` `of`, a node center — it is a no-op. A node's default connection surface lives on [`<Node boundary>`](/kernel/components/node/overview#connection-surface-boundary); the endpoint `boundary` is the per-edge override.

Below, two edges target the same five-pointed star (no node `boundary` set) and each picks its connection surface at the endpoint: the solid edge clips to the real tips by default, the dashed edge uses `boundary="circle"` to clip to the circumscribed circle — the surface is decided per edge.

#### Dash offset

`dashOffset` shifts only where the dash rhythm starts; it does not change the `dashPattern`. The three lines below all use `[18, 10]` and only vary the offset:

<ComponentPreview files="path-dash-offset" size="xs" />

#### Gradient stroke

Besides a plain color string, `stroke` accepts a `PaintSpec`. Linear / radial gradients, patterns, and images enter the same paint resource table; `dashPattern`, `dashOffset`, `lineCap`, `strokeOpacity`, and other stroke styles still apply to the line itself.

<ComponentPreview files="path-stroke-paint" size="sm" />

If a gradient-stroked path also has arrows, give `arrowDetail.color` or the endpoint `color` an explicit solid color; marker geometry cannot inherit a resource-backed stroke.

#### Stroke endpoints / corners

`lineCap` controls the stroke endpoint shape: `'butt'` default (square end at endpoint) / `'round'` half-circle cap / `'square'` square cap extended past the endpoint by half a stroke. `lineJoin` controls the corner shape: `'miter'` default (sharp) / `'round'` rounded / `'bevel'` flat-cut.

<ComponentPreview files="path-line-style" />

#### Semantic thickness preset

`thickness` is component / builder sugar for a semantic stroke preset — `'ultraThin'` / `'veryThin'` / `'thin'` / `'semithick'` / `'thick'` / `'veryThick'` / `'ultraThick'` — resolved into numeric `strokeWidth` before IR is produced (`thin = 1` matches the default `strokeWidth`). **Explicit `strokeWidth` always wins** — `thickness` only applies when `strokeWidth` is omitted:

<ComponentPreview files="path-thickness" size="md" />

#### Opacity

Three independent channels: `opacity` overall (multiplies onto stroke and fill), `fillOpacity` for fill only, `strokeOpacity` for stroke only. The three compose:

`strokeOpacity` uses the same stroke-opacity naming as Scene primitives, and matches the stroke-only opacity field on `<Node>`.

<ComponentPreview files="path-opacity" />

#### Stacking order (zIndex)

By default stacking = declaration order. `zIndex` overrides it explicitly: higher draws on top, omitted = 0, ties keep declaration order; effective only among siblings at the same level (same scope / top level). The two filled rectangles below are declared dodgerblue-then-red (red on top by default); setting `zIndex={1}` on the earlier dodgerblue path lifts it above the red one:

### Curves and transforms

#### Out / in angles and self-loops

Besides the symmetric `bendDirection` + `bendAngle`, `<Step kind="bend">` accepts `outAngle` / `inAngle` for the start out-angle and end in-angle to draw asymmetric curves; `looseness` tunes the control-point distance (default ≈1). **out/in take precedence over `bendDirection`.** When `from == to` (same node / same coordinate) it degenerates into a **self-loop** — the prime use case for out/in (a state-machine self transition), which a symmetric bend cannot draw.

<ComponentPreview files="path-outin-loop" size="sm" />

#### Whole-path transform (rotate / scale)

`rotate` (degrees) / `scale` (a number for uniform, or `{ x, y }` for non-uniform) transform the whole path around its **bounding-box center**, sparing a wrapping `<Scope transforms>` for a single path. The order is a hard contract: path endpoints resolve first, arrow shrink is computed on the **untransformed** geometry, then everything is wrapped in a group — so arrow direction follows the transform correctly without misalignment.

<ComponentPreview files="path-transform" size="sm" />

#### Mid-path marks

`marks` places directional marks along the path: each `{ pos, mark }` has `pos ∈ [0, 1]` (out-of-range rejected by the schema), and `mark` is initially `{ kind: 'arrow', shape, ... }` (a registered arrow name + visual subset, see [Custom Arrows](/kernel/components/extend/custom-arrow)), **oriented by the tangent at that point** (not a fixed direction). Lines, Béziers, and arcs are all tangent-oriented. Their size **scales with `strokeWidth`**, just like endpoint arrows: the thicker the line, the larger the mark.

<ComponentPreview files="path-marks" size="xs" />

#### Rounded corners (roundedCorners)

`roundedCorners` rounds every **line↔line joint** of the path with a tangent arc of the same radius — handy for flowcharts, routing, and polyline connections where you want soft corners instead of sharp ones. Omitted = sharp corners everywhere (behavior unchanged). The first / last endpoint stays sharp; a joint whose neighbor is a curve / arc / Bézier / fold stays sharp too. When the radius is too large it is **clamped per joint** to what the adjacent segment lengths allow. After a `cycle` close, the closing joint is rounded as well.

<ComponentPreview files="path-rounded-corners" size="sm" />

`roundedCorners` changes the **path geometry** — it pulls the joint vertices back and inserts a tangent arc, so it affects the bounding box, arc length, path-level `marks` normalization, and connection-point resolution. This is distinct from `lineJoin`, which only styles the **stroke render** while the path centerline stays a sharp fold. (Note: per-step edge `label`s are currently positioned along the step's own segment and are not re-fitted to the shortened, rounded geometry.) The contrast bottom uses a very thick stroke: the top path uses `lineJoin="round"` (only the stroke is rounded, the centerline stays sharp), the bottom uses `roundedCorners` (the centerline itself is an arc):

<ComponentPreview files="path-rounded-vs-linejoin" size="sm" />

### Ribbon path

`<Path kind="ribbon">` uses the same Path host to draw a fillable relation band. The centerline is still described with `<Step>`, while width, caps, sampling, and boundary mode live under `ribbon={{ ... }}`. Host fields such as `fill`, `stroke`, `opacity`, `label`, and `zIndex` stay on the Path itself.

```tsx
<Path kind="ribbon" ribbon={{ start: { width: 32 }, end: { width: 12 } }} fill="#60a5fa">
  <Step kind="move" to={[-120, 0]} />
  <Step kind="cubic" control1={[-40, -48]} control2={[40, 48]} to={[120, 0]} />
</Path>
```

#### Basic band

Centerline mode offsets both sides of the open path by `width` and emits a closed Path primitive. `stroke` outlines the band boundary; it does not draw the centerline.

<ComponentPreview files="ribbon-basic" size="xs" />

#### Width and interpolation

`width` can be fixed, split across start/end endpoints, or expressed as `kind: 'stops'` along the path. `interpolation` controls how width changes between those values.

<ComponentPreview files="ribbon-interpolation" size="md" />

<ComponentPreview files="ribbon-width-stops" size="xs" />

The built-in `bulge` profile uses `base` for both endpoint widths and `peak` for the midpoint width; when `peak` is smaller than `base`, the middle narrows instead.

<ComponentPreview files="ribbon-width-profile" size="xs" />

#### Label placement

Ribbon labels use the same GeometryLabel contract. `position` accepts keywords or a numeric `0..1` offset; `side` keeps the same default outside distance as Path labels; `placement="inside"` places the label inside the band, and `sloped: true` rotates along the centerline tangent.

<ComponentPreview files="ribbon-label" size="sm" />

#### Endpoints and caps

`start` / `end` configure endpoint width, direction, and cap. `align` controls where the centerline sits inside the band width, and `samples` can switch complex curves to sampled construction.

<ComponentPreview files="ribbon-direction" size="md" />

<ComponentPreview files="ribbon-align-cap" size="md" />

#### Precomputed boundaries

When a layout algorithm has already computed both sides, use `ribbon.mode = 'boundary'` and provide `upper` / `lower` as two open step sequences. This mode does not need `children`, and it does not accept `width`.

<ComponentPreview files="ribbon-boundary" size="sm" />

#### Styling

Ribbon is a closed area, so styling focuses on `fill`, outline `stroke`, opacity, shadows, and blend modes. `pathDefault` forwards the Path-shared drawable style fields to ribbon kind; arrows, dashes, line caps, and other stroke-only semantics belong to the default `stroke` kind.

<ComponentPreview files="ribbon-style" size="md" />

| `meta`           | `Record<string, JSON value>`                                                                                  | —              | Provenance metadata, passed through verbatim onto the Scene primitives this path emits; ignored by renderers and never part of layout / style. ### Ribbon

Ribbon reuses the Path host fields in the table above; this subsection lists only the ribbon selector and ribbon-specific entry points.

| Prop     | Type                                    | Default | Description                                                                                                    |
| -------- | --------------------------------------- | ------- | -------------------------------------------------------------------------------------------------------------- |
| `kind`   | `'ribbon'`                              | —       | Selects the built-in ribbon Path kind                                                                          |
| `ribbon` | `PathRibbonOptions`                     | —       | Required; configures widths, caps, sampling, and boundary mode                                                 |
| `label`  | `GeometryLabel \| Array<GeometryLabel>` | —       | Host label for centerline mode; shared paint, opacity, effect, stacking, and animation fields are listed above |
