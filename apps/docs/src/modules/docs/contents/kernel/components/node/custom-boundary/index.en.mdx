`boundary` decides where a connector meets a node. It normally follows the visual `shape`; register a custom boundary only when “what the node looks like” and “where lines should attach” must be independent.

The rectangle below still renders with its original shape, while `horizontal-ports` restricts connectors to the left and right ports. Open the source to see the full definition, injection, and consumption loop.

## When to extend

Check whether an existing choice already solves the problem:

| Requirement                            | Choose                                |
| -------------------------------------- | ------------------------------------- |
| Attach along the visual outline        | Omit `boundary` or use `shape`        |
| Use a circle, rectangle, or ellipse    | Select the matching built-in boundary |
| Reuse a registered shape's geometry    | Put the shape name in `boundary`      |
| Add fixed directional ports or anchors | Register a `BoundaryDefinition`       |

A boundary owns only “where the connector stops” and “where standard directional anchors sit.” It does not size the node or emit primitives; `shape` still owns visual geometry, layout bounds, and drawing. If the connection rule always matches a new visual shape, write a [custom shape](/kernel/components/shapes/custom-shape) instead of maintaining two geometries. Shape-specific custom anchors still belong to the visual shape, not the boundary extension.

## Define the capability

Use `defineBoundary` to declare a stable registry key, parameter schema, and ray intersection. Even parameterless definitions provide `z.strictObject({})`, so every payload follows the same validation path.

```ts
import { defineBoundary } from '@retikz/core';
import { z } from 'zod';

export const horizontalPorts = defineBoundary({
  name: 'horizontal-ports',
  paramsSchema: z.strictObject({}),
  boundaryPoint: (rect, toward) =>
    toward[0] < rect.x ? [rect.x - rect.width / 2, rect.y] : [rect.x + rect.width / 2, rect.y],
  anchor: (rect, name) => {
    if (name === 'left') return [rect.x - rect.width / 2, rect.y];
    if (name === 'right') return [rect.x + rect.width / 2, rect.y];
    return undefined;
  },
});
```

`boundaryPoint` receives the boundary's final resolved `rect`. Without `resolveRect`, this is the node box already derived by the visual shape. `toward` is the connector target measured from the node center. Parameterized boundaries use `{ type, params }`, where `params` must remain JSON-serializable. Functions stay in the definition and never enter IR (the intermediate representation).

Implement optional `resolveRect(context, params)` when the surface needs to resize before intersection. `context.visualRect` is the visual AABB, while `context.connectionEnvelope(kind)` asks the visual shape for a safe circle / ellipse / rectangle envelope and shares a node-local cache. The returned rect must have finite coordinates and positive width and height, or compilation fails immediately.

### Parameterized boundaries

The definition's schema owns the parameters and infers the callback's third argument. This `bias` moves the left and right ports along the node height from top `-1` to bottom `1`:

```ts
const biasedPorts = defineBoundary({
  name: 'biased-ports',
  paramsSchema: z.strictObject({ bias: z.number().min(-1).max(1) }),
  boundaryPoint: (rect, toward, { bias }) => [
    toward[0] < rect.x ? rect.x - rect.width / 2 : rect.x + rect.width / 2,
    rect.y + (rect.height / 2) * bias,
  ],
});
```

The node selects that definition with JSON-safe `{ type, params }`:

```tsx
<Node id="io" position={[0, 0]} boundary={{ type: 'biased-ports', params: { bias: 0.5 } }} />
```

## Inject into the host

The React host accepts definitions through `<Layout boundaries>`, while each node stores only the registry key:

```tsx
<Layout boundaries={[horizontalPorts]}>
  <Node id="io" position={[0, 0]} boundary="horizontal-ports">
    IO
  </Node>
</Layout>
```

When compiling core IR directly, pass the same array through `CompileOptions.boundaries`:

```ts
const { scene } = compileToScene(ir, { boundaries: [horizontalPorts] });
```

Application code owns the definitions; serialized figures keep only names or parameter objects. React and direct compilation therefore share one registration and resolution model.

## Execution model

| Stage    | Input                         | Result                                                                                 |
| -------- | ----------------------------- | -------------------------------------------------------------------------------------- |
| Merge    | Built-in + custom definitions | Build a Boundary Registry keyed by `name`                                              |
| Lookup   | `boundary` name               | Check boundary first, then the Shape Registry                                          |
| Validate | `{ type, params }`            | Parse params with the matched definition's schema                                      |
| Consume  | Direction or standard anchor  | Optionally call `resolveRect`, then `boundaryPoint` / `anchor`, without changing shape |

`boundary="shape"` is reserved and always reuses the visual shape. Other names prefer the Boundary Registry and fall back to a same-named shape only when no boundary exists. A custom boundary can therefore share a name with a shape and override only the connection rule.

## Errors and limits

- **Duplicate key**: custom definitions cannot replace built-ins, and one injection array cannot contain duplicate names; registry construction throws before compilation proceeds.
- **Empty key**: `name` must be a non-empty string.
- **Unknown name**: the error lists registered boundaries and shapes and points to the `boundaries` / `shapes` options.
- **Invalid params**: `paramsSchema` runs before any geometry function and reports the corresponding `.boundary.params` IR path.
- **Invalid resolved rect**: a non-finite or non-positive `resolveRect` result, or an exception inside the hook, reports the boundary name and Node IR path.
- **Unknown anchor**: `anchor` may be omitted or return `undefined`; standard directions fall back to the node box, while shape-specific names still resolve through the visual shape.
- **No drawing responsibility**: a boundary cannot change node size, shape, or content; use a Shape Definition or Node props for those concerns.

Two common failures throw immediately during compilation:

```tsx
<Node id="io" position={[0, 0]} boundary={{ type: 'biased-ports', params: { bias: 2 } }} />
```

```ts
compileToScene(ir, { boundaries: [biasedPorts, biasedPorts] });
```

The first violates `paramsSchema`; the second registers the same key twice.

## API Reference

### `BoundaryDefinitionInput<TParams>`

| Prop            | Type                                 | Default      | Description                                                   |
| --------------- | ------------------------------------ | ------------ | ------------------------------------------------------------- |
| `name`          | `string`                             | —            | Registry key referenced by Node `boundary`                    |
| `paramsSchema`  | `z.ZodType<TParams>`                 | —            | Validates JSON-safe `boundary.params`                         |
| `resolveRect`   | `(context, params) => Rect`          | `visualRect` | Optionally derive the surface rect from visual or safe bounds |
| `boundaryPoint` | `(rect, toward, params) => Position` | —            | Returns the ray intersection with the surface                 |
| `anchor`        | `BoundaryDefinition['anchor']`       | —            | Optional standard directional-anchor resolver                 |

Import `defineBoundary`, `BoundaryDefinition`, `BoundaryDefinitionInput`, and `BUILTIN_BOUNDARIES` from `@retikz/core`. The author-side definitions are not re-exported by `@retikz/react` or `@retikz/vanilla`.
