`<Draw>` compiles down to `<Path>` and covers everyday step / fold / curve / arc connections; but `<Path>` additionally exposes element-level capabilities — `rotate` / `scale` / `marks` / `id` / `meta` / `animations` — that `<Draw>` does not. Reach for `<Draw>`'s single-line `way` array for everyday connections, and `<Path>` when you need an explicit Step sequence, multiple `move`s, per-segment mixing of `kind` / label / control points, or any of those Path-only capabilities:

|                                                             | `<Draw>`                | `<Path>` + `<Step>`                              |
| ----------------------------------------------------------- | ----------------------- | ------------------------------------------------ |
| Form                                                        | Single-line `way` array | Container + child nodes                          |
| step / curve / fold / arc                                   | Yes                     | Yes                                              |
| `rotate` / `scale` / `marks` / `id` / `meta` / `animations` | Not exposed             | Yes                                              |
| Use when                                                    | Common connections      | Explicit Step sequence, element-level capability |

## Composition structure

Explicit steps normally need at least two entries; a single self-contained `rectangle` is an exception. Vanilla replaces a non-move first step with move. Write the starting point explicitly:

```tsx
<Path>
  <Step kind="move" to={...} />     {/* First: must be move */}
  <Step kind="line" to={...} />     {/* Then any number of line / move / step */}
  ...
</Path>
```

The following sections cover each Step action and its constraints.

### Subpaths and closure

Compare a polyline, multiple subpaths, and a closed fill in one panel. Repeated `move`s lift the pen and begin independent subpaths; the fill case uses `cycle`, which maps to SVG `Z`, to close its outline. See [Way](/kernel/components/path/draw) for focused fold and closure controls; this panel stays at the Path-container composition level.

## Path actions

Switch between `line`, repeated `move`s, `fold`, `cycle`, and `rectangle` in one panel. Repeated `move`s begin independent subpaths inside one `<Path>`; `fold` switches between two- and three-leg orthogonal connections, with `fraction` positioning the middle leg in three-leg modes; `rectangle` exposes its corner radius, and `cycle` closes back to the most recent `move` target.

| kind        | Parameters               | Result                          |
| ----------- | ------------------------ | ------------------------------- |
| `line`      | `to`                     | Straight line to the target     |
| `move`      | `to`                     | Start a subpath without drawing |
| `fold`      | `to, via, fraction`      | Orthogonal route                |
| `cycle`     | `—`                      | Close the current subpath       |
| `rectangle` | `from, to, cornerRadius` | Rectangle contour               |

<ComponentPreview files="step-actions" size="sm" />

### Orthogonal connections

Switch between two single-axis projections and fold connections over the same nodes: `horizontal` takes the target x while preserving the current y, and `vertical` preserves the current x while taking the target y; after choosing `fold`, “Fold direction” switches among `-\|`, `\|-`, `-\|-`, and `\|-\|`, while `fraction` positions the middle leg in three-leg modes. The blue solid line is the actual path, while the gray dotted line only hints at the direct direction between the nodes.

| Connection      | Step syntax                                                                           | Behavior                                                                    |
| --------------- | ------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| Horizontal axis | `kind="axis-line" axis="horizontal"`                                                  | Project on the current Scope's local horizontal axis and take only target x |
| Vertical axis   | `kind="axis-line" axis="vertical"`                                                    | Project on the current Scope's local vertical axis and take only target y   |
| Two-leg fold    | `kind="fold" via="-\|"`<br />`kind="fold" via="\|-"`                                  | Reach the target through one corner                                         |
| Three-leg fold  | `kind="fold" via="-\|-" fraction={0.5}`<br />`kind="fold" via="\|-\|" fraction={0.5}` | Reach it through two corners; `fraction` positions the middle leg           |

<ComponentPreview files="axis-line" size="sm" />

In either `axis-line` mode, omitting the target `anchor` projects to the node center and disables target-side automatic boundary clipping; a source node still clips toward the projected endpoint. The target is restricted to Cartesian coordinates or NodeTarget, excluding polar, relative, offset, and between forms.

### Target positioning

Besides absolute coordinates, `to` accepts `{ of, offset }`, `{ relative }`, and `{ relativeAccumulate }`. Switch modes and adjust x / y in the panel to see how their anchors differ:

- `offset`: offset from a node, coordinate, or PolarPosition base
- `relative`: resolve from the previous endpoint without advancing `prevEnd`
- `relativeAccumulate`: resolve from the previous endpoint and advance `prevEnd`

Relative targets also have the sugar strings `'+dx,dy'` / `'++dx,dy'`.

<ComponentPreview files="step-targeting" size="sm" />

## Curves

Switch among `curve`, `cubic`, `bend`, `smooth`, `arc`, `circlePath`, and `ellipsePath` in the panel below. Bezier control points are edited as `[x, y]` pairs and appear as dashed handles on the canvas; other kinds reveal only their bend angle, tension, angles, or radii so you can compare how they advance the cursor and produce geometry.

| kind          | Parameters                     | Result                      |
| ------------- | ------------------------------ | --------------------------- |
| `curve`       | `control, to`                  | Quadratic Bezier            |
| `cubic`       | `control1, control2, to`       | Cubic Bezier                |
| `bend`        | `bendDirection, bendAngle, to` | Bend by angle               |
| `smooth`      | `points, tension`              | Smooth curve through points |
| `arc`         | `startAngle, endAngle, radius` | Arc                         |
| `circlePath`  | `radius`                       | Circle                      |
| `ellipsePath` | `radius: { x, y }`             | Ellipse                     |

### Out / in angles and self-loops

Besides the symmetric `bendDirection` + `bendAngle`, `<Step kind="bend">` accepts `outAngle` / `inAngle` for the start out-angle and end in-angle to draw asymmetric curves; `looseness` tunes the control-point distance (default ≈1). **out/in take precedence over `bendDirection`.** When `from == to` (same node / same coordinate) it degenerates into a **self-loop** — the prime use case for out/in (a state-machine self transition), which a symmetric bend cannot draw. Switch between a self-loop and a two-endpoint connection in the panel, then use the dotted direction guides to tune both angles and looseness.

## Endpoints and connections

### Arrows

`arrow` picks direction (`'->'` / `'<-'` / `'<->'` / `'none'`), `arrowDetail` owns visual shape / size / color fields, and `arrowPlacement` uses a normalized `[0,1]` ratio to move an arrow from its existing default to final-visual-back alignment at the logical endpoint, with shared and `start` / `end` overrides. All three are equivalent on `<Path>` and `<Draw>`. See **[Arrow](/kernel/components/path/arrow)** for the `0 / 0.5 / 1` comparison, failure boundaries, and complete API.

### Endpoint connection surface

When an endpoint references a node (the `{ id }` object form, or an id inside a way), you can add a `boundary` field to override the target node's [`boundary`](/kernel/components/node/mechanism#visual-shape-vs-connection-geometry) (connection surface) **for that endpoint only**. It takes the same forms as the node's `boundary`: `'shape'` (the visual shape itself) / `'circle'` (a true circle) / any registered shape name / `{ type, params }`.

```tsx
<Path arrow="->">
  <Step kind="move" to="a" />
  <Step kind="line" to={{ id: 'star', boundary: { type: 'circle', params: { fit: 'tight', gap: 8 } } }} />
</Path>
```

`circle`, `rectangle`, and `ellipse` share `fit: 'tight' | 'bounds'` plus a signed `gap`. They default to shape-aware `tight` and `gap: 0`. Both fit values are equivalent for `rectangle`; a negative gap contracts inward but may cross the visual shape.

`boundary` only applies where a connection surface is meaningful: endpoint auto-clip (no explicit `anchor`) and that endpoint's standard direction / angle anchor. In direction-less reference contexts — `between` endpoints, an `offset` `of`, a node center — it is a no-op. A node's default connection surface lives on [`<Node boundary>`](/kernel/components/node/mechanism#visual-shape-vs-connection-geometry); the endpoint `boundary` is the per-edge override.

The five-pointed star below has no node `boundary`. The panel starts on the circle boundary, so you can compare `tight` with `bounds` and adjust `gap` immediately; switch back to the star outline to compare the real shape surface. The light dotted outline is the current circle boundary and updates with the real endpoint.

## Path-level capabilities

### Control-point inspection

After installing `@retikz/inspect`, use `InspectLayout` and `InspectPath` to display Bezier control points and handles; `labels` adds their identifiers. These helpers do not change the original path geometry or interaction. See [`@retikz/inspect`](/kernel/packages/inspect) for setup.

<ComponentPreview files="path-inspector" size="sm" />

### Whole-path transform

`rotate` (degrees) / `scale` (a number for uniform, or `{ x, y }` for non-uniform) transform the whole path around its **bounding-box center**, sparing a wrapping `<Scope transforms>` for a single path. Arrows and labels follow the path transform. The dotted path preserves the original geometry while the panel's rotation and two-axis scale affect only the solid path for direct comparison.

<ComponentPreview files="path-transform" size="sm" />

### Mid-path marks

`marks` places directional marks along the path: each `{ pos, mark }` has `pos ∈ [0, 1]` (out-of-range rejected by the schema), and `mark` is initially `{ kind: 'arrow', shape, ... }` (a registered arrow name + visual subset, see [Custom Arrows](/kernel/components/path/custom-arrow)), **oriented by the tangent at that point** (not a fixed direction). Lines, Béziers, and arcs are all tangent-oriented. Their size **scales with `strokeWidth`**, just like endpoint arrows: the thicker the line, the larger the mark. Move both position controls to watch the marks follow the local tangent as they travel along the path.

<ComponentPreview files="path-marks" size="sm" />

### Rounded corners

`roundedCorners` rounds every **line↔line joint** of the path with a tangent arc of the same radius — handy for flowcharts, routing, and polyline connections where you want soft corners instead of sharp ones. Omitted = sharp corners everywhere (behavior unchanged). The first / last endpoint stays sharp; a joint whose neighbor is a curve / arc / Bézier / fold stays sharp too. When the radius is too large it is **clamped per joint** to what the adjacent segment lengths allow. After a `cycle` close, the closing joint is rounded as well.

<ComponentPreview files="path-rounded-corners" size="lg" />

`roundedCorners` changes the **path geometry** — it pulls the joint vertices back and inserts a tangent arc, so it affects the bounding box, arc length, path-level `marks` normalization, and connection-point resolution. This is distinct from `lineJoin`, which only styles the **stroke render** while the path centerline stays a sharp fold. The panel shows `lineJoin` above and geometric rounding below so you can drag the radius and compare them directly. See [Implementation](/kernel/components/path/mechanism) for label sampling and gaps.

<Comparison target="tikz" title="Path Syntax Mapping">

| retikz                             | TikZ mapping                                      |
| ---------------------------------- | ------------------------------------------------- |
| `style.lineCap` / `style.lineJoin` | `line cap` / `line join`                          |
| `ultraThin` … `ultraThick`         | `ultra thin` … `ultra thick`                      |
| `marks` and endpoint arrows scale  | Mark and endpoint-arrow sizing follows line width |
| `roundedCorners={r}`               | `rounded corners=<r>`                             |
| `style.color`                      | `color=`                                          |

</Comparison>

## Styling

Set `strokeWidth` directly or use the semantic `thickness` presets from `ultraThin` through `ultraThick`; an explicit `strokeWidth` wins. `dashOffset` shifts only the dash rhythm's origin. `lineCap` / `lineJoin` shape endpoints and corners; the panel keeps overall and stroke-opacity channels so each change remains directly observable.

<ComponentPreview files="path-style" size="lg" />

### Gradient stroke

Besides a plain color string, `stroke` accepts an `IRPaint`. Linear / radial / conic gradients, patterns, and images enter the same paint resource table; `dashPattern`, `dashOffset`, `lineCap`, `strokeOpacity`, and other stroke styles still apply to the line itself. Switch among the three gradients in the panel: linear uses a direction angle, radial uses a center and radius, and conic uses a center and start angle. They share the same three color stops. The curve shows the stroke result, while the swatch below makes the full gradient distribution easier to inspect.

<ComponentPreview files="path-stroke-paint" size="lg" />

If a gradient-stroked path also has arrows, give `arrowDetail.color` or the endpoint `color` an explicit solid color; marker geometry cannot inherit a resource-backed stroke.

### Stacking order

By default stacking = declaration order. `zIndex` overrides it explicitly: higher draws on top, omitted = 0, ties keep declaration order; effective only among siblings at the same level (same scope / top level). The two filled rectangles below are declared dodgerblue-then-red; move the blue path's `zIndex` through negative, zero, and positive values to compare the overlap order.
