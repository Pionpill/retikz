## 一张图看懂

React JSX、Vanilla plain spec 与外部生成的 IR 最终汇合到同一份 JSON 契约。`@retikz/core` 只接收 IR 和显式注入的编译能力，输出 renderer-agnostic（不绑定渲染后端）的 Scene；SVG 与 Canvas 在 Scene 之后才分流。

<ComponentPreview files="principles-pipeline" size="sm" hideCode />

这条主链刻意设置了四个边界：

- **作者入口**负责书写体验，把框架或 plain spec 归一成 IR，不重新实现几何与渲染语义。
- **IR**保存“想画什么”，必须是可校验、可序列化的 JSON，供持久化、AI 和跨运行时共享。
- **core compiler**负责 lowering、布局、命名引用、路径解析与资源收集，把声明转换成可渲染结果。
- **Scene**保存“renderer 应该画什么”，SVG、Canvas、SSR 和交互 runtime 都从这里继续工作。

## 设计原则

这些原则不是口号，而是一组能力归属测试。遇到新需求时，先判断它改变的是书写体验、共享绘图语义、高层领域模型、可替换编译策略，还是后端运行行为，再从对应 owner 开始读源码。

<ComponentPreview files="principles-placement" size="md" hideCode />

读图顺序是“需求信号 → 设计原则 → 源码 owner”。箭头指向第一责任 owner，不代表一项功能只能改一个文件；同一能力可以同时包含 authoring、contract 与 runtime 接线，但每一层语义只能有一个真源。

| ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------- |
| 入口归一为 IR       | [`builder.ts`](https://github.com/Pionpill/retikz/blob/main/packages/kernel/react/src/kernel/adapter/builder.ts)<br />[`normalize.ts`](https://github.com/Pionpill/retikz/blob/main/packages/kernel/vanilla/src/spec/normalize.ts)<br />作者输入 → IR | React / Vanilla<br />输出不一致  |

### 共享契约

React 的 `buildIRWithContributions` 与 Vanilla 的 `normalizeFigureSpec` 都把作者输入归一为 IR；`compileToScene` 只接收 IR 和本次调用的 `CompileOptions`，再输出 Scene。因此，同一份输入可以脱离具体框架被持久化、测试或交给不同 renderer。

IR 保存“想画什么”，所以只能包含可校验、可序列化的数据；Scene 保存“已经布局好的图元”，所以只能包含各后端都能解释的 primitive、layout、资源与动画。回调、DOM 节点和 Canvas 状态分别留在 adapter 或 runtime。

判断边界是否失守很直接：如果同一能力需要 React 与 Vanilla 各写一次布局，或者 Scene 必须携带 DOM / Canvas 对象才能表达，它就落在了错误的 owner。

### 能力归属

新增能力先问 core 是否已经能够表达它。只是换一套更友好的参数写法时，用 Sugar 同步展开为现有 Kernel；需要保留高层领域结构时，用 composite 在布局前 lowering；需要增加可替换的几何或编译策略时，定义 `XxxDefinition` 并接入 provider registry。

`createCompileContext` 会先 lowering composite，再把内置与调用方注入的 definitions 解析成当前编译专用的 registries。之后所有入口共享同一套布局、anchor、path 与资源组装逻辑，而不是在 adapter 或 renderer 中复制实现。

一个实用的审查信号是：如果 shape、anchor 或 path 行为在 React、Vanilla 与某个 renderer 中出现多份实现，应先补足 core 契约，再删除上层分叉。

### 运行时边界

React 的 `Layout.tsx` 负责组件生命周期、编译选项和 hydration 接线；Vanilla 的 `to-scene.ts` 负责输入归一、compile 与 mount 前准备；SVG、Canvas backend 则只消费 Scene。它们可以拥有宿主环境能力，但不能重新定义 IR 语义。

因此，移除 React 不应改变几何结果，新增 renderer 也不应要求修改作者 DSL 或 core 布局算法。出现这两种情况时，应先检查是否把共享语义误放进了 adapter 或 backend。

## Definition-registry 扩展机制

“define-registry”不是一个全局注册 API，而是一套反复使用的扩展模式：contract 定义能力形状，`defineXxx` 保留定义点的类型安全，provider 集合提供内置与自定义项，compile 在本次调用的 registry 中按 key 查找。

<ComponentPreview files="principles-registry" size="sm" hideCode />

完整过程分为五步：

1. **声明 contract**：`XxxDefinitionInput` 描述作者需要提供的强类型字段，擦除后的 `XxxDefinition` 是 registry 可统一保存的形态。
2. **调用 `defineXxx`**：在定义点校验泛型、schema 与回调签名，并集中完成必要的类型擦除；它不会修改进程级全局状态。
3. **收集 definitions**：内置项放入 `BUILTIN_XXX`，调用方通过 `CompileOptions` 注入自定义项，两者使用相同 definition 类型。
4. **解析 registry**：`resolveXxxRegistry` 先加入内置项，再加入自定义项，生成当前 compile 独享的 `ReadonlyMap`；空 key 或重复 key 立即报错，自定义项不能静默覆盖内置项。
5. **编译期消费**：IR 通过 `name`、`type` 或 `kind` 提供 lookup key，compiler 取得 definition，校验 payload 后执行对应的 geometry、lowering 或 emit 回调。

当前主要扩展族都沿用这套结构：

| 能力                 | IR 中的选择方式         | 注入入口                                     |
| -------------------- | ----------------------- | -------------------------------------------- |
| Shape                | `Node.shape`            | `CompileOptions.shapes`                      |
| Boundary             | `Node.boundary`         | `CompileOptions.boundaries`                  |
| Clip                 | `Scope.clip`            | `CompileOptions.clips`                       |
| Arrow                | path arrow mark         | `CompileOptions.arrows`                      |
| Pattern              | pattern paint           | `CompileOptions.patterns`                    |
| Path generator       | `Step.kind='generator'` | `CompileOptions.`<br />`pathGenerators`      |
| Path kind            | `Path.kind`             | `CompileOptions.pathKinds`                   |
| Ribbon width profile | ribbon options          | `CompileOptions.`<br />`ribbonWidthProfiles` |
| Composite            | `namespace + type`      | `CompileOptions.composites`                  |

普通 provider 找不到 key 时会 fail-loud，并列出已注册项；未注册 composite 是例外，它发出 compile warning、跳过该高层节点并继续编译其余内容。独立调用 `lowerIRToKernel` 时则会把未注册 composite 提升为错误。

## 完整执行流程

`compileToScene` 的内部主线不是“遍历 IR 后直接输出 SVG”。它先把高层能力降到 Kernel，再建立 provider 与运行时上下文，分阶段解决布局和引用，最后才组装 Scene。

<ComponentPreview files="principles-compile" size="sm" hideCode />

### 1. 作者输入生成 IR

React 的 `builder.ts` 静态遍历 children：Kernel 组件一一写入 IR，Sugar 函数组件同步展开后继续遍历，可嵌入 Tier 2 组件通过 adapter 贡献 composite 节点和 definition。Vanilla 的 `normalize.ts` 则把 plain spec 与 adapter 输出规范化为相同 IR。

这一阶段不做最终文字测量、anchor 求解或 renderer 输出。IR 可以在这里被保存、发送给 AI、做 JSON Patch，或者直接交给其它运行时。

### 2. 创建编译上下文

`createCompileContext` 把 `CompileOptions` 解析成一次编译专用的上下文：文字度量、精度、默认距离、warning dispatcher、TeX lowering，以及各个 provider registry。

没有隐式全局注册意味着两次 compile 可以注入不同扩展而互不污染，也让 SSR、测试与并行渲染更容易保持确定性。

### 3. Composite lowering

带 `namespace + type` 的 Tier 2 节点先查 composite registry，经 schema 校验后调用 `expand`，递归展开到只剩 Node、Path、Coordinate 与 Scope 等 Tier 1 Kernel IR。展开必须在布局和 anchor 解析之前完成。

### 4. 节点、Scope 与命名空间

compiler 先解析 Node、Coordinate 和 Scope 的位置、文字、shape、boundary、transform 与样式继承，计算 layout，并把带 `id` 的结果登记进 namespace stack。Scope 的命名 layout 会在子树 bbox 完成后回填。

这一步产出的 layout 是后续相对定位、anchor 查询和自动 viewBox 的共同依据。

### 5. 延迟解析 Path

Path 在遍历时先保留输出位置并进入待处理队列；可引用布局就绪后，再按 `Path.kind`、step target、arrow、generator 与 ribbon definitions 解析成 primitives。这样路径可以引用同一作用域中稍后声明的节点，同时保持原始绘制顺序。

### 6. 组装 Scene 与启动 runtime

core 合并 primitives、layout bounds、paint/clip 资源和根动画。显式 `viewBox` 优先，否则根据收集到的边界与 padding 计算 Scene layout，最后按 `zIndex` 稳定排序。

SVG backend 把 Scene 转成中性 SVG 描述树，再序列化或交给 React；Canvas backend 直接绘制 Scene。hydration 根据 `data-retikz-id` 或 hit-test 把运行时 handler 重新绑定到图元，animation runtime 则在相同 Scene 动画描述上驱动 WAAPI 或 Canvas 时钟。

## 包与源码职责

Kernel 组的依赖方向从能力提供方指向使用方。实线是主要构建链，虚线表示补充的直接依赖。

| 包                | 主要职责                                                        |
| ----------------- | --------------------------------------------------------------- |
| `@retikz/math`    | 零依赖几何、曲线、矩阵与数值算法                                |
| `@retikz/core`    | IR/schema、Scene contract、provider contract 与编译器           |
| `@retikz/render`  | SVG、Canvas、hydration 与 animation runtime                     |
| `@retikz/react`   | Kernel/Sugar JSX adapter、`<Layout>` runtime 与 React 水合接线  |
| `@retikz/vanilla` | plain spec、IR/Scene 输入、SVG/Canvas mount 与 SSR              |
| `@retikz/tex`     | MathJax 接入，把 LaTeX 公式 lowering 成 renderer-neutral glyphs |
