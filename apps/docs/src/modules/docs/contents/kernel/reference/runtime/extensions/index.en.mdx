This page explains how to **extend** retikz from the runtime perspective: host-injected extension points fill capabilities the built-in components do not cover. It is for people shipping third-party packages, integrating a host, or adding new primitives. Everyday authoring still starts from [Components](/kernel/components/layout), with each domain-specific extension page placed at the end of its related component group.

> Extension functions and registries **never enter the IR**. The IR stores only serializable names, kinds, and parameters; the host injects behavior through `CompileOptions`, `<Layout>` props, or an optional lowerer.

## What each part covers

| Topic                     | Extends                                                                                                      | Reach for it when                                                                                                                              |
| ------------------------- | ------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| Custom Shapes             | Registering new node shapes (`ShapeDefinition` + `CompileOptions.shapes`)                                    | You need cylinder / cloud beyond the 6 registered built-ins + 2 presets (hexagon is already expressible via the built-in `polygon{ sides:6 }`) |
| Custom Boundaries         | Registering new node connection surfaces (`BoundaryDefinition` + `CompileOptions.boundaries`)                | The visual shape stays the same, but lines should attach to semantic ports, a circular outline, or another separate surface                    |
| Custom Clips              | Registering new scope clipping regions (`ClipDefinition` + `CompileOptions.clips`)                           | Scope clipping needs a reusable named mask, path clip, or domain-specific viewport                                                             |
| Custom Arrows             | Registering new arrow styles (`defineArrow` / `ArrowDefinition` + `CompileOptions.arrows`)                   | You need bracket / domain-specific end caps                                                                                                    |
| Custom Patterns           | Registering new fill patterns (`definePattern` / `PatternDefinition` + `CompileOptions.patterns`)            | You need cross / stripes / special motifs                                                                                                      |
| Custom Paths              | Registering new Path kinds (`definePathKind` / `PathKindDefinition` + `CompileOptions.pathKinds`)            | You need to treat the whole Path as a highlight, double line, domain relation, or another relation form                                        |
| Path Generators           | Registering new curve generators (`PathGeneratorDefinition` + `CompileOptions.pathGenerators`)               | You need parabola / waves / custom curves                                                                                                      |
| Composite (Tier 2)        | Registering Tier 2 high-level nodes (`CompositeDefinition` + `CompileOptions.composites`)                    | A domain package lowers high-level nodes into Tier 1 primitives — see [Composites](/kernel/reference/composites)                               |
| Custom Easing             | Registering new easing curves (`EasingRegistry` + `<Layout easings>`)                                        | You need spring or other easings beyond the built-ins                                                                                          |
| Custom Animation Property | Registering new animation property channels (`AnimationPropertyDefinition` + `<Layout animationProperties>`) | You need blur or other animation properties beyond the built-ins                                                                               |

## Three extension models

Extension points fall into three models by mechanism; knowing which one a capability belongs to tells you how it's defined and when it takes effect:

- **Definition extensions** (shape / boundary / clip / arrow / pattern / custom path / path generator / composite): defined with an `xxxDefinition`, injected via `CompileOptions` / `<Layout>`, applied at compile time; the IR only carries a name, kind, or operation. Providers are uniformly injected as definition arrays. Shape / boundary / arrow / pattern / path generator use `name` as the key, clip and path kind use the schema `kind` literal, and composite uses explicit `namespace` + `type`. Any key collision throws, including collisions with built-ins.
- **Registry extensions** (easing / animation property): the injection points are lightweight registries on `<Layout>`, applied at runtime inside the renderer, never entering compile. Easing has no `EasingDefinition` — the value is just a cubic-bezier tuple or a function; an animation property needs both an interpolator and backend application, which is why it uses `AnimationPropertyDefinition`.
- **Host lowerer** (TeX formula): `CompileOptions.lowerTex` is an optional host capability that lowers formulas into plain paths at compile time; it is not a general primitive extension and degrades diagnosably when absent.
