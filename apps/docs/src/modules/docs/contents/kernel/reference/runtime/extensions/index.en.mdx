This page is an extension-point dictionary. Use it to decide which mechanism owns a custom capability, where it is injected, and what remains in IR. Step-by-step implementations live in the extension guide at the end of each capability group. See [Architecture Principles](/kernel/concepts/design/principles) for ownership and completeness checks.

> Extension functions and registries never enter IR. IR stores serializable keys and parameters; the host injects behavior during compile or runtime.

## Extension models

| Model               | Capability families                                    | Stage                          |
| ------------------- | ------------------------------------------------------ | ------------------------------ |
| Definition registry | shape, boundary, clip, arrow, pattern, path, composite | compile / layout-aware compile |
| Runtime registry    | easing, animation property                             | render / animation runtime     |
| Host lowerer        | optional heavy lowering such as TeX                    | compile-time text layout       |

Definition capabilities use `XxxDefinition` and `defineXxx`; built-ins and custom definitions merge into a compile-local registry. Runtime registries hold host functions outside the compile contract. A host lowerer supplies an optional integration without expanding the general primitive model.

Layout proposals are not a new registry. They are the closed, general child-evaluation contract inside each layout-aware `CompositeDefinition.compile` callback. Built-in children, third-party providers, and nested composites continue through the same composite / provider registries, compile environment, and replay transaction; Core has no child-type measurement whitelist.

## Capability index

| Capability         | IR selection key   | Injection point                                                   |
| ------------------ | ------------------ | ----------------------------------------------------------------- |
| Shape              | `Node.shape`       | `CompileOptions.shapes`                                           |
| Boundary           | `Node.boundary`    | `CompileOptions.boundaries`                                       |
| Clip               | `Scope.clip.kind`  | `CompileOptions.clips`                                            |
| Arrow              | arrow shape name   | `CompileOptions.arrows`                                           |
| Pattern            | pattern shape name | `CompileOptions.patterns`                                         |
| Path generator     | generator name     | `CompileOptions.pathGenerators`                                   |
| Path kind          | `Path.kind`        | `CompileOptions.pathKinds`                                        |
| Composite          | `namespace + type` | `CompileOptions.composites`                                       |
| Easing             | easing name        | `<Layout easings>`                                                |
| Animation property | property name      | `<Layout animationProperties>` (custom properties on Canvas only) |
| TeX lowerer        | math text payload  | `CompileOptions.lowerTex`                                         |

Core's generic path-kind slot is `CompileOptions.pathKinds`, and Core supplies only the `stroke` definition. Optional path kinds such as Ribbon are Standard Definitions loaded through that same slot; their schemas, geometry, and runtime datasets stay outside Core.

## Diagnostics

- Compile Definition registries reject empty and duplicate keys while merging built-ins with custom items; custom definitions cannot silently replace built-ins.
- Runtime registries such as easings and animation properties use the host-provided `Record` directly and do not run that Definition merge diagnostic. A renderer warns and skips unknown custom animation properties.
- Missing ordinary Definition keys fail loudly and list registered items.
- Missing composites warn and skip the node during full compile; standalone lowering promotes the condition to an error.
- The Composite registry accepts mutually exclusive `expand` and `compile` branches; `lowerIRToKernel` fails explicitly on a `compile` branch that requires the complete environment.
- A layout-aware composite's `layoutChild(child, proposal)` returns a resolved / failed outcome. Discarded failure stays isolated; selected failure must be promoted through the current callback's `raise()`, preserving the original provider, cause, source path, and `probe[...]` occurrence.
- A proposal is validated and frozen by value for each call. Failures, results, replays, and output children instead have callback-local / compile-local ownership and are selected only through `replay()` / `raise()` / `scope()`. Reusing, forging, spread-copying, or transferring these ownership-bound objects across compiles or callbacks fails before any commit.
- An ordinary error thrown by a provider may become a recoverable failed probe. Malformed provider output, invalid proposals, token misuse, and Core invariants remain fatal contract / invariant errors rather than discardable failures.
- Schema and payload validation run before consuming a definition, and diagnostics identify the capability family and lookup key.
