After [basic usage](/kernel/visual/shadow/usage), this page explains preset resolution, shadow framing, and how SVG and Canvas consume the same result.

## Presets resolve into shadows on primary geometry

A preset string supplies its shadow fields. An object merges preset fields first, then overrides them with explicit fields. For example, `{ preset: 'md', offsetX: 12 }` changes horizontal offset while retaining other preset fields. An object without a resulting color receives `rgba(0,0,0,0.5)`.

The string `'none'` produces no shadow. In an object, `preset: 'none'` supplies no base fields: explicit offsetX and offsetY can still produce a shadow. Finding none does not mean the entire object is discarded.

The resolved shadow enters Scene on primary geometry. Node text and labels are separate outputs and do not automatically receive its shadow. Scope defaults do not flatten descendants into an image.

The resolved value below has two consumers: extent estimation and rendering. Estimating bounds does not render shadow pixels.

## Shadows expand framing while geometry determines connections

Three regions have distinct responsibilities:

- **Geometry bounds** describe the shape itself. Shadows do not change node dimensions, path points, or connection surfaces.
- **Estimated visible bounds** add room for offset and blur and participate in automatic framing.
- **The output window** is the resulting viewBox. An explicit viewBox is not enlarged automatically.

Follow the same 100-by-60 rectangle. Blue is the shape, gray dots mark the original geometry, and orange marks estimated bounds. All three views use the same scale.

<ComponentPreview files="shadow-bounds" size="md" hideCode type="illustration" />

With `offsetX = 12`, `offsetY = 8`, and `blur = 6`, the implementation expands left by 6, right by 18, top by 6, and bottom by 14. Bounds `(0, 0, 100, 60)` become `(-6, -6, 124, 80)`:

| Direction    | Expansion                                        |
| ------------ | ------------------------------------------------ |
| Left / right | blur + max(0, -offsetX) / blur + max(0, offsetX) |
| Top / bottom | blur + max(0, -offsetY) / blur + max(0, offsetY) |

This is a layout extent estimate, not a pixel scan of blur. Automatic layout collects it alongside the original geometry. Connections still use the original shape. A viewBox limited to the rectangle can leave its shadow outside the output window.

## SVG expands the filter computation region separately

An SVG filter has its own computation region. A small region can clip a shadow even when the canvas has room. A horizontal line can have a zero-height geometry box; percentage expansion can still give zero.

Retikz uses `filterUnits="userSpaceOnUse"`, starts with the Scene viewBox, and expands the filter region for offset and blur. This changes the filter computation window, not an explicit viewBox.

Matching fields produce the same stable key for reusing filter definitions within the current SVG output. Geometry references the filter. Keys visit offsetX, offsetY, blur, color, and opacity in a fixed order, independent of object field order.

SVG uses `feDropShadow` with `stdDeviation = blur / 2`. Canvas saves context, sets shadow parameters, draws, and restores context. Its offset vector is mapped through the current transform; blur is calibrated by the geometric mean of the axis scales.

Both express the same shadow intent, but blur rasterization need not match pixel for pixel. The color's alpha and explicit opacity both affect transparency.
