After [basic usage](/kernel/visual/pattern/usage), this page explains how spacing becomes a repeat period, how matching patterns share resources, and how each backend applies the texture.

Pattern processing involves three forms of data:

- Pattern specification: the name, size, and styles stored in IR, describing what to draw.
- Pattern definition: generation logic registered by name, whose `emit` function produces texture geometry.
- Tile: serializable geometry and a final repeat period, ready for a backend to repeat.

## How spacing becomes a repeat period

`resolvePaint` looks up the definition by `shape` in the active registry, then selects the base size: explicit `size`, the definition's `defaultSize`, or finally 8. Unknown names fail instead of selecting another pattern. Size must be finite and positive and is rounded to the current compilation precision.

Next, `resolvePatternStyle` prepares effective styles. Top-level line settings form the base, while horizontal and vertical grid settings independently override it. Sparse `lineStyleCycle.overrides` expand into a complete cycle; positions without an override retain the base style. Definitions can consume effective styles without interpreting sparse configuration again.

Base size and final period can differ. For built-in `lines` with `size: 10` and a cycle length of 3, adjacent lines remain 10 units apart, but a 30 × 30 tile holds all three styles. Repeating every 10 units would restart the tile before the second and third styles could form a complete cycle.

Orange distinguishes the accented line in each cycle. The left square holds one complete tile; the larger region on the right preserves the same spacing.

<ComponentPreview files="pattern-period" size="sm" hideCode type="illustration" />

The return value of `emit` expresses this distinction. A primitive iterable retains the base size; `{ tileSize, motif }` supplies an explicit period. Core checks that the period is finite and positive and validates the emitted primitives. Custom definitions can therefore control repetition without teaching backends new pattern names.

## How elements share a texture

During compilation, the paint registry converts specifications into resource references. On the first registration of a specification, Core invokes the bound definition's `emit`, collects and validates its geometry, and creates a Scene paint resource containing `spec` and `tile`. The element's fill or stroke stores a `resourceRef` pointing to that resource.

The Node fill and Path stroke below use the same specification. Both reference one paint resource consumed by the backend.

<ComponentPreview files="pattern-resource" size="sm" hideCode type="flow" />

Registering the same specification again in that registry returns the existing reference and skips generation. Resource keys recursively sort object fields, so changing field insertion order does not create another resource. Array order remains significant because arrays such as cycle configurations carry ordering information.

Reuse compares specifications, not rendered appearances. Omitting a default and explicitly supplying that default are not guaranteed to share a resource. The cache belongs to the created paint registry; it is not a global cache across every compilation task.

Definition functions stay in Core's resolution context and never enter IR or Scene. Scene carries specifications, tiles, and references, so backends need neither the registry nor another execution of user definitions.

## How backends consume the same tile

SVG converts a tile into a `<pattern>`. Its width and height use the final period, `patternUnits="userSpaceOnUse"` selects drawing units, and `rotation` becomes `patternTransform`. Enlarging the target outline therefore reveals more texture instead of stretching the tile to fit. This does not fix the texture to screen pixels: view scaling still affects its appearance.

Canvas creates an offscreen canvas, draws the tile into it, and calls `createPattern(..., 'repeat')`. It applies rotation through `setTransform`. This path requires a working `createOffscreen` factory; without an offscreen context, it cannot produce the texture.

Both backends use the texture as fill or stroke, with the target geometry determining the visible region. A pattern does not create a node outline or change layout or hit geometry.

Background handling differs: SVG draws `motif` directly and does not turn `tile.background` into a separate rectangle. Canvas paints that background before drawing `motif`. Built-in definitions already include background geometry in their tiles. Custom definitions that need a background on both backends should likewise handle `context.background` inside `emit`, rather than relying solely on Canvas's background step.
