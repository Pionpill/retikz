`@retikz/core` is retikz's **graphics foundation**: it defines a stable, validated, renderable graphics contract and provides the shared IR, Scene compilation, geometry, and extension capabilities. Downstream modules such as `@retikz/plot` build on these capabilities and share the same underlying semantics.

It brings a mature vocabulary of nodes, paths, and anchors into the browser through React components and Vanilla plain specs. The underlying JSON IR is the shared contract connecting human-authored DSLs, LLM output, and SVG / Canvas renderers.

`@retikz/core` has a simple mental model: first describe **what each primitive is**, then describe **the connections and geometry between primitives**.

| Core capability             | Carried by               | What it solves                                                                                                                                                |
| --------------------------- | ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Primitive model**         | `Node`                   | Describes a visible object itself: shape, text, fill, stroke, size, position, and anchors that other elements can reference.                                  |
| **Primitive relationships** | `Path` / `Step` / `Draw` | Describes connections and geometry between objects: start point, end point, intermediate actions, and how arrows or edge labels are organized along the path. |

## AI-First

**AI-friendliness is not one of retikz's features — it's the reason retikz exists.**

retikz picks IR JSON over JSX as the primary AI interface, using OpenAI Structured Outputs or Anthropic Tool Use to constrain output to the expected schema, followed by runtime validation.

AI-friendliness shapes every layer of the design: schemas keep their hierarchy and discriminators clear, field values use semantically explicit and verifiable types, and higher-level abstractions map predictably to the same core IR. The goal is to reduce guesswork and make generated results easier to validate, correct, and reuse.

| Design layer                     | How                                                             |
| -------------------------------- | --------------------------------------------------------------- |
| **Schema structure**             | Clear discriminators and nesting reduce generation ambiguity    |
| **Value types**                  | Prefer bounded, serializable, and verifiable data structures    |
| **Higher-level abstractions**    | Map high-level intent predictably to the same core IR           |
| **Single-source types & schema** | zod single source → TS types + JSON Schema                      |
| **Text DSL (long-term)**         | Mature drawing syntax that gives LLMs stronger zero-shot priors |

## IR at the Center

<ComponentPreview name="ir-centric" hideCode />

Every input form (JSX / DSL / AI) compiles to the same IR; every output form (renderer) reads from it.
**Persistence, cross-platform support, and AI integration aren't separate features — they're the same dividend paid by an IR-centric model.**
The practical benefit is straightforward:

- You maintain saving, editing, and rendering around one IR contract.
- You do not need separate formats for JSX, AI output, or each renderer.
- System boundaries stay clearer, and future extensions get cheaper.

## Layered Abstraction

retikz's DSL surface has three kinds of constructs. Their boundaries show whether a capability belongs in IR, only simplifies authoring, or lowers from a higher-level module:

| Layer      | Examples                              | In IR?                                 | Where           |
| ---------- | ------------------------------------- | -------------------------------------- | --------------- |
| **Kernel** | `<Layout>` `<Node>` `<Path>` `<Step>` | ✅ Maps 1:1 to IR nodes                | `@retikz/core`  |
| **Sugar**  | `<Draw way={[...]} />`                | ❌ Expands into Kernel at compile time | `@retikz/react` |
| **Tier 2** | `<Plot>`                              | ✅ High-level node + lowering hook     | Domain packages |

For example, `<Draw way={['a', 'b']} />` only provides a more concise way to author a path. When the IR is built, `way` is parsed into a sequence of `Step`s and assembled into a `Path`; the final IR contains only `Path` and `Step`, not `Draw`.

Hard rule: **Sugar introduces no new capabilities** — anything Sugar can express, Kernel can. That lets Sugar optimize authoring ergonomics without hiding core semantics inside an adapter.

## General Primitives, Arbitrary Composition

retikz describes figures with a small set of components whose responsibilities stay explicit. Each component owns one layer of structure or geometry, then combines through nesting and references into a complete figure.

| Group                       | Component      | Responsibility                                                                |
| --------------------------- | -------------- | ----------------------------------------------------------------------------- |
| **Layout**                  | `<Layout>`     | Hosts the figure, collects its description, and configures size and rendering |
|                             | `<Scope>`      | Groups child primitives and applies local transforms and inherited styles     |
| **Primitive model**         | `<Node>`       | Describes a visible object's shape, text, position, and anchors               |
|                             | `<Coordinate>` | Declares an invisible named coordinate for positioning and references         |
| **Primitive relationships** | `<Path>`       | Describes a complete path, including stroke, fill, markers, and child `Step`s |
|                             | `<Step>`       | Describes one move, line, curve, arc, or other path action                    |

Higher-level modules can keep composing these three groups of responsibilities without changing core semantics.

Sugar only simplifies common authoring. It does not enter the IR or add capabilities that Kernel cannot express:

| Sugar                                     | Expands to                         | Responsibility                                     |
| ----------------------------------------- | ---------------------------------- | -------------------------------------------------- |
| `<Draw>`                                  | `<Path>` + a sequence of `<Step>`s | Provides concise path relationships through `way`  |
| `<EdgeLabel>`                             | `Step.label`                       | Declares a path-segment label through child syntax |
| `<Arc>` / `<Circle>` / `<Rectangle>` etc. | `<Path>` + geometric `<Step>`s     | Converts high-level geometry into a path structure |

## Package Relationships

The Kernel group currently contains six lockstep-versioned packages, spanning the zero-dependency computation base, rendering, framework entries, and optional formula support:

Solid lines show primary build dependencies; dashed lines show secondary direct dependencies. `math` provides pure computational geometry, `core` defines the graphics contract, `render` provides rendering backends, `react` / `vanilla` provide authoring entries, and `tex` plugs formula rendering into core.

| Package           | Role                        | Depends on    |
| ----------------- | --------------------------- | ------------- |
| `@retikz/math`    | Computational geometry      | None          |
| `@retikz/core`    | IR, schemas, Scene compiler | math · zod    |
| `@retikz/render`  | SVG / Canvas runtime        | core · math   |
| `@retikz/react`   | React JSX adapter           | core · render |
| `@retikz/vanilla` | Plain specs and SSR         | core · render |
| `@retikz/tex`     | LaTeX formula lowering      | core          |

## Framework-Agnostic, Shared IR

React components and Vanilla plain specs both produce the same IR, while the SVG and Canvas renderers consume the same Scene. Framework layers only own authoring ergonomics, lifecycle, and backend selection; they do not introduce new geometry semantics.

The same figure data can therefore be reused across authoring entries and renderers without describing its primitives and relationships again.

<Comparison target="tikz" title="Relation to TikZ">

retikz's naming, path actions, and anchor model are direct tributes to LaTeX's TikZ package.

| Aspect        | LaTeX TikZ      | retikz                             |
| ------------- | --------------- | ---------------------------------- |
| Runtime       | LaTeX compiler  | Browser / Node                     |
| Syntax        | `\node` `\draw` | `<Node>` `<Draw>`                  |
| Output        | PDF / SVG       | SVG / Canvas; PDF / Native planned |
| Interactivity | None            | React / runtime events             |
| Persistence   | `.tex` source   | JSON IR                            |

IR ↔ TikZ source conversion belongs to a future codec direction: the goal is to edit in the browser and still fit into a LaTeX workflow, or migrate existing TikZ figures from `.tex` files into retikz IR / React.

You do not need to know TikZ to use retikz. retikz borrows naming vocabulary (node / path / anchor / step), while figures can be described with React components or Vanilla plain specs.
