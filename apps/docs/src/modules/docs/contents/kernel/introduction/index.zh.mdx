`@retikz/core` 是 retikz 的 **绘图底座**：它定义稳定、可校验、可渲染的图形契约，并提供共享的 IR、Scene 编译、几何与扩展能力。`@retikz/plot` 等后续模块都建立在这些能力之上，共享同一套底层语义。

它把成熟的节点 / 路径 / anchor 词汇带进浏览器，并提供 React 组件与 Vanilla plain spec 两种写法。底层 JSON IR 作为统一的数据契约，连接人类编写的 DSL、LLM 生成结果与 SVG / Canvas renderer。

## 核心概念

这张图只做一件最小的事：放两个命名节点，再用一条带箭头的 `Draw` 把它们连起来。它说明 retikz 的基本顺序是先摆可引用的点，再用路径关系把图元串起来。

<ComponentPreview name="minimal-example" size="xs" />

`@retikz/core` 最重要的心智模型只有两层：先描述**图元是什么**，再描述**图元之间的连接与几何关系**。

| 核心能力     | 由谁承担                 | 解决什么问题                                                                     |
| ------------ | ------------------------ | -------------------------------------------------------------------------------- |
| **图元模型** | `Node`                   | 描述一个可见对象本身：形状、文本、填充、边框、尺寸、位置和可被引用的 anchor。    |
| **图元关系** | `Path` / `Step` / `Draw` | 描述对象之间的连接与几何关系：起点、终点、中间动作、箭头和边标注如何沿路径组织。 |

## AI 友好优先

**AI 友好不是 retikz 的功能之一，是 retikz 存在的理由。**

retikz 选择 IR JSON 而非 JSX 作为 AI 接入的主接口，借力 OpenAI Structured Outputs / Anthropic Tool Use 的 schema 约束输出能力，让 LLM 输出符合既定结构，并在 runtime 继续校验。

AI 友好会贯穿每一层设计：schema 的层级与判别字段保持清晰，字段值采用语义明确、边界可校验的类型，上层封装则稳定映射到同一份 core IR。目标是减少模型猜测，让生成结果更容易校验、修正和复用。

| 设计层面               | 落地                                      |
| ---------------------- | ----------------------------------------- |
| **schema 结构**        | 判别字段和嵌套关系明确，减少生成歧义      |
| **值类型**             | 优先采用有限、可序列化、可校验的数据结构  |
| **上层封装**           | 高层意图稳定映射到同一份 core IR          |
| **类型 / schema 同源** | zod 单源 → TS 类型 + JSON Schema          |
| **text DSL（远期）**   | 复用成熟绘图语法，让 LLM 更容易零样本生成 |

## IR 居中

<ComponentPreview name="ir-centric" hideCode />

所有输入方式（JSX / DSL / AI）都翻成同一份 IR；所有输出方式（renderer）都从 IR 出发。
**持久化、跨平台和 AI 接入并不是彼此独立的能力，而是 IR 居中带来的同一份红利。**
这样做的好处很直接：

- 你只需要围绕同一份 IR 维护保存、编辑和渲染逻辑。
- 不必为 JSX、AI 输出和不同 renderer 分别设计一套格式。
- 系统边界会更清楚，后续扩展也更省力。

## 分层抽象

retikz DSL 表面有三类构造。理解它们的边界，可以判断一个能力应进入 IR、只作为书写简化，还是由上层模块下沉：

| 层         | 例子                                  | 是否进 IR                   | 落在哪          |
| ---------- | ------------------------------------- | --------------------------- | --------------- |
| **Kernel** | `<Layout>` `<Node>` `<Path>` `<Step>` | ✅ 直接对应 IR 节点         | `@retikz/core`  |
| **Sugar**  | `<Draw way={[...]} />`                | ❌ 编译期展开为 Kernel      | `@retikz/react` |
| **Tier 2** | `<Plot>`                              | ✅ 高层节点 + lowering 下沉 | 独立 domain 包  |

以 `<Draw way={['a', 'b']} />` 为例，`Draw` 只提供更简洁的路径写法。构建 IR 时，`way` 会被解析为一组 `Step`，再组成一个 `Path`；最终 IR 里只有 `Path` 和 `Step`，不会保留 `Draw`。

关键约束：**Sugar 不引入新能力**——任何 Sugar 能表达的，Kernel 都能表达。这样 Sugar 可以放心地服务书写体验，而不把核心语义藏进 adapter 里。

## 通用图元，任意组合

retikz 用一组职责明确的组件描述图形。每个组件只负责一个层面的结构或几何语义，再通过嵌套与引用组合成完整图形。

| 分组         | 组件           | 职责                                               |
| ------------ | -------------- | -------------------------------------------------- |
| **布局**     | `<Layout>`     | 承载整张图，收集内部描述并配置尺寸与渲染方式       |
|              | `<Scope>`      | 对子图元分组，应用局部变换与继承样式               |
| **图元模型** | `<Node>`       | 描述可见对象的形状、文本、位置和 anchor            |
|              | `<Coordinate>` | 声明供定位和引用的不可见命名坐标                   |
| **图元关系** | `<Path>`       | 描述完整路径，承载描边、填充、marker 与内部 `Step` |
|              | `<Step>`       | 描述移动、直线、曲线或圆弧等单次路径动作           |

上层模块可以继续组合这三组职责，而不需要改变 core 的底层语义。

Sugar 只简化常见写法，不进入 IR，也不增加 Kernel 无法表达的新能力：

| Sugar                                   | 展开结果                 | 职责                         |
| --------------------------------------- | ------------------------ | ---------------------------- |
| `<Draw>`                                | `<Path>` + 一组 `<Step>` | 用 `way` 简写路径关系        |
| `<EdgeLabel>`                           | `Step.label`             | 用子组件写法声明路径段标注   |
| `<Arc>` / `<Circle>` / `<Rectangle>` 等 | `<Path>` + 几何 `<Step>` | 把高层几何参数换算成路径结构 |

## 包关系

Kernel 组目前包含六个同版本发布的包，从零依赖计算底座到渲染、框架入口与可选公式能力逐层协作：

<ComponentPreview name="package-viz" size="md" hideCode />

实线表示主要构建依赖，虚线表示次要直接依赖。`math` 提供纯计算几何，`core` 定义图形契约，`render` 提供渲染后端，`react` / `vanilla` 提供作者入口，`tex` 通过 core 的注入能力接入公式渲染。

| 包                | 职责                     | 主要依赖      |
| ----------------- | ------------------------ | ------------- |
| `@retikz/math`    | 纯计算几何               | 无            |
| `@retikz/core`    | IR、schema 与 Scene 编译 | math · zod    |
| `@retikz/render`  | SVG / Canvas runtime     | core · math   |
| `@retikz/react`   | React JSX adapter        | core · render |
| `@retikz/vanilla` | Plain spec 与 SSR        | core · render |
| `@retikz/tex`     | LaTeX 公式 lowering      | core          |

## 跨框架，共享 IR

React 组件与 Vanilla plain spec 最终都生成同一份 IR，SVG 与 Canvas renderer 也消费同一份 Scene。框架层只负责书写体验、生命周期和渲染后端选择，不引入新的底层几何语义。

因此，同一份图形数据可以在不同作者入口与 renderer 之间复用，不需要重新描述图元和关系。

<Comparison target="tikz" title="与 TikZ 的关系">

retikz 的命名 / 路径动作 / anchor 体系直接致敬 LaTeX 的 TikZ 包。

| 维度     | LaTeX TikZ      | retikz                            |
| -------- | --------------- | --------------------------------- |
| 运行环境 | LaTeX 编译器    | 浏览器 / Node                     |
| 语法     | `\node` `\draw` | `<Node>` `<Draw>`                 |
| 输出     | PDF / SVG       | SVG / Canvas；PDF / Native 计划中 |
| 交互     | 无              | React / runtime 事件              |
| 持久化   | `.tex` 源码     | JSON IR                           |

IR ↔ TikZ 源码转换属于后续 codec 方向：目标是在浏览器里编辑后能进入 LaTeX 工作流，或把已有 `.tex` 中的 TikZ 图迁移到 retikz 的 IR / React 表达里。

不需要先懂 TikZ 才能使用 retikz。retikz 借用的是命名词汇（node / path / anchor / step），可以使用 React 组件或 Vanilla plain spec 描述图形。
