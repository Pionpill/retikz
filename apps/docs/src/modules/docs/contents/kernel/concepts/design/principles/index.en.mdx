retikz separates describing a drawing, supplying capabilities, and executing output. Authors express intent as IR, Core compiles IR into a backend-neutral Scene, and renderers only execute that Scene. React, Vanilla, LLMs, and multiple rendering backends can therefore share one set of drawing semantics.

## Architecture at a glance

Start with two stable artifacts: **IR is the description boundary, and Scene is the execution boundary**. React JSX and Vanilla `InputScene` data converge through one normalization flow, while validated external IR enters compilation directly. Core outputs Scene rather than SVG strings, DOM objects, or Canvas pixels.

<ComponentPreview files="principles-packages" size="sm" hideCode />

Solid arrows show data flow: author input becomes IR, `compileToScene` creates Scene and typed artifacts together, and a renderer emits the Scene as SVG or Canvas. Dashed arrows show capability dependencies: `@retikz/math` supplies pure geometry, while `@retikz/tex` enters as an optional lowerer instead of creating a special IR or renderer branch.

| Package           | First responsibility                              | Explicitly does not own               |
| ----------------- | ------------------------------------------------- | ------------------------------------- |
| `@retikz/math`    | Dependency-free geometry, curves, matrices, maths | IR, schemas, drawing-domain semantics |
| `@retikz/core`    | IR / Scene, Definitions, registries, compilation  | React lifecycle, DOM, Canvas          |
| `@retikz/render`  | SVG, Canvas, hydration, animation runtime         | Author DSL, IR meaning, layout        |
| `@retikz/react`   | JSX adapter, `<Layout>` host, React wiring        | Parallel IR or renderer semantics     |
| `@retikz/vanilla` | InputScene, processing, mount, hydrate, SSR       | Geometry different from React         |
| `@retikz/tex`     | Lower LaTeX into renderer-neutral glyph paths     | General text model or backend hacks   |

## How Core source folders work together

The folders under `@retikz/core/src` are separated by contracts and execution stages rather than being arbitrary feature buckets. In the figure, the horizontal solid path shows convenient input becoming canonical IR and then Scene. The two vertical dashed paths show schema constraints and Definition / registry injection. The `shared/` band is the pure vocabulary and utility foundation reused by every layer, not part of the execution flow.

<ComponentPreview files="principles-folders" size="md" hideCode />

| Folder       | Owns                                                                   | Does not own                               |
| ------------ | ---------------------------------------------------------------------- | ------------------------------------------ |
| `shared/`    | Dependency-free vocabulary, types, pure utilities, cross-layer helpers | IR schemas, Definitions, orchestration     |
| `schemas/`   | Zod schemas and IR type source of truth; field `.describe()` text      | Provider functions or backend behavior     |
| `contract/`  | `XxxDefinition`, `defineXxx`, and Scene output contracts               | Built-in implementations or registry merge |
| `providers/` | Built-in Definitions, `BUILTIN_*`, registry resolvers, lookup errors   | Parallel IR or renderer semantics          |
| `parse/`     | Pure normalization from strings, DSL shorthand, and Sugar to IR pieces | Registries, layout, or runtime             |
| `compile/`   | Lowering, layout, namespaces, references, resources, IR → Scene        | DOM, SVG / Canvas backend execution        |

`schemas/` is the single data authority for IR. TypeScript types derive from schemas, and English `.describe()` text enters JSON Schema for LLM tool use, external tooling, and documentation. External JSON should be parsed explicitly with `SceneSchema` at the input boundary; `compileToScene` consumes canonical `IRScene` and does not replace that validation boundary.

## Built-ins and extensions share one path

Extensible capabilities do not use a built-in switch followed by an extension patch. Each capability begins with an `XxxDefinition` protocol. Built-in items and custom items created with `defineXxx(...)` enter one effective registry, after which compile looks up and consumes both through the same key path.

<ComponentPreview files="principles-registry" size="xs" hideCode />

“Built-ins and extensions are first-class” means three concrete things:

1. **One protocol**: both satisfy the same Definition, with no hidden fields reserved for built-ins.
2. **One registry**: `BUILTIN_*` and `options.xxx` become one `ReadonlyMap` at the start of each compile call.
3. **One consumer path**: resolvers, diagnostics, and compile consumers do not branch on where a key came from.

Built-ins register first and custom items follow. Registry construction rejects empty and duplicate keys. When a consumer later encounters an unknown key, that capability's contract determines whether to throw or warn and skip. First-class therefore means the same protocol and execution path, not that a custom item can silently override a built-in. See [Extension Mechanisms](/kernel/reference/runtime/extensions) for extension families, injection points, and failure semantics.

## End-to-end execution

`compileToScene` does not walk IR and immediately emit SVG. Authoring helpers and parsers first normalize convenience syntax into IR. Compile then builds a call-local capability context, resolves lowering, layout, and references in dependency order, and only then assembles Scene.

<ComponentPreview files="principles-compile" size="xs" hideCode />

1. **Authoring converges on IR**: React JSX and Vanilla InputScene data normalize to one JSON IR; parser sugar expands in its owning input layer, and external JSON is validated before entering.
2. **Create compile context**: combine call-local measurement, warnings, lowerers, and built-in plus custom provider Definitions without global state.
3. **Composite lowering**: validate Tier 2 nodes against registered Definitions and expand them into Tier 1 Kernel IR.
4. **Layout and namespaces**: resolve Node, Coordinate, and Scope positions, shapes, boundaries, and styles, then register layouts.
5. **Deferred Path resolution**: after nodes exist, resolve anchors, generators, arrows, ribbons, and path kinds while preserving order.
6. **Scene and runtime**: combine primitives, resources, animations, and bounds; SVG / Canvas, hydration, and animation execute after Scene.

This order defines the boundaries: parsers do not read provider registries, renderers do not reinterpret IR, and adapters do not repeat layout. If a capability only works by crossing these boundaries, fix the contract before adding a special case.

## Capability ownership

Once the overall framework is clear, decide whether a request changes authoring ergonomics, shared drawing semantics, a high-level domain model, a replaceable compile strategy, or backend runtime behavior. Design from that first owner.

<ComponentPreview files="principles-placement" size="md" hideCode />

Each arrow points to the first owner, while the second line in the node shows common implementation anchors; this does not mean only one package can change. One capability may need authoring, contract, compile, and runtime wiring, but each semantic layer has one source of truth.

| Request signal                 | First owner             | Boundary failure                       |
| ------------------------------ | ----------------------- | -------------------------------------- |
| Friendlier JSX / InputScene    | React / Vanilla adapter | Adapters produce different geometry    |
| Shared drawing semantics       | `@retikz/core`          | Adapter / renderer repeats layout      |
| High-level domain model        | Domain composite        | Chart / domain fields enter core IR    |
| Pure geometry and numeric work | `@retikz/math`          | Math depends on schema or runtime      |
| SVG / Canvas execution         | `@retikz/render`        | DOM / Canvas objects enter Scene       |
| Optional lowering such as TeX  | Dedicated lowerer       | Heavy dependency becomes core-required |

The central constraint is that upper packages obtain foundations from `@retikz/core` or `@retikz/math`. Adapters may change authoring and domain packages may preserve high-level IR, but neither may create parallel IR, rendering semantics, or geometry foundations.

## Completeness gate

Rendering one built-in example does not make a capability complete. Every long-lived capability must answer four groups of questions:

| Axis            | Required answer                                                                 | Action when missing                 |
| --------------- | ------------------------------------------------------------------------------- | ----------------------------------- |
| Problem / owner | What root problem is solved, who owns it, and what remains outside the scope?   | Reassign ownership or narrow scope  |
| Internal model  | Can IR, pure computation, and compile express it without host special cases?    | Move down a shared contract         |
| Extension       | Do built-ins and custom items share Definition, registry, resolver, and errors? | Complete one extension path         |
| End-to-end loop | Are input, compile, Scene, renderer, adapters, tests, and docs connected?       | Record the missing links explicitly |

When a subpackage lacks a capability, first decide whether the need is composition, an extension gap in the current domain, or a missing shared foundation. Keep only composition in the caller; add a domain contract for the second case or move the foundation to its true owner for the third.
