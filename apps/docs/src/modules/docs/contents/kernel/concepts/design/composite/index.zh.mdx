retikz 的 IR 子节点分两层：**Tier 1** 是 core 内置的 `node` / `path` / `coordinate` / `scope`；**Tier 2 composite** 是 domain 包提供的高层节点，例如 `@retikz/plot` 的整张统计图 spec。

Tier 2 节点用 `namespace + type` 判别，拥有完整 schema，并由同一套 composite registry 在 compile 中处理。只需结构变换时使用 `expand`；需要真实子内容反馈布局时使用布局感知的 `compile`。两条路径最终都产出 Tier 1，布局、anchor、zIndex 与 renderer 继续复用 core 能力；core 不需要认识 table、chart、tree 等领域语义。

## 为什么需要 composite

直接保存几十个矩形和连线，会丢失“这是一张图表 / 一棵树”的高层意图。composite 把领域字段保留在可序列化 IR 中，再把具体几何延迟到 compile 期生成：

<ComponentPreview files="composite-pipeline" size="xs" hideCode />

图中的 `lower` 是关键边界：上游仍能存储、传输、diff 或由 AI 生成高层节点；下游只接收统一的 Tier 1，因此所有 renderer 共享同一次 Core compile 的结果。

适合 composite 的能力通常同时满足三点：

- 一个高层节点会按数据或算法生成数量不固定的 Tier 1 图元；
- 领域 schema 比展开后的几何更能表达用户意图；
- 展开结果应被 React、Vanilla、SVG、Canvas 等入口共同复用。

## 两种互斥分支

`defineComposite` 把 schema 与一个处理分支注册为同一项。definition 必须且只能提供 `expand` 或 `compile`；`schema` 可以是单个 object，也可以是共享同一 `namespace` / `type` literal 的直接 object union。每个 schema 分支的 literal 都必须与 definition key 一致，union 中出现非 object 分支、空 literal 或混合 key 时会立即报错。

Core 只按顶层 `namespace + type` 路由 composite，不读取领域 schema 内部的判别字段。例如 Table 可以在同一个 `table.table` composite 下定义多种 spec 分支，但 `structure.kind` 的解释与缩窄仍由 Table 包负责。

<ComponentPreview files="composite-basic" size="sm" />

| 字段             | 职责                                   | 约束                                  |
| ---------------- | -------------------------------------- | ------------------------------------- |
| `namespace`      | 划分 domain                            | 与 schema literal 一致                |
| `type`           | 标识 domain 内的节点类型               | 与 schema literal 一致                |
| `schema`         | 校验完整高层节点并填充默认值           | object 或共享 key 的直接 object union |
| `expand`         | 读取有效 Theme 后生成 Tier 1 / Tier 2  | 与 `compile` 互斥，最终收敛到 Tier 1  |
| `compile`        | 在完整编译环境中测量、约束并放置子内容 | 与 `expand` 互斥                      |
| `artifactSchema` | 校验 `compile` 同次返回的领域 artifact | 有 artifact 类型时必填                |

编译器按 `${namespace}.${type}` 查注册表，校验节点后调用对应分支。嵌套 composite 会继续处理，直到最终输出只含 Tier 1 与已提交 replay。未注册节点产生 warning 并跳过，循环或超过深度限制则报错。完整字段、诊断与独立 lowering 入口见[编译](/kernel/reference/runtime/compile)。

## Theme 上下文

`expand(node, context)` 与布局感知 `compile(node, context)` 都能读取冻结的 `context.theme`。它始终是完整的 `{ style?, mode, colors }`：Core 从默认 light 基线开始，按 Scene → 外层 Scope → 内层 Scope 逐字段继承 selector，再由默认 palette 或当前 style resolver 生成 `colors`。`colors` 是 detached/frozen 的 Core shared view，固定提供 `semantic.error/success/warning` 与非空 `categorical` palette，不是 Core 图元的隐式样式。

Composite 负责把 shared `colors` 与自己 style resolver 生成的领域 token、palette 或其它默认映射为已经物化的正式 IR。Core 不解释 Tier 2 token，也不拥有 Plot、Chart、Table 的具体 token；Core primitive 与 renderer 也不解释 Theme。普通输出 Scope 与 `context.scope({ theme }, children)` 可以建立更内层环境；replay child 则保留 probe 时已经解析的 Theme，不会在提交位置被重新解释。自定义 style 必须同时注入 Core 与实际消费它的 Tier 2 resolver；任一 registry 缺失该名称都会 fail-loud。

## 空间透明与 qualified handle

有些 composite 不只生成可见图元，还要让外层工具在嵌套 Scope、布局 replay 与变换之后找到一个有领域含义的区域。`expand` 因而统一返回结构化结果；布局感知 `compile` 也可在同一结果中声明局部矩形：

```ts
return {
  children: [{ type: 'node', position: [0, 0], text: 'Card' }],
  spatialHandles: [
    {
      key: 'body',
      role: 'card',
      bounds: { x: -40, y: -20, width: 80, height: 40 },
      tags: ['content'],
      payload: { itemId: 'card-a' },
    },
  ],
};
```

声明中的 `bounds` 位于当前 composite allocation coordinate。Core 在最终 traversal、Scope transform 与 replay settle 后，把它投影成 world-space 矩形 AABB，并在 `CompileResult.spatialHandles` 发布；`ownerPath` 按外到内保留每层 composite 的 `namespace`、`type`、显式 `id` 与 occurrence。

| 层次                    | 保存什么                                   | 不进入什么                       |
| ----------------------- | ------------------------------------------ | -------------------------------- |
| callback declaration    | owner-local `key` / `role` / 局部矩形      | IR schema、Scene                 |
| qualified compile index | `ownerPath` / world AABB / origin 与 final | SVG 属性、Canvas draw state      |
| query                   | 精确 owner、祖先路径、key、role、全部 tags | renderer DOM 查询、几何 contains |

`selectSpatialHandles()` 返回零到多项，`resolveSpatialHandle()` 要求恰好一项；跨 owner 查询不充分时会明确报告 miss 或 ambiguity，不猜“最近”的节点。没有声明时 index 仍存在且为空。

`lowerIRToKernel()` 无法结算 world geometry：无声明或空声明仍可下沉，遇到非空 `spatialHandles` 会同步失败并要求改用 `compileToScene()`。这避免把局部矩形静默丢弃，或冒充已经结算的空间结果。

## 布局感知编译

`CompositeDefinition.expand()` 拿不到文字测量、provider、引用环境或父级可用空间，因此不能表达“查询子贡献 → 求解父布局 → 再分配 child slot”的反馈过程。`compile(node, context)` 把这条闭环放在同一次 Core compile 中；根 composite 收到冻结的 `NaturalLayoutProposal`，nested composite 收到父级为该 occurrence 发出的完整双轴 `context.proposal`。

Proposal 是父级提供的**可用空间条件**，不是 child 的真实尺寸，也不是 slot 本身。`LayoutProposal` 必须同时给出 `x` 与 `y`：

| 单轴 proposal         | 含义                                                     |
| --------------------- | -------------------------------------------------------- |
| `intrinsic.minimum`   | 在另一轴 proposal 仍生效时查询最小 contribution          |
| `intrinsic.natural`   | 在另一轴 proposal 仍生效时查询自然 contribution          |
| `range { min, max? }` | 在区间内解析 slot；省略 `max` 表示无上限                 |
| `exact { value }`     | 父 solver 要求固定 slot；不强迫 child 缩放或改变真实几何 |

<ComponentPreview files="layout-aware-compile" size="xl" hideCode />

图中的每次 probe 都先得到 `resolved` 或 `failed` outcome。Resolved result 再分开保存下面五项；它们不能互相反推或替代：

| 字段               | 含义                                                    |
| ------------------ | ------------------------------------------------------- |
| `slotSize`         | proposal 求值后的无原点 allocation slot                 |
| `allocationBounds` | child 在自身局部坐标中的真实布局占用，可大于或小于 slot |
| `visualBounds`     | 最终静态墨迹包络，只描述视觉贡献，不参与 slot 求值      |
| `alignmentGuides?` | child-local 一维 guide；Core 内置 first / last baseline |
| `replay`           | 对应本次隔离 transaction 的 opaque、one-use token       |

`exact` 轴的 slot 严格等于 `value`；`range` 轴落在 `[min, max]`，无上限时不小于 `min`；intrinsic 的 slot 是该次 contribution probe 解析出的尺寸。`slotSize` 只有 width / height，没有 origin。父 solver 在自己的坐标系里据此建立 slot rect，再用真实 bounds 与 guides 决定 alignment、overflow 和 clip。

Plain text 的 x minimum 取最宽不可断单元，natural 取自然行宽，有限 range / exact 可以触发换行；y contribution 是应用完整 x proposal 后的真实排版高度。Mixed runs、TeX、Path、Coordinate 与普通 Scope 没有通用重排合同，因此可以保留自然 allocation，只让 slot 响应 range / exact。Core 不从 DOM、SVG / Canvas 或 renderer 回读尺寸，也不拥有 Box / Flex / Grid / Overlay 的 line、track 或 slot policy。

### 选择、失败与提交

每次 `layoutChild()` 都在隔离 transaction 中执行。父 solver 可以比较多组 minimum / natural / range / exact 结果；未选中的 resolved result 与 failed outcome 都不会泄漏 primitive、resource、warning、artifact、namespace、identity 或 observation。选中成功结果时调用 `context.replay(result)`；选中失败时调用 `context.raise(failure)`，Core 会保留原始 provider、source path、cause 与完整 nested probe occurrence。

Failure、result、replay 与 output child 都由 callback-local、compile-local identity 管理，不能伪造、复制后重用、跨 callback / compile 传递或重复提交。Occurrence 中的 `probe[index]` 表示候选 child dispatch，成功提交后的 `replay[index]` 表示最终 output；两者不是同一个阶段。

下面是一个完整的第三方 layout-aware Composite。第一次 probe 查询 contribution，第二次发出 allocation proposal；示例用真实 allocation 对齐 slot、把 guide 投影到 composite 坐标，再只提交最终结果：

```ts
import { ChildSchema, CompositeBaseSchema, defineComposite } from '@retikz/core';
import { z } from 'zod';

export const cardComposite = defineComposite({
  namespace: 'demo',
  type: 'card',
  schema: CompositeBaseSchema.extend({
    namespace: z.literal('demo'),
    type: z.literal('card'),
    child: ChildSchema,
    width: z.number().nonnegative(),
    height: z.number().nonnegative(),
  }),
  compile: (node, context) => {
    const contribution = context.layoutChild(node.child, {
      x: { kind: 'intrinsic', mode: 'minimum' },
      y: { kind: 'intrinsic', mode: 'natural' },
    });
    if (contribution.kind === 'failed') return context.raise(contribution.failure);

    const final = context.layoutChild(node.child, {
      x: { kind: 'exact', value: Math.max(node.width, contribution.result.slotSize.width) },
      y: { kind: 'range', min: 0, max: node.height },
    });
    if (final.kind === 'failed') return context.raise(final.failure);

    const { slotSize, allocationBounds } = final.result;
    const x = 8 + (slotSize.width - allocationBounds.width) / 2 - allocationBounds.x;
    const y = 8 + (slotSize.height - allocationBounds.height) / 2 - allocationBounds.y;

    return {
      allocationBounds: { x: 0, y: 0, width: slotSize.width + 16, height: slotSize.height + 16 },
      alignmentGuides: final.result.alignmentGuides?.map(guide => ({
        ...guide,
        position: guide.position + (guide.dimension === 'x' ? x : y),
      })),
      children: [
        context.replay(final.result, {
          transforms: [{ kind: 'translate', x, y }],
          clip: { kind: 'rect', x: 8, y: 8, width: slotSize.width, height: slotSize.height },
        }),
      ],
    };
  },
});
```

Replay wrapper 先用 `transforms` 把 child 放进 parent allocation coordinate，再在该父坐标系应用 `clip`。Wrapper 不回写原始 `LayoutChildResult`；clip 只收紧最终提交后的 Scene visual contribution。需要 identity、local namespace、metadata、zIndex 或递归结构时，再用 `context.scope()` 组合普通 `IRChild`、replay child 与 nested scope child。它们都不引入新的 IR / Scene primitive kind、renderer contract 或第二条 compile pipeline。

### 同次类型化产物

布局感知定义可以声明 `artifactSchema` 并从 `compile` 返回 JSON-safe `artifact`。Core 在 `CompileResult.artifacts` 中用 `namespace`、`type` 和 occurrence locator 封装它；locator 由原始 `sourcePath` 与结构化 expansion / output / replay 路径组成，不依赖全局 Map、回调捕获或第二次遍历。宿主因而能从同一次 compile 同时得到 Scene 与领域产物。

同一个 artifact 也可以成为外部观察者的稳定 owner output。下面在 `@retikz/inspect` 中独立定义 Card Inspector；`compileCard` 仍只负责返回符合 `CardArtifactSchema` 的 artifact。

```ts
const CardArtifactSchema = z.strictObject({
  bounds: z.strictObject({
    x: z.number(),
    y: z.number(),
    width: z.number().nonnegative(),
    height: z.number().nonnegative(),
  }),
});

type CardArtifact = z.infer<typeof CardArtifactSchema>;

const CardInspector = defineInspector({
  namespace: 'demo',
  name: 'card-bounds',
  owner: { kind: 'composite', namespace: 'demo', type: 'card' },
  subjectSchema: CardArtifactSchema,
  optionsInputSchema: z.strictObject({}),
  optionsSchema: z.strictObject({}),
  inspect: (artifact: CardArtifact, context) => ({
    type: 'path',
    stroke: context.appearance.scopeColor,
    children: [
      { type: 'step', kind: 'move', to: [artifact.bounds.x, artifact.bounds.y] },
      {
        type: 'step',
        kind: 'rectangle',
        to: [artifact.bounds.x + artifact.bounds.width, artifact.bounds.y + artifact.bounds.height],
      },
    ],
  }),
});

export const CardDefinition = defineComposite({
  namespace: 'demo',
  type: 'card',
  schema: CardSchema,
  compile: compileCard,
  artifactSchema: CardArtifactSchema,
});

const inspectorRegistry = createInspectorRegistry([CardInspector]);
```

`inspect()` 返回普通 `IRChild` 或稠密只读数组，不声明 `outputSchema`。Core 只发布最终 occurrence 的已校验 artifact；`@retikz/inspect` 再校验 `subjectSchema`，并在独立环境中编译辅助输出，默认不递归触发观察者。选择与注册不进入 Composite Definition，详见 [`@retikz/inspect`](/kernel/packages/inspect)。

`lowerIRToKernel()` 只支持可独立执行的 `expand` 分支。它遇到布局感知 composite 会明确报错，因为正确结果依赖完整 compile 环境。

## 在 React `<Layout>` 中使用

普通用户只需要把支持嵌入的 domain 组件放进 `<Layout>`。组件所属包负责贡献高层节点与 composite definition，`<Layout>` 再把它们交给同一条 core lowering 管线；core 仍不依赖具体 domain。

如果你在实现 domain adapter、注入 `composites` / `embeddables`，或排查 datasets 汇总与宿主行为，请直接查 [Layout 高级能力与宿主接入](/kernel/components/layout/overview#高级能力与宿主接入)和[扩展运行时](/kernel/reference/runtime/extensions)，概念页不展开 React 静态遍历与聚合细节。

## Provider roots 与传递依赖

嵌入式 adapter 不直接拼 Definition 数组。它返回高层 `node`，并用 `CoreProviderContribution` 声明当前节点实际需要的 `roots` 与本次程序已经导入的 `providers`。普通 provider key 使用 `capability + name`；composite key 使用 `capability: 'composite' + namespace + type`。每个 provider 还声明直接依赖、runtime-only datasets 和稳定的 `makeDefinition` 函数。

<ComponentPreview files="embeddable-flow" size="xl" hideCode />

Core 从 roots 计算可达闭包，按依赖优先、首次可达顺序物化每个 Definition 一次。下面的第三方 `third.card` 依赖 Standard Frame；两者进入同一张图，没有内置白名单：

```ts
import type { CoreDependencyProvider } from '@retikz/core';

import { resolveCoreProviderDependencies } from '@retikz/core';
import { FrameProvider } from '@retikz/standard';

const CardProvider = {
  key: { capability: 'composite', namespace: 'third', type: 'card' },
  dependencies: [FrameProvider.key],
  datasets: {},
  makeDefinition: () => CardDefinition,
} satisfies CoreDependencyProvider;

const definitions = resolveCoreProviderDependencies({
  contributions: [
    {
      roots: [CardProvider.key],
      providers: [CardProvider, FrameProvider],
    },
  ],
});
```

`datasets` 只在 maker 调用前按 provider key 与 reference 合并，不进入 IR、Scene 或 manifest。同 reference 只有 `Object.is` 同源才能去重；provider maker、依赖顺序或 dataset identity 冲突都会在任何 maker 执行前失败。缺失依赖与环也在预检阶段报出完整 key 链。

Provider graph 负责从可复用模块装配“需要哪些 Definition”。`resolveCoreProviderDependencies()` 产出按 Core capability 分组的 options；直接 IR 作者可以显式传完整 Definition 集合，React、Vanilla 或其它工具链则先解析 contribution。Provider 结果先写入，显式 Definitions 后追加；同 key 只允许同一个 Definition 对象去重，不同对象 fail-loud。
