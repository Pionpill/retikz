A primitive is the smallest drawable, referenceable unit in retikz. The **primitive model** describes how a primitive is built up geometrically — from content, inner frame, and shape, out to the bounding box, boundary, and anchors — so it can be measured, laid out, connected, and referenced. It is an abstraction, not tied to one specific component.

Node is the most common concrete implementation of this model. Think of it as a box model that paths can recognize: `position` gives the semantic reference point; text measurement and `padding` form the inner frame; shape derives a visual bounding box; `minimumSize` then sets a lower bound on that box; and boundary plus anchors decide where paths connect.

From the inside out, the layers are: the content box innermost, then the inner frame, the shape outline, the bounding box, boundary, and finally the anchors. In real output you usually only see the orange shape; the other layers are geometry used by compile-time layout and connection logic.

| Layer        | Defined by                                                     | Affects                                                                              |
| ------------ | -------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| Content box  | `text` / children / font                                       | Base text measurement                                                                |
| Inner frame  | Text measurement + `padding`                                   | Base half-axes passed to the shape                                                   |
| Shape        | `shape.circumscribe` and `shape.emit`                          | The visible outline                                                                  |
| Bounding box | Shape enclosing the inner frame, then clamped by `minimumSize` | Base for rendering/clipping; plus `margin` it becomes the layout footprint / viewBox |
| Boundary     | `boundary`, following shape by default                         | The surface border anchors attach to (automatic / named direction / angle)           |
| Anchor       | Web direction / angle / shape-specific / edge point            | Precise points other primitives can reference                                        |

The bounding box excludes `margin`. The compiler always expands the layout / viewBox footprint by `margin`, but whether a connection point moves depends on how the selected boundary resolves geometry: rect-driven boundaries consume the expanded box, while the default boundary of param-driven shapes such as star / sector rebuilds its real contour from params.

## Box Model

Like the CSS box model, a Node is three nested frames from the inside out.

- **Content box**: determined by `text` / children and `font` — the base size from text measurement.
- **Inner frame**: the content box plus `padding`, producing the base half-axes passed to the shape — for a rectangular node, this is the starting size of the drawn shape.
- **Bounding-box floor**: the shape first circumscribes the inner frame, then `minimumSize` takes the larger value. It constrains the bounding box; it is not fed back into `circumscribe`.
- **Outer frame**: the bounding box plus `margin`. It leaves the visible shape unchanged and always contributes to layout / viewBox; whether connection points land on this frame depends on boundary / anchor resolution.

<ComponentPreview files="node-frames" size="md" hideCode />

The innermost gray block is the content box, the middle dashed ring is the inner frame (the rectangular shape's starting size), and the outermost dashed ring is the outer frame. This figure uses a rect-driven rectangular boundary, so `margin` expands both its connection surface and layout footprint; see the param-driven exception below.

The inner frame is the starting point for later geometry: the shape circumscribes it first, then `minimumSize` sets a lower bound on the result. Padding can give an empty-text node an inner frame; use `minimumSize` when the final footprint itself needs a guaranteed size.

| Prop      | Changes                          | Result                                                                                           |
| --------- | -------------------------------- | ------------------------------------------------------------------------------------------------ |
| `padding` | Distance from content to shape   | Shape grows, bounding box grows                                                                  |
| `margin`  | Layout clearance outside the box | Shape stays; layout always expands, while connection points depend on the boundary / anchor path |

Padding enlarges the inner frame before `circumscribe`; `minimumSize` constrains the bounding box afterward; margin leaves the shape unchanged, expands the layout frame, and moves connection points that consume rect geometry. All default to no additional geometric effect.

## Shape

Shape is not just a CSS-like border radius. It is a geometry definition: given inner half-axes and params, it answers "how large must my enclosing box be?" and draws the final visual outline.

| Shape family          | Size source                               | Examples                                     |
| --------------------- | ----------------------------------------- | -------------------------------------------- |
| Text-container shapes | Text + padding, then a bounding-box floor | rectangle, circle, ellipse, polygon, diamond |
| Param-driven shapes   | Shape params define the geometry          | sector, arc, star                            |

<ComponentPreview files="shapes" size="md" hideCode />

The gray block is the content box and the dashed rectangle is the inner frame; these five text-container shapes share one inner frame, and each circumscribes it: rectangle is the inner frame, the rest wrap it more loosely (circle / diamond are presets of ellipse / polygon). Param-driven shapes (sector / arc / star) take their geometry from params and don't follow this inner-frame logic.

Text-container shapes behave like buttons or DOM boxes: longer text makes the node grow. Param-driven shapes behave more like geometric glyphs: radius, angle, and point count already define the size, and text is attached to that geometry.

To extend shapes yourself, `defineShape` must supply the same geometry answers — how the shape is enclosed, where a ray hits it, where named anchors live, and how it emits primitives — so the Node stays measurable, connectable, referenceable, and renderable like any built-in. Read [Custom Shapes](/kernel/components/shapes/custom-shape) for the implementation contract.

## Outer Boundaries

The bounding box and the boundary are both enclosing surfaces outside the shape, but they play different roles: the bounding box drives layout and rendering footprint, while the boundary decides where automatic connections attach. By default both follow the shape; they diverge only when you set `boundary` explicitly.

<ComponentPreview files="bbox-boundary" size="sm" hideCode />

Both nodes are the same polygon shape (a hexagon) with the same inner frame (the innermost dashed rectangle) and bounding box (the gray dashed rectangle) — identical on both sides. On the left, `boundary="shape"` (the default), so automatic connections attach to the polygon edge; on the right, `boundary="circle"`, so they attach to the blue dashed circle instead — note it can extend past the bounding box. Changing boundary only moves the surface border anchors attach to — it leaves the shape, inner frame, bounding box, and layout footprint untouched.

The **bounding box** is not the visual outline itself. It is the rectangle that encloses the outline, so complex shapes can still participate in viewBox calculation, layout, and rendering with one shared model. A few shapes also provide `circumscribeOffset`, allowing the semantic `position` to differ from the bounding-box center. For example, a sector is positioned by its circle center, while its bounding box is offset toward the sector.

The **boundary** answers one question: when a path connects to this Node automatically, which surface should the endpoint attach to? By default, `boundary="shape"`, so automatic path endpoints attach to the visible shape edge. You can also give a star a circular or elliptical connection surface to make lines look more regular; the star itself and its bounding box do not change.

The built-in circle and ellipse boundaries support two fitting strategies. The default `fit: 'tight'` reads a safe connection envelope supplied by the visual shape and stays close to its real outline. `fit: 'bounds'` instead constructs a regular surface that encloses all four corners of the visual bounding box. Both apply `gap` after fitting and remain outside layout sizing.

Here, `tight` is not merely the longer half-axis of the bounding box: shapes such as star and polygon derive a safe envelope from their real vertices. Only a plain shape name that is not registered as a boundary provider is laid directly over the visual bounding box without rerunning its `circumscribe` step.

| Setting                    | Changes                                                                    | Does not change                             |
| -------------------------- | -------------------------------------------------------------------------- | ------------------------------------------- |
| `shape`                    | Visible outline, bounding box, shape anchors                               | Center semantics                            |
| `boundary`                 | The surface border anchors (automatic / named direction / angle) attach to | Visual node, bounding box, layout footprint |
| Per-edge boundary override | Current path endpoint                                                      | Node defaults                               |

So the bounding box is the visual envelope used for rendering (plus `margin` it becomes the layout footprint), while the boundary is closer to a connection hit surface — neither is the drawn shell.

The boundary sets the shape of the connection surface; `margin` always expands the rectangle supplied to connection resolution. Rect-driven boundaries such as circle / rectangle expand with it, while the default boundary of param-driven shapes such as star / sector still computes from params. `margin` is therefore stable layout clearance, and becomes connection clearance only when the boundary consumes rect dimensions.

## Anchors

Anchors are the stable points that a Node exposes to other primitives. Paths, positioning, and labels can all use anchors to find a point on a node.

| Anchor family   | Examples                             | Best for                              |
| --------------- | ------------------------------------ | ------------------------------------- |
| Center          | `center`                             | Alignment, rotation, radial relations |
| Direction       | `top`, `right`, `bottom-left`        | Common connections and layout         |
| Angle           | `'A.35'` / `{ id: 'A', anchor: 35 }` | Intersecting a ray with the boundary  |
| Shape-specific  | star tips, sector arc endpoints      | Semantic points on complex shapes     |
| Edge proportion | `{ side: 'top', fraction: 0.25 }`    | Tables, lanes, frame edges            |

<ComponentPreview files="anchors" size="lg" hideCode />

The top row uses a rectangle to explain standard directional, angle, and edge-proportional anchors. The bottom row shows that complex shapes may add semantic points. The concept page distinguishes geometry owners instead of cataloging every shape-specific name:

| Anchor family        | Geometry owner                | Authority                                           |
| -------------------- | ----------------------------- | --------------------------------------------------- |
| `center` / direction | Node shape / boundary         | [Node Geometry](/kernel/components/node/overview)   |
| Numeric angle        | Selected connection boundary  | [Path target](/kernel/reference/schema/path#target) |
| Shape-specific name  | The corresponding shape       | [Shapes](/kernel/components/shapes)                 |
| `{ side, fraction }` | Real edge of the visual shape | [Node Geometry](/kernel/components/node/overview)   |

IR / schema keeps `top` / `right` / `bottom` / `left` plus four corners as its standard directional vocabulary, with `center` separate. A named direction asks the shape / boundary first and falls back to its AABB when absent; a numeric angle casts a ray onto the selected boundary; shape-specific names and edge proportions remain owned by the visual shape.

<Comparison target="tikz" title="Anchor Names">

TikZ uses compass names such as `north` / `south` / `east` / `west`. retikz IR / schema only store canonical names such as `top` / `right` / `bottom` / `left`; when a sugar layer supports TikZ-style input, it normalizes before producing IR.

</Comparison>

Complete names, per-shape semantic points, and boundary exceptions live on the Node and Shapes pages; see [Custom Shapes](/kernel/components/shapes/custom-shape) for custom geometry. Continue with [Primitive Relations](/kernel/concepts/core/primitive-relations) for how another primitive references these points and how endpoints choose between auto and locked modes.

## Try it yourself

First edit the content and add a line break, then switch among rectangle, circle, ellipse, diamond, polygon, star, sector, and arc to see one Node adopt different visual shapes. The first five derive their outer size from the content and inner frame; star, sector, and arc instead use representative geometry parameters supplied by the demo and place the text over that fixed geometry.

Next switch among the four boundary modes: `shape`, `circle`, `rectangle`, and `ellipse`. Circle and ellipse also let you compare `fit: 'tight'` with `fit: 'bounds'`, while all three regular connection surfaces accept `gap`. Then adjust the source angle and observe the real connector endpoint. The final `fill`, `stroke`, and `strokeWidth` fields provide only minimal appearance feedback; use the [Text](/kernel/components/node/text), [Node](/kernel/components/node/overview), and [Shapes](/kernel/components/shapes) pages for the complete APIs.
