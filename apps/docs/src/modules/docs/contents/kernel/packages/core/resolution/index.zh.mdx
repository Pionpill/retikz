[Core 总览](/kernel/packages/core)区分了图形声明、原子编译阶段和 Reconciler 的调度职责。本页从一个节点的 `shadow: 'md'` 出发，追踪声明如何经过 Schema 约束、字段语义描述与 resolve，成为下游可以直接消费的阴影配置。

这里的终点是“语义已经确定、可以继续编译”的结构。文字有多大、节点最终放在哪里、连线如何与边界相交，需要后续布局与几何求值才能回答。

## 整体流程

IR 是作者保存或传入的图形声明。Schema 定义它允许的结构；resolve 在当前默认配置和能力上下文就绪时，展开声明中的不同写法，产出 Canonical 或带有额外绑定信息的 Resolution。

下图区分两种输入来源：JSON 等外部数据先由 Schema 校验；已经类型明确的 TypeScript 声明可以直接进入解析。图中箭头表示数据交接，不代表每次编译都先执行一个全局 Schema pass。

Reconciler 负责准备上下文和安排调用，Core 提供对应领域的 resolver。本文用 Node 展开一条具体主线；Path、Scope 与 Composite 按各自需要的上下文执行，不要求所有元素同时完成 resolve。

## IR 与 Schema

下面是一份节点声明。它只保存绘图意图：节点 A 使用中等阴影预设，文字是 A。

```json
{
  "type": "node",
  "id": "A",
  "text": "A",
  "style": { "shadow": "md" }
}
```

IR 是所有 DSL 最终遵循的统一规范，100% 可用 JSON 表达，由 Zod Schema 定义和管理。

Schema 允许省略部分字段，并定义输入的校验规则。外部数据在 Schema 入口完成结构校验；进入 resolve 后，再结合上下文补全默认值并检查语义约束。

为简化声明，Schema 保留了一部分语法糖，例如 `shadow: 'md'`。resolve 会将它展开为包含偏移、模糊和颜色的内部数据结构，供后续编译使用。

## 用描述表达语义

类型能说明 `offsetY` 是数字，但读者还需要知道它使用什么单位、正值朝哪个方向，以及与预设同时出现时采用哪个值。这些信息通过 Schema 字段的 `.describe()` 写入契约。

例如，`DropShadowSchema` 对 `offsetY` 的实际描述是：

```ts
offsetY: number()
  .optional()
  .describe('Vertical shadow offset in user units (overrides preset); positive = downward under screen y-down.'),
```

这段描述同时给出单位、覆盖规则和坐标方向。与 `preset` 字段的说明结合，调用者或 LLM 就能理解：要保留 `md` 的其余设置、只让阴影向下偏移 8，可以声明 `{ preset: 'md', offsetY: 8 }`。

描述应回答字段使用时的具体问题：

| 问题           | 阴影中的说明                                     |
| -------------- | ------------------------------------------------ |
| 值表达什么     | `preset` 提供偏移、模糊和颜色的预设              |
| 单位与参考系   | 偏移使用 user units；屏幕坐标中 y 正向向下       |
| 字段如何组合   | 显式字段覆盖预设中的对应值                       |
| 省略意味着什么 | 阴影整体省略时不投影；对象没有预设时需要显式偏移 |

`.describe()` 是可供人和工具读取的语义元数据，不执行上述行为。允许的结构由 Schema 约束，预设展开和覆盖由 resolver 实现，最终效果还需要编译与渲染支持。三者一致，描述才足以指导生成与调用。

## 从简写到确定值

对作者而言，`'md'` 是有意义的表达：它选择一组协调的阴影参数。下游绘制阶段需要的是偏移、模糊和颜色，而不需要反复判断预设字符串与对象分支。

节点解析中的内部 helper `resolveDropShadow` 负责完成这次转换。以下只展示同一个节点的阴影字段：

<DocTab value="source" label="Source IR">

```json
{ "shadow": "md" }
```

</DocTab>
<DocTab value="canonical" label="Canonical">

```json
{
  "shadow": {
    "offsetX": 0,
    "offsetY": 3,
    "blur": 6,
    "color": "rgba(0,0,0,0.12)"
  }
}
```

</DocTab>
<DocTab value="override" label="显式覆盖">

```json
{ "shadow": { "preset": "md", "blur": 10 } }
```

解析后仍使用相同偏移和颜色，只有 `blur` 变为 10，结果不再保留 `preset`。

</DocTab>
</DocTabs>

这些数值来自当前 Core 的阴影预设表。换成显式偏移对象时，resolver 不查预设；未提供颜色则补默认颜色。省略阴影或使用 `'none'` 时，结果没有阴影配置。

“作者侧语义表达”和“编译消费形态”各自是所在阶段的一等内容：IR 用适合描述意图的形式，Canonical 用适合计算的形式。阴影简写是正式 IR 能力；它进入绘制阶段前展开，目的是让每个下游消费者都遵循同一套解释。

这种分工遵循一个原则：IR 面向人类编写与 LLM 生成，表达应尽量简单，降低心智负担；Canonical 值则直接供编译流程消费，需要保证结构严谨、语义明确，满足所属阶段的不变量。

## 合并后再确定默认

真实节点还可能继承 Scope 的默认配置。Reconciler 将当前作用域的有效默认值交给 `resolveNode`；后者先合并，再展开字段和应用相应默认，避免过早补值遮住父级配置。

以描边宽度为例：Scope 的共同样式设为 1，节点通道设为 2，A 自身设为 3，最终使用 3。如果 A 省略线宽，就保留节点通道的 2。这里决定的是“哪个声明生效”，随后才轮到字段的默认与值转换。

`undefined` 不覆盖继承值，但已经由 Schema 物化的默认字段会作为实际值参与合并。因此，外部输入的解析结果与作者保留省略字段的声明，不一定具有相同的后续继承行为。不能在每一层重新 parse 完整对象，期待它仍保留原先的省略意图。

合并也不是对所有对象无限递归。阴影配置作为一个样式字段覆盖；节点自己指定阴影对象时，不会自动拼入父级阴影对象的各个属性。节点想沿用某个预设并修改一项，应在自己的对象中明确写出 `preset`。字体、不透明度等有各自的合并规则。

## 解析结果与编译边界

阴影说明了无需查询外部对象的值展开；其他字段还需要语义上下文。例如，节点的形状名称需要从当前注册表找到 Definition，再按该定义的参数契约解析。Definition 是能力的实现契约，registry 是按名称索引的定义集合。

这些运行时能力不会写回可持久化 IR。解析结果可以携带已选定的 Definition、参数与绘制能力，后续阶段直接消费它们。注册过程与扩展实现的细节属于后续定义注册专题。

不是每个字段都需要展开。节点的 `id: 'A'` 保留其标识语义，明确给出的数值线宽在合并后直接成为有效线宽。resolve 只在简写、默认、优先级或上下文要求时做对应处理，不为已经确定的值增加另一套表示。

| 表达或产物           | resolve 完成什么                 | 后续仍需做什么             |
| -------------------- | -------------------------------- | -------------------------- |
| `shadow: 'md'`       | 展开为具体阴影配置               | 随图元交给后端呈现         |
| `shape: 'rectangle'` | 绑定形状定义并确定参数           | 结合内容计算形状尺寸与边界 |
| 数值颜色             | 结合有效主色与主题模式确定颜色   | 使用已确定的 paint 绘制    |
| 相对位置表达         | 补齐距离等配置，保留目标引用     | 读取目标布局并求实际坐标   |
| `CanonicalNode`      | 汇集布局意图、有效样式与能力绑定 | 文字度量、布局、图元生成   |

Canonical 表示本领域的输入形态已确定，不表示所有结果都已经变成数值。最终节点尺寸依赖文字度量，引用位置依赖目标几何；这些属于后续编译。没有文字、阴影或显式宽度时，相关字段仍可省略，因为“没有内容”或“由布局决定”本身具有语义。

Schema 与 resolve 的校验边界也不同。外部输入的结构在 Schema 入口检查一次；resolver 检查合并后才出现的不变量和真实上下文错误。例如节点自身的宽度小于继承来的最小宽度，只有有效配置合并后才能判断。形状不存在同样需要当前注册表才能发现。
