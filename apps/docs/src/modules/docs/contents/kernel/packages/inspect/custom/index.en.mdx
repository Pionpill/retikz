## Scope

Start with [Built-in inspection](/kernel/packages/inspect/builtins). Use built-in options to toggle control points, bounds, or labels. Define an Inspector when different auxiliary content is needed. This example reads final stroke Path commands and adds circles at explicit endpoints without changing the primary figure.

## Define the capability

The preview includes `endpoint-inspector.ts`, the shared definition for both hosts. Copy that file, then choose an integration below. `namespace` and `type` form the registry key. `owner: { kind: 'path', name: 'stroke' }` selects an existing stroke Path result, validated by `subjectSchema`. The callback reads commands and returns ordinary Core drawing elements for auxiliary compilation.

This example has no custom configuration, so it omits `optionsSchema` and `resolveOptions`. Add a schema when options are needed; add a resolver only when consumption requires a different representation.

The callback combines two inputs: geometry determines where to draw, and options determine what to show. Arrows express dependencies, not parallel execution.

## Inject and use

Both forms register the same Definition and request its key. React displays a component; Vanilla returns SVG containing the markers.

<DocTabs defaultValue="react">
<DocTab value="react" label="React">

```tsx
import { createInspectorRegistry } from '@retikz/inspect';
import { InspectLayout, InspectPath } from '@retikz/inspect/react';
import { Step } from '@retikz/react';
import { endpointInspector, endpointInspectorKey } from './endpoint-inspector';

const registry = createInspectorRegistry([endpointInspector]);

export const Diagram = () => (
  <InspectLayout registry={registry}>
    <InspectPath request={{ inspector: endpointInspectorKey, options: true }}>
      <Step kind="move" to={[0, 0]} />
      <Step kind="cubic" control1={[20, -30]} control2={[80, 30]} to={[100, 0]} />
    </InspectPath>
  </InspectLayout>
);
```

</DocTab>
<DocTab value="vanilla" label="Vanilla">

```ts
import { createInspectorRegistry } from '@retikz/inspect';
import { createInspectionVanillaAuthoring, createInspectionVanillaDriver } from '@retikz/inspect/vanilla';
import { path, renderToSvgString, scene } from '@retikz/vanilla';
import { endpointInspector, endpointInspectorKey } from './endpoint-inspector';

const registry = createInspectorRegistry([endpointInspector]);
const input = scene({
  children: [
    path('curve', {
      authoring: createInspectionVanillaAuthoring({ inspector: endpointInspectorKey, options: true }),
      way: [
        [0, 0],
        {
          cubic: [
            [20, -30],
            [80, 30],
          ],
        },
        [100, 0],
      ],
    }),
  ],
});
const svg = renderToSvgString(input, { compileDriver: createInspectionVanillaDriver({ registry }) });
```

## Errors and limitations

Duplicate registry keys, unregistered requests, and invalid options or subjects terminate inspection compilation. The Core owner must already publish final output; registration does not create an observation source. Read only available geometry, using `context.warn()` when optional data is missing while retaining other results.

Ordinary returned elements use local coordinates. Use an `InspectorFragment` with `coordinateSpace: 'scene'` for scene coordinates to avoid applying a transform twice. Consult the reference and internals pages for complete context, output types, and stage rules.

## Recommended conventions

Follow the auxiliary visual language used by official Inspectors so that concurrent observations remain distinguishable without competing with the primary figure. These are authoring recommendations, not styles automatically added by the compiler.

1. **Share one palette color within each observation.** Use `context.appearance.scopeColor` consistently for lines, markers, and labels instead of hardcoding the same color for every Inspector or maintaining a separate palette. The driver assigns categorical colors from the current theme per observation request, reducing confusion across nested scopes and concurrent observations. Colors repeat when the palette cycles, so also distinguish content with line patterns and labels. Use the corresponding `context.appearance.semanticColors` for explicit meanings such as warnings.

2. **Prefer dashed or dotted auxiliary lines.** Express control handles, reference axes, and bounding boxes through `style.dashPattern`; different patterns can distinguish content sharing a color. Reserve solid lines for actual outlines that need continuity, such as the current built-in Clip outline, rather than turning every line into a dashed line mechanically.

3. **Minimize obstruction of the primary figure.** Prefer thin, unfilled outlines and small point markers. Add fills only to communicate occupied areas, spacing, or warning regions, using low opacity or patterns to keep the underlying figure readable. Keep labels short, transparent, and slightly offset from their markers; place them late in the auxiliary output so auxiliary lines do not cover them.

4. **Expose switches by observation content.** Provide options for independently meaningful content, such as Node outlines, key points, and content boxes, or Path control points and vertices. Control labels separately with `labels`, rather than making every color and line width configurable. Omit `optionsSchema` when there are no options, and omit `resolveOptions` when no conversion is needed.

5. **Make style inheritance intentional.** Inspection fragments can inherit the environment at the observed site. For a stable auxiliary appearance, follow the built-ins: isolate primary defaults with an ordinary Scope using `defaults: { reset: true }`, then set the necessary styles explicitly. This prevents primary fills, fonts, or path defaults from changing the meaning of markers; it should not introduce another theme or rendering system.
