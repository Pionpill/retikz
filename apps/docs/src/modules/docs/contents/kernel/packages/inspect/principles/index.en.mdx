After drawing a curve, you may want to see which control points it actually uses. Inspect can display those points and guide lines without recomputing the primary figure or changing your drawing description. Start with how the primary figure becomes a displayable result to understand where these auxiliary marks come from.

## How Inspect cooperates with Core

Inspect does not analyze your drawing code directly. It waits for Core to compute drawing results, then uses those results to describe auxiliary marks. Core compilation resolves coordinates, references, and layout into scene data (Scene) for Render to display; compilation itself does not paint pixels on screen.

When connecting Inspect, you also select the objects and inspectors to use. The left branch preserves the primary result; the right branch shows the auxiliary work enabled by inspection. Both reach Render, with no arrow returning from the auxiliary branch to modify the primary figure.

<ComponentPreview files="inspect-compile-flow" size="lg" hideCode />

1. **Compute drawing results first.** Core compiles the primary figure and determines the final results of primitives or components. Each specific instance is called an occurrence (one instance after compilation; the same definition can produce multiple instances).
2. **Report selected results.** Objects that support observation publish their final output in Core. Core notifies Inspect of each selected instance's location and output. This notification is an observation (an event carrying a result), and its recipient is an observer. Inspect does not reconstruct the result from the displayed image.
3. **Describe auxiliary marks.** Inspect finds the corresponding Inspector and passes it the result. The Inspector returns ordinary drawing descriptions for control points, guide lines, and other marks: auxiliary IR (intermediate representation), not direct canvas operations.
4. **Compile separately, then display together.** Inspect asks Core to compile those descriptions in isolation into separate scenes. The host connects them as readonly layers, and Render displays them with the primary figure, whose result stays unchanged.

With that flow in mind, the following fields show how Core supplies results and compilation capabilities to Inspect. The `owner` identifies what owns the observed object, while a request expresses the user's inspection selection:

| What Core provides                            | How Inspect uses it                                                                                       |
| --------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| `CompileObservation.owner` and `occurrence`   | Matches a request to the observed object's final instance by owner and occurrence location                |
| `CompileObservation.value`                    | Validates final output with `subjectSchema` and supplies it to `inspect()`                                |
| `CompileObservationContext.theme`             | Gives auxiliary content the current occurrence's theme and semantic colors                                |
| `CompileObservationContext.compileFragment()` | Compiles ordinary IR returned by an Inspector in the current Theme, Scope-style, and provider environment |

A custom Inspector therefore requires the corresponding object to publish final output in Core. Registering an Inspector alone does not make an object without observation support emit observations. Core provides notification and isolated compilation; it does not look up Inspectors or choose auxiliary styling.

## Drawing flow

The diagram shows data flow, not an instruction to draw a guide line as soon as each notification arrives. Execution separates collecting results from generating auxiliary content:

- **`observe()`: collect only.** When Core dispatches a selected instance's final result, Inspect saves the output and its context. It does not generate auxiliary graphics in this callback.
- **`complete()`: generate together.** After Core finishes dispatching final observations, Inspect resolves selection, merges options, validates outputs, and calls each Inspector's `inspect()`. Returned `IRChild` values are compiled in isolation through `compileFragment()` and collected into an InspectionPlane (a collection of auxiliary scenes).

Within one compile, `observe()` runs zero or more times, once for each selected final occurrence; `complete()` runs once only after every notification finishes. The three occurrences in the diagram represent one batch of final instances converging on the same observer session:

<ComponentPreview files="inspect-observer-batch-flow" size="md" hideCode />

The host then converts those scenes into non-hittable readonly layers for Render to display. Primary and auxiliary layers belong to the same compilation revision and commit only when both succeed; a new primary figure is not displayed with auxiliary content from an older revision. Auxiliary scenes also exclude public identity, metadata, and animation semantics.

Ordinary drawing need not load Inspect. When enabled, if no result matches or all Inspectors return empty content, the InspectionPlane is `null` and no auxiliary layer is produced. Extra cost comes from observing selected objects, running Inspector callbacks, and compiling non-empty auxiliary fragments.

## Runtime selection

A `request` is an Inspect selection rule declared on a scene, authored subtree, or object. It specifies the Inspector to invoke (`inspector`), the final occurrences within scope (`target`), and optional configuration (`options`); `true` uses default options, while `false` disables that Inspector at the current site.

The tree below follows one Inspector that supports scene-wide selection, with matching object owners. Lines represent parent-child structure; blue means enabled, and gray dashed boxes mean disabled or blocked. A inherits the parent's enabled state. B disables inspection for its subtree, but the object can reopen it. C sets a barrier, so even an explicit request cannot reopen inspection. These switches affect auxiliary inspection only; all objects still render in the primary figure.

<ComponentPreview files="inspect-selection-tree" size="md" hideCode />

B's `options: false` disables only the selected Inspector; C's `barrier` blocks every Inspector in the subtree. In React, `<InspectScope request={false}>` declares that barrier.

These selections are runtime rules for which final occurrences reach an Inspector at each compile, rather than persisted diagram data:

| Structure                         | Meaning                                                                       |
| --------------------------------- | ----------------------------------------------------------------------------- |
| `InspectionSelectionRule` request | Selects an Inspector and scope with `inspector`, `target`, and `options`      |
| `InspectionSelectionRule` barrier | Prevents descendants from reopening Inspectors at a scene or authored subtree |
| scene target                      | Matches final occurrences with a given owner across the whole scene           |
| subtree target                    | Matches final occurrences below one authored Scope                            |
| self target                       | Matches the current object by source or occurrence index                      |

The playground places two curves in separate subtrees. Change target, control points, and labels, then enable the right barrier to see how local requests resolve against Core final occurrences:

One site may request several Inspectors. Sparse options for one Inspector merge from scene to subtree to current occurrence; ordinary `false` disables one Inspector only at the current site, while a barrier prevents descendants from reopening any Inspector.

Merging uses authored options, then the single `optionsSchema` applies defaults before `resolveOptions` expands shorthand. A parent with `labels: true` and a child with `{}` keeps labels enabled; an explicit child `labels: false` disables them. Every enabled rule is still validated at admission, even if it never matches or is later overridden.

Calling `StrokePathInspectOptionsSchema.parse({})` directly produces a defaulted snapshot containing `labels: false`. Passing that snapshot as child options makes `false` an explicit override. Persist authored configuration to retain omission intent; persisting parsed output stores materialized defaults instead.

## Drawing style

Inspect assigns ordinary auxiliary colors from the current Core theme's categorical palette in effective inspection-request order. Guide lines, control points, and labels produced by the same request share a color so their associated object is easy to identify. Control point labels have transparent backgrounds.

Inspect uses Core's palette and semantic colors without providing a separate Inspect Theme configuration. Built-in Inspectors also offer less styling freedom than Core drawing components: the path Inspector exposes only control-point and label visibility, while its implementation determines line widths, dash patterns, and font sizes. As auxiliary content for understanding the primary figure, inspection prioritizes clarity, consistency, and restraint.

Custom Inspectors can still define styles in the ordinary Core IR they return. This belongs to Inspector extensibility rather than the built-in Inspector's styling options.

## Results and errors

| Field                                 | Meaning                                                                |
| ------------------------------------- | ---------------------------------------------------------------------- |
| `InspectionCompileResult.primary`     | Ordinary Core compile output, unchanged by auxiliary content           |
| `InspectionCompileResult.inspection`  | Ordered auxiliary plane; `null` when every callback produces no output |
| `InspectionCompileResult.diagnostics` | Structured warnings from isolated fragments                            |

`RetikzInspectError.details.origin.stage` identifies a failure in selection, final-output validation, an `inspect` callback, output normalization, auxiliary-fragment compilation, or final assembly. Duplicate registry keys, unregistered requests, owner mismatch, and schema failures stop that inspection compile without delivering a partial auxiliary result.
