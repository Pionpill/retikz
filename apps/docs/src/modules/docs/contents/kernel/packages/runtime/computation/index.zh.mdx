[Source · 来源](/kernel/packages/runtime/source)保存了坐标，但到原点的距离需要由坐标计算得到。当坐标从 `[3, 4]` 变为 `[6, 8]`，距离也应从 `5` 更新为 `10`；如果只是从 `[3, 4]` 变为 `[-3, 4]`，距离仍然是 `5`，依赖距离的计算就可能不必继续执行。

**Computation**（计算）定义如何从来源或其他计算的结果派生数据。Runtime 负责按依赖顺序执行和持有结果，计算作者负责具体算法，以及什么时候可以复用旧结果。本篇沿着“坐标 → 距离 → 显示文本”说明这个过程；事务如何统一发布留给后续章节。

## 整体流程

| 环节     | 接口或配置                               | 作用                                                           |
| -------- | ---------------------------------------- | -------------------------------------------------------------- |
| 定义     | `defineRuntimeComputation(...)`          | 声明依赖、算法与结果管理规则                                   |
| 注册     | `createRuntimeComputationRegistry(...)`  | 登记计算并校验依赖关系                                         |
| 首次执行 | `createRuntime(...)` → `run`             | 按依赖顺序计算初始结果                                         |
| 更新     | `runtime.update(...)` → `update` / `run` | 对受影响计算尝试增量更新；无增量实现或采用全量策略时执行 `run` |
| 读取     | `runtime.result(token)`                  | 读取已发布的计算结果及版本                                     |
| 释放     | `runtime.dispose()`                      | 释放 Runtime 持有的计算结果                                    |

计算先定义和注册，再由 Runtime 首次执行或随更新重新执行，成功发布后才能读取新结果。

## 定义与依赖

### 定义计算

先区分三个概念：

- **计算定义**：声明依赖和执行规则，可以供多个 Runtime 复用。
- **计算凭证**（Token）：定义函数返回的对象，后续注册、声明依赖和读取结果都使用它。
- **计算结果**（Result）：一次执行产生的数据，本例是数值距离，由各个 Runtime 独立持有。

`defineRuntimeComputation(input)` 接收计算配置并返回 Token。定义时不执行计算，也不产生距离值。函数签名如下：

```ts
declare const defineRuntimeComputation: <
  TResultInput,
  TResult = TResultInput,
  TComputationRead = TResult,
  TPublicRead = TResult,
>(
  input: RuntimeComputationDefinitionInput<TResultInput, TResult, TComputationRead, TPublicRead>,
) => RuntimeComputationDefinition<TResultInput, TResult, TComputationRead, TPublicRead>;
```

输入配置中的成员按下面的职责协作；结果转换在“结果管理”中展开，观测相关用法见 [Trace · 错误诊断](/kernel/packages/runtime/trace)。

计算标识 `RuntimeComputationId` 包含归属来源的 `owner` 和该来源内的计算名称 `key`。它与[实体身份](/kernel/packages/runtime/identity)的 `owner/path` 用途不同：这里标识一项计算规则，不标识状态中的某个节点。

```ts
type RuntimeComputationId = Readonly<{ owner: string; key: string }>;
```

下面用只读坐标定义距离计算。为了让例子独立可读，坐标来源直接接收数值元组；捕获、读取和比较的细节见来源篇。

```ts
import { defineRuntimeSource, defineRuntimeComputation } from '@retikz/runtime';

type Position = readonly [number, number];
const position = defineRuntimeSource<Position, Position, Position, never>({
  key: 'example/position',
  value: {
    capture: input => Object.freeze([input[0], input[1]] as const),
    read: value => value,
    equals: (left, right) => left[0] === right[0] && left[1] === right[1],
  },
});

const distance = defineRuntimeComputation<number>({
  // [!code ++]
  id: { owner: position.key, key: 'distance' }, // [!code ++]
  sources: [position], // [!code ++]
  run: view => ({ kind: 'full', result: Math.hypot(...view.snapshot(position).value) }), // [!code ++]
}); // [!code ++]
```

`run` 返回 `{ kind: 'full', result }`，表示从完整输入得到结果。返回的 `distance` 则仍是 Token，不是这个数值；它与处理回调在 Runtime 内部关联，后续要沿用同一对象。

计算定义中的 `sources` 声明依赖哪些来源，`computations` 声明依赖哪些上游计算。可以把它理解为订阅上游变化：调用 `runtime.update` 后，Runtime 判断来源是否实际变化，再按依赖顺序更新相关计算。直接修改外部对象不会自动触发这条流程。

例如，“坐标来源 → 距离计算 → 显示文本计算”：坐标实际变化会触发距离计算；距离计算产生新结果后，再触发显示文本计算。如果距离计算明确返回 `bailout`，表示复用旧结果，就不沿这条依赖继续触发下游；下游若还有其他变化的依赖，仍会执行。具体返回形式见[增量更新](#增量更新)。

后面的注册配置也有 `sources` 和 `computations`，但它们只是提供来源注册表与计算清单。**依赖关系由每个计算定义声明**，不是由注册列表的位置或顺序建立。

### 依赖作用

`sources` 和 `computations` 不是两种传参写法，而是两类数据入口：前者读来源状态，后者读别的计算已经生成的公开结果。对于同一个当前计算，每一项声明都有两个作用：允许读取这个上游，并将其变化纳入当前计算的执行条件。

| 当前计算声明的字段         | 可以读什么                      | 什么变化会影响当前计算                              |
| -------------------------- | ------------------------------- | --------------------------------------------------- |
| `sources: [position]`      | `view.snapshot(position).value` | position 的完整状态被判定发生变化                   |
| `computations: [distance]` | `view.result(distance).value`   | distance 产生了新结果；只复用旧结果时不沿此依赖触发 |

下面每条箭头都对应**下游定义**中的一项声明。`distance` 接收来源中的 `[3, 4]`；`label` 接收距离结果 `5`，不需要重新读取坐标或重复计算距离。

<ComponentPreview files="computation-dependencies" size="sm" hideCode type="illustration" />

只声明 `computations: [distance]` 不会间接授权读取 `position`。反过来，若给 `label` 额外声明 `sources: [position]`，坐标变化就能直接触发它，即使距离计算已经 `bailout`。因此，声明应反映当前计算真正依赖的数据：漏掉会导致读取报错，多写则可能引入本不需要的重新执行。

读取回调不会动态建立订阅。已声明但本次没有读取的依赖仍然影响执行条件；同一次更新中多个依赖变化时，当前计算按依赖顺序执行一次，而不是每条依赖各调用一次。

### 读取依赖

回调收到的 `view` 是本次执行的**候选视图**：包含准备发布的新来源，以及已经完成的上游计算结果。它与调用方通过 Runtime 读取的已发布状态不同。

| 读取入口                   | 功能                                         |
| -------------------------- | -------------------------------------------- |
| `view.snapshot(source)`    | 读取已声明来源的快照，通过 `.value` 取得值   |
| `view.isChanged(source)`   | 判断该来源在本次更新中是否实际变化           |
| `view.changeSet(source)`   | 读取该来源的变更提示，未提供时为 `undefined` |
| `view.result(computation)` | 读取已声明上游计算的公开结果快照             |

例如，显示文本依赖距离计算，而不直接读取坐标。因此它只声明 `distance`，不必重复声明上游的 `position`：

```ts
const label = defineRuntimeComputation<string>({
  id: { owner: position.key, key: 'label' },
  sources: [],
  computations: [distance],
  run: view => ({ kind: 'full', result: `Distance: ${view.result(distance).value}` }),
});
```

读取未声明的来源或计算会报错，即使它已经注册。`id.owner` 只说明归属，不能代替依赖声明。

### 注册计算

注册解决“哪些定义可用、按什么顺序执行”，依赖声明解决“某项计算具体需要谁”。两者分开，才能校验缺失依赖并允许调用方以任意顺序组织注册列表。

**计算注册表**把这些定义组织成可以执行的依赖图：先确认所有依赖存在，再安排上游先于下游执行。`createRuntimeComputationRegistry(input)` 创建这个固定注册表，不会立即调用 `run`。

```ts
declare const createRuntimeComputationRegistry: (input: RuntimeComputationRegistryInput) => RuntimeComputationRegistry;
```

所有计算使用同一套注册和校验规则。调用方可以自行组织内置与自定义计算，再合并到 `computations`；注册表不区分这些类别，也不提供覆盖优先级。省略列表时创建空计算注册表。

```ts
import { createRuntimeSourceRegistry, createRuntimeComputationRegistry } from '@retikz/runtime';

const sources = createRuntimeSourceRegistry([position]);
const computations = createRuntimeComputationRegistry({ sources, computations: [label, distance] });

console.log(computations.definitions().map(token => token.id.key)); // ['distance', 'label']
console.log(computations.find(distance.id) === distance); // true
console.log(computations.resolve(distance) === distance); // true
```

注册时拒绝无效 Token、重复计算标识、缺失的来源或上游计算，以及循环依赖。`definitions()` 返回依赖优先的稳定顺序；同时可执行的计算按 `owner`、`key` 的字符串顺序排列，不依赖输入列表顺序。`find(id)` 按标识内容查找，未找到返回 `undefined`；`resolve(token)` 检查原 Token 是否属于注册表，不能用另一个同名定义替代。

## 结果管理

**计算结果**是一次计算完成后，由 Runtime 保存下来供后续使用的数据。前面距离计算得到的 `5` 就是结果；它不只是在回调结束时临时返回，还承担三种用途：

- **供调用方读取**：界面通过 `runtime.result(distance).value` 取得已发布的距离，无需为了读取再执行计算。
- **供下游计算使用**：显示文本计算通过 `view.result(distance).value` 读取上游距离，继续派生文本。
- **供下一次更新复用**：本计算的 `update` 收到旧结果的私有视图 `previous`，可以利用保留的结果、索引或缓存更新数据，是否能减少计算量取决于具体算法。

要区分结果数据与同名配置：`run/update` 返回的 `result` 是本次产生的数据，计算定义中的 `result` 则是管理这些数据的捕获、读取和释放规则。简单数字可以省略这项配置，但计算仍会产生和保存结果。

数值距离可以直接保存和读取；复杂计算还可能保存索引、缓存或资源句柄，却只希望向外暴露结果。因此，结果区分执行返回值、内部持有值、当前计算使用的旧结果视图，以及公开视图。

下图从一次回调的返回值出发，区分结果的两类读取者。私有视图只服务当前计算的后续更新；公开视图则服务下游计算和外部使用者。图中的“本计算下次 update”是下一次实际执行增量回调，不是每次外部读取。

<ComponentPreview files="computation-result" size="md" hideCode type="flow" />

这里不要求保留四份副本：四个类型区分职责，是否复制由转换函数决定。比如内部保存 `{ point, distance }`，私有视图保留这个对象，公开视图只返回 `distance`，就能把下次更新需要的信息留在计算内部，而不让所有使用者依赖缓存结构。

`result` 配置管理这些转换。`readForComputation` 的结果只交给本计算下一次 `update` 的 `previous`；`read` 的结果供下游计算、宿主读取和提交通知使用。

例如，把坐标和距离一起保存在内部，下一次更新可以读取全部信息，而公开读取只得到距离：

```ts
type DistanceCache = Readonly<{ point: Position; distance: number }>;
const cachedDistance = defineRuntimeComputation<DistanceCache, DistanceCache, DistanceCache, number>({
  id: { owner: position.key, key: 'cached-distance' },
  sources: [position],
  result: { read: value => value.distance },
  run: view => {
    const point = view.snapshot(position).value;
    return { kind: 'full', result: Object.freeze({ point, distance: Math.hypot(...point) }) };
  },
});
```

下游通过 `view.result(cachedDistance).value` 只能得到数值距离，不能访问 `point`。如果为这项计算提供 `update`，它的 `previous` 则是带有 `point` 和 `distance` 的私有对象，可以使用这些信息决定如何更新。改变内部缓存结构时，只要公开读取仍返回数值，下游就不需要跟着修改。

此例公开读取从对象变成数值，因此 `read` 必须提供；其余转换类型一致，可以省略。所有转换都可省略且无需清理时，整个 `result` 配置也可省略，前面的 `distance` 就是这种情况。默认原值返回不会复制或冻结对象，作者仍需保证只读隔离，尤其不能在更新中直接修改 `previous`。

捕获完成后，Runtime 先生成私有视图，再生成公开视图，并缓存这两份结果；每次读取快照不会重新执行转换。读取转换失败时会清理已经捕获的新结果；成功替换后才释放旧结果。需要资源释放时提供 `dispose`，复用当前结果应通过后文的 `bailout` 表达。

## 执行与传播

### 候选阶段与执行方式

Runtime 在初始化和更新中都可能调用 `run`，因此不能用回调名称判断当前生命周期。候选视图说明“准备哪一版数据”，上下文说明“采用哪条计算路径”，返回值说明“这次产生了什么”。

| 入口                     | 取值与含义                                                                   |
| ------------------------ | ---------------------------------------------------------------------------- |
| `view.phase`             | `initial` 是初始化，`update` 是后续事务                                      |
| `view.baseRevision`      | 仅更新阶段存在，表示当前已发布版本                                           |
| `view.candidateRevision` | 本次候选成功后将发布的版本；初始化为 `0`                                     |
| `context.execution`      | `full` 调用全量路径；`incremental` 尝试增量；`fallback` 调用回退后的全量路径 |
| 返回 `kind`              | `run` 只返回 `full`；`update` 返回 `incremental`、`bailout` 或 `fallback`    |

例如版本 `2` 的更新中，`update` 可以收到 `phase: 'update'`、`candidateRevision: 3`、`execution: 'incremental'`。若它返回 `fallback`，Runtime 在相同候选视图上调用 `run`，此时 `execution` 变为 `fallback`，但 `run` 仍返回 `kind: 'full'`。最终提交事件会将本计算记为 `fallback`。

候选快照中的版本也是 `candidateRevision`，包括复用未变化的来源或上游结果；这不表示该值已经对宿主发布。成员间的先后关系见[生命周期](/kernel/packages/runtime/lifecycle#一次更新)。

### 增量更新

**首次执行一定调用 `run`**；后续依赖变化触发计算时，默认优先调用 `update`，未提供 `update` 则调用 `run`。全量策略、上游全量或回退，以及 `update` 返回 `fallback` 时，也会调用 `run`；未受依赖变化影响的计算直接跳过。

`update(previous, view, context)` 接收旧结果的私有视图和本次候选数据，由计算作者选择如何得到正确结果。下面是三种返回形式；`run` 则始终返回 `full` 和完整新结果。

| `update` 返回                        | Runtime 的处理                                                     |
| ------------------------------------ | ------------------------------------------------------------------ |
| `{ kind: 'incremental', result }`    | 捕获并准备新结果，继续触发依赖它的计算                             |
| `{ kind: 'bailout' }`                | 保留旧结果，不执行结果转换，也不因本项计算触发下游                 |
| `{ kind: 'fallback', diagnostics? }` | 放弃增量路径，在同一候选数据上调用 `run`；可附带说明原因的业务警告 |

`incremental` 不表示返回一个补丁，而是用增量算法得到**完整的新结果**。Runtime 不会把它与旧结果自动合并。`bailout` 表示作者确认旧结果仍可用；`fallback` 表示当前增量方法不适用，要求在相同候选输入上重新调用 `run`，不是放弃这次更新。

下图只展开已经进入 `update` 的计算；没有依赖变化而被跳过的计算，不会进入任何返回分支。

<ComponentPreview files="computation-outcomes" size="lg" hideCode type="flow" />

回退后的 `run` 必须返回 `{ kind: 'full', result }`，随后也会捕获新结果并继续传播。抛出异常则是执行失败，不是另一种 `fallback`；本次更新如何回滚由 Runtime 篇说明。

给距离计算增加 `update`，可以在坐标变化但距离不变时保留旧结果。以下是替换前面 `distance` 定义的版本，不要将两个同名定义一起注册：

```ts
const distance = defineRuntimeComputation<number>({
  id: { owner: position.key, key: 'distance' },
  sources: [position],
  run: view => ({ kind: 'full', result: Math.hypot(...view.snapshot(position).value) }),
  update: (previous, view) => {
    const next = Math.hypot(...view.snapshot(position).value);
    return next === previous ? { kind: 'bailout' } : { kind: 'incremental', result: next };
  },
});
```

这里仍重新计算一次距离，目的是展示返回值如何影响传播，不意味着算法已经更快。Runtime 没有为计算结果配置 `equals`：即使新结果的数值相同，返回 `incremental` 仍会继续传播；是否复用由作者明确决定。

| 坐标变化           | 距离计算                     | 显示文本计算                    |
| ------------------ | ---------------------------- | ------------------------------- |
| `[3, 4] → [3, 4]`  | 来源相等，跳过               | 跳过                            |
| `[3, 4] → [-3, 4]` | 距离仍为 `5`，返回 `bailout` | 没有其他依赖变化，跳过          |
| `[3, 4] → [6, 8]`  | 返回新距离 `10`              | 执行 `run`，得到 `Distance: 10` |

`bailout` 只停止这一条传播路径；下游若还有其他变化的依赖，仍然会执行。上游使用全量执行时，下游也使用全量执行；上游回退时，下游沿回退路径执行。显式全量策略会跳过增量尝试，但不会因此执行完全不受影响的计算。

下图每个圆形表示一项计算，箭头从上游指向依赖它的下游；三行分别表示一次更新中的不同情况。假设下游直接依赖的 Source 均未变化，蓝色节点均产生新结果。

<ComponentPreview files="computation-propagation" size="lg" hideCode type="illustration" />

橙色节点执行了 `update` 并返回 `bailout`；灰色节点则完全没有执行，直接复用旧结果。最后一行中，A 的 `bailout` 不会阻止 D 的新结果触发 B，再由 B 的新结果触发 C。箭头始终表示依赖关系，即使本次没有沿该依赖触发执行，它也仍然存在。

`view.changeSet(source)` 是可选变更提示的读取入口，未提供时返回 `undefined`。提示如何随完整输入提交、如何校验以及如何影响 Runtime 的执行路径，将在 Runtime 篇统一说明。

回调的 `context.execution` 区分当前执行方式；`context.trace` 和 `context.diagnose` 用于记录观测信息。`observeCommit` 在新结果成功发布后通知调用方；复用旧结果时不触发该通知。它是隔离的观察回调，不负责计算和资源提交。

### 消费变更提示

下面把坐标例子换成一份包含 A/B 的节点来源，完整演示提示的创建、消费和回退。节点值乘以二后生成标签对象；只改 A 时，复用 B 的旧标签对象。蓝图是“来源身份稳定 → 算法校验提示 → 采用新结果”，不是 Runtime 自动按 Identity 更新。

代码可独立运行。绿色 `+` 标出本步新增的提示消费逻辑，其余是定义和运行上下文：

```ts
import {
  createRuntime,
  createRuntimeSourceRegistry,
  createRuntimeComputationRegistry,
  createRuntimeSourceInput,
  createRuntimeSourceUpdate,
  createRuntimeChangeSet,
  createRuntimeIdentity,
  defineRuntimeSource,
  defineRuntimeComputation,
} from '@retikz/runtime';

type NodeKey = 'A' | 'B';
type Values = Readonly<Record<NodeKey, number>>;
type Labels = Readonly<Record<NodeKey, Readonly<{ text: string }>>>;
type Cached = Readonly<{ values: Values; labels: Labels }>;
const graph = defineRuntimeSource<Values, Values, Values, NodeKey>({
  key: 'graph',
  value: {
    capture: input => Object.freeze({ ...input }),
    read: value => value,
    equals: (a, b) => a.A === b.A && a.B === b.B,
  },
  collectIdentities: () => ['A', 'B'].map(key => createRuntimeIdentity('graph', ['nodes', key])),
});
const label = (value: number) => Object.freeze({ text: String(value * 2) });
const doubled = defineRuntimeComputation<Cached, Cached, Cached, Labels>({
  id: { owner: graph.key, key: 'doubled' },
  sources: [graph],
  result: { read: result => result.labels },
  run: view => {
    const values = view.snapshot(graph).value;
    return {
      kind: 'full',
      result: Object.freeze({
        values,
        labels: Object.freeze({ A: label(values.A), B: label(values.B) }),
      }),
    };
  },
  update: (previous, view) => {
    // [!code ++]
    const values = view.snapshot(graph).value; // [!code ++]
    const hints = view.changeSet(graph)?.changes; // [!code ++]
    const changed = (['A', 'B'] as const).filter(key => previous.values[key] !== values[key]); // [!code ++]
    if (!hints || changed.some(key => !hints.includes(key))) {
      // [!code ++]
      return {
        kind: 'fallback',
        diagnostics: [
          {
            // [!code ++]
            code: 'graph/incomplete-hint',
            phase: 'update',
            message: 'Use full calculation', // [!code ++]
          },
        ],
      }; // [!code ++]
    } // [!code ++]
    const labels = { ...previous.labels }; // [!code ++]
    for (const key of changed) labels[key] = label(values[key]); // [!code ++]
    return { kind: 'incremental', result: Object.freeze({ values, labels: Object.freeze(labels) }) }; // [!code ++]
  }, // [!code ++]
});
const sources = createRuntimeSourceRegistry([graph]);
const computations = createRuntimeComputationRegistry({ sources, computations: [doubled] });
const runtime = createRuntime({
  sources,
  computations,
  initialSnapshots: [createRuntimeSourceInput(graph, { A: 1, B: 2 })],
});
try {
  const before = runtime.result(doubled).value;
  const baseRevision = runtime.revision();
  const next = runtime.update({
    baseRevision,
    sources: [createRuntimeSourceUpdate(graph, { A: 3, B: 2 }, createRuntimeChangeSet<NodeKey>(baseRevision, ['A']))],
  });
  console.log(next.outcome, runtime.result(doubled).value.A.text); // 'incremental', '6'
  console.log(runtime.result(doubled).value.B === before.B); // true
  const fallback = runtime.update({
    baseRevision: runtime.revision(),
    sources: [createRuntimeSourceUpdate(graph, { A: 4, B: 2 })],
  });
  console.log(fallback.outcome, fallback.diagnostics[0]?.code); // 'fallback', 'graph/incomplete-hint'
  console.log(runtime.result(doubled).value.A.text); // '8'
} finally {
  runtime.dispose();
}
```

这个示例扫描两个字段以核对提示是否覆盖实际变化，仍有比较成本；复用的是未变化节点的标签对象，不宣称减少了全部扫描工作。大型数据应由领域算法建立可靠的提示验证方式。Source 的身份收集与算法的 `NodeKey` 对应关系由本例定义，不是隐式依赖。

缺少或漏报提示时返回 `fallback`，附带 `code/phase/message` 说明原因，Runtime 再执行 `run`。回退警告随成功结果进入诊断；若后续计算或提交失败，候选计算业务警告不会作为已提交警告发布，执行与清理故障仍按 [Trace](/kernel/packages/runtime/trace#消费诊断) 的规则保留。

### 计算流程

先定义依赖与执行规则，再由注册表校验并排序。运行实例需要这些定义时，才调用 `run/update` 生成结果；结果转换决定哪些内容供后续更新使用，哪些内容对外公开。

<ComponentPreview files="computation-flow" size="md" hideCode type="flow" />

计算内部通过 `view.result(distance).value` 读取本次执行可用的上游结果；外部通过 `runtime.result(distance).value` 读取已发布结果。查询结果不会重新执行计算。初始化、更新、版本与发布的串联见后续 Runtime 篇；当前可运行的接入代码见[入门示例](/kernel/packages/runtime/usage)。

## 提交观察

`observeCommit` 接收已经发布的公开结果，不参与决定事务是否成功。初始化会在 `createRuntime(...)` 返回前通知一次；后续仅当该计算产生新结果时通知，跳过或返回 `bailout` 不通知。需要原子更新 DOM 等外部资源时，应使用 [Participant](/kernel/packages/runtime/participant)。

| 事件成员                      | 初始化           | 后续更新                                       |
| ----------------------------- | ---------------- | ---------------------------------------------- |
| `phase`                       | `initial`        | `update`                                       |
| `baseRevision`                | 不存在           | 更新前版本                                     |
| `revision`、`result.revision` | `0`              | 已发布的新版本                                 |
| `outcome`                     | `full`           | 本项计算的 `full`、`incremental` 或 `fallback` |
| `result.value`                | 首次结果公开视图 | 本次结果公开视图                               |
| `diagnostics`                 | 通知前冻结的诊断 | 通知前冻结的整笔事务诊断                       |

将前面的距离计算加上观察者，注册这份新定义后再创建实例。回调直接消费事件，不读取尚未赋值的 Runtime 变量，也不重入实例方法：

```ts
const observedDistance = defineRuntimeComputation<number>({
  id: { owner: position.key, key: 'observed-distance' },
  sources: [position],
  run: view => ({ kind: 'full', result: Math.hypot(...view.snapshot(position).value) }),
  observeCommit: event => {
    // [!code ++]
    console.log(event.phase, event.revision, event.outcome, event.result.value); // [!code ++]
  }, // [!code ++]
});
```

观察者按计算注册表的依赖顺序同步通知。事件的 `outcome` 只描述当前计算，可能与 `runtime.update(...)` 的聚合结果不同。观察者抛错会记录诊断，不撤销发布，也不会阻止后续观察者；这些较晚的诊断不追加到已经冻结的事件列表中，消费方式见 [Trace](/kernel/packages/runtime/trace#消费诊断)。

## Core 应用

Core 将图文档编译包装成一项 Computation。公开工厂 `createCoreComputation(options)` 创建编译计算 Token；它消费文档来源，内部保存增量编译需要的状态，并向外提供编译结果和 Scene 快照。

```ts
import { CoreSourceDefinition, createCoreComputation } from '@retikz/core';
import { createRuntimeSourceRegistry, createRuntimeComputationRegistry } from '@retikz/runtime';

const compile = createCoreComputation({});
const sources = createRuntimeSourceRegistry([CoreSourceDefinition]);
const computations = createRuntimeComputationRegistry({ sources, computations: [compile] });
// 将这两个注册表与文档初始输入交给 createRuntime
// runtime.result(compile).value.output.result.scene 是已发布的 Scene
```

这个应用对应了前面的三项职责：`run` 从完整文档编译，`update` 尝试支持的局部更新并在不适用时回退，`result` 将内部编译状态与公开结果分开。Runtime 不理解图元或编译算法，这些规则由 Core 提供，具体展开见 Core 文档。
