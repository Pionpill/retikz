description: Derive distance from coordinates and understand computation definitions, dependencies, result views and incremental updates

[Source](/kernel/packages/runtime/source) holds coordinates, but the distance to the origin must be computed. Moving from `[3, 4]` to `[6, 8]` changes the distance from `5` to `10`. Moving to `[-3, 4]` leaves it at `5`, so computations that depend on the distance may not need to run again.

**Computation** defines how to derive data from Sources or other computations. Runtime executes dependencies in order and owns the results; the author supplies the algorithm and decides when an old result can be reused. This page follows “coordinates → distance → display text”. Transaction publication is left to a later chapter.

## Defining a computation

Distinguish three concepts:

- **Computation definition**: dependency declarations and execution rules that multiple Runtime instances can reuse.
- **Computation token**: the object returned by the definition function, used for registration, dependency declarations and result lookup.
- **Result**: the data produced by an execution, here a numeric distance, owned independently by each Runtime.

`defineRuntimeComputation(input)` accepts configuration and returns a token. Defining a computation does not execute it or produce a distance. Its signature is:

```ts
declare const defineRuntimeComputation: <
  TResultInput,
  TResult = TResultInput,
  TComputationRead = TResult,
  TPublicRead = TResult,
>(
  input: RuntimeComputationDefinitionInput<TResultInput, TResult, TComputationRead, TPublicRead>,
) => RuntimeComputationDefinition<TResultInput, TResult, TComputationRead, TPublicRead>;
```

The configuration members cooperate as follows. Result conversion is expanded in “Computation results”; diagnostics and Trace receive only a brief introduction here.

The main structure is expanded below. Conditional types that require `result` when conversion types differ are omitted.

```ts
type RuntimeComputationDefinitionInput<
  TResultInput,
  TResult = TResultInput,
  TComputationRead = TResult,
  TPublicRead = TResult,
> = Readonly<{
  id: RuntimeComputationId;
  sources: ReadonlyArray<RuntimeSourceToken>;
  computations?: ReadonlyArray<RuntimeComputationToken>;
  tracePhases?: ReadonlyArray<RuntimeTracePhaseDefinition>;
  result?: RuntimeComputationResultDefinitionInput<TResultInput, TResult, TComputationRead, TPublicRead>;
  run: (view: RuntimeCandidateView, context: RuntimeComputationContext) => RuntimeRunOutcome<TResultInput>;
  update?: (
    previous: TComputationRead,
    view: RuntimeCandidateView,
    context: RuntimeComputationContext,
  ) => RuntimeUpdateOutcome<TResultInput>;
  observeCommit?: (event: RuntimeCommitEvent<TPublicRead>) => void;
}>;
```

</DocTab>
</DocTabs>

`RuntimeComputationId` consists of the owning Source's `owner` and a computation `key` within that Source. It serves a different purpose from an [entity identity](/kernel/packages/runtime/identity) with `owner/path`: it identifies a computation rule, not a node within state.

```ts
type RuntimeComputationId = Readonly<{ owner: string; key: string }>;
```

Define a distance computation over read-only coordinates. To keep this example self-contained, the Source accepts a numeric tuple directly. Capture, reads and equality are explained in the Source chapter.

```ts
import { defineRuntimeSource, defineRuntimeComputation } from '@retikz/runtime';

type Position = readonly [number, number];
const position = defineRuntimeSource<Position, Position, Position, never>({
  key: 'example/position',
  value: {
    capture: input => Object.freeze([input[0], input[1]] as const),
    read: value => value,
    equals: (left, right) => left[0] === right[0] && left[1] === right[1],
  },
});

const distance = defineRuntimeComputation<number>({
  id: { owner: position.key, key: 'distance' },
  sources: [position],
  run: view => ({ kind: 'full', result: Math.hypot(...view.snapshot(position).value) }),
});
```

`run` returns `{ kind: 'full', result }`, a result derived from complete input. The returned `distance` is still a token, not that numeric value. Runtime associates it with the callbacks internally; subsequent operations must retain the same token object.

## Dependencies and registration

In a computation definition, `sources` declares Source dependencies and `computations` declares upstream computation dependencies. Think of these as subscriptions to upstream changes: after a call to `runtime.update`, Runtime determines which Sources actually changed and updates affected computations in dependency order. Mutating an external object does not trigger this process automatically.

For example, “coordinate Source → distance computation → display text computation”: changed coordinates trigger the distance computation, and its new result triggers the display text computation. If the distance computation explicitly returns `bailout` to reuse its old result, propagation stops along that dependency. A downstream computation still executes if another dependency changed. See [Incremental updates](#incremental-updates) for the result forms.

The registration configuration below also has `sources` and `computations`, but these supply a Source registry and a list of computations. **Each computation definition declares its dependencies**; registration positions or list order do not establish them.

### Dependency effects

`sources` and `computations` are two kinds of data inputs: Source state and public results already produced by other computations. Each declaration both permits reading that upstream and includes its changes in the execution condition of the current computation.

| Declaration in this computation | Allowed read                    | Change that affects this computation                                                    |
| ------------------------------- | ------------------------------- | --------------------------------------------------------------------------------------- |
| `sources: [position]`           | `view.snapshot(position).value` | The complete position state is determined to have changed                               |
| `computations: [distance]`      | `view.result(distance).value`   | Distance produces a new result; reusing its old result does not trigger this dependency |

Each arrow below corresponds to a declaration in its **downstream definition**. Distance consumes `[3, 4]` from the Source, while label consumes the result `5` without reading coordinates or recomputing distance.

<ComponentPreview files="computation-dependencies" size="sm" hideCode type="illustration" />

Declaring `computations: [distance]` does not indirectly authorize reading `position`. Adding `sources: [position]` to label creates a direct trigger: coordinate changes can execute label even if distance bailed out. Declare the data the current computation actually depends on; missing declarations cause read errors, while unnecessary declarations may cause unnecessary execution.

Reads do not dynamically subscribe to dependencies. A declared dependency still affects scheduling even when a callback does not read it on this execution. Multiple changed dependencies select the current computation once per update, not once per dependency.

### Reading dependencies

The callback's `view` is a **candidate view** for this execution: it contains prepared Source state and already-computed upstream results awaiting publication. It differs from the committed state callers read through Runtime.

| Read operation             | Purpose                                                        |
| -------------------------- | -------------------------------------------------------------- |
| `view.snapshot(source)`    | Reads a declared Source snapshot; `.value` contains the value  |
| `view.isChanged(source)`   | Reports whether that Source actually changed in this update    |
| `view.changeSet(source)`   | Reads its change hint, or `undefined` when absent              |
| `view.result(computation)` | Reads a declared upstream computation's public result snapshot |

The display text depends on the distance computation without reading coordinates directly. It declares `distance` and does not need to repeat the upstream `position` dependency:

```ts
const label = defineRuntimeComputation<string>({
  id: { owner: position.key, key: 'label' },
  sources: [],
  computations: [distance],
  run: view => ({ kind: 'full', result: `Distance: ${view.result(distance).value}` }),
});
```

Reading an undeclared Source or computation throws even when it is registered. `id.owner` expresses ownership and does not replace a dependency declaration.

### Registering computations

Registration determines which definitions are available and their execution order. Dependency declarations determine what each computation needs. Keeping these separate allows missing dependencies to be rejected and registration lists to be supplied in any order.

A **computation registry** organizes definitions into an executable dependency graph: it checks that dependencies exist and orders upstream computations before their consumers. `createRuntimeComputationRegistry(input)` creates this fixed registry without calling `run`.

```ts
declare const createRuntimeComputationRegistry: (input: RuntimeComputationRegistryInput) => RuntimeComputationRegistry;
```

<DocTab value="members" label="Properties">

| Member         | Required | Purpose                                                                               |
| -------------- | -------- | ------------------------------------------------------------------------------------- |
| `sources`      | Yes      | Binds the Source registry containing each computation's owner and Source dependencies |
| `computations` | No       | Computation tokens to register; defaults to `[]`                                      |

</DocTab>
<DocTab value="definition" label="Type definition">

```ts
type RuntimeComputationRegistryInput = Readonly<{
  sources: RuntimeSourceRegistry;
  computations?: ReadonlyArray<RuntimeComputationToken>;
}>;
```

</DocTab>
</DocTabs>

All computations use the same registration and validation rules. Callers may organize built-in and custom computations themselves, then combine them in `computations`. The registry does not distinguish these categories or provide override precedence. Omitting the list creates an empty computation registry.

```ts
import { createRuntimeSourceRegistry, createRuntimeComputationRegistry } from '@retikz/runtime';

const sources = createRuntimeSourceRegistry([position]);
const computations = createRuntimeComputationRegistry({ sources, computations: [label, distance] });

console.log(computations.definitions().map(token => token.id.key)); // ['distance', 'label']
console.log(computations.find(distance.id) === distance); // true
console.log(computations.resolve(distance) === distance); // true
```

Registration rejects invalid tokens, duplicate computation IDs, missing Sources or upstream computations, and dependency cycles. `definitions()` returns stable dependency-first order. Computations ready at the same time are ordered by the strings `owner` and `key`, independently of input order. `find(id)` matches ID contents and returns `undefined` if absent; `resolve(token)` checks membership of the original token, so a separately created definition with the same ID cannot replace it.

## Computation results

A **result** is data Runtime retains after a computation for later use. The distance `5` produced earlier is a result. It is more than a temporary callback return value and serves three purposes:

- **Host reads**: a UI obtains the published distance through `runtime.result(distance).value` without executing the computation again just to read it.
- **Downstream computations**: the display text computation reads the upstream distance through `view.result(distance).value` and derives text from it.
- **Reuse on the next update**: this computation's `update` receives the old result's private view as `previous`. It can use retained results, indexes or caches to update data; whether this reduces work depends on the algorithm.

Distinguish result data from the configuration with the same name: `result` returned by `run/update` is the data produced by that execution, while `result` in the computation definition supplies capture, read and disposal rules. A simple number can omit that configuration, but the computation still produces and retains a result.

A numeric distance can be stored and read directly. More complex computations may retain indexes, caches or resource handles while exposing only a result. Results therefore distinguish execution output, the internally owned value, a previous-result view for this computation, and a public view.

The figure starts from one callback return and separates two kinds of readers. The private view serves future updates of this computation; the public view serves downstream computations and external consumers. “Next local update” means the next actual incremental callback, not the next external read.

<ComponentPreview files="computation-result" size="md" hideCode type="flow" />

This does not require four copies: the types distinguish responsibilities, while conversion functions decide whether to copy. An internal `{ point, distance }` object can remain available privately while the public view exposes only `distance`, avoiding coupling every reader to the cache structure.

The `result` configuration manages these conversions. `readForComputation` supplies only this computation's next `update` as `previous`; `read` supplies downstream computations, host reads and commit notifications.

<DocTabs defaultValue="members">
<DocTab value="members" label="Properties">

| Member                       | Purpose and default                                                                             |
| ---------------------------- | ----------------------------------------------------------------------------------------------- |
| `capture(input)`             | Converts `run/update` output into a Runtime-owned result; defaults to identity when types match |
| `readForComputation(result)` | Creates the private view for this computation; defaults to identity when types match            |
| `read(result)`               | Creates the public view; defaults to identity when types match                                  |
| `dispose(result)`            | Releases replaced, unpublished or final results on Runtime disposal; no cleanup by default      |

</DocTab>

```ts
  TResultInput,
  TResult = TResultInput,
  TComputationRead = TResult,
  TPublicRead = TResult,

  capture?: (input: TResultInput) => TResult;
  readForComputation?: (result: TResult) => TComputationRead;

```

</DocTab>

For example, retain both the coordinates and distance internally so a later update can inspect them, while exposing only the distance:

```ts
type DistanceCache = Readonly<{ point: Position; distance: number }>;
const cachedDistance = defineRuntimeComputation<DistanceCache, DistanceCache, DistanceCache, number>({
  id: { owner: position.key, key: 'cached-distance' },
  sources: [position],
  result: { read: value => value.distance },
  run: view => {
    const point = view.snapshot(position).value;
    return { kind: 'full', result: Object.freeze({ point, distance: Math.hypot(...point) }) };
  },
});
```

Downstream reads through `view.result(cachedDistance).value` receive only the numeric distance, not `point`. If this computation defines `update`, its `previous` argument is the private object containing both `point` and `distance`, available to decide how to update. Internal cache structures can change without changing consumers as long as the public read still returns a number.

The public read converts an object to a number, so `read` is required. The other conversions preserve types and may be omitted. When all conversions may be omitted and no cleanup is needed, the entire `result` configuration is optional, as in the earlier `distance`. Identity defaults neither copy nor freeze objects. Authors must still preserve read isolation, particularly by never mutating `previous` during an update.

After capture, Runtime creates the private view, then the public view, and caches both. Reading a snapshot does not run those conversions again. A failed read conversion cleans up the newly captured result; an old result is released only after successful replacement. Provide `dispose` for resource cleanup, and use the `bailout` result described next to retain the current result.

## Incremental updates

**The first execution always calls `run`**. Later executions triggered by dependency changes prefer `update` by default, or call `run` if `update` is omitted. A full strategy, an upstream full or fallback execution, or `update` returning `fallback` also leads to `run`. Computations unaffected by dependency changes are skipped.

`update(previous, view, context)` receives the old result's private view and the candidate data. The author chooses how to obtain the correct result. It has three result forms; `run` always returns `full` with a complete new result.

| `update` result                   | Runtime behavior                                                                            |
| --------------------------------- | ------------------------------------------------------------------------------------------- |
| `{ kind: 'incremental', result }` | Captures and prepares a new result, triggering consumers                                    |
| `{ kind: 'bailout' }`             | Retains the old result without conversions or triggering consumers through this computation |
| `{ kind: 'fallback' }`            | Abandons the incremental path and calls `run` on the same candidate data                    |

`incremental` carries a **complete new result** produced by an incremental algorithm, not a patch that Runtime merges with the previous result. `bailout` confirms that the old result remains usable. `fallback` says the incremental method is unsuitable and requests `run` with the same candidate inputs; it does not abandon the update.

This figure covers a computation already executing `update`. A computation skipped because no dependency changed enters none of these branches.

<ComponentPreview files="computation-outcomes" size="lg" hideCode type="flow" />

The fallback `run` must return `{ kind: 'full', result }`; that new result is then captured and propagated too. Throwing is an execution failure, not another form of fallback. Runtime rollback is covered separately.

Adding `update` lets the distance computation retain its result when coordinates change without changing the distance. Replace the earlier `distance` definition with this version; do not register both same-ID definitions:

```ts
const distance = defineRuntimeComputation<number>({
  id: { owner: position.key, key: 'distance' },
  sources: [position],
  run: view => ({ kind: 'full', result: Math.hypot(...view.snapshot(position).value) }),
  update: (previous, view) => {
    const next = Math.hypot(...view.snapshot(position).value);
    return next === previous ? { kind: 'bailout' } : { kind: 'incremental', result: next };
  },
});
```

This example still recalculates the distance to demonstrate propagation; it does not claim a faster algorithm. Runtime has no computation-result `equals` option. Returning `incremental` propagates even when the numeric result is unchanged; the author explicitly chooses reuse.

| Coordinate change  | Distance computation         | Display text computation                 |
| ------------------ | ---------------------------- | ---------------------------------------- |
| `[3, 4] → [3, 4]`  | Equal Source state; skipped  | Skipped                                  |
| `[3, 4] → [-3, 4]` | Still `5`; returns `bailout` | Skipped when no other dependency changed |
| `[3, 4] → [6, 8]`  | Produces distance `10`       | Executes `run`, producing `Distance: 10` |

`bailout` stops only this propagation path. A downstream computation still executes if another dependency changed. A full upstream execution causes downstream full execution; an upstream fallback propagates fallback execution. An explicit full strategy skips incremental attempts without executing wholly unaffected computations.

Each circle below represents a computation; arrows point from an upstream computation to its dependent. The three rows show different updates. Assume no Source directly used by a downstream computation changed, and every blue node produces a new result.

<ComponentPreview files="computation-propagation" size="lg" hideCode type="illustration" />

Orange nodes execute `update` and return `bailout`; gray nodes do not execute at all and reuse their old results. In the last row, A bailing out does not prevent the new result from D from triggering B, whose new result then triggers C. Arrows always represent dependencies, even when they trigger no execution in this update.

`view.changeSet(source)` reads an optional change hint and returns `undefined` when none is supplied. Submitting hints with complete input, validating them and selecting Runtime execution paths will be covered together in the Runtime chapter.

The callback's `context.execution` identifies the execution mode; `context.trace` and `context.diagnose` record observations. `observeCommit` runs after a new result is published successfully and does not run when the old result is reused. It is an isolated observer, not a computation or resource-commit mechanism.

## Complete flow

Define dependencies and execution rules, then let the registry validate and order them. A running instance calls `run/update` when it needs those computations. Result conversions decide what remains available for later updates and what readers can access publicly.

<ComponentPreview files="computation-flow" size="md" hideCode type="flow" />

Inside a computation, `view.result(distance).value` reads the upstream result available for this execution. Outside, `runtime.result(distance).value` reads the published result. Reading does not execute the computation again. Initialization, updates, revisions and publication will be connected in the Runtime chapter; see the [introductory example](/kernel/packages/runtime/usage) for runnable integration code.

## Core application

Core wraps drawing compilation in a Computation. Its public `createCoreComputation(options)` factory returns a compilation token. It consumes the document Source, retains state for incremental compilation internally, and exposes compilation output and a Scene snapshot.

```ts
import { CoreSourceDefinition, createCoreComputation } from '@retikz/core';
import { createRuntimeSourceRegistry, createRuntimeComputationRegistry } from '@retikz/runtime';

const compile = createCoreComputation({});
const sources = createRuntimeSourceRegistry([CoreSourceDefinition]);
const computations = createRuntimeComputationRegistry({ sources, computations: [compile] });
// Pass these registries and the initial document input to createRuntime
// runtime.result(compile).value.output.result.scene is the published Scene
```

This maps to the three responsibilities above: `run` compiles a complete document, `update` tries supported local updates and falls back when inapplicable, and `result` separates internal compiler state from public results. Runtime does not interpret drawing primitives or compilation algorithms. Core supplies those rules, which its own documentation explains in detail.
