画出一条曲线后，你可能想知道它最终使用了哪些控制点。Inspect 可以把这些控制点和辅助线显示出来，但它不重新计算主图，也不修改你写下的绘图描述。下面从主图如何变成可显示的结果开始，说明这些辅助内容从哪里来。

## Inspect 与 Core 的协作

Inspect 不直接分析你写下的绘图代码，而是等待 Core 算出绘图结果，再根据这些结果生成辅助内容。Core 的“编译”是把绘图描述中的坐标、引用和布局等确定下来，生成供 Render 显示的场景数据（Scene）；编译本身不是把像素画到屏幕上。

接入 Inspect 时，你还会选择要观察的对象和观测器。图中左侧保留主图结果，右侧展示启用观测后的辅助支路；两条路径最后汇入 Render，没有从辅助支路返回修改主图的箭头。

<ComponentPreview files="inspect-compile-flow" size="lg" hideCode />

1. **先得到绘图结果。** Core 编译主图，确定图元或组件的最终结果。这里的一次具体出现称为 occurrence（编译后的一个具体实例，同一份定义可以对应多个实例）。
2. **再通知选中的结果。** 支持观测的对象会在 Core 中发布最终产物；Core 把选中实例的位置和产物通知 Inspect。这次通知就是 observation（观测事件），而接收通知的一方称为 observer（观察者）。它不是 Inspect 从画面上反推出来的结果。
3. **生成辅助绘图描述。** Inspect 找到对应的 Inspector（观测器），把结果交给它。观测器返回控制点、辅助线等普通绘图描述，也就是辅助 IR（中间表示），而不是直接操作画布。
4. **单独编译，再一起显示。** Inspect 请求 Core 隔离编译这些辅助描述，得到独立场景。宿主把它们接成只读图层，Render 再与主图一起显示；主图结果保持不变。

理解这条流程后，再看 Core 通过哪些字段把结果和编译能力交给 Inspect。`owner` 标识被观测对象的所属者，request 则是用户发出的观测请求：

| Core 提供的内容                               | Inspect 如何使用                                                           |
| --------------------------------------------- | -------------------------------------------------------------------------- |
| `CompileObservation.owner` 与 `occurrence`    | 让 request 按所属者与实例位置，精确匹配被观测对象的最终实例                |
| `CompileObservation.value`                    | 作为 `subjectSchema` 校验的最终产物，供 `inspect()` 读取                   |
| `CompileObservationContext.theme`             | 为辅助内容分配与当前 occurrence 一致的主题与语义颜色                       |
| `CompileObservationContext.compileFragment()` | 在当前 Theme、Scope 样式和 provider 环境中隔离编译 Inspector 返回的普通 IR |

因此，自定义观测器的前提是：对应对象已经能在 Core 中发布最终产物。仅仅注册一个 Inspector，不会让原本不支持观测的对象自动产生 observation。Core 只提供这套通知与隔离编译能力，不负责查找 Inspector 或决定辅助内容的样式。

当前 Core 的 observation owner 包括：`path`（按名称区分的最终 Path kind）、`node`（Node 的几何与正文布局）、`scope`（Scope 固有包络）、`coordinate`（已解析坐标点）、`clip`（一次逻辑 Clip application）和 `composite`（按命名空间与类型区分的复合组件）。内置 Inspector 分别绑定这些 owner；owner 没有发布最终产物时，注册 Inspector 也不会凭空增加观测。

每条 observation 还带有从外到内排列的 `ancestors`，记录它所在的 Scope / composite 链条及各自 occurrence。Inspector 可以用它解释层级或区分同一 owner 在不同容器中的实例，而不必从 source path 猜测父级。

## 绘制流程

上图描述的是数据流，不代表每收到一次通知就立即画出辅助线。实际执行分为“收集结果”和“生成辅助内容”两个时机：

- **`observe()`：只收集。** Core 派发选中实例的最终结果时，Inspect 保存产物与该实例的上下文，不在这个回调中生成辅助图形。
- **`complete()`：集中生成。** Core 完成最终观测通知后，Inspect 解析选择、合并 options、校验产物，再调用观测器的 `inspect()`。返回的 `IRChild` 经 `compileFragment()` 隔离编译，汇成 InspectionPlane（辅助场景集合）。

一次 compile 中，`observe()` 会按选中的最终 occurrence 调用零到多次；`complete()` 则只在全部通知结束后调用一次。图中三个 occurrence 代表一批最终实例，都会汇入同一个 observer 会话：

<ComponentPreview files="inspect-observer-batch-flow" size="md" hideCode />

之后，宿主将辅助场景集合转换为不可命中的只读图层，由 Render 显示。主图与辅助层属于同一次编译版本，只有一起成功才提交，不会先显示新主图、再补上旧版本的辅助内容。辅助场景也不会保留公开身份、元数据和动画语义。

普通绘图不需要加载 Inspect。启用后，若没有匹配结果或所有观测器都返回空内容，InspectionPlane 为 `null`，不会生成辅助图层；额外成本来自选中对象的观测、观测器回调和非空辅助片段的编译。

`inspect(subject, context)` 还可以调用 `context.warn(code, message)` 报告某个可选几何 facet 无法提供的原因，同时返回其余可用辅助内容。这个 warning 会进入同一次 `InspectionCompileResult.diagnostics`；它不会改写主图，也不会把一个局部缺失升级成整次主编译失败。

## 运行时选择

`request` 是你在场景、authored 子树或对象上声明的一条 Inspect 选择规则。它指定哪个 Inspector 要响应（`inspector`）、哪些最终 occurrence 在范围内（`target`），以及可选参数（`options`）；`true` 使用默认参数，`false` 则在当前位置关闭该 Inspector。

下图以支持整图选择、且对象 owner 匹配的同一个 Inspector 为例。连线表示父子结构；蓝色表示开启，灰色虚线框表示关闭或封锁。A 继承父级开启；B 在子树关闭后可由对象重新开启；C 设置屏障后，对象即使请求开启也无效。开关只影响辅助观测，所有对象的主图仍正常绘制。

<ComponentPreview files="inspect-selection-tree" size="md" hideCode />

这里 B 的 `options: false` 只关闭指定 Inspector，C 的 `barrier` 则封锁子树内全部 Inspector；React 中可用 `<InspectScope request={false}>` 声明这个屏障。

这些选择不是持久化图形数据，而是在每次编译时决定哪些最终 occurrence 交给 Inspector 的运行时规则：

| 结构                              | 含义                                                      |
| --------------------------------- | --------------------------------------------------------- |
| `InspectionSelectionRule` request | 以 `inspector`、`target`、`options` 选择 Inspector 与范围 |
| `InspectionSelectionRule` barrier | 在整图或 authored 子树阻止后代重新开启 Inspector          |
| scene target                      | 匹配整张图中属于指定 owner 的最终实例                     |
| subtree target                    | 匹配一个 authored Scope 下的最终实例                      |
| self target                       | 按来源或 occurrence index 匹配当前对象                    |

对 Path 做批量选择时，scene target 会匹配整张图中所有 owner 相符的最终 Path；subtree target 会匹配某个 authored Scope 子树中的所有 Path；只有 self target（React 的 `<InspectPath>`）才把请求限制到当前 authored Path。因而可以在 `<InspectLayout request>` 上统一打开一类 Path 检查，也可以用 `<InspectScope request>` 只打开一个子树；无需为每条 Path 重复声明同一 request。

Inspector callback 返回的普通 Core IR child 默认使用 occurrence-local 坐标，Inspect 用 `context.transform` 将其放回主 Scene。需要显式指定空间时，返回 `InspectorFragment`：`{ type: 'fragment', coordinateSpace: 'local' | 'scene', child }`。`scene` 片段使用单位变换，同一次回调可混合两种空间；`NODE_INSPECTOR` 的局部几何与 AABB 就共享这一通道。

同一位置可以请求多个不同 Inspector。同一 Inspector 的稀疏 options 从整图到子树再到当前实例合并；普通 `false` 只关闭当前位置的一个 Inspector，barrier 则阻止后代重新开启任何 Inspector。

合并使用作者传入的原始配置，随后由唯一的 `optionsSchema` 补默认值，再交给 `resolveOptions` 展开简写。例如父级 `labels: true`、子级 `{}` 会继续显示标签；子级显式 `labels: false` 才会关闭。每条启用规则仍会在准入时校验，即使未匹配或随后被覆盖也不能携带非法选项。

直接调用 `PathInspectOptionsSchema.parse({})` 会得到包含 `labels: false` 的完整默认快照；再把它作为子级配置时，`false` 就是显式覆盖。保存原始配置才能保留省略意图；保存 parse 结果则保存已物化的默认值。

## 绘制样式

Inspect 的常规辅助颜色按有效观测请求的顺序，从 Core 当前主题的分类色板中选取。同一请求生成的辅助线、控制点与标签共用一种颜色，便于识别它们对应的对象；控制点标签背景透明。

Inspect 沿用 Core 的色板与语义颜色，不提供独立的 Inspect Theme 配色配置。内置观测器也不提供 Core 绘图组件那样自由的样式定制：例如路径观测器只开放控制点、顶点、圆弧几何与标签的显示开关，线宽、虚线和字号由实现统一决定。它的定位是帮助理解主图的辅助内容，因此优先保证清晰、一致与克制。

自定义 Inspector 仍可在返回的普通 Core IR 中定义样式；这是观测器扩展能力，不属于内置观测器的样式选项。

## 结果与错误

| 字段                                  | 含义                                          |
| ------------------------------------- | --------------------------------------------- |
| `InspectionCompileResult.primary`     | 未被辅助内容修改的普通 Core 编译结果          |
| `InspectionCompileResult.inspection`  | 有序辅助平面；所有 callback 无输出时为 `null` |
| `InspectionCompileResult.diagnostics` | 观测器回调与隔离片段产生的结构化警告列表      |

`RetikzInspectError.details.origin.stage` 标明失败发生在选择、最终产物校验、`inspect` callback、输出规范化、辅助片段编译或最终组装。重复 registry key、未注册 request、owner 不匹配以及 schema 失败都会终止该次检查编译，不会交付部分辅助结果。
