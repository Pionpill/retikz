In the [compilation flow](/kernel/packages/core/compilation), Node and Path resolve their effective configuration before their respective geometry stages. This page follows a node and a path in the same Scope through shared style inheritance, theme colors, and definition lookup, then compares the results of `resolveNode` and `resolvePath`.

These mechanisms apply to basic IR entering Core's compiler, including nodes and paths generated by upper packages such as Plot. Those packages still own their domain resolution, such as Plot data and scales; that work is separate from node style resolution.

## Overall flow

A compilation first prepares registries and the root theme. On entering a Scope, traversal merges inherited and local descendant defaults and resolves its local theme. Node and Path read that environment to merge properties, resolve colors, bind definitions, and complete fields, producing `NodeResolution` and `PathResolution` respectively.

## Definition binding

A Definition contains a capability's implementation and parameter contract. `shape: 'rectangle'` in IR is a name; layout needs the rectangle Definition and its resolved parameters. A registry provides that lookup.

`createCompileContext` builds a separate registry for each capability, adding builtins before external definitions from `CompileOptions`. Names must be unique within a registry. An external definition that collides with a builtin also causes an error.

| Registry                | Capability                            | Consumer                                               |
| ----------------------- | ------------------------------------- | ------------------------------------------------------ |
| `shapes` / `boundaries` | Node shapes and connection boundaries | Node configuration resolution                          |
| `patterns` / `clips`    | Pattern paints and clipping           | Corresponding paint or clip resolution and compilation |
| `paths` / `arrows`      | Path definitions and arrows           | Corresponding path and arrow processing                |
| `themeDefinitions`      | Themes                                | Root or local theme resolution                         |
| `composites`            | Composite compilation                 | Traversal of a composite item                          |

After Node styles and defaults are merged, `resolveNodeShape` looks up the effective `shape`, parses parameters with the Definition's `paramsSchema`, and returns `{ name, definition, params }`. An omitted shape selects `rectangle`. `circle` first expands into `ellipse` with equal-dimension parameters, then looks up that definition.

Path looks up a path by `kind`, using builtin `stroke` when the field is omitted. Arrows also use their registry; their binding timing is covered in the Path branch below.

`resolveBoundaryReference` resolves the connection boundary next. It can use the visual shape or bind a separate boundary. Layout receives these results and calls the selected capabilities directly. Unknown names and parameters that violate a Definition's contract fail the compilation.

## Style inheritance

On entering each Scope, `resolveScopeDefaults` merges the parent's effective defaults with the current `defaults` into an `EffectiveScopeDefaults` object with Node, Path, Label, and Arrow channels. Children in that scope share this object. Node's `resolveEffectiveNodeStyle` and Path's `resolveEffectivePath` read their channel and apply the element's own properties without walking ancestor Scopes for each element.

Within each frame, the Scope's general `defaults.style` applies before `defaults.node.style`. The example's `strokeWidth` therefore starts at 1, becomes 2 through node defaults, and ends at 3 through A's own declaration.

P follows the same override order through `defaults.path.style` and also ends with width 3. Both inherit the Scope's master color, but A's default fill does not pass to P, nor does P's default stroke pass to A. The table follows A's fields:

| Field         | Scope / node defaults        | A's declaration | Merged value                    |
| ------------- | ---------------------------- | --------------- | ------------------------------- |
| `color`       | `'#204060'`                  | Omitted         | `'#204060'`                     |
| `fill`        | `0.5`                        | Omitted         | `0.5`, pending color resolution |
| `strokeWidth` | `1`, then `2`                | `3`             | `3`                             |
| `textColor`   | `'#ffffff'`                  | Omitted         | `'#ffffff'`                     |
| `minimumSize` | `{ width: 100, height: 48 }` | Omitted         | Inherited value                 |

Merging skips `undefined`. The `style` and `layout` groups merge by field, while object fields such as `font` and `padding` replace the whole previous value. For example, an outer font of `{ family: 'serif', size: 14 }` followed by an inner `{ size: 18 }` leaves only `{ size: 18 }` after inheritance. Later font resolution supplies missing defaults.

`position` always comes from the node itself. Defaults describe shared appearance and sizing without placing every node at an inherited default position.

### Inheritance barriers

A Scope's `defaults.reset` cuts selected style channels. With `['node']`, Scope entry clears inherited node defaults, styles, and layout properties before applying the current Scope's configuration. `true` cuts every style channel. Path, Label, and Arrow have their own channels too.

This barrier controls style inheritance. The theme travels through a separate context chain; `reset` neither restores Light mode nor clears capability registries.

A child Scope derives a new effective configuration without changing its parent; unchanged channels can be shared. Primary-color expansion into fill, stroke, and text, and host-color handling for Label and Arrow, still happen during element resolution. The Scope frame inherits the shared primary color separately, unaffected by element-channel `reset`.

## Theme resolution

The theme records the current theme name, mode, and shared colors. `resolveTheme` inherits `name` and `mode` independently. A local Scope specifying only `mode: 'dark'` keeps the parent theme name and regenerates shared colors for that mode. If both selectors remain unchanged, resolution reuses the parent theme.

`theme.name` names a `ThemeDefinition`, looked up in `themeDefinitions` and evaluated through `resolve({ mode })`. Without a selected style, Core supplies default colors for the mode. A node's `style` instead holds properties such as fill and stroke; it serves a different purpose from the theme selector.

Shared theme colors are available to their consumers. Basic node resolution takes `mode` from the theme and combines it with the effective node master color to resolve numeric colors. It does not copy the entire theme color table into node styles. If an upper component generates node styles from a theme, those fields subsequently enter Core resolution as ordinary IR styles.

### Style properties

Style properties have two distinct roles:

| Category                | Role                                                                | Examples                                     |
| ----------------------- | ------------------------------------------------------------------- | -------------------------------------------- |
| Direct style properties | Specify the appearance of a particular drawing part                 | `fill`, `stroke`, `textColor`, `strokeWidth` |
| Base style properties   | Supply defaults or a calculation basis for multiple specific styles | `color`                                      |

`color` is the base color: it supplies omitted colors and provides the basis for numeric colors. It does not override explicitly specified colors. Direct style properties can still require resolution. For example, `fill: 0.5` specifies a fill whose actual color must be calculated from the base color.

After style merging, Node uses `color` to supply missing `fill`, `stroke`, and `textColor`, leaving existing values unchanged. Path does not apply this set of fallback rules: its own resolution result and emitter handle omitted drawing values. Both use the base color and theme mode to resolve numeric colors.

<ComponentPreview files="style-properties" size="lg" hideCode type="flow" />

This step determines which value each property uses; later steps resolve it according to its type. `color` neither overrides existing direct styles nor supplies non-color properties such as `strokeWidth`.

### Numeric resolution

In this page's example, Node retains the explicit `fill: 0.5` and white text, while the missing `stroke` becomes `'#204060'`.

A numeric color uses the final base color as its foreground, blending it with the mode's backdrop at the given weight. Light uses white; Dark uses black. The result is an opaque color string.

<ComponentPreview files="numeric-resolution" size="lg" hideCode type="flow" />

The path's `stroke: 0.5` calls the same `resolveContextualColor` and matches the node's fill.

| The same A | Input `fill` | Resolved `fill` | `stroke`    |
| ---------- | ------------ | --------------- | ----------- |
| Light      | `0.5`        | `'#90a0b0'`     | `'#204060'` |
| Dark       | `0.5`        | `'#102030'`     | `'#204060'` |

This does not set `fillOpacity` to 0.5. The renderer receives the blended color. Use the corresponding opacity property to reveal the actual background. String colors retain their original value. Numeric colors fail if the base color is missing or cannot be parsed statically.

Node resolution determines fill and stroke before handling `textColor: 'contrast'`, so contrast selection can read the actual fill. Derived colors for body lines, runs, labels, and pins follow. This example explicitly supplies white text and does not invoke automatic contrast.

## Paint resolution

`fill` and `stroke` describe the paint used for the interior and outline. Either can be a solid color, a gradient, or a pattern. Unlike a numeric property such as `strokeWidth`, paint may require a bound drawing capability and resources generated during compilation. Node and Path therefore both call `resolvePaint` for these two fields.

Color resolution determines a concrete color. Paint resolution prepares the drawing description and binds any capabilities it needs.

| Property value                          | Resolution                                                                           | Result                                      |
| --------------------------------------- | ------------------------------------------------------------------------------------ | ------------------------------------------- |
| Solid color string, such as `'#204060'` | `resolvePaint` returns it unchanged                                                  | Color string                                |
| Numeric color, such as `0.5`            | Resolve it to a color using the preceding rules, then resolve paint                  | Color string                                |
| Gradient object                         | Preserve the gradient description inside a `PaintResolution`                         | `{ kind: 'paint', spec }`                   |
| Pattern object                          | Bind a Pattern Definition from the registry, supply its size, and resolve its styles | `PaintResolution` with `spec` and `pattern` |

<ComponentPreview files="paint-resolution" size="xl" hideCode type="flow" />

For example, a solid fill requires no registry lookup. A pattern fill must determine which Definition generates the pattern and which size and styles it uses. `resolvePaint` applies the same rules to fill and stroke.

These results are still compilation inputs. Generating, deduplicating, and registering gradient and pattern resources, and referencing them from Scene primitives, belong to later resource compilation. See [Resources in Compilation Output](/kernel/packages/core/compilation-output#resources) for those steps.

## Defaults and results

Node and Path both turn sparse declarations into compilation inputs, but complete different fields and bind different capabilities. The branches below use the inheritance and color rules already described.

### Node

Once effective colors are determined, `expandNodeFields` expands compact values into fields that downstream code can read directly: a text string becomes a line array, scale gets x / y values, minimum size gets width / height, and spacing gets four sides. It also collects the IR `style` and `layout` fields into `CanonicalNode`.

Defaults materialize at their corresponding stages. Position uses the schema field default, node padding is supplied during field expansion, and a Definition's schema handles shape parameters. Merging sparse declarations before applying defaults preserves parent values that were not overridden. If schema parsing has already materialized default fields in the input, those fields participate in later merging as existing values.

After shape and boundary binding, the results of `resolvePaint` are stored in `CanonicalNode.fill` and `CanonicalNode.stroke`.

The example's `NodeResolution` has four fields:

| Field      | Content                                              | Downstream use                               |
| ---------- | ---------------------------------------------------- | -------------------------------------------- |
| `irPath`   | Source path of the node                              | Diagnostics and location                     |
| `node`     | Merged, expanded `CanonicalNode` with resolved paint | Properties for layout and primitive emission |
| `shape`    | Shape name, Definition, and parameters               | Outer-box measurement and shape emission     |
| `boundary` | Resolved connection boundary                         | Anchors and path connections                 |

```ts
// Selected CanonicalNode fields
{
  id: 'A',
  position: [0, 0],
  text: ['A'],
  color: '#204060',
  fill: '#90a0b0',
  stroke: '#204060',
  strokeWidth: 3,
  textColor: '#ffffff',
  minimumSize: { width: 100, height: 48 },
  scale: { x: 1, y: 1 },
  align: 'middle',
  rotate: 0,
}
```

`CanonicalNode` is an internal resolved result and can carry bound paint capabilities. It still retains position expressions for layout to resolve and has no final text dimensions or outer box. `compileResolvedNode` receives `NodeResolution` and combines it with measurement capabilities and position context to produce separate layout, paint, and identity metadata.

### Path

`resolvePath` obtains effective styles and resolves contextual colors for Path, Label, and Arrow. `resolvePathDefinition` then looks up the Definition by `kind`, using builtin `stroke` when omitted. Unlike a shape Definition that parses `params`, a path Definition parses the full path declaration through its `schema`.

That schema may supply fields, so contextual colors are resolved again afterward. `canonicalizePath` then expands path fields: it collects `style` fields into the path, turns labels into arrays, and supplies static defaults for label placement and steps such as bend and smooth. The result is not yet final drawing commands.

P inherits master color `'#204060'`; its stroke resolves to `'#90a0b0'` in Light mode, with width 3. Its two absolute-coordinate steps retain their positions. `resolvePath` also binds targets, records `irPath`, and writes resolved paint and effective stroke width into `CanonicalPath`. The compile context supplies the transform chain. Target references and relative coordinates belong to the path geometry topic.

| Field                | Content                                                                  | Downstream use                      |
| -------------------- | ------------------------------------------------------------------------ | ----------------------------------- |
| `path`               | `CanonicalPath` with resolved paint, effective styles, steps, and labels | Main path compilation input         |
| `kind`               | Kind name, Definition, and schema result                                 | Invoke the selected path capability |
| `irPath` / `targets` | Source path and target bindings                                          | Diagnostics and subsequent geometry |

```ts
// Selected PathResolution fields
{
  path: { id: 'P', color: '#204060', stroke: '#90a0b0', strokeWidth: 3 },
  kind: { name: 'stroke' },
}
```

Path likewise stores resolved paint in its Canonical object, as `path.fill` and `path.stroke`.

Label appearance comes from the Label channel; path canonicalization supplies static placement configuration. Arrow defaults come from the Arrow channel. Its master color resolves first, then supplies the basis for its fill. The builtin Stroke emission chain subsequently calls `resolveStrokePathProviders` to supply omitted fill and stroke as `none` and `currentColor` and bind Definitions for the arrow marks it consumes. This produces `StrokePathResolution` with an `arrows` map. Those bindings are absent from the base `resolvePath` result. This example has no arrows, so the map is empty.
