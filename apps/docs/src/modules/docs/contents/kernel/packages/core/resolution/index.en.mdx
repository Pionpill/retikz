The [Core overview](/kernel/packages/core) distinguishes drawing declarations, atomic compilation stages and Reconciler's scheduling role. This page starts with a node's `shadow: 'md'` and follows Schema constraints, field descriptions and resolve into a shadow configuration that downstream stages can consume directly.

The endpoint here is a structure whose semantics are determined enough to continue compilation. Text dimensions, final node placement and intersections with connection boundaries require later layout and geometry evaluation.

## Overall flow

IR is the drawing declaration an author stores or supplies. Schema defines its permitted structure. When the required defaults and capability context are available, resolve expands the different forms into Canonical data or a Resolution carrying additional binding information.

The diagram distinguishes two input sources: external data such as JSON first passes through Schema validation; typed TypeScript declarations can enter resolution directly. Arrows show data handoffs, not a mandatory global Schema pass at the start of every compilation.

## IR and Schema

This node declaration stores drawing intent: node A uses a medium shadow preset and contains the text A.

```json
{
  "type": "node",
  "id": "A",
  "text": "A",
  "style": { "shadow": "md" }
}
```

IR is the shared specification that all DSLs ultimately follow. It is 100% representable as JSON and is defined and managed through Zod Schemas.

Schema allows some fields to be omitted and defines input validation rules. External data receives structural validation at the Schema entry point. Resolve then applies defaults using the current context and checks semantic constraints.

To simplify declarations, Schema retains some syntactic sugar, such as `shadow: 'md'`. Resolve expands it into an internal data structure containing offsets, blur and color for later compilation.

## Describing semantics

A type can say that `offsetY` is a number. Readers also need its units, the direction of positive values, and which value wins when it accompanies a preset. Schema fields record this information through `.describe()`.

For example, `DropShadowSchema` describes `offsetY` as follows:

```ts
offsetY: number()
  .optional()
  .describe('Vertical shadow offset in user units (overrides preset); positive = downward under screen y-down.'),
```

This description supplies units, precedence and coordinate direction. Together with the description of `preset`, it tells a caller or LLM that `{ preset: 'md', offsetY: 8 }` retains the other medium-preset values while moving the shadow downward by 8.

A description should answer concrete questions about a field:

| Question                                | Shadow example                                                                     |
| --------------------------------------- | ---------------------------------------------------------------------------------- |
| What does the value mean?               | `preset` supplies offsets, blur and color                                          |
| What are its units and reference frame? | Offsets use user units; positive y points down in screen coordinates               |
| How do fields combine?                  | Explicit fields override corresponding preset values                               |
| What does omission mean?                | Omitting the shadow disables it; an object without a preset needs explicit offsets |

`.describe()` is semantic metadata for people and tools; it does not execute these behaviors. Schema constrains the structure, the resolver expands presets and applies overrides, and compilation and rendering produce the effect. Descriptions can guide generation and calls only when those parts agree.

## From shorthand to determined values

For authors, `'md'` selects a coordinated set of shadow parameters. Downstream drawing stages need offsets, blur and color without repeatedly branching on strings and objects.

The internal node-resolution helper `resolveDropShadow` performs this conversion. Only the shadow field of the same node is shown below:

<DocTab value="source" label="Source IR">

```json
{ "shadow": "md" }
```

</DocTab>
<DocTab value="canonical" label="Canonical">

```json
{
  "shadow": {
    "offsetX": 0,
    "offsetY": 3,
    "blur": 6,
    "color": "rgba(0,0,0,0.12)"
  }
}
```

</DocTab>
<DocTab value="override" label="Explicit override">

```json
{ "shadow": { "preset": "md", "blur": 10 } }
```

The resolved result keeps the same offsets and color, changes `blur` to 10, and no longer carries `preset`.

</DocTab>
</DocTabs>

These values come from Core's current shadow preset table. With explicit offsets, the resolver does not look up a preset and supplies a default color when none is provided. Omission and `'none'` produce no shadow configuration.

Author-facing expressions and compilation inputs are each first-class within their stage: IR expresses intent, while Canonical data supports computation. Shadow shorthand is a supported IR capability. Expanding it before drawing gives downstream consumers one consistent interpretation.

This division follows one principle: IR is written by humans and generated by LLMs, so its expressions should stay simple and reduce cognitive load. Canonical values feed directly into compilation, so they require rigorous structure, unambiguous semantics and the invariants of their stage.

## Merge before applying defaults

A node can also inherit Scope defaults. Reconciler supplies the effective defaults to `resolveNode`, which merges them before expanding fields and applying the corresponding defaults. This prevents early completion from hiding inherited values.

Consider stroke width: shared Scope style supplies 1, node defaults supply 2, and A supplies 3. The result is 3. If A omits the field, the inherited 2 remains. This selects the effective declaration before field defaults and value conversions take place.

`undefined` does not override inherited values, but defaults already materialized by Schema participate as actual values. Parsed external input and an author declaration retaining omitted fields can therefore behave differently in later inheritance. Repeatedly parsing complete objects at every layer does not preserve the original omission intent.

Merging is not universally recursive. A shadow configuration overrides as one style field; a node's own shadow object does not automatically receive individual properties from its parent's shadow object. To modify one property of a preset, the node should name that `preset` in its own object. Font and opacity have their own merge rules.

## Resolution results and compilation boundaries

Shadow illustrates value expansion without looking up another object. Other fields require semantic context. A shape name, for example, must select a Definition from the current registry and resolve parameters against that definition's contract. A Definition is a capability implementation contract; a registry indexes definitions by name.

These runtime capabilities do not become part of persistent IR. A resolution result can carry the selected Definition, parameters and paint capabilities for later stages to consume. Registration and extension implementation are covered by the capability registration topics.

Not every field needs expansion. A node's `id: 'A'` retains its identity meaning, and an explicit numeric stroke width becomes the effective width after merging. Resolve handles shorthand, defaults, precedence or context where needed, without inventing another representation for values that are already determined.

| Expression or product | What resolve determines                                   | What remains                                      |
| --------------------- | --------------------------------------------------------- | ------------------------------------------------- |
| `shadow: 'md'`        | Concrete shadow configuration                             | Backend presentation through primitives           |
| `shape: 'rectangle'`  | Shape definition and parameters                           | Shape dimensions and boundaries based on content  |
| Numeric color         | Color based on effective master color and theme mode      | Drawing with the determined paint                 |
| Relative position     | Defaults such as distance, retaining the target reference | Reading target layout and evaluating coordinates  |
| `CanonicalNode`       | Layout intent, effective styles and capability bindings   | Text measurement, layout and primitive generation |

Canonical means the domain input form has been determined, not that every result is already numeric. Final node dimensions depend on text measurement, and reference positions depend on target geometry. These belong to later compilation. Text, shadow or an explicit width can remain absent because absence or layout-driven sizing carries meaning.

Schema and resolve also have different validation boundaries. External structure is checked once at its Schema entry. A resolver checks invariants that emerge after merging and actual context errors. A node width smaller than an inherited minimum width, for example, can only be detected once effective configuration is available. An unknown shape likewise requires the current registry.
