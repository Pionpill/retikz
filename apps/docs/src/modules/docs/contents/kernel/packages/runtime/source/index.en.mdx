The [starter example](/kernel/packages/runtime/usage) stores a number, so returning the original value is enough. Now consider a coordinate form: its fields provide strings, `{ x: '10', y: '20' }`, while readers need numeric coordinates. After submitting the object, the caller changes its `x` to `'99'`. Should the state already published by Runtime change too?

It should not. Otherwise, readers would see new contents without an `update`, while dependent computation results would still reflect the old contents. This page follows that position to explain how external input becomes state that Runtime can safely retain, and when that state is kept, replaced or released.

A **Source** is a definition that tells Runtime how to receive and manage a particular kind of complete state. Our Source owns the position itself; derived results such as its distance from the origin belong to a Computation, introduced in the starter example. The Source definition is not an individual submitted object, and it does not automatically watch the form for changes.

## Overall flow

First distinguish three representations: the caller's input, the value held internally by Runtime, and the view given to readers. A **view** here means the data representation readers may access, not a UI component. Follow the same position below: text fields become internal numbers, then a read-only `[x, y]` tuple.

<ComponentPreview files="source-values" size="xs" hideCode type="flow" />

All three representations describe the same position. Internal storage and the read view both display `[10, 20]`, but use separate arrays, and the read view is read-only:

| Representation | Example data                      | Purpose                                                                                     |
| -------------- | --------------------------------- | ------------------------------------------------------------------------------------------- |
| Form input     | `{ x: '10', y: '20' }`            | Input fields provide text; named fields make submission straightforward                     |
| Internal value | `[10, 20]`, ordinary tuple        | Convert to numbers and store them independently; index 0 is x and 1 is y                    |
| Read view      | `[10, 20]`, frozen ordinary array | Readers receive an independent read-only `[x, y]` tuple, without sharing the internal array |

`capture` converts strings to numbers and allocates independent storage. `read` copies the two numbers into a read-only tuple. The position has the same meaning throughout; its representation and access rules change. When no separate representation or isolation is needed, all three types can be the same.

## Capture and reading

### Defining a Source

`defineRuntimeSource(input)` defines a kind of state source. It accepts one configuration object and returns a Source token preserving the input, internal value, read value and change-hint types. Defining it does not capture data.

```ts
declare const defineRuntimeSource: <TInput, TValue, TRead, TChange>(
  input: RuntimeSourceDefinitionInput<TInput, TValue, TRead, TChange>,
) => RuntimeSourceDefinition<TInput, TValue, TRead, TChange>;
```

`defineRuntimeSource` accepts the following configuration members. The `value` object contains the rules for capturing, reading, comparing and disposing state:

<DocTabs defaultValue="members">
<DocTab value="members" label="Properties">

| Member              | Required | Purpose                                                                                 |
| ------------------- | -------- | --------------------------------------------------------------------------------------- |
| `key`               | Yes      | The nonempty Source registration key, `example/position` here                           |
| `value.capture`     | Yes      | Convert input into the internal value retained by Runtime                               |
| `value.read`        | Yes      | Produce an immutable view for external readers from the internal value                  |
| `value.equals`      | Yes      | Compare two complete internal values and return whether they are equal                  |
| `value.dispose`     | No       | Release resources held by the internal value; unnecessary here                          |
| `collectIdentities` | No       | Accept the internal value and return all entity identities; omitted means no collection |
| `validateChangeSet` | No       | Accept previous/next read views and a change hint; return `valid` or `fallback`         |

</DocTab>
<DocTab value="definition" label="Type definition">

```ts
type RuntimeSourceValueDefinitionInput<TInput, TValue, TRead> = Readonly<{
  capture: (input: TInput) => TValue;
  read: (value: TValue) => TRead;
  equals: (left: TValue, right: TValue) => boolean;
  dispose?: (value: TValue) => void;
}>;

type RuntimeSourceDefinitionInput<TInput, TValue, TRead, TChange> = Readonly<{
  key: string;
  value: RuntimeSourceValueDefinitionInput<TInput, TValue, TRead>;
  collectIdentities?: (value: TValue) => ReadonlyArray<RuntimeIdentity>;
  validateChangeSet?: (previous: TRead, next: TRead, changeSet: RuntimeChangeSet<TChange>) => 'valid' | 'fallback';
}>;
```

</DocTab>
</DocTabs>

Define the coordinate Source as follows:

```ts
import { defineRuntimeSource } from '@retikz/runtime';

type PositionInput = { x: string; y: string };
type PositionValue = [number, number];
type PositionRead = readonly [number, number];

const position = defineRuntimeSource<PositionInput, PositionValue, PositionRead, never>({
  key: 'example/position',
  value: {
    capture: input => [Number(input.x), Number(input.y)],
    read: value => Object.freeze([value[0], value[1]] as const),
    equals: (left, right) => Object.is(left[0], right[0]) && Object.is(left[1], right[1]),
  },
});
```

The first three type parameters correspond to the input, internal value and read view:

| Parameter | Type in this example | Consumer                                                               |
| --------- | -------------------- | ---------------------------------------------------------------------- |
| `TInput`  | `PositionInput`      | The caller submits complete input to `capture`                         |
| `TValue`  | `PositionValue`      | Runtime retains it; `read`, `equals` and optional `dispose` receive it |
| `TRead`   | `PositionRead`       | Read `[x, y]` through a Snapshot, typed as `readonly [number, number]` |

The fourth type parameter describes change hints; `never` means this example provides none. Resource cleanup and the two optional callbacks are explained later.

The returned `position` is a definition token identifying this Source; it does not expose the callbacks directly. Runtime stores the associated rules internally, and registration, submission and reading reuse this token. No input data exists yet, so defining the Source neither invokes `capture` nor creates state.

### Source registration

Defining a Source describes how a kind of state is captured, read and disposed. A Runtime also needs to know which Sources it will use. **Source registration** collects the selected definitions into a **Source registry**, the set of state Sources that Runtime can manage.

For example, `position` defines how coordinate data is handled. Adding it to the registry lets Runtime locate those rules and check that a Source used later is registered. The registry holds definitions; actual coordinate data is supplied separately when Runtime is initialized or updated. Registration itself does not capture state.

`createRuntimeSourceRegistry` accepts an array of Source tokens and registers the definitions Runtime may use:

```ts
declare const createRuntimeSourceRegistry: (tokens: Array<RuntimeSourceToken>) => RuntimeSourceRegistry;
```

Returns the newly created Source registry.

| Item     | Description                                                  |
| -------- | ------------------------------------------------------------ |
| `tokens` | Required Source token array; pass `[]` for an empty registry |

The registry handles every Source in the array uniformly, without distinguishing built-in and custom Sources. Callers organize and merge those groups when needed. Any duplicate `key` is rejected, including the same token supplied twice. No Sources are loaded automatically.

```ts
// Method signature on the returned object
find: (key: string) => RuntimeSourceToken | undefined;
```

Look up a string key; return `undefined` if absent. The generic token does not retain a particular Source's input and read types

```ts
// Method signature on the returned object
resolve: <TInput, TValue, TRead, TChange>(definition: RuntimeSourceDefinition<TInput, TValue, TRead, TChange>) =>
  RuntimeSourceDefinition<TInput, TValue, TRead, TChange>;
```

Confirm that this exact definition is registered and return it unchanged, preserving generic types. A different object with the same name throws

```ts
// Method signature on the returned object
definitions: () => ReadonlyArray<RuntimeSourceToken>;
```

List definitions in stable string order by `key`; the returned list cannot modify the registry

Register the `position` defined above:

```ts
import { createRuntimeSourceRegistry } from '@retikz/runtime';

const sources = createRuntimeSourceRegistry([position]);

console.log(sources.find('example/position') === position); // true
console.log(sources.resolve(position) === position); // true
console.log(sources.definitions().map(source => source.key)); // ['example/position']
```

Registration iterates over the supplied token array, checks token validity and key uniqueness, and associates each definition with its handling rules. The resulting registry is fixed: it exposes no append or replace operation.

Resolving a newly created same-name Source fails because its token differs. Registering it alongside `position` fails because the key is duplicated. These are respectively membership checks during use and uniqueness checks during construction.

### Connecting to Runtime

The Source registry now identifies the available definitions. Next, supply the initial coordinates and create a Runtime instance. This example has no derived computations; it creates an empty Computation registry bound to `sources` as required for initialization. Computation definitions and registration will be covered in “Derived Computation and Incremental Updates”.

The APIs below pair the initial data with its Source and create the instance. Transactions and version publication are covered separately.

```ts
declare const createRuntimeSourceInput: <TInput, TValue, TRead, TChange>(
  source: RuntimeSourceDefinition<TInput, TValue, TRead, TChange>,
  value: TInput,
) => RuntimeSourceInput;
```

Return an initial input command pairing a Source with data; no capture occurs yet.

| Item     | Description                            |
| -------- | -------------------------------------- |
| `source` | the Source definition, `position` here |
| `value`  | complete input data, `input` here      |

```ts
declare const createRuntime: (options: RuntimeOptions) => Runtime;
```

Capture initial input and return a Runtime instance for updates, reads and disposal.

The same `sources` registry is used to create the computation registry and passed to Runtime. `createRuntimeSourceInput` only pairs a definition with data; `capture` and `read` run during Runtime initialization. Append the following code to the definition above, leaving out derived computations to observe input isolation:

```ts
import { createRuntime, createRuntimeComputationRegistry, createRuntimeSourceInput } from '@retikz/runtime';

const input = { x: '10', y: '20' };
const computations = createRuntimeComputationRegistry({ sources });
const runtime = createRuntime({
  sources,
  computations,
  initialSnapshots: [createRuntimeSourceInput(position, input)],
});

try {
  input.x = '99';
  console.log(input); // { x: '99', y: '20' }
  console.log(runtime.snapshot(position).value); // [10, 20]
  const [x, y] = runtime.snapshot(position).value;
  console.log(x, y); // 10 20
} finally {
  runtime.dispose();
}
```

The output shows that changing the original input's `x` leaves Runtime's coordinates at `[10, 20]`. This is because `capture` stored the coordinates independently, and `read` provided a read-only copy. The result contains x followed by y and can be destructured as `[x, y]`.

### Preparing state

Creating Runtime in the example first invokes an internal `prepare` operation to turn input into managed state. Updates use the same process:

1. Call `capture` to obtain the internal value retained by Runtime.
2. If a disposal callback exists, check whether the new value directly reuses the current internal value, preventing cleanup from releasing resources still in use.
3. If `collectIdentities` exists, collect entity identifiers and validate their Source ownership and uniqueness. Their purpose is explained under “Identities and change hints”.
4. Call `read` to produce the read-only view exposed to readers.

Once all steps succeed, the executor stores the internal value, read view and optional identity lookup in a **prepared record**. Subsequent Snapshot reads use its existing view instead of invoking `read` again.

A prepared record is the internal representation used to manage state, not necessarily unpublished state. A newly prepared record can be a candidate and remain in use as current state after adoption. The enclosing Runtime decides whether to adopt and publish it.

Preparation invokes rules and manages state; it does not automatically isolate arbitrary input data. The example's input, internal value and read view are independent because its `capture` and `read` callbacks each create separate data.

The preceding sections describe individual callback responsibilities. In the implementation, `createRuntimeSourceExecutor` organizes them into a lifecycle manager bound to one Source registry. It invokes only registered Source rules and tracks which Source owns each prepared record and whether the record remains usable. Creating the executor does not capture input.

<ComponentPreview files="source-lifecycle" hideCode type="flow" />

`prepare` captures the value, optionally collects identities and creates the read view; `compare` calls the definition's `equals`. Equal values lead to candidate cleanup. Different values proceed to Runtime's update flow: success adopts the new value and cleans up the old one, while failure cleans up the candidate. “Hand to Runtime” includes downstream computation and transaction publication, whose orchestration is outside this page's scope.

`RuntimeSourceExecutor` provides four operations as an internal execution mechanism. Application code does not need to create or call it directly:

| Operation           | Responsibility                                                                      |
| ------------------- | ----------------------------------------------------------------------------------- |
| `prepare`           | Prepare complete input as an internal value, read view and optional identity lookup |
| `compare`           | Check records, then compare their internal values using `equals`                    |
| `validateChangeSet` | Check records, then validate change hints against their read views                  |
| `retire`            | Mark a record unusable before attempting to release its internal value              |

Cleanup responsibility depends on where execution failed. Callback exceptions become Runtime errors carrying the Source, phase and original cause. Cleanup failures become diagnostics so that they do not replace the primary error:

| Failure point                                      | Cleanup responsibility                                                                                                         |
| -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `capture` before returning                         | The callback cleans up resources it acquired; the executor has not received an internal value                                  |
| Identity collection, identity validation or `read` | The executor attempts to release the captured value; no usable prepared record is produced                                     |
| `equals`                                           | The executor wraps the error; the enclosing Runtime cleans up candidates                                                       |
| Change-hint validator                              | The executor immediately cleans up the candidate and throws an error preserving the original cause                             |
| Disposal callback                                  | The executor returns diagnostics so the caller can continue other cleanup; the record remains unusable with no automatic retry |

The executor manages individual Source state lifecycles. Cross-Source updates, candidate adoption, atomic publication and transaction rollback belong to the enclosing Runtime.

## State comparison

In the coordinate example above, the initial input is `{ x: '10', y: '20' }`, and Runtime captures it as the initial value `[10, 20]`. Suppose we now submit `{ x: '10.0', y: '20' }`. The text for x has changed, but conversion still produces position `(10, 20)`. Comparing input text, or two newly allocated internal arrays with only `left === right`, would incorrectly treat this as a state change.

`equals` compares the **meaning of two complete internal values**. This example compares x and y in the two internal tuples. Its arguments are `TValue`, not input objects or read views.

Runtime captures the next input and creates its read view before comparing internal values. This prepared but unpublished state is a **candidate**. Both input arrows below carry `TValue`; the comparison determines whether to keep the candidate for the update:

<ComponentPreview files="source-comparison" hideCode type="flow" />

A next internal value of `[10, 20]` takes the `true` branch; `[13, 20]` takes the `false` branch, but replaces the previous state only after a successful update:

| Next input               | Equality result | Treatment of this Source's state                                                  |
| ------------------------ | --------------- | --------------------------------------------------------------------------------- |
| `{ x: '10.0', y: '20' }` | Equal           | Keep the old state and clean up the unused candidate                              |
| `{ x: '13', y: '20' }`   | Different       | Keep the candidate for the update; replace old state after successful publication |

Equality means this Source has not changed, not that every other Source in the same submission is unchanged. The comparison must cover the full meaning that downstream computations rely on. Ignoring a relevant field can incorrectly preserve old state and results.

Before invoking `equals`, the executor's `compare` checks that both prepared records belong to this executor and the specified Source and are still usable. It only returns the comparison result; the enclosing Runtime orchestrates the retention, cleanup and update branches in the diagram. If `equals` throws, the executor wraps the error and leaves candidate cleanup to Runtime.

This example copies data to isolate it. Immutable data that needs no exclusive disposal can also be shared. The requirement is that external changes cannot bypass the update flow and affect published state.

## Resource cleanup

Our position uses ordinary JavaScript memory reclaimed by garbage collection, so no `dispose` callback is needed. Internal values containing bitmaps, subscriptions or other resources may need explicit cleanup. Provide `dispose(value)` to tell Runtime how to release its retained `TValue`.

**Ownership** here means responsibility for a resource's lifetime and eventual release. For example, a Source that exclusively owns an `ImageBitmap` could call `value.bitmap.close()` from its disposal callback. Its read view should expose only data readers need and may safely retain, rather than handing out that closable resource handle.

Cleanup happens at more points than shutting down the whole Runtime:

| Situation                                                 | Value to clean up                           |
| --------------------------------------------------------- | ------------------------------------------- |
| Candidate equals the old value                            | Unused candidate                            |
| Capture returned, but later preparation or updating fails | Created candidate resources being abandoned |
| Successful update replaces old state                      | Old value that is no longer used            |
| `runtime.dispose()` is called                             | Current values still held by Runtime        |

When `dispose` is defined, old and new states need to own their disposable resources independently. Otherwise, discarding a candidate could release resources still used by the old state. Runtime rejects candidates that directly reuse the current internal value; definition authors must also avoid sharing underlying resources that require exclusive disposal.

If `capture` throws before returning, Runtime has not received a value it can clean up. The callback must release resources it has already acquired. If `capture` has returned and identity collection or `read` later fails, the lifecycle executor attempts to dispose the captured value while preserving the original failure.

If disposal itself fails, Runtime records a diagnostic and continues cleaning up other values while preserving the original failure.

The implementation calls stopping use of a prepared state and attempting to release it `retire`. It checks ownership and usability, marks the record unusable, then invokes the disposal callback. Even if disposal fails, that record cannot be compared, used for hint validation or retired again. Each record gets one disposal attempt, without automatic retries. With no disposal callback, the record still becomes unusable.

## Identities and change hints

The position needs no additional callbacks. But a state containing a graph of nodes may need to distinguish “the same node changed color” from “an old node was deleted and replaced”. An **identity** identifies the same entity across updates.

`collectIdentities(value)` collects these identities from the complete internal value. Each identity contains its Source's `owner` and domain-defined `path` segments. For example, `{ owner: 'example/graph', path: ['nodes', 'A'] }` identifies node A in that graph. A color change preserves its identity. The callback collects all identities, not just changed nodes. Runtime collects them after `capture` and before `read`, checks Source ownership and duplicates, and builds a lookup. Omitting the callback does not automatically create that lookup.

A separate question is whether callers that already know what changed can pass that information to incremental computation. A **ChangeSet** is an optional hint containing its base version, `baseRevision`, and a domain-defined `changes` list. It accompanies complete next input and cannot replace it.

For example, if the read view changes from `[10, 20]` to `[13, 20]`, a hint could say “x increased by 3”. To accept such hints, replace the fourth type parameter, `never`, with a suitable change type. You can also provide `validateChangeSet(previous, next, changeSet)` to check the hint against the previous and next read views. Here it should confirm that x increased by 3 and y stayed unchanged. Note that `equals` compares internal values, while this callback checks read views.

| Return value | Judgment                               | Subsequent behavior                                                                                                 |
| ------------ | -------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| `valid`      | The hint may be passed to computations | Incremental computation may be attempted, but is not guaranteed to succeed                                          |
| `fallback`   | The hint cannot be confirmed reliable  | Discard the hint, use a full fallback path for computations directly depending on this Source, and record a warning |

`fallback` discards the hint while allowing the complete new input to be processed. When the callback is omitted, the executor returns `valid`: the Source layer does not block the hint, but has not proven it correct. The Computation still decides whether it can use it.

Like comparison, validation first checks both records' ownership and usability. Failure handling differs: if the validator throws, the executor immediately retires and cleans up the candidate before throwing a wrapped error. It does not release the previous state. If cleanup also fails, its diagnostics are attached to the validation error, preserving the original failure.

This section introduces only the two optional Source callbacks. See [Identity](/kernel/packages/runtime/identity) for identity structure, comparison and lookup. Incremental use of change hints and version constraints will be covered in the planned “Derived Computation and Incremental Updates” and “Transactions and Version Publication” pages.

## Complete flow

Connect the APIs described above: define a Source to obtain its token, register it, pair the token with initial data, then pass the resulting inputs to `createRuntime`. The empty Computation registry satisfies this example's initialization requirements.

<ComponentPreview files="source-registration" size="sm" hideCode type="flow" />

The registry holds handling rules while the initial-input command carries actual data. They meet when Runtime is created, triggering capture and initial state preparation. Read committed snapshots through the same token, then dispose Runtime when finished. Submitting new input repeats preparation, comparison and publication without redefining or registering the Source again.

## Core application

Core treats the complete Scene IR—a structured description of a drawing document—as one Source, rather than creating a Source for each node. It defines `CoreSourceDefinition` once when the module loads and reuses that token for initialization, updates and compilation. This excerpt omits imports and the type declaration:

```ts
export const CoreSourceDefinition = defineRuntimeSource({
  key: CORE_SOURCE_KEY, // '@retikz/core/document'
  value: {
    capture: input => cloneAndFreezeJson(input, 'CoreSourceDefinition input'),
    read: value => value,
    equals: jsonStructuralEquals,
  },
});
```

Input, internal value and read value all use the Scene IR structure: `capture` stores an independent read-only document, `read` exposes that document, and `equals` compares document contents. The two JSON helpers are internal Core utilities; consumers simply import the existing token.

The enclosing application handles integration. For example, Vanilla registers this Source and pairs its token with the initial or updated complete document. Core's compilation computation reads the data through the same token. These excerpts come from different call sites; surrounding registry, Runtime and computation setup is omitted:

```ts
// Application initialization: an entry in createRuntime's initialSnapshots
createRuntimeSourceInput(CoreSourceDefinition, initial.source);

// Application update: submit the next complete document
runtime.update({
  baseRevision: runtime.revision(),
  sources: [createRuntimeSourceUpdate(CoreSourceDefinition, next.source)],
});

// Inside Core's compilation computation: read the document to compile
const source = view.snapshot(CoreSourceDefinition).value;
// Then pass source to compileCoreSnapshot to produce a Scene
```

The token identifies the Source definition and stores no document data. Multiple Runtime instances can reuse it while owning independent state. This example connects the earlier steps—define rules, capture input, read state—to a real consumer. Core documentation covers compilation and incremental updates in detail.
