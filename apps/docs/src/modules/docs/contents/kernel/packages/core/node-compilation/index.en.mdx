This page follows the next questions: how much space does the text need, how does the shape contain it, and which geometry positions labels and connections?

Start with [Node basic usage](/kernel/components/node/usage) and [text syntax](/kernel/components/node/text). This page starts at the resolved `CanonicalNode` and ends at `CompiledNode` and its emission and reference consumers. Browser font loading, the TeX engine, and path clipping algorithms are outside its scope.

## Overall flow

Node layout determines the space needed by content, computes shape dimensions, and then places the body and attached labels. `CanonicalNode` contains effective node configuration and bound shape and boundary definitions. `CompiledNode` retains final geometry, layout, and drawing data. `CompiledNodeLayout` is the measured and positioned layout result. It retains bindings needed for geometry queries and can be passed into compilation as prepared layout.

`resolveNode` applies input scaling: padding, margin, and minimum dimensions follow their respective axes; fixed width and maximum text width follow the horizontal axis. Font size, line height, and shape parameters are also handled during resolution. `CanonicalNode` stores these effective values without a pending `scale`, and compilation consumes them directly. Runtime width proposals from parent layouts are not multiplied by node scale; stroke width and label distance retain their existing semantics.

The text is first split into the lines that will actually be displayed, called **physical lines**. Once their bounds are known, padding is added and the result is passed to the shape. A label needs the shape's position before it can be placed, so it does not enlarge the node shape in return.

## Content measurement

Core obtains metrics through the injected `measureText` function; it does not read the DOM. Inputs are text and font settings. Results contain width, height, and optional `ascent` and `descent`, the extents above and below the baseline. When both are absent, Core assigns half the height to each. Without an injected measurer, it estimates using average character width. Accuracy depends on the measurement provider.

Text preserves explicit line breaks, then prefers word boundaries within the width limit; oversized words split at grapheme boundaries. Content width is the widest physical line, and height is the sum of line slots. Each slot is the larger of `lineHeight` and actual ascent + descent, with extra leading split equally above and below the content.

Math or explicit `segments` content uses the same wrapping rules and aligns fragments to a shared baseline within each physical line. Widths are added; the required extents above and below the baseline are taken separately. Each line slot is tall enough for those fragments. Formulas remain indivisible and may overflow on their own line.

Reconciler shares metrics by text and font values across nodes and probes within one compilation. Node layout calls the supplied measurer without maintaining a local cache. The measurement cache does not survive another full compilation or incremental batch, and a width change still requires layout to segment again. See [Query evaluation and caching](/kernel/packages/core/composite-compilation#query-evaluation-and-caching).

## Node dimensions

Three bounds serve different purposes:

- **Content box**: laid-out text width and the combined height of its line slots.
- **Visual shape**: the outline that contains the content box plus padding, subject to size constraints.
- **Layout allocation**: the space reserved by the parent layout, accounting for margin and rotation around the node's outer box.

The shape's `computeCircumscribedGeometry` receives content half-width and half-height and returns an outer box that can contain them. A rectangle usually encloses the content directly; a circle needs a larger diameter to contain the same rectangular content area.

The diagram assumes an already measured content box of `40 × 24`, an unrotated rectangle, `padding = 8` on all sides, `minimumSize = { width: 80, height: 48 }`, and `margin = 6`, with no fixed `width`. Geometry is enlarged uniformly for readability. Gray dotted lines show calculated bounds, not additional node borders.

<ComponentPreview files="layout-boxes" size="lg" hideCode type="illustration" />

Padding produces `56 × 40`. The minimum size expands the visual box to `80 × 48`. Margin gives an allocation of `92 × 60`. These dimensions do not replace each other: margin does not make the visible rectangle larger.

Width constraints also have distinct roles:

| Constraint            | Effect                                                                                          |
| --------------------- | ----------------------------------------------------------------------------------------------- |
| `maxTextWidth`        | Limits text wrapping width without forcing the shape to that exact width                        |
| `minimumSize`         | Sets a lower bound for the shape box without shrinking text                                     |
| `width`               | Fixes the visual box width; plain text may reflow, and compilation fails if it still cannot fit |
| Parent width proposal | Constrains allocation, accounting for shape, margin, and rotation                               |

A fixed `width` determines the final visual width; horizontal `minimumSize` does not enlarge it. Height still follows content and minimum height. A parent proposal has a different contract: it cannot guarantee that every unbreakable segment fits, and the parent must handle the actual allocation returned. See [Composite Compilation](/kernel/packages/core/composite-compilation) for the full proposal and replay process.

Asymmetric padding can also make the visual box center differ from the content center. Layout stores both so text emission does not accidentally use the outer box center.

## Baselines and labels

A baseline is the vertical reference used to place glyphs, not the center line of their box. For plain text, Core takes the first physical line's metrics, divides the remaining line height equally above and below the glyphs, and locates its baseline. Later baselines advance by `lineHeight`. Mixed content determines each line's baseline from its own fragment heights.

For example, with line height `24`, normalized `ascent = 14`, and `descent = 4`, the extra space is `3` on each side. The baseline is `17` from the top of the line slot. The enlarged diagram below uses these metrics: blue marks the baseline, and gray marks the glyph metric box.

<ComponentPreview files="layout-baseline" size="lg" hideCode type="illustration" />

Attached labels are measured independently, then positioned using attachment points on the visible shape, attachment direction, label rotation, and `distance`. That distance is the clear gap between the shape edge and the label's visual box. The opening example shows the result: a label changes neither the body nor the shape dimensions, but the automatic viewBox still includes it so exported images do not crop it.

When placement aligns a node's own anchor with a target, Core first needs a provisional layout to locate that anchor, then translates the layout as a whole. Labels retain offsets relative to the node and move with it. See [Coordinate resolution](/kernel/packages/core/coordinates) for reference timing.

## Connection boundaries

Completing node layout does not mean every connection ends on the visible outline. `shape` determines what is drawn; `boundary` selects the connection surface for automatic connections and standard border anchors. Only a resolved value of `'shape'` directly reuses the visual shape.

The diagram keeps the same circle and connection direction while changing the boundary and margin. Gray dotted outlines show auxiliary connection bounds; compare the arrow endpoints.

<ComponentPreview files="layout-boundaries" size="lg" hideCode type="illustration" />

Standard directional and numeric-angle anchors use the connection surface with margin. Shape-specific anchors and `{ side, fraction }` edge positions use the visual shape. Outside labels do not move connection endpoints to the label edges.

When the same layout is referenced repeatedly, Core reuses calculated connection envelopes and anchors. These serve the current geometry; they are not another persistent node configuration. See [Node implementation](/kernel/components/node/mechanism#visual-shape-vs-connection-geometry) for the detailed reference rules.

Node layout accepts only the current node's `boundaryState`; it neither creates nor retains a multi-node store. Before layout, Reconciler obtains the state through `boundaryStore.get(canon.shape)` and supplies diagnostics. Later references reuse state through the same shape binding. Direct Core callers may omit the state: ordinary positioning needs no initialization, while self-anchor positioning carries only `warn` and `irPath`, without implicitly creating a connection-envelope cache.

## Complete implementation flow

The flow below follows a plain-text node. The left side shows layout stages; the right side shows consumers of the result. Geometry queries segment when needed, without precomputing every anchor before emission.

<ComponentPreview files="layout-implementation" size="xl" hideCode type="flow" />

Start reading at `compileNode`. It consumes `CanonicalNode` and optional prepared results, calling `layoutNode` only when layout is absent; Reconciler decides whether results can be reused. The `content/`, `label/`, and `shape/` directories group code by product, each with a `layout.ts` and an `emit.ts` for calculation and drawing. The node-level `layout.ts` coordinates these products, keeping feedback between text width and shape dimensions, anchor positioning, and overall layout in the same file. The top-level `emit.ts` assembles node primitives and bounds. Width feedback remains bounded to 32 attempts; the measurer injected for the current compilation handles measurement reuse. The final `CompiledNode` separates geometry, metrics, metadata, styles, text, labels, and animations, and retains the shape and boundary bindings needed by later geometry queries.

Traversal then projects geometry into world space for named references. Emission turns the local layout into shape, body-text, and label primitives. Reference geometry in the namespace and local primitives in Scene have different consumers; drawing coordinates do not all need to be expanded into world coordinates beforehand.
