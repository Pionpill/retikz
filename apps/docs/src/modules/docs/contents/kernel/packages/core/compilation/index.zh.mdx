前面的[语义解析](/kernel/packages/core/resolution)、[能力注册](/kernel/packages/core/definitions)和[能力依赖](/kernel/packages/core/providers)围绕 resolve 与编译准备展开：声明如何获得确定的语义，所需定义如何注册和装配。本页把这些准备接到 compile，说明解析后的数据怎样变成布局、几何和绘制结果。后续各篇再分别展开坐标求值、Node、Path、Scope 与 Composite 的编译过程，最后说明编译输出。

Node 提供形状与内容，Coordinate 提供命名位置，Scope 组织局部空间，Path 连接几何目标。下面沿 A、B 两节点及连线追踪这些实体。Core 提供实体的解析与计算，Reconciler 按依赖就绪情况调用它们。

## 整体流程

对一个实体来说，resolve 负责确定“这份声明是什么意思”，compile 负责计算“它的位置、尺寸和输出是什么”。两者之间传递的解析结果，以及编译后得到的计算结果，在源码中常用 canon 和 compiled 命名：

| 概念     | 含义                                                                | 以 Node 为例                                                          |
| -------- | ------------------------------------------------------------------- | --------------------------------------------------------------------- |
| resolve  | 结合继承与定义，将默认值、简写和能力参数解析为当前实体可消费的形式  | 确定样式、绑定形状定义、解析布局配置，产出 CanonicalNode              |
| canon    | canonical 的简称，表示已解析的实体数据，类型通常命名为 CanonicalXxx | 包含有效样式、形状绑定与布局要求；尺寸和引用位置继续交给 compile 计算 |
| compile  | 消费解析结果与测量、定位等上下文，完成实体所需的计算和输出          | 测量内容、布局形状、求值位置，再生成形状与文字图元                    |
| compiled | 编译结果，类型通常命名为 CompiledXxx，保存该实体的计算产物          | CompiledNode 包含布局与绘制结果，供几何查询、父布局和 Scene 组装使用  |

因此，Node 的数据变化是 **IRNode → resolveNode → CanonicalNode → compileNode → CompiledNode**。canon 中确定的是语义与配置；compiled 中得到的是本次上下文下的计算结果。不同实体按需组织产物：Path 的解析结果 PathResolution 将 canon 与定义等信息一起传给 compilePath；CompiledCoordinate 只提供求值后的位置。各实体的绘制产物汇总后形成 Scene，再由渲染后端消费。

编译从 IRScene 的子项开始。每个实体先确定当前阶段所需的样式、定义和位置上下文，再计算布局或几何。Node 和 Coordinate 提供可查询的位置；Scope 根据子布局形成包络并确定空间变换；Path 在目标几何就绪后计算连线。各实体的绘制结果最终组成 Scene。

```ts
import { SceneReconciler } from '@retikz/reconciler';
import type { IRScene } from '@retikz/core';

const ir: IRScene = {
  type: 'scene',
  version: 1,
  children: [
    {
      type: 'path',
      children: [
        { type: 'step', kind: 'move', to: { id: 'A' } },
        { type: 'step', kind: 'line', to: { id: 'B' } },
      ],
    },
    {
      type: 'node',
      id: 'A',
      position: [0, 0],
      text: 'A',
      layout: { minimumSize: { width: 60, height: 40 }, padding: 0, margin: 0 },
    },
    {
      type: 'node',
      id: 'B',
      position: [180, 0],
      text: 'B',
      layout: { minimumSize: { width: 60, height: 40 }, padding: 0, margin: 0 },
    },
  ],
};
const reconciler = new SceneReconciler({}, { incremental: false });
try {
  const result = reconciler.mount(ir).compilation.result;
  console.log(result.scene);
} finally {
  reconciler.dispose();
}
```

沿这份输入，节点先得到包含确定样式与能力绑定的 CanonicalNode，再得到几何与 emit 产物。路径暂存命名目标，等节点发布几何后，才选择边界交点并生成路径指令。

## 实体之间的依赖与执行顺序

四类实体需要的上下文和产物不同，处理时机取决于它们要读取什么：

| 实体       | 处理过程                                                       | 后续使用的结果                           |
| ---------- | -------------------------------------------------------------- | ---------------------------------------- |
| Node       | 根据继承样式和形状定义解析属性，测量内容，确定形状尺寸与位置   | 锚点、边界等查询几何，以及形状和内容图元 |
| Coordinate | 在当前坐标空间中求值位置表达式，读取已有命名引用               | 命名位置，可供后续定位和路径引用         |
| Scope      | 向子项传递继承配置与空间上下文，再根据子布局确定包络和放置变换 | 分组几何、空间变换、裁剪和分组属性       |
| Path       | 读取目标几何，换算到所属空间，计算端点、路径和装饰             | 路径图元、布局边界与资源引用             |

在上例中，访问 Path 声明时先保留输出槽位。A、B 完成布局并发布几何后，Path 才能查询它们的边界，确定 [30, 0] 与 [150, 0] 两个端点。若把节点放入 Scope，路径查询还要使用该 Scope 确定后的空间变换；Scope 的包络则依赖子项提供的布局结果。

Node 的定位和 Coordinate 的位置在访问时求值，引用目标需要已经可查。Path 有专门的延迟处理，因此支持示例中的前向引用。引用无法求值时，按对应契约报告失败。

求值顺序与绘制顺序分别保留：延迟 Path 完成后回填原声明位置的槽位，同层输出再按 zIndex 稳定排序，同值维持原有次序。因此本例虽然先计算节点，路径仍处于节点之前的绘制位置。
