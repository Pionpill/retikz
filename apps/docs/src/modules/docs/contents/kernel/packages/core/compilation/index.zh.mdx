本页从 Core 接收完整 IR 开始，追踪一次同步编译，直到返回可交给渲染器的 Scene。React / Vanilla 怎样产生 IR、渲染器怎样绘制，以及后续更新怎样复用结果，分别属于这条主线的上游、下游和另一轮执行。

## 输入与案例

IR 是可保存的图形声明，例如“在这里放一个节点”“连接 A 和 B”。Scene 则记录已经确定几何和样式的图元，例如矩形、文字和路径指令。`compileToScene` 负责完成这次转换，并返回包含 Scene 的编译结果。下面是省略泛型细节后的公开签名：

```ts
compileToScene(ir: IRScene, options?: CompileOptions): CompileResult
```

| 输入 / 输出             | 本页追踪的含义                                   |
| ----------------------- | ------------------------------------------------ |
| `ir`                    | 完整、符合 Core 契约的图形声明                   |
| `options`               | 本次使用的测量能力、扩展定义和输出设置；可以省略 |
| `result.scene`          | 已布局的图元、画布范围与绘制资源                 |
| `result.artifacts`      | 复合组件产物及显式请求的节点布局数据             |
| `result.spatialHandles` | 本次编译收集的具名空间区域索引                   |

`compileToScene` 接收已类型化的 IR；它不会在入口对整棵树调用 `SceneSchema.parse`。来自 JSON 等外部输入的数据应先经过 schema 入口校验。编译过程中仍会检查需要 Definition 或布局上下文才能判断的约束。

贯穿案例有两个宽 60、高 40 的矩形节点，中心分别位于 `[0, 0]` 和 `[180, 0]`，连线声明刻意放在节点前面。节点文字只用 A、B，保证本例的最小尺寸足以容纳正文。

<ComponentPreview files={['compilation-example', 'compilation-example.data']} size="xs" hideCode type="illustration" />

下面是这个案例的 Core 输入。`minimumSize` 限制节点外框，`padding` 和 `margin` 分别是内间距与连接边界外侧间距；设为零后，本例的连线直接落在矩形边上。

```ts
import { compileToScene, type IRScene } from '@retikz/core';

const ir: IRScene = {
  version: 1,
  type: 'scene',
  children: [
    {
      type: 'path',
      children: [
        { type: 'step', kind: 'move', to: { id: 'A' } },
        { type: 'step', kind: 'line', to: { id: 'B' } },
      ],
    },
    {
      type: 'node',
      id: 'A',
      position: [0, 0],
      text: 'A',
      layout: { minimumSize: { width: 60, height: 40 }, padding: 0, margin: 0 },
    },
    {
      type: 'node',
      id: 'B',
      position: [180, 0],
      text: 'B',
      layout: { minimumSize: { width: 60, height: 40 }, padding: 0, margin: 0 },
    },
  ],
};

const result = compileToScene(ir, { padding: 10 });
```

## 整体流程

第一次遇到 Path 时，A 和 B 还没有布局结果。Core 先记住这条路径，继续处理节点；节点的中心和连接边界确定后，再计算路径端点，最后汇总画布范围。

## 编译上下文

进入编译前，Core 需要知道怎样量文字、按什么规则解析形状，以及把共享的绘制资源放在哪里。这里涉及两个概念：

- Definition：一种形状、路径或复合组件的具体能力定义。
- registry：本次编译按名称查找 Definition 的注册表。

`createCompileEnvironment` 把内置能力与调用方注入的定义整理到只读注册表，并保存测量服务和数值配置。内部的 `createCompileContext` 基于这个环境准备单次工作区，解析根主题，建立独占的文本测量缓存、paint / clip 资源表和警告收集入口。没有注入文字测量时，使用内置近似度量；Core 自身不读取 DOM。

内置定义与 CompileOptions 中的外部定义按能力注册到 context 对应的 registry，供编译时按名称查找和调用，而生成的 paint / clip 资源由上下文的 `paint`、`clip` 收集并写入 Scene 的资源表。

本例没有额外定义，因此使用内置矩形和路径能力。上下文中的 `loweredIr` 在此处仍指向传入的 IR，复合组件会在后续遍历遇到时处理。

遍历还会建立本轮执行状态，包括已生成的图元、累计边界和命名空间。命名空间按 id 保存可查询的布局结果，使路径能由 A、B 找到对应几何。这些状态属于本次完整编译，不负责跨调用保留更新结果。

## 节点解析

`compileChildrenToPrimitives` 按 `children` 的声明顺序分派子项。本例先把 Path 放入待处理列表，再处理 A、B。一个节点的内部过程可以用三个结果理解：

- CanonicalNode：合并有效样式、补齐缺省值并解析填充与描边后的节点，`fill` / `stroke` 直接携带 paint 解析结果。
- NodeResolution：CanonicalNode 加上已经选定的形状与连接边界，供布局使用。
- CompiledNodeLayout：测量并定位后的节点结果，按节点属性、形状、连接面、几何、正文排版和标签分组。

`resolveNode` 先确定有效配置和能力绑定，`compileNodeResolution` 再确定正文与标签的文字属性，计算排版、节点尺寸及位置。返回的 `properties` 保存完整有效属性及身份，`layout` 保存计算后的几何与排版。描边宽度、颜色和虚线保持在同一属性来源；标签引线也保留完整配置。`emitNodePrimitives` 消费布局与当前属性生成 Scene 图元；普通文本通过作者行索引读取当前行样式，改色时无需重新折行。这里的数据结构不代替变化影响判断，Weave 的分类调度仍需要独立的能力契约。

## 路径解析

节点布局先完成，依赖节点的路径随后解析。遍历按子项声明顺序推进：

1. 遇到 Node，立即解析配置、测量定位、注册布局并生成节点图元。
2. 遇到 Path，先记录待处理任务并插入占位，暂不解析节点引用和生成路径图元。
3. 到当前容器的收尾阶段，再查询已注册的节点布局，解析并生成待处理路径。

这个顺序以当前容器为范围：Scope 会递归处理子项，在自身收尾时处理内部待处理路径；根层则在根子项遍历完成后处理根层路径。因此，并非整棵树的所有 Node 都处理完，才开始处理任何 Path。

路径可能引用稍后才出现的节点。`queuePathChild` 会同时保存两样东西：待处理路径记录，以及插入当前图元数组的占位项。记录保留路径输入、样式与坐标环境，还持有占位项及其所属数组的引用。

下图逐行展示本例的数组状态。Group A、Group B 分别包含对应节点的矩形和文字；槽位内的文字是结构摘要。

<ComponentPreview files="compilation-slots" size="xl" hideCode type="illustration" />

A、B 登记完成后，`flushPendingPathEmissions` 查询目标布局，解析路径并生成图元。只指定节点 id 时，本例会按连接边界裁剪端点，所以 A 的右边界 `[30, 0]` 和 B 的左边界 `[150, 0]` 成为可见线段的起止点。

随后，Core 在原数组中找到占位项，用实际 PathPrimitive 替换它。虽然路径比节点晚计算，它仍位于数组第 0 项。回填完成后再按 `zIndex` 稳定排序；相同 `zIndex` 保持声明顺序。所有占位必须在返回 Scene 前消失。

本例的最终路径字段摘录如下：

```ts
{
  type: 'path',
  commands: [
    { kind: 'move', to: [30, 0] },
    { kind: 'line', to: [150, 0] },
  ],
}
```

这种等待发生在对应分组的收尾阶段。它支持本例同组 Path 对后续节点的引用，但节点自己的相对定位在布局时就需要目标，不能由此推断所有位置表达都支持前向引用。

## 作用域处理

遇到 Scope 时，父级遍历先进入它的子树。Core 为子项准备样式、主题、变换链和独立的结果容器，再按声明顺序处理 `children`：Node 立即布局，Path 先排队，嵌套 Scope 则递归执行同一流程。

下面按进入、递归处理与返回的顺序展示 Scope 的编译过程；嵌套 Scope 会完整执行同一流程，再返回父级继续遍历：

<ComponentPreview files="compilation-scope" size="md" hideCode type="flow" />

例如 S 的子项依次是 Node A、Scope T、Node B：先处理 A，再进入 T，等 T 的子项、布局和待处理路径都完成后，返回 S 继续处理 B。S 的所有子项完成后，才确定 S 的包络和最终定位、更新可查询布局、处理 S 的待处理路径，最后向父级交付 Group。

每层 Scope 都有自己的子遍历上下文，但默认共享当前命名帧。假设外层已注册节点 A，Scope 内又声明节点 A 和 B，两种模式的区别如下：

| 操作          | `localNamespace: false`（默认）         | `localNamespace: true`                             |
| ------------- | --------------------------------------- | -------------------------------------------------- |
| 进入 Scope    | 复用当前命名帧                          | 压入一个新的局部命名帧                             |
| 注册内部 A、B | 写入当前帧；同帧 A 被覆盖并发出重名警告 | 写入局部帧；内部 A 遮蔽外层 A                      |
| 组内查找名称  | 从当前帧向外查找                        | 优先查局部帧，未命中再向外查找                     |
| 返回父级后    | 内部 A、B 仍可按名称查到                | 局部帧已弹出；再次查 A 得到外层 A，内部 B 不再可查 |

组内待处理路径在局部帧弹出前解析，因此仍能引用内部节点。出栈只移除这层名称的可见性，已经生成的图元仍保留在 Scene 中。Scope 自身若有 id，会在入栈前登记到父命名帧，并在收尾时更新为最终布局，所以外部仍能通过该 id 引用整个分组。

Scene 输出可以保留局部几何和 Group 变换。命名查询使用所需的坐标投影，并不要求最终输出把每个点都展开为世界坐标。

复合项通过注册的 Definition 接入编译编排，产出的基础 IR 继续走上述处理流程，详见[复合组件实现原理](/kernel/packages/core/composite-compilation)。

## 汇总编译结果

子项编译完成后，`prepareSceneCompilation` 收集有序图元、paint 与 clip 资源，以及可用于根场景的动画配置。画布范围分两种情况：指定 `viewBox` 时直接使用该范围；否则根据累计布局边界加上 `padding` 计算。

本例的内容范围从 `[-30, -20]` 到 `[210, 20]`。四周增加 10 后，`result.scene.layout` 为：

```ts
{ x: -40, y: -30, width: 260, height: 60 }
```

这一步决定最终画布范围，不会再次移动 A、B。输出中的 `primitives` 依次为路径、Group A、Group B；本例没有渐变或裁剪资源，因此不产生 `resources` 字段。

Scene 之外，编译结果还携带 `artifacts` 与 `spatialHandles`。前者保存复合组件产物或按需输出的节点布局；后者保存具名空间区域。它们与同次编译的 Scene 对应，渲染器无需据此重新执行节点布局。普通 `compileToScene` 不建立 observer 会话；显式观测入口会在同一完整编译过程中派发最终观测结果。

| 属性             | 类型                                                             | 作用                                                                                                                                   |
| ---------------- | ---------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| `scene`          | `Scene`                                                          | 保存已布局、按绘制顺序排列的图元，以及画布边界、可选资源和根时间轴动画，交给渲染器绘制。                                               |
| `artifacts`      | `ReadonlyArray<TCompositeArtifact \| NodeLayoutCompileArtifact>` | 保存复合组件返回的领域产物，以及显式请求的节点布局结果，供调用方读取和后续处理。未产生产物时为空数组。                                 |
| `spatialHandles` | `SpatialHandleIndex`                                             | 保存复合组件声明的具名空间区域，包含所属组件、世界坐标边界、角色和标签等信息，供调用方查询与定位。没有空间区域时，`entries` 为空数组。 |

## 独立编译与可复用状态

需要自行调度元素时，调用方可持有 `CompileEnvironment`，并通过以下入口计算一个基础元素。它们复用全量编译的 resolve、layout 和 emit 实现，不递归编译其他元素，也不自动注册名称。

| 入口                | 完成状态             | 保存的内容                                                              |
| ------------------- | -------------------- | ----------------------------------------------------------------------- |
| `compileNode`       | `CompiledNode`       | `layout` 保存 CompiledNodeLayout，`output` 保存绘制、资源和必要观察贡献 |
| `compileCoordinate` | `CompiledCoordinate` | `id` 与局部 `position`；选中观察时才有 `output`                         |
| `compilePath`       | `CompiledPath`       | `output` 保存完整路径输出，包括定制 kind 的宿主处理                     |
| `compileScope`      | `CompiledScope`      | `envelope`、不含 children 的 `group` 和自身 `output`                    |

`NodeLayoutObservation` 是面向调用方的节点布局观察投影，原名为 `CompiledNodeLayout`。它不包含重新绘制所需的完整编译状态；缓存应使用 `CompiledNode`。

```ts
import { assembleSceneCompilation, compileNode, createCompileEnvironment, resolveScopeContext } from '@retikz/core';

const environment = createCompileEnvironment();
const result = compileNode(
  { type: 'node', id: 'A', position: [0, 0], text: 'A' },
  {
    environment,
    context: resolveScopeContext({}, environment),
    irPath: 'children[0].node',
  },
);

if (result.status === 'compiled') {
  const prepared = assembleSceneCompilation({}, [result.compiled.output], environment, {
    diagnostics: result.diagnostics,
  });
  // prepared.result.scene 可交给 renderer，diagnostics 尚未派发
}
```

单元素调用返回 `compiled` 或 `pending`。前者包含完整状态、`reads` 与诊断；后者只包含读取事实，不发布半成品。名称由 `CompileNamespace` 的父链从内向外查找，`reads` 同时记录未命中和命中的绑定。需要跟踪后续新增名称时，必须提供显式的空命名空间；省略 namespace 表示本次没有可查询的绑定。调用方只登记声明位置可见的名称，不能用 pending 放宽 Node / Scope 的前向引用限制；Path 仍可等到引用就绪后编译。`projectCompileReference` 负责将完成状态投影为可登记的引用几何。

Scope 分两步计算：先 `prepareScopeCompilation` 得到有效继承上下文与初步变换，再以已完成的子布局调用 `compileScope`，确定包络与最终变换。子元素编译必须接收所属层级已确定的变换；最终包络相关的放置由 Scope 完成后投影。`assembleScopeOutput` 将 Scope 自身输出与子输出组装，不重新运行 provider，也不把重复子树写入缓存。

输出中的资源编号属于局部片段。`assembleScopeOutput` / `assembleSceneCompilation` 会导入并重映射资源、稳定排序同层 zIndex、应用最终变换，再组装 Scene。选中的节点布局产物和 owner 观察贡献随片段一起传递；观察会话由 `createCompileObservationRuntime` 创建，并传给元素调用及最终组装，一次组装完成后不可跨批次复用。其他已完成的 Composite artifacts、空间句柄和 provenance 通过同版本 metadata 传入，组装函数不会推断这些编排信息。

这些入口是 Core 提供的调度基础。Reconciler 负责名称映射、依赖失效、版本隔离和提交；本接口不自动构建或更新 Weave 树。调用方不得修改已发布的 compiled 可达数据，环境定义或测量服务改变时也必须使相关缓存失效。包含 Definition 与文本 emit 函数的编译状态不能直接作为 Worker 消息序列化。

## Weave 接入

Core 与 Weave 共用 `formatCompileChildPath(prefix, index, type?)` 生成声明来源路径。`prefix` 为空或以点结尾；基础元素传入类型后缀，Composite 声明省略类型。该路径用于来源与诊断，不作为跨版本身份。

Weave 是 Reconciler 持有的编译树：每个节点保留自身输入、有效上下文与 Core 编译状态。Root 统一持有编译环境、Scene 配置、容器定位索引和本版本的读取记录；Scope 的自动定位 id 不写回 IR，也不参与绘图包络计算。

Reconciler 会话通过 Weave 协调器持有稳定 WeaveRoot，作为整棵树的入口。节点和 Root 各自保存已提交的 current 与候选 pending 状态；父子关系、依赖和索引引用稳定节点对象。候选修改先隔离对应状态与可变集合，未变的 Core 产物只读共享。只修改子节点属性时，Scope 的 children 无需复制；增删成员时才取得独立数组。提交逐个切换本批触及的状态，完成前保留恢复依据，节点引用本身不提供历史快照。

基础元素输入按声明顺序建立节点与名称绑定。Node 和 Coordinate 使用当前位置可见的引用；Scope 先准备上下文，再计算子元素和包络，最后完成所属路径。顶层 Path 可等到两侧 Scope 的节点发布后计算。名称注册由 `createCompileNamespaceRegistry` 保持同层覆盖诊断，`projectScopeCompileLayouts` 与 `projectPublishedCompileLayout` 复用 Core 的包络贡献和最终引用投影规则。

编译完成后，Reconciler 通过 Core 组装完整输出。`createCompileProvenanceTracker` 保存图元来源，在资源重映射和 Scope 包装时转移到新图元；最终来源路径与排序后的 Scene 配对，不需要再次完整编译补齐。候选计算失败时，Reconciler 会话保留旧结果；成功后才发布配对的树与输出。

内部 Weave 协调器支持在已构建的 Root 上处理 WeaveBatch：先按顺序应用增删改，再基于最终输入计算。上下文沿声明结构传递，依赖失效沿消费者传播；Scope 准备、子布局、包络与最终投影遵守 Core 的计算顺序，Path 保留延后引用能力。未受影响且输入、声明位置和名称绑定仍有效的编译产物可以复用；启用观察会话或需要重新生成诊断时重新计算相关元素。当前采用保守失效，Scope 变化可能使整个子树重新计算，尚不按 style / layout 粒度过滤。

更新返回完整输出和提交、确认、回滚操作。准备期间旧状态保持不变；提交后仍可恢复，最终确认才释放恢复依据。名称索引恢复、来源与输出组装仍可能遍历完整树，局部编译不等于整次更新具有局部成本。

Reconciler 的 `replace` 接收完整 IR 并重新编译，`update` 接收已有基础元素树的 `WeaveBatch`；批次必须绑定当前会话结果，Composite 场景不支持该批次入口。React 与 Vanilla 的普通输入更新仍调用完整替换。Render 提交目标将新的编译结果转换为 `replaceScene`，不能据此推断后端已执行细粒度 Patch 更新。含 Composite 的输入使用 Core 完整准备路径，保留 probe、实例输入、artifacts 与空间句柄。
