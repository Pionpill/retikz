[Semantic Resolution](/kernel/packages/core/resolution) explains how declarations become determined inputs. When a node says `shape: 'rectangle'`, resolution also needs to know which implementation computes dimensions, attachment points and primitives. A Definition describes that capability; a registry associates its name with the implementation.

This page follows definition, registration, reference and consumption. A definition can contain functions and Schemas. IR continues to store serializable names, parameters and domain declarations.

## Overall flow

Reconciler accepts compilation options and calls Core's registry resolvers. Domain resolvers then select definitions from IR, determine parameters and pass the results to layout, geometry or compilation callbacks.

<ComponentPreview files="definition-overview" size="lg" hideCode type="flow" />

The shared pattern is lookup and consumption through a contract. The contracts differ: shapes supply geometry and primitives, path definitions own path compilation, and composites produce children that require further execution.

## Extension capabilities and registration

Scope, Node, Path and Composite organize declarations or define processing subjects. Their extension points follow the capabilities they need.

| Entity    | Extension points                                 | What remains with the core mechanism                    |
| --------- | ------------------------------------------------ | ------------------------------------------------------- |
| Scope     | Referenced capabilities such as Clip             | Inheritance, local space and grouping products          |
| Node      | Shape and Boundary                               | Text measurement, node layout, labels and shared output |
| Path      | Path Definition, Arrow and Mark                  | Shared target evaluation, resources and host services   |
| Composite | Domain definition identified by namespace / type | Child-layout contracts and Reconciler execution         |

Pattern supplies paint for fills and strokes across entities. Theme has its own definition and registry contract for resolving the effective theme. It is separate from the drawing-provider dependency graph described next.

A different fill color does not require a new Definition. New content envelopes, named anchors or shape drawing behavior belong to Shape Definition. Layout algorithms and domain compositions generally belong to Composite. Choose the contract that owns the behavior.

Once the capability category is determined, registration keys connect definitions to IR references. Named capabilities are identified by category and name: for example, `node.shape` looks up a definition by name in the shape registry. Composite uses separate `namespace` and `type` keys.

These excerpts show how runtime wiring corresponds to instance references; they are not complete compilation options:

| Runtime wiring                 | IR selection                         | Consumer                         |
| ------------------------------ | ------------------------------------ | -------------------------------- |
| `shapes: [shapeDefinition]`    | `shape: { type: name, params }`      | Node resolution and layout       |
| `paths: [pathDefinition]`      | `type: 'path', kind: name`           | Path resolution and compilation  |
| `composites: [pairDefinition]` | `namespace: 'example', type: 'pair'` | Composite binding and evaluation |

The built-in shape registry contains rectangle, ellipse and polygon definitions. Circle and diamond are declaration-side presets that node resolution maps to definitions and parameters.

## Following one definition

The following small domain composition declares a gap and expands into two nodes. It illustrates registration and consumption; the Composite compilation topic covers layout cooperation.

```ts
import { defineComposite } from '@retikz/core';
import { SceneReconciler } from '@retikz/reconciler';
import { z } from 'zod';

const pair = defineComposite({
  namespace: 'example',
  type: 'pair',
  schema: z.strictObject({
    namespace: z.literal('example'),
    type: z.literal('pair'),
    gap: z.number().positive().default(180),
  }),
  compile: input => ({
    children: [
      { type: 'node', position: [0, 0], text: 'A' },
      { type: 'node', position: [input.gap, 0], text: 'B' },
    ],
  }),
});

const reconciler = new SceneReconciler({ composites: [pair] }, { incremental: false });
try {
  const output = reconciler.mount({
    type: 'scene',
    version: 1,
    children: [{ namespace: 'example', type: 'pair', gap: 180 }],
  });
  console.log(output.compilation.result.scene);
} finally {
  reconciler.dispose();
}
```

First a definition object is created, then explicitly supplied to Reconciler. Core finds the definition by its full key and validates the input through its Schema: a supplied `gap` must be a positive number, and omitting it applies the default value of `180`. Reconciler invokes the definition's `compile` callback at the Composite execution point and continues processing the returned children. Its returned nodes go through normal node processing.

## Built-ins and custom definitions

Ordinary registries add built-ins before explicitly supplied definitions. Duplicate keys within a capability are errors; order cannot be used to override a built-in. Composite has no reserved official namespace list, and duplicate types within a namespace are also errors.

Unknown shapes and paths fail through their compilation error paths. An unregistered Composite currently warns and skips that item. Callback failures also preserve diagnostics and causes at the owning boundary.

Built-ins use the same Definition, resolution and consumption contracts as extensions. Registries own keys and conflicts, callers own references, and each definition owns its domain semantics.
