`@retikz/react` is the primary entry for React applications. You declare figures with JSX components such as `<Layout>`, `<Node>`, `<Path>`, `<Scope>`, and `<Draw>`; its collector turns props and children into an `@retikz/vanilla` `InputScene`, then `<Layout>` hosts the processed SVG or Canvas result.

When wrapping a JSX component, import its props from `@retikz/react`. `CoordinateProps` is identical to Vanilla’s `CoordinateOptions`; `NodeProps` also accepts hydration events and text children. Use `<Path>` for JSX steps and `<Draw way={…}>` for shorthand. Both accept `PathLabel` children. A custom Path can get its geometry from its definition. The Vanilla path factory still accepts either way or a step array.

It owns React authoring and result hosting rather than new drawing semantics. IR, schemas, geometry, and compilation belong to `@retikz/core`; Input normalization, composite dependency resolution, the Core Computation, and session processing state belong to `@retikz/vanilla`.

The package root exposes components, Props, and authoring protocols. `Layout` handles component-name lookup and event collection internally. The source helpers `getDisplayName` and `collectHydrationHandlers` are not package-root exports.

## Install and usage

`react` and `react-dom` are peer dependencies at version 18 or newer:

```bash
pnpm add @retikz/react react react-dom
```

```tsx
import { Draw, Layout, Node } from '@retikz/react';

export const Diagram = () => (
  <Layout>
    <Node id="source" position={[0, 0]}>
      Source
    </Node>
    <Node id="target" position={[160, 0]}>
      Target
    </Node>
    <Draw way={['source', 'target']} arrow="->" />
  </Layout>
);
```

`<Layout>` emits SVG by default; pass `renderer="canvas"` when you need a raster bitmap. Start with [Getting Started](/kernel/components/get-start), then see [Layout](/kernel/components/layout/usage) for the complete host options.

`<Layout theme>` writes the root `IRScene.theme`, while `<Scope theme>` writes a local `IRScope.theme`. Theme is a sparse `name / mode` override; `themeDefinitions` is the runtime-only compile option that registers custom Core themes defined with `defineTheme`. When `ir` and an explicit `theme` are both present, the prop overrides `ir.theme` per field without mutating either input. See [Layout: Inherited Theme](/kernel/components/layout/extend#theme-configuration) for the complete example.

## Why @retikz/react exists

### JSX reduces authoring overhead

You can construct `@retikz/core` IR directly, but figures commonly contain nested, reusable, and compositional structures. JSX expresses those relationships as a component tree, keeping declarations such as `<Layout>`, `<Scope>`, `<Node>`, and `<Path>` close to the figure hierarchy while reducing the boilerplate of assembling authoring input by hand.

retikz treats React as its officially supported first-class framework: the component API, documentation, examples, and adapter behavior in `@retikz/react` are maintained alongside the Kernel. React is the authoring and result-host layer here; framework-neutral `@retikz/core` and shared `@retikz/vanilla` processing still own the data contract and compilation semantics.

### Why other adapters are not official packages

This does not mean Core can only integrate with React. Any framework can reuse the retikz Kernel by converting its component or template structure into the same `InputScene` and passing it to `@retikz/vanilla` processing.

`@retikz/react` also serves as the implementation reference for other framework adapters, demonstrating the complete boundaries for component-tree-to-`InputScene` conversion, host capability injection, and processing-result wiring. The official project focuses its maintenance resources on React and does not develop, release, or maintain packages for Vue, Svelte, or other frameworks; the community can implement those adapters independently against the same boundaries.

## Components do not render DOM directly

### Why marker components

Marker components are not used because React is incapable of drawing. They keep drawing semantics in one source of truth. If `<Node>` and `<Path>` each implemented their own DOM, browser layout, and geometry rules, the React DSL would gradually become a second system beside Core IR, and the same figure could produce different results in React, Vanilla, or another adapter.

JSX therefore organizes declarations while the collector converges them into a framework-neutral `InputScene`. The intermediate path creates no extra DOM and does not make CSS layout an implicit input to compilation. Shared processing then normalizes Input to Core IR that persistence, transport, and other framework adapters can reuse.

React still operates where it adds value. It subscribes to the read-only Vanilla processing result and connects React commit, refs, and unmounting to a stable `<svg>` / `<canvas>` host. Vanilla manages the scene session; React only maps the completed Scene to that host. Drawing semantics are thin in this layer, not host integration.

Kernel components such as `<Node>`, `<Path>`, and `<Scope>` are **Input markers**, not DOM components. They return `null` and expose only a stable `displayName` that tells the React collector which primitive they represent. A `<Node>` therefore does not produce an intermediate `<div>` or acquire a second browser-layout model.

Import `KernelDisplayName` from the package root instead of the former individual constants. It names the built-in markers as well as Layout and Draw; for example, `KernelDisplayName.StepLabel` is `RetikzKernelStepLabel`.

```tsx
export const Node: FC<NodeProps> = () => null;
Node.displayName = KernelDisplayName.Node;
```

Draw calls Vanilla’s `parseWay` and passes the parsed steps to Path as JSX children. These forms are equivalent:

```tsx
const shorthand = <Draw way={['A', 'B']} />;
const explicit = (
  <Path>
    <Step kind="move" to="A" />
    <Step kind="line" to="B" />
  </Path>
);
```

`readSceneChildren` walks children synchronously: it recognizes Kernel markers, unwraps fragments, and directly invokes function Sugar before recursing into the result. This does not pass through the React DOM renderer, so Kernel and Sugar must be hook-free, side-effect-free function components. `createInputScene()` produces the single `InputScene` with adapters bound to each embed for Vanilla normalization.

To check whether a React element is marked as embeddable, pass `element.type` to `isEmbeddableMarked`. To obtain its adapter, use `resolveInputEmbedAdapter(element.type)`. If the element is optional, check that it exists first.

### Update boundaries

The first render compiles synchronously through Vanilla, so the server can emit SVG without firing commit callbacks. After the client commits, Layout subscribes to a Vanilla scene session. New JSX or IR replaces the whole source in that session. If replacement fails, the last successful result stays visible.

Equivalent inline extension arrays such as `[shape]` do not trigger recompilation: Layout compares the order and identity of the definitions. Changing compile options recompiles the current source. Changing reconciler options starts a new session. Unmounting disposes the session.

### Execution modes and update strategies

Layout passes `reconciler` to Vanilla. The default `full` mode does not retain an incremental cache; `incremental` retains the cache and supports batch update strategies. In either mode, new JSX or complete IR goes through `replace` and is compiled in full. Layout does not infer a batch from changed props.

```tsx
<Layout />
<Layout reconciler={{ mode: 'incremental', updateStrategy: 'auto' }} />
<Layout onDiagnostic={diagnostic => console.warn(diagnostic.message)} />
```

## From JSX to Scene

`<Layout>` first calls the React collector to adapt JSX into Vanilla Input. After the client commit, Vanilla processes subsequent input or compile option changes. In the figure, blue nodes belong to `@retikz/react` authoring / hosting, green nodes are shared `@retikz/vanilla` processing, and orange nodes are the data contracts and compiler owned by `@retikz/core`.

<ComponentPreview files="react-to-scene" size="xs" hideCode />

| Stage                | Owner                | Responsibility                                                                                 |
| -------------------- | -------------------- | ---------------------------------------------------------------------------------------------- |
| Kernel / Sugar JSX   | `@retikz/react`      | Collect props and children; expand Sugar into Kernel first                                     |
| `createInputScene()` | `@retikz/react`      | Walk the component tree, produce `InputScene`, with adapters bound to embeds                   |
| `normalizeScene()`   | `@retikz/vanilla`    | Normalize typed Input to `IRScene`, lower embeds, and aggregate composite dependencies         |
| `IRScene`            | `@retikz/core`       | JSON-serializable drawing contract with no React element, hook, or DOM                         |
| `SceneReconciler`    | `@retikz/core`       | Process composites; resolve registries, references, geometry, layout, resources, and animation |
| `CompileResult`      | `@retikz/reconciler` | Scene and artifacts from one compilation                                                       |

`Layout` injects host capabilities such as text measurement, Definition registries, and the TeX lowerer as processing compile options, but those options do not put React into IR or Scene. Passing the `ir` prop skips the JSX collector. The `artifacts` prop requests opt-in outputs, while `onArtifacts` receives immutable same-compile artifacts after the selected host publishes; notification does not trigger another compile.

The optional `@retikz/inspect/react` entry provides `InspectionOverlay`, which consumes a completed ordinary result and presents auxiliary content independently. Inspection requests do not enter primary IR or participate in primary compilation and commits.

Use `Layout.onCompileResult` to receive the compiled frame after React commits. It does not run during server rendering.

## After Scene

Scene no longer contains React component semantics. Vanilla processing obtains the result for the current revision, while `@retikz/react` only subscribes to and hosts that result through React:

| Target | `@retikz/vanilla`                                                     | `@retikz/react`                                                 |
| ------ | --------------------------------------------------------------------- | --------------------------------------------------------------- |
| SVG    | Manages the processing controller, Core Computation, and Scene result | Maps the result with `ProcessingResultHost` and binds hydration |
| Canvas | Manages the processing controller, Core Computation, and Scene result | Maps the result with `ProcessingResultHost` to a Canvas host    |

Event handlers are functions and cannot enter JSON IR. In children mode, React separately runs `collectHydrationHandlers` to collect functions by primitive id, then binds them after rendering through SVG location or Canvas hit-testing. With the `ir` prop, the `handlers` prop supplies this runtime side channel instead.

## Responsibility boundaries

| Capability              | What `@retikz/react` owns                                             | Source of truth                    |
| ----------------------- | --------------------------------------------------------------------- | ---------------------------------- |
| JSX DSL                 | Kernel components construct Input; Sugar expands into Kernel          | `@retikz/vanilla` Input / Core IR  |
| Compilation host        | Collect children / IR, inject options, subscribe to processing result | `@retikz/vanilla` processing       |
| Rendering & interaction | Select SVG / Canvas, collect events, connect the React host           | `@retikz/render` output capability |

`@retikz/react` does not include framework-neutral Input helpers or DOM mounting. Use [`@retikz/vanilla`](/kernel/packages/vanilla/overview) outside React, for SSR strings, or for direct DOM mounting.
