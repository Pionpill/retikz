[Source · 来源](/kernel/packages/runtime/source)介绍了如何定义、注册和管理一份状态。当状态包含一张图时，还需要区分图中的各个节点：节点 A 从红色变成蓝色，它仍是同一个节点；另一张图中也有节点 A，却不能把两者混在一起。

**实体身份**用于跨状态更新标识同一个实体。本篇说明如何创建身份、比较两个身份，以及收集和查找一份状态中的身份。来源 Token 标识整份来源定义，Identity 标识该来源状态中的实体；一个来源可以包含多个实体身份。

## 整体流程

| 环节       | 接口或配置                                       | 作用                                   |
| ---------- | ------------------------------------------------ | -------------------------------------- |
| 创建       | `createRuntimeIdentity(owner, path)`             | 用来源名称和实体路径构成身份           |
| 比较       | `runtimeIdentityEquals(a, b)`                    | 判断两个身份是否指向同一实体           |
| 收集       | `collectIdentities(value)`                       | 来源回调返回捕获后数据中的完整身份列表 |
| 建立查找表 | `createRuntimeIdentityLookup(owner, identities)` | 校验身份列表并建立查找表               |
| 查询       | `lookup.has(identity)`、`lookup.values()`        | 检查身份是否存在，或列举集合           |

## 身份与状态

身份回答“这是哪一个实体”，状态回答“它现在是什么样”。这两个问题必须分开：只改颜色时，身份保持不变，状态却已经变化。如果用完整节点数据充当身份，就无法识别修改前后的节点仍是同一个对象；如果只用 `'A'`，又无法区分不同来源中的同名节点。

因此，Identity 由两个字段共同组成：

```ts
type RuntimeIdentity = Readonly<{
  owner: string;
  path: ReadonlyArray<string>;
}>;
```

`owner` 确定在哪个来源内寻找实体；`path` 确定该来源中的哪一个实体。比如 `owner = 'example/graph'`、`path = ['nodes', 'A']`。来源名称相同但路径不同，是同一来源中的不同实体；路径相同但来源不同，也不是同一身份。

下图并排摘录身份字段与节点颜色；`color` 属于实体状态，不是 Identity 的第三个字段。

<ComponentPreview files="identity-fields" size="md" hideCode type="illustration" />

两个节点记录可以是不同的 JavaScript 对象。只要 `owner` 与完整 `path` 内容相同，身份比较就相等；这既不表示两份状态相等，也不自动复用计算结果。调用方决定如何用稳定身份对应前后实体，Runtime 提供统一的创建、比较和查找工具。

## 创建与查询

### 创建与比较

节点的颜色可以变化，身份则应在它仍是同一个实体时保持不变。使用 `createRuntimeIdentity(owner, path)` 创建身份：

```ts
declare const createRuntimeIdentity: (owner: string, path: ReadonlyArray<string>) => RuntimeIdentity;
```

| 项目    | 说明                                           |
| ------- | ---------------------------------------------- |
| `owner` | 必填；所属 Source 的注册键，不能是空串或纯空白 |
| `path`  | 必填；至少一段，每段为非空、非纯空白字符串     |
| 返回值  | 包含 `owner` 与 `path` 的 Identity             |

<ComponentAlert
  type="tip"
  title="owner 与 Source key"
  description="Identity 的 owner 对应所属 Source 的 key，两者应保持一致。通常将这个字符串定义为常量，例如 GRAPH_SOURCE_KEY，并在定义 Source 和创建 Identity 时共同使用，避免重复手写造成不一致；已有 Source Token 时也可以直接使用它的 key。"
/>

```ts
declare const runtimeIdentityEquals: (left: RuntimeIdentity, right: RuntimeIdentity) => boolean;
```

| 项目            | 说明                                     |
| --------------- | ---------------------------------------- |
| `left`、`right` | 必填；待比较的两个 Identity              |
| 返回值          | `boolean`；来源与完整路径相同才为 `true` |

```ts
import { createRuntimeIdentity, runtimeIdentityEquals } from '@retikz/runtime';

const nodeA = createRuntimeIdentity('example/graph', ['nodes', 'A']);
const sameNodeA = createRuntimeIdentity('example/graph', ['nodes', 'A']);
const otherGraphA = createRuntimeIdentity('example/other-graph', ['nodes', 'A']);

console.log(runtimeIdentityEquals(nodeA, sameNodeA)); // true
console.log(runtimeIdentityEquals(nodeA, otherGraphA)); // false
```

路径由领域自己定义，不是文件路径。Runtime 按来源、段数和每段文本精确比较，不拆分斜杠、不合并路径，也不规范化大小写或 Unicode。例如 `['nodes', 'A']` 与 `['nodes/A']` 不同。创建后再修改原路径数组，不会改变已经创建的身份。

<ComponentAlert
  type="tip"
  title="为什么 path 使用数组？"
  description={
    <>
      数组保留明确的分段边界，无需约定分隔符和转义规则：<code>['nodes', 'A/B']</code> 与<code>['nodes', 'A', 'B']</code>{' '}
      是不同路径，也方便在父路径后追加子实体的标识。
      调用方可以按自己的约定，从共同前缀观察层级、辅助调试或实现子树查询；Runtime

    </>
  }
/>

稳定性由定义者保证：颜色变化时继续使用节点 A 的身份；若是另一个实体，就应分配另一个身份。Runtime 不会从颜色、对象引用或数组位置自动推断它们是不是同一节点。

### 建立查找集合

一张图可能包含多个节点。`createRuntimeIdentityLookup(owner, identities)` 将同一来源的身份整理成查找表，用来回答“这个实体是否存在”：

```ts
declare const createRuntimeIdentityLookup: (
  owner: string,
  identities: ReadonlyArray<RuntimeIdentity>,
) => RuntimeIdentityLookup;
```

创建身份查找表。

| 项目         | 说明                                                |
| ------------ | --------------------------------------------------- |
| `owner`      | 所属来源的注册键，必填                              |
| `identities` | 该来源的完整身份列表，必填，可为空                  |
| 返回值       | 提供 `size`、`has(identity)` 和 `values()` 的查找表 |

```ts
// 返回对象中的方法签名
has: (identity: RuntimeIdentity) => boolean;
```

入参是待查的完整 Identity；返回是否存在的布尔值，其他来源的身份会报错

```ts
// 返回对象中的方法签名
values: () => ReadonlyArray<RuntimeIdentity>;
```

无入参；返回按路径稳定排序的只读身份列表

```ts
import { createRuntimeIdentityLookup } from '@retikz/runtime';

const nodeB = createRuntimeIdentity('example/graph', ['nodes', 'B']);
const identities = createRuntimeIdentityLookup('example/graph', [nodeB, nodeA]);

console.log(identities.size); // 2
console.log(identities.has(sameNodeA)); // true
console.log(identities.has(createRuntimeIdentity('example/graph', ['nodes']))); // false
console.log(identities.values().map(identity => identity.path));
// [['nodes', 'A'], ['nodes', 'B']]
```

`has` 查询完整身份，存在子路径不代表父路径也存在。查询同一来源中不存在的身份返回 `false`；查询其他来源的身份会报错。构造查找表时，也会拒绝来源不一致或完整路径重复的条目，空身份列表则合法。

`values()` 按路径逐段的字符串顺序返回身份，前缀相同时短路径在前；这不是插入顺序，也不受本地语言排序规则影响。查找表保存独立的身份集合，修改原列表不会改变它。

查找表解决的是集合问题，而不是状态比较：`size` 回答这份集合包含多少身份，`has` 回答一个完整身份是否在集合中，`values` 用于逐项检查或交给调用方自己的匹配逻辑。它不会返回节点的颜色等数据；需要从身份找到实体内容时，调用方还要维护自己的数据索引。

例如，旧状态的集合为 `[A, B]`，新状态为 `[A, C]`：调用方分别查询两份集合，就能识别 B 不再存在、C 是新加入的实体。A 在两份集合中都存在，只能说明身份延续，不能说明其颜色没有变化。共同前缀也不代表 `has` 会匹配子树。

## 与来源和计算协作

### 从来源收集

`collectIdentities` 接收 `capture` 产生的完整内部值，返回其中需要被标识的实体集合。Runtime 会检查这些身份的归属与重复项，并保存内部查找表。目前这个内部表没有公开查询入口，也不会自动驱动计算依赖或失效；调用方需要查询身份时，仍应使用自己的身份列表建立查找表，需要取得实体数据时则维护数据索引。

在 Source 中提供 `collectIdentities` 后，Runtime 会在捕获状态时使用这套查找逻辑（此处只说明收集契约；它在一次更新中的调用时机与失败处理留到 Runtime 篇）。复用[Source · 来源](/kernel/packages/runtime/source#定义来源)介绍的 `defineRuntimeSource(input)`，它接收来源配置并返回 Token；这里额外提供 `collectIdentities(value)`，接收内部值并返回完整身份列表。下面定义图来源：输入是节点列表，捕获后保存独立的只读数据，并收集所有节点的身份。

```ts
import { defineRuntimeSource } from '@retikz/runtime';

type GraphNode = Readonly<{ id: string; color: string }>;
type GraphState = ReadonlyArray<GraphNode>;

const graph = defineRuntimeSource<GraphState, GraphState, GraphState, never>({
  key: 'example/graph',
  value: {
    capture: input => Object.freeze(input.map(node => Object.freeze({ ...node }))),
    read: value => value,
    equals: (left, right) =>
      left.length === right.length &&
      left.every((node, index) => node.id === right[index].id && node.color === right[index].color),
  },
  collectIdentities: value => value.map(node => createRuntimeIdentity('example/graph', ['nodes', node.id])), // [!code ++]
});
```

颜色变化会改变这份状态，但不改变节点身份。`collectIdentities` 返回完整集合，不能只返回变化的节点；省略它时，Runtime 不会扫描状态自动发现身份。本例只关心节点，因此不收集边或图本身的身份。

### 计算如何使用身份

实体身份 `{ owner, path }` 与计算身份 `{ owner, key }` 解决不同的问题。例如，来源 `example/graph` 中节点 A 的实体身份是 `{ owner: 'example/graph', path: ['nodes', 'A'] }`；为图计算布局的 Computation 可以使用 `{ owner: 'example/graph', key: 'layout' }`。前者标识节点，后者标识计算本身。

即使两者的 `owner` 相同，计算仍必须声明 `sources: [graph]` 才能读取图。节点颜色改变时，身份可以不变；来源是否变化由 `equals` 判断，计算是否执行由依赖关系决定。若布局算法需要按节点复用结果，应从来源公开视图或 ChangeSet 读取身份信息，并在结果私有视图中保存自己的索引；不能查询 Runtime 内部收集的身份表。

身份比较只回答“是否同一个实体”，不回答“状态是否相等”或“缓存是否仍有效”。从身份到更新的完整关系见[生命周期](/kernel/packages/runtime/lifecycle#成员与状态)。

### 身份的使用边界

身份有两种常见用法：直接比较两个身份，或者把完整身份列表整理成查找表。下面用 API 串起这两条路径；箭头表示输入与输出的传递，不表示所有调用都必须依次执行。

<ComponentPreview files="identity-flow" size="sm" hideCode type="flow" />

`createRuntimeIdentity` 创建单个身份；`runtimeIdentityEquals` 直接比较两个身份，不需要查找表。需要查询集合时，将身份列表交给 `createRuntimeIdentityLookup`，再通过 `has` 查询、`values` 列举。Source 的 `collectIdentities` 则把完整列表交给 Runtime 做内部校验与保存，不会向调用方返回图中的查询对象。

## Core 应用

Core 用同一套身份结构标识图文档中的实体。例如，在增量比较使用的文档索引中，根的路径是 `['root']`，子实体的路径由父路径、实体类型和显式 `id` 拼接而成。对于根下一个 `id` 为 `A` 的普通节点，对应身份如下：

```ts
import { createRuntimeIdentity } from '@retikz/runtime';

const root = createRuntimeIdentity('@retikz/core/document', ['root']);
const nodeA = createRuntimeIdentity('@retikz/core/document', [...root.path, 'node', 'A']);
```

这里的 `owner` 是 Core 文档来源的注册键，`path` 区分文档内部的实体。节点只改颜色时身份不变；父路径改变时，身份也随之改变。Core 在比较前后文档、核对变更提示时使用这些身份。当前文档来源没有配置 `collectIdentities`，这份索引由 Core 的增量计算逻辑建立。
