## Overall flow

A path declares targets, steps, styles, and labels. Once its Scope finishes processing its subtree, Core resolves those declarations, builds geometry commands in local coordinates, and combines strokes, arrows, and text. The result replaces the slot reserved in Scene.

## Target binding

When traversal encounters a Path, it saves a pending record containing the input, current transforms, inherited configuration, and a primitive placeholder. After the containing Scope finishes its subtree, Core resolves targets and replaces that placeholder. Root-level paths run after the root subtree. This allows references to later nodes in the same level while preserving drawing order. See [Reference timing](/kernel/packages/core/coordinates) for visibility across Scopes.

These snapshots follow declarations `Node A → Path P(A, B) → Node B` within one Scope. The pending record appears once at the top; its displayed fields stay unchanged in this example. `T` denotes the current transform. ## Cursor and segments

The compiler consumes steps in declaration order and keeps the positions needed by later steps:

- Previous target: where an ordinary segment starts and whether it carries a node boundary.
- Latest `move` target: where `cycle` closes the current subpath.
- Pen position from special steps: an arc endpoint, for example, where the next segment continues.
- Relative baseline: the origin used by `relative` and `relativeAccumulate`.

Both paths below start at `[0, 0]` and apply `[60, 30]` twice. `relative` keeps the baseline unchanged, so both endpoints coincide. `relativeAccumulate` updates it, letting the second segment continue forward.

<ComponentPreview files="path-relative" size="md" hideCode type="illustration" />

Relative targets that can be determined early become local coordinates during resolution. Targets that depend on runtime results, such as axis-line projection, are calculated while consuming steps. A `move` starts a new pen position. Lines, folds, and curves become commands segment by segment; arcs, closed shapes, smooth curves, and generators use dedicated branches and pass on their pen positions.

| Input step                                 | Geometry change                                                                               |
| ------------------------------------------ | --------------------------------------------------------------------------------------------- |
| line / axis-line                           | Emit a line; axis-line first projects the target onto the current horizontal or vertical line |
| fold                                       | Compute orthogonal corners and connect them                                                   |
| curve / cubic / bend                       | Emit a quadratic or cubic Bezier curve using supplied or calculated controls                  |
| arc / circlePath / ellipsePath / rectangle | Emit shape commands and maintain the following pen position                                   |
| smooth / generator                         | Emit continuous curves or commands supplied by a Definition                                   |
| cycle                                      | Return to the latest move target and close the current subpath                                |

## Boundary intersections

For a connection to a node reference, Core computes attachment points on the connection boundary before generating path commands. A line from A to B follows four steps:

1. **Read reference points and node geometry**: the bound targets provide the reference points, shapes, and connection boundaries of A and B.
2. **Determine the connection direction**: the A endpoint points toward B's reference point; the B endpoint points toward A's reference point.
3. **Query the boundary intersection**: transform the direction reference point to world coordinates and select the target's `boundary`, or the node's `boundary` when unspecified. Core resolves its geometry, applies the node's `margin`, and calls the Definition's `boundaryPoint` to obtain the attachment point.
4. **Generate local path commands**: transform the intersection points back to the current Scope's local coordinates and use them as the segment endpoints.

In the opening example, the circle centers are `[0, 0]` and `[220, 0]`, both radii are 24, and margin is 0. The center-to-center direction gives attachment points `[24, 0]` and `[196, 0]`. Core first generates the line between these points; arrow shortening is applied later. See [Node Compilation](/kernel/packages/core/node-compilation#connection-boundaries) for connection surfaces and margin.

### Direction for each segment family

| Segment      | Boundary calculation                                                                                                  |
| ------------ | --------------------------------------------------------------------------------------------------------------------- |
| line         | Each endpoint points toward the opposite reference point                                                              |
| curve        | Both endpoints point toward the shared quadratic Bezier control point                                                 |
| cubic / bend | The start points toward the first control point; the end points toward the second. A bend computes its controls first |
| fold         | Build the corners, then locate where the polyline exits the start boundary and enters the end boundary                |

Bezier segments use control-point directions to determine attachment points, then generate the curve from the new endpoints and control points. This queries boundary points along direction rays; it does not solve the intersection of the entire Bezier curve with the shape.

For node targets without an anchor or offset, folds inspect successive corners to find the first segment crossing from inside to outside the boundary. A segment starting at the boundary center uses `boundaryPoint` directly; other segments use bisection to approximate the crossing. Core removes the internal polyline prefix and applies the same operation in reverse at the end, preserving the original polyline directions.

### Explicit anchors and offsets

An explicit `anchor` supplies the attachment point. An `offset` is added after that point is computed, so an offset alone still uses the directional boundary query. The offset is applied in world coordinates before conversion back to the current Scope's local coordinates.

## Arrows and labels

Labels use a sampled point and direction on the path, then text measurement determines their visual bounds. Step labels follow their segment's sampling rule; path-level labels use the combined sampling intervals. A segment parameter is not necessarily proportional to arc length. See [Path labels](/kernel/components/path/label) for position semantics.

Labels that interrupt a stroke turn their visual bounds and gap into intervals along the path. Core splits the stroke around those intervals. Arrow Definitions supply endpoint decorations and required shortening; Core shortens terminal segments and protects the arrow regions near the endpoints.

In the opening example, node boundaries determine the contact points, the label creates a middle gap, and arrow shortening affects the terminal segment. Adding the label leaves the original target references unchanged.

### How endpoints are shortened

Default endpoint arrows satisfy two conditions: **the tip reaches the target, and the tail joins a cut point on the original curve**. Core derives a contact length from arrow geometry and stroke width, then searches inward from the target for a point whose straight-line distance to the target equals that length.

1. **Keep the target**: record the original endpoints; label gaps are still calculated on the complete path.
2. **Find the contact**: search inward through the endpoint fragment, then refine the curve parameter with bisection. The search can cross multiple commands within that continuous fragment.
3. **Slice without changing shape**: retain the original curve up to the contact. Bezier slices receive recalculated control points; circular and elliptical arcs change angles while keeping their center, radii, and rotation.
4. **Place the arrow**: orient an end arrow from the contact toward the original target; reverse this for start arrows. Internal marker transforms compensate for the host tangent rotation, so SVG and Canvas consume the same result.

The stroke overlaps the arrow tail by half a stroke width to prevent antialiasing seams. This adjusts the contact while keeping the tip fixed. The arrow follows the line from the cut point to the target, which can differ slightly from the curve tangent at the cut.

`endpointOverlap` still controls how far the arrow enters the target, and automatic node boundaries retain hollow-arrow outer-edge protection. Arrows shrink to fit short paths; paths with no usable length omit endpoint arrows. Shape preservation reuses [curve slicing](/kernel/components/path/mechanism).

## Full implementation flow

Start at `resolvePath` and follow its canonical result into `emitPathPrimitive`. Read down the left column, then up the right: step consumption produces geometry commands; corner rounding, labels, and decorations follow. Traversal then replaces the placeholder with the path body and attached primitives.

<ComponentPreview files="path-implementation" size="lg" hideCode type="flow" />

Output can contain multiple stroke fragments, text, and decoration primitives. An output group carries the path's own rotation and scale. Outer groups retain Scope transforms, and the renderer consumes this structured result.

An unresolved ordinary target or a missing required predecessor produces a warning in the relevant branch and skips the whole path. Some steps with no drawable content can emit no commands. Contract violations such as invalid generator output throw errors, so failure behavior depends on the branch.
