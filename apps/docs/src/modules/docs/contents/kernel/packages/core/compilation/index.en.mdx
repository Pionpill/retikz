The preceding pages on [Resolution](/kernel/packages/core/resolution), [Capability Registration](/kernel/packages/core/definitions) and [Capability Dependencies](/kernel/packages/core/providers) cover resolve and compilation preparation: how declarations acquire concrete semantics and how their definitions are registered and assembled. This page connects that preparation to compile, where resolved data becomes layout, geometry and emitted output. The following pages expand Scope, Node, Coordinate, Path and Composite compilation, then explain compilation output.

Nodes provide shapes and content, Coordinates provide named positions, Scopes organize local spaces, and Paths connect geometric targets. We follow nodes A and B and their connecting path. Core supplies entity resolution and computation; Reconciler calls these stages as dependencies become ready.

## Overall Flow

For an entity, resolve establishes what its declaration means; compile computes its position, dimensions and output. Source code often names the resolved data canon and the computed result compiled:

| Concept  | Meaning                                                                                                           | Node example                                                                                                             |
| -------- | ----------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| resolve  | Apply inheritance and definitions to resolve defaults, shorthand and capability parameters into a consumable form | Resolve style, bind the shape definition and prepare layout configuration, producing CanonicalNode                       |
| canon    | Short for canonical: resolved entity data, usually typed as CanonicalXxx                                          | Effective style, shape bindings and layout requirements; dimensions and referenced positions are computed during compile |
| compile  | Consume resolved data and context such as measurement and positioning to compute the entity's results             | Measure content, lay out the shape, evaluate position, then emit shape and text primitives                               |
| compiled | An entity's computed results, usually typed as CompiledXxx                                                        | CompiledNode contains layout and emission results for geometry queries, parent layout and Scene assembly                 |

For Node, the data flow is **IRNode → resolveNode → CanonicalNode → compileNode → CompiledNode**. canon establishes semantics and configuration; compiled contains results computed in the current context. Each entity organizes its products as needed: PathResolution passes canon together with its definition and other resolution data to compilePath; CompiledCoordinate provides only the evaluated position. Emitted products are assembled into a Scene for a rendering backend to consume.

Compilation starts with the children of an IRScene. Each entity resolves the style, definitions and position context needed for its current stage, then computes layout or geometry. Nodes and Coordinates provide queryable positions. Scopes use child layouts to establish envelopes and transforms. Paths compute connections once target geometry is ready. The emitted results form the Scene.

## Follow One Diagram Through the Stages

Both nodes below have a minimum 60 × 40 outer box, at centers [0, 0] and [180, 0], with zero padding and margin. The path is declared first. Its final segment still runs from A's right boundary [30, 0] to B's left boundary [150, 0].

<ComponentPreview files={['compilation-example', 'compilation-example.data']} size="xs" hideCode type="illustration" />

```ts
import { SceneReconciler } from '@retikz/reconciler';
import type { IRScene } from '@retikz/core';

const ir: IRScene = {
  type: 'scene',
  version: 1,
  children: [
    {
      type: 'path',
      children: [
        { type: 'step', kind: 'move', to: { id: 'A' } },
        { type: 'step', kind: 'line', to: { id: 'B' } },
      ],
    },
    {
      type: 'node',
      id: 'A',
      position: [0, 0],
      text: 'A',
      layout: { minimumSize: { width: 60, height: 40 }, padding: 0, margin: 0 },
    },
    {
      type: 'node',
      id: 'B',
      position: [180, 0],
      text: 'B',
      layout: { minimumSize: { width: 60, height: 40 }, padding: 0, margin: 0 },
    },
  ],
};
const reconciler = new SceneReconciler({}, { incremental: false });
try {
  const result = reconciler.mount(ir).compilation.result;
  console.log(result.scene);
} finally {
  reconciler.dispose();
}
```

A node first becomes a CanonicalNode with effective style and capability bindings, then geometry and emitted output. The path retains named targets until node geometry is published; it can then select boundary intersections and produce commands.

## Entity Dependencies and Execution Order

Each entity runs when the context it needs to read is available:

| Entity     | Processing                                                                                                            | Results used downstream                                                          |
| ---------- | --------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| Node       | Resolve inherited style and shape definitions, measure content, determine shape size and position                     | Query geometry such as anchors and boundaries, plus shape and content primitives |
| Coordinate | Evaluate a position expression in the current space using existing named references                                   | A named position for subsequent placement and paths                              |
| Scope      | Pass inheritance and spatial context to children, then derive an envelope and placement transforms from child layouts | Group geometry, transforms, clipping and group attributes                        |
| Path       | Read target geometry, convert it to the owning space, compute endpoints, route and decorations                        | Path primitives, layout bounds and resource references                           |

In the example, visiting the Path declaration reserves an output slot. Once A and B finish layout and publish geometry, the Path can query their boundaries and determine the endpoints [30, 0] and [150, 0]. If the nodes belong to a Scope, path queries also need its established transforms; the Scope envelope in turn depends on child layout results.

Node placement and Coordinate positions are evaluated during their visit, so referenced targets must already be readable. Paths have dedicated deferred processing, which supports the forward references in this example. Unresolvable references report failure according to the relevant contract.

Evaluation and drawing order are tracked separately. A completed deferred Path fills its original declaration slot. Sibling output is then stably sorted by zIndex, preserving order for equal values. Thus the example computes node geometry first while retaining the path's drawing position before the nodes.
