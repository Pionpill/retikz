This page follows one synchronous compilation from a complete IR input to a Scene ready for a renderer. React / Vanilla input construction happens upstream, rendering happens downstream, and subsequent updates belong to another execution.

## Input and example

IR stores drawing declarations such as “place a node here” and “connect A to B.” Scene stores primitives with resolved geometry and appearance, such as rectangles, text, and path commands. `compileToScene` performs this conversion and returns a result containing the Scene. Its public signature, with generic details omitted, is:

```ts
compileToScene(ir: IRScene, options?: CompileOptions): CompileResult
```

| Input / output     | Meaning in this page                                                            |
| ------------------ | ------------------------------------------------------------------------------- |
| `ir`               | A complete drawing declaration conforming to the Core contract                  |
| `options`          | Measurement, extension definitions, and output settings for this call; optional |
| `result.scene`     | Laid-out primitives, the canvas bounds, and drawing resources                   |
| `result.artifacts` | Composite outputs and explicitly requested node layout data                     |

`compileToScene` accepts typed IR; it does not call `SceneSchema.parse` on the entire tree at entry. External data such as JSON should pass through the schema boundary first. Compilation still checks constraints that require a Definition or layout context.

Our example contains two rectangular nodes, each 60 wide and 40 high, centered at `[0, 0]` and `[180, 0]`. The connection is deliberately declared before the nodes. The short labels A and B fit inside the specified minimum size.

<ComponentPreview files={['compilation-example', 'compilation-example.data']} size="xs" hideCode type="illustration" />

Here is the Core input for that drawing. `minimumSize` constrains the node border, while `padding` and `margin` set inner spacing and the outer offset of the connection boundary. Setting both to zero places this example's endpoints directly on the rectangles.

```ts
import { compileToScene, type IRScene } from '@retikz/core';

const ir: IRScene = {
  version: 1,
  type: 'scene',
  children: [
    {
      type: 'path',
      children: [
        { type: 'step', kind: 'move', to: { id: 'A' } },
        { type: 'step', kind: 'line', to: { id: 'B' } },
      ],
    },
    {
      type: 'node',
      id: 'A',
      position: [0, 0],
      text: 'A',
      layout: { minimumSize: { width: 60, height: 40 }, padding: 0, margin: 0 },
    },
    {
      type: 'node',
      id: 'B',
      position: [180, 0],
      text: 'B',
      layout: { minimumSize: { width: 60, height: 40 }, padding: 0, margin: 0 },
    },
  ],
};

const result = compileToScene(ir, { padding: 10 });
```

The preview shows the final geometry. We will follow the same path as its `{ id: 'A' }` and `{ id: 'B' }` references become a segment from `[30, 0]` to `[150, 0]`.

## Compilation context

Core needs a way to measure text, resolve shapes, and collect shared drawing resources. Two concepts describe how capabilities are supplied:

- Definition: an implementation of a shape, path, or composite capability.
- Registry: a lookup table used to find a Definition by name during this compilation.

`createSharedCompileContext` assembles built-in and caller-provided definitions into read-only registries and retains measurement services and numeric settings. The internal `createFullCompileContext` uses that shared context to create a per-call workspace: the root theme, isolated geometry state, paint / clip resources, and warning collection. Without injected text measurement, it uses an approximate built-in measurer. Core itself does not read the DOM.

`FullCompileContext` holds `shared`, `workspace`, `compositeInputs`, and `theme`. `shared` holds reusable `registries`, `host`, `layout`, and `limits`. `CompileContextRegistries` contains `shapeRegistry`, `boundaryRegistry`, `clipRegistry`, `arrowRegistry`, `markRegistry`, `patternRegistry`, `pathRegistry`, `compositeRegistry`, and `themeRegistry`. Input options still use definition-array fields such as `shapes` and `clips`.

Full compilation, element compilation, and probes each create an isolated `WorkspaceCompileContext` through `createWorkspaceCompileContext`. It holds `nodeBoundaryContext`, `paintRegistry`, `clipRegistry`, and `diagnostics`. Diagnostics are appended through `diagnostics.collect` and exposed through the read-only `diagnostics.warnings`; the external `CompileOptions.onWarn` still receives diagnostics after success. The full context separately carries the root `theme` and `compositeInputs`; element computation adds reference-read and position-resolution state. Creation and consumption are unified, while mutable state stays isolated per computation. Generated resources and diagnostics are published only with successful results.

The shared context has four groups:

| Group        | Contents                                                                     |
| ------------ | ---------------------------------------------------------------------------- |
| `registries` | Registries combining built-in and external definitions                       |
| `host`       | Text measurement and TeX lowering services                                   |
| `layout`     | Layout padding, node and label distances, root font size, and output rounder |
| `limits`     | Depth limits for composite expansion and clip conversion                     |

Compilation uses the host measurement service through `shared.host.measureText` and normalizes metrics where they are consumed. The context has no separate measurement entry or compilation-wide text cache. Weave can reuse the shared context across incremental updates within one instance, while resource workspaces remain isolated per computation. Input fields in `CompileOptions` remain flat; the shared context groups the configuration after applying defaults.

Shared context creation validates numeric options even for an empty scene: `padding` and `labelDistance` must be finite and nonnegative, and `fontSize` must be finite and positive. `nodeDistance` must be finite; negative values offset in the opposite direction. `precision` must be a nonnegative integer with a finite `10 ** precision`; this does not guarantee overflow-free arithmetic for arbitrarily large coordinates. `maxCompositeDepth` and `maxClipDepth` must be nonnegative safe integers; `maxCompositeDepth: 0` prevents composite expansion.

This example uses the built-in rectangle and path capabilities. Compilation traverses the input IR directly; composites are processed when traversal reaches them.

Traversal also creates state for this execution: emitted primitives, accumulated bounds, and a namespace. The namespace stores queryable layouts by id so that a path can find the geometry of A and B. This state belongs to one full compilation and does not retain update results across calls.

## Node resolution

`compileChildrenToPrimitives` dispatches children in declaration order. Here it records the pending Path before processing A and B. Three results explain the work inside a node:

- CanonicalNode: the node after effective styles are merged, defaults are filled, and paints are resolved; `fill` / `stroke` directly carry the paint resolution results.
- NodeResolution: CanonicalNode together with the selected shape and connection boundary, ready for layout.
- CompiledNodeLayout: the measured and positioned result, grouped into node properties, shape, boundary, geometry, text layout, and labels.

`resolveNode` determines effective configuration and capability bindings. `compileNodeResolution` then prepares body and label text properties and computes typesetting, node size, and position. The returned `properties` field holds complete effective properties and identity, while `layout` holds computed geometry and typesetting. ## Path resolution

Node layout finishes before paths that depend on those nodes are resolved. Traversal visits children in declaration order:

1. On a Node, Core immediately resolves its configuration, measures and positions it, registers its layout, and emits its primitives.
2. On a Path, Core records a pending task and inserts a placeholder, postponing node-reference resolution and path emission.
3. When the current container finishes, Core looks up the registered node layouts, resolves the pending paths, and emits their primitives.

This order applies within each container. A Scope recursively processes its children and handles its pending paths as it finishes. The root handles its pending paths after visiting its children. Paths inside a Scope can therefore be processed before all nodes in the entire tree have been visited.

A path may reference nodes declared later. `queuePathChild` saves a pending path record and inserts a placeholder into the current primitive array. The record preserves the path input, style and coordinate environment, plus references to the placeholder and its owning array.

Each row below shows an array state from our example. Group A and Group B contain their node's rectangle and text; cell labels summarize those structures.

<ComponentPreview files="compilation-slots" size="xl" hideCode type="illustration" />

Once A and B are registered, `flushPendingPathEmissions` looks up their layouts, resolves the path, and emits its primitives. With only node ids as targets, this example clips the endpoints to the connection boundaries. A's right edge at `[30, 0]` and B's left edge at `[150, 0]` become the visible segment endpoints.

Core then finds the placeholder in its original array and replaces it with the actual PathPrimitive. Although computed after the nodes, the path remains at index 0. Once paths are filled, a stable `zIndex` sort preserves declaration order among equal values. All placeholders must be gone before Scene is returned.

The final path contains these fields:

```ts
{
  type: 'path',
  commands: [
    { kind: 'move', to: [30, 0] },
    { kind: 'line', to: [150, 0] },
  ],
}
```

Deferred work runs when its enclosing group finishes. It supports this example's Path references to later nodes in the same group. A node's own relative position needs its target during layout, so forward references are not available for every position expression.

## Scope processing

When traversal encounters a Scope, it enters that subtree before continuing with the parent's next child. Core prepares styles, a theme, a transform chain, and separate result containers, then visits `children` in declaration order: Nodes are laid out immediately, Paths are queued, and nested Scopes recursively follow the same steps.

The diagram follows entry, recursive processing, and return. A nested Scope completes this same sequence before traversal resumes in its parent:

<ComponentPreview files="compilation-scope" size="md" hideCode type="flow" />

For example, let S contain Node A, Scope T, and Node B in that order. Core processes A, enters T, finishes T's children, layout, and pending paths, then returns to S and processes B. Once all of S's children are complete, Core determines S's bounds and final placement, updates queryable layouts, processes S's pending paths, and passes a Group to the parent.

Every Scope has its own child traversal context, but it shares the current namespace frame by default. Suppose the outer frame already contains node A, and the Scope declares nodes A and B:

| Operation                     | `localNamespace: false` (default)                                        | `localNamespace: true`                                                              |
| ----------------------------- | ------------------------------------------------------------------------ | ----------------------------------------------------------------------------------- |
| Enter Scope                   | Reuse the current frame                                                  | Push a new local frame                                                              |
| Register inner A and B        | Write to the current frame; replace A and issue a duplicate-name warning | Write to the local frame; inner A shadows outer A                                   |
| Look up a name inside         | Search from the current frame outward                                    | Search the local frame first, then outer frames on a miss                           |
| After returning to the parent | Inner A and B remain accessible by name                                  | The local frame is gone; A resolves to outer A, and inner B is no longer accessible |

Pending paths inside the Scope are resolved before the local frame is popped, so they can still reference inner nodes. Popping removes name visibility, not the primitives already emitted into Scene. If the Scope itself has an id, Core registers it in the parent frame before pushing the local frame and updates it to the final layout during finalization. Outside references can therefore still target the whole group by that id.

Scene output can retain local geometry and Group transforms. Named queries use the coordinate projection they need; the output does not require every point to be expanded into world coordinates.

Composite entries join compilation through registered Definitions, and the basic IR they produce follows the same processing steps; see [Composite implementation](/kernel/packages/core/composite-compilation).

## Assemble the result

After child compilation, `compileSceneSnapshot` collects ordered primitives, paint and clip resources, and supported root animation configuration. An explicit `viewBox` determines the canvas bounds directly. Otherwise, Core computes them from accumulated layout bounds and `padding`.

The example's content spans `[-30, -20]` to `[210, 20]`. Adding 10 units on all sides produces this `result.scene.layout`:

```ts
{ x: -40, y: -30, width: 260, height: 60 }
```

This step determines the canvas bounds without moving A or B again. The output `primitives` are the path, Group A, and Group B, in that order. This example has no gradient or clip resources, so `resources` is omitted.

Alongside Scene, `artifacts` contains domain values returned by composites and is empty when none are produced. The result contains only `scene` and `artifacts`, both from the same compilation. See [Compilation output](/kernel/packages/core/compilation-output) for the fields and domain coordinate conventions.

Warnings and fatal errors have different outcomes. Recoverable cases follow the capability's degradation rules: for example, a missing path target can produce a warning and remove that path's placeholder. The synchronous entry dispatches collected warnings only after full compilation succeeds. A fatal error terminates the call without returning a partial Scene.

## Independent compilation and reusable state

A caller that schedules elements itself can retain a `SharedCompileContext` and compile one basic element through these entries. They share resolve, layout and emit logic with full compilation, do not recursively compile other elements, and do not register names automatically.

| Entry               | Completed state      | Retained data                                                                        |
| ------------------- | -------------------- | ------------------------------------------------------------------------------------ |
| `compileNode`       | `CompiledNode`       | CompiledNodeLayout in `layout`; primitives, resources and visible bounds in `output` |
| `compileCoordinate` | `CompiledCoordinate` | `id` and local `position`; no visible output                                         |
| `compilePath`       | `CompiledPath`       | Complete `output`, including host processing for custom kinds                        |
| `compileScope`      | `CompiledScope`      | `envelope`, `group` without children, and its own `output`                           |

`CompiledNodeLayout` contains geometry used by reference and layout calculations. Cache `CompiledNode` when reusing the complete element result, including its drawing state and output.

```ts
import {
  assembleCompileOutputs,
  assembleSceneCompilationSnapshot,
  compileNode,
  computeCompileOutputBounds,
  createSharedCompileContext,
  resolveScopeContext,
} from '@retikz/core';

const shared = createSharedCompileContext();
const result = compileNode(
  { type: 'node', id: 'A', position: [0, 0], text: 'A' },
  {
    shared,
    context: resolveScopeContext({}, shared),
    irPath: ['children', 0],
  },
);

if (result.status === 'compiled') {
  const output = assembleCompileOutputs([result.compiled.output], shared);
  const prepared = assembleSceneCompilationSnapshot({
    root: {},
    primitives: output.primitives,
    resources: output.resources,
    layoutBounds: computeCompileOutputBounds(output),
    round: shared.layout.round,
    diagnostics: result.diagnostics,
  });
  // prepared.result.scene is ready for a renderer; diagnostics are not dispatched
}
```

An element call returns `compiled` or `pending`. The completed branch contains the compiled state and diagnostics; pending publishes neither partial state nor diagnostics. The caller supplies `lookupReference(name)`: return `undefined` for a missing name, `ready` with a `layout` and optional `irPath` for a completed reference, `pending` for an unfinished reference, or `ancestor` for a forbidden ancestor Scope. Core converts unfinished references to a pending result and reports ancestor references as drawing errors. Other lookup callback failures are retained as the cause of a Core error.

The caller owns name registration, namespaces and read records. Reconciler searches parent frames inside-out and records each missed or matched frame for binding checks and dependency refresh. Register only names visible at the declaration site: pending must not enable forward references for Node / Scope. Path can wait for its references. `projectCompileReference` projects completed state into registerable reference geometry.

Scope calculation has two stages. `prepareScopeCompilation` resolves inherited context and preliminary transforms; `compileScope` consumes completed child layouts to determine the envelope and final transforms. Pass the established ancestor transforms when compiling children. Envelope-dependent placement is projected after Scope completion. `assembleScopeOutput` combines the Scope's own output with child outputs without running providers again or storing a duplicate subtree in cached state.

Resource IDs are local to each output fragment. `assembleCompileOutputs` imports and remaps resources and stably sorts sibling zIndex values; `assembleScopeOutput` also handles Scope wrapping, clipping and bounds. The caller selects the current output contributions, aggregates their visible bounds with `computeCompileOutputBounds`, then calls `assembleSceneCompilationSnapshot` to finalize viewBox, padding, root animations, diagnostics and provenance. Supplied Composite artifacts must already be in final declaration order and belong to this result. Assembly does not recompile elements or determine incremental reuse.

These entries provide Core's scheduling primitives. Reconciler owns name mapping, dependency invalidation, version isolation and publication; the interface does not construct or update the Weave tree automatically. Callers must not mutate data reachable from published compiled state. Changes to shared definitions or measurement services invalidate affected caches. Compiled state containing Definitions and text emit functions cannot be serialized directly into Worker messages.

## Weave integration

Core and Weave share `createCompileChildPath(prefix, index)`, which appends `'children'` and a numeric index to a property-path array. The path identifies source and diagnostic locations, not cross-version identity.

Weave is the compilation tree retained by Reconciler. Each node holds its own input, effective context and Core compilation state. The root holds the shared context, Scene configuration, container index and version-specific read records. Automatically assigned Scope addresses stay outside the IR and do not affect drawing envelopes.

The Reconciler session holds a stable WeaveRoot through its Weave reconciler as the tree entry. Nodes and Root each retain committed current and candidate pending states; parent-child links, dependencies and indexes reference stable node objects. Candidate writes isolate the affected state and mutable collections while sharing unchanged Core products read-only. Changing a child’s properties does not copy its Scope’s children array; changing membership does. Commit switches the states touched by the batch and retains recovery references until confirmation. A node reference does not provide a historical snapshot.

Basic elements create nodes and bindings in declaration order. Node and Coordinate consume references visible at their declaration site. Scope prepares context, compiles its children and envelope, then completes its deferred paths. A top-level Path can wait for nodes in both Scopes to be published. Reconciler owns name registration and binding replacement, using Core's `createDuplicateCompileWarning` for same-frame replacement diagnostics; `projectScopeCompileLayouts` and `projectPublishedCompileLayout` reuse Core's envelope-contribution and final reference-projection rules.

Reconciler then asks Core to assemble the complete output. `CompileProvenanceTracker` retains primitive ownership through resource remapping and Scope wrapping, pairing final provenance paths with the sorted Scene without another full compilation. The Reconciler session retains the previous result if preparation fails and publishes the matching tree and output only after success.

The internal Weave reconciler accepts WeaveBatch on a mounted Root: it applies insert, update and remove operations in order, then computes from the final inputs. Context follows declaration links and dependency invalidation follows consumers. Scope preparation, child layout, envelopes and final projections follow Core's evaluation order, preserving deferred Path references. Unaffected compiled products can be reused while their inputs, declaration positions and name bindings remain valid. Diagnostics that require regeneration cause the relevant elements to be recomputed. Invalidation is conservative: a Scope change may recompute its entire subtree, without style/layout filtering.

Updates return complete output with commit, finish and rollback operations. Preparation preserves committed state; rollback remains available after commit until final confirmation releases recovery references. Rebuilding name indexes, provenance and output may still traverse the whole tree, so local compilation does not imply local total update cost.

Reconciler `replace` accepts complete IR and recompiles it; `update` accepts a `WeaveBatch` for an existing basic-element tree. A batch must belong to the current session result, and Composite scenes do not support that entry. Ordinary React and Vanilla input updates still use complete replacement. The Render commit target converts changed compilation output to `replaceScene`; this does not imply fine-grained backend Patch updates. Composite input uses Core full preparation, preserving probes, instance inputs, artifacts.
