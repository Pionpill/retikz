This page follows one synchronous compilation from a complete IR input to a Scene ready for a renderer. React / Vanilla input construction happens upstream, rendering happens downstream, and subsequent updates belong to another execution.

## Input and example

IR stores drawing declarations such as “place a node here” and “connect A to B.” Scene stores primitives with resolved geometry and appearance, such as rectangles, text, and path commands. `compileToScene` performs this conversion and returns a result containing the Scene. Its public signature, with generic details omitted, is:

```ts
compileToScene(ir: IRScene, options?: CompileOptions): CompileResult
```

| Input / output     | Meaning in this page                                                            |
| ------------------ | ------------------------------------------------------------------------------- |
| `ir`               | A complete drawing declaration conforming to the Core contract                  |
| `options`          | Measurement, extension definitions, and output settings for this call; optional |
| `result.scene`     | Laid-out primitives, the canvas bounds, and drawing resources                   |
| `result.artifacts` | Domain outputs explicitly returned by Composites                                |

`compileToScene` accepts typed IR; it does not call `SceneSchema.parse` on the entire tree at entry. External data such as JSON should pass through the schema boundary first. Compilation still checks constraints that require a Definition or layout context.

Our example contains two rectangular nodes, each 60 wide and 40 high, centered at `[0, 0]` and `[180, 0]`. The connection is deliberately declared before the nodes. The short labels A and B fit inside the specified minimum size.

<ComponentPreview files={['compilation-example', 'compilation-example.data']} size="xs" hideCode type="illustration" />

Here is the Core input for that drawing. `minimumSize` constrains the node border, while `padding` and `margin` set inner spacing and the outer offset of the connection boundary. Setting both to zero places this example's endpoints directly on the rectangles.

```ts
import { type IRScene } from '@retikz/core';
import { compileToScene } from '@retikz/reconciler';

const ir: IRScene = {
  version: 1,
  type: 'scene',
  children: [
    {
      type: 'path',
      children: [
        { type: 'step', kind: 'move', to: { id: 'A' } },
        { type: 'step', kind: 'line', to: { id: 'B' } },
      ],
    },
    {
      type: 'node',
      id: 'A',
      position: [0, 0],
      text: 'A',
      layout: { minimumSize: { width: 60, height: 40 }, padding: 0, margin: 0 },
    },
    {
      type: 'node',
      id: 'B',
      position: [180, 0],
      text: 'B',
      layout: { minimumSize: { width: 60, height: 40 }, padding: 0, margin: 0 },
    },
  ],
};

const result = compileToScene(ir, { padding: 10 });
```

The preview shows the final geometry. We will follow the same path as its `{ id: 'A' }` and `{ id: 'B' }` references become a segment from `[30, 0]` to `[150, 0]`.

## Compilation context

Reconciler uses Foundation's `createIdAllocator(prefix)` to allocate runtime Scope IDs unique within a tree, including anonymous Scopes. Callers own Scope prefixes and root identity. Each tree owns an allocator, shared by its speculative compilation branches; deletion, rollback, or discarding a branch never reuses allocated IDs. Hosts that address multiple trees must supply non-overlapping prefix namespaces. Reconciler preserves identity for each element instance's lifetime. Runtime IDs are not written into author `id` fields or Scene output and do not change local name shadowing.

Reconciler needs a way to measure text, resolve shapes, and collect shared drawing resources. Two concepts describe how capabilities are supplied:

- Definition: an implementation of a shape, path, or composite capability.
- Registry: a lookup table used to find a Definition by name during this compilation.

`createSharedCompileContext` assembles built-in and caller-provided definitions into read-only registries and retains measurement services and numeric settings. The internal `createCompileRuntime` uses that shared context to create a per-call workspace: the root theme, isolated geometry state, paint / clip resources, and warning collection. Without injected text measurement, it uses an approximate built-in measurer. Core itself does not read the DOM.

`CompileRuntime` separates stable inputs in `context` from mutable `state`. `CompileContext` extends `SharedCompileContext` directly with the entry `theme`, `compositeInputs`, and final Scene viewport `padding`, retaining the `registries`, `host`, `layout`, and `limits` groups. Probes reuse these groups, override the entry theme and component inputs, and clear `padding` to keep final viewport configuration out of subtree measurement. Input options keep definition arrays such as `shapes` and `clips`.

State is grouped by its isolation boundary:

| Group       | Contents                                                                    | During a probe                                            |
| ----------- | --------------------------------------------------------------------------- | --------------------------------------------------------- |
| `workspace` | Boundary caches, paint / clip resources, diagnostic collection              | Created independently                                     |
| `execution` | Namespace stack, provenance, transform cache, diagnostic occurrence binding | Namespace is forked; other state is created independently |
| `composite` | Component handles, measurement cache, replay tokens                         | Shared with the owning root compilation                   |

Full compilation, element compilation, and probes create isolated workspaces through `createWorkspaceCompileState`. `createCompileEnvironment` creates tree execution state and binds diagnostic collection to the current occurrence without modifying the supplied base workspace. Diagnostics are appended through `diagnosticCollector.collect` and read through `diagnosticCollector.warnings`; external `CompileOptions.onWarn` callbacks still receive diagnostics after success.

Each recursive subtree uses `SubtreeCompileRuntime`: its `context` holds effective styles, accumulated transforms, layout constraints, and declaration positions; its `state` collects primitives, layouts, bounds, deferred paths, and artifacts. Entering a child Scope derives a new inherited context. Output containers are isolated or explicitly shared according to their subtree ownership. Reconciler creates its candidate workspace and adapts reference lookup, measurement, resource registration, and diagnostics to each stage’s narrow context. One-shot compilation, non-incremental sessions, and Weave updates all call these stages through the same CompileManager / SubtreeCompiler.

After successful compilation, repeated declarations of an ID in the same namespace produce one `DUPLICATE_NODE_ID` diagnostic. Its message lists every location in declaration order, and `path` points to the last declaration; the last declaration still wins name resolution. Independent namespaces are handled separately. Probed declarations count toward the actual destination namespace only when selected for replay; discarded probes publish no diagnostics.

Reconciler owns stable environments and per-execution workspaces in `compile/runtime`, including namespaces, transform caches, and component state. Core organizes atomic computation by domain under `compile`: node, path, and scope. Node layout types live in `compile/node/types.ts`; Scope bounds contributions live in `compile/scope/types.ts`. Layout projection and position reference adaptation belong to Core; tree traversal and stage scheduling belong to Reconciler.

The shared context has four groups:

| Group        | Contents                                                     |
| ------------ | ------------------------------------------------------------ |
| `registries` | Registries combining built-in and external definitions       |
| `host`       | Text measurement and TeX lowering services                   |
| `layout`     | Node and label distances, root font size, and output rounder |
| `limits`     | Depth limits for composite expansion and clip conversion     |

Compilation uses the host measurement service through `shared.host.measureText` and normalizes metrics where they are consumed. The context has no separate measurement entry or compilation-wide text cache. Weave can reuse the shared context across incremental updates within one instance, while resource workspaces remain isolated per computation. Input fields in `CompileOptions` remain flat; the shared context groups the configuration after applying defaults.

Shared context creation validates numeric options even for an empty scene: `labelDistance` must be finite and nonnegative, and `fontSize` must be finite and positive. `nodeDistance` must be finite; negative values offset in the opposite direction. `precision` must be a nonnegative integer with a finite `10 ** precision`; this does not guarantee overflow-free arithmetic for arbitrarily large coordinates. `maxCompositeDepth` and `maxClipDepth` must be nonnegative safe integers; `maxCompositeDepth: 0` prevents composite expansion.

Scene assembly separately validates `padding` as finite and nonnegative, including when an explicit viewBox is supplied.

This example uses the built-in rectangle and path capabilities. Compilation traverses the input IR directly; composites are processed when traversal reaches them.

Traversal also creates state for this execution: emitted primitives, accumulated bounds, and a namespace. The namespace stores queryable layouts by id so that a path can find the geometry of A and B. This state belongs to one full compilation and does not retain update results across calls.

## Node resolution

`compileChildrenToPrimitives` dispatches children in declaration order. Here it records the pending Path before processing A and B. Three results explain the work inside a node:

- CanonicalNode: the node with inherited styles, defaults, body and label fonts, and paints resolved; `fill` / `stroke` directly carry the paint resolution results.
- NodeResolution: CanonicalNode together with the selected shape and connection boundary, ready for layout.
- CompiledNodeLayout: the measured and positioned result, grouped into node properties, shape, boundary, geometry, text layout, and labels.

`resolveNode` uses the root font size and TeX gating flag to resolve effective configuration, capability bindings, and body and label fonts, segments, and styles into a complete `CanonicalNode`. `layoutNode` consumes those properties to measure and wrap text and compute node size and position; trying another width does not parse text again. The returned `properties` field retains the resolution result, while `layout` holds computed geometry and typesetting. Stroke width, color, and dashes share one property source; label pins also retain their complete configuration. `emitNodePrimitives` consumes layout and current properties to produce Scene primitives. Physical text lines retain their authored-line index so painting can read current line styles without wrapping again. This structure does not replace change-impact analysis; Weave still needs a separate capability contract for classified scheduling.

## Path resolution

Node layout finishes before paths that depend on those nodes are resolved. Traversal visits children in declaration order:

1. On a Node, Reconciler immediately resolves its configuration, measures and positions it, registers its layout, and emits its primitives.
2. On a Path, Reconciler records a pending task and inserts a placeholder, postponing node-reference resolution and path emission.
3. When the current container finishes, Reconciler looks up the registered node layouts, resolves the pending paths, and emits their primitives.

This order applies within each container. A Scope recursively processes its children and handles its pending paths as it finishes. The root handles its pending paths after visiting its children. Paths inside a Scope can therefore be processed before all nodes in the entire tree have been visited.

A path may reference nodes declared later. `queuePathChild` saves a pending path record and inserts a placeholder into the current primitive array. The record preserves the path input, style and coordinate environment, plus references to the placeholder and its owning array.

Each row below shows an array state from our example. Group A and Group B contain their node's rectangle and text; cell labels summarize those structures.

<ComponentPreview files="compilation-slots" size="xl" hideCode type="illustration" />

Once A and B are registered, `flushPendingPathEmissions` looks up their layouts, resolves the path, and emits its primitives. With only node ids as targets, this example clips the endpoints to the connection boundaries. A's right edge at `[30, 0]` and B's left edge at `[150, 0]` become the visible segment endpoints.

Reconciler then finds the placeholder in its original array and replaces it with the actual PathPrimitive. Although computed after the nodes, the path remains at index 0. Once paths are filled, a stable `zIndex` sort preserves declaration order among equal values. All placeholders must be gone before Scene is returned.

The final path contains these fields:

```ts
{
  type: 'path',
  commands: [
    { kind: 'move', to: [30, 0] },
    { kind: 'line', to: [150, 0] },
  ],
}
```

Deferred work runs when its enclosing group finishes. It supports this example's Path references to later nodes in the same group. A node's own relative position needs its target during layout, so forward references are not available for every position expression.

## Scope processing

When traversal encounters a Scope, it enters that subtree before continuing with the parent's next child. Reconciler prepares styles, a theme, a transform chain, and separate result containers, then visits `children` in declaration order: Nodes are laid out immediately, Paths are queued, and nested Scopes recursively follow the same steps.

The diagram follows entry, recursive processing, and return. A nested Scope completes this same sequence before traversal resumes in its parent:

<ComponentPreview files="compilation-scope" size="md" hideCode type="flow" />

For example, let S contain Node A, Scope T, and Node B in that order. Reconciler processes A, enters T, finishes T's children, layout, and pending paths, then returns to S and processes B. Once all of S's children are complete, Reconciler determines S's bounds and final placement, updates queryable layouts, processes S's pending paths, and passes a Group to the parent.

Every Scope has its own child traversal context, but it shares the current namespace frame by default. Suppose the outer frame already contains node A, and the Scope declares nodes A and B:

| Operation                     | `localNamespace: false` (default)                                        | `localNamespace: true`                                                              |
| ----------------------------- | ------------------------------------------------------------------------ | ----------------------------------------------------------------------------------- |
| Enter Scope                   | Reuse the current frame                                                  | Push a new local frame                                                              |
| Register inner A and B        | Write to the current frame; replace A and issue a duplicate-name warning | Write to the local frame; inner A shadows outer A                                   |
| Look up a name inside         | Search from the current frame outward                                    | Search the local frame first, then outer frames on a miss                           |
| After returning to the parent | Inner A and B remain accessible by name                                  | The local frame is gone; A resolves to outer A, and inner B is no longer accessible |

Pending paths inside the Scope are resolved before the local frame is popped, so they can still reference inner nodes. Popping removes name visibility, not the primitives already emitted into Scene. If the Scope itself has an id, Reconciler registers it in the parent frame before pushing the local frame and updates it to the final layout during finalization. Outside references can therefore still target the whole group by that id.

Scene output can retain local geometry and Group transforms. Named queries use the coordinate projection they need; the output does not require every point to be expanded into world coordinates.

Composite entries join compilation through registered Definitions, and the basic IR they produce follows the same processing steps; see [Composite implementation](/kernel/packages/core/composite-compilation).

## Assemble the result

After child compilation, `compileSceneSnapshot` collects ordered primitives, paint and clip resources, and supported root animation configuration. An explicit `viewBox` determines the canvas bounds directly. Otherwise, Reconciler computes them from accumulated layout bounds and `padding`.

The example's content spans `[-30, -20]` to `[210, 20]`. Adding 10 units on all sides produces this `result.scene.layout`:

```ts
{ x: -40, y: -30, width: 260, height: 60 }
```

This step determines the canvas bounds without moving A or B again. The output `primitives` are the path, Group A, and Group B, in that order. This example has no gradient or clip resources, so `resources` is omitted.

Alongside Scene, `artifacts` contains domain values returned by composites and is empty when none are produced. The result contains only `scene` and `artifacts`, both from the same compilation. See [Compilation output](/kernel/packages/core/compilation-output) for the fields and domain coordinate conventions.

Warnings and fatal errors have different outcomes. Recoverable cases follow the capability's degradation rules: for example, a missing path target can produce a warning and remove that path's placeholder. The synchronous entry dispatches collected warnings only after full compilation succeeds. A fatal error terminates the call without returning a partial Scene.

## Independent compilation and reusable state

Core provides composable domain stages. Reconciler owns traversal, dependency waiting, and workspace lifetime, supplying the narrow capabilities required by each stage.

| Element    | Shared stages                                                                           | Facts retained by the driver                               |
| ---------- | --------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| Node       | `resolveNode` → `layoutNode` → `emitNodeOutput`                                         | Effective properties, layout, output, and paired resources |
| Coordinate | `resolvePosition` → `createCoordinateLayout`                                            | Local `CompiledNodeLayout`                                 |
| Path       | `resolvePathAnimations` → `compilePath`                                                 | Kind-host output, resources, and bounds                    |
| Scope      | `resolveScopeStyle`, `prepareScopeGeometry`, `compileScopeGeometry`, `createScopeGroup` | Envelope, own group properties, and output                 |

Resolution may use semantic context such as registries and position lookup, but does not read compilation execution state. Layout and output require their own measurement, position, and resource capabilities. The caller owns the complete `SharedCompileContext` and workspace. This example composes the stages for a node without references; `undefined` from lookup means no named target is visible.

```ts
import { createPositionResolveContext, emitNodeOutput, layoutNode, resolveNode } from '@retikz/core';
import { createSharedCompileContext, createWorkspaceCompileState } from '@retikz/reconciler';

const shared = createSharedCompileContext();
const workspace = createWorkspaceCompileState(shared);
const resolution = resolveNode(
  { type: 'node', id: 'A', position: [0, 0], text: 'A' },
  {
    ...shared.registries,
    ...shared.layout,
    gatingOn: shared.host.lowerTex !== undefined,
    scopeDefaults: {},
    mode: 'light',
    irPath: ['children', 0],
    warn: (code, message, path = ['children', 0]) => workspace.diagnosticCollector.collect({ code, message, path }),
  },
);
const compilation = layoutNode(resolution, {
  measureText: shared.host.measureText,
  positionContext: createPositionResolveContext({
    nodeDistance: shared.layout.nodeDistance,
    lookupReference: () => undefined,
  }),
});
const output = emitNodeOutput(compilation, {
  round: shared.layout.round,
  registerPaint: workspace.paintRegistry.register,
});
const resources = workspace.paintRegistry.getResources();
```

Keep the resource references in `output` together with `resources`. This example only composes node calculation; the driver decides when to publish names, dispatch diagnostics, and assemble the Scene. `CompiledNodeLayout` retains layout geometry; `CompiledNode` retains effective properties and layout; `emitNodeOutput` returns drawing output separately. Separate calls do not imply unconditional independent caching.

Reconciler’s namespace stack manages declaration visibility and unfinished Scope state. Paths are compiled when their dependencies are ready. Stages consume names through narrow lookup capabilities; failed candidate workspaces publish neither resources nor partial results, and real errors retain their cause.

Scope resolves inherited styles and prepares placement before its children. Once child layouts are ready, it computes the envelope and final transforms, then prepares group properties without animation. After actual child output is available, assembly prunes empty groups before resolving animations; pruned Scopes produce no animation diagnostics. Children receive established ancestor transforms; the driver projects envelope-dependent placement after completion.

Resource IDs are derived from content when resources are created. `assembleCompileOutputs` deduplicates resources, preserves primitive references and stably sorts sibling zIndex values; the Scope visitor handles group wrapping, clipping and bounds. The caller selects the current output contributions, aggregates their visible bounds with `computeCompileOutputBounds`, then calls `assembleSceneCompilationSnapshot` to finalize viewBox, padding, root animations, diagnostics and provenance. Supplied Composite artifacts must already be in final declaration order and belong to this result. Assembly does not recompile elements or determine incremental reuse.

To calculate a layout rectangle from existing axis-aligned bounds, call Core's public `computeLayoutFromBounds(bounds, padding, round)`. It applies padding and output precision, returning a 100×100 fallback rectangle at the origin when `bounds` is `undefined`. Callers with a point set first compute its bounds using `boundsOf` from `@retikz/math`.

Core provides domain algorithms; Reconciler owns complete output assembly. Reconciler owns name mapping, dependency invalidation, version isolation and publication; the interface does not construct or update the Weave tree automatically. Callers must not mutate data reachable from published compiled state. Changes to shared definitions or measurement services invalidate affected caches. Compiled state containing Definitions and text emit functions cannot be serialized directly into Worker messages.

## Weave integration

One-shot `compileToScene`, `compileSceneSnapshot`, and `ReconcilerSession` share Reconciler's executor. `incremental` defaults to `true`: initial compilation builds the authored Weave tree and retains the actual products returned by Core. With `false`, the same compilation flow runs without retaining Weave; `update` and `updateStrategy` are rejected. Both modes support `replace`.

An incremental update applies `WeaveBatch` operations in order, then traverses the candidate input with the shared executor. A stage can reuse its product while its inputs, declaration path, and observed name lookups remain valid. Resources accompany reused products into the new workspace, and provenance is rebuilt for the current execution. Stages with diagnostics are recomputed so current warnings are not lost. Reference queries preserve declaration visibility, local shadowing, and deferred Path semantics.

Weave retains stable authored nodes with committed `current` and candidate `pending` states. Coordinate retains `CompiledNodeLayout`, Node retains `CompiledNode`, and Path and Scope retain their actual atomic products. Candidate state shares unchanged products and copies collections when modifying them. Old state remains recoverable until final confirmation.

Composite inputs use the same executor and allow batch edits to authored basic elements. Generated children are outside the editable Weave address space; change Composite author input through `replace`. Probes, replay tokens, and measurement workspaces belong to one execution and are recomputed across updates. `captureProvenance` defaults to false independently of incremental mode.

`replace` recompiles complete IR; `update` accepts basic-element operations tied to the current session result. Ordinary React and Vanilla updates still use complete replacement. New results are published only after compilation state and the output target commit successfully. Render currently uses `replaceScene`; compilation caches do not imply fine-grained backend patches. Name indexing, traversal, and output assembly may still cover the whole tree.
