This page follows one synchronous compilation from a complete IR input to a Scene ready for a renderer. React / Vanilla input construction happens upstream, rendering happens downstream, and subsequent updates belong to another execution.

## Input and example

IR stores drawing declarations such as “place a node here” and “connect A to B.” Scene stores primitives with resolved geometry and appearance, such as rectangles, text, and path commands. `compileToScene` performs this conversion and returns a result containing the Scene. Its public signature, with generic details omitted, is:

```ts
compileToScene(ir: IRScene, options?: CompileOptions): CompileResult
```

| Input / output          | Meaning in this page                                                            |
| ----------------------- | ------------------------------------------------------------------------------- |
| `ir`                    | A complete drawing declaration conforming to the Core contract                  |
| `options`               | Measurement, extension definitions, and output settings for this call; optional |
| `result.scene`          | Laid-out primitives, the canvas bounds, and drawing resources                   |
| `result.artifacts`      | Composite outputs and explicitly requested node layout data                     |
| `result.spatialHandles` | Named spatial regions collected during this compilation                         |

`compileToScene` accepts typed IR; it does not call `SceneSchema.parse` on the entire tree at entry. External data such as JSON should pass through the schema boundary first. Compilation still checks constraints that require a Definition or layout context.

Our example contains two rectangular nodes, each 60 wide and 40 high, centered at `[0, 0]` and `[180, 0]`. The connection is deliberately declared before the nodes. The short labels A and B fit inside the specified minimum size.

<ComponentPreview files={['compilation-example', 'compilation-example.data']} size="xs" hideCode type="illustration" />

Here is the Core input for that drawing. `minimumSize` constrains the node border, while `padding` and `margin` set inner spacing and the outer offset of the connection boundary. Setting both to zero places this example's endpoints directly on the rectangles.

```ts
import { compileToScene, type IRScene } from '@retikz/core';

const ir: IRScene = {
  version: 1,
  type: 'scene',
  children: [
    {
      type: 'path',
      children: [
        { type: 'step', kind: 'move', to: { id: 'A' } },
        { type: 'step', kind: 'line', to: { id: 'B' } },
      ],
    },
    {
      type: 'node',
      id: 'A',
      position: [0, 0],
      text: 'A',
      layout: { minimumSize: { width: 60, height: 40 }, padding: 0, margin: 0 },
    },
    {
      type: 'node',
      id: 'B',
      position: [180, 0],
      text: 'B',
      layout: { minimumSize: { width: 60, height: 40 }, padding: 0, margin: 0 },
    },
  ],
};

const result = compileToScene(ir, { padding: 10 });
```

The preview shows the final geometry. We will follow the same path as its `{ id: 'A' }` and `{ id: 'B' }` references become a segment from `[30, 0]` to `[150, 0]`.

## Compilation context

Core needs a way to measure text, resolve shapes, and collect shared drawing resources. Two concepts describe how capabilities are supplied:

- Definition: an implementation of a shape, path, or composite capability.
- Registry: a lookup table used to find a Definition by name during this compilation.

`createCompileEnvironment` assembles built-in and caller-provided definitions into read-only registries and retains measurement services and numeric settings. The internal `createCompileContext` uses that environment to create a per-call workspace: the root theme, an isolated text measurement cache, paint / clip resources, and warning collection. Without injected text measurement, it uses an approximate built-in measurer. Core itself does not read the DOM.

Built-in definitions and external definitions from CompileOptions are registered by capability in the context's registries for lookup and invocation during compilation, while generated paint and clip resources are collected by the context's `paint` and `clip` and written to the Scene resource table.

This example uses the built-in rectangle and path capabilities. The context's `loweredIr` still refers to the input IR here. Composites are processed when traversal reaches them.

Traversal also creates state for this execution: emitted primitives, accumulated bounds, and a namespace. The namespace stores queryable layouts by id so that a path can find the geometry of A and B. This state belongs to one full compilation and does not retain update results across calls.

## Node resolution

`compileChildrenToPrimitives` dispatches children in declaration order. Here it records the pending Path before processing A and B. Three results explain the work inside a node:

- CanonicalNode: the node after effective styles are merged, defaults are filled, and paints are resolved; `fill` / `stroke` directly carry the paint resolution results.
- NodeResolution: CanonicalNode together with the selected shape and connection boundary, ready for layout.
- NodeLayout: the measured and positioned result, grouped into node properties, shape, boundary, geometry, text layout, and labels.

`resolveNode` determines effective configuration and capability bindings. `compileResolvedNode` then prepares body and label text properties and computes typesetting, node size, and position. The returned `properties` field holds complete effective properties and identity, while `layout` holds computed geometry and typesetting. ## Path resolution

Node layout finishes before paths that depend on those nodes are resolved. Traversal visits children in declaration order:

1. On a Node, Core immediately resolves its configuration, measures and positions it, registers its layout, and emits its primitives.
2. On a Path, Core records a pending task and inserts a placeholder, postponing node-reference resolution and path emission.
3. When the current container finishes, Core looks up the registered node layouts, resolves the pending paths, and emits their primitives.

This order applies within each container. A Scope recursively processes its children and handles its pending paths as it finishes. The root handles its pending paths after visiting its children. Paths inside a Scope can therefore be processed before all nodes in the entire tree have been visited.

A path may reference nodes declared later. `queuePathChild` saves a pending path record and inserts a placeholder into the current primitive array. The record preserves the path input, style and coordinate environment, plus references to the placeholder and its owning array.

Each row below shows an array state from our example. Group A and Group B contain their node's rectangle and text; cell labels summarize those structures.

<ComponentPreview files="compilation-slots" size="xl" hideCode type="illustration" />

Once A and B are registered, `flushPendingPathEmissions` looks up their layouts, resolves the path, and emits its primitives. With only node ids as targets, this example clips the endpoints to the connection boundaries. A's right edge at `[30, 0]` and B's left edge at `[150, 0]` become the visible segment endpoints.

Core then finds the placeholder in its original array and replaces it with the actual PathPrim. Although computed after the nodes, the path remains at index 0. Once paths are filled, a stable `zIndex` sort preserves declaration order among equal values. All placeholders must be gone before Scene is returned.

The final path contains these fields:

```ts
{
  type: 'path',
  commands: [
    { kind: 'move', to: [30, 0] },
    { kind: 'line', to: [150, 0] },
  ],
}
```

Deferred work runs when its enclosing group finishes. It supports this example's Path references to later nodes in the same group. A node's own relative position needs its target during layout, so forward references are not available for every position expression.

## Scope processing

When traversal encounters a Scope, it enters that subtree before continuing with the parent's next child. Core prepares styles, a theme, a transform chain, and separate result containers, then visits `children` in declaration order: Nodes are laid out immediately, Paths are queued, and nested Scopes recursively follow the same steps.

The diagram follows entry, recursive processing, and return. A nested Scope completes this same sequence before traversal resumes in its parent:

<ComponentPreview files="compilation-scope" size="md" hideCode type="flow" />

For example, let S contain Node A, Scope T, and Node B in that order. Core processes A, enters T, finishes T's children, layout, and pending paths, then returns to S and processes B. Once all of S's children are complete, Core determines S's bounds and final placement, updates queryable layouts, processes S's pending paths, and passes a Group to the parent.

Every Scope has its own child traversal context, but it shares the current namespace frame by default. Suppose the outer frame already contains node A, and the Scope declares nodes A and B:

| Operation                     | `localNamespace: false` (default)                                        | `localNamespace: true`                                                              |
| ----------------------------- | ------------------------------------------------------------------------ | ----------------------------------------------------------------------------------- |
| Enter Scope                   | Reuse the current frame                                                  | Push a new local frame                                                              |
| Register inner A and B        | Write to the current frame; replace A and issue a duplicate-name warning | Write to the local frame; inner A shadows outer A                                   |
| Look up a name inside         | Search from the current frame outward                                    | Search the local frame first, then outer frames on a miss                           |
| After returning to the parent | Inner A and B remain accessible by name                                  | The local frame is gone; A resolves to outer A, and inner B is no longer accessible |

Pending paths inside the Scope are resolved before the local frame is popped, so they can still reference inner nodes. Popping removes name visibility, not the primitives already emitted into Scene. If the Scope itself has an id, Core registers it in the parent frame before pushing the local frame and updates it to the final layout during finalization. Outside references can therefore still target the whole group by that id.

Scene output can retain local geometry and Group transforms. Named queries use the coordinate projection they need; the output does not require every point to be expanded into world coordinates.

Composite entries join compilation through registered Definitions, and the basic IR they produce follows the same processing steps; see [Composite implementation](/kernel/packages/core/composite-compilation).

## Assemble the result

After child compilation, `prepareSceneCompilation` collects ordered primitives, paint and clip resources, and supported root animation configuration. An explicit `viewBox` determines the canvas bounds directly. Otherwise, Core computes them from accumulated layout bounds and `padding`.

The example's content spans `[-30, -20]` to `[210, 20]`. Adding 10 units on all sides produces this `result.scene.layout`:

```ts
{ x: -40, y: -30, width: 260, height: 60 }
```

This step determines the canvas bounds without moving A or B again. The output `primitives` are the path, Group A, and Group B, in that order. This example has no gradient or clip resources, so `resources` is omitted.

Alongside Scene, the result carries `artifacts` and `spatialHandles`. The former contains composite outputs or requested node layouts; the latter contains named spatial regions. Both correspond to this compilation's Scene. The renderer does not use them to rerun node layout. Ordinary `compileToScene` does not create an observer session; the explicit observation entry dispatches final observations as part of the same full compilation.

| Property         | Type                                                             | Purpose                                                                                                                                                                                                      |
| ---------------- | ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `scene`          | `Scene`                                                          | Holds laid-out primitives in drawing order, canvas bounds, optional resources, and root timeline animations for the renderer.                                                                                |
| `artifacts`      | `ReadonlyArray<TCompositeArtifact \| NodeLayoutCompileArtifact>` | Holds domain artifacts returned by composites and explicitly requested node layout results for callers to inspect or process. Empty when no artifacts are produced.                                          |
| `spatialHandles` | `SpatialHandleIndex`                                             | Holds named spatial regions declared by composites, including their owners, world-space bounds, roles, and tags, for callers to query and locate. Its `entries` array is empty when no regions are declared. |

## Independent compilation and reusable state

A caller that schedules elements itself can retain a `CompileEnvironment` and compile one basic element through these entries. They share resolve, layout and emit logic with full compilation, do not recursively compile other elements, and do not register names automatically.

| Entry               | Completed state      | Retained data                                                                    |
| ------------------- | -------------------- | -------------------------------------------------------------------------------- |
| `compileNode`       | `CompiledNode`       | NodeLayout in `layout`; drawing, resources and selected observations in `output` |
| `compileCoordinate` | `CompiledCoordinate` | `id` and local `position`; `output` only when observation is selected            |
| `compilePath`       | `CompiledPath`       | Complete `output`, including host processing for custom kinds                    |
| `compileScope`      | `CompiledScope`      | `envelope`, `group` without children, and its own `output`                       |

`NodeLayoutObservation`, previously named `CompiledNodeLayout`, is a public observation projection. It lacks the complete state required for drawing reuse; cache `CompiledNode` instead.

```ts
import { assembleSceneCompilation, compileNode, createCompileEnvironment, resolveScopeContext } from '@retikz/core';

const environment = createCompileEnvironment();
const result = compileNode(
  { type: 'node', id: 'A', position: [0, 0], text: 'A' },
  {
    environment,
    context: resolveScopeContext({}, environment),
    irPath: 'children[0].node',
  },
);

if (result.status === 'compiled') {
  const prepared = assembleSceneCompilation({}, [result.compiled.output], environment, {
    diagnostics: result.diagnostics,
  });
  // prepared.result.scene is ready for a renderer; diagnostics are not dispatched
}
```

An element call returns `compiled` or `pending`. The former includes complete state, `reads` and diagnostics; the latter includes reads only and publishes no partial result. Names are searched inside-out along a `CompileNamespace` parent chain; reads include both missing and matched bindings. Supply an explicit empty namespace to track names that may be added later. Omitting namespace means there are no queryable bindings for this call. Register only names visible at the declaration site: pending must not enable forward references for Node / Scope. Path can still wait for its references. `projectCompileReference` projects completed state into registerable reference geometry.

Scope calculation has two stages. `prepareScopeCompilation` resolves inherited context and preliminary transforms; `compileScope` consumes completed child layouts to determine the envelope and final transforms. Pass the established ancestor transforms when compiling children. Envelope-dependent placement is projected after Scope completion. `assembleScopeOutput` combines the Scope's own output with child outputs without running providers again or storing a duplicate subtree in cached state.

Resource IDs are local to each output fragment. `assembleScopeOutput` / `assembleSceneCompilation` import and remap resources, stably order sibling zIndex values, apply final transforms, and assemble Scene. Selected node layout artifacts and owner observations travel with the fragments. Create an observation session with `createCompileObservationRuntime`, pass it to element calls and final assembly, and do not reuse it across batches after completion. Other completed Composite artifacts, spatial handles and provenance are supplied through metadata from the same version; assembly does not infer this orchestration data.

These entries provide Core's scheduling primitives. Reconciler owns name mapping, dependency invalidation, version isolation and publication; the interface does not construct or update the Weave tree automatically. Callers must not mutate data reachable from published compiled state. Changes to environment definitions or measurement services invalidate affected caches. Compiled state containing Definitions and text emit functions cannot be serialized directly into Worker messages.

## Weave integration

Core and Weave share `formatCompileChildPath(prefix, index, type?)` to construct declaration source paths. The prefix is empty or ends with a dot; basic elements supply a type suffix, while Composite declarations omit it. These paths identify source locations for provenance and diagnostics, not identities across versions.

Weave is the compilation tree retained by Reconciler. Each node holds its own input, effective context and Core compilation state. The root holds the environment, Scene configuration, container index and version-specific read records. Automatically assigned Scope addresses stay outside the IR and do not affect drawing envelopes.

The Reconciler session holds a stable WeaveRoot through its Weave reconciler as the tree entry. Nodes and Root each retain committed current and candidate pending states; parent-child links, dependencies and indexes reference stable node objects. Candidate writes isolate the affected state and mutable collections while sharing unchanged Core products read-only. Changing a child’s properties does not copy its Scope’s children array; changing membership does. Commit switches the states touched by the batch and retains recovery references until confirmation. A node reference does not provide a historical snapshot.

Basic elements create nodes and bindings in declaration order. Node and Coordinate consume references visible at their declaration site. Scope prepares context, compiles its children and envelope, then completes its deferred paths. A top-level Path can wait for nodes in both Scopes to be published. `createCompileNamespaceRegistry` preserves same-frame replacement diagnostics; `projectScopeCompileLayouts` and `projectPublishedCompileLayout` reuse Core's envelope-contribution and final reference-projection rules.

Reconciler then asks Core to assemble the complete output. `createCompileProvenanceTracker` retains primitive ownership through resource remapping and Scope wrapping, pairing final provenance paths with the sorted Scene without another full compilation. The Reconciler session retains the previous result if preparation fails and publishes the matching tree and output only after success.

The internal Weave reconciler accepts WeaveBatch on a mounted Root: it applies insert, update and remove operations in order, then computes from the final inputs. Context follows declaration links and dependency invalidation follows consumers. Scope preparation, child layout, envelopes and final projections follow Core's evaluation order, preserving deferred Path references. Unaffected compiled products can be reused while their inputs, declaration positions and name bindings remain valid. Active observation sessions or diagnostics that require regeneration cause the relevant elements to be recomputed. Invalidation is conservative: a Scope change may recompute its entire subtree, without style/layout filtering.

Updates return complete output with commit, finish and rollback operations. Preparation preserves committed state; rollback remains available after commit until final confirmation releases recovery references. Rebuilding name indexes, provenance and output may still traverse the whole tree, so local compilation does not imply local total update cost.

Reconciler `replace` accepts complete IR and recompiles it; `update` accepts a `WeaveBatch` for an existing basic-element tree. A batch must belong to the current session result, and Composite scenes do not support that entry. Ordinary React and Vanilla input updates still use complete replacement. The Render commit target converts changed compilation output to `replaceScene`; this does not imply fine-grained backend Patch updates. Composite input uses Core full preparation, preserving probes, instance inputs, artifacts and spatial handles.
