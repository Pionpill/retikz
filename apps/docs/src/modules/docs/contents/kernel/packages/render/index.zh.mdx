> 这里是包文档，不是组件教程；写图请从 [组件](/kernel/components/layout) 开始。

这一组讲 retikz 怎么把图真正画到屏幕上。你写的图会先被编译成一份**与渲染器无关的 Scene**，再交给某个后端落地：**SVG** 产出矢量 DOM，每个图元都是页面上能被 CSS 命中的真实元素；**Canvas** 把同一份 Scene 画成像素位图，适合图元很多或高频重绘的场景。两个后端共享 Scene 语义，在各自支持的能力范围内对齐输出；切换前仍需确认目标宿主和交互需求。**水合**是两个后端共用的机制：先静态出图，客户端再按 id 把事件 handler 绑回图元。

## 职责一览

| 主题             | 职责                                                   | 何时查阅                               |
| ---------------- | ------------------------------------------------------ | -------------------------------------- |
| SVG              | Scene → 矢量 DOM，或 SSR / 构建期的字符串输出          | 默认选它：要清晰矢量、CSS 命中、无障碍 |
| Canvas           | Scene → 像素位图，即时模式绘制 + 命中查询              | 图元成百上千、高频重绘、性能优先       |
| Retained Runtime | 在 Runtime transaction 中 prepare / commit Scene Patch | 需要稳定宿主 identity 与增量更新       |
| 水合             | 静态出图后按 id 把事件 handler 绑回图元（两后端共用）  | 给图加点击 / 悬停等交互                |

## Retained Runtime

`createRetainedRenderParticipant()` 把 Core Program、`RenderRuntimeOwnerDefinition` 与一个 retained renderer 接入同一 Runtime Session。首次 transaction 物化完整 Scene，后续 transaction 把 Scene Patch 与 renderer config 一起 prepare；只有所有 participant 都成功 commit 后，DOM / bitmap、事件、动画控制器与公开 read 才推进到同一 revision。失败 transaction 不发布新 revision，并尝试 rollback；rollback 成功时旧宿主继续可用，rollback 自身失败时 Session 进入 broken，需要 dispose 后重新创建。

`RenderRuntimeConfigInput` 是 closed transaction config：`handlerContributions` 按注册序合并水合 handler，`animation` 控制播放、截帧与扩展 registry，`cachePolicy` 传递 layer cache 策略，`canvas.width` / `canvas.height` 声明 Canvas CSS user-space 尺寸。Canvas 尺寸字段省略时从 committed Scene layout 推导，再乘 session-lifetime DPR 得到设备像素；尺寸更新与位图绘制原子 commit，dirty reuse 仅在目标尺寸稳定时成立。

这些 retained API 从 `@retikz/render/runtime` 导入，不从 `@retikz/render` package root 导出。第三方后端通过 `RetainedRendererFactory` 创建 nominal SVG / Canvas renderer，并声明 `none` / `group` / `entity` capability。Render participant 会校验 Snapshot / Patch lineage；后端无法解释某个 Patch 时，统一降级为完整 Scene replacement 并发布 diagnostic。
