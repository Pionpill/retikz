Structure has decided which Cell this is and where it belongs, but a raw scalar is neither its final display text nor measurable graphics content. Table first resolves a final Cell plan from preset/tokens, Cell configuration, encodings, and ordered rules. It then runs the winning formatter and Presentation to turn the value and final appearance into a Core child.

## From raw value to styled content

<ComponentPreview files="table-presentation-flow" hideCode size="xxxl" />

The upper half of the figure is a candidate cascade, not value execution order. The built-in preset establishes the appearance baseline and user tokens replace its leaves. Cell configuration then supplies formatter and presentation references plus local appearance, encodings write color channels, and ordered rules apply the last matching overrides. Once the Cell plan contains the winning references and final `appearance`, the lower half runs the formatter on the raw value. Presentation then receives `rawValue`, formatted `value`, `context`, and that final `appearance` before producing the styled child.

Selectors and encodings always read the canonical raw value, not formatted text. Displaying `-3` as `−3` therefore changes neither numeric rule matching nor a scale domain.

## Two content paths

Both paths produce one Core child with the same identity and order as the source Cell. They differ in who constructs the content:

| Payload   | Stored value                                                              | How it becomes a Core child                |
| --------- | ------------------------------------------------------------------------- | ------------------------------------------ |
| `value`   | Ordinary values such as `string`, `number`, and `boolean`                 | Formatter and Presentation registries      |
| `content` | Any renderable content, such as text, icons, Nodes, or composite graphics | Validate directly; bypass both Definitions |

`value` stores ordinary Cell values, such as a name string, an amount number, or a boolean state. Presentation decides how those values are displayed.

`content` stores any renderable content directly, such as styled text, an icon, a Node, or a composite graphic. It bypasses formatter and Presentation but still receives content styles resolved from style and rules; encodings select value Cells only. Pairing a content payload with formatter or presentation fails loudly. A matching root rule that tries to override either reference for a content Cell also fails during cascade instead of being ignored.

## Formatter and Presentation ABI

A custom formatter only performs scalar-to-scalar conversion, and its output must remain a JSON scalar. Presentation owns scalar-to-Core-child conversion:

| Definition                   | Callback input                                      | Output              |
| ---------------------------- | --------------------------------------------------- | ------------------- |
| `CellFormatterDefinition`    | `{ value, context }`, where value is the raw scalar | JSON scalar         |
| `CellPresentationDefinition` | `{ rawValue, value, context, appearance }`          | JSON-safe `IRChild` |

`context` contains stable Cell identity, address, roles, and provenance. Presentation `value` is the formatter output, while `rawValue` preserves the original value for rules, diagnostics, and domain semantics. `appearance` already merges preset tokens, encodings, and rules.

## Built-in and custom use the same entry

A value Cell uses built-in identity when no formatter is named and built-in `text` when no presentation is named. `text` converts the scalar into a zero-padding Core Node without stroke or fill; `null` becomes an empty string.

Custom Formatter and Presentation Definitions each have a stable name, a precise options schema, and one callback. Runtime merges built-in and custom Definitions into their respective registries. Empty keys and duplicate registrations fail loudly while identifying the provider key during registry construction. During per-Cell dispatch, an unregistered name, invalid options, non-scalar formatter output, or non-JSON-safe Presentation output fails loudly while retaining the Definition name and Cell id.

Presentation output must still pass the Core child schema. Built-in text and custom graphics therefore share measurement, layout, replay, and renderers instead of introducing a second Table-specific rendering language.

## What Presentation does not own

| Neighbor  | Presentation reads        | Presentation does not decide         |
| --------- | ------------------------- | ------------------------------------ |
| Structure | Cell id and payload       | Address, roles, provenance, or span  |
| Style     | Final `appearance`        | Selector, encoding, and rule winners |
| Layout    | The produced styled child | Tracks, padding, fit, or overflow    |
| Renderer  | No direct renderer input  | SVG, Canvas, or SSR implementation   |

The same Presentation Definition can therefore serve different table forms, while the same Cell can change layout policy independently of how its value is presented.
