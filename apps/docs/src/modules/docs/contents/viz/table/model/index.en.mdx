A detail table generates Cells from records, an explicit grid lists Cells directly, and a custom structure asks an extension definition to produce Cells. Their inputs differ, but they converge on one semantic model and then share presentation, layout, and lowering.

## One shared pipeline

This pipeline is Table's internal model; users do not need to author it stage by stage.

<ComponentPreview files="table-model-pipeline" hideCode size="xs" />

`Structure` determines rows, columns, and Cells. The semantic model gives every Cell a stable identity, location, role, and source. `Presentation` turns Cell payloads into Core children. `Layout` measures content, solves tracks, replays selected content, and emits the manifest inside one Core compile.

## Structure: how a table produces Cells

`structure.kind` discriminates the current structure operation. The current release has two built-in structures and permits registered custom structures:

| kind     | Where the data lives                                          | Intended use                                   |
| -------- | ------------------------------------------------------------- | ---------------------------------------------- |
| `detail` | Field mappings live in spec; records arrive at runtime        | Record-per-row detail tables                   |
| `manual` | Rectangular `rows` and Cell entries live directly in spec     | Low-level scenarios that need an explicit grid |
| custom   | Custom parameters live in spec and a definition resolves them | Extension-defined structure operations         |

Custom Structures reuse the same definition registry, semantic output, and consumer pipeline. An LLM or tool that emits one structure should retain the precise `IRDetailTableSpec`, `IRManualTableSpec`, or `IRCustomTableSpec`; use aggregate `IRTableSpec` only when one store or protocol accepts several structures.

### Explicit-grid entry

`ManualTable` accepts a row-major matrix. It suits headers, summaries, or static grids without external records. Table derives row count, column count, and zero-based addresses from rectangular `rows`.

<ComponentPreview files={['table-manual', 'table-manual.en.data.ts']} size="xs" />

Scalar entries are value Cell shorthands. `null` means that a coordinate has no Cell; write `{ value: null }` for a real null scalar. Use rich `{ value, ... }` / `{ content, ... }` objects for presentation, spans, layout, semantic fields, or direct content.

React can also generate the same rectangular structure in declaration order with nested `Row` / `Cell` markers:

```tsx
import { Cell, ManualTable, Row } from '@retikz/table-react';

<ManualTable>
  <Row kind="columnHeader">
    <Cell span={{ columns: 2 }}>Identity</Cell>
    <Cell>Score</Cell>
  </Row>
  <Row>
    <Cell>Alice</Cell>
    <Cell>Engineering</Cell>
    <Cell value={95} />
  </Row>
</ManualTable>;
```

Markers occupy the lowest free column in the current row, while `span` reserves its full rectangle across future rows. The widest occupied position determines the final width, and every other coordinate is padded with `null`. Spans cannot overflow, overlap, or cross row kinds. If every `Row` is empty, use an explicit null-matrix `rows` prop because marker width cannot be inferred. A `Cell` accepts exactly one of scalar children, `value`, or `content`.

## Cells and Presentation

For manual authoring, Table normalizes each non-null entry into a canonical Cell payload:

| kind      | Stored content                                        | Processing                                                         |
| --------- | ----------------------------------------------------- | ------------------------------------------------------------------ |
| `value`   | A JSON scalar plus an optional presentation reference | Resolved by a presentation definition; defaults to `text`          |
| `content` | A JSON-safe Core or Tier 2 child                      | Used directly in Cell-local coordinates without value presentation |

`{ value: 'Score' }` therefore means “this is a scalar value to present.” Use `{ content }` when a Cell directly hosts a Node, Path, or another Tier 2 child. The precise canonical payload schemas remain public for Structure output, presentation, and manifest contracts.

Presentation only turns a value into Core content; it does not decide which row owns the Cell or how wide it is. Built-in `text` and custom presentations resolve through the same registry.

## Layout and Manifest

Table first measures every Cell intrinsically, then solves columns from fixed / auto / fraction / minmax rules, gaps, and span contributions. Content with `wrap: true` receives the solved column constraint before rows resolve from final heights. Padding defines the content box, fit and alignment transform the selected replay, overflow controls visibility, and the Border Graph resolves shared-edge conflicts last.

`TableLayoutManifest` and Scene come from one compile. The root records both `allocationBounds` and `visualOverflowBounds`; each Cell records its span, box/content box, pre- and post-transform allocation/visual bounds, semantic location, roles, and source. Visible borders retain winner and contributor provenance, so hit testing, debugging, export, and interaction do not reverse-engineer SVG geometry.

## Extension boundary

Extension authors can add a Structure through `defineTableStructure()` or a value presentation through `defineCellPresentation()`. Both definitions arrive at runtime and stay outside JSON TableSpec. New capabilities must still output the shared semantic model or a Core child instead of bypassing the pipeline with parallel layout and rendering semantics.
