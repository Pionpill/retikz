Detail Table contracts persist “one external record becomes one row” as a serializable rule without copying records into IR. `data.ref` points to a runtime dataset, while `structure.columns` controls field access, column order, headers, and body presentations.

## DetailTableSpec

`IRDetailTableSpec` is the precise detail-table root. Unlike aggregate `IRTableSpec`, it requires `data` and narrows `structure` to the detail variant.

| Field       | Type                                                                                                                                                   | Default                                    | Description                                                                                                                                       |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| `data`      | `IRDetailTableSpec['data']`<br />- `reference: string`<br />- `model?: IRDataModel`                                                                    | —<br />- —<br />- —                        | Required external dataset reference<br />- Runtime dataset name<br />- Optional data model                                                        |
| `structure` | `IRDetailTableStructure`<br />- `kind:` <ApiValues name="TableStructureKind" /><br />- `columns: Array<IRTableDetailColumn>`<br />- `header?: boolean` | —<br />- `'detail'`<br />- —<br />- `true` | Record-per-row Structure<br />- Structure discriminator<br />- At least one column with unique ids<br />- Whether to generate a column-header row |

## Column

### TableDetailColumnSchema

<ZodSchema name="TableDetailColumnSchema" />

Authoring-side `TableDetailColumnInput` also accepts a string `header`. `createDetailTableSpec()`, `DetailTable`, and `detailTable()` normalize it to `{ kind: 'value', value: header }`.

## When to use the precise schema

An LLM, form, or persistence endpoint that only emits detail tables should use `DetailTableSpecSchema`, avoiding irrelevant manual/custom fields. Switch to aggregate `TableSpecSchema` only when one protocol must accept several Table root variants.
