明细表从记录生成 Cell，显式网格直接列出 Cell，自定义结构则由扩展定义产生 Cell。它们的输入方式不同，但进入 Table 后都会收敛到同一个语义模型，再共用呈现、布局和下沉逻辑。

## 一条共享管线

下面这条管线是 Table 自身的底层模型，不要求普通用户逐层手写。

<ComponentPreview files="table-model-pipeline" hideCode size="xs" />

`Structure` 决定有哪些行、列和 Cell；语义模型统一 Cell 的身份、位置、角色和来源；`Presentation` 把 Cell payload 变成 Core child；`Layout` 在同一次 Core compile 中测量内容、求解轨道、回放选中内容并生成 manifest。

## Structure：表格如何产生 Cell

`structure.kind` 判别当前结构操作。当前内置两种结构，并允许注册自定义结构：

| kind     | 数据放在哪里                             | 适合谁                         |
| -------- | ---------------------------------------- | ------------------------------ |
| `detail` | spec 保存字段映射，记录在运行时注入      | 一条记录对应一行的明细表       |
| `manual` | spec 直接保存矩形 `rows` 与 Cell entries | 需要精确声明静态网格的底层场景 |
| custom   | spec 保存自定义参数，由 definition 解析  | 扩展作者定义新的结构操作       |

自定义 Structure 也复用同一个 definition registry、语义输出和消费管线。只生成一种结构的 LLM 或工具应持有精确的 `IRDetailTableSpec`、`IRManualTableSpec` 或 `IRCustomTableSpec`；需要在同一存储或协议中接收多种结构时，才使用聚合的 `IRTableSpec`。

### 显式网格入口

`ManualTable` 直接接收行优先二维数组，适合表头、摘要或不依赖外部记录的静态网格。行数、列数和零基地址都由矩形 `rows` 推导，不再重复声明。

<ComponentPreview files={['table-manual', 'table-manual.zh.data.ts']} size="xs" />

标量 entry 是 value Cell 简写；`null` 表示该坐标没有 Cell，真正的空标量写成 `{ value: null }`。需要 presentation、span、layout、语义字段或直接内容时，使用 `{ value, ... }` / `{ content, ... }` rich object。

React 中也可以用嵌套的 `Row` / `Cell` 按声明顺序生成同一种矩形结构：

```tsx
import { Cell, ManualTable, Row } from '@retikz/table-react';

<ManualTable>
  <Row kind="columnHeader">
    <Cell span={{ columns: 2 }}>身份</Cell>
    <Cell>分数</Cell>
  </Row>
  <Row>
    <Cell>Alice</Cell>
    <Cell>研发</Cell>
    <Cell value={95} />
  </Row>
</ManualTable>;
```

marker 按当前行最小未占用位置放置，`span` 会预占完整矩形和未来行；最终列数取全部 marker 的最大占用宽度，其余位置补成 `null`。span 不能越界、重叠或跨越不同 row kind。所有 `Row` 都为空时无法推导列数，应改用显式 null matrix 的 `rows` props。`Cell` 的 children、`value` 与 `content` 三者只能选一个。

## Cell 与 Presentation

manual authoring 中，每个非 null entry 会被 Table 规范化成 canonical Cell payload：

| kind      | 保存内容                         | 处理方式                                      |
| --------- | -------------------------------- | --------------------------------------------- |
| `value`   | JSON 标量值与可选呈现引用        | 交给 presentation definition；默认使用 `text` |
| `content` | JSON-safe 的 Core / Tier 2 child | 直接作为 Cell 局部坐标中的内容，不经过值呈现  |

因此 `{ value: 'Score' }` 表示“这是一个待呈现的标量值”；若 Cell 要直接容纳 Node、Path 或另一个 Tier 2 child，则使用 `{ content }`。canonical payload 的精确 schema 仍供 Structure output、presentation 与 manifest 契约复用。

Presentation 只负责把值变成 Core 内容，不决定 Cell 属于哪一行或多宽。内置 `text` 与自定义 presentation 通过同一个 registry 解析。

## Layout 与 Manifest

Table 先对每个 Cell 内容做自然尺寸测量，再按 fixed / auto / fraction / minmax、gap 与 span contribution 求解列；`wrap: true` 的内容随后收到列宽约束，行轨道再依据最终高度求解。padding 划出 content box，fit 与对齐只变换选中的 replay，overflow 决定可见范围，Border Graph 最后解析共享边冲突。

`TableLayoutManifest` 与 Scene 来自同一次 compile。根同时记录 `allocationBounds` 与 `visualOverflowBounds`；每个 Cell 记录 span、box/content box、内容变换前后的 allocation/visual bounds、语义位置、角色和来源；可见 border 还保留 winner 与 contributors。命中测试、调试、导出或交互不必从 SVG 反推几何。

## 扩展边界

扩展作者可以用 `defineTableStructure()` 增加新的 Structure，或用 `defineCellPresentation()` 增加新的 value 呈现。两类 definition 都在运行时传入，不进入 JSON TableSpec；新能力仍必须输出既有语义模型或 Core child，不能绕开共享管线另造布局与渲染语义。
