Chart Source separates “what kind of graphic is this?” from “how should the complete graphic be presented?” The root `type` is a stable family for discovery; nested `recipe.chartType` selects one globally unique recipe. People and LLMs can therefore discover a family first and inspect only that family's exact schema.

## Start with a Chart Source

This Point-family Scatter Source preserves author intent. Coordinates, scales, guides, and recipe-generated Plot marks are resolved later and never written back into Source.

```ts
{
  namespace: 'chart',
  type: 'point',
  id: 'weight-efficiency',
  presentation: {
    title: 'Weight and efficiency',
    subtitle: 'Compared by vehicle group',
    source: 'Example vehicle data',
  },
  theme: 'clean',
  data: { reference: 'rows' },
  layout: { width: 640, height: 360 },
  recipe: {
    chartType: 'scatter',
    encodings: {
      x: {
        field: 'weight',
        scale: { operation: { type: 'linear', name: 'weightScale', nice: true } },
      },
      y: {
        aggregate: { kind: 'mean', field: 'efficiency', as: 'meanEfficiency' },
      },
      color: 'group',
      column: { field: 'region', order: ['North', 'South'] },
      facet: { header: { column: true } },
    },
    properties: { opacity: 0.82 },
    marks: [
      { kind: 'scatter', override: true, properties: { size: 5 } },
    ],
  },
  plotExtension: {
    marks: [/* an independent Plot-owned mark */],
  },
}
```

`encodings` are the exact field-mapping plan for the selected chartType. They may contain field shorthands, rich direct mappings, aggregates, constrained derived transforms, named scales, and composition; `properties` contain constants. `recipe.marks` append by default, while `override: true` can replace a built-in semantic mark group by kind. `plotExtension.marks` do not inherit Chart encodings or properties, but they consume the same final encoding data view as recipe marks.

## Root shell and nested recipe envelope

| Field           | Meaning                                                     | Owner                       |
| --------------- | ----------------------------------------------------------- | --------------------------- |
| `namespace`     | Fixed `chart` capability namespace                          | Chart                       |
| `type`          | Stable family for discovery and first-stage routing         | Chart                       |
| `id`            | Optional unique Chart identity                              | Chart / Core                |
| `presentation`  | Four fixed slots: title, subtitle, note, source             | Chart / Standard            |
| `theme`         | Registered name, or authored `base` plus owner token slices | Chart, Plot, current recipe |
| `data`          | Dataset reference and optional data model                   | Plot / Data                 |
| `layout`        | Chart Surface border-box `width` / `height`                 | Chart / Layout              |
| `recipe`        | Exact payload for the selected chartType recipe             | Chart                       |
| `plotExtension` | Explicit Plot-owned fragment authored by the user           | Plot                        |

`layout` allocates the outer Chart Surface. It does not describe Plot facets, tracks, coordinates, guides, or an internal plot area. When you want complete low-level drawing control, use Plot directly; the current Source contract has no `type: 'base'` special case.

## family → chartType → exact schema

A family is finite, stable, and intended for discovery. A chartType is a globally unique recipe key; each key belongs to exactly one family. The first Point-family routes are:

| Family (`type`) | chartType | Exact schema and core difference                                                              |
| --------------- | --------- | --------------------------------------------------------------------------------------------- |
| `point`         | `scatter` | `ScatterChartSchema`; required x/y plus optional visual, aggregate, scale, and facet mappings |

Import the exact schema from `@retikz/chart/point/scatter`. Use the aggregate `@retikz/chart/point` entry only when the application intentionally needs the whole Point family.

Every chartType owns a strict `XxxChartSchema`, `XxxChartEncodingsSchema`, `XxxChartPropertiesSchema`, and exact recipe Theme schema. Shared atoms are extracted only when the semantic invariant is genuinely shared; there is no wide union containing every family. Unknown chartTypes, family mismatches, unknown keys, and incompatible marks fail at the Source or provider boundary.

Chart does not provide a third-party recipe Definition registration entry. The application owns the dynamic family / chartType catalog, loads the concrete schema and provider it selects, and routes JSON to the matching `XxxChartSchema` and provider contribution; multiple providers from one family are still merged under `chart.<family>` only within the current compile boundary. For complex graphics that are not built-in Chart chartTypes, use Plot directly.

## encodings, properties, and marks

The recipe first resolves rich encodings into final fields, transforms, scales, and composition. It then passes direct field projections and constant properties to its semantic mark before emitting official Plot marks. When both map to the same target slot, encoding wins; schema-valid explicit values such as `false`, `0`, and empty arrays are preserved rather than treated as missing.

Field type, format, and categorical order remain Data-owned facts in `data.model`; Chart does not create a parallel `ChartFieldType`. Transform and reducer kinds and scale types reuse owner-provided open schemas and runtime Definition registries. Function-bearing Definitions stay in a runtime sidecar rather than entering JSON Source.

A recipe explicitly declares the slots its resolver actually consumes instead of treating every schema field as consumed. A mark inheritance declaration becomes active only when that mark is present in Source. If neither the recipe nor the current authored marks consume a field, Chart fails at that field path rather than silently dropping it.

A Chart mark has `{ kind, override?, encodings?, properties? }`. Its Definition declares which fields and properties it may inherit. A Scatter authored mark accepts direct x/y/color/size/opacity/shape mappings only; it cannot declare root aggregates, derived transforms, or composition. Omitting `override` or setting it to `false` appends a mark; `true` replaces the complete built-in group with the same kind in place. An explicit property outranks an inherited encoding, and an explicit encoding still wins when the mark declares both.

```ts
recipe: {
  chartType: 'scatter',
  encodings: { x: 'time', y: 'value', color: 'id' },
  properties: { opacity: 0.8 },
  marks: [
    { kind: 'scatter', override: true, properties: { size: 4, opacity: 0.4 } },
    { kind: 'scatter', properties: { size: 7 } },
  ],
}
```

The first authored `scatter` mark replaces the recipe's complete built-in group, and the second mark is then appended in authored order. A semantic group may contain multiple Plot marks, and override replaces that group atomically. If `override: true` finds no group with the same kind, the mark is still appended and `onWarn` receives `CHART_MARK_OVERRIDE_TARGET_NOT_FOUND`. To connect the points, write a Plot-owned Path mark in `plotExtension.marks`; it remains independent of Chart context.

```ts
plotExtension: {
  marks: [
    {
      type: 'path',
      order: 'time',
      encoding: { x: { field: 'time' }, y: { field: 'value' } },
    },
  ],
}
```

## presentation and Theme owners

`presentation` contains four optional slots. Resolution always creates the fixed `title → subtitle → plot → note → source` content order; JSON property order, Vanilla object construction order, and React marker order have no semantic meaning. Free composition requires a later explicit capability and is not inferred from Source ordering.

The Theme input can be a registered name such as `'clean'`, or an authored object with `base` and owner slices:

```ts
theme: {
  base: 'clean',
  tokens: {
    chart: { 'chart.gap': 12 },
    plot: { /* consumed by Plot */ },
    recipe: { axisGridEnabled: false },
  },
}
```

The Chart-shell cascade is mode fallback → Core style chain → authored named/base chain → inline `tokens.chart`. The current recipe cascade is recipe fallback → Core style chain → authored chain → inline `tokens.recipe` → `properties` → `encodings`. Chart resolves canvas, padding, and presentation tokens; Plot owns its Plot slice, and the current chartType's exact schema validates its recipe slice. The complete resolved map is never written back into Source.
