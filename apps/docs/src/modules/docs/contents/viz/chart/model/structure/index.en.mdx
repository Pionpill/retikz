If you only need to describe how data maps to graphical elements, you can use Plot directly. When you already know that you want a scatter, bubble, or connected scatter chart, Chart provides a typed entry with useful defaults, reduces configuration, and handles chart-wide capabilities such as titles, sources, canvas, and theme consistently.

The type-based Chart wrapper is easier to learn and easier for an LLM to understand. Once you are familiar with Plot, you can also use a type-generated chart as a starting point and add Plot members through `plot` to build a more complex figure. The next example establishes the overall shape before the field and parsing details.

## Start with a Chart Source

The following example uses Scatter. It keeps the field relationships and omits the exact data and presentation item contents:

```ts
{
  namespace: 'chart',
  type: 'scatter',
  config: {
    encoding: {
      x: { field: 'height' },
      y: { field: 'weight' },
    },
  },
  plot: {
    data: { /* Plot data */ },
    // Plot transforms, marks, guides, and other members can be added here
  },
  presentation: {
    children: [
      { kind: 'preset', preset: 'title', /* ... */ },
      { kind: 'plot', key: 'plot' },
      { kind: 'preset', preset: 'source', /* ... */ },
    ],
  },
}
```

This input says: select `scatter` in the Chart domain, use `config` to define the x/y roles, allow `plot` to extend the Plot side, and use `presentation` to place the generated Plot in a complete chart with a title and source.

## Field layout: responsibility at a glance

Use this table to locate each field first; the subsections below then explain its behavior and boundary:

| Field          | Primary responsibility                | Typical contents                                                      |
| -------------- | ------------------------------------- | --------------------------------------------------------------------- |
| `namespace`    | Route the input to Chart              | The fixed value `chart`                                               |
| `type`         | Select the exact schema and recipe    | Type identifiers such as `scatter` and `bubble`                       |
| `config`       | Express type-specific intent          | x/y, size, order, and allowed visual patches                          |
| `plot`         | Reuse Plot and keep an extension path | Data, transforms, scales, coordinates, marks, guides, theme, and size |
| `presentation` | Organize the complete-chart layout    | Title, subtitle, one Plot placeholder, note, source, and their order  |

### `namespace`: declare the capability domain

`namespace: 'chart'` is a fixed discriminator. It tells the parser that this is Chart Source rather than input intended directly for Plot. It only selects the capability domain; `type` is still responsible for choosing Scatter or Bubble.

### `type`: select a type and its defaults

`type` is the exact discriminator. It selects both the schema that checks the input and the recipe that generates the default Plot semantics. It is therefore more than a label:

| `type`              | Core inputs in `config`                                      | Default semantics supplied by Chart                                    |
| ------------------- | ------------------------------------------------------------ | ---------------------------------------------------------------------- |
| `base`              | No type-specific `config`                                    | No primary mark is generated; `plot` must describe a complete figure   |
| `scatter`           | x/y positions, with optional color, size, opacity, and shape | A Point mark, two-dimensional scales, a coordinate, and default guides |
| `bubble`            | x/y positions and a required size field                      | A quantitative size mapping and size legend on top of Point semantics  |
| `connected-scatter` | x/y positions and a required order, with optional series     | A path that connects data in order on top of Point semantics           |

Chart does not guess the type through one broad public union schema. Each exact `type` has its own schema and recipe, so errors are found at the relevant entry and the type's default behavior remains explicit.

### `config`: express type-specific intent

`config` contains inputs that are meaningful only for the current Chart type. For Point types, x/y define position roles, while color, size, opacity, and shape define visual channels. Bubble's `size` is its required quantitative role. Connected Scatter's `order` determines the connection path order, and `series` can split the data into independent paths.

Think of `config` as “what am I drawing, and which fields define it,” rather than as an unrestricted style object. The type recipe reads it to generate the primary mark, scales, coordinate, and default guides. A type's allowed `mark` or `components` patches also belong in `config`, but they must still satisfy that type's schema.

### `plot`: reuse Plot and keep an extension path

`plot` belongs to Plot. It carries Plot data, transforms, scales, coordinates or composition, marks, guides, themes, and dimensions. A Chart type recipe first generates its default Plot parts from `config`, then merges the author's `plot` content into them. Authors can add marks and provide or override Plot configuration according to Plot's contracts.

This is the boundary between Chart and Plot: Chart supplies approachable type defaults, while Plot remains the lower-level capability for complex figures. `plot` is not a second input system that bypasses Chart; it is the Plot member through which a Chart can be extended.

### `presentation`: organize the complete chart

`presentation` describes the complete chart layout rather than plotting grammar. Its `children` arrange a title, subtitle, one Plot placeholder, note, and source in order. The Plot placeholder tells Chart where to place the already-parsed figure. Chart can therefore manage titles, sources, canvas spacing, and theme consistently instead of making each Plot implement them independently.

Remember the boundary this way: `plot` decides “what the graphic draws,” while `presentation` decides “how the complete chart is read.”

The Source can also carry shared metadata such as `id` and Chart theme tokens. These identify an instance or tune the Chart outer style; they do not change the responsibilities of `namespace`, `type`, `config`, `plot`, or `presentation`.

## Parsing mechanics

The pipeline starts with user input and ends with a Plot that the common Chart outer layer can consume. You do not need to know the names `Source`, `IRPlot`, or `Base Chart` in advance. Read the process as these steps:

<ComponentPreview files="chart-recipe-pipeline" hideCode size="sm" />

1. **Collect input for a concrete type**: A React or Vanilla entry receives user configuration and forms a Chart Source. Source means the structured input that describes what to draw; it preserves `type`, `config`, and the author's `plot`.
2. **Match and check the type**: The entry finds the exact schema and recipe for `type`, then checks required fields and their shapes. The `match` label in the figure represents this step.
3. **Read the type configuration and generate Plot defaults**: The type recipe binds the Source, reads `config`, and generates the primary mark, scales, coordinate, and default guides. A recipe is simply the rule that translates type input into default Plot parts.
4. **Merge the authored Plot**: Chart combines those defaults with the data, transforms, theme, dimensions, and extension marks declared in `plot`. Simple charts can stop at `config`; complex charts can keep expressing themselves through `plot`.
5. **Validate and hand off to the common outer layer**: The merged result passes the Plot schema and becomes a complete `IRPlot`. IR is just the internal serializable representation. It is then placed together with `presentation` in a common Base Chart (the code type is `IRBaseChart`) for Chart's complete-chart definition to process.

In the figure, `Type Recipe`, `Plot Merge`, and `IRPlot` correspond to steps 3, 4, and 5. They are internal roles in the parsing process, not another public API that users must construct directly. Once each concrete Chart type has bound its recipe, all types reuse the same Chart resolution and lowering path.
