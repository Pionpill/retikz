Point charts use position to show observations. They help reveal distributions, relationships, clusters, and outliers, and can also show trajectories or before-and-after differences. Data typically has one observation per row, with numeric fields and optional category or ordering fields.

## What point charts reveal

Point charts preserve the position of each observation, helping you compare values while seeing individual differences. Instead of showing only totals or averages, they reveal whether a relationship is consistent, whether observations form distinct groups, and which observations stand apart.

For example, when comparing income per person and life expectancy across regions, position shows the relationship between the two measures and color can distinguish region categories. Bubble area can add population, bringing magnitude into the comparison. To follow one region over several years, preserve the year order and use a connected scatter chart.

## Choosing a chart

| Chart                                                    | When to use it                                                     | Suitable data                                        |
| -------------------------------------------------------- | ------------------------------------------------------------------ | ---------------------------------------------------- |
| [Scatter](/viz/chart/points/scatter)                     | Explore relationships between two variables, clusters, or outliers | Two numeric fields                                   |
| [Bubble](/viz/chart/points/bubble)                       | Compare magnitude alongside two variables                          | Three numeric fields, one representing magnitude     |
| [Regression](/viz/chart/points/regression)               | Examine overall or grouped trends                                  | Two numeric fields, optionally with a grouping field |
| [Connected scatter](/viz/chart/points/connected-scatter) | Follow observations along a trajectory                             | Two numeric fields and an explicit order             |
| [Ranged dot](/viz/chart/points/ranged-dot)               | Compare before-and-after values or two endpoints by category       | A category field and two numeric fields              |
| [Strip](/viz/chart/points/strip)                         | Compare observation distributions within categories                | A category field and one numeric field               |

## Preparing data and reading the chart

Decide what one point represents: a user, a measurement, a region, or an observation at a particular time. Values being compared should belong to the same observation; comparisons between groups also need a clear category field. An ordinary scatter chart does not depend on row order. An explicit sequence becomes necessary when connecting observations into a trajectory.

Read the overall distribution first, then compare groups and inspect individual outliers. An upward or downward trend can suggest association, but a chart alone does not establish causation. A regression line summarizes a trend and should not replace the original observations.

- **When points overlap:** try smaller points, lower opacity, or separate views for groups. Consider a strip chart when observations crowd together within categories. Visible point counts can underestimate the number of observations.
- **When bubbles represent magnitude:** read their area, rather than their diameter, and compare against the legend. Use the data table as well when you need exact values.

## Shared configuration

All six point chart types share edge-padding configuration. React accepts it through the corresponding properties component, such as `ScatterProperties`, or the root `recipe.properties` prop. The Vanilla API uses `properties`; direct IR uses `recipe.properties`. These settings apply to the chart, not individual marks.

| Property        | Type                                                    | Description                                                                                                                                        |
| --------------- | ------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| `autoPadding`   | `'max-radius'`, `'point-aware'`, `{ kind; clearance? }` | Automatic padding policy; defaults to the largest final point radius. Object form selects a policy with `kind` and edge clearance with `clearance` |
| `domainPadding` | `number`, Directional padding object                    | Explicit position-domain padding takes precedence over automatic padding. Numeric `0` disables padding; objects configure individual directions    |

Keep the default policy for ordinary use. Choose `point-aware` when existing space around individual points should reduce padding; it requires Cartesian2D, linear/time position scales, and no jitter. Ranged dot’s categorical axis and Strip’s discrete axis and jitter do not meet these requirements. Bubble charts with a logarithmic position axis are also unsupported. The implementation section below explains calculation and precedence.

Size, color, and stroke are common concepts, but their inputs and semantics vary. Bubble requires a numeric size encoding; Connected Scatter styles points and paths separately; Ranged Dot distinguishes shared endpoint styles from start and end overrides. Each chart’s API retains these differences.

### Automatic edge padding

A point's position identifies its center. Mapping the data minimum and maximum directly to plot boundaries leaves the radius extending outside those boundaries. Point charts therefore supply `domainPadding` for continuous position scales that have no padding configured, leaving room inside the edges for point centers. The linear-coordinate illustration compares explicit `domainPadding: 0` with omitting the property. Overflow remains visible on the left to show the clipping risk.

<ComponentPreview files="point-padding-figure" hideCode type="illustration" size="lg" />

Both panels use the same data, point radius, and plot dimensions. Automatic padding changes the position-scale domain; it does not change data, shrink points, or enlarge the canvas. Each edge reserves one radius for extreme points in this illustration.

#### Default maximum-radius padding

After default, appended, and replacement marks are determined, Chart reads the final point sizes and selects the largest radius. A constant `size` supplies the radius directly. A field-mapped size uses the maximum of the size scale's output range rather than scanning individual rows to estimate it. Without an explicit size, it uses the default point radius. This calculation covers the radius only; it does not measure additional stroke, shadow, or text extents, so it does not guarantee room for those effects.

When `domainPadding` is omitted, each side reserves the maximum point radius in drawing-coordinate lengths, not data values.

#### Per-point calculation and clearance

The default `autoPadding: 'max-radius'` keeps the policy above without scanning individual rows. With `autoPadding: 'point-aware'`, Chart supplies the final point marks to Plot. Before generating geometry, Plot uses actual data views, positions, and radii to find compact padding. Space already available around large central points counts toward protection; large points near an edge also contribute, even when they are not position extrema.

The four charts below use identical data, size mappings, and canvas dimensions, comparing each policy with zero clearance and directional clearance (default 8, top 20, left 0). The default reserves the maximum radius at every edge; point-aware padding uses existing space around the central point and adds the space needed at the edges.

Use `autoPadding: { kind: 'point-aware', clearance: 8 }` to reserve clearance between protected point extents and automatic plot-area edges. `clearance` is a nonnegative drawing-coordinate length, defaulting to `0`. Both strategies support it; explicitly configured `domainPadding` ends do not add clearance.

`clearance` also accepts an `IRBoxSpacing` object. Explicit visual sides require Cartesian coordinates and retain their visual meaning with reversed axes.

<ComponentPreview files="point-auto-padding" hideCode type="illustration" size="lg" />

Both policies change position domains, not point sizes. Point-aware solving reuses numeric positions and sizes with bounded iterations and coordinates final plot-area dimensions. It never reads rendered geometry. Each solve pass is linear in the effective point count, so it costs more than the default mark-level calculation; strictly minimum padding is not guaranteed.

#### Explicit configuration and limitations

- Explicit `domainPadding` wins. A number applies to all sides; `0` disables padding. Missing `range` ends use the selected policy; missing `ratio` ends remain `0`. Fully explicit padding bypasses point-aware solving.
- When a scale already defines `domainPadding` or comes from `plotExtension.scales`, Chart preserves it without adding automatic padding.
- Point-aware mode currently requires Cartesian2D, linear/time position scales, and no placement. Unsupported combinations or infeasible drawing areas produce errors without falling back.
- Only effective points inside the baseline domain contribute size-radius constraints. Strokes, shadows, and text are excluded. Outside points retain Plot rendering and clipping semantics; domain expansion may bring some of them into view.
- Shared scales solve one domain across panels. Incompatible fixed pixel padding across differently sized panels produces an error.
- Chart references its final Point marks and Relation endpoints; `plotExtension.marks` are not included automatically.

Both `autoPadding` and `domainPadding` belong to the chart’s `recipe.properties`, not an individual mark’s `properties`.
