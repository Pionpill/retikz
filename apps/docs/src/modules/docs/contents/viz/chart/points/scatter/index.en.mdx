  Scatter uses the exact `ScatterChartSchema`. The root `type` is `point` and `recipe.chartType` is `scatter`; data, layout, presentation, and Theme stay in the Source shell, while field bindings live in `recipe.encodings` and constant styles live in `recipe.properties`.

All examples on this page use `ScatterChart` from `@retikz/chart-react/point/scatter`. The recipe emits a built-in `scatter` semantic mark group, two-dimensional scales, and default Plot structure. A direct `ScatterMark` child writes `recipe.marks` and inherits consumable encodings and properties. A plain `ScatterMark` appends points; `<ScatterMark override>` replaces the complete implicit `scatter` group in place, which changes the primary point style without drawing a duplicate layer.

`encodings` contain field names only; constants belong in `properties`. At the recipe root, an encoding wins when both map to the same target. On an authored mark, an explicit property outranks an inherited encoding, and an explicit encoding wins again. An unmatched override still appends the mark and reports `CHART_MARK_OVERRIDE_TARGET_NOT_FOUND` through `onWarn`.

Complex authoring is split by owner: `ChartFacet` writes `recipe.facet` and reuses the current Chart recipe's coordinate and scales, while `PlotTransform`, `PlotAxis`, and other `PlotXxx` declarations write `plotExtension` through the Plot normalization path. Use `Plot` directly—or write an explicit `plotExtension` fragment—for custom coordinate views, tracks, nested composition, or independent Plot marks. An independent fragment neither inherits Chart context nor participates in semantic-group override.

## Shared Chart rules

Scatter shares family / chartType routing, exact schemas, the authoring pipeline, fixed presentation slots, and Theme owner slices with every other Chart type. Refer to [Chart Model](/viz/chart/model) for those rules; this page stays focused on Scatter's two-dimensional position, categorical encoding, and mark semantics.
