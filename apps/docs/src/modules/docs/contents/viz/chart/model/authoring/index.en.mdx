description: Understand how React, Vanilla, and JSON produce exact Chart Source that a chartType recipe resolves consistently.

Chart separates convenient authoring from stable execution. React and Vanilla normalize their input forms into exact Chart Source. The parser first reads the family, then selects the unique recipe from `recipe.chartType`.

## One shared pipeline

<ComponentPreview files="chart-authoring-pipeline" hideCode size="sm" />

| Stage              | Owner                     | Result                                                        |
| ------------------ | ------------------------- | ------------------------------------------------------------- |
| React declarations | `@retikz/chart-react`     | Folds owner slots into Vanilla Input                          |
| Plain input        | `@retikz/chart-vanilla`   | `normalizeXxxChart` produces exact Source                     |
| JSON               | Concrete chartType schema | Application selects a strict schema by family and `chartType` |
| recipe             | Active Chart provider     | Produces shared parts and kind-tagged semantic mark groups    |
| resolve            | Chart resolver            | Merges marks by kind, Plot fragments, and Theme inputs        |

JSON is an alternate input, not a schema bypass. The application selects the concrete schema from `type` and `recipe.chartType`, and the active provider confirms that the recipe belongs to the root family. Unknown families, recipes, fields, and incompatible marks fail loudly. The parsed Source preserves author intent; recipe-generated coordinates, guides, and Plot marks only exist in later resolution stages.

Plain authored marks append in Source order. `override: true` replaces the complete built-in semantic group with the same kind in place. If no group matches, the mark still appends and Core reports a stable warning through `onWarn`. This merge belongs only to the Chart resolver; React, Vanilla, and the visible Source IR do not perform or expose it.

## Field Mappings Keep One Shape

React, Vanilla, and JSON use the same concrete chartType encoding structure. Adapters do not translate aggregate, scale, transform, or composition into a private configuration model:

| Entry   | What it does to `encodings`                                                                                        | What it does not do                           |
| ------- | ------------------------------------------------------------------------------------------------------------------ | --------------------------------------------- |
| JSON    | Parses directly with the concrete chartType strict schema                                                          | Bypass schemas or invent fields at runtime    |
| Vanilla | Expands only `row` and `column` string shorthand to `{ field }`; keeps every other rich mapping unchanged in shape | Inspect data or registries to infer semantics |
| React   | Collects shared Chart and chartType-private declarations into the same Vanilla Input                               | Execute aggregate, scale, or facet algorithms |

Field-induced execution also follows one order:

```text
plotExtension.transform
  → encoding-derived operations (row-shape → field-derive → row-order → cumulative-derive → field-adjust)
  → final field / scale / facet binding
  → semantic marks → authored Chart marks → plotExtension.marks
  → Plot lowering
```

Operations in the same phase follow the active recipe's exact slot order, not JSON property order. A rich mapping first resolves to its final direct field projection before semantic and authored Chart marks consume it; marks never inherit root aggregate or transform configuration. Every mark ultimately consumes the same encoding data view.

Custom transform, reducer, scale, and similar Definitions enter the Chart provider through `lowerOptions` as a runtime sidecar shared with the same Plot lowering request. Their schemas and functions never enter Source; serializable Source keeps only `{ kind, ...config }` and field mappings.

## Three packages, one stage each

The root `@retikz/chart` entry exposes shared Chart Source schemas, constants, and the Theme contract. Each concrete chartType subpath exposes its exact schema and provider contribution. Recipe / mark Definitions and resolvers are package-internal implementation contracts, not third-party extension entry points. Plain types such as `InputScatterChart`, normalizers, and factory functions belong to `@retikz/chart-vanilla`. Typed React Charts fold `ChartData`, `ChartLayout`, `ChartExtension`, presentation markers, and chartType-private declarations into the same Vanilla Input. Plot declarations are legal only inside `ChartExtension` and continue through the Plot normalizer. Dynamic family / chartType routing belongs to the application layer.

| Entry          | Root `type` | `recipe.chartType` | Import                      |
| -------------- | ----------- | ------------------ | --------------------------- |
| `ScatterChart` | `point`     | `scatter`          | `@retikz/chart-react/point` |

The Vanilla factory `createScatterChart` comes from `@retikz/chart-vanilla/point/scatter`. The concrete subpath loads only its chartType; the family root remains an explicit aggregate entry. It returns an authoring result that preserves runtime theme data while reusing the shared Chart adapter and resolution pipeline for rendering.
