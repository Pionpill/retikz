## Chart authoring

Every Chart entry follows the same field layout, but there is no public `ChartSchema` union. `BaseChartSchema` and each packaged type's exact schema fix `namespace: 'chart'` and an exact `type`; `plot` stores Plot-owned input, packaged types keep their unique configuration in `config`, and `presentation` stores chart-wide narrative content.

The three packages divide responsibility by stage. `@retikz/chart` owns only Source IR, exact schemas, recipes, resolution, and canonical presentation. Plain `InputChart`, `normalizeChart`, presentation records, and factories belong to `@retikz/chart-vanilla`. `@retikz/chart-react` only converts JSX and props into those Vanilla inputs before calling the matching normalizer. React and Vanilla therefore do not maintain separate Source IR assembly rules.

After an exact schema parses, its matching recipe binds the value. Every recipe then resolves through `resolveChart` to `IRBaseChart`, so Core consumes only `chart.base` rather than a separate execution entry for Scatter, Bubble, or another packaged type.

| Entry                   | Use it when                                                | Chart `type`        |
| ----------------------- | ---------------------------------------------------------- | ------------------- |
| `Chart`                 | You describe a complete Plot explicitly                    | `base`              |
| `ScatterChart`          | You compare two continuous fields                          | `scatter`           |
| `BubbleChart`           | You add a quantitative area to two-dimensional position    | `bubble`            |
| `ConnectedScatterChart` | You trace one ordered series through two-dimensional space | `connected-scatter` |

Scatter & Points remains a documentation, source-organization, and multi-entry import boundary. Import Base Chart capabilities from each package root; the matching `/point` entry exposes only Point typed contracts and does not re-export the root. `@retikz/chart/point` fully exports each concrete type's schema, IR, recipe, and owned mark/component patch contracts; `@retikz/chart-react/point` exposes `ScatterChart`, `BubbleChart`, and `ConnectedScatterChart`; and `@retikz/chart-vanilla/point` exposes exact `InputXxxChart`, `normalizeXxxChart`, and `createXxxChart` APIs. This directory boundary does not introduce a `PointChartSchema`, a Point-specific resolver, or a separate adapter path; each entry binds its exact schema and then converges on `resolveChart` and the Chart adapter contract.

A packaged type stores its unique fields under `config`. Scatter supplies x/y through `config.encoding`, Bubble adds size, and Connected Scatter adds order; local adjustments to the primary mark also belong to `config`. Data, transforms, scales, coordinates, guides, and explicit additional marks live under `plot` and continue to use Plot's public contracts.

## Presentation

`title`, `subtitle`, `source`, and `note` are Chart shorthands. Without markers, title and subtitle appear above the Plot, while note and source appear below it in their fixed shorthand order. Chart default tokens style them, and they share one Flex layout with the Plot.

| React marker    | Matching shorthand | Purpose                                                    |
| --------------- | ------------------ | ---------------------------------------------------------- |
| `ChartTitle`    | `title`            | Chart subject or observable conclusion                     |
| `ChartSubtitle` | `subtitle`         | Scope, year, sample, units, or method                      |
| `ChartSource`   | `source`           | Dataset and any transformation that affects interpretation |
| `ChartNote`     | `note`             | Reading constraint, definition, or supporting note         |

Place markers as direct children of `Chart` or `XxxChart`; transparent `Fragment` groups are allowed. A marker fully overrides the matching shorthand, and each preset can appear only once. Markers retain JSX order within their side of the Plot: `ChartSubtitle` followed by `ChartTitle` appears in that order above it, while `ChartSource` then `ChartNote` appears in that order below it.

Marker children currently accept only strings, transparent `Fragment`, and Core `Text`. Multiple `Text` children create lines and may each supply font, fill, or opacity. `position="top"` and `position="bottom"` only normalize the authoring location around the Plot; the resolved Base Chart retains only the final presentation-child order.

Each type factory accepts the same shorthands as React. For custom order or position, provide ordered plain `presentation` records. A record's `text` is a string or JSON-safe Core TextBlock, never a React object.

## Runtime styles

A named style needs same-named definitions from Core, Chart, and Plot. The static adapter in `<Layout>` passes its resolved Core Theme and inherited Core definitions to an embedded Chart, so recipe defaults match standalone authoring. `themeStyles` configures only the Layout created by a standalone Chart; an embedded Chart's named Core definition belongs on its parent `<Layout>`. Pass Chart- and Plot-owned definitions directly through `chartThemeStyles` and `plotThemeStyles`; a standalone subtree may instead inject them through `ChartThemeProvider` and `PlotThemeProvider`. Vanilla passes `theme` and `themeStyles` when calling `createChart()` or a typed factory; the returned authoring result retains them, and `renderChart()` consumes that result in one compile. Pass Core definitions or other compile options through `renderChart()`'s `compile` option; it does not accept a `compileDriver` that could produce extra layers or diagnostics. The base `createChart()` path keeps Plot definitions in `lowerOptions.plotThemeStyles` so it reuses the complete Plot runtime-options contract.

## Plot extensions

Chart interprets `config` by `type`, organizes chart narrative, and completes Chart composition. Plot continues to own coordinates, scales, axes, legends, marks, annotations, transforms, and interaction semantics. Therefore `Legend`, `Axis`, and additional marks can appear alongside Chart markers, but they are not presentation items.

The adapter assembles `SurfaceProvider`, `FlexLayoutProvider`, the Plot provider, and `ChartProvider` into one contribution. Title, subtitle, Plot, source, and note can therefore lay out together while Plot preserves its own guide, lowering, and diagnostic path.
