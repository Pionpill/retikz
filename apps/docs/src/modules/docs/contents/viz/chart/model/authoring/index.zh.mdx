---
title: 编写与解析
description: 理解 React、Vanilla 与 JSON 如何形成精确 Chart Source，并由 chartType recipe 统一解析。
---

Chart 把“方便编写”与“稳定执行”分成两个阶段。React 和 Vanilla 负责把各自的输入形态规范化为精确 Chart Source；解析入口先读取 family，再用 `recipe.chartType` 选择唯一 recipe。

## 一条共享主链

<ComponentPreview files="chart-authoring-pipeline" hideCode size="sm" />

| 阶段              | owner                   | 结果                                                |
| ----------------- | ----------------------- | --------------------------------------------------- |
| React props / JSX | `@retikz/chart-react`   | 转换为 Vanilla Input，不直接拼 Source               |
| Plain input       | `@retikz/chart-vanilla` | `normalizeXxxChart` 生成精确、可序列化的 Source     |
| JSON              | 具体 chartType schema   | 应用层按 family 与 `chartType` 选择 strict schema   |
| recipe            | 当前 Chart provider     | 生成共享部分与带 kind 的内建 semantic mark groups   |
| resolve           | Chart resolver          | 按 kind 合并 marks、Plot fragment 与主题并交给 Plot |

JSON 是输入旁路，不跳过 schema。应用层先按 `type` 与 `recipe.chartType` 选择具体 schema，active provider 再确认 recipe 与 family 一致；未知 family、未知 recipe、未知字段和不允许的 mark 都 fail-loud。解析结果保留作者写下的 Source，recipe 产生的坐标、guide 和 Plot mark 只存在于后续解析阶段。

普通 authored mark 按 Source 顺序追加；`override: true` 会按 kind 原位替换完整内建 semantic group。未命中时 mark 仍追加，并由 Core 的 `onWarn` 接收稳定 warning；这套合并只发生在 Chart resolver，不进入 React、Vanilla 或可见 Source IR。

## 字段映射在三套入口中保持同形

React、Vanilla 与 JSON 使用同一份具体 chartType encoding 结构。adapter 不会把 aggregate、scale、transform 或 composition 翻译成另一套私有配置：

| 入口    | 对 `encodings` 做什么                                                         | 不做什么                           |
| ------- | ----------------------------------------------------------------------------- | ---------------------------------- |
| JSON    | 直接由具体 chartType strict schema 解析                                       | 不绕过 schema 或运行时补字段       |
| Vanilla | 只把 `row`、`column` 字符串简写展开为 `{ field }`；其余 rich mapping 保持同形 | 不读取数据或 registry 猜测语义     |
| React   | 把 typed props、Chart marks 与 Plot declarations 收集成同一 Vanilla Input     | 不执行 aggregate、scale 或分面算法 |

字段映射诱导的执行顺序也只有一条：

```text
plotExtension.transform
  → encoding-derived operations（row-shape → field-derive → row-order → cumulative-derive → field-adjust）
  → final field / scale / facet binding
  → semantic marks → authored Chart marks → plotExtension.marks
  → Plot lowering
```

同一阶段内按当前 recipe 的精确 slot 顺序执行，而不是按 JSON 属性顺序。rich mapping 会先解析成最终 direct field projection，再交给 semantic mark 与 authored Chart mark；mark 不会继承 root aggregate 或 transform 配置。所有 marks 最终消费同一个 encoding data view。

自定义 transform、reducer、scale 等 Definition 通过 `lowerOptions` 作为运行时 sidecar 进入 Chart provider，并与同次 Plot lowering 共享。Definition 中的 Schema 与函数不会写进 Source；可序列化 Source 仍只保存 `{ kind, ...config }` 与字段映射。

## 三套包，各自只做一段

根 `@retikz/chart` 公开 Chart Source 的共享 schema、constants 与 Theme contract；具体 chartType 子路径公开自己的精确 schema 与 provider contribution。recipe / mark Definition 和 resolver 只属于包内实现契约，不是第三方扩展入口。plain `InputScatterChart`、`normalizeXxxChart` 与创建函数属于 `@retikz/chart-vanilla`。React typed Chart 解析 presentation marker 与 Chart mark 组件后，复用相同 normalizer，因此 React 与 Vanilla 不维护平行的 Source 组装规则。动态 family / chartType 路由由应用层负责。

| 入口           | 根 `type` | `recipe.chartType` | 导入位置                            |
| -------------- | --------- | ------------------ | ----------------------------------- |
| `ScatterChart` | `point`   | `scatter`          | `@retikz/chart-react/point/scatter` |

Vanilla 的 `createScatterChart` 从 `@retikz/chart-vanilla/point/scatter` 导入。具体子路径只装载对应 chartType；family 根入口仅作为显式聚合入口。它返回保留运行时主题信息的编写结果；最终渲染仍复用共享 Chart 适配与解析主链。
