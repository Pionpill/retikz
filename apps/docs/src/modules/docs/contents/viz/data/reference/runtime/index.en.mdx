Data schemas store configuration only. External rows, field parsers, Definitions, registries, and event sinks are runtime objects. `@retikz/data` remains pure and host-independent: it returns canonical rows, field information, provenance markers, or lineage events, never a Scene or visual primitives.

Follow the solid row-processing path: host data is resolved and normalized before transforms run in declaration order. Dashed arrows mark runtime dependencies supplied by Definitions, registries, and JSON contracts, plus optional diagnostic output.

JSON-safe contracts determine which configuration can be stored. Definitions describe semantics; Implementations and the executor determine computation. Processed rows can carry opt-in Symbol provenance; lineage is returned as a separate run or sent to an event sink.

## Separate semantics and computation

| Contract   | Semantic Definition                             | Computing Implementation |
| ---------- | ----------------------------------------------- | ------------------------ |
| transform  | schema, input fields, outputModel, dependencies | apply                    |
| reducer    | schema, input fields, outputs                   | reduce                   |
| selector   | schema, input fields                            | select                   |
| regression | schema                                          | fit                      |

Semantic factories such as `defineTransform` and their `define*Implementation` factories register separately. An implementation must reference the exact registered Definition; matching kind strings alone are insufficient. Built-ins follow the same contract. FieldFormatDefinition retains its source parser.

Semantic registries merge built-in and custom Definitions, rejecting duplicate keys and built-in overrides. Open JSON operation schemas store parameters; dispatch parses each operation once with the exact Definition schema. `resolveDataTransforms(declarations, inputModel, options?)` resolves fields and complete output models in order without reading rows or computing results.

## Async execution

`createDataTransformExecutor(options?)` holds local implementations, named externalProviders, default dataExecution and optional materializeSource. Priority is executor < host root < declaration; mode and external name inherit independently.

1. `executor.prepare(descriptor, resolution, options?)` preflights the whole plan; descriptors carry models and necessary source handles rather than fabricated rows
2. On ready, `bind(actualInput)` binds a real source or result
3. Call `execute()` once for a `DataTransformResult` or Promise; success, failure and cancellation all consume the instance
4. `ingestDataTransformResult` checks rows, the complete model and the semantic plan; empty output retains fields and category order, and extra payload fields never become model fields automatically

`executeDataTransforms` provides a single-call entry for this sequence. Both provider resolve and stage execute may return Promises. Hybrid chooses local computation only for explicit unsupported preflight; query exceptions, computation failures, invalid output and cancellation never trigger recomputation. See [Extensions](/viz/data/transform/extensions) for modes and a working example.

## Field preparation

| Entry point              | Responsibility                                                                     |
| ------------------------ | ---------------------------------------------------------------------------------- |
| `resolveFieldTypes()`    | Merge `model` declarations with sample inference and validate the strict field set |
| `applyFieldResolver()`   | Apply host-provided per-field type and parser overrides                            |
| `collectFormatFields()`  | Add implied types and parsers from named format Definitions                        |
| `normalizeRows()`        | Map physical paths and write parsed values under logical field names               |
| `validateBoundData()`    | Sample-check why a field has no valid values                                       |
| `assertAllValuesValid()` | Apply full strict validation to canonical rows                                     |

`normalizeRows()` does not execute transforms. A consumer collects fields, resolves types, and normalizes rows before passing canonical rows to the transform pipeline. That boundary lets Plot, Table, and other hosts share one Data-processing contract.

## Category Domains

`defineFieldOrder` defines a named comparator. `resolveFieldOrderRegistry(definitions?)` combines built-ins and request-local definitions, rejecting duplicates. `assertFieldOrders(model, registry?)` validates all named orders at intake, including empty category sets.

`resolveCategoryDomain(values, order, registry?)` returns a new ordered category list, skipping values other than strings and finite numbers and deduplicating by identity. Omitted registries use built-ins. Explicit arrays retain declared categories and append unlisted observations. Ordering does not change rows, types, or lineage. See [extension mechanisms](/viz/data/model/extensions#defining-category-orders).

## Transforms and lineage

`applyTransforms(rows, operations?, options?)` executes operations in declaration order and returns rows only; options carry the registry, separate synchronous implementations and context. Use the executor for Promise or external computation. `applyTransformsWithLineage(rows, operations?, options?)` first tags input rows with Symbol provenance that JSON serialization ignores, then returns:

| Field     | Type                 | Meaning                                                                                        |
| --------- | -------------------- | ---------------------------------------------------------------------------------------------- |
| `rows`    | `Array<ExternalRow>` | Transformed caller-input rows; canonical semantics are preserved when the input was normalized |
| `lineage` | `DataLineageRun`     | Retained structured events; a sink disables duplicate retention by default                     |

`DataLineageOptions` records lightweight source and transform-step summaries by default. `rowSamples` and `calculationDetails` require an explicit `maxRows` and field allowlist; complete source indexes require an explicit `sourceIdentity: { mode: 'full' }`. These are diagnostic outputs and never mutate Data IR.
