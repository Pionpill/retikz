title: Computation Operators
description: Understand how reducers, selectors and regression operators return fields, records or prediction models for hosts to assemble output data.

A **transform operator** is a computation unit used inside a transform. Three families are available: reducers return fields, selectors return records and optional ranks, and regression operators return prediction models. The transform organizes inputs and outputs; operators perform the individual computations.

[Transform operations](/viz/data/transform/operations) explains how the whole chain progresses. This page looks inside one transform, following a group of rows through an operator and back to the calling transform, its **host**, which assembles the final result. The host owns grouping boundaries and output row shape; operators perform local computations without advancing the whole chain. This page follows all three families through their hosts. See [Computation operators](/viz/data/operators) for built-in methods and parameters.

## Overall flow

- **Reducer**: consumes a group of rows and returns declared fields, such as one or more fields in `{ total: 40, count: 2 }`.
- **Selector**: consumes a group and returns references to selected original rows, optionally with rank information.
- **Regression**: consumes finite observation pairs and returns a model with `predict(x)`.
- **Host transform**: assembles fields into new rows, broadcasts them onto detail rows, turns selections into output rows, or samples a model to generate predictions.

The three families differ in their results and have separate definition, implementation, and registration contracts. Selectors may also compare, sort, or compute ranks; their final result is a row selection. Custom operators extend the corresponding category, and hosts consume results according to its contract.

Operators also serve transforms beyond aggregation: `annotate` writes computation results back onto detail rows while preserving row count, `select` outputs selected records, and `relate` uses selectors to choose source and target records. Different hosts can reuse the same operator. Final row counts follow the host's output semantics.

For the grouped invocation shown above, the host collects rows by group keys, then passes each group and operator parameters to computation dispatch. Definitions declare input fields; reducer definitions also declare outputs so the outer pipeline can derive models and check output-name collisions before execution.

Semantic definitions and implementations are registered separately. Dispatch matches both `kind` and the bound Definition, preventing a same-named computation with different semantics from replacing the resolved contract. Built-in and custom suboperators use the same matching mechanism.

## reducer operators

Compare the tables: four detail rows become two summary rows. `item` and `value` disappear; `total` and `count` are added. A real summary transform computes the right-hand table.

<ComponentPreview files="reducer-example" hideCode type="illustration" size="md" />

For team A, the host passes the two records with values 10 and 30. Two reducers return `{ total: 40 }` and `{ count: 2 }`. The host merges the fragments and adds `{ team: 'A' }` to form a complete output row.

A reducer returns neither a complete table nor necessarily a single number. A multi-output reducer can return several declared fields. Before merging, output names are checked: metrics cannot write the same name, nor overwrite reserved group keys.

One row per group comes from the summary host. Another host can broadcast the same statistical fields onto every detail row and preserve row count, without inventing a separate broadcast-specific reducer.

## selector operators

With the same input, select the row with the greatest `value` in each group. The result still contains `item`: a selector returns an original record, not just its maximum value.

<ComponentPreview files="selector-example" hideCode type="illustration" size="md" />

Team A selects a2 and team B selects b2. Each selection contains `row` and may contain `rank`. The host consumes these selections, copies the selected rows, and writes a ranking field when requested. Selection records themselves are not the final output rows.

A selector may return zero, one, or multiple selections. Tie handling belongs to the specific selector; the host cannot assume exactly one representative per group. Similar names such as “maximum” do not erase the contract distinction: reduction produces fields, while selection retains record identity and other fields.

## regression operators

A fitting operator receives finite $(x,y)$ observations and returns a callable model. The example keeps the gray observations in place and draws blue predictions from a linear model.

<ComponentPreview files="regression-example" hideCode type="illustration" size="lg" />

`method` first selects the model form and fitting algorithm. With `linear`, the model is $y=a+bx$, but intercept $a$ and slope $b$ are still unknown. `smooth` groups rows by `groupBy`, extracts each group's valid observations and passes them to the implementation's `fit`. It estimates $a$ and $b$ from those observations and returns a `RegressionModel` with `predict(x)`.

For example, fitting a line to $(1,10)$ and $(3,30)$ gives $a=0$ and $b=10$, so the model predicts through $y=10x$. The host then chooses three sample positions in $[1,3]$ and calls `predict(x)` to produce $(1,10)$, $(2,20)$ and $(3,30)$. Observations determine model parameters; the host determines sample positions and output fields. The middle point is a prediction, not a selected original record.

Without an explicit sampling range, the host uses the valid observations' $x$ range. An explicit range changes predictions without filtering fitting observations. A definition may check the prediction domain through `validateExtent`; logarithmic models, for example, require sampled $x>0$. Model functions stay at runtime; their generated prediction rows enter subsequent transforms.

## Numeric and execution boundaries

Field access, missing-value filtering, and empty-input results belong to each suboperator's semantics; the host does not universally substitute zero. A count may count records, while a numeric reduction decides which field values participate. Both cannot be modeled as “the number of valid numeric values.” Individual usage and contract documentation owns these details.

Grouped algorithms invoke suboperators through shared computation dispatch. The synchronous path uses synchronous implementations; an asynchronous path may wait for a subcomputation before assembling results. Grouping and assembly are shared, without silently accepting Promises in the synchronous API.

A suboperator failure stops its host computation, and the outer chain identifies the failing stage. There is no default mechanism that skips failed groups and returns a partial statistical table.
