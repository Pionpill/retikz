**Transform**（数据变换）是对输入数据进行计算与转换、得到结果数据的处理步骤。原始数据往往记录的是一条条明细，而我们想查看的可能是每组的总量、部分代表记录，或按某个数值排列的结果。Transform 的作用就是把已有数据整理、计算成适合当前问题的数据。

一次变换可以改变字段的值、增加或移除字段、改变行数，也可以只调整行的顺序。结果仍然是数据，可以继续交给下一次变换，也可以交给表格或图形展示。表格的颜色、边框等外观由展示组件负责。

## 整体流程

Transform 的过程本质上是**数据内容的计算与转换**：接收输入行，按照指定规则读取字段、计算数值或组织记录，再产出结果行。多个 transform 可以按顺序串联，前一步的输出就是后一步的输入。

在上面的例子中，四条明细先按 `team` 分组，对每组的 `value` 求和并统计记录数，得到两条汇总记录；随后根据汇总后的 `total` 调整行序，得到右侧的结果。这里的分组、求和和计数共同完成一次汇总变换，排序则是接在它后面的另一次变换。

为了执行这个过程，系统同时管理**行数据**与**字段模型**：行数据承载实际计算的值，字段模型说明每一步可以读取哪些字段、将产出哪些字段。下面再从实现层面说明如何描述规则、检查输入并执行计算：

- **声明**：可序列化的操作参数，用 `kind` 指明语义。
- **定义**（Definition）：规定参数结构、输入字段、输出模型和依赖的子算子。
- **计算实现**（Implementation）：提供真正处理数据的函数，并绑定对应定义。

定义让系统在计算前判断链路是否成立；实现负责产生数据值。下面是同步行数据入口的主线。

## 声明解析

注册表以 `kind` 找到唯一的 Definition，再用该定义的 schema 解析作者参数。未知操作或不合法参数在这里失败，错误携带操作位置；后面的模型推导消费已解析声明。

以前面例子中的第二步为例，它声明“按 `total` 降序排列”：

```json
{ "kind": "sort", "params": { "field": "total", "order": "descending" } }
```

解析时，系统先用 `kind: 'sort'` 在注册表中找到排序定义，再交给它的完整操作 schema 检查声明。统一外壳包含 `kind` 和 `params`，排序参数由 `SortParamsSchema` 定义；`defineTransform` 将两者组合起来。其中 `params.field` 必须是非空白字符串，`params.order` 若提供，必须是合法的排序方向。这里的 `total` 和 `descending` 满足这些要求，因此得到解析后的排序声明；此时还没有读取数据行，也没有真正排序。

如果把 `kind` 写成未注册的名称，系统找不到定义；如果将 `params.field` 写成空字符串，或将 `params.order` 写成 `'sideways'`，则会在该定义的 schema 校验中失败。

但 `field: 'total'` 通过解析，只代表字段名的写法合法，不代表输入中已经存在 `total`。这个字段由前一步汇总产生，所以还需要下一阶段结合字段模型检查它是否可读。

## 字段模型推进

这一阶段在计算开始前，推导**每一步之后的数据结构**。字段模型记录字段名及已知类型；系统读取变换定义中的 `outputModel`，沿声明顺序推导后续阶段可用的字段。

在贯穿本文的例子中，汇总定义说明结果将包含 `team/total/count`，排序定义则保留这些字段。系统因此能提前得到下面的结构变化，此时还没有计算出 40 或 60。

<ComponentPreview files="transform-model" hideCode type="flow" size="xs" />

推导出的输出模型会成为下一阶段的输入模型，所以排序可以读取 `total`。如果把排序提前，或者在汇总后读取已移除的 `item`，模型推进时就能发现链路无法衔接。字段类型也随模型一起传递。

这一阶段产出的是各阶段的预期字段模型，供后续执行与结果校验使用。它描述数据将变成什么结构，具体数值由计算实现产生。

## 计算实现预检

字段模型确定后，系统还要在计算开始前确认**当前环境能执行整条变换链**。Definition 描述操作的含义与输出结构，Implementation 才提供处理行数据的函数；预检负责为各阶段匹配可用的计算实现。

例如，汇总后的字段足够供排序使用，说明数据结构能够衔接。但如果本次运行环境缺少排序实现，同步入口会在开始汇总之前报错，整条链都不会开始计算。预检覆盖全部阶段，避免前半段已经算完才发现后半段无法执行。

<ComponentPreview files="transform-preflight" hideCode type="flow" size="md" />

匹配时，实现必须绑定解析阶段选中的同一个 Definition；仅有相同的 `kind` 还不够。若操作依赖其它子算子，其计算实现也要一并就绪。预检通过后，系统才会依次调用各阶段的 `apply`。

原生数据源或异步计算通过执行器完成准备：`prepare` 协商整条链的执行能力，`bind` 绑定与准备描述匹配的输入，最后由 `execute` 执行。准备结果不支持时不会开始计算，绑定后的执行权只能消费一次。

## 结果校验

这一阶段发生在**计算实现返回数据之后**。同步入口先执行汇总，得到 A 组总量 40、B 组总量 60，再将返回的结果与提前推导的输出模型核对；通过后才交给排序，排序结果同样经过校验。

例如，`total` 已被声明为连续数值字段，实现却返回字符串 `"forty"`，结果校验就会失败，后续排序不会执行。校验关注结果模型是否符合预期，以及已知类型字段的实际值是否符合值域约束；它不会重新求和来证明 40 算得对不对，算法正确性仍由计算实现负责。

<ComponentPreview files="transform-result" hideCode type="flow" size="md" />

校验通过后，结果同时保留规范行与字段模型，供下一阶段或展示组件消费。`applyTransformsToDataView` 返回这两部分，便捷入口 `applyTransforms` 只返回行数组。

计算抛错或结果校验失败都会终止后续阶段。此时计算已经发生，预检和结果校验都不能撤销已产生的外部计算副作用。
