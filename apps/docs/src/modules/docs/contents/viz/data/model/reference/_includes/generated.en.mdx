Look up the data-reference, field-model, and field-declaration schemas exported by `@retikz/data`. See [Field Types](/viz/data/model/field-types) for usage and [API Reference](/viz/data/model/reference) for runtime definitions.

These schemas describe serializable configuration only. Data rows, parsers, and comparators remain in consumer runtime code. Omitting `type` preserves inference; omitting `format` uses default coercion for the resolved type; omitting `order` preserves category appearance order. Runtime resolution applies these behaviors; schema validation does not materialize them as field values.

<DocTab value="schema" label="Schema">

Field declarations branch by `type`: `categorical` supports category `order`; `continuous` and `temporal` forbid it. Omitting `type` preserves inference; when `order` is declared, the resolved field type must be categorical.

`format` accepts a nonblank built-in or custom parsing format name. Registration is checked at runtime.

`order` accepts a nonblank built-in or custom name, or a nonempty category array. Built-ins include `naturalAscending` / `naturalDescending`. Custom orders must be registered in the consuming request; comparator functions stay outside JSON.

export const BUILTIN_FIELD_ORDERS: ReadonlyArray<FieldOrderDefinition> = freezeDefinitions([
  defineFieldOrder({ name: BuiltinFieldOrderMode.Appearance, compare: () => 0 }),
