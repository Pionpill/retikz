---

图形或表格展示的数据会不断更新，也可能来自不同接口。Data 对接的是**数据源在运行时提供的行**，而不是把某一批数据写死在图形配置里。文件、接口或数据库由应用读取后交给 Data；Data 负责把这些行整理成后续配置能稳定使用的字段。

## 数据行与字段

假设今天使用销售接口，明天改用预测接口。两份数据都表示地区和收入，但写法不同：

销售接口：

```json
{ "region": "north", "revenue": 12 }
```

预测接口：

```json
{ "area": "north", "pricing": { "amount": "12" } }
```

如果后续配置直接写死 `revenue`，第二个接口就找不到收入；如果每次切换数据源都去改图形或变换配置，同一个业务含义会在多处出现不同名字。即使仍使用第二个接口，过段时间 `pricing.amount` 也可能缺失，或从数字串变成另一种存储格式。字段名对齐只能解决“从哪里读”，不能保证每次都能读到有效值。

## 物理路径与逻辑字段

解决办法是在原始数据与后续处理之间建立**数据模型**。它提供稳定的模型层：先约定后续需要的字段名称和含义，再由数据接入把当前数据源的记录映射、规范化到这些字段，最后交给数据变换和可视化。这样，可视化只依赖数据模型确定的逻辑字段契约，无需了解原始记录用了什么路径。

先看整体关系：字段契约约束数据接入，规范化后的行再交给后续处理。

图中的字段契约描述逻辑字段，不保存原始数据行；实线表示数据从外部行流向后续处理。

在上面的例子中，模型约定后续始终使用 `region` 和 `revenue`，并说明 `revenue` 是可以计算的连续量。原始记录中的 `area`、`pricing.amount` 叫**物理路径**；模型约定的 `region`、`revenue` 叫**逻辑字段**。销售接口的收入路径已经是 `revenue`，预测接口则通过接入映射把 `pricing.amount` 对齐到 `revenue`，地区也从 `area` 对齐到 `region`。物理路径与逻辑字段同名时无需映射。

再看具体值。下图的两份原始记录是**可替换的来源**，不是要合并的两行：两者经过各自的接入规则后，都交出相同的逻辑字段与数值。

<ComponentPreview files="source-to-logical-fields" size="md" hideCode type="illustration" />

预测源的 `pricing.amount` 原本是数字串 `"12"`，解析后成为数值 `12`；后续配置只读取 `revenue`。

更换数据源时，调整的是接入映射和必要的解析规则；图形、表格和数据变换仍引用同一组逻辑字段。这里的“建立模型”是为字段建立稳定的名字与语义，不是保存这两条实际数据行。配置中的 `model` 可以显式声明字段；简单数据也允许省略它并自动推断类型。跨数据源复用或需要明确处理类型时，显式声明更可靠。

一行外部数据需要两层约定：逻辑字段回答“从哪里读取”，测量类型回答“这个值表示什么”。字段声明可以保存在可序列化的 `model` 中，真实数据行在运行时传入。

## 为什么需要测量类型

同样是数字 `10`，它可能表示可以计算差值的收入，也可能只是一个阶段编号。`@retikz/data` 的字段类型描述的是**怎样理解和使用字段**，不是原始数据采用了 `number`、`string` 还是 `Date` 存储。

数据源会切换，字段里的值也会变化。如果数据变换和可视化各自根据当前值猜测字段含义，同一个逻辑字段可能一会儿被当作可计算的数值，一会儿被当作类别；原始值从 `12` 变成 `'12'` 也可能改变处理结果。

测量类型让数据模型先约定字段的含义。`@retikz/data` 在接入时据此解析并归一化字段值，后续处理依赖同一份字段语义，不必重新猜测原始数据。这样数据源或样本发生变化时，字段的计算、分组与映射规则仍有稳定的依据。

## 三种内置类型

| 测量类型      | 字段含义                         | 例子                         |
| ------------- | -------------------------------- | ---------------------------- |
| `continuous`  | 数值大小和差值有意义             | 收入 `12`、温度 `20`         |
| `categorical` | 值用于区分类别，编码间距没有意义 | 地区 `north`、阶段编号 `10`  |
| `temporal`    | 值表示日期或时间点               | `2026-09-23`、带时区的时间戳 |

这三类是当前数据处理与可视化共同需要的基本区分：数值距离、类别身份和时间顺序。`@retikz/data` 据此整理参与字段的有效值：连续字段成为有限数值，时间字段成为毫秒时间戳，分类字段保留字符串或有限数字类别。下游消费模块可按相同的字段语义做变换或映射，而无需重新猜测原始值。[Plot 的比例尺](/viz/plot/scale)是一个消费例子；类型本身不规定图形怎样呈现。

| Vega-Lite 类型 | 字段含义                 | 与 `@retikz/data` 的关系                        |
| -------------- | ------------------------ | ----------------------------------------------- |
| `quantitative` | 可比较大小与差值的量     | 对应 `continuous`                               |

## 原始值不决定字段语义

考虑下面两列：

```json
{ "stage": 10, "revenue": "12" }
```

`stage` 应声明为 `categorical`：`10` 与 `20` 是不同阶段，不意味着阶段之间有十个单位的距离。`revenue` 应声明为 `continuous`：虽然原始值是字符串，归一化后它可以成为数值 `12`，供求和等操作使用。数字也能表示类别，字符串也能表示数值；选择类型要看字段含义。

`temporal` 与连续数值同样可以比较先后和间隔，但它保留时间语义，让消费模块选择时间刻度和日期格式。普通数字不会仅因看起来像时间戳就自动推断成时间；非默认日期格式也需要明确解析。

## 类型与解析格式

`type` 回答“这个字段表示什么”；`format` 回答“原始值按什么规则解析”。例如，`'50%'` 表示连续量，但需要 `percent` 格式才会解析成 `0.5`。类型与格式可以一起声明；具名格式也可以蕴含类型。完整字段写法与优先级见[字段契约](/viz/data/model/contract)，内置格式及字段映射见[数据接入](/viz/data/model/intake)。

未声明时，`@retikz/data` 会从有效样本推断类型。数字编码的类别可能被推断为连续，数字字符串则不会仅凭内容被推断为连续。因此，当类型会影响结果，或输入格式不够明确时，应在 `model` 中显式声明；简单、无歧义的数据可以先使用推断。

## 先规范化，再交给下游

模型层不仅约定字段名称，还要让交出的值符合约定。Data 按当前数据源的路径取值，再按字段类型与解析格式处理，写回逻辑字段名。上面两行数据的有效收入在规范化后都可按 `revenue: 12` 读取；第二行的原始数字串也变成数值。后续处理实际读取的是这些规范化后的行及字段类型，而不是仅仅读取 `model` 声明。规范化保持输入行数，不负责汇总或筛选；需要改变行数或生成新字段时再使用[数据变换](/viz/data/transform)。

预测接口后来可能返回 `{ area: 'north' }`，让收入字段缺失；也可能把金额改存为 `'1,200'`，需要相应的解析格式。规范化不会为缺失值凭空补出 `12`；如果数据源连整条记录都不再返回，模型也不会重建这条记录。默认消费方可以跳过无效值；需要知道哪些参与字段缺失或解析失败，可开启抽样诊断或严格校验。数据模型隔开了原始数据的结构变化与可视化配置，但数据源的字段或格式变动仍可能需要更新接入规则；**它不会保证数据源永远完整**。
