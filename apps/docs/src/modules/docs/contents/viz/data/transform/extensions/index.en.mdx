---
title: Extension mechanisms
description: Extend data processing with custom transforms and operators, from definitions and implementations to host registration.
---

A custom extension describes what parameters an operation accepts, what fields it produces, and how to compute the result. Data separates these responsibilities into a Definition and an Implementation, which the host registers and calls.

## When to extend

First check whether a combination of built-in operations can do the job. If you need an extension, choose its scope:

- A custom transform adds a complete row-processing operation, such as deriving a field from parameters.
- A custom operator adds a computation or row-selection rule while keeping the existing transform's grouping and result assembly. A reducer returns computed fields; a selector returns selected original rows.

See [Transform Operations](/viz/data/transform/operations) and [Computation Operators](/viz/data/transform/statistics) for how they work together. To run an existing operation on another engine, reuse its Definition and follow [Computation Contracts](/viz/data/transform/computation).

The definition functions below are exported from `@retikz/data`. A custom `kind` can be a new string, but it must not duplicate a built-in name or another name in the same registry.

## Custom transforms

The `scale-field` example reads `x`, multiplies it by `factor`, and writes the result to `scaledX`. Changing the factor moves the blue points while the gray source points stay in place:

<DocSteps>
<DocStep title="Declare parameters and field changes">

Use `defineTransform` to declare the operation name, parameter constraints and field changes. It accepts a configuration object:

- `kind` (required): the unique operation name. This example uses `scale-field`, referenced through `operation.kind`.
- `paramsSchema` (required): defines the structure, defaults and validation rules for `operation.params`. Here it contains the input `field`, output name `as` and positive multiplier `factor`.
- `inputFields` (optional): returns the field names read by the operation so the system can check field dependencies. Here it reads `operation.params.field`.
- `outputModel` (required): declares the field model after computation. `preserve.outputs` retains existing fields and adds or overwrites fields; `replace.fields` lists the complete replacement field set. This example adds a continuous field.
- `schedule` (optional): describes the execution `phase`, allowed `bindingClass` and `fieldEffect` for host scheduling. Here these mean field derivation, field binding, and preserving and extending existing fields.
- `validate` (optional): checks constraints involving operation parameters and the current field model.
- `dependencies` (optional): declares computation dependencies for this operation, such as reducers or selectors it calls.

These callbacks analyze parameters and field models without processing rows. The `scaleField` below only reads a field and adds another, so it does not configure `validate` or `dependencies`.

```ts
import {
  DataFieldType,
  DataTransformBindingClass,
  DataTransformFieldEffect,
  DataTransformPhase,
  defineTransform,
} from '@retikz/data';
import { z } from 'zod';

const scaleField = defineTransform({
  kind: 'scale-field',
  paramsSchema: z.strictObject({
    field: z.string().min(1).describe('Input field read from each row'),
    as: z.string().min(1).describe('Output field written to each row'),
    factor: z.number().positive().describe('Serializable multiplication factor'),
  }),
  inputFields: operation => [operation.params.field],
  outputModel: operation => ({
    kind: 'preserve',
    outputs: [{ field: operation.params.as, type: DataFieldType.Continuous }],
  }),
  schedule: {
    phase: DataTransformPhase.FieldDerive,
    bindingClass: DataTransformBindingClass.Field,
    fieldEffect: DataTransformFieldEffect.Preserve,
  },
});
```

</DocStep>
<DocStep title="Provide the computation">

Reference the definition with `defineTransformImplementation` and compute the result in `apply`. This implementation multiplies each value and returns new rows, preserving existing fields and provenance without modifying the input.

```ts
import { defineTransformImplementation } from '@retikz/data';

const scaleFieldImplementation = defineTransformImplementation({
  definition: scaleField,
  apply: (rows, operation) =>
    rows.map(row => ({
      ...row,
      [operation.params.as]: Number(row[operation.params.field]) * operation.params.factor,
    })),
});
```

</DocStep>
<DocStep title="Register and reference the operation">

Register the definition and implementation on Plot, then reference the operation name and parameters through `PlotTransform`. This code continues from the previous steps and plots the derived `scaledX` field.

```tsx
import type { IRDataModel } from '@retikz/data';
import { Plot, PlotTransform, PointMark } from '@retikz/plot-react';
import type { FC } from 'react';

const rows = [
  { x: 1, y: 2 },
  { x: 2, y: 4 },
  { x: 3, y: 3 },
];

const model: IRDataModel = [
  { name: 'x', type: 'continuous' },
  { name: 'y', type: 'continuous' },
];

export const CustomTransformExample: FC = () => (
  <Plot
    data={rows}
    model={model}
    width={420}
    height={260}
    transformDefinitions={[scaleField]}
    transformImplementations={[scaleFieldImplementation]}
  >
    <PlotTransform operation={{ kind: 'scale-field', params: { field: 'x', as: 'scaledX', factor: 2 } }} />
    <PointMark x="scaledX" y="y" />
  </Plot>
);
```

Definitions and implementations are registered at runtime; JSON stores only operation names and parameters. An implementation must reference the same definition object and cannot be registered twice. Other hosts accept these registrations through their lowering options. See [Computation Contracts](/viz/data/transform/computation) for external computation and Promises.

</DocStep>
</DocSteps>

## Custom operators

An operator processes the group of rows supplied by its host. Both examples below use the same groups: the left plot uses `midpoint` to compute the midpoint of the minimum and maximum, while the right plot uses `closest-to-mean` to select the original row nearest to the mean.

<DocTabs defaultValue="reducer">
<DocTab value="reducer" label="Reducer">
<DocSteps>
<DocStep title="Declare parameters and outputs">

Use `defineStatisticsReducer` to declare the operator parameters and output fields:

- `schema` (required): the complete operator structure, including its `kind`, input `field` and output name `as`.
- `inputFields` (optional): returns the field names read by the operator for dependency checks.
- `outputs` (required): lists every returned field and its type. For non-scalar or unknown output types, declare only the field name.

```ts
import { DataFieldType, defineStatisticsReducer } from '@retikz/data';
import { z } from 'zod';

const midpoint = defineStatisticsReducer({
  schema: z.strictObject({
    kind: z.literal('midpoint'),
    field: z.string().min(1),
    as: z.string().min(1),
  }),
  inputFields: operation => [operation.field],
  outputs: operation => [{ field: operation.as, type: DataFieldType.Continuous }],
});
```

</DocStep>
<DocStep title="Provide the computation">

`reduce` receives the current group of rows and returns the computed fields. This implementation takes the midpoint of the minimum and maximum, or returns `NaN` when no finite values exist.

```ts
import { defineStatisticsReducerImplementation } from '@retikz/data';

const midpointImplementation = defineStatisticsReducerImplementation({
  definition: midpoint,
  reduce: (rows, operation) => {
    const values = rows.map(row => Number(row[operation.field])).filter(Number.isFinite);
    if (values.length === 0) return { [operation.as]: Number.NaN };
    return { [operation.as]: (Math.min(...values) + Math.max(...values)) / 2 };
  },
});
```

</DocStep>
<DocStep title="Register and reference the operator">

Register the definition and implementation on Plot, then reference the operator in `summarize.metrics`. The host groups the rows and combines the returned `midpoint` with the grouping fields.

```tsx
import type { IRDataModel } from '@retikz/data';
import { Plot, PlotTransform, PointMark } from '@retikz/plot-react';
import type { FC } from 'react';

const rows = [
  { group: 'A', score: 62 },
  { group: 'A', score: 74 },
  { group: 'A', score: 91 },
];

const model: IRDataModel = [
  { name: 'group', type: 'categorical' },
  { name: 'score', type: 'continuous' },
];

export const CustomReducerExample: FC = () => (
  <Plot
    data={rows}
    model={model}
    width={420}
    height={260}
    statisticsReducerDefinitions={[midpoint]}
    statisticsReducerImplementations={[midpointImplementation]}
  >
    <PlotTransform
      operation={{
        kind: 'summarize',
        params: {
          groupBy: ['group'],
          metrics: [{ kind: 'midpoint', field: 'score', as: 'midpoint' }],
        },
      }}
    />
    <PointMark x="group" y="midpoint" />
  </Plot>
);
```

</DocStep>
</DocSteps>
</DocTab>
<DocTab value="selector" label="Selector">
<DocSteps>
<DocStep title="Declare parameters and input fields">

Use `defineRowSelector` to declare the selection parameters. It adds no statistical fields:

- `schema` (required): the complete operator structure, here containing its `kind` and input `field`.
- `inputFields` (optional): returns the field names read during selection.

```ts
import { defineRowSelector } from '@retikz/data';
import { z } from 'zod';

const closestToMean = defineRowSelector({
  schema: z.strictObject({
    kind: z.literal('closest-to-mean'),
    field: z.string().min(1),
  }),
  inputFields: operation => [operation.field],
});
```

</DocStep>
<DocStep title="Provide the selection">

`select` returns selected original rows as `[{ row }]`, optionally with a `rank` starting at 1. This implementation selects the row nearest to the mean, keeps the first row on a tie, and returns an empty array when no valid candidates exist.

```ts
import { defineRowSelectorImplementation } from '@retikz/data';

const closestToMeanImplementation = defineRowSelectorImplementation({
  definition: closestToMean,
  select: (rows, operation) => {
    const candidates = rows
      .map(row => ({ row, value: Number(row[operation.field]) }))
      .filter(candidate => Number.isFinite(candidate.value));
    if (candidates.length === 0) return [];

    const mean = candidates.reduce((sum, candidate) => sum + candidate.value, 0) / candidates.length;
    const selected = candidates.reduce((best, candidate) =>
      Math.abs(candidate.value - mean) < Math.abs(best.value - mean) ? candidate : best,
    );

    return [{ row: selected.row }];
  },
});
```

</DocStep>
<DocStep title="Register and reference the operator">

Register the definition and implementation on Plot, then reference the operator through `select.selector`. This example keeps the original row with score 74 in group A.

```tsx
import type { IRDataModel } from '@retikz/data';
import { Plot, PlotTransform, PointMark } from '@retikz/plot-react';
import type { FC } from 'react';

const rows = [
  { group: 'A', score: 62 },
  { group: 'A', score: 74 },
  { group: 'A', score: 91 },
];

const model: IRDataModel = [
  { name: 'group', type: 'categorical' },
  { name: 'score', type: 'continuous' },
];

export const CustomSelectorExample: FC = () => (
  <Plot
    data={rows}
    model={model}
    width={420}
    height={260}
    rowSelectorDefinitions={[closestToMean]}
    rowSelectorImplementations={[closestToMeanImplementation]}
  >
    <PlotTransform
      operation={{
        kind: 'select',
        params: {
          groupBy: ['group'],
          selector: { kind: 'closest-to-mean', field: 'score' },
        },
      }}
    />
    <PointMark x="group" y="score" />
  </Plot>
);
```

Custom selectors work with `select` and transforms that explicitly support them. `annotate` accepts only a built-in subset of single-row selectors.

</DocStep>
</DocSteps>
</DocTab>
</DocTabs>

For local execution, register both the definition and implementation, with the implementation referencing the same definition object. Duplicate names and implementations follow the same checks as custom transforms. Hosts also accept these registrations through their lowering options.
