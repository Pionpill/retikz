title: Extension mechanisms
description: Define and register custom transforms, reducers and selectors with separate semantics and local implementations.
---

Data uses a Definition to describe an operation and an Implementation to compute it. Operations `{ kind, params }` and execution settings are JSON-safe; schemas, functions, executors and source handles remain runtime objects.

## When to extend

Define a transform for new row semantics, a reducer when `summarize` or `annotate` needs a statistic, or a selector when `select` needs a selection rule. To replace the computation engine, reuse the existing Definition instead of assigning different semantics to the same name.

`kind` is open, but custom names cannot replace built-ins. All entries are exported from the `@retikz/data` root.

## Define the capability

`defineTransform` accepts `kind`, an exact `paramsSchema`, optional `inputFields`, and required `outputModel`. It assembles the complete operation schema with `createTransformSchema`; built-in and custom transforms share the same envelope. Callbacks receive the complete operation and read parsed parameters through `operation.params`. Semantic callbacks read parameters and field models, never rows or computation. Declare every statistical dependency with `dependencies`; use `validate` for model invariants.

Use `preserve.outputs` to extend a model or `replace.fields` to replace it. An output may omit its type when no evidence exists. `{ from: field }` preserves the source type and applicable categorical order. Derived field names are projected from this model.

`defineTransformImplementation({ definition, apply })` references that same Definition. This `scale-field` example reads `x` and creates `scaledX` using `factor`:

Implementations must honor the Definition and leave input arrays and rows unchanged. Spreading an original row preserves its provenance Symbols; use the computation context's `groupProvenance(out, members)` for grouped output. Semantic Definitions do not hold these helpers.

### Transform operators

`defineStatisticsReducer` describes its schema, inputs and every output through required `outputs`. Non-scalar or unknown outputs declare only their names. `defineStatisticsReducerImplementation({ definition, reduce })` supplies computation.

`defineRowSelector` declares a schema and inputs; `defineRowSelectorImplementation({ definition, select })` returns original rows and optional one-based ranks. `defineRegression` and `defineRegressionImplementation({ definition, fit })` follow the same split.

Custom selectors work in `select` and operations that explicitly support them. Data's `annotate` accepts only the built-in single-row selector subset.

## Inject and use

Register semantic definitions and local implementations separately. Plot exposes these props; Chart accepts the same names in `lowerOptions`, while Table uses its lowering options.

| Capability | Semantic definitions           | Synchronous local implementations  |
| ---------- | ------------------------------ | ---------------------------------- |
| transform  | `transformDefinitions`         | `transformImplementations`         |
| reducer    | `statisticsReducerDefinitions` | `statisticsReducerImplementations` |
| selector   | `rowSelectorDefinitions`       | `rowSelectorImplementations`       |
| regression | `regressionDefinitions`        | `regressionImplementations`        |

Hosts use `{ operation, dataExecution? }` declarations. `operation` holds computation parameters; `dataExecution` selects execution:

```tsx
<Plot data={rows} transformDefinitions={[scaleField]} transformImplementations={[scaleFieldImplementation]}>
  <PlotTransform operation={{ kind: 'scale-field', params: { field: 'x', as: 'scaledX', factor: 2 } }} />
  <PointMark x="scaledX" y="y" />
</Plot>
```

Data's synchronous `applyTransforms` still takes operation arrays. For asynchronous execution, first resolve declarations and an input model with `resolveDataTransforms`, then call `executeDataTransforms`.

See [Computation Contracts](/viz/data/transform/computation) for external providers, execution modes, asynchronous hosts and input bindings.

## Errors and limitations

- Duplicate semantic keys, duplicate implementations and mismatched Definition references fail immediately.
- Definition-only extensions can execute externally; local execution requires an Implementation.
