A field model gives data stable names and meanings. Decide whether a field represents categories, quantities, or time, then use `model` to declare parsing rules and any required category order. Transforms and consumers can use the same contract.

## Field model

A sales API might return `{ region: 'north', revenue: 12 }`, while a forecast API returns `{ area: 'north', pricing: { amount: '12' } }`. Both describe a region and revenue, but their paths and stored values differ.

The model establishes `region` and `revenue` as **logical fields** for downstream use. The raw record's `area` and `pricing.amount` are **physical paths**. Intake maps the names and parses the numeric string. The two records below are alternative sources that produce the same logical fields:

No mapping is needed when physical and logical names match; see [Data Intake](/viz/data/model/intake) for configuration. A field model (`IRDataModel`) stores declarations only. Actual rows arrive separately at runtime.

## Measurement types

The number `10` might be an amount whose differences matter, or it might only be a stage code. In `@retikz/data`, a field type describes **how to interpret and use a field**, not whether its raw values happen to be stored as JavaScript `number`, `string`, or `Date` values.

`@retikz/data` provides three built-in measurement types:

| Measurement type | Type name  | Meaning                                      | Example                         |
| ---------------- | ---------- | -------------------------------------------- | ------------------------------- |
| `continuous`     | Continuous | Numeric magnitudes and differences matter    | Revenue `12`, temperature `20`  |
| `categorical`    | Discrete   | Values identify categories; code gaps do not | Region `north`, stage code `10` |
| `temporal`       | Timestamp  | Values represent dates or points in time     | `2026-09-23`, zoned timestamps  |

These three types capture the basic distinctions shared by current data processing and visualization: numeric distance, category identity, and time order. `@retikz/data` uses them to normalize valid values in participating fields: continuous values become finite numbers, temporal values become millisecond timestamps, and categorical values retain string or finite-number category values. Consumers can transform or map fields using the same semantics instead of guessing from raw values again. [Plot scales](/viz/plot/scale) are one consumer example; the field type itself does not prescribe a visual representation.

<Comparison target="vega" title="Vega-Lite Field Semantic Types">

| Vega-Lite type | Field meaning                        | Relationship to `@retikz/data`                             |
| -------------- | ------------------------------------ | ---------------------------------------------------------- |
| `quantitative` | Magnitudes and differences matter    | Corresponds to `continuous`                                |
| `nominal`      | Unordered discrete categories        | Corresponds to `categorical`                               |

| `geojson`      | Geographic shapes for geoshape marks | `@retikz/data` has no corresponding field measurement type |

`@retikz/data` groups ordered and unordered categories under `categorical`; it has no separate `ordinal` type. Vega-Lite's `geojson` is specific to geographic shapes. Numeric latitude and longitude channels still use `quantitative`, so not every geographic field is `geojson`. We are not considering `geojson` support for now; we will revisit it when designing map capabilities for Plot.

Choose a measurement type by the field's meaning, not how its raw values are stored. Consider these two fields:

```json
{ "stage": 10, "revenue": "12" }
```

Declare `stage` as `categorical`: `10` and `20` are different stages, not stages separated by ten units. Declare `revenue` as `continuous`: although the raw value is a string, normalization can produce the number `12` for operations such as summation. Numbers can identify categories, and strings can represent quantities. Choose a type by meaning.

Like continuous values, `temporal` values can be ordered and compared by interval, but their time semantics let consumers use time ticks and date formatting. An ordinary number is not inferred as a timestamp simply because it looks like one; non-default date formats also need explicit parsing.

## Field declarations

`model` is an array of field declarations. This example treats regions as categories and revenue as a continuous quantity:

```ts
import type { IRDataModel } from '@retikz/data';

const model: IRDataModel = [
  { name: 'region', type: 'categorical' },
  { name: 'revenue', type: 'continuous' },
];
```

Pass it to the consumer's `model` property to parse `revenue: '12'` as `revenue: 12`. Simple, unambiguous data can omit the model and use inference. Declare fields explicitly when their meaning must remain stable across samples.

Each field declaration is an `IRDataFieldDefinition` exported from `@retikz/data`. It is a union distinguished by `type`, with these shared fields:

| Shared field | Type                                             | Responsibility                                                                                                  |
| ------------ | ------------------------------------------------ | --------------------------------------------------------------------------------------------------------------- |
| `name`       | `string`                                         | Required non-blank logical field name referenced by transforms and consumers                                    |
| `format?`    | <ApiValues name="DataFieldFormat" /> \| `string` | Optional built-in or custom parsing format; omission uses default coercion, and a named format can imply a type |

Besides the shared fields, a field declaration has two further fields: `type` specifies the measurement type, inferred from format or data when omitted; `order` specifies the category-domain order, and whether it is allowed depends on `type`. Their combination constraints are:

| `type`                        | Field meaning                        | `order` constraint                                                                                                                                                        |
| ----------------------------- | ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `'categorical'`               | Discrete categories                  | Optional; accepts <ApiValues name="FieldOrderMode" />, a custom name, or a non-empty `Array<string \| number>`                                                            |
| `'continuous'` / `'temporal'` | Continuous numbers / dates and times | Forbidden, including `'appearance'`                                                                                                                                       |
| Omitted                       | Type inferred from format or data    | Optional; accepts <ApiValues name="FieldOrderMode" />, a custom name, or a non-empty `Array<string \| number>`; resolution fails if the resulting type is non-categorical |

**Omitting a field type is different from omitting a field declaration.** You can write `{ name: 'region' }` to retain type inference. Once `model` is declared, however, every source field referenced by the current pipeline must be listed, and field names must be unique. For example, referencing `revenue` when the model contains only `size` fails. Unreferenced extra columns in the raw data need not be listed.

## Field resolution

`name` identifies the logical field to read; `type` and `format` determine its type and parsing rule. The diagram separates three cases according to whether `format` and `type` are declared. Follow one branch, then continue to value parsing and order handling:

<ComponentPreview files="field-resolution" hideCode type="flow" size="xl" />

- **With `format`**: use the registered format's type and parser. An explicit `type` must agree with the format; unknown formats and conflicting types fail. For example, `percent` implies `continuous` and parses `'50%'` as `0.5`.
- **Without `format`, with `type`**: use default coercion for the declared type. For example, `continuous` converts a strict numeric string such as `'12'` to the number `12`.
- **Neither declared**: infer the type from samples, then use default coercion. Declare numeric category codes explicitly as `categorical`; numeric strings are not inferred as continuous merely from their content.

`order` does not participate in type inference. An explicit non-categorical type with `order` is rejected during declaration validation. With `type` omitted, resolution also fails if the resulting type is non-categorical. The next section explains category ordering.

The diagram reads logical fields. See [Data Intake](/viz/data/model/intake) for physical-path mapping and built-in formats. To override a type or parsing rule programmatically before values are parsed, see [Extensions](/viz/data/model/extensions).

### Automatic inference

When `type` is omitted and no `format` implies a type, `@retikz/data` classifies raw samples as follows:

| JavaScript value     | Example or condition                                                                      | Sample measurement type               |
| -------------------- | ----------------------------------------------------------------------------------------- | ------------------------------------- |
| `number`             | Finite values such as `12`, including numeric timestamps                                  | `continuous`                          |
| `bigint`             | Such as `12n`                                                                             | `continuous`                          |
| `Date`               | A `Date` instance                                                                         | `temporal`                            |
| Date-shaped `string` | `2026-09-23`, or a date-time with `Z` / a timezone offset, such as `2026-09-23T08:00:00Z` | `temporal`                            |
| Other `string`       | `'north'`, `'12'`, `'2026/09/23'`, or a date-time without a timezone                      | `categorical`                         |
| `boolean`            | `true`, `false`                                                                           | `categorical`                         |
| Other values         | `null`, `undefined`, `NaN`, infinities, plain objects, arrays, functions, `symbol`        | Skipped; not counted as valid samples |

Inference applies to the whole column: it scans at most the first 1000 rows and collects up to 100 valid samples. If all samples share one measurement type, that type is used; mixed measurement types or no valid samples fall back to `categorical`. For example, `12` and `12n` both imply `continuous`, while mixing `12` and `'12'` yields `categorical`. Recognizing a date-shaped value does not validate the date; actual values still undergo parsing afterward.

Normalized rows use logical field names and preserve the row count; normalization does not invent missing data. See [Validation & Diagnostics](/viz/data/model/validation) for missing values, parsing failures, and handling policies.

## Category order

Categorical fields form their domain in data-appearance order by default. Put `order` on the field when the business order should be `S → M → L → XL`:

| `order`                         | Effect                                                         |
| ------------------------------- | -------------------------------------------------------------- |
| Omitted / `'appearance'`        | Preserve data-appearance order                                 |
| `'ascending'` / `'descending'`  | Compare all-numeric categories numerically, otherwise as text  |
| Array such as `['S', 'M', 'L']` | Use the array first, then append remaining observed categories |

`model.order` orders the **categorical domain**; it does not reorder rows. Consumers can use it to preserve category semantics. In a Plot application, it affects categorical positions, legends, and discrete colors without changing path connection order. Use [data-transform sorting](/viz/data/transform/operations#sort) for rows; an explicit Plot scale `domain` takes precedence over `order`.

### Natural ordering

Keep versions as strings. Alphabetical ascending places `'10.18'` before `'10.2'`; `order: 'naturalAscending'` produces `10.2 → 10.18`. Use `naturalDescending` for the opposite direction.

Natural ordering compares ASCII digit runs as arbitrary-length integers and other runs in case-sensitive UTF-16 order. Numeric runs precede text runs; a shorter sequence comes first when shared runs compare equally. It does not interpret decimals, negative numbers, or SemVer. Equivalent keys such as `'v02'` and `'v2'` retain appearance order in both natural directions while remaining distinct categories.

### Custom ordering

When built-in rules do not fit your business needs, define a named comparator with `defineFieldOrder`, inject it through the consumer’s `fieldOrderDefinitions`, and reference its name in the field’s `order`. Built-in and custom orders share the same registration and execution mechanism. The model stores only the name; comparator functions stay at runtime.

For example, define `labelLength` to order labels from shortest to longest: `compare(a, b)` returns `String(a).length - String(b).length`. Pass the definition to `fieldOrderDefinitions` and use `order: 'labelLength'` on the field to produce `2.0 → 10.2 → 10.18 → 10.2.0`.
