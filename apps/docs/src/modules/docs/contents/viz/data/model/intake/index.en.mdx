Start with the logical contract in [Field Types](/viz/data/model/field-types), then bind real data to it. Mapping determines where a value comes from; types and formats determine how to interpret it. For example, read `pricing.amount` as `revenue`, then parse `'50%'` as `0.5`. After parsing, choose to skip, diagnose, or reject unusable values. The examples visualize Data processing results.

## Field mapping

Sources with the same names and types only require replacing the rows. When names differ, use `fieldMap` to map logical names to physical paths while consumers keep referencing logical names. Mapping requires `model` and can only target declared fields. An omitted entry reads the logical name directly.

Physical paths support dotted access such as `pricing.amount`. Reading first checks for an exact own key, then traverses nested properties. Arrays are not unwound automatically; reshape the source first when one record must produce multiple rows.

Switch between actual, forecast, and finance data below. The first two only replace rows; finance also maps paths. Consumers always reference `month` and `revenue`.

Choose `fieldMap` based on the source. The pseudocode below omits data selection and consumer configuration, keeping only the mapping logic:

```ts
const fieldMap = source === 'finance' ? { month: 'period', revenue: 'amount' } : undefined;
```

Actual and forecast rows already contain `month` and `revenue`, so they need no mapping. Finance rows use `period` and `amount`; `fieldMap` aligns them with the logical names. The model and the logical fields referenced by consumers stay the same for every source.

Mapping changes where values are read, not how they are parsed. When mapping to a different path, explicitly declare `type` or `format` in the model rather than relying on inference, which reads logical field names from raw rows.

Mapping and rows stay at runtime; the field model only stores the contract. Consumers keep reading the same logical fields when a mapping changes.

## Value parsing

Once the type is known, default coercion converts finite numbers, safe-integer `bigint` values, and strict numeric strings to continuous values. It converts `Date`, strict ISO strings, and epoch milliseconds to temporal values. Converting a numeric string is distinct from inferring an undeclared type; see [Measurement types](/viz/data/model/field-types).

Declare non-default storage formats through the field's `format`. The model stores the name; a built-in or runtime definition supplies the parser:

| `format`       | Type         | Parsing                                        |
| -------------- | ------------ | ---------------------------------------------- |
| `iso`          | `temporal`   | Strict ISO, equivalent to default time parsing |
| `epochSeconds` | `temporal`   | Epoch seconds to milliseconds                  |
| `epochMillis`  | `temporal`   | Epoch milliseconds                             |
| `slashDate`    | `temporal`   | Strict `YYYY/MM/DD` at UTC midnight            |
| `numberString` | `continuous` | Numeric strings with whitespace or commas      |
| `percent`      | `continuous` | Percentage string `'50%'` to `0.5`             |

`format` also determines the field type; a conflicting explicit `type` fails. A registered parser is used instead of default coercion. A failed parse does not retry default coercion: the result goes through the [validation policy](/viz/data/model/intake#validation-policy).

## Category order

Categorical fields form their domain in data-appearance order by default. Put `order` on the field when the business order should be `S → M → L → XL`:

| `order`                                      | Effect                                                                                    |
| -------------------------------------------- | ----------------------------------------------------------------------------------------- |
| Omitted / `'appearance'`                     | Preserve data-appearance order                                                            |
| `'ascending'` / `'descending'`               | Compare all-numeric categories numerically, otherwise as text                             |
| `'naturalAscending'` / `'naturalDescending'` | Natural ascending / descending by digit runs, suitable for version labels and identifiers |
| Array such as `['S', 'M', 'L']`              | Use the array first, then append remaining observed categories                            |

`model.order` orders the **categorical domain** without reordering rows. Consumers can reuse this category order; use [data-transform sorting](/viz/data/transform/operations#sort) to change row order.

Keep versions as strings. Alphabetical ascending places `'10.18'` before `'10.2'`; `order: 'naturalAscending'` produces `10.2 → 10.18`. Use `naturalDescending` for the opposite direction.

Natural ordering compares ASCII digit runs as arbitrary-length integers and other runs in case-sensitive UTF-16 order. Numeric runs precede text runs; a shorter sequence comes first when shared runs compare equally. It does not interpret decimals, negative numbers, or SemVer. Equivalent keys such as `'v02'` and `'v2'` retain appearance order in both natural directions while remaining distinct categories.

## Validation policy

The example intake configuration defaults to `invalid: 'skip'`: normalization retains rows without inventing replacement values, and consumers decide how to skip unusable values. Use sampled diagnostics when a field has no valid values.

`invalid` determines whether bad values are strictly rejected and only accepts `skip` or `error`. `validateData` is a separate sampled-diagnostics switch, not a third `invalid` policy.

| Property       | Value                           | Behavior and use case                                                                                           |
| -------------- | ------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `invalid`      | `'skip'` (default)              | Retain normalized rows and let consumers skip invalid values; tolerate a few bad points                         |
| `invalid`      | `'error'`                       | Check all participating values and reject missing or invalid values; enforce strict data admission              |
| `validateData` | `false` (default)               | Disable sampled diagnostics                                                                                     |
| `validateData` | `true` or `{ sampleRows: 100 }` | Require at least one valid value per participating field in the sample; diagnose blank charts and path mappings |

`validateData: true` checks the first 100 rows by default. Pass an object with `sampleRows` to change the sample size. Sampling allows some bad values, so it does not replace the per-value checks performed by `invalid: 'error'`.

Choose a dataset, then switch policy. Partially invalid data can pass sampling but fails strict validation. An entirely invalid field fails sampling. Switch back to valid data to recover the preview.

## Diagnostics

Checks inspect normalized values after intake and before transforms. Errors identify logical field names and zero-based input row indices, not positions after sorting or filtering.

| Error text                                | Meaning and next step                                                                                     |
| ----------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| `has no valid values in the sampled data` | No valid value for this field in the sample; check its physical path, type, and format                    |
| `missing or invalid at row 1`             | This field is unusable in the second input row; inspect the original value and parser result              |
| Unknown format or conflicting type        | Configuration is invalid; repair declarations or registration, since skip mode cannot bypass these errors |

Sampled `invalid` / `missing` counts describe normalized results and may not preserve the original failure reason. Passing sampling does not validate other rows. `sampleRows: 0` and empty data skip sampled checks. Use strict validation when every value must be valid.

Unusable results from custom parsers follow the same policies.
