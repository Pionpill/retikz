title: Data Intake
description: Bind external field paths and storage formats to logical fields, producing canonical rows before transforms run.

Data intake converts API, file, or database records into logical fields that consumers can reference consistently. The examples use React `<Plot>` to visualize the result, but Plot is only the example host: field paths, models, formats, and normalization belong to Data and can be reused by other consumers.

## Field paths

A field name may be a dotted path: `user.address.city` traverses nested objects, and the leaf must be a scalar such as text, number, boolean, or time. Resolution checks for an exact own key before traversing `.`, so a canonical logical name can itself contain dots.

```tsx
<Plot data={rows}>
  <PathMark x="user.createdAt" y="metrics.revenue" order="user.createdAt" />
</Plot>
```

Arrays are not unwound automatically. Flatten them into separate rows in the data layer when one source record should produce several observations.

## Switching data sources

Real rows stay outside the serializable field contract, so one consumer configuration can use different sources. Choose the binding based on what changed; the examples below continue to use Plot.

### Same field contract

When both sources expose the same names and types, the consumer only replaces its data input. In the Plot example below, that means replacing `<Plot data>`; actual and forecast values share one field contract and consumer configuration.

### Different field names

Use `fieldMap` to map logical names to physical paths. Data transforms and consumer configuration continue to reference only logical names. In a Plot application, marks and transforms therefore do not need to know the physical path either:

```tsx
<Plot
  data={rows}
  model={[
    { name: 'month', type: 'temporal' },
    { name: 'revenue', type: 'continuous' },
  ]}
  fieldMap={{ month: 'period', revenue: 'pricing.amount' }}
>
  <PathMark x="month" y="revenue" order="month" />
</Plot>
```

`fieldMap` aligns names without computing values. It requires `model`, because there is no logical field set to map without a field contract.

### Different storage shapes

Default coercion unifies `Date`, strict ISO strings, and epoch milliseconds as temporal values. It also unifies finite numbers, safe-integer `bigint` values, and strict numeric strings as continuous values. The mixed representations below still normalize against one model.

## Declaring parsing formats

Put common non-default formats on the field as `format`. The format name enters the serializable model, while a built-in or injected Definition supplies the parser.

| `format`       | Type         | Parsing                                        |
| -------------- | ------------ | ---------------------------------------------- |
| `iso`          | `temporal`   | Strict ISO, equivalent to default time parsing |
| `epochSeconds` | `temporal`   | Epoch seconds to milliseconds                  |
| `epochMillis`  | `temporal`   | Epoch milliseconds                             |
| `slashDate`    | `temporal`   | Strict `YYYY/MM/DD` at UTC midnight            |
| `numberString` | `continuous` | Numeric strings with whitespace or commas      |
| `percent`      | `continuous` | Percentage string `'50%'` to `0.5`             |

`format` implies a type. The intake stage reports an error when an explicit `type` conflicts with the format's type. The standard intake path applies declarative `format` before falling back to default coercion.

## Intake order

1. Collect fields referenced by the current configuration.
2. Read physical paths through `fieldMap`.
3. Resolve type from the model / format, then inference.
4. Parse with the declarative format, then default coercion.
5. Write the result under the logical name to form a canonical row.

Data transforms and consumer modules read those canonical rows instead of repeating parsing independently. In a Plot application, those consumers include scales, marks, and locators.
