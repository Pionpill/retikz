title: Field Contract

`model` is the field contract between data and consumer configuration. Downstream logic can depend on stable logical names without guessing whether a column is numeric, temporal, or categorical.

In a Plot application, that downstream logic includes marks, transforms, and scales. Table and other modules can read the same model through their own consumption contracts. The examples below use Plot to show visible differences caused by field types and category order, but `model` belongs to Data and does not depend on Plot.

## Declaring fields

Each field declaration is an `IRDataFieldDefinition` exported from `@retikz/data`:

| Field     | Type                                                                  | Default        | Responsibility                                                                  |
| --------- | --------------------------------------------------------------------- | -------------- | ------------------------------------------------------------------------------- |
| `name`    | `string`                                                              | —              | Logical name referenced by data transforms and consumer config                  |
| `type?`   | <ApiValues name="DataFieldType" />                                    | inferred       | Field measurement type                                                          |
| `format?` | <ApiValues name="DataFieldFormat" /> \| `string`                      | default parser | Declarative parsing format; a named format may also imply the field type        |
| `order?`  | <ApiValues name="FieldOrderMode" /> \|<br />`Array<string \| number>` | `'appearance'` | Category-domain order; explicit values take priority and only affect categories |

The playground below keeps one PointMark and axis structure across continuous, temporal, categorical, and numeric-category scenarios. In the funnel scenario, the uneven codes `10`, `20`, `50`, and `100` follow numeric distance when inferred as continuous, then become equally spaced when declared categorical.

Once `model` exists, every source field referenced by the current data pipeline must be listed. Misspelled references and duplicate declarations fail immediately instead of degrading into an empty result. In a Plot application, the check covers position and color channels, mark ordering, size and shape channels, and transform inputs.

### Partial declarations

`type` is optional: `{ name }` still enters the strict field set while leaving type inference to runtime. When `format` is present, its implied type takes precedence over inference.

```tsx
<Plot
  data={sales}
  model={[{ name: 'createdAt', format: 'slashDate' }, { name: 'statusCode', type: 'categorical' }, { name: 'revenue' }]}
>
  {/* … */}
</Plot>
```

Declare `type` or `format` on every field when the configuration must be fully self-describing without data. Omit `model` entirely for quick exploration.

## Automatic inference

When a field has neither `type` nor `format`, retikz scans at most 1,000 rows and collects up to 100 valid samples:

| Sample value                                         | Classified as       |
| ---------------------------------------------------- | ------------------- |
| `Date`, unambiguous ISO date, or zoned datetime      | `temporal`          |
| Finite `number` or `bigint`                          | `continuous`        |
| Other strings or booleans                            | `categorical`       |
| Empty values, non-finite numbers, objects, or arrays | Skipped as a sample |

All samples must be temporal to produce `temporal`, and all must be numeric to produce `continuous`; mixed samples, empty fields, and everything else fall back to `categorical`. `2024/01/01`, timezone-less datetimes, and bare numeric strings are not inferred as temporal or continuous. Parse non-default formats explicitly in [Data Intake](/viz/data/model/intake).

## How types affect downstream behavior

Field types let consumer modules understand data semantics; Data supplies the type without prescribing its presentation. In a Plot application, types affect scales, axes, and legends. When a position channel omits a scale, `continuous`, `temporal`, and `categorical` derive linear, time, and band scales respectively.

The field-contract playground above covers all three default position scales. Because the PointMark and axes stay fixed between scenarios, the visible difference comes from field type alone.

Within Plot, color behavior depends on the authoring layer. React `<Plot>` can synthesize a default discrete or continuous color scale when the `model` type is known. In low-level Plot IR, categorical fields may default to `ordinal`, while continuous and temporal fields must explicitly reference a continuous color scale. See [Scales](/viz/plot/scale) for the full rules and overrides.

## Category order

Categorical fields form their domain in data-appearance order by default. Put `order` on the field when the business order should be `S → M → L → XL`:

| `order`                         | Effect                                                         |
| ------------------------------- | -------------------------------------------------------------- |
| Omitted / `'appearance'`        | Preserve data-appearance order                                 |
| `'ascending'` / `'descending'`  | Compare all-numeric categories numerically, otherwise as text  |
| Array such as `['S', 'M', 'L']` | Use the array first, then append remaining observed categories |

`model.order` orders the **categorical domain**; it does not reorder rows. Consumers can use it to preserve category semantics. In a Plot application, it affects categorical positions, legends, and discrete colors without changing path connection order. Use [data-transform sorting](/viz/data/transform/operations#sort) for rows; an explicit Plot scale `domain` takes precedence over `order`.
