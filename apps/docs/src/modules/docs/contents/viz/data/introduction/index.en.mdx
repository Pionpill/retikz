`@retikz/data` prepares external rows from files, APIs, or application state into reusable data results: declare logical fields, normalize values, and run serializable data transforms in order. It does not decide how graphics are presented, so Plot, Table, and other consumers can share one prepared result.

## When to use it

Start with Data when a preparation rule is shared by multiple views, or when field types, mappings, and transforms must be stored as JSON. Real rows still arrive at runtime; rows, parser functions, and custom Definitions never enter persistent IR.

| Documentation                             | Task                                                                   |
| ----------------------------------------- | ---------------------------------------------------------------------- |
| [Data Model](/viz/data/model)             | Declare field types, formats, category order, or source-field mappings |
| [Data Transforms](/viz/data/transform)    | Sort, summarize, select representative rows, or annotate statistics    |
| [Data Traceability](/viz/data/provenance) | Trace source rows before and after processing into downstream marks    |
| [API Reference](/viz/data/reference)      | Look up schemas, Definitions, and runtime entry points                 |

## How data flows

Real rows do not enter the serializable contract. Configuration describes fields to read, their types, and the processing and transform operations to run; a consumer supplies rows when it runs the data pipeline. One configuration can therefore serve different data sources, be saved as JSON, and be generated by AI.

<ComponentPreview files="data-pipeline" size="sm" hideCode />

The pipeline first collects fields a consumer actually uses, then turns external rows into canonical rows: it aligns fields, parses values, normalizes types, and writes results under logical field names. Transforms and consumer modules read canonical rows rather than repeatedly reading raw data.

| Step                | What it does                                                                                                | Main config                            |
| ------------------- | ----------------------------------------------------------------------------------------------------------- | -------------------------------------- |
| Data reference      | Select the external dataset for this view; rows themselves stay out of IR                                   | `data` / `data.reference`              |
| Field contract      | Define logical field names, types, category order, and declarative formats; infer from samples when omitted | `model`                                |
| Source mapping      | Map logical fields to real data paths, including renamed fields and nested paths                            | `fieldMap` / `fieldMaps`               |
| Parse / normalize   | Parse values from field contracts and formats, then write results under logical field names                 | `model` / `format` / field type        |
| Validation          | Sample-check or fully check participating fields, and decide whether invalid values skip or throw           | `validateData` / `invalid`             |
| Transform / handoff | Data transforms rewrite canonical rows, then hand the result to a consumer module                           | `sort` / `summarize` / consumer config |

`model`, `format`, and data transform operations can persist. Functions participate only at runtime and never enter IR. See [Data Model Extensions](/viz/data/model/extensions) for custom field formats and parsing, and [Data Transform Extensions](/viz/data/transform/extensions) for custom transforms, reducers, and selectors.

## Module boundary

Data produces canonical rows and their field semantics, not primitives or rendered output. Plot owns channels, scales, marks, and layout; Table owns two-dimensional structure and cell presentation. They can read the same Data result without making Data depend on either visualization module.

When rows only serve one specific chart, its host can still supply them directly at runtime. Put the work in a Data contract only when the field processing or transform semantics need independent reuse, auditing, or persistence.

In a Plot application, marks, transforms, and scales can read results by logical field name. [Plot Grammar channels](/viz/plot/channel) explain how fields or constants enter `x` / `y` / `color` / `size` / `text`; other consumers can apply their own contracts to the same canonical rows.
