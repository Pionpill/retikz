title: Extension Mechanisms
description: Define field formats, category orders, and runtime resolvers while keeping model configuration serializable.

Data-model extensions cover field parsing and category ordering. Reusable parsing rules become named formats, while one-off or source-specific rules use a runtime resolver. Neither form writes functions into serializable configuration.

## Applicability

Read [Field Types](/viz/data/model/field-types) and [Data Intake](/viz/data/model/intake) first; prefer built-in formats and ordering rules. Register a `FieldFormatDefinition` only when a storage format must be reused across data sources; use `resolveField` for parsing branches local to the current source.

| Extension entry point | Responsibility                     | Stored configuration |
| --------------------- | ---------------------------------- | -------------------- |
| `defineFieldOrder`    | Custom category comparison         | `order` name         |
| `defineFieldFormat`   | Reusable field storage formats     | `format` name        |
| `resolveField`        | Temporary type and parser override | Nothing              |

`fieldMap` only maps logical fields to physical paths; it neither parses values nor registers an extension. Measurement types remain the closed set `continuous`, `temporal`, and `categorical`. Custom parsing must normalize values into one of those domains.

## Defining Field Formats

Use `defineFieldFormat` for formats referenced by name and reused across data sources. `name` is the model lookup key, `impliedType` declares the canonical value type, and `parse` converts raw input to text, a finite number, or `undefined`.

A report may express revenue as `'1.2K'`, while calculation and plotting need the number `1200`. The example defines a format named `thousands` for the K suffix (thousands). It removes the suffix, multiplies the preceding number by `1000`, and sets the field type to `continuous`: `'1.2K' → 1200` and `'2.4K' → 2400`. Plain numbers and numeric strings without the suffix retain their numeric value.

`thousands` is a custom name registered by this example, not a built-in format. Add its definition to the format registry for this data-processing request, then reference it on the revenue field with `format: 'thousands'`. The model stores only the name; the parser remains at runtime.

Define the parser, register its name, and reference it from the model. The Data API can be used directly:

```ts
import type { IRDataModel } from '@retikz/data';
import { defineFieldFormat, resolveFormatRegistry } from '@retikz/data';

const thousands = defineFieldFormat({
  name: 'thousands',
  impliedType: 'continuous',
  parse: raw => {
    if (typeof raw === 'number') return raw;
    if (typeof raw !== 'string') return undefined;
    const text = raw.trim();
    const value = text.endsWith('K') ? Number(text.slice(0, -1)) * 1000 : Number(text);
    return Number.isFinite(value) ? value : undefined;
  },
});
const model: IRDataModel = [{ name: 'revenue', format: 'thousands' }];
const registry = resolveFormatRegistry([thousands]);
registry.get('thousands')?.parse('1.2K'); // 1200
```

## Defining Category Orders

Use `defineFieldOrder` for language-specific or business ordering. This example registers `labelLength` and selects it by default. Equal-length labels keep their appearance order. Switch to built-in rules to compare results; length ordering demonstrates a custom comparator, not version ordering.

After defining and registering a comparator, generate the category domain directly with the Data API:

```ts
import { defineFieldOrder, resolveCategoryDomain, resolveFieldOrderRegistry } from '@retikz/data';

const labelLength = defineFieldOrder({
  name: 'labelLength',
  compare: (a, b) => String(a).length - String(b).length,
});
const registry = resolveFieldOrderRegistry([labelLength]);
const domain = resolveCategoryDomain(['10.18', '2.0', '10.2', '10.2.0'], 'labelLength', registry);
// ['2.0', '10.2', '10.18', '10.2.0']
```

A definition contains `name` and `compare(a, b, context)`. Return a finite number: negative places a first, zero keeps relative order, and positive places a last. `context.values` holds deduplicated effective categories in appearance order. Comparators must be pure, antisymmetric, and transitive, without modifying values or context.

Category ordering determines the domain without reordering source rows. The model stores `order: 'labelLength'`; the runtime registry supplies the comparator.

## Runtime Field Resolution

Use `resolveField` for one-off or source-specific logic. It returns optional `type` and `parse` overrides for each logical field; returning `undefined` preserves existing results. Format registration and type compatibility are checked first, so a resolver cannot bypass an unknown format or a conflicting explicit type.

The example converts quarter labels such as `2026Q1` to quarter start timestamps. The model explicitly declares `quarter` as temporal, so the resolver only returns `parse`. Without an explicit model type, a parser override must also return `type`, even if a format or inference has already determined a type.

A runtime resolver only needs the field and raw values. This version explicitly returns a temporal type and converts quarter labels to quarter start timestamps:

```ts
import type { ResolveField } from '@retikz/data';

const resolveField: ResolveField = field =>
  field === 'quarter'
    ? {
        type: 'temporal',
        parse: raw => {
          const match = /^(\d{4})Q([1-4])$/.exec(String(raw));
          return match ? Date.UTC(Number(match[1]), (Number(match[2]) - 1) * 3, 1) : undefined;
        },
      }
    : undefined;
```

`resolveField` is a runtime escape hatch that bypasses the registry. Neither the callback nor the parser it returns can be serialized or included in IR; both remain in the consuming application’s runtime code. Use a `FieldFormatDefinition` when a stable name, cross-host reuse, or persisted configuration is required: IR stores only the format name, while the consumer still supplies the definition and its parser at runtime.

## Errors And Limits

| Condition                                                                | Result                                                                                                                  |
| ------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------- |
| Empty format name, blank order name, or duplicate/built-in name          | Registry construction fails                                                                                             |
| Unknown format or order in the model                                     | Intake fails; receiving processes must also inject the named definition                                                 |
| Format type conflicts with explicit `type`                               | Fails before the resolver runs                                                                                          |
| Resolver returns `parse` without an explicit type in the model or result | Intake fails; inference and format-implied types do not satisfy this requirement                                        |
| Parser returns an incompatible value, `undefined`, or a nonfinite number | Unusable value follows [validation policies](/viz/data/model/intake#validation-policy); default coercion is not retried |
| Order comparator throws or returns a nonfinite number                    | Throws `RetikzDataError`; callback exceptions are preserved as `cause`                                                  |

Field parsing normalizes individual values. It does not reorder rows, change row counts, or produce statistical fields; those capabilities belong to [Data Transform Extensions](/viz/data/transform/extensions).
