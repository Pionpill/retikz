A **transform** is a processing step that computes and converts input data into result data. Raw data often contains individual records, while the question we want to answer calls for group totals, representative records, or results ordered by a value. A transform organizes and computes existing data into a form suited to that question.

A transform may change field values, add or remove fields, change the number of rows, or simply reorder rows. Its result is still data: another transform can process it, or a table or chart can display it. Presentation components own appearance, such as table colors and borders.

## Overall flow

A transform fundamentally **computes and converts data content**: it receives input rows, follows specified rules to read fields, calculate values or organize records, and produces result rows. Multiple transforms can run in sequence, with each output becoming the next input.

In the example above, four detail records are grouped by `team`. Summing `value` and counting records within each group produces two summary records. A subsequent step orders them by the resulting `total`, producing the right-hand table. Grouping, summation, and counting together perform one summary transform; sorting is a separate transform that follows it.

To execute this process, the system manages both **rows** and a **field model**. Rows carry computed values; the field model describes what each stage can read and what it will produce. The implementation below describes the rules, checks inputs, and runs the computation:

- **Declaration**: serializable parameters whose `kind` identifies the operation semantics.
- **Definition**: specifies parameter structure, input fields, output model, and suboperator dependencies.
- **Implementation**: supplies the computation and binds to its definition.

Definitions let the system check the chain before computation. Implementations produce values. The diagram follows the synchronous row-data entry point.

## Declaration parsing

The registry finds the unique Definition by `kind`; its schema parses the author parameters. Unknown operations and invalid parameters fail here, with the operation position attached. Model resolution consumes these parsed declarations.

Take the second step of the example: it declares a descending sort by `total`.

```json
{ "kind": "sort", "params": { "field": "total", "order": "descending" } }
```

The system looks up the sorting definition using `kind: 'sort'`, then validates the declaration with its complete operation schema. The shared envelope contains `kind` and `params`; `SortParamsSchema` defines the sorting parameters, and `defineTransform` assembles both. `params.field` must be a nonblank string, and `params.order`, when provided, must be a valid sort direction. Both `total` and `descending` satisfy these requirements, producing a parsed sort declaration. No rows have been read or sorted yet.

An unregistered `kind` fails definition lookup. An empty `field` or an `order` such as `'sideways'` fails the definition's schema validation.

However, parsing `field: 'total'` only establishes that the field name is valid, not that the input contains it. The preceding summary produces this field, so the next phase must use the field model to check whether it is available.

## Field-model propagation

Before computation begins, this stage derives **the data structure after each operation**. A field model records field names and known types. The system reads each Definition's `outputModel` in declaration order to determine which fields later stages can use.

In the running example, the summary definition declares `team/total/count` as its output, and the sort definition preserves those fields. This produces the following structural progression before either 40 or 60 has been calculated.

<ComponentPreview files="transform-model" hideCode type="flow" size="xs" />

Each derived output model becomes the next stage's input model, so sorting can read `total`. Moving the sort earlier, or reading the removed `item` after aggregation, reveals a broken connection during model propagation. Field types travel with the model too.

This stage produces the expected field model for each step, which execution and result validation consume later. It describes the resulting structure; computation implementations produce the actual values.

## Implementation preflight

Once field models are resolved, the system must confirm **the current environment can execute the whole chain**, still before computation begins. A Definition describes semantics and output structure; an Implementation supplies the function that processes rows. Preflight matches each stage to an available implementation.

For example, the summary output contains the fields sorting needs, so the structures connect. But if the current environment lacks a sort implementation, the synchronous entry point fails before aggregation begins. No stage starts computing. Checking the entire chain prevents discovering an unavailable later step after earlier work has run.

<ComponentPreview files="transform-preflight" hideCode type="flow" size="md" />

An implementation must bind to the same Definition selected during resolution; matching `kind` alone is insufficient. Any required suboperator implementations must also be available. Only after preflight succeeds does the system call each stage's `apply` in order.

Native sources and asynchronous computations prepare through an executor: `prepare` negotiates execution capabilities for the whole chain, `bind` attaches input matching the prepared descriptor, and `execute` performs the computation. Unsupported preparation does not start computation, and a bound execution right can be consumed only once.

## Result validation

This stage happens **after an implementation returns data**. The synchronous entry point first computes the summary, producing totals of 40 for A and 60 for B. It checks the result against the previously derived output model before passing it to sorting. The sort result is validated in turn.

For example, if `total` is declared as a continuous numeric field but an implementation returns the string `"forty"`, validation fails and sorting does not run. Validation checks that the result model matches expectations and that values in fields with known types satisfy their value constraints. It does not recompute the sum to prove that 40 is correct; algorithm correctness remains the implementation's responsibility.

<ComponentPreview files="transform-result" hideCode type="flow" size="md" />

A validated result retains both canonical rows and their field model for the next stage or a display component. `applyTransformsToDataView` returns both parts; the convenience entry point `applyTransforms` returns only the row array.

A computation error or validation failure stops subsequent stages. Computation has already occurred at this point, and neither preflight nor result validation can undo external computation side effects.
