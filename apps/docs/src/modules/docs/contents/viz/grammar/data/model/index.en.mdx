A chart has two inputs: **config** (what to draw — marks / coordinate / scales) and **data** (which values). retikz keeps them apart: data does **not** enter the chart config (the IR); it is supplied separately at compile time. That lets one config be reused across different datasets.

<ComponentAlert
  title="Why data stays out of the IR"
  description="Data is usually much larger than the chart config. Embedding every row into the IR would make JSON and persisted artifacts bulky, hard to diff, and hard to maintain. Config and data are naturally separate: the IR describes how to draw, while data is supplied at compile time through the model; as long as the field contract lines up, the same config can run against another data source."
/>

The simplest form: hand a row array to `<Plot data>` and have marks reference columns by field name.

```tsx
<Plot data={rows}>
  <PathMark x="month" y="revenue" order="month" />
</Plot>
```

A field name is a **path**, so nested data (MongoDB documents, JSON from an API) works directly: `x="user.address.city"` drills to the leaf. The leaf must be a scalar (string / number / boolean / time) — not an object or array.

Field resolution first checks whether the whole field name exists as a direct key on the row, then falls back to `.` traversal. That means `user.age` can be either a nested path or a normalized logical field name. During preparation, Plot parses fields into canonical values (the standardized values after parsing and coercion) and writes them back under logical names; later transforms, scales, and marks read that result.

## Declaring field types

Declare field types through `<Plot model>`. The `model` is the field contract: whether `month` is time or a plain string, and whether `revenue` is continuous or categorical, affects scale selection, axis formatting, legend derivation, and validation. When `model` is omitted, retikz **infers field types** from data samples.

Field types and default inference:

| Type          | Meaning                       | Examples                        | Default inference and explicit declarations                                                                                                                              |
| ------------- | ----------------------------- | ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `continuous`  | continuous measurable numbers | sales, price, temperature       | Default: sample values are finite numbers or bigints<br />Declare: numeric strings, numeric enums, ids, or status codes should behave as continuous values or categories |
| `temporal`    | date / time values            | dates, timestamps               | Default: `Date` or unambiguous ISO date / datetime strings<br />Declare: non-default date formats or timezone-less times                                                 |
| `categorical` | discrete categories           | countries, color names, ratings | Default: other strings, booleans, mixed values, or unknown fields<br />Declare: category order, axes, or legends need fixed ordering                                     |

Customize `model` when you need to override inference, parse non-default storage formats, or make the config self-describing without the data. Each field declaration can contain:

| Field    | Purpose                                                                                                       |
| -------- | ------------------------------------------------------------------------------------------------------------- |
| `name`   | logical field name, also the name referenced by marks / transforms                                            |
| `type`   | measurement type; omitted fields are inferred from data                                                       |
| `format` | declarative parsing format, such as `slashDate` / `percent`; see [Processing](/viz/grammar/data/processing) |
| `order`  | category order for categorical fields                                                                         |

**Declaring a model = strict mode**: every data field referenced by a mark / transform must be listed in the model; a misspelled field name **fails immediately** instead of drawing an empty chart. References include not only `x` / `y` / `z`, but also `color`, `series`, a mark's `order`, point `size` / `opacity` / `shape`, and transform input fields. Field names inside one model must be unique; duplicate declarations also throw.

With no `model`, field types follow the default inference rules above, which is handy for quick drafts.

**`type` is optional — partial models**: a field's type can be omitted, leaving just `{ name }`. The field still joins strict mode and keeps a portable field contract; only its type is left to inference. This is useful when most fields are obvious and only a few need pinning: give `type` to numeric enums, use `format` for non-default dates / percentages, and leave the rest bare.

```tsx
<Plot
  data={sales}
  model={[
    { name: 'createdAt', format: 'slashDate' }, // '2024/01/01' → temporal
    { name: 'statusCode', type: 'categorical' }, // numeric enum pinned as category
    { name: 'revenue' }, // name only → inferred continuous
  ]}
>
  {/* … */}
</Plot>
```

Fields with `type` omitted need the data at lowering to determine their type. Fields with `format` get their type from the format, so `format: 'percent'` is treated as `continuous`. To keep a spec fully self-describing without the data (LLM-friendly / fully portable), fill in `type` or `format`.

<ComponentAlert
  title="Inference is best-effort; the model is the contract"
  description="Without a model (or with a field's type / format omitted), types are guessed from samples: time is only recognized in unambiguous ISO form (YYYY-MM-DD, an ISO datetime with a timezone, including the space-separated SQL form like '2024-01-01 12:00:00Z') — '2024/01/01' and timezone-less times are not treated as time; bare numeric strings are not inferred as continuous either. ## Type-driven scales

Once field types are declared, positional channels (x / y, and ternary x / y / z) **no longer need an explicit scale**: retikz picks one from the field type, `continuous` → linear, `temporal` → time axis, `categorical` → band. Color channels follow the same field types: continuous / temporal fields derive continuous color ramps, while categorical fields derive discrete color. See [Scales](/viz/grammar/scale) for the full mapping and override rules.

The three charts below declare no scale config at all: `continuous` fields derive linear axes, `temporal` fields derive time axes, and `categorical` fields derive band axes.

## Category order: `order`

A `categorical` field orders its categories by **data appearance** by default; axes and legends follow that order. To control it — sizes should read `S → M → L → XL`, not whatever order they happen to appear in the data — give the field an `order`:

The two charts below use the same size data. The left chart follows data appearance order; the right chart fixes the business order `S → M → L → XL`.

<ComponentPreview name="data-model-order" sourceFiles={['data-model-order.data.ts']} />

This `order` sorts the **category domain**: axis ticks, legends, and categorical colors follow it. It does not reorder data rows or change the connection order of a line. To reorder rows, use [row sort](/viz/grammar/transform/row#sort).

| `order`                        | Effect                                                                                                   |
| ------------------------------ | -------------------------------------------------------------------------------------------------------- |
| omitted / `'data'`             | data appearance order (default)                                                                          |
| `'ascending'` / `'descending'` | sort the categories: numeric when all numbers, else as strings                                           |
| `Array` (e.g. `['S','M','L']`) | the array is the order; categories present in the data but absent from the array are appended at the end |

Rules:

- **It lives on the field, so position and color share the order**: when the same field drives both the x-axis (band) and color (ordinal), both use the same category order.
- **Only valid on `categorical`**: an `order` on a `continuous` / `temporal` field **throws** (order is meaningless for continuous values / time).
- **An explicit scale `domain` wins**: if the scale declares its own `domain`, that takes precedence and `order` is ignored.
- A **non-default** `order` (a sort or an explicit array) marks the field as ordered — retikz's three field types have no dedicated "ordered category" type; orderedness is expressed through this parameter.

## How It Works

`model` stores the field contract, not the data rows. Before lowering, Plot **collects, validates, and types** the fields actually referenced by the config, assembling one set of field metadata shared by scales, axes, legends, and validation.

<ComponentPreview name="data-model-pipeline" size="sm" hideCode />

Type resolution follows the priority "explicit `type` > type implied by `format` > inference from data", and a `categorical` field's `order` is stored alongside. Real rows are still supplied at compile time and never written into IR — that is what keeps one config reusable across data sources.

### Automatic field-type inference

When a field has neither `type` nor `format`, retikz infers it from data samples in two steps.

**Step 1, classify each value**: scan the field's sample values; each value is classified on its own first.

| Sample value                                             | Classified as                    |
| -------------------------------------------------------- | -------------------------------- |
| `Date` instance                                          | `temporal`                       |
| ISO date / datetime string                               | `temporal`                       |
| Finite `number`, `bigint`                                | `continuous`                     |
| Other strings, booleans                                  | `categorical`                    |
| `null` / `undefined`, `NaN` / `Infinity`, object / array | Skipped, not counted as a sample |

ISO only accepts unambiguous formats: `YYYY-MM-DD`, and a datetime with a timezone (`T` or space separated, and a required `Z` or `±HH:MM`, e.g. `2024-01-01 12:00:00Z`). `2024/01/01`, timezone-less times, and bare number strings do not count.

**Step 2, classify the whole field**: scan at most the first 1000 rows, take up to 100 valid samples, then resolve the field type from them.

- **Every** sample is temporal → field is `temporal`
- **Every** sample is continuous → field is `continuous`
- Otherwise (mixed types, all categorical, or no valid samples) → `categorical`

In other words: a single non-time, non-numeric value drops the whole field back to `categorical`; an empty field, or one with only empty values, also defaults to `categorical`. A field declared in `model` uses its `type` first, then a type implied by `format`, and only then this inference.

### Deriving scales from types

Once a field type is resolved, channels that **omit scale configuration** derive a default scale from it.

**Position channels** (x / y / z, when the coordinate system gives no explicit scale for that channel):

| Field type                                    | Derived scale       |
| --------------------------------------------- | ------------------- |
| `continuous`                                  | `linear`            |
| `temporal`                                    | `time`              |
| `categorical`                                 | `band`              |
| No bound field (e.g. an all-constant channel) | `linear` (fallback) |

The fields bound to one position channel must share a single type; omitting the scale while mixing types throws and asks for an explicit scale. If a field has a non-default `order` and derives `band` / `point`, the category domain follows that `order`.

**Color channel**: a categorical field synthesizes `ordinal` (discrete, one color per category) when no scale is given; a continuous / temporal field is not auto-derived — it must explicitly reference a `sequential` / `diverging` / `quantize` / `threshold` / `quantile` color scale, and applies only to per-datum marks (point / bar / sector), erroring on line / area. See [Scales](/viz/grammar/scale) for the full color derivation and schemes.
