Beyond the built-in marks, define your own glyph with `defineMark`. It follows the same runtime-definition paradigm as `defineCoordinate` and `defineScale`: the spec still stores only a JSON operation, such as `{ type: 'diamond', encoding: { x: { field: 'month' }, y: { field: 'sales' } } }`; the field collection and lowering function live in a runtime definition injected through `<Plot markDefinitions={[...]}>`.

A custom mark's `type` is any non-built-in discriminator; its `encoding` reuses the same channel shape as built-in marks. Common coordinates use `x` / `y` / `color`, and custom coordinates may declare their own position roles. Position channels feed scale inference, so the custom mark shares the same coordinate system and scales as built-in marks.

Custom marks can also put `transform` on the operation. That mark-local pipeline runs after the plot-level transform, and `lower(mark, rows, ...)` receives the rows for this mark after its own transform; the custom definition does not need to call `applyTransforms` again.

When an authoring shortcut needs to prepare data automatically, do not hide that data change inside `lower`. The React DSL can use `markTransformShortcuts` to expand higher-level syntax into ordinary transforms; `<Transform>`, `dataTransforms`, mark-local `transform`, and those shortcuts all feed the same transform pipeline. The mark definition only consumes prepared rows.

## Diamond glyph

The `diamond` mark below projects each row into a diamond. It is registered in `markDefinitions`; a custom mark has **no dedicated React component**, so it is authored via the `<Plot spec={...}>` entry — write `{ type: 'diamond', ... }` directly in the `marks` array.

The third argument to `lower` is the coordinate `frame`. It projects each row's `x` / `y` through `frame.projectRoles` into a screen point, then assembles a core `Node` (`shape: 'diamond'`). The `frame` hides cartesian / polar differences: the mark just asks for a projected point; how the coordinate system interprets `x` / `y` is decided by the coordinate layer.

## Definition contract

| Field           | Required | Purpose                                                                                                                                           |
| --------------- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| `schema`        | required | Complete operation schema; `type` must be a non-empty `z.literal(...)`, whose value is the registry key and must not collide with a built-in mark |
| `lower`         | required | Receives the schema-parsed mark, data rows, `frame`, and channel resolvers, then lowers to core IR; returns `null` when nothing is drawable       |
| `collectFields` | optional | Receives the same schema contract and registers source fields so strict model validation does not flag them as missing                            |
| `buildCell`     | optional | Per-row cell builder for interval-like marks (built-in `interval` uses this; plain glyphs do not)                                                 |

Use `defineMark<MyMark>` with the operation type inferred from your schema, so `lower` / `collectFields` receive the precise mark shape. Lowering first checks that the operation is a JSON object, then parses it through the definition schema, so invalid config never reaches behavior callbacks.

## Three-layer boundary

A mark spans three layers, with the same boundary as built-in marks:

| Layer     | Holds                                                                                               | In IR | Responsibility                                                 |
| --------- | --------------------------------------------------------------------------------------------------- | ----- | -------------------------------------------------------------- |
| schema    | `type`, `encoding`, `transform`, and other serializable fields                                      | yes   | validation, persistence, AI generation, cross-runtime transfer |
| authoring | built-in via React components; custom via the spec entry; shortcuts expand into ordinary transforms | no    | assemble user input into JSON-safe mark IR and transforms      |
| registry  | `lower(mark, rows, frame, channels)` behavior                                                       | no    | lower into core IR at compile time                             |

Built-in and custom marks dispatch through the same `resolveMarkRegistry`: built-in marks go through the strict discriminated union, custom marks through `type` passthrough, and lowering uses the mark definition contract to separate built-in-specific geometry, relation targets, and generic position channels.
