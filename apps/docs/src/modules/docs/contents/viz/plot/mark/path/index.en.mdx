title: PathMark
description: Connect data positions in order with PathMark to draw lines, multiple series, polar outlines, and closed regions.
---

`PathMark` connects the positions of multiple data rows into paths. `x` and `y` locate each point, `order` determines the connection order, and `series` separates independent paths. The same mark can draw a line, radar outline, or closed region.

Start with one line, then explore grouping, curves, closure, and missing values. See [channel bindings](/viz/plot/channel/binding) for field bindings and [Quick start](/viz/plot/get-start) for installation and host setup.

## Using this topic

The example connects three revenue records by month. With `order="month"`, rearranging the input rows preserves the monthly connection order.

## Basic usage

### Position

#### Vertex positions and order

`encodings.position` specifies each vertex position, and `encodings.order` selects the connection order. Bind x to month, y to revenue, and order to month to connect revenue values chronologically. Without order, PathMark follows the input row order.

The example deliberately shuffles the rows. Switch connection order to compare a path that doubles back with monthly ordering. In polar coordinates, x represents angle and y represents radius.

| Property             | Purpose           | Notes                                                                                                 |
| -------------------- | ----------------- | ----------------------------------------------------------------------------------------------------- |
| `encodings.position` | Vertex positions  | Each role accepts a field, constant, or range edge; x/y represent horizontal/vertical or angle/radius |
| `order`              | Connection order  | Sort by this field before connecting; omit to preserve data array order                               |
| `Plot.coordinate`    | Coordinate system | Determines position semantics; the example switches between `cartesian2D` and `polar2D`               |

### Series and labels

When rows contain several stores, bind `series` to the store field so each store sorts and connects independently. Bind `color` to a categorical field to distinguish colors. Without `series`, that color field also splits paths; without `color`, color follows `series`.

`label` places labels along path geometry. Compare a single path, explicit series, and color-based grouping, then toggle series labels.

| Property       | Purpose           | Notes                                                                                               |
| -------------- | ----------------- | --------------------------------------------------------------------------------------------------- |
| `series`       | Series field      | Split independent paths by field value and sort within each series                                  |
| `color`        | Categorical color | Color by category; also splits paths when `series` is absent, and defaults to `series` when omitted |
| `label`        | Path labels       | One or more labels placed along path geometry                                                       |
| `resolveLabel` | Label callback    | Generate text at runtime; requires a mark `id` and is not stored in IR                              |

Label position uses a fraction from `0` to `1` along the path. With Side set to Auto, a horizontal label sits above the path; enabling Follow path tangent centers it along the tangent. Toggle Interrupt path in that state to see a gap beneath the text. Interruption cuts the stroke, not the text. An explicit side and offset distance move the label beside the path.

### Connection and style

`curve` chooses how neighboring points connect. Straight and step lines emphasize changes between observations; smooth curves change the route between points. Not every curve passes through every observation. The gray points are references for comparing the curve with its input positions.

Stroke color, width, dashes, and opacity control appearance. In polar coordinates, `monotoneX` and `monotoneY` use `linear`.

| Property              | Purpose               | Notes                                                                                                              |
| --------------------- | --------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `curve`               | Connection shape      | Defaults to `linear`; choose step or smooth curves. Polar coordinates use `linear` for `monotoneX` and `monotoneY` |
| `dashOffset`          | Dash offset           | Finite positive or negative offset; combines with `dashPattern` and supports fixed properties or field encodings   |
| `lineCap`, `lineJoin` | Stroke caps and joins | Caps: butt / round / square; joins: miter / round / bevel; fixed properties or field encodings                     |
| `stroke`              | Stroke color          | Field or constant; use `{ kind: 'constant', value }` to force a constant                                           |
| `strokeWidth`         | Stroke width          | Nonnegative constant or field mapping                                                                              |
| `dashPattern`         | Dash pattern          | Array alternating dash and gap lengths; the example dash switch controls this property                             |
| `opacity`             | Opacity               | Control overall, fill, or stroke opacity                                                                           |
| `closed`              | Endpoint connection   | Connect the last point to the first; does not select the curve between points                                      |

Fixed `fill` and `stroke` accept CSS colors, structured Paint, or a master color weight from 0 to 1 (`0` is valid). Fixed `opacity: 0.6` is equivalent to `{ overall: 0.6 }`. `encodings.opacity` still binds `overall`, `fill`, and `stroke` separately and overrides only the matching fixed factor.

## Extended usage

### Closure and fill

`closed` connects the last point to the first. Cartesian paths default to open, while polar paths default to closed. Use `closure` to specify a region boundary and `fill` to give the region a fill color.

| Closure           | Configuration                                         | Result                                  |
| ----------------- | ----------------------------------------------------- | --------------------------------------- |
| Cycle             | `closure={{ kind: 'cycle' }}`                         | Return from the last point to the first |
| Constant baseline | `closure={{ kind: 'baseline', baseline: 0 }}`         | Return along a fixed value              |
| Per-row baseline  | `closure={{ kind: 'stack', baselineField: 'lower' }}` | Read the lower boundary from each row   |

Compare open paths, cycle closure, and a constant baseline below. If `baseline` is omitted, it uses 0 when the value domain includes 0, otherwise the domain edge nearest 0.

| Property                | Purpose                | Notes                                                                                                    |
| ----------------------- | ---------------------- | -------------------------------------------------------------------------------------------------------- |
| `closed`                | Endpoint connection    | Defaults to `false` in Cartesian coordinates and `true` in polar coordinates                             |
| `closure`               | Return boundary        | `cycle` returns to the first point, `baseline` to a fixed baseline, and `stack` along a per-row baseline |
| `closure.baseline`      | Fixed baseline value   | Only used by `baseline`; defaults to 0 or the domain edge nearest 0                                      |
| `closure.baselineField` | Per-row baseline field | Required for `stack`; names the lower-boundary field in each row                                         |
| `fill`                  | Region fill            | Color or Paint for the closed region; `none` hides the fill                                              |

### Missing values

A row that cannot project to a valid position breaks the path by default. For an open, unfilled path, `connectNulls` bridges valid points on either side of a gap with a dashed stroke while leaving ordinary segments unchanged.

Both `connectNulls={true}` and `connectNulls={{}}` use the default dash pattern `[6, 4]`. An object can override the bridge stroke. Consecutive missing rows produce one bridge; leading and trailing gaps do not extend the path.

Closed paths, paths with `closure`, and filled paths accept only a boolean. Here, `true` joins valid points into one run without a separate dashed bridge. The fill switch below adds a baseline-closed layer: the area joins valid positions as a whole, while the original open stroke still marks gaps with dashed bridges.

| Property                     | Purpose               | Notes                                                                                                                                       |
| ---------------------------- | --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `connectNulls`               | Gap connection        | Defaults to `false`. For open unfilled paths, `true` or `{}` bridges gaps with the default dash pattern `[6, 4]`                            |
| `connectNulls` stroke object | Bridge style          | Accepts `stroke`, `strokeWidth`, `strokeOpacity`, `dashPattern`, `dashOffset`, `lineCap`, and `lineJoin`; only for open unfilled paths      |
| `closed`, `closure`, `fill`  | Connection conditions | Closed paths, paths with closure, or filled paths accept only boolean `connectNulls`, joining valid points without separate bridge segments |

### Polar interpolation

Polar coordinates map x to angle and y to radius. Even with the same endpoints, two connections can follow different routes:

The coordinate system defaults to `polar` for a continuous angular scale and `chord` for a discrete one. PathMark can override `interpolation` for its own path; the grid still uses the coordinate setting. The two plots below explicitly choose different coordinate interpolation, so their paths and grids change together.

| Property                        | Purpose                  | Notes                                                                                                                                                               |
| ------------------------------- | ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Plot.coordinate.interpolation` | Coordinate interpolation | `chord` joins projected points; `polar` samples angles and radii before projection. Defaults to `polar` for continuous angular scales and `chord` for discrete ones |
| `interpolation`                 | Path override            | Only valid in `polar2D`; inherits the coordinate setting when omitted, otherwise affects only this path                                                             |
| `closed`                        | Endpoint connection      | Connect the last point to the first, independently of interpolation                                                                                                 |

## Errors and limitations

- Built-in Cartesian 2D and polar 2D coordinates support paths and closed regions. Generic coordinate frames support open paths with no `closure` and `closed` other than `true`.
- Explicit `interpolation` is only valid in polar coordinates. Other coordinate systems reject it.
- `color` requires a categorical field; continuous and temporal fields are rejected.
- Closed or filled paths reject stroke objects in `connectNulls`; use a boolean.
- A path segment needs at least two valid positions. Use [PointMark](/viz/plot/mark/point) for isolated points.
- The runtime callback `resolveLabel` requires a mark `id` and is not stored in Source IR.

### Resolving a path

Points, paths, and intervals relate to the coordinate system through the geometry they represent:

- **A point mark represents a position**: the coordinate system places the point, while its circle, rectangle, or text keeps its own shape without bending under the coordinate mapping. Orientation alignment can additionally use coordinate directions to rotate the node.
- **A path mark represents a line**: the coordinate system can determine both the positions and the route between them. In continuous polar coordinates, `polar` interpolation between two positions with the same radius and different angles follows the circle through intermediate angles. With `chord` interpolation, the projected endpoints are connected directly by a chord.
- **An interval mark represents an area**: the coordinate system affects the boundary and shape of the whole region. A rectangular interval in Cartesian coordinates can become a sector or annular sector in polar coordinates. Both interval and path marks map geometry into coordinate space: a path describes the course of a line, while an interval describes the extent of an area. A path can also be closed and filled, but its boundary still comes from the connection route.

A path mark therefore needs the connections between several positions. Series grouping, sorting, and missing-value segmentation determine where each path starts, which positions it visits, and where it ends. Once the coordinate system and interpolation strategy determine the route, PathMark converts it into steps for the underlying [Path](/kernel/components/path/step), which handles compilation and rendering.

Follow the same ordered positions through three stages: Cartesian coordinates appear above, continuous polar coordinates below. Orange dots and numbers identify original data positions, gray dotted lines help locate them, and blue lines show the connection route. Small gray dots in stages 2 and 3 represent samples inserted between original data positions.

1. **Position**: group by `series` or implicit color, then sort each group by `order`, preserving row order when no sorting field is set. Check whether positions can project, then use `connectNulls` to break, bridge, or skip missing values; baseline closure also requires valid lower bounds. Scales and coordinates determine each valid data vertex's screen position.
2. **Draw**: Cartesian and `chord` interpolation use projected points directly; the upper row connects them with straight segments. This sample count does not represent the actual sampling density; the next section explains sampling in detail.
3. **Handle details**: create underlying Paths for continuous runs and gap bridges, apply strokes and path labels, then compile to a Scene for SVG or Canvas. The figure shows a thicker stroke, round caps and joins, and a sloped label. These details do not move the original data vertices. ### Path sampling

In polar coordinates, projecting two data positions and connecting them directly produces a straight line. To follow changes in angle and radius, the path first adds intermediate positions and then projects each one.

Consider two positions whose scale outputs are “0°, radius 100” and “90°, radius 100”. With `polar` interpolation, path generation proceeds as follows:

1. **Read angle and radius**: apply the scales to obtain each endpoint's angle and drawing radius. Sampling operates on these mapped values.
2. **Add intermediate positions**: divide the segment evenly and interpolate angle and radius linearly at each subdivision. Here the radius stays at 100 while the angle increases from 0° to 90°. When endpoint radii differ, the radius changes as well.
3. **Project into drawing space**: convert each intermediate position to screen coordinates. In this example, all points lie on the same quarter circle.
4. **Connect the samples**: the default `curve="linear"` approximates the arc with short straight segments. Other `curve` settings generate steps using their respective connection algorithms. Polar sampling and smoothing through points are therefore two successive stages.

The straight-connection branch needs no intermediate coordinate samples: Cartesian coordinates and polar `chord` interpolation project the original positions directly, producing straight segments when `curve="linear"`. Categorical angle scales default to chord connections; continuous angle scales default to polar sampling. For closed paths, polar sampling also covers the segment from the last position back to the first.

The following figure compares a direct chord with sampled connections between the same endpoints:

<ComponentPreview files="path-sampling" hideCode type="illustration" size="lg" />

Orange dots are the original endpoints, blue dots are added samples, and the gray dotted line is the reference arc. The right panel uses few samples to make the short straight segments visible; this illustrative count does not represent the runtime sample count.

The current `polar` branch uses a fixed sample count. It does not detect straight segments individually or adapt sample density to curvature. For example, endpoints with the same angle and different radii form a radial straight line, but this branch still generates intermediate samples.

The default polar connection depends on what the angle axis represents:

- **Discrete angles default to straight connections**: each angle represents a separate category, such as “speed, strength, endurance” in a radar chart. There is no intermediate category to interpolate between adjacent categories. Connecting the projected data positions directly emphasizes their values and comparisons, producing the familiar polygonal radar outline.
- **Continuous angles default to sampled connections**: intermediate positions on the angle axis are meaningful. For example, angles vary continuously between 0° and 90°. Interpolating angle and radius before projection follows that angular progression; two positions with the same radius follow the circle instead of taking a straight shortcut.

These are defaults chosen from the angle scale, not restrictions imposed by the coordinate system. Set `interpolation` explicitly to choose `chord` or `polar`. The `curve` option still determines how the resulting samples are connected.

## API Reference

Use `encodings.label: 'name'` for a content field or `properties.label: 'Highlight'` for fixed text. Object labels support field bindings for `font.size`, `font.weight`, `textColor` and other targets. Label arrays match by index; unencoded font leaves retain inheritance. See [label encodings](/viz/plot/reference/encoding#labelencodingschema).

`PathMarkProps` is exported by `@retikz/plot-react` and reuses `InputPlotPathMark` from `@retikz/plot-vanilla`. Members are grouped by purpose. `—` means the declaration has no field-level default; runtime defaults are explained above.
