title: Custom Channels
description: Register new channel definitions through channelDefinitions, so custom channels share the same resolving, registry, and delivery path as built-ins.
---

Common channels (`size`, `opacity`, `shape`, `strokeWidth`, `lineCap`, and related styles) have named props. To add your own channel, declare a runtime definition with `defineScopeChannel`, `defineNodeChannel`, `definePathChannel`, or `defineChannel`, then register it through `<Plot channelDefinitions={...}>`.

In the React DSL, custom channel bindings live on the mark's `channels` prop, for example `<PointMark channels={{ intensity: 'score' }} />`. This assembles to `encoding.channels.intensity = { field: 'score' }` in the PlotSpec; the PlotSpec still stores only field / constant bindings, not the runtime definition.

The demo below defines `intensity`: it reads the `score` field, maps values into `[0.3, 1]`, then delivers the result to core `IRNode.opacity`. The definition does not check `mark.type`; whether a mark consumes Node / Path / Scope channels belongs to the mark definition.

The definition is runtime capability. Built-in and custom channels are merged into one registry, then routed by definition kind into the position / mark / scope / node / path consumption path.

A channel definition should not check `mark.type` to decide which marks may use it. It only answers whether the binding exists, how to resolve the value, and how to deliver that value to a core property. Whether a mark consumes node / path / scope channels belongs to the mark definition, so custom marks can reuse the same channel path.

A custom channel cannot override a built-in channel name, and binding an unregistered channel fails during lowering. String values in the `channels` prop are treated as field names; for string constants, write `{ value: 'literal' }` or `{ kind: 'constant', value: 'literal' }`. JSON constants are also allowed, so `channels={{ badge: { kind: 'constant', value: { preset: 'warn' } } }}` can feed an object-valued custom channel.

## Contract Boundaries

| Rule                                                               | Reason                                                                                             |
| ------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------- |
| `channel` cannot collide with built-in channel names               | Built-in and custom channels share one registry, so names must not override each other             |
| `resolve` only builds per-row resolvers                            | Rendered values, legend descriptors, and rows stay in sync                                         |
| `deliver` only writes existing core scope / node / path properties | New rendering capability should be added to core first instead of bypassing the foundation in plot |
| Definitions do not enter IR                                        | Functions are not serializable; IR stores only field / constant bindings                           |

If you are extending field parsing or named formats, return to [Data Model](/viz/data/model). If you are extending how values map to colors or radii, start with [Custom Scales](/viz/plot/extend/scale).
