`@retikz/plot` is the chart-semantics layer in the Viz group. It uses serializable Plot IR to describe field bindings, scales, coordinates, marks, guides, and composition, then lowers those high-level semantics into Core IR that Kernel can compile.

Plot does not own the data foundation or renderers. [Data](/viz/data) owns field models and general data processing, Kernel owns compilation, layout, and Scene, and SVG / Canvas renderers consume only Scene. React, Vanilla, handwritten specs, and AI-generated configurations therefore share one semantic contract and one lowering path.

## From declaration to Scene

1. **Build Plot IR**: `<Plot>` children, the Vanilla builder, and a plain spec all produce the same JSON-safe `IRPlotSpec`. The React DSL is an authoring entry, not a separate chart model.
2. **Attach external data**: IR points to runtime datasets through `data.reference`. Data owns field parsing, general transforms, and provenance; dataset rows do not enter the IR.
3. **Resolve chart semantics**: lowering applies data transforms, channel bindings, scales, and coordinate projection before mark and guide definitions produce lowerable results. Built-in and custom capabilities share the same registry, resolver, and consumer path.
4. **Lower to Core IR**: `lowerPlots` is a Tier 2 composite definition that expands Plot nodes into Core IR such as `Scope`, `Node`, and `Path`. Lineage, locators, and diagnostics remain separate runtime results.
5. **Compile and render**: Kernel compiles Core IR into a renderer-agnostic Scene, then an SVG or Canvas renderer emits output. Plot neither bypasses Scene nor implements a parallel renderer.

## How the three packages split responsibility

| Package                | Owns                                                    | Typical entries                               |
| ---------------------- | ------------------------------------------------------- | --------------------------------------------- |
| `@retikz/plot`         | Plot IR, definitions / registries, resolution, lowering | `PlotSpecSchema`, `lowerPlots`                |
| `@retikz/plot-react`   | React authoring and runtime wiring                      | `<Plot>`, `buildPlotSpec`                     |
| `@retikz/plot-vanilla` | Framework-free / SSR spec construction and wiring       | `plotBuilder(...).build()`, `renderPlot(...)` |

All three packages share the IR and lowering source of truth in `@retikz/plot`. Adapters may add framework-appropriate authoring sugar, but they must not duplicate or alter scale, coordinate, mark, or guide semantics.

## What Plot owns—and what it does not

| Plot owns                                           | Owned elsewhere                                                                                       |
| --------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| Plot IR and graphic-grammar contracts               | Field models, parsing, general transforms, and provenance belong to [Data](/viz/data)                 |
| Channels, scales, coordinates, marks, and guides    | Core IR, layout, reference resolution, and Scene compilation belong to [Kernel](/kernel/introduction) |
| Composition and Plot-to-Core lowering               | SVG / Canvas output belongs to renderers                                                              |
| Definitions, registries, resolvers, and diagnostics | React / Vanilla lifecycles and host wiring belong to adapters                                         |
| Chart-oriented semantic mapping                     | Row / column structure, Cell semantics, and table layout belong to [Table](/viz/table)                |

If a capability does not depend on chart field mapping—general data transforms, low-level geometry, or table Cells, for example—it should not enter Plot. Conversely, a new scale, coordinate, mark, or guide should first become a registerable Definition, then use the same path as built-ins.
