`@retikz/plot` is the chart-semantics layer in the Viz group. It uses serializable Plot IR to describe field bindings, scales, coordinates, marks, guides, and composition, then lowers those high-level semantics into Core IR that Kernel can compile.

Plot does not own the data foundation or renderers. [Data](/viz/data) owns field models and general data processing, Kernel owns compilation, layout, and Scene, and SVG / Canvas renderers consume only Scene. React, Vanilla, handwritten specs, and AI-generated configurations therefore share one semantic contract and one lowering path.

## From declaration to Scene

1. **Build Plot IR**: `<Plot>` children, Vanilla `plot()`, and a complete `InputPlot` all produce the same JSON-safe `IRPlot`. `InputPlot` is the TypeScript authoring input owned by `@retikz/plot-vanilla`; React DSL is only a bridge, not a separate chart model.
2. **Attach external data**: IR points to runtime datasets through `data.reference`. Data owns field parsing, general transforms, and provenance; dataset rows do not enter the IR.
3. **Resolve chart semantics**: lowering applies data transforms, channel bindings, scales, and coordinate projection before mark and guide definitions produce lowerable results. Built-in and custom capabilities share the same registry, resolver, and consumer path.
4. **Lower to Core IR**: `lowerPlots` is a Tier 2 composite definition that expands Plot nodes into Core IR such as `Scope`, `Node`, and `Path`. Lineage, locators, and diagnostics remain separate runtime results.
5. **Compile and render**: Kernel compiles Core IR into a renderer-agnostic Scene, then an SVG or Canvas renderer emits output. Plot neither bypasses Scene nor implements a parallel renderer.

## How the three packages split responsibility

| Package                | Owns                                                                          | Typical entries                                            |
| ---------------------- | ----------------------------------------------------------------------------- | ---------------------------------------------------------- |
| `@retikz/plot`         | `IRPlot*` schema, definitions / registries, domain resolution, lowering       | `PlotSchema`, `lowerPlots`                                 |
| `@retikz/plot-react`   | React `XxxProps` / children collection and React host wiring                  | `<Plot>`                                                   |
| `@retikz/plot-vanilla` | `InputPlot*` types, normalization, InputEmbed wiring, SSR, DOM-free rendering | `plot()`, `normalizePlot()`, `embedPlot()`, `renderPlot()` |

All three packages share the IR and lowering source of truth in `@retikz/plot`. `@retikz/plot-vanilla` is the framework-neutral authoring owner: it owns the TypeScript-only `InputPlot*`, `PlotSource`, and `InputPlotEmbed` contracts and expands `facets`, `scaffolds`, and axis / topology bindings from `InputPlot` into `IRPlot`, without schema-parsing typed input again. Only `IRPlot*` values are persisted schema types; unknown external data must still enter IR through a Plot schema or parser.

React only collects JSX / props and dispatches Plot Vanilla; it owns no parallel Plot IR builder, schema parse, or lowering. If you already have a complete `IRPlot`, pass it directly to the runtime without wrapping it in another authoring helper.

## React hosting and embedding

`<Plot>` is already a complete standalone entry. Rendering it directly creates one internal `Layout`, so callers do not add another host. Inside an existing `<Layout>`, the same component degrades to one Plot Scope/composite: it shares the outer Scene, renderer, and effective Theme and does not create a nested SVG.

Plot `width` / `height` and panel fields such as `x` / `y`, transforms, and clip remain valid embedded inputs. `className`, `style`, `renderer`, and Core `themeStyles` control only the standalone host and belong on the outer `<Layout>`; `lineage`, `hostLineageMetadata`, and `onLineage` depend on the standalone React lifecycle and must be omitted when embedded. An embedded Plot fails loudly when it owns any of those fields—even an explicit `undefined`. This keeps host or observer configuration from being ignored and does not generate an extra model id for an embedded Plot.

## What Plot owns—and what it does not

| Plot owns                                                   | Owned elsewhere                                                                                       |
| ----------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| Plot IR, domain theme tokens, and graphic-grammar contracts | Field models, parsing, general transforms, and provenance belong to [Data](/viz/data)                 |
| Channels, scales, coordinates, marks, and guides            | Core IR, layout, reference resolution, and Scene compilation belong to [Kernel](/kernel/introduction) |
| Composition and Plot-to-Core lowering                       | SVG / Canvas output belongs to renderers                                                              |
| Definitions, registries, resolvers, and diagnostics         | React / Vanilla lifecycles and host wiring belong to adapters                                         |
| Chart-oriented semantic mapping and theme lowering          | Row / column structure, Cell semantics, and table layout belong to [Table](/viz/table)                |

If a capability does not depend on chart field mapping—general data transforms, low-level geometry, or table Cells, for example—it should not enter Plot. Conversely, a new scale, coordinate, mark, or guide should first become a registerable Definition, then use the same path as built-ins.

Plot also owns canonical theme tokens for its Plot area, guides, and palettes. It consumes the Core effective Theme to select the same-named domain preset, then maps local `plotThemeTokens`, Axis `plotThemeTokenRules`, and native `plotTheme` into the same lowering path. Built-in and custom presets use the same `definePlotThemeStyle` / `plotThemeStyles` resolver. See the [theme contract](/viz/plot/reference/theme) for the complete key set and precedence.
