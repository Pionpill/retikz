title: RelationMark
description: RelationMark lowers source / target relationships from data rows into core Paths, using kind to distinguish stroked paths from ribbon bands.
---

`<RelationMark>` draws relationships between two targets. A target can be an existing core id, a stable id generated by `PointMark` / `IntervalMark` / `PathMark` through `anchorId`, or a coordinate projected from the current relation row.

It is not the older group / stack / dodge data-composition relation from early design notes. This relation is a drawable source-target mark: each relation row lowers to one core `Path`; the default is a stroked path, while `kind="ribbon"` emits a Path with `kind: 'ribbon'`.

## Usage

```tsx
import { Plot, PointMark, RelationMark } from '@retikz/plot-react';
```

```tsx
<Plot data={edges}>
  <PointMark x="sourceX" y="sourceY" anchorId={{ prefix: 'node', field: 'sourceId' }} />
  <PointMark x="targetX" y="targetY" anchorId={{ prefix: 'node', field: 'targetId' }} />
  <RelationMark
    source={{ anchorId: { prefix: 'node', field: 'sourceId' } }}
    target={{ anchorId: { prefix: 'node', field: 'targetId' } }}
    path={{ options: { marks: [{ pos: 1, mark: { kind: 'arrow' } }] } }}
  />
</Plot>
```

`RelationMark` is usually paired with positional marks that define `anchorId`. The positional mark projects rows into core `Node` / `Coordinate` elements and gives them stable ids. The relation mark uses the same rule shape on its own rows to compute source / target ids, then lowers to a core `Path`. When the edge rows do not already exist, `transform` can derive relation rows locally for this mark.

## Presentation Layer

RelationMark is the low-level relationship path mark. It does not reinvent arrows, labels, or routed lines; it turns relationship data into a core `Path.children` step sequence. Dependency lines, flow lines, reference lines, and labeled connectors are all different configurations of the same source-target path.

| Presentation            | Key props                           | Notes                                                                                                       |
| ----------------------- | ----------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| Point-to-point relation | `source` / `target`                 | Reference existing nodes by id or generated anchor rules, then connect with the default `move -> line` path |
| Waypoint path           | `path.via` / `path.route[].to`      | Projected waypoints generate core `Coordinate` elements, so later ids can reference them                    |
| Geometry label          | `label`                             | Lowers to core `Path.label`; path and ribbon relations share the same host label                            |
| Step label              | `path.label` / `path.route[].label` | Lowers to core step label; explicit step labels win over shorthand                                          |
| Core Path capabilities  | `path.options`                      | Passes through path-only options such as marks, rounded corners, and dash patterns                          |
| Path ribbon kind        | `kind="ribbon"` / `ribbon`          | Lowers source-target rows into core `Path` objects with `kind: 'ribbon'` for Sankey-style bands             |
| Shared style            | `style`                             | Shared paint and opacity fields used by both path and ribbon relations                                      |

## Examples

### Scatter Relations

Each scatter row declares both `id` and `target`. `PointMark` generates node ids with `anchorId`, and `RelationMark` joins those ids from the data fields. This example does not need `transform`: the relationship already exists in the raw rows, so RelationMark only resolves those fields into source / target paths.

### Sankey Ribbon

Sankey-style relations use the same `source` and `target` target refs, but set `kind="ribbon"` and provide `ribbon.width`. Shared paint lives in `style`, so the same relation mark can switch between path and ribbon geometry without moving fill, stroke, or opacity fields.

<ComponentPreview files={['relation-sankey', 'relation-sankey.data.ts']} size="lg" />

### Bubble Relation

Bubble charts often need to highlight one business relationship inside a broader distribution. This example uses 20 bubbles for the distribution, and the bubble layer generates reusable Node ids with `anchorId`. The relation layer does not hand-write an edge row; its `transform` runs `relate`: source selects the bubble with the largest `value`, target selects the bubble with the highest `y`, and the transform emits `sourceId`, `targetId`, and the path label. Source / target then reference those derived ids with `boundary`, so the connector stops at the bubble boundary.

<ComponentPreview files={['relation-bubble', 'relation-bubble.data.ts']} size="lg" />

### Path Extremes

The path mark draws 20 ordered points and registers each vertex with `anchorId`. This example also avoids a separate edge table: `RelationMark.transform` runs `relate` over the same points, selects the minimum `y` row as source and the maximum `y` row as target, then emits `sourceId`, `targetId`, and `deltaLabel`. Source / target connect to those derived vertex ids, and `path.routing={{ kind: 'bend' }}` draws the low-to-high relationship as a curve.

<ComponentPreview files={['relation-path-extremes', 'relation-path-extremes.data.ts']} size="lg" />

### Interval Relation

In a bar or interval chart, a relation can connect the tops of two interval elements to explain a handoff or difference between stages. This example keeps only before / after interval rows, not five handwritten relation lines. Two `RelationMark.transform` pipelines split decrease and increase groups: the decrease layer reads `decreaseOrder`, the increase layer reads `increaseOrder`, and both group by `pair` to emit source / target coordinates, the `sourceViaY` waypoint height, and `deltaLabel`. `path.routing={{ kind: 'orthogonal' }}` consumes those derived fields to draw the upward right-angle connector; decreases are red, increases are green.

## How It Works

`<RelationMark>` does not render DOM directly. `<Plot>` collects it into mark IR with `type: 'relation'` while building the `PlotSpec`. During lowering, plot resolves `source`, `target`, `label`, `path.via`, and `path.route[].to`. Both geometries lower into core `Path`: path relations omit `kind`, while ribbon relations set `kind: 'ribbon'` and provide `ribbon` options. Projected waypoints still generate core `Coordinate` elements when needed.

`transform` runs after the plot-level transform pipeline and only feeds the current relation mark. Derived fields such as `sourceId`, `targetId`, or `deltaLabel` can be consumed by `source`, `target`, `label`, `path.label`, `style`, `ribbon.width`, and relation channels without adding them to the root data model.

Target references share the `PlotTargetRef` structure:

| Form           | Use                                                  | Notes                                                                                             |
| -------------- | ---------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| `{ id }`       | Reference an existing core target directly           | Can also carry `anchor` / `offset` / `boundary`                                                   |
| `{ anchorId }` | Generate the target id from the current relation row | Uses the same rule shape as positional mark `anchorId`; useful for joining by data fields         |
| `{ project }`  | Project a point from the current relation row        | `project` maps coordinate roles to fields; add `anchorId` only when the point needs a reusable id |

Without `path.route`, the default path is `move(source) -> line(target)`. With `path.via`, intermediate points are inserted as `line(via)` in order. `path.routing` is a route strategy: `line` keeps straight segments, `bend` emits core bend steps, and `orthogonal` emits explicit right-angle line steps when the endpoints are projected coordinates. With `path.route`, route steps align with core path steps and support `line`, `fold`, `curve`, `cubic`, and `bend`. `path.route` and `path.routing` are mutually exclusive. Top-level `label` is the host label and attaches to the final core `Path.label`, shared by path and ribbon relations; it carries no `kind`, and its text source lives in `content.field` / `content.value`. `path.label` is shorthand for a step label: it lands on the default path, the selected routing segment, or the final drawable explicit route step. If a `path.route[].label` is already set, that explicit step label wins. Step labels generated by RelationMark default to `sloped: true`, so they rotate along the path; an explicit `side` only controls the placement side. Ribbon relations do not use path routing; they draw a direct ribbon centerline from source to target.

When a relation uses generated `anchorId` and the target does not exist, lowering fails after the plot finishes and reports the relation mark id / index, data row index, and generated id. Duplicate generated anchor ids also fail loudly.

## API

`RelationMark` groups its API by targets, route, path, label, common props, and custom channels. `FieldName` means a data field name or field path, for example `sourceId` / `meta.to`. Top-level `label` labels the whole geometry; `path.label` and `path.route[].label` are step labels.

### Mark API

| Prop                  | Type                                                                            | Default                      | Description                                                                                                                                  |
| --------------------- | ------------------------------------------------------------------------------- | ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `source`              | `RelationMarkProps['source']`                                                   | Required                     | Start target of the relationship: direct id, generated anchor id, or projected coordinate                                                    |
| `target`              | `RelationMarkProps['target']`                                                   | Required                     | End target of the relationship, using the same structure as `source`                                                                         |
| `transform?`          | `RelationMarkProps['transform']`                                                | —                            | Mark-local transform pipeline for deriving the current relation layer's rows from plot rows; see the transform table below for each type     |
| `kind?`               | <ApiValues name="RelationGeometryKind" />                                       | `path`                       | Chooses whether each relation row lowers to the default Path or a Path with `kind: 'ribbon'`                                                 |
| `label?`              | `RelationMarkProps['label']`                                                    | —                            | Label for the whole relation geometry; path and ribbon both lower it to core `Path.label`, with content in `content.field` / `content.value` |
| `path.via?`           | `NonNullable<RelationMarkProps['path']>['via']`                                 | —                            | Waypoints for the default route; each projected waypoint generates a core `Coordinate`                                                       |
| `path.route?`         | `NonNullable<RelationMarkProps['path']>['route']`                               | —                            | Explicit step sequence; the last step may omit `to` and default to `target`                                                                  |
| `path.routing?`       | `NonNullable<RelationMarkProps['path']>['routing']`                             | `line`                       | Algorithmic route strategy: `line`, `bend`, or `orthogonal`; mutually exclusive with `path.route`                                            |
| `path.route[].label?` | `NonNullable<NonNullable<RelationMarkProps['path']>['route']>[number]['label']` | —                            | Label for the current step; higher priority than `path.label` shorthand                                                                      |
| `path.label?`         | `NonNullable<RelationMarkProps['path']>['label']`                               | —                            | Shorthand path label for the default path or the final drawable route step; defaults to `sloped: true`                                       |
| `path.options?`       | `NonNullable<RelationMarkProps['path']>['options']`                             | —                            | Path-only options such as `marks`, `dashPattern`, `roundedCorners`, `lineCap`, and `lineJoin`                                                |
| `ribbon.width`        | `NonNullable<RelationMarkProps['ribbon']>['width']`                             | Required for `kind="ribbon"` | Ribbon width at the source side, or the whole width when `endWidth` is omitted                                                               |
| `ribbon.endWidth?`    | `NonNullable<RelationMarkProps['ribbon']>['endWidth']`                          | —                            | Optional target-side width for tapered ribbons                                                                                               |
| `ribbon.options?`     | `NonNullable<RelationMarkProps['ribbon']>['options']`                           | —                            | Ribbon-only options: `align`, `samples`, `sampling`, and taper `interpolation`                                                               |
| `style?`              | `RelationMarkProps['style']`                                                    | —                            | Shared style: `color`, `fill`, `fillOpacity`, `stroke`, `strokeWidth`, `strokeOpacity`, `opacity`, `shadow`, `blendMode`, `zIndex`           |
| `color?`              | `RelationMarkProps['color']`                                                    | —                            | Field-driven relation color channel                                                                                                          |
| `id?`                 | `RelationMarkProps['id']`                                                       | —                            | Optional mark handle for layer ids, errors, and runtime lookup                                                                               |
| `channels?`           | `RelationMarkProps['channels']`                                                 | —                            | Custom channel entry point, resolved by registered channel definitions                                                                       |

Path-only fields live under `path.options`, while fields that both path and ribbon can use live under `style`. This keeps `strokeWidth`, `fillOpacity`, `opacity`, `fill`, and `stroke` in one shared place and keeps marks / route-only behavior out of ribbon configs.

### Transform API

`transform` is the mark-local data entry shared by all marks, and it reuses the plot transform structure; see [Transform](/viz/plot/transform) for common transform types. Inside `RelationMark`, it only feeds the current relation mark and does not rewrite the rows seen by sibling marks. This table lists the relation-oriented transform that is most often used here.

| Type     | Row count         | Meaning                                                                                                                     |
| -------- | ----------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `relate` | N → relation rows | Reuses common selectors to choose source / target rows, usually for `RelationMark.transform`, and can also feed other marks |
