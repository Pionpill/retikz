The atomic custom-transform capability belongs to [Data Transform Extensions](/viz/data/transform/extensions). This page only demonstrates its injection and consumption in the Plot domain; Plot does not introduce a parallel transform contract.

The example `waterfall` operation turns each change into cumulative `from` / `to` intervals plus a `direction` field, which an `IntervalMark` then draws as a waterfall chart.

## Applicability

- Define and inject a transform in a Plot scenario when the logic is a pure, deterministic row operation whose outputs serve Plot position, interval, or relation encodings.
- Prefer [Data Built-In Transforms](/viz/data/transform/operations) for sorting, filtering, summarizing, and other general semantics. Data remains the source of truth for reusable extensions.
- Use [Custom Marks](/viz/plot/mark/custom-mark) or [Custom Coordinates](/viz/plot/coordinate/custom-coordinate) when the change belongs to mark lowering or projection instead of row processing.

`waterfall` is a documentation example kind, not a Plot built-in transform.

## Define the Capability

The Definition passed to `defineTransform` declares field semantics without reading rows. A separate `defineTransformImplementation` supplies `apply`. Neither knows about `IntervalMark`, colors, or renderers:

| field                  | responsibility in this example                                                |
| ---------------------- | ----------------------------------------------------------------------------- |
| `schema`               | Validate `kind`, the change field name, and the optional initial value        |
| `inputFields`          | Declare the source field corresponding to `delta`                             |
| `outputModel`          | Declare continuous from/to and categorical direction through preserve.outputs |
| Implementation `apply` | Accumulate rows and return new objects that spread each input row             |

## Inject the Host

Definition and Implementation remain runtime objects, registered through `transformDefinitions` and `transformImplementations`; `<PlotTransform>` adds only a JSON-safe operation to Plot IR:

```tsx
<Plot
  data={rows}
  transformDefinitions={[waterfallTransform]}
  transformImplementations={[waterfallTransformImplementation]}
>
  <PlotTransform operation={{ kind: 'waterfall', params: { field: 'delta', initialValue: 60 } }} />
  <IntervalMark x="period" color="direction" bounds={{ y: { kind: 'extent', from: 'from', to: 'to' } }} />
</Plot>
```

The same `{ operation }` declaration can be passed through `dataTransforms`. Put it on a mark's `transform` when only that mark should read the derived view. All three entry points use the same Plot transform registry.

## Execution

1. Plot merges Data built-ins and host-injected Definitions into one registry.
2. Field collection looks up `waterfall`, validates the operation with the same schema, and registers source and derived fields.
3. After all stages pass preflight, the root pipeline runs Implementation `apply` in declaration order and produces `from`, `to`, and `direction`.
4. `IntervalMark` consumes ordinary fields and does not need to know they came from a custom transform.

## Errors and Limits

- A custom `kind` cannot override a Data built-in or duplicate another injected Definition.
- Rendering fails before drawing when `waterfallTransform` is missing, the operation fails its schema, or the operation contains a non-JSON value.
- This example requires every change field to coerce to a finite number. Invalid values report their row and field instead of being skipped.
- A row-preserving transform should spread the input row to retain provenance. When row counts change, use `TransformContext.groupProvenance` as described in [Data Transform Extensions](/viz/data/transform/extensions).
- A Definition should not write color, mark, or renderer logic. `direction` is an ordinary categorical field; Plot channels still choose its colors.

## API Reference

See [Data Transform Extensions](/viz/data/transform/extensions#related-props) for the complete atomic Definition contract. This page directly uses these public entry points:

| entry point                               | use                                                |
| ----------------------------------------- | -------------------------------------------------- |
| `defineTransform` / `TransformDefinition` | Define the runtime capability from `@retikz/data`  |
| `<PlotTransform>`                         | Declare a root operation from `@retikz/plot-react` |
| `PlotProps.transformDefinitions`          | Inject Definitions into the React host             |
| `RenderPlotOptions.transformDefinitions`  | Inject from the `@retikz/plot-vanilla` host        |
| `LowerPlotsOptions.transformDefinitions`  | Inject when calling Plot lowering directly         |
