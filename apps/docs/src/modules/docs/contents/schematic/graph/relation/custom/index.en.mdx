Built-in and custom Relation semantics use the same definition, registration, and drawing path. This page assumes the endpoints and directions covered in [Basic usage](/schematic/graph/relation/usage).

## Scope

Register a definition when several relations share stable semantics, direction constraints, or marker structure. Configure an instance for a one-off path, label, or color; use Graph rules to change appearance based on existing semantics. Definitions do not perform layout, obstacle avoidance, or business-condition evaluation.

## Define capabilities

| Entry                     | Contract                                                                             | Constraint                                                                                |
| ------------------------- | ------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------- |
| `defineRelationRole`      | role, description, defaultDirection, allowedDirections, directions                   | Every allowed direction needs a complete sourceMarker / targetMarker / dashPattern recipe |
| `defineRelationKind`      | Globally unique kind, owning role, optional direction constraints and sparse recipes | May only narrow the role's directions; omitted fields inherit                             |
| `defineRelationPredicate` | name, role, optional kinds, paramsSchema, optional resolveStructure                  | Resolver receives parsed parameters and returns a non-empty sparse structure override     |

A role recipe uses `{ shape: 'registered Arrow key' }` or `false` for each marker, and a number array or `false` for dashPattern. `false` explicitly removes a marker or dashes; it does not mean inheritance. Kind and predicate overrides only need fields they change.

```ts
import { defineRelationRole } from '@retikz/graph';

const signalRole = defineRelationRole({
  role: 'domain.signal',
  description: 'One-way domain signal',
  defaultDirection: 'forward',
  allowedDirections: ['forward'],
  directions: {
    forward: { sourceMarker: false, targetMarker: { shape: 'stealth' }, dashPattern: false },
  },
});
```

`define*` returns a definition ready for assembly; it does not immediately register or validate the whole registry. Inject custom keys through the host before referencing them. Marker shapes use Core Arrow providers, with no separate Graph marker registry.

## Inject and use

In React, pass `relationRoles`, `relationKinds`, and `relationPredicates` to `<Graph>` and reference their keys from nested Relations. Vanilla uses the same options on `graph({ ... })`, referenced by `relation({ ... })`. The example source shows definition → Graph injection → Relation reference → rule consumption end to end.

For direct IR compilation, pass definitions to `createGraphDefinitions(options)` and install its composite extensions on the host. Provider-based hosts use `createGraphProviders(options)`. Functions, schemas, and resolvers belong to runtime assembly and cannot be persisted in IR. IR stores only role, kind, and predicate names with JSON parameters.

## Errors and limitations

- Registry assembly rejects duplicate keys, replacement of built-ins, unknown parent roles, and conflicting role / kind ownership.
- A role's default direction must be allowed and every allowed direction needs a complete recipe. A kind may only narrow directions, and its effective default must remain allowed.
- Predicates may restrict kinds. Parameter parse failures prevent `resolveStructure` from running. Callback exceptions or invalid overrides become Graph errors with the cause preserved.
- Register custom Arrow shapes in the Core host. Missing providers do not fall back to another shape.
- Custom structure does not rewrite source / target or route. Omitted routes still connect endpoints directly.
