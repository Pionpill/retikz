## Connections and routing

### Orthogonal avoidance

Use `orthogonal` for axis-aligned connections. Omit `turnPosition` to compare midpoint `0.5`, then `0.25` and `0.75`; an explicit fraction locks the turn and disables automatic selection.

| Configuration                     | Effect                                                    |
| --------------------------------- | --------------------------------------------------------- |
| `{ kind: 'orthogonal' }`          | Compare three candidates, preferring the midpoint on ties |
| `turnPosition: 0.25 / 0.5 / 0.75` | Lock a source-to-target boundary-gap fraction             |
| `cornerRadius`                    | Round corners without adding candidates                   |

The example uses rectangles for Source and Target and an ellipse for Obstacle. Adjust obstacle X / Y (its center in Flow root coordinates) to see automatic turn selection while endpoints remain fixed. Select an explicit fraction to compare a locked route. Horizontally or vertically aligned endpoints always connect directly without avoidance.

Scores compare node-conflict count, penetration length inside nodes, then label conflicts. Remaining ties prefer `0.5 / 0.25 / 0.75`. If all candidates conflict, the best route is drawn with `FlowOrthogonalObstacleConflict`; explicit routes warn without changing. Feedback retains its outer lane, unaffected by the fraction. Parallel relations retain lane offsets and gap clamping.

The fraction inherits only between orthogonal root, Group and Relation settings, with local values taking precedence. `-|` and `|-` do not accept it. Checks use the reference polyline before corner rounding, with no global collision-free guarantee for complex scenes or final rounded corners. See [orthogonal routing internals](/schematic/diagram/flow/mechanism#automatic-orthogonal-avoidance).

### Bend curves and labels

`bend` is a regular route alongside straight, orthogonal, and single-elbow routes. This example fixes rectangular Source and Target nodes. Move the elliptical Obstacle using X / Y to see the curve change. By default, side and angle are omitted, comparing left/right at `30° / 45° / 60°`. Candidates first compare node-conflict count, then total collision parameter span, then label conflicts; remaining ties prefer smaller angles, then left. Edge overlaps and crossings are not compared. Disable “Automatic angle” to compare only the two sides at the specified angle. Nodes and route kinds remain unchanged. With the obstacle on the direct line and explicit angle 0, both candidates coincide and cross the obstacle; the relation is still drawn and a `FlowBendObstacleConflict` warning points to the original relation.

<ComponentPreview

  defaultSourceFile="flow-bend.preview.tsx"
  size="md"
  caption="Switch between automatic and explicit angles to explore bounded candidate selection as the obstacle moves; move the label and toggle slope and interruption along the same curve."

A compact `label: 'Continue'` retains the default label strategy. A complete object such as `label: { text: 'Continue', position: 0.5, sloped: true }` exposes all Core GeometryLabel options: `position`, `side`, `sloped`, `placement`, `distance`, `interrupt`, `gap`, `textColor`, `font`, and `opacity`. Position uses the curve parameter rather than equal arc length; slope follows the tangent, while interruption and gap control the stroke opening around the label. An object containing only text still uses complete-label defaults. Font fields inherit individually, with label appearance taking precedence over relation appearance. Reserved boxes inform layout scoring; Core draws the final text and clips endpoints to node boundaries.

### Bezier curves

Prefer bend for simple curves. When its finite candidates are insufficient, use `curve` or `cubic` on an individual Relation. Omit all controls for automatic generation; there is no mode field. This example fixes rectangular Source and Target nodes: move the elliptical Obstacle and switch between quadratic and cubic routing to compare automatic detours. Disable automatic generation to edit control coordinates; the second control is available only for explicit cubic routing.

| routing                                                       | Meaning                          |
| ------------------------------------------------------------- | -------------------------------- |
| `{ kind: 'curve' }`                                           | Automatic quadratic              |
| `{ kind: 'cubic' }`                                           | Automatic cubic                  |
| `{ kind: 'curve', control: [100, -80] }`                      | Explicit quadratic control       |
| `{ kind: 'cubic', control1: [30, -80], control2: [160, 50] }` | Complete explicit cubic controls |

<ComponentPreview

  defaultSourceFile="flow-bezier.preview.tsx"
  size="md"
/>

Providing only one cubic control is rejected. Root and Group defaults cannot use Bezier routing. Controls use Flow root coordinates and usually do not lie on the curve. Subtract `regions.drawing.origin` when copying controls from an artifact. Layout changes do not move explicit controls.

Automatic quadratics/cubics propose at most 13/49 candidates; collision checks bisect at most 8 levels. Candidates compare node-conflict count, label-conflict count, curve length, then lateral deviation, using each criterion only to break ties in the previous one. Penetration depth is not compared. If every candidate conflicts, the best finite route is retained with `FlowBezierSearchExhausted`. Checks concern the center reference curve; Core boundary connections can change its shape, so inspect the final drawing. See [automatic Bezier avoidance](/schematic/diagram/flow/mechanism#automatic-bezier-avoidance) for details.

### Through-point curves

When the route must pass through known positions, set `routing: { kind: 'smooth', points, tension? }` on an individual Relation. Supply only intermediate waypoints: Flow adds the relation source and target. Start with 2–3 points and add points at changes of direction; there is no hard count limit.

| Field     | Effect                                                                                                     |
| --------- | ---------------------------------------------------------------------------------------------------------- |
| `points`  | At least one ordered Target: Cartesian, polar, node anchor/offset, between, relative or relativeAccumulate |
| `tension` | Positive tangent multiplier, default 1; changes the curve without moving its knots                         |

The example fixes three nodes and defaults to two waypoints relative to the endpoints. Choose 1–3 points: one above the obstacle, two inside the endpoints, or all three. Height moves the points; tension reshapes the curve through the same points.

<ComponentPreview
  files={['flow-smooth', 'flow-smooth.preview.tsx']}
  defaultSourceFile="flow-smooth.preview.tsx"
  size="md"
  caption="A lower detour may cross the obstacle. Smooth warns but never moves the points or adjusts tension automatically."
/>

References must name an Entity or Group in this Flow, not a Layout or an external node. Ordinary `relative` leaves the reference cursor unchanged; `relativeAccumulate` and absolute points advance it. NodeTarget `offset` is a world vector; other Target forms retain their own coordinate semantics. Root, Group and layout Definition defaults do not accept smooth.

For avoidance, normally try automatic bend, quadratic and cubic routing in that order. Use explicit Bezier controls when tangent directions are known, and smooth when passage positions are known. This is authoring guidance, not a runtime upgrade chain. A safe knot chain does not guarantee a safe interpolated curve: inspect the curve, arrows and labels. See [through-point routing internals](/schematic/diagram/flow/mechanism#through-point-curves-preserve-the-authored-route).

## Structure and layout

`FlowLayout` fixes the arrangement of direct children. `FlowGroup` draws a named semantic boundary and automatically lays out the steps inside it. Examine each one before combining them in one diagram.

### Fixed placement

`FlowLayout` is a container without a visible shell. `kind="linear"` places direct children in declaration order along one direction; `kind="grid"` aligns them in explicit rows and columns. A Layout draws no border or title and cannot be a Relation endpoint.

| Property            | Values                                                  | Purpose                                                                 |
| ------------------- | ------------------------------------------------------- | ----------------------------------------------------------------------- |
| `kind`              | `"linear"`, `"grid"`                                    | Selects one-dimensional placement or row and column alignment           |
| `direction`         | `up`, `right`, `down`, `left`                           | Places direct children in order along this direction in Linear          |
| `gap`               | Nonnegative number; Grid also accepts `{ row, column }` | Sets adjacent spacing in Linear or row and column track gaps in Grid    |
| `itemWidth`         | `"match-largest"` or a positive number; optional        | Matches the largest natural width or fixes the width of direct Entities |
| `placements`        | Matrix or mapping from child id to row and column       | Assigns a cell to each direct child in Grid                             |
| `reserveLabelSpace` | Boolean; `true` by default                              | Expands Grid gaps for Relation labels                                   |
| `excludeFromBounds` | `Array<string>`; exclude none by default                | Omits direct children from the footprint reported to the parent         |

The example contains only Input, Check, and Output. Switch between left and right and change the gap to see that Layout preserves their declared order. There is no Relation between them: fixed placement does not depend on a connection. `direction` also supports up and down.

Set `itemWidth` when the edges of a step group should align. `"match-largest"` measures the Layout's direct Entities and draws each at the largest natural visible width; a number such as `itemWidth={180}` fixes that width, wrapping long plain text and growing its height. It does not cross a nested Layout or Group, excludes margin from the comparison, and does not wrap horizontal children onto another row.

<ComponentPreview
  files={['flow-item-width', 'flow-item-width.preview.tsx']}
  defaultSourceFile="flow-item-width.preview.tsx"
  size="md"
  caption="Switch between vertical and horizontal placement and natural, matched, or fixed widths to see two step edges align and long text wrap."
/>

Use Grid when nodes in different rows must align in pairs. The recommended `placements` form is a matrix: the outer index is the zero-based row, the inner index is the column, each cell contains a direct child id, and `null` leaves a cell empty. An id-keyed `{ childId: { row, column } }` mapping is also supported. React and Vanilla use the same `placements`; Vanilla `children` controls only containment and paint order. Every direct child needs one cell; overlaps, spans, and references to descendants in other containers are invalid. Empty tracks create no placeholder elements. Columns share center x, rows share center y, and nodes retain their measured sizes.

The example has four Entities in two rows and two columns. Change the row and column gaps and label reservation to see their centers stay aligned and the label expand the column gap. The preview source shows the `placements` configuration.

<ComponentPreview
  files="flow-grid"
  size="md"
  caption="Change row and column gaps and label reservation; watch the node centers and the space occupied by the edge label."
/>

For Grid, a numeric `gap` sets both row and column gaps. To set them separately, provide a complete `{ row, column }` object; both fields are required. Linear accepts only a numeric `gap`. When Grid `gap` is omitted, both axes inherit an explicitly authored `nodeGap`; otherwise their built-in defaults are `32` and `48`, respectively. Explicit `0` is valid. `reserveLabelSpace` is enabled by default: a labeled horizontal Relation adds its measured width to column gaps, while a vertical label adds its height to row gaps. Labels on the same axis use the largest dimension; disable the option to use the configured gaps exactly. Labels may be strings (`\n` is a hard break) or TextBlock line arrays, both measured as complete blocks. Asymmetric margins reserve space symmetrically without shifting node centers. Grid does not rotate with flow direction or guarantee global collision avoidance for diagonal, orthogonal, or cross-node routes. The [TeX cache diagram](/kernel/packages/tex/mechanism#caching-failures-and-retries) demonstrates this layout.

Linear defaults to `gap=48` for left and right, and `gap=32` for up and down. Fixed spacing comes from the local explicit value, an ancestor's explicit `nodeGap` (or Linear `gap`), then the Definition's physical-axis default. An ancestor's explicit `0` is inherited, while a materialized parent default is not treated as authored. Custom Layout Definitions supply finite nonnegative `defaults.placementGap: { horizontal, vertical }`, independently of the root and Group automatic-layout defaults `nodeGap=48` and `rankGap=48`.

Set `excludeFromBounds` on a Layout when attached nodes should still draw but must not shift their primary node's alignment in an outer layout. In the example, Canvas and SVG share a column center, while PNG and JPEG remain vertically arranged in their own layout and connect to Canvas independently. Toggle exclusion of `formats` to see it remain arranged while the footprint reported by `canvas-output` to its parent changes.

<ComponentPreview
  files="flow-bounds"
  size="md"
  caption="The gray dashed frame encloses the footprint canvas-output reports to its parent. Toggle exclusion of formats: PNG and JPEG remain visible while the frame changes with the footprint."
/>

React `<FlowLayout excludeFromBounds={['formats']}>` and `{ excludeFromBounds: ['formats'] }` in Vanilla `layouts` express the same configuration; compare them in the preview source. Only direct child ids of this Layout are allowed. Omission or an empty array preserves existing behavior; duplicate ids, descendants, ids from another container, and excluding every child fail. The list is not inherited by nested layouts.

Exclusion changes only the footprint and alignment basis reported to the parent. It does not hide nodes or make them absolutely positioned. Local order, gaps, margins, Grid tracks, and label reservation remain active. An attached item between two primary items can still change their distance; use a dedicated Layout as in the example to isolate that effect. The complete canvas still contains attached nodes and relations, and visible Groups still enclose all descendants. Exclusion does not provide obstacle avoidance. A Layout artifact's `bounds` describes its layout footprint, not its complete drawing extent or clip. Custom providers must forward the exclusion configuration and preserve every child and relative coordinate returned by `placeLayout`.

### Visible group

`FlowGroup` expresses a semantic boundary and directly reuses the presentation and context properties of [Graph Group](/schematic/graph/group). Its shell can contain both a title and a description, with additional labels on the boundary. Its `children` are laid out automatically. A Group can be a Relation endpoint and can set local routing.

| Property                                                          | Values                                         | Purpose                                                    |
| ----------------------------------------------------------------- | ---------------------------------------------- | ---------------------------------------------------------- |
| `caption.title`                                                   | `{ text, ...text formatting }`                 | Group title; `text` accepts TextBlock                      |
| `caption.description`                                             | `{ text, ...text formatting }`                 | Group description, also usable without a title             |
| `caption.side`                                                    | `top`, `bottom`; default `top`                 | Places the caption above or below the content              |
| `caption.direction`                                               | `horizontal`, `vertical`; default `horizontal` | Arranges the title and description                         |
| `caption.itemGap` / `bodyGap`                                     | Nonnegative number; default `4`                | Space between text items and between caption and content   |
| `labels`                                                          | Optional nonempty label array                  | Boundary labels with Graph positioning and text formatting |
| `padding` / `background` / `border` / `cornerRadius` / `overflow` | Corresponding Graph Group properties           | Shell spacing, fill, border, corners, and content overflow |
| `graphDefaults` / `graphRules`                                    | Graph defaults and rules                       | Default appearance for Graph descendants inside the Group  |
| `layout.direction`                                                | `up`, `right`, `down`, `left`                  | Sets the automatic layout direction inside the Group       |
| `layout.nodeGap`                                                  | Nonnegative number                             | Changes the gap between peers in one rank                  |
| `layout.rankGap`                                                  | Nonnegative number                             | Changes the gap between adjacent ranks                     |

The example puts Request, Validate, and Authorize inside Service entry. Request connects to both Validate and Authorize. This example uses `direction: "vertical"` to stack the title and description. Toggle the title, description, and boundary labels independently, then adjust the internal layout to see the shell follow its content.

### Grouped placement

Groups and Layouts can both contain children and nest each other. A Grid can align steps inside a Group while the Group itself keeps automatic layout. Their visible results and placement responsibilities differ.

| Difference        | `FlowGroup`                                                               | `FlowLayout`                                                               |
| ----------------- | ------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| Primary role      | Express a named, styled semantic group                                    | Place direct children in a fixed arrangement                               |
| Visible result    | Materialize a Graph Group with a shell and optional title                 | Add no border, background, or title                                        |
| Internal layout   | `layout` controls automatic direction, peer gap, and rank gap             | `kind="linear"` for one axis, or `kind="grid"` for shared rows and columns |
| Relation endpoint | Allowed                                                                   | Not allowed; connect an Entity or Group inside it                          |
| Source catalog    | Stored in `groups`; `children` preserves direct members and sibling order | Stored in `layouts`; `children` preserves fixed order                      |

The combined example places a visible Group above a shell-free Layout; an outer Layout fixes their vertical order. A Relation from the Group shell to the queue demonstrates a Group endpoint. Change each container's controls to compare automatic layout with fixed placement.

## Appearance and defaults

Flow, Graph, and Diagram appearance settings change visible styles without changing graph structure.

### Defaults and themes

`flowDefaults` supplies one shared default style for each Flow object category at the root. `entity.style` applies to every Entity, while `relation.style` applies to every Relation; neither setting changes Source ids, containment, node layout, or routing. Local `style` can still override a global value when needed, but this example shows global configuration only.

<ComponentPreview
  files="flow-theme"
  size="md"
  caption="Changing either section updates every object of that category, while the nodes, relations, and their relative positions remain unchanged."
/>

`theme: { style, mode }` selects the theme environment; `flowThemeStyles` / `diagramThemeStyles` inject matching Definitions. Flow-level `graphRules` set conditional appearance for materialized Entities and Relations. The same field on Group adds local rules for its descendants without changing routing or containment. Explicit `flowDefaults` and `diagramDefaults` use the same paths as formal Source. Entity and Relation `group` directly reuse Graph: equal groups in one Flow root share an automatic color taken from the head of the categorical palette, while ungrouped elements keep their existing appearance. Entity and Relation appearance precedence is Graph Theme, defaults and rules from the owning Graph context, `flowDefaults`, then instance fields.

Flow defaults contain `layout.nodeGap/rankGap`, `entity.style/layout`, Group Surface appearance and caption arrangement and formatting, and Relation path, marker, and label formatting. Defaults for `caption.title` and `caption.description` apply only to authored text items and never create content. They exclude identity, children, automatic layout direction, routing, and overflow, and never create Groups or markers. Empty objects and undefined do not override values; 0 and false remain meaningful. Node fonts replace as a whole; Relation `labelFont` merges by field.
