本页以已读[基础用法](/schematic/diagram/flow/usage)为前提，追踪一次 Flow 编译。输入是一份可序列化的 Source 和当前宿主的 Definition / Theme；输出是可渲染的 Diagram Scene、`FlowDiagramArtifact` 与空间句柄。任一阶段失败会终止这次编译，不交付部分几何。

## 整体流程

| 阶段       | 输入                                        | 交给下一阶段的结果                                 |
| ---------- | ------------------------------------------- | -------------------------------------------------- |
| 解析       | Source、Definition、Theme                   | 有效的 Entity、Group、Layout 和 Relation 语义      |
| 测量       | 已解析语义、Graph 外观                      | 元素尺寸、作用域、关系标签尺寸和 `FlowLayoutInput` |
| 布局与校验 | `FlowLayoutInput`、选中的 Layout Definition | 已验证且脱离回调对象的 bounds 与 route             |
| 物化与装配 | 同一份已验证几何                            | Graph 图元与 `FlowDiagramArtifact`                 |

Source 中只有声明和引用；测量产生布局输入，Definition 返回的几何经校验后才进入物化和结果装配。下图展示这条主线，后续各节沿同一组“接收 → 校验”元素说明数据如何变化。

## 语义解析建立唯一包含关系

Flow 的输入是声明式的：描述图中有哪些内容、内容之间如何连接、哪些元素属于同一容器，以及希望如何布局即可。下面把“接收 → 校验”两个实体放进线性 Layout，再由一个可见 Group 包含它。代码树展示 Source 的字段与条目；其中的 `children` 保存 id 引用，不是嵌套的实体对象。

```text
Flow Source
├── namespace: "diagram", type: "flow"
├── entities
│   ├── { id: "receive", text: "接收", role: "activity" }
│   └── { id: "verify", text: "校验", role: "activity" }
├── groups
│   └── { id: "pipeline", children: ["steps"] }
├── layouts
│   └── { id: "steps", kind: "linear", direction: "right",
│         children: ["receive", "verify"] }
├── children: ["pipeline"]
└── relations
    └── { source: "receive", target: "verify" }
```

这几个字段各有明确职责：

- `entities`：实体目录，声明文字、角色等内容；每个实体只需声明一次。
- `groups`：可见分组目录；每项通过 `children` 引用直接成员，可设置外框、说明与局部自动布局。
- `layouts`：固定排布目录；每项通过 `children` 引用直接成员，`kind` 等配置指定线性或网格排列。
- 根 `children`：图的直接成员与同级顺序。目录中的声明顺序不替代包含关系。
- `relations`：根级关系目录，通过 `source`、`target` 引用实体或 Group，不决定谁包含谁。

这种分工有两个目的：

1. 人工和 LLM 都围绕内容、关系、包含与布局声明输入，职责明确，不必手算坐标或编写绘制步骤。
2. 将声明与解析逻辑隔离。作者仍需用 id 表达包含关系，但不必构造内部嵌套树或重复嵌入实体对象；查找引用、校验结构和建立递归对象树由实现负责。React 的组件嵌套也会先归一为这份平级 Source。

解析器先按 id 登记三类目录，再检查 `children` 引用是否存在、每项是否恰好有一个父级，以及是否有自包含、包含循环或未被包含的条目。校验通过后，从根 `children` 开始递归查找成员，把 id 引用转换为内部 `elements` 数组：`pipeline` 包含 `steps`，`steps` 包含两个 Entity。关系端点单独校验，关系仍保存在根级有序列表中；Graph Definition 与 Theme 同时确定后续测量所需的语义与外观。

## 测量把图元变为布局输入

Flow 会先测出布局需要的信息：每个图元有多大、周围要留多少空隙、分组内部要留多少空间，以及连线上的文字会占多少空间，再把这些信息和布局、连线配置一起交给布局阶段。

这些信息保存在 `FlowLayoutInput` 中。布局阶段拿到后，只需安排图元的位置和连线的走向，不用再测一遍。例如“校验”的文字变长时，Flow 会先算出它需要的宽度，布局时就能给它留出足够的空间。

## 布局确定位置和连线

布局阶段拿到前面测好的信息后，由布局回调安排每个图元的位置，并决定连线怎么走。它返回每个图元的位置和大小（`bounds`），以及组成连线的一串点。如果连线上有文字，还可以为文字预留空间。

对于输入中指定的固定 Layout，回调先通过 `context.placeLayout` 算出内部排列，再把它放进整张图。每个固定 Layout 只计算一次，整体移动时保留内部图元的相对位置。

Flow 会检查布局结果是否完整、实体的大小是否与测量结果一致、分组能否容纳内容，以及图元、连线和文字之间是否出现不允许的重叠。检查通过后，才会用这些位置和连线继续绘图。

## 按布局绘图并保存结果

位置和连线确定后，Flow 会把它们交给 Graph 来生成图形：实体绘制成节点，Group 绘制成分组，Layout 用 Scope 保留排列和层级。连线也按布局结果绘制，原来的包含关系保持不变。

同时，Flow 会把图元的位置、大小和连线上的点保存在 `FlowDiagramArtifact` 中，供调用方查询。这个结果记录布局信息，文字和样式仍来自输入声明。
