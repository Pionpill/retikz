## 整体流程

| 阶段       | 输入                                        | 交给下一阶段的结果                                 |
| ---------- | ------------------------------------------- | -------------------------------------------------- |
| 解析       | Source、Definition、Theme                   | 有效的 Entity、Group、Layout 和 Relation 语义      |
| 测量       | 已解析语义、Graph 外观                      | 元素尺寸、作用域、关系标签尺寸和 `FlowLayoutInput` |
| 布局与校验 | `FlowLayoutInput`、选中的 Layout Definition | 已验证且脱离回调对象的 bounds 与 route             |
| 物化与装配 | 同一份已验证几何                            | Graph 图元与 `FlowDiagramArtifact`                 |

Source 中只有声明和引用；测量产生布局输入，Definition 返回的几何经校验后才进入物化和结果装配。下图展示这条主线，后续各节沿同一组“接收 → 校验”元素说明数据如何变化。

## 语义解析建立唯一包含关系

Flow 的输入是声明式的：描述图中有哪些内容、内容之间如何连接、哪些元素属于同一容器，以及希望如何布局即可。下面把“接收 → 校验”两个实体放进线性 Layout，再由一个可见 Group 包含它。代码树展示 Source 的字段与条目；其中的 `children` 保存 id 引用，不是嵌套的实体对象。

```text
Flow Source
├── namespace: "diagram", type: "flow"
├── entities
│   ├── { id: "receive", text: "接收", role: "activity" }
│   └── { id: "verify", text: "校验", role: "activity" }
├── groups
│   └── { id: "pipeline", children: ["steps"] }
├── layouts
│   └── { id: "steps", kind: "linear", direction: "right",
│         children: ["receive", "verify"] }
├── children: ["pipeline"]
└── relations
    └── { source: "receive", target: "verify" }
```

这几个字段各有明确职责：

- `entities`：实体目录，声明文字、角色等内容；每个实体只需声明一次。
- `groups`：可见分组目录；每项通过 `children` 引用直接成员，可设置外框、说明与局部自动布局。
- `layouts`：固定排布目录；每项通过 `children` 引用直接成员，`kind` 等配置指定线性或网格排列。
- 根 `children`：图的直接成员与同级顺序。目录中的声明顺序不替代包含关系。
- `relations`：根级关系目录，通过 `source`、`target` 引用实体或 Group，不决定谁包含谁。

这种分工有两个目的：

1. 人工和 LLM 都围绕内容、关系、包含与布局声明输入，职责明确，不必手算坐标或编写绘制步骤。
2. 将声明与解析逻辑隔离。作者仍需用 id 表达包含关系，但不必构造内部嵌套树或重复嵌入实体对象；查找引用、校验结构和建立递归对象树由实现负责。React 的组件嵌套也会先归一为这份平级 Source。

解析器先按 id 登记三类目录，再检查 `children` 引用是否存在、每项是否恰好有一个父级，以及是否有自包含、包含循环或未被包含的条目。校验通过后，从根 `children` 开始递归查找成员，把 id 引用转换为内部 `elements` 数组：`pipeline` 包含 `steps`，`steps` 包含两个 Entity。关系端点单独校验，关系仍保存在根级有序列表中；Graph Definition 与 Theme 同时确定后续测量所需的语义与外观。

## 测量把图元变为布局输入

Flow 会先测出布局需要的信息：每个图元有多大、周围要留多少空隙、分组内部要留多少空间，以及连线上的文字会占多少空间，再把这些信息和布局、连线配置一起交给布局阶段。

这些信息保存在 `FlowLayoutInput` 中。布局阶段拿到后，只需安排图元的位置和连线的走向，不用再测一遍。例如“校验”的文字变长时，Flow 会先算出它需要的宽度，布局时就能给它留出足够的空间。

## 布局确定位置和连线

布局阶段拿到前面测好的信息后，由布局回调安排每个图元的位置，并决定连线怎么走。它返回每个图元的位置和大小（`bounds`），以及带有种类的参考路线（`route`）：直线与折线保存点链，bend 保存两个参考端点和生效的曲线参数。如果连线上有文字，还可以为文字预留空间。

对于输入中指定的固定 Layout，回调先通过 `context.placeLayout` 算出内部排列，再把它放进整张图。每个固定 Layout 只计算一次，整体移动时保留内部图元的相对位置。

Flow 会检查布局结果是否完整、实体的大小是否与测量结果一致、分组能否容纳内容，以及图元、连线和文字是否满足输出约束。契约错误会终止编译；bend 穿越节点则保留路线并发出 warning，具体处理见下方的 [bend 曲线的自动避让](#bend-曲线的自动避让)。

## 正交折线的自动避让

先检查两个端点是否水平或垂直对齐：对齐就直接连接，跳过避让与冲突警告。其余前向关系以节点面对面边界为基准，沿 source → target 的间隙取 `0.5 / 0.25 / 0.75`；间隙重叠时改用中心间隔。横向布局改变中间竖段位置，纵向布局改变中间横段位置。回边保留外侧通道。

每条候选至多三段轴对齐直线，直接与节点矩形求交，不做曲线二分。把跨折点连续的接触合并为路径长度区间，仅豁免起点离开和终点进入的连续区间；离开节点后重入仍算冲突。逐项比较节点数、穿越长度和标签冲突，同分保留中点优先顺序。障碍数量为 N、标签数量为 L 时，候选评分为 O(3 × 3 × (N + L))，不递归增加候选。

圆角不参与参考折线评分，由 Core 在最终绘图时处理。失败保留最佳候选并警告，显式比例只检查而不改选。可在[正交避让试验场](/schematic/diagram/flow/extended#正交自动避让)切换折点比例和障碍位置。

## bend 曲线的自动避让

内置 layered 布局先确定节点位置，再从有限的 bend 候选中选择路线。自动避让优先减少节点冲突，再考虑标签；它不移动节点，也不保证全局无碰撞。

### 有限候选按优先级选优

没有指定或继承角度时，候选角度是 `30° / 45° / 60°`；方向省略时比较左右，最多六条。显式或继承的方向只允许该侧，显式或继承的角度只允许该角度；两者都确定或采用切线参数时直接使用作者配置。

候选按以下优先级采纳，前一项相同才比较下一项：

1. **节点冲突更少**：先选穿越障碍盒数量更少的候选，再比较曲线处于障碍盒内的参数区间总跨度。例如两侧 `30°` 都穿过节点，而 `45°` 能绕开，就优先选择 `45°`。
2. **标签冲突更少**：节点评分并列时，比较曲线与已有标签、候选标签与已有标签及节点障碍盒的冲突次数。即使角度更大，只要节点评分相同且标签冲突更少，也优先采纳。
3. **角度更小**：节点和标签评分都相同时，按 `30° → 45° → 60°` 采纳。例如 `45°` 和 `60°` 都无冲突，就选 `45°`。
4. **左侧优先**：评分和角度都相同时，选左侧，保证结果稳定。

角度省略状态一直保留到布局阶段，避免把自动角度误当成作者指定的 `30°`。

下图固定两个端点，叠加六条参考候选。中间节点挡住两条 `30°`，上方已有标签挡住左侧 `45°`；右侧 `45°` 与两条 `60°` 都无冲突，因此按小角度优先选中右侧 `45°`。图中的候选角度标注仅用于讲解，不参与标签评分。

### 递归细分排除曲线周围的空白

整个判定可以分为三个步骤：**整曲线 AABB 初筛 → 子曲线 AABB 细判 → 候选逐项排序**。AABB 是与坐标轴对齐的包围矩形。下图沿用同一组障碍盒：左侧 `60°` 的整曲线包围盒排除 C，细分后确认 A 附近接触、B 所在空白不接触；将同样的检测应用于六条候选后，无标签的例子选中右侧 `30°`。这是按优先级比较，不是加权求和。

<ComponentPreview files="flow-bend-screening" hideCode type="illustration" size="lg" />

节点检测先用整曲线在 x、y 方向上的真实极值计算 AABB，每条候选只计算一次，用来排除不相交的障碍盒。判断对象是整个障碍盒，不是节点中心；边缘相切及数值容差内的接触仍保留。剩余节点进入子曲线细判，不只检查中点或控制点。初筛仍遍历同一 Flow 各层级的障碍盒，没有建立空间索引。

细判并不把曲线拉直。每次将当前曲线的参数区间一分为二，保留两条真实子曲线，再各自用 x、y 方向的极值计算 AABB：

1. **AABB 与障碍盒分离**：立即排除该区间，不再细分。
2. **AABB 完全落入障碍盒**：记录该区间。
3. **仍重叠但未完全包含**：继续二分；达到 `8` 层，或子段 AABB 的宽、高都不超过 `0.25` 用户单位时，保守记录尚未分离的区间。

下图放大前两步中的曲线检测，依次展示整段、二分与第 3 层的包围盒。橙色虚线表示仍与障碍盒重叠的小盒，灰色点线表示可排除的小盒；实际执行只继续细分重叠分支，图中统一展开同层盒用于对照。

<ComponentPreview files="flow-bend-subdivision" hideCode type="illustration" size="lg" />

曲线内侧的大块空白会随细分被排除，但终止时小盒的空白角落仍可能产生保守误判。这里是**参数二分，不是等弧长采样，也没有最终的线段求交**。相邻保留区间合并后，先豁免端点节点的合法出入，再统计冲突节点数与参数跨度之和 `Σ(t_end − t_start)`；跨度不是实际穿越长度。节点侧仍使用矩形避让盒而非形状轮廓。

### 逐条处理与冲突告警

障碍盒包含叶节点的 margin；相关祖先 Group 外壳不作为实心障碍。端点节点只豁免连续的合法离开与进入，曲线离开后重新穿入仍算冲突。

关系按 Source 顺序处理。标签比较包含先前选定的自动路线与全部非自动路线的标签，不包含尚未选择的自动路线。因此结果可重复，但不是所有关系同时优化的全局解。

节点最优候选唯一时直接交付；多个候选比较标签时，按小角度、左侧优先的顺序找到零标签冲突即可停止。没有标签的平行边可能选择同一路线。

路径之间的重叠与交叉不参与检测或评分，主要有两个原因：

1. **计算开销大**：每条候选曲线都需要与其它路径比较；曲线细分后还涉及多组线段的求交。图元和连线越多，这类比较的开销越明显，因此不把它纳入每次自动选路。
2. **交点很常见**：流程图中的连线交叉是常见情况，出现交点并不等于遮挡节点或标签。仅为减少交点单独检测和评分，收益不足以抵消开销，因此自动避让优先保障节点和标签的可读性。

## 贝塞尔曲线的自动避让

贝塞尔沿用 bend 的“生成候选、检测冲突、比较路线”流程，但控制点由障碍位置反求，允许不对称绕行。`curve` 是二次曲线，`cubic` 是三次曲线；省略控制点才进入自动求解，完整提供控制点时直接保留作者配置。

### 从经过点反求控制点

- **P₀、P₁**：布局给出的两个节点中心，是参考曲线端点。
- **Q**：希望曲线经过的绕行位置，取自冲突障碍包络的两侧。
- **τ**：到达 Q 的曲线参数位置，候选为 `1/4、1/2、3/4`，不是弧长比例。
- **C / C₁、C₂**：决定弯曲的控制点，曲线通常不经过它们。

下图固定 τ = 1/2。蓝色曲线经过障碍上方的 Q，橙色 C 更靠外；灰色控制折线只用于说明控制关系。

<ComponentPreview files="flow-bezier-controls" hideCode type="illustration" size="xxl" />

二次曲线由 `C = [Q − (1−τ)²P₀ − τ²P₁] / [2(1−τ)τ]` 反求。三次先选定首尾方向，再解 `C₁ = P₀ + a d₀`、`C₂ = P₁ − b d₁` 中的控制臂 a、b，使曲线在 τ 经过 Q。每个 Q/τ 比较四组方向组合；没有正解、方程退化或控制臂超过四倍弦长时淘汰。二次控制点到任一端点也不能超过四倍弦长。这些约束只用于自动生成，不限制合法显式点。

### 有界候选逐轮比较

先生成同阶共线基线，无冲突就返回，所以自动贝塞尔不一定弯曲。基线受阻时，把当前最优路线碰到的节点及标签投影到弦方向与法线方向，取两侧 Q；后续轮合并已发现的冲突障碍，避免只绕开第一个节点。

首轮绕行间距为最近公共布局作用域 `max(nodeGap, rankGap, 1) / 2`，第二轮翻倍。每侧取三个 τ，三次另有四组方向，因此二次最多提出 **13 条**、三次最多 **49 条**候选，包括基线、无效和重复提案。下图展示一次扩展的顺序；基线无冲突时跳过扩展，最多执行两轮。

<ComponentPreview files="flow-bezier-search" hideCode type="flow" size="md" />

下面把同一组节点画三次，观察路线变化：基线穿过 A、B，因此先用 A、B 的包络生成两侧经过点；上侧候选虽然绕开 A、B，却碰到 C，下侧候选则同时避开三个节点。虚框是生成候选的参考范围，不是用来判定整条曲线碰撞的大盒子。

<ComponentPreview files="flow-bezier-obstacles" hideCode type="illustration" size="xxxl" />

图中只画 τ = 1/2 的两条二次代表候选；实现仍会完整比较本轮的全部候选。这里第一轮已有无冲突路线，所以不会因为另一条候选碰到 C 就强制继续。只有**本轮最优路线仍有冲突**时，才合并它新碰到的障碍、增大间距并进入第二轮。节点位置始终不变，也不是每遇到一个节点就追加一段曲线。

每条候选复用上一节的真实极值 AABB 和子曲线细分，**最多沿同一分支二分 8 次**，不把子曲线替换成直线。碰撞检测与长度估计是两件事：长度使用 32 个等参数区间近似，不能把它理解成碰撞只采样 32 个点。

同一轮完整比较后，按 **节点冲突数 → 标签冲突对数 → 近似长度 → 最大法向偏移 → 固定提案顺序** 选优。节点与标签都无冲突时结束；否则进入下一轮。它只选已评估集合中的最佳，不承诺未生成的路线更差，也不使用 bend 的参数跨度比较不同曲线。关系仍按 Source 顺序求解，共享此前自动路线和全部非自动路线的标签预留。

### 三次曲线如何用两个控制点绕行

三次仍从冲突包络生成 Q，但一个经过点不足以唯一确定两个控制点。因此先选择首尾切线方向，再求两个控制臂的长度，使曲线在指定 τ 经过 Q。下图沿用 A、B、C 场景，固定下侧 Q 与 τ = 1/2；第一幅标出两个控制点，第二幅比较不同方向组合。

<ComponentPreview files="flow-cubic-avoidance" hideCode type="illustration" size="xxl" />

第一幅蓝线采用相对弦方向的 `(30°, −30°)` 组合并镜像到下侧。`P₀→C₁` 决定出发方向，`C₂→P₁` 决定到达方向；灰色控制折线不是实际路径。第二幅橙线换成 `(60°, −60°)`，仍经过同一个 Q，但端点附近弯曲不同；上侧红线则碰到 C，不能只因为通过了包络外的 Q 就判为安全。

实现还会尝试 `(60°, 30°)`、`(−30°, −60°)` 两组非对称方向，以及另外两个 τ。只有控制臂为正、有限且不超过四倍弦长的候选才进入碰撞评分；图中只展示其中三条代表曲线。每轮最多 `两侧 × 三个 τ × 四组方向 = 24` 个提案，两轮加基线最多 49 个，仍按节点、标签、长度、偏移的顺序择优，不是逐个节点分别设置一个控制点。

### 参考路线与最终连接分开理解

显式冲突发出 `FlowBezierObstacleConflict`，自动结果仍冲突则发出 `FlowBezierSearchExhausted`；两者都保留路线，不切换 bend 或 smooth。后者只表示有限搜索没有找到通过检测的路线，不表示不存在可行路线。自动模式端点中心重合、无法建立方向时，以 `FlowBezierRouteUnavailable` 失败。

**检测和 artifact 记录的是中心参考曲线。** Core 按节点真实边界重新确定曲线首尾并保留控制点，之后还处理箭头缩短、标签中断；最终曲线形状和标签位置可能变化。没有 warning 不等于最终像素安全，仍需检查实际绘图。

artifact 中端点、控制点、标签盒统一处于完整 allocation-local 坐标；`regions.drawing.origin` 记录 Flow 根原点的实际平移。从同一次编译结果复制控制点时先减去 origin，再填回 Relation.routing。drawing 包围盒左上角不能代替 origin，尤其是曲线向负坐标溢出时。

## 过点曲线保留作者指定的路线

smooth 的点是曲线必须经过的位置，不是贝塞尔控制点。图中的 S、P₁、P₂、P₃、T 构成有序点链：P₁ 从障碍 A 上方经过，P₂ 改变绕行方向，P₃ 从障碍 B 下方经过。蓝色样条穿过所有点，灰虚线只是点链参照。

<ComponentPreview files="flow-smooth-knots" hideCode type="illustration" size="xl" />

1. **绑定真实位置。** 布局确定全部节点矩形后，用与正式绘制相同的 Graph 元素查询 Target。节点形状的 anchor、连接面、变换与相对 cursor 由 Core 解析，不用矩形近似自定义形状的锚点。点列包含起点、全部中间点和自动追加的终点。
2. **在相邻点之间插值。** Core 复用 centripetal Catmull–Rom 算法生成连续三次贝塞尔段；`tension` 缩放控制臂，经过点不动。合法重复点保留。最后的隐式节点终点沿入射方向接到真实边界，再由 Core 缩短箭头。
3. **检查生成的曲线。** 每个三次段先比较包围盒，再对相交部分最多二分 8 层，用子曲线 AABB 判断接触区间。跨段连续区间合并后，只豁免端点处的连续连接区间；离开端点后重新穿回仍被检测。相关祖先 Group 外壳按既有规则豁免。

发现冲突时发出 `FlowSmoothObstacleConflict`，保留原点列和倍率，不搜索新点、不自动增删点。安全点链不能保证样条安全；连接边界后的形状与标签仍须检查。K 个中间点、N 个障碍的检测上界是 O((K + 1) × N × 2⁸)，包围盒剪枝通常提前终止。这是工作量上界，不是耗时基准。

自定义布局通过 `context.resolveRoutePoints` 使用同一查询能力。回调返回后，Flow 用最终节点位置再次查询，核对全部点数、顺序、坐标和 tension，拒绝替换作者路线。标签按实际三次曲线及切线预留；artifact 只保存平移后的数值点列和倍率，不重复保存控制点。

## 按布局绘图并保存结果

位置和连线确定后，Flow 会把它们交给 Graph 来生成图形：实体绘制成节点，Group 绘制成分组，Layout 用 Scope 保留排列和层级。连线也按布局结果绘制，原来的包含关系保持不变。

同时，Flow 会把图元的位置、大小和连线上的点保存在 `FlowDiagramArtifact` 中，供调用方查询。这个结果记录布局信息，文字和样式仍来自输入声明。

布局关系输出统一使用 `{ route, labelBounds? }`。`route.kind` 区分直线、三类轴对齐路线、bend 与二次/三次贝塞尔；bend 只保存两个中心参考端点和一个有效参数族，不保存重复的控制点或采样点。完整标签通过 `labelSize` 与 `labelPlacement` 进入布局，空几何投影仍使用 Core 默认；倾斜标签预留盒是旋转文字盒的 AABB。

Graph/Core 随后负责端点边界、箭头缩短、标签断线与最终绘制包络。artifact 的 route 和预留盒只平移坐标，不是最终裁剪后的描边或 glyph bounds。
