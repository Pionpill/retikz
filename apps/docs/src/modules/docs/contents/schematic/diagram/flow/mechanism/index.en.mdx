This page assumes [Basic usage](/schematic/diagram/flow/usage) and follows one Flow compilation. Input is a serializable Source plus the host's Definitions and Theme. Output is a renderable Diagram Scene, a `FlowDiagramArtifact`, and spatial handles. A failure in any stage stops this compilation without delivering partial geometry.

## Overall flow

| Stage                    | Input                                            | Output passed onward                                               |
| ------------------------ | ------------------------------------------------ | ------------------------------------------------------------------ |
| Resolve                  | Source, Definitions, Theme                       | Effective Entity, Group, Layout, and Relation semantics            |
| Measure                  | Resolved semantics and Graph appearance          | Element sizes, scopes, relation-label sizes, and `FlowLayoutInput` |
| Layout and validate      | `FlowLayoutInput` and selected Layout Definition | Validated bounds and routes detached from callback objects         |
| Materialize and assemble | The same validated geometry                      | Graph primitives and `FlowDiagramArtifact`                         |

Source contains declarations and references; measurement produces layout input, and the Definition's geometry passes validation before materialization and result assembly. The figure below shows this path, and the following sections trace a “receive → verify” example as its data changes.

## Semantic resolution establishes containment

Flow input is declarative: describe what the diagram contains, how elements connect, which container owns each element, and how they should be laid out. The compact “receive → verify” example places two Entities in a linear Layout inside a visible Group. This code tree shows Source fields and entries. Each `children` list stores id references rather than nested Entity objects.

```text
Flow Source
├── namespace: "diagram", type: "flow"
├── entities
│   ├── { id: "receive", text: "Receive", role: "activity" }
│   └── { id: "verify", text: "Verify", role: "activity" }
├── groups
│   └── { id: "pipeline", children: ["steps"] }
├── layouts
│   └── { id: "steps", kind: "linear", direction: "right",
│         children: ["receive", "verify"] }
├── children: ["pipeline"]
└── relations
    └── { source: "receive", target: "verify" }
```

Each field has a distinct responsibility:

- `entities`: the Entity catalog, declaring text, role, and other content. Each Entity is declared once.
- `groups`: the visible Group catalog. Each entry references direct members through `children` and may configure its shell, caption, and local automatic layout.
- `layouts`: the fixed-placement catalog. Each entry references direct members through `children`; `kind` and related settings select linear or grid placement.
- Root `children`: the diagram's direct members and sibling order. Catalog declaration order does not replace containment references.
- `relations`: the root relation catalog. `source` and `target` reference Entities or Groups without establishing containment.

This separation serves two purposes:

1. Humans and LLMs declare content, connections, containment, and layout with clear responsibilities, without calculating coordinates or writing drawing steps.
2. Declaration stays separate from resolution. Authors still express containment through ids, but do not construct the internal nested tree or repeat Entity objects inside containers. The implementation looks up references, validates structure, and builds recursive objects. React component nesting also normalizes to this flat Source first.

The resolver registers all three catalogs by id, then checks that `children` references exist, every entry has exactly one parent, and no entry contains itself, forms a containment cycle, or remains uncontained. It then walks root `children` recursively and replaces id references with internal `elements` arrays: `pipeline` contains `steps`, and `steps` contains the two Entities. Relation endpoints are validated separately; relations remain in an ordered root list. Graph Definitions and Theme resolve the semantics and appearance needed by measurement.

The figure compares containment fields, the resolved nested structure, and the final drawing for the same input. The first two blocks are field excerpts; Source keys denote field paths. Text, style, and other fields unrelated to containment are omitted. Their array records represent the same elements throughout.

## Measurement turns drawing objects into layout input

Flow first measures what layout needs: how large each drawing object is, how much space to leave around it and inside groups, and how much room the text on each connection needs. It then passes this information, along with layout and connection settings, to the layout stage.

This information is stored in `FlowLayoutInput`. The layout stage can then arrange objects and route connections without measuring them again. For example, if the text in “verify” becomes longer, Flow calculates the width it needs first, so layout can leave enough room for it.

## Layout determines positions and connections

Using the measurements from the previous stage, the layout callback places each object and decides where connections go. It returns each object's position and size (`bounds`), plus a reference `route` for each connection: straight and axis-aligned routes store point chains, while bend stores two reference endpoints and its active curve parameters. It can also reserve room for text on a connection.

For each fixed Layout specified in the input, the callback first uses `context.placeLayout` to calculate its internal arrangement, then places it in the whole diagram. Each fixed Layout is calculated once; moving it as a whole preserves the relative positions of its objects.

Flow checks that the result is complete, Entity sizes match their measurements, groups contain their contents, and objects, connections, and text satisfy the output contract. Contract errors stop compilation; a bend crossing a node keeps its route and emits a warning, as explained in [Automatic avoidance for bend curves](#automatic-avoidance-for-bend-curves).

## Automatic orthogonal avoidance

First check endpoint alignment: horizontally or vertically aligned endpoints connect directly, skipping avoidance and conflict warnings. Other forward routes use source-to-target facing boundary gaps at `0.5 / 0.25 / 0.75`, falling back to center intervals when boundaries overlap. Horizontal layouts move the middle vertical segment; vertical layouts move the middle horizontal segment. Feedback retains its outer lane.

Each candidate has at most three axis-aligned segments. Intersect them directly with obstacle rectangles, without curve subdivision. Merge consecutive contact intervals across corners using path distance, exempting only continuous source egress and target ingress; reentry still conflicts. Compare node count, penetration length and label conflicts, preserving midpoint-first order on ties. With N obstacles and L labels, candidate scoring is O(3 × 3 × (N + L)); it does not recursively add candidates.

Core rounds corners during drawing; scoring uses the reference polyline. Exhausted searches retain the best route with a warning, and explicit fractions are checked without replacement. Try the [orthogonal playground](/schematic/diagram/flow/extended#orthogonal-avoidance).

The red dashed candidate crosses the obstacle; the blue solid candidate is selected. The gray dashed candidate is also clear but comes later in the candidate order. Labels are omitted, and paths show the reference polylines before corner rounding.

## Automatic avoidance for bend curves

The built-in layered layout places nodes before selecting from a bounded set of bend routes. Automatic avoidance prioritizes node conflicts, then labels; it neither moves nodes nor guarantees a globally collision-free result.

### Bounded candidates are ranked by priority

With no authored or inherited angle, it compares `30° / 45° / 60°`; with no direction, it compares both sides, giving at most six candidates. An explicit or inherited side limits selection to that side; an explicit or inherited angle fixes the angle. When both are fixed, or tangent parameters are used, the author's configuration is used directly.

Candidates are selected in the following priority order, moving to the next criterion only on a tie:

1. **Fewer node conflicts:** prefer fewer intersected obstacle boxes, then a smaller total curve-parameter span inside those boxes. For example, if both `30°` curves cross a node but `45°` clears it, prefer `45°`.
2. **Fewer label conflicts:** when node scores tie, count conflicts between the curve and existing labels, and between its label and existing labels or node obstacle boxes. A larger angle wins if it has the same node score and fewer label conflicts.
3. **Smaller angle:** when both node and label scores tie, prefer `30° → 45° → 60°`. For example, if both `45°` and `60°` are clear, choose `45°`.
4. **Left side:** when scores and angles all tie, prefer left for a stable result.

Omitted angles remain omitted until layout, so automatic selection is not mistaken for an authored `30°` constraint.

The figure keeps both endpoints fixed and overlays six reference candidates. The middle node blocks both `30°` curves, and an existing label blocks left `45°`. Right `45°` and both `60°` curves are clear, so the smaller-angle preference selects right `45°`. Candidate angle annotations are explanatory guides and do not enter label scoring.

### Recursive subdivision excludes empty space around the curve

The check has three stages: **whole-curve AABB filtering → subcurve AABB checks → ordered candidate comparison**. An AABB is an axis-aligned bounding box. The same obstacles appear in each panel: the left `60°` curve excludes C in the broad phase; subdivision retains contact near A and excludes the empty space at B. Applying the same check to all six candidates selects right `30°` in this example without labels. Scores are compared in priority order, not combined into a weighted sum.

<ComponentPreview files="flow-bend-screening" hideCode type="illustration" size="lg" />

Node checks first compute an AABB from the whole curve's true x and y extrema, once per candidate, to exclude separate obstacle boxes. The test uses the entire obstacle box, not its center; edge contact and contact within numerical tolerance are retained. Remaining nodes undergo subcurve checks rather than checks of only the midpoint or control points. The broad phase still traverses obstacle boxes across all levels of the same Flow; no spatial index is built.

Refinement does not straighten the curve. Each step bisects the current parameter interval, preserves both exact subcurves, and computes each AABB from its x and y extrema:

1. **The AABB is separate from the obstacle box:** discard the interval without further subdivision.
2. **The AABB lies entirely inside the obstacle box:** retain the interval.
3. **The boxes still overlap without containment:** bisect again. At depth `8`, or when both AABB dimensions are at most `0.25` user units, conservatively retain any unresolved interval.

The next figure expands the curve check used in the first two stages, showing the whole curve, halves, and depth 3. Orange dashed boxes still overlap an obstacle; gray dotted boxes can be discarded. Execution only refines overlapping branches; all boxes at each illustrated depth are shown for comparison.

<ComponentPreview files="flow-bend-subdivision" hideCode type="illustration" size="lg" />

Subdivision excludes large empty regions inside the bend, but empty corners of terminal boxes can still cause conservative false positives. This is **parameter bisection, not equal-arc-length sampling or a final line-segment intersection test**. Adjacent retained intervals are merged, legal endpoint departure and arrival are exempted, and the score counts conflicting nodes followed by the total parameter span `Σ(t_end − t_start)`. That span is not physical intersection length. Nodes still use rectangular obstacle boxes rather than shape contours.

### Sequential processing and conflict warnings

Leaf margins contribute to obstacle boxes. Relevant ancestor Group shells are not solid obstacles. Endpoint nodes exempt only continuous legal departure and arrival; re-entering after departure still counts as a conflict.

Relations are processed in Source order. Label comparisons include previously selected automatic routes and all non-automatic routes, excluding automatic routes still awaiting selection. The result is repeatable, but does not jointly optimize all relations.

A unique best node candidate is returned directly. When labels need comparison, the first zero-conflict candidate in smaller-angle, left-side preference order ends the search. Unlabeled parallel relations may choose identical routes.

Edge overlaps and crossings are neither checked nor scored for two main reasons:

1. **High computational cost:** each candidate curve would need comparison against other paths, with multiple segment-intersection checks after curve subdivision. This cost becomes more pronounced as the number of elements and connections grows, so it is excluded from automatic route selection.
2. **Crossings are common:** intersecting connections are normal in flowcharts, and an intersection does not necessarily obscure a node or label. Detecting and scoring crossings solely to reduce their number does not justify the additional cost here; automatic avoidance prioritizes node and label readability.

The following flow follows each relation: filter, refine and score every allowed candidate, then compare labels only when the best node scores tie.

<ComponentPreview files="flow-bend-routing" hideCode type="flow" size="md" />

Search stays within the allowed candidates without moving nodes or searching for arbitrary control points. If all candidates are obstructed, the best-scoring route is still selected. A shared post-layout check also covers explicitly configured bends and custom providers. Node crossings emit a `FlowBendObstacleConflict` warning at the relation's Source path while preserving the drawing, without switching route kinds.

## Automatic Bezier avoidance

Bezier follows the same generate–check–compare process as bend, but derives controls from obstacles to allow asymmetric detours. `curve` is quadratic and `cubic` is cubic. Omitting all controls requests automatic routing; complete controls preserve the authored geometry.

### Derive controls from a point on the curve

- **P₀, P₁**: reference endpoints supplied by layout: resolved anchor positions when present, otherwise node centers.
- **Q**: a desired point on the curve, placed on either side of conflicting obstacles.
- **τ**: the parameter at Q, chosen from `1/4, 1/2, 3/4`; it is not an arc-length fraction.
- **C / C₁, C₂**: controls that shape the curve; the curve usually does not pass through them.

The figure fixes τ = 1/2. The blue curve passes Q above the obstacle; orange C lies farther away. The gray control polygon only explains how the shape is controlled.

<ComponentPreview files="flow-bezier-controls" hideCode type="illustration" size="xxl" />

A quadratic uses `C = [Q − (1−τ)²P₀ − τ²P₁] / [2(1−τ)τ]`. A cubic first chooses endpoint directions, then solves the arms a, b in `C₁ = P₀ + a d₀`, `C₂ = P₁ − b d₁` so that the curve passes Q at τ. Four direction profiles are tried per Q/τ. Singular equations, nonpositive arms, or arms longer than four chord lengths are rejected. A quadratic control must also stay within four chord lengths of both endpoints. These limits only filter automatic candidates, not valid explicit controls.

### Compare bounded candidates in waves

Start with collinear controls of the requested degree and return immediately if clear; an automatic Bezier need not visibly bend. When blocked, project conflicting nodes and labels onto the chord and its normal to choose Q on either side. Later waves accumulate discovered blockers rather than only avoiding the first obstacle.

The first clearance is `max(nodeGap, rankGap, 1) / 2` from the nearest common layout scope; the second doubles it. Two sides, three τ values and four cubic direction profiles give at most **13 quadratic** or **49 cubic** proposals, including the baseline, invalid proposals and duplicates. The figure shows one expansion; a clear baseline skips expansion, and there are at most two waves.

<ComponentPreview files="flow-bezier-search" hideCode type="flow" size="md" />

The same nodes appear three times below. The baseline crosses A and B, so their envelope supplies waypoints on both sides. The upper candidate clears A/B but hits C; the lower candidate clears all three. The dotted envelope guides candidate generation; it is not a single box used to decide whether the entire curve collides.

<ComponentPreview files="flow-bezier-obstacles" hideCode type="illustration" size="xxxl" />

Only two representative quadratic candidates at τ = 1/2 are drawn; the implementation compares the whole wave. A clear route already exists here, so another candidate hitting C does not force a second wave. Only when **the best route still conflicts** are its new blockers merged and clearance increased for wave two. Nodes stay fixed, and encountering another node does not append another curve segment.

Each candidate reuses the true-extrema AABB and subcurve checks above, with **at most 8 bisections along a branch**. Subcurves are not replaced by line segments. Length estimation is separate: 32 equal-parameter intervals approximate length, not collision detection at only 32 points.

Finish evaluating a whole wave, then compare **node conflicts → label conflict pairs → approximate length → maximum normal offset → fixed proposal order**. Stop when both conflict counts are zero; otherwise expand again. The winner is best only among evaluated candidates. Bend parameter spans are not used to compare different curves. Relations still follow Source order, sharing labels of earlier automatic routes and all nonautomatic routes.

### How two cubic controls guide avoidance

Cubic routing generates Q from the same blocker envelope, but one waypoint cannot uniquely determine two controls. It first chooses endpoint tangent directions, then solves both arm lengths so the curve passes through Q at τ. The same A/B/C scene below fixes the lower Q and τ = 1/2: the first panel exposes both controls; the second compares direction profiles.

<ComponentPreview files="flow-cubic-avoidance" hideCode type="illustration" size="xxl" />

The first blue curve uses the chord-relative `(30°, −30°)` profile mirrored to the lower side. `P₀→C₁` sets the departure direction and `C₂→P₁` the arrival direction; the dotted control polygon is not the route. Orange uses `(60°, −60°)`: it reaches the same Q with different bending near the endpoints. The red upper candidate hits C, showing why a waypoint outside the envelope does not itself prove safety.

The implementation also tries asymmetric `(60°, 30°)` and `(−30°, −60°)` profiles and two other τ values. Only finite positive arms no longer than four chord lengths proceed to collision scoring; the figure shows three representative curves. Each wave proposes at most `two sides × three τ values × four profiles = 24` candidates, totaling 49 with two waves and the baseline. Node conflicts, label conflicts, length and offset still determine the ranking; controls are not assigned one per obstacle.

### Separate reference routes from final connections

Explicit conflicts emit `FlowBezierObstacleConflict`; an automatic result with conflicts emits `FlowBezierSearchExhausted`. Both retain the route without switching to bend or smooth. Exhaustion means bounded search did not find a clear route, not that none exists. Automatic coincident reference endpoints cannot define a direction and fail with `FlowBezierRouteUnavailable`.

**Checks and artifacts describe the reference curve.** Resolved anchors supply exact endpoints; otherwise Core recomputes endpoints on real node boundaries while preserving controls, then handles arrow shortening and label interruption. The final shape and label position can change. No warning is not a guarantee of pixel-level safety; inspect the rendered drawing.

Artifact endpoints, controls and label boxes use full allocation-local coordinates. `regions.drawing.origin` records the actual translation of the Flow root origin. Subtract it from controls in the same compilation artifact before copying them into Relation.routing. The drawing bounds' top-left cannot replace origin, especially with negative curve overflow.

## Through-point curves preserve the authored route

Smooth points are positions the curve passes through, not Bezier controls. S, P₁, P₂, P₃ and T form an ordered chain: P₁ passes above obstacle A, P₂ changes direction and P₃ passes below obstacle B. The blue spline passes through every knot; the dotted chain is only a reference.

<ComponentPreview files="flow-smooth-knots" hideCode type="illustration" size="xl" />

1. **Bind real positions.** After layout determines all bounds, Core resolves Targets against the same Graph elements used for drawing. Shape anchors, boundaries, transforms and relative cursors use the real resolver, not rectangle approximations. The chain includes source, intermediate knots and the appended target.
2. **Interpolate between knots.** Core uses centripetal Catmull–Rom to generate cubic Bezier segments. `tension` scales tangent arms without moving knots. Valid repeats remain. The final implicit node target connects to its real boundary along the incoming direction; Core then shortens arrows.
3. **Check the generated curve.** Each cubic starts with a bounds test, then subdivides overlapping portions up to 8 levels using subcurve AABBs. Continuous contact intervals merge across segments. Only continuous endpoint connection intervals are exempt; leaving and reentering an endpoint still counts. Relevant ancestor Group shells follow the existing exemption rules.

A conflict produces `FlowSmoothObstacleConflict`, preserving the points and multiplier without searching, adding or removing knots. A safe knot chain does not guarantee a safe spline; inspect boundary-adjusted geometry and labels. For K intermediate knots and N obstacles the check is bounded by O((K + 1) × N × 2⁸), with bounds pruning usually terminating earlier. This is a work bound, not a timing benchmark.

Custom layouts use `context.resolveRoutePoints`. After the callback returns, Flow queries with final bounds again and verifies every knot, its order and tension. Labels sample actual cubics and tangents. Artifacts store translated numeric knots and tension without duplicating controls.

## Endpoint allocation

Layout input normalizes each relation source/target into an object with id, effective overlap and optional side or anchor. The endpointPlacement capability is checked before the callback. Output retains only `{ id, anchor? }` and never writes back to Source.

The built-in layout collects both ends by element, fixes explicit anchors, then sorts each separate endpoint and one shared allow slot per side. Fractions use i/(n+1) with full precision. Opposite node centers determine tangential order; ties retain relation input order. Automatic slots conflicting with fixed points try the nearest gap midpoint; coincident fixed points requiring separation fail.

The rectangles below share the same side length. Compare one, two and three separate positions without fixed anchors. Blue dots mark connection points; fractions on the left side increase from 0 at the top to 1 at the bottom.

<ComponentPreview files="flow-endpoint-allocation" hideCode type="illustration" size="lg" />

The two-position labels display 0.33 and 0.67, while geometry uses 1/3 and 2/3. Positions count slots: multiple automatic allow endpoints occupy one shared slot.

The context.resolveEndpoint query resolves real Core boundaries from target and elements, rather than replacing shapes with layout rectangles. Routing, Graph materialization and artifacts share the assigned result. Custom layouts must satisfy the same side, fixed-anchor and separation constraints. Separation only guarantees distinct connection points and does not measure arrow sizes.

## Draw from the layout and save the results

Once positions and connections are determined, Flow passes them to Graph to build the drawing: Entities become nodes, Groups become visible groups, and Layouts use Scopes to preserve their arrangement and hierarchy. Connections follow the layout results, and containment stays the same.

Flow also stores object positions, sizes, and connection points in `FlowDiagramArtifact` for callers to query. This result records layout information; text and styles still come from the input declarations.
