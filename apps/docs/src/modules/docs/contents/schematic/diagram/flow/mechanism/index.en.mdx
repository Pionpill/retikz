This page assumes [Basic usage](/schematic/diagram/flow/usage) and follows one Flow compilation. Input is a serializable Source plus the host's Definitions and Theme. Output is a renderable Diagram Scene, a `FlowDiagramArtifact`, and spatial handles. A failure in any stage stops this compilation without delivering partial geometry.

## Overall flow

| Stage                    | Input                                            | Output passed onward                                               |
| ------------------------ | ------------------------------------------------ | ------------------------------------------------------------------ |
| Resolve                  | Source, Definitions, Theme                       | Effective Entity, Group, Layout, and Relation semantics            |
| Measure                  | Resolved semantics and Graph appearance          | Element sizes, scopes, relation-label sizes, and `FlowLayoutInput` |
| Layout and validate      | `FlowLayoutInput` and selected Layout Definition | Validated bounds and routes detached from callback objects         |
| Materialize and assemble | The same validated geometry                      | Graph primitives and `FlowDiagramArtifact`                         |

Source contains declarations and references; measurement produces layout input, and the Definition's geometry passes validation before materialization and result assembly. The figure below shows this path, and the following sections trace a “receive → verify” example as its data changes.

## Semantic resolution establishes containment

Flow input is declarative: describe what the diagram contains, how elements connect, which container owns each element, and how they should be laid out. The compact “receive → verify” example places two Entities in a linear Layout inside a visible Group. This code tree shows Source fields and entries. Each `children` list stores id references rather than nested Entity objects.

```text
Flow Source
├── namespace: "diagram", type: "flow"
├── entities
│   ├── { id: "receive", text: "Receive", role: "activity" }
│   └── { id: "verify", text: "Verify", role: "activity" }
├── groups
│   └── { id: "pipeline", children: ["steps"] }
├── layouts
│   └── { id: "steps", kind: "linear", direction: "right",
│         children: ["receive", "verify"] }
├── children: ["pipeline"]
└── relations
    └── { source: "receive", target: "verify" }
```

Each field has a distinct responsibility:

- `entities`: the Entity catalog, declaring text, role, and other content. Each Entity is declared once.
- `groups`: the visible Group catalog. Each entry references direct members through `children` and may configure its shell, caption, and local automatic layout.
- `layouts`: the fixed-placement catalog. Each entry references direct members through `children`; `kind` and related settings select linear or grid placement.
- Root `children`: the diagram's direct members and sibling order. Catalog declaration order does not replace containment references.
- `relations`: the root relation catalog. `source` and `target` reference Entities or Groups without establishing containment.

This separation serves two purposes:

1. Humans and LLMs declare content, connections, containment, and layout with clear responsibilities, without calculating coordinates or writing drawing steps.
2. Declaration stays separate from resolution. Authors still express containment through ids, but do not construct the internal nested tree or repeat Entity objects inside containers. The implementation looks up references, validates structure, and builds recursive objects. React component nesting also normalizes to this flat Source first.

The resolver registers all three catalogs by id, then checks that `children` references exist, every entry has exactly one parent, and no entry contains itself, forms a containment cycle, or remains uncontained. It then walks root `children` recursively and replaces id references with internal `elements` arrays: `pipeline` contains `steps`, and `steps` contains the two Entities. Relation endpoints are validated separately; relations remain in an ordered root list. Graph Definitions and Theme resolve the semantics and appearance needed by measurement.

The figure compares containment fields, the resolved nested structure, and the final drawing for the same input. The first two blocks are field excerpts; Source keys denote field paths. Text, style, and other fields unrelated to containment are omitted. Their array records represent the same elements throughout.

## Measurement turns drawing objects into layout input

Flow first measures what layout needs: how large each drawing object is, how much space to leave around it and inside groups, and how much room the text on each connection needs. It then passes this information, along with layout and connection settings, to the layout stage.

This information is stored in `FlowLayoutInput`. The layout stage can then arrange objects and route connections without measuring them again. For example, if the text in “verify” becomes longer, Flow calculates the width it needs first, so layout can leave enough room for it.

## Layout determines positions and connections

Using the measurements from the previous stage, the layout callback places each object and decides where connections go. It returns each object's position and size (`bounds`), plus a reference `route` for each connection: straight and axis-aligned routes store point chains, while bend stores two reference endpoints and its active curve parameters. It can also reserve room for text on a connection.

For each fixed Layout specified in the input, the callback first uses `context.placeLayout` to calculate its internal arrangement, then places it in the whole diagram. Each fixed Layout is calculated once; moving it as a whole preserves the relative positions of its objects.

Flow checks that the result is complete, Entity sizes match their measurements, groups contain their contents, and objects, connections, and text satisfy the output contract. Contract errors stop compilation; a bend crossing a node keeps its route and emits a warning, as explained below.

### bend uses bounded candidates to avoid nodes and labels

The built-in layered layout places nodes before selecting bend routes. With no authored or inherited angle, it compares `30° / 45° / 60°`; with no direction, it compares both sides, giving at most six candidates. An explicit or inherited side limits selection to that side; an explicit or inherited angle fixes the angle. When both are fixed, or tangent parameters are used, the author's configuration is used directly.

Candidates are selected in the following priority order, moving to the next criterion only on a tie:

1. **Fewer node conflicts:** prefer fewer intersected obstacle boxes, then a smaller total curve-parameter span inside those boxes. For example, if both `30°` curves cross a node but `45°` clears it, prefer `45°`.
2. **Fewer label conflicts:** when node scores tie, count conflicts between the curve and existing labels, and between its label and existing labels or node obstacle boxes. A larger angle wins if it has the same node score and fewer label conflicts.
3. **Smaller angle:** when both node and label scores tie, prefer `30° → 45° → 60°`. For example, if both `45°` and `60°` are clear, choose `45°`.
4. **Left side:** when scores and angles all tie, prefer left for a stable result.

Omitted angles remain omitted until layout, so automatic selection is not mistaken for an authored `30°` constraint.

The figure keeps both endpoints fixed and overlays six reference candidates. The middle node blocks both `30°` curves, and an existing label blocks left `45°`. Right `45°` and both `60°` curves are clear, so the smaller-angle preference selects right `45°`. Candidate angle annotations are explanatory guides and do not enter label scoring.

<ComponentPreview files="flow-bend-candidates" hideCode type="illustration" size="lg" />

Edge overlaps and crossings are neither checked nor scored for two main reasons:

1. **High computational cost:** each candidate curve would need comparison against other paths, with multiple segment-intersection checks after curve subdivision. This cost becomes more pronounced as the number of elements and connections grows, so it is excluded from automatic route selection.
2. **Crossings are common:** intersecting connections are normal in flowcharts, and an intersection does not necessarily obscure a node or label. Detecting and scoring crossings solely to reduce their number does not justify the additional cost here; automatic avoidance prioritizes node and label readability.

Unlabeled parallel relations may consequently choose identical routes. A unique best node candidate is returned directly. When labels need comparison, the first zero-conflict candidate in preference order ends the search without changing the node-first, label-second result.

Relations are processed in Source order. Label comparisons include previously selected automatic routes and all non-automatic routes, excluding automatic routes still awaiting selection. The result is repeatable, but does not jointly optimize all relations.

Node checks first compute one bounding rectangle per candidate curve using Math's curve extrema. Nodes whose obstacle boxes do not intersect that rectangle are excluded. The test uses the entire obstacle box, not its center; edge contact and contact within numerical tolerance are retained. Rectangle overlap only calls for further checking and is not itself a conflict.

Remaining nodes undergo continuous curve checks with a conservative geometric approximation, rather than checks of only the midpoint or control points. Leaf margins contribute to obstacle boxes. Relevant ancestor Group shells are not solid obstacles. Endpoints exempt only continuous legal departure and arrival; re-entering after departure still counts as a conflict. Rectangle filtering still traverses obstacle boxes across all levels of the same Flow, but computes the candidate rectangle once and keeps distant nodes out of further curve checks. No spatial index is built.

The flow below follows automatic route selection. Rectangle filtering and continuous checks run separately for each allowed candidate. Labels are compared only when the best node scores tie.

Rectangle filtering reduces the objects checked while preserving node priority, secondary label scoring, and tie preferences. A unique best node candidate is delivered directly.

Search stays within the allowed candidates without moving nodes or searching for arbitrary control points. If all candidates are obstructed, the best-scoring route is still selected. A shared post-layout check also covers explicitly configured bends and custom providers. Node crossings emit a `FlowBendObstacleConflict` warning at the relation's Source path while preserving the drawing, without switching route kinds.

## Draw from the layout and save the results

Once positions and connections are determined, Flow passes them to Graph to build the drawing: Entities become nodes, Groups become visible groups, and Layouts use Scopes to preserve their arrangement and hierarchy. Connections follow the layout results, and containment stays the same.

Flow also stores object positions, sizes, and connection points in `FlowDiagramArtifact` for callers to query. This result records layout information; text and styles still come from the input declarations.

Layout relations return `{ route, labelBounds? }`. The discriminated route records straight or axis-aligned points, or two bend reference centers and one active parameter family; it does not duplicate controls or samples. Full labels enter layout as `labelSize` plus `labelPlacement`, including an empty projection for Core defaults. Sloped reservations use the rotated measured rectangle AABB.

Graph/Core then applies boundary clipping, arrow shortening, label interruption and final drawing bounds. Artifact reference routes and reservations translate coordinates only; they are not final clipped strokes or glyph bounds.
