---
title: Versioning
description: retikz follows Semantic Versioning with pre-release channels. 0.x is loose, 1.x onwards is strict.
---

retikz follows Semantic Versioning 2.0.0: versions read as `MAJOR.MINOR.PATCH`, optionally tagged `-alpha.x` / `-beta.x` / `-rc.x`.

The current repository version is `0.4.0`, with all six kernel packages moving from `0.4.0-rc.1` to the stable channel in lockstep. v0.4 converges the shape-aware boundary `fit` / `gap` contract and fixes Canvas shadow opacity; no public capability or breaking change was added after the RC. Compatible fixes now ship as `0.4.x`, while new mechanisms move to the next minor line.

## Segment meanings

| Segment | Bumped when                        | Upgrade guidance         |
| ------- | ---------------------------------- | ------------------------ |
| MAJOR   | Backward-incompatible API change   | Read the migration guide |
| MINOR   | Backward-compatible new capability | Upgrade freely           |
| PATCH   | Backward-compatible bug fix        | Upgrade freely           |

Kernel packages (`@retikz/math`, `@retikz/core`, `@retikz/render`, `@retikz/react`, `@retikz/vanilla`, and `@retikz/tex`) normally share the same version and **ship together**. Unless release notes say otherwise, users should not need to upgrade one without the others.

## 0.x vs 1.x

| Phase         | API stability                 | Breaking change frequency |
| ------------- | ----------------------------- | ------------------------- |
| `0.x`         | Unstable, alpha / beta polish | May land in a MINOR       |
| `1.x` onwards | Strict SemVer                 | Only in MAJOR             |

Breaking changes before `1.0.0` **do not force a MAJOR bump**, but the changelog and release notes will call them out explicitly.

## Pre-release channels

| Channel | Format          | Main content                                                                                                         | Main driver                                      | Suitable for             |
| ------- | --------------- | -------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------ | ------------------------ |
| alpha   | `0.4.0-alpha.x` | New features / new IR fields / API reshaping (schema in flux, IR unstable)                                           | **Human-directed + AI-authored and implemented** | Exploration / feedback   |
| beta    | `0.4.0-beta.x`  | Performance / readability / refactoring / test hardening / docs completion; final breaking renames are still allowed | **Human-led optimization and refactoring**       | Integration testing      |
| rc      | `0.4.0-rc.x`    | Public API frozen; compatible bug fixes, docs, installation acceptance, and release notes only                       | Human-led                                        | Pre-production rehearsal |
| stable  | `0.4.0`         | Under SemVer; normal PATCH / MINOR / MAJOR cadence                                                                   | —                                                | Production               |

Channels move forward only: alpha → beta → rc → stable. There's no rollback.

During alpha, retikz uses a **human-directed, AI-authored and implemented** workflow. Humans provide ideas, define goals and constraints, and confirm key directions. AI writes the ADR, develops the design, and carries out implementation, testing, and documentation. Humans guide the work through discussion and review rather than authoring the ADR. Full workflow details: [AI-assisted development](/about/developer/ai-assisted-development).

beta inverts this — schema is frozen, the API stops growing, and AI's freedom narrows; this phase emphasizes human review of alpha-era implementation, performance tuning, refactoring, test hardening, and documentation completion, laying the foundation for rc / stable.

rc narrows the work again: public APIs no longer break, and npm uses the `next` dist-tag. Installation acceptance uses `pnpm add @retikz/react@next react react-dom`; any issue that requires a breaking compatibility fix should stop the rc and return to a human version decision.

## Deprecation flow

| Step            | When              | Marker                                        |
| --------------- | ----------------- | --------------------------------------------- |
| Mark deprecated | Immediately       | `@deprecated` type, `console.warn` at runtime |
| Grace period    | At least 2 MINORs | Changelog points to the replacement           |
| Removal         | Next MAJOR        | Listed under Removed                          |

The deprecation flow is not enforced during `0.x`; it kicks in once `1.0` ships.
