This guide is for developers reading, extending, or contributing to retikz. Start with published packages and public entry points to establish boundaries; follow an implementation directory only when you need to change that capability.

This mirrors the group boundaries in the [roadmap](/about/releases/roadmap): Kernel supplies the foundation, while Library supplies cross-domain reuse. Schematic and Viz own their domain semantics. `*-vanilla` packages assemble authoring inputs; `*-react` packages bridge JSX and host lifecycles. Neither should rebuild a domain package's schema, resolution, or compile semantics.

## Vertical extension packages

When a domain needs an extensible capability, the problem is not merely supplying built-in implementations. Authors, built-ins, and compilation consumers must collaborate through one contract. Otherwise, every new capability adds another branch to schemas, built-ins, user configuration, and compilation, and the extension boundary gradually disappears.

define-registry reduces that vertical path to `Definition → registry → resolve → compile`. `defineXxx()` lets authors declare a capability as a stable `XxxDefinition`; providers merge built-ins and user definitions into one registry; resolve performs contextual lookup, defaults, and diagnostics; compile only schedules and consumes the determined result. The benefits are a shared path for built-ins and custom definitions, centralized fail-loud duplicate-key diagnostics, no copied built-in allowlists downstream, and no parallel compile path for extensions.

### Core as an example

Core is the base owner of this mechanism. It places persistent models, author contracts, built-in implementations, domain completion, and Scene orchestration in adjacent layers with one-way dependencies:

```text
core/src/
  shared/                 Cross-capability pure vocabulary and helpers
  schemas/<domain>/       Source IR Zod schemas and IRXxx types
  contract/<capability>/
    types.ts              XxxDefinition and author-facing contracts
    define.ts             defineXxx() entry point
  providers/<capability>/
    <builtin>.ts          One built-in implementation
    definitions.ts        BUILTIN_XXXS collection
    registry.ts           Built-in/user merge and duplicate diagnostics
  resolve/<domain>/       IR + context -> Canonical / Resolution
  compile/                Context creation; resolve, lower, layout, emit Scene
```

The important point is not any one drawing primitive, but each layer's role: `contract/` does not depend on built-in implementations, `providers/` does not depend on resolve or compile, `resolve/` owns lookup, defaults, and contextual errors, and `compile/` manages only context lifetime and scheduling.

| Extension package | Domain                                                         |
| ----------------- | -------------------------------------------------------------- |
| `@retikz/core`    | General drawing capabilities and compile extensions            |
| `@retikz/graph`   | Entity, relation, and theme definitions                        |
| `@retikz/data`    | Data selectors and statistics reducers                         |
| `@retikz/plot`    | Channels, scales, coordinates, marks, and transforms           |
| `@retikz/table`   | Table structures, presentations, formatters, and visual scales |

## Horizontal extension packages

When a package offers several finished capabilities in one family, the problem is how to share its domain model and processing pipeline without piling every implementation into one directory or the package root. A horizontal extension uses one internal shared owner for common contracts and logic, then separates peer subdomains by family or finished capability. Each subdomain owns only its differences; shared parts are not copied.

This organization lets a new sub-capability evolve without changing its peers, and lets consumers import only the stable subpath they need. The package root exposes genuinely shared public capabilities, while the internal shared owner is not a package-external dependency. That preserves family consistency while separating the API surface from implementation detail.

### Chart as an example

In `@retikz/chart`, `_chart/` is the internal owner shared by every chart, while `point/` is a public domain organized by chart family. A point chart implements its own recipe, mark, encoding, and provider while reusing `_chart/` Source, theme, registry, and resolution capabilities.

```text
chart/src/
  _chart/                 Internal owner shared by all Charts
    schemas/              Chart Source, encoding, theme, presentation
    contract/             Recipe, mark, locator, theme contracts
    providers/            Definitions, themes, registry, selection
    resolve/              Encoding, mark, theme, presentation -> Plot
  point/                  Public Point-family domain
    shared/               Encoding, mark, recipe shared by point charts
    scatter/              One chart's schema, provider, recipe, mark
    bubble/               Same structure
    connected-scatter/    Same structure
    ranged-dot/           Same structure
    regression/           Same structure
    strip/                Same structure
  index.ts                Package-root public entry
```

Consumers import only from entries declared in `package.json`: `@retikz/chart` for shared Chart APIs, `@retikz/chart/point` for the Point family, or a concrete chart subpath such as `@retikz/chart/point/scatter`. Do not deep-import `_chart/`, `schema.ts`, or other implementation files: they are not stable package contracts.

| Extension package | Shared owner and public subdomain                                                                        |
| ----------------- | -------------------------------------------------------------------------------------------------------- |
| `@retikz/diagram` | `_diagram/` shares diagram capability; `./flow` exposes the Flow subdomain                               |
| `@retikz/chart`   | `_chart/` shares chart capability; `./point` and concrete point-chart subpaths support on-demand imports |

## API adapter packages

Domain packages own schemas, definitions, resolution, and compile semantics. API adapter packages do not split domain capabilities again; they connect an authoring style or host environment to existing domain packages. In Kernel, `@retikz/vanilla` is the core layer for every API package: it integrates public domain capabilities, assembles author input into Source IR, and owns shared runtime processing, incremental execution, and performance optimizations.

`@retikz/react` is the only officially maintained framework adapter. It is a thin shell: it translates React JSX children, component declarations, and host lifecycles into author input that Vanilla can consume, preserving JSX composition benefits. The actual normalization, processing, and runtime execution remain in `@retikz/vanilla`; React does not rebuild a separate domain-logic path.

In general, `*-vanilla` and `*-react` packages paired with a domain package are API adapter packages. They extend authoring entries or host capabilities, rather than belonging to the vertical or horizontal extension classifications for domain packages.

## Ground rules

Before changing source, first decide which layer owns the change. The relevant skills are compact decision checklists, not a second implementation path.

| Question                                                                  | Read this skill first       | What it confirms                                                                                         |
| ------------------------------------------------------------------------- | --------------------------- | -------------------------------------------------------------------------------------------------------- |
| How should a new directory, file, type, function, or export be named?     | `standard-name`             | Accurate owner, phase names, barrels, and public symbols                                                 |
| Which layer owns a capability, and which dependency direction is allowed? | `standard-structure`        | The `shared → schemas → contract → providers → resolve → pipeline/compile` direction and boundaries      |
| How do I change persistent IR, Zod, defaults, or field descriptions?      | `standard-schema`           | Schema is the single source of truth; context rules do not belong in schemas                             |
| How do I add a capability shared by built-ins and third parties?          | `standard-contract`         | `XxxDefinition`, `defineXxx()`, and author-visible context boundaries                                    |
| How do I add a built-in definition or registry behavior?                  | `standard-providers`        | Built-ins and user definitions merge on one path; conflicts are diagnosed centrally                      |
| Where do defaults, inheritance, lookup, and domain completion belong?     | `standard-resolve`          | `IR + ResolveContext → Canonical / Resolution` is the only completion path                               |
| How do I change a Vanilla authoring API?                                  | `standard-normalize`        | Only `*-vanilla` packages assemble `InputXxx` into Source IR                                             |
| How do I change lowering, compile context, or Scene output?               | `standard-pipeline-compile` | Pipeline and compile orchestrate and consume; they do not repeat resolve defaults, lookup, or precedence |

All of these rules share three limits: public imports follow `package.json` `exports` and owner barrels; unknown JSON is validated exactly once at a schema or parse boundary; obsolete structures are removed rather than retained through aliases, fallbacks, or parallel paths.
