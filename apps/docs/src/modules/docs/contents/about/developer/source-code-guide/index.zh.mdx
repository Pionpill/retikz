## 纵向能力扩展包

当一个领域需要开放“可替换、可新增”的能力时，问题不只是提供几个内置实现：作者、内置实现和编译消费方必须围绕同一份契约协作。否则每增加一种能力，都要在 schema、内置分支、用户配置和编译器里各补一套判断，扩展会逐渐失去边界。

define-registry 将这条纵向路径收束为 `Definition → registry → resolve → compile`。`defineXxx()` 让作者按稳定的 `XxxDefinition` 声明能力；providers 将内置与用户定义合并到同一个 registry；resolve 在有上下文时完成 lookup、默认和诊断；compile 只调度并消费已确定的结果。它带来的好处是：内置与自定义同路、重复 key 可集中 fail-loud、下游不需要复制内置白名单，也不会因扩展而出现平行编译路径。

### 以 Core 为例

Core 是这条机制的基础 owner。它把持久化模型、作者契约、内置实现、领域确定化与 Scene 编排分别放在相邻但单向依赖的层中：

```text
core/src/
  shared/                 跨能力复用的纯词汇与工具
  schemas/<domain>/       Source IR 的 Zod schema 与 IRXxx 类型
  contract/<capability>/
    types.ts              XxxDefinition 与作者侧契约
    define.ts             defineXxx() 入口
  providers/<capability>/
    <builtin>.ts          单个内置实现
    definitions.ts        BUILTIN_XXXS 集合
    registry.ts           内置与用户定义合并、重复诊断
  resolve/<domain>/       IR + context -> Canonical / Resolution
  compile/                创建 context、调度 resolve、lower/layout/emit Scene
```

这里的关键不是某一种具体图元，而是层的职责：`contract/` 不依赖内置实现，`providers/` 不依赖 resolve 或 compile，`resolve/` 负责 lookup、默认和上下文错误，`compile/` 只管理上下文生命周期与调度。

| 扩展包          | 领域                                           |
| --------------- | ---------------------------------------------- |
| `@retikz/core`  | 通用绘图能力与编译扩展                         |
| `@retikz/graph` | 实体、关系与主题的领域 definition              |
| `@retikz/data`  | 数据选择器与统计 reducer                       |
| `@retikz/plot`  | 通道、scale、coordinate、mark 与 transform     |
| `@retikz/table` | 表格结构、presentation、formatter 与视觉 scale |

## 横向能力扩展包

当一个包要提供同类的多个成品能力时，问题是如何让它们共享领域模型与处理管线，又不把所有实现堆在一个目录或包根入口。横向扩展以一个内部共享 owner 承担共同契约和通用逻辑，再按家族或成品能力拆成并列子域；每个子域只拥有自己的差异，公共部分不复制。

这种组织让新增子能力不必修改其它子域，也让使用者可以从稳定子路径按需导入。包根只暴露真正公共的共享能力，内部共享 owner 不成为包外依赖；这样既能保持同一家族的一致性，又能把 API 面与实现细节分开。

### 以 Chart 为例

`@retikz/chart` 的 `_chart/` 是所有图表共享的内部 owner；`point/` 是按图表家族划分的公开子域。一个 point 图表只实现自己的 recipe、mark、encoding 和 provider，再复用 `_chart/` 的 Source、主题、registry 与解析能力。

```text
chart/src/
  _chart/                 所有 Chart 共享的内部 owner
    schemas/              Chart Source、encoding、theme、presentation
    contract/             recipe、mark、locator、theme 契约
    providers/            definition、theme、registry 与选择
    resolve/              encoding、mark、theme、presentation -> Plot
  point/                  Point 家族的公开子域
    shared/               多个 point 图表共享的 encoding、mark、recipe
    scatter/              单一图表的 schema、provider、recipe、mark
    bubble/               同上
    connected-scatter/    同上
    ranged-dot/           同上
    regression/           同上
    strip/                同上
  index.ts                包根公开入口
```

消费者只能从 `package.json` 声明的入口导入：`@retikz/chart` 获取共享 Chart API，`@retikz/chart/point` 获取 Point 家族，或从 `@retikz/chart/point/scatter` 等具体图表子路径获取能力。不要 deep import `_chart/`、`schema.ts` 或其它实现文件；它们不是稳定的包外契约。

| 扩展包            | 共享 owner 与公开子域                                             |
| ----------------- | ----------------------------------------------------------------- |
| `@retikz/diagram` | `_diagram/` 共享图式能力，`./flow` 提供 Flow 子域                 |
| `@retikz/chart`   | `_chart/` 共享图表能力，`./point` 和具体 point 图表子路径按需导入 |

## API 适配包

领域功能包拥有 schema、definition、resolve 和编译语义；API 适配包不再划分领域能力，而是把一种作者写法或宿主环境接到已有功能包上。以 Kernel 为例，`@retikz/vanilla` 是所有 API 包的核心层：它对接领域包的公开能力，将作者输入组装为 Source IR，并承接运行时处理、增量执行和性能优化等通用工作。

`@retikz/react` 是官方唯一维护的框架适配包。它是一个薄壳：负责把 React JSX 的 children、组件声明与宿主生命周期转换为 Vanilla 可消费的作者输入，保留 JSX 组合写法的优势；实际的 normalize、处理与运行时执行仍在 `@retikz/vanilla` 中完成，而不是在 React 层重建一套领域逻辑。

一般来说，与领域包配对的 `*-vanilla`、`*-react` 发布包就是 API 适配包：它们扩展作者入口或宿主能力，不属于领域包的纵向或横向能力扩展分类。

## 基础准则

开始改源码前，先判断改动属于哪一层；相关 skill 提供的是最小的决策检查表，而不是另一套实现。下面是常用入口的简要说明。

| 遇到的问题                             | 先看哪个 skill              | 它帮助确认什么                                                                      |
| -------------------------------------- | --------------------------- | ----------------------------------------------------------------------------------- |
| 新目录、文件、类型、函数或导出怎么命名 | `standard-name`             | owner、阶段名称、barrel 和公共符号是否准确                                          |
| 不确定能力应放哪层、能否依赖           | `standard-structure`        | `shared → schemas → contract → providers → resolve → pipeline/compile` 的方向与边界 |
| 改持久化 IR、Zod、默认或字段描述       | `standard-schema`           | schema 是唯一真源；context 规则不放在 schema                                        |
| 新增可供内置与第三方共用的能力         | `standard-contract`         | `XxxDefinition`、`defineXxx()` 和作者可见 context 的契约边界                        |
| 添加内置 definition 或 registry 行为   | `standard-providers`        | 内置与用户定义同路合并；冲突集中诊断，不建两套消费路径                              |
| 处理默认、继承、lookup 或领域确定化    | `standard-resolve`          | `IR + ResolveContext → Canonical / Resolution` 是唯一确定化路径                     |
| 改 Vanilla authoring API               | `standard-normalize`        | 只有 `*-vanilla` 可将 `InputXxx` 组装为 Source IR                                   |
| 改 lowering、编译上下文或 Scene 输出   | `standard-pipeline-compile` | pipeline / compile 只编排和消费，不重复 resolve 的默认、lookup 或优先级             |

所有这些准则共享三条底线：公开入口以 `package.json` 的 `exports` 和 owner barrel 为准；未知 JSON 只在 schema / parse 边界校验一次；过时结构直接删除，不通过 alias、fallback 或两条并行路径维持兼容。
