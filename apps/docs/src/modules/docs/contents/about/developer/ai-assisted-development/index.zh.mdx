title: AI 辅助开发
description: 了解 retikz 如何按任务规模与发布阶段组织人机协作，并以明确的计划、验证和授权边界交付改动
---

retikz 将 AI 视为工程协作者，而不是自动提交器。AI 可以完成调研、方案起草、实现、验证和文档；人负责能力边界、范围取舍和对外写入的最终决定。流程的目标不是增加步骤，而是让每项改动都有清楚的所有权、证据和授权来源。

## 协作边界

每个任务先根据语义风险、依赖与验证复杂度确定规模，再选择相应流程。AI 的工作范围由当前任务的确认计划决定；计划外的文件、能力边界、审查轮次或外部操作都必须重新交由人确认。

| 重点       | 当前做法                                                                            |
| ---------- | ----------------------------------------------------------------------------------- |
| 能力与范围 | 人决定公开契约、包边界、非目标与优先级；AI 基于已有约束提出证据与实施方案           |
| 实施与验证 | AI 按已确认范围实现，并用受影响模块的检查、测试和页面证据验证结果                   |
| 审查与协作 | 默认由主 agent 负责；只有计划明确授权时才加入独立 reviewer、worker 或交叉评审       |
| 外部写入   | commit、push、tag、publish 均需当前对话中的明确人工授权，不能从旧计划或相似任务推断 |

这也意味着 AI 不会用兼容层、跳过检查或扩大改动来“完成”一个任务。若实现发现公开契约、默认语义或包职责需要改变，流程会停在设计决策处，而不是把变化混入原任务。

## 按任务规模工作

小任务直接处理并验证受影响范围，例如局部文案、格式、私有命名或明确的 bugfix。中型任务先在对话中确认一次执行计划，明确目标、非目标、文件范围和验证方式；默认仍由主 agent 完成。大型任务用于 ADR 实施、公开能力重塑或跨包架构变更，需要在实现前完成设计与计划关卡。

| 规模 | 适用改动                                       | AI 的工作方式                                         |
| ---- | ---------------------------------------------- | ----------------------------------------------------- |
| 小   | 局部文档、明确 bugfix、机械调整                | 直接实施，完成受影响验证后交付                        |
| 中   | 文档主线重写、范围清楚的多文件改动、优化型重构 | 先确认计划；按计划实施、验证与自审                    |
| 大   | ADR、公开能力、跨包架构或复杂功能重构          | 先确认 ADR 与实施计划；通过设计与计划关卡后再进入实现 |

任务规模不由代码行数决定。少量文件也可能改变公开契约；反过来，大量但机械的文档修订仍可以是小任务。必要时还会根据问题的不确定性和错误代价选择合适的主模型，但模型选择不会自动扩大 AI 的操作权限。

## 按发布阶段收敛

发布通道决定 AI 可以做什么，而不是只改变版本号。能力越接近交付，允许的变动越小，证据要求越高。

| 阶段  | 主要目标                | 流程边界                                                                         |
| ----- | ----------------------- | -------------------------------------------------------------------------------- |
| Alpha | 设计并实现新的稳定能力  | 以 ADR 明确能力归属、公开契约和非目标；实现前完成 Architecture Gate 与 Plan Gate |
| Beta  | 收敛已确认的优化与 TODO | 不伪装新增功能；重点检查重构回归、breaking 影响、性能、测试和文档一致性          |
| RC    | 可靠交付已冻结的公开面  | 只接受兼容 bugfix、文档补齐与发布验证；需要破坏 API 时停止并交由人决定           |

所有阶段都遵循同一条原则：先跑通最小端到端闭环，再扩展已验证的需求。用户可见行为变更必须同步文档，中英文内容与实际公开入口保持一致。

## 验证与交付

验证优先覆盖受影响的 workspace：格式、类型、测试、文档完整性和浏览器页面按改动类型选择。跨包公开契约、发布候选或用户明确要求时，验证范围才扩大到发布组或全仓。独立评审的价值在于提供新的证据视角，不是固定的仪式；它只在已确认计划中出现。

完成实现不等于可以对外写入。AI 会报告修改范围、验证结果和仍存风险；是否暂存、提交、推送、打 tag 或发布始终由人逐项授权。这样，无论任务由一个 agent 还是多个 agent 协作，都能追溯“为什么改、如何验证、谁允许交付”。

## Skill 分类与自动化边界

retikz 将绝大部分可抽象、可复核的机械流程交给 LLM 处理：检索约束、生成计划、实现、格式化、受影响范围验证、文档同步与审查证据整理。skill 把这些重复工作收束为可复用的检查表；它不替人决定产品方向、公开契约或对外写入。

| 分组       | 职能                                       | 举例                                           |
| ---------- | ------------------------------------------ | ---------------------------------------------- |
| `flow`     | 按 Alpha、Beta、RC 组织阶段与关卡          | `flow-alpha`：ADR 能力从设计到收尾             |
| `develop`  | 为设计、实现、文档、收尾等工作提供阶段规则 | `develop-document`：用户可见改动的文档同步     |
| `standard` | 约束源码分层、命名、契约与编译边界         | `standard-structure`：确认 owner 与依赖方向    |
| `docs`     | 指导页面结构、双语、demo 与文档校验        | `docs-doc-principle`：所有 Docs 改动的基础规则 |
| `test`     | 定义测试契约与既有测试的审查方式           | `test-contract`：明确可观察行为与最低测试层    |
| `theme`    | 约束参考主题的设计、实现与文档             | `theme-academic`：Academic 主题的统一规则      |
| `cross`    | 处理需要独立视角的交叉工作                 | `cross-review`：多 LLM 的固定快照交叉评审      |
| `package`  | 组织发布前审计、版本与发布门禁             | `package-publish`：发布组的契约与 tag 审计     |

当任务命中某类工作时，AI 先加载对应 skill，再在已授权范围内执行。没有匹配 skill 的简单工作不会被强行复杂化；需要新的能力归属、扩大范围或执行 commit、push、tag、publish 时，则回到人工决策与授权。
