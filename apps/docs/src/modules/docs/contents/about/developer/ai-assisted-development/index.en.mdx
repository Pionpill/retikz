---
title: AI-assisted development
description: Learn how retikz organizes human-AI collaboration by task scale and release stage, with explicit boundaries for planning, verification, and authorization.
---

retikz treats AI as an engineering collaborator, not an automatic committer. AI can research, draft approaches, implement, verify, and document; people make the final decisions about capability boundaries, scope trade-offs, and external writes. The goal is not more process, but clear ownership, evidence, and authorization for every change.

## Collaboration boundaries

Each task is first sized by semantic risk, dependencies, and verification complexity, then follows the matching flow. AI's scope is defined by the plan confirmed for the current task. Files, capability boundaries, review rounds, and external operations outside that plan return to human confirmation.

| Focus                           | Current practice                                                                                                                                               |
| ------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Capability and scope            | People decide public contracts, package boundaries, non-goals, and priorities; AI supplies evidence and an implementation approach within existing constraints |
| Implementation and verification | AI implements within confirmed scope and verifies with affected-workspace checks, tests, and page evidence                                                     |
| Review and collaboration        | The main agent leads by default; independent reviewers, workers, or cross-review are used only when the plan explicitly authorizes them                        |
| External writes                 | Commit, push, tag, and publish each require explicit human authorization in the current conversation; an old plan or similar task is not enough                |

AI also does not use compatibility layers, skipped checks, or broader edits to make a task look complete. If implementation reveals a need to change public contracts, default semantics, or package ownership, the flow stops for a design decision instead of hiding the change in the original task.

## Working by task scale

Small tasks are handled directly and verified within their affected scope, such as local copy, formatting, private naming, or a well-defined bugfix. Medium tasks confirm one execution plan in the conversation, including goals, non-goals, file scope, and verification; the main agent still implements by default. Large tasks cover ADR execution, public-capability reshaping, or cross-package architecture work, and complete design and planning gates before implementation.

| Scale  | Suitable changes                                                                 | How AI works                                                                                       |
| ------ | -------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| Small  | Local documentation, a defined bugfix, mechanical changes                        | Implement directly and deliver after affected validation                                           |
| Medium | Documentation rewrites, clear multi-file changes, optimization refactors         | Confirm a plan first, then implement, validate, and self-review to that plan                       |
| Large  | ADRs, public capabilities, cross-package architecture, complex feature refactors | Confirm the ADR and implementation plan first; implement only after design and planning gates pass |

Task scale is not determined by line count. A small file change can alter a public contract, while a large mechanical documentation revision can remain small. The appropriate main model may also be chosen from uncertainty and error cost, but model selection never expands AI authority automatically.

## Converging by release stage

The release channel determines what AI may change, not just a version number. As work gets closer to delivery, permitted changes narrow and evidence requirements rise.

| Stage | Primary goal                                   | Flow boundary                                                                                                                                 |
| ----- | ---------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| Alpha | Design and implement new stable capabilities   | An ADR states capability ownership, public contracts, and non-goals; Architecture Gate and Plan Gate pass before implementation               |
| Beta  | Converge confirmed optimization work and TODOs | Do not disguise new features; focus on refactor regressions, breaking impact, performance, tests, and documentation consistency               |
| RC    | Reliably deliver a frozen public surface       | Only compatible bugfixes, documentation completion, and release verification are allowed; stop for human judgment if an API break is required |

Every stage follows the same principle: establish a minimal end-to-end loop first, then extend only verified needs. User-visible behavior changes travel with documentation, and both languages stay aligned with actual public entries.

## Verification and delivery

Verification starts with the affected workspace: formatting, types, tests, documentation integrity, and browser pages are selected according to the change. The scope expands to a release group or the whole repository only for cross-package public contracts, release candidates, or an explicit user request. Independent review adds a new evidence perspective rather than a fixed ritual, and occurs only when the confirmed plan includes it.

Finishing implementation does not authorize an external write. AI reports changed scope, verification results, and remaining risks; people authorize staging, committing, pushing, tagging, and publishing one action at a time. This keeps the reason for a change, its verification, and its delivery authorization traceable whether one agent or many agents collaborated.

## Skill categories and automation boundaries

retikz delegates most abstractable, reviewable mechanical work to LLMs: finding constraints, drafting plans, implementing, formatting, affected-scope validation, documentation synchronization, and assembling review evidence. Skills turn that repeated work into reusable checklists; they do not decide product direction, public contracts, or external writes for people.

| Group      | Responsibility                                                            | Example                                                                    |
| ---------- | ------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| `flow`     | Organize stages and gates for Alpha, Beta, and RC                         | `flow-alpha`: an ADR capability from design through wrap-up                |
| `develop`  | Define phase rules for design, implementation, documentation, and wrap-up | `develop-document`: documentation synchronization for user-visible changes |
| `standard` | Constrain source layering, naming, contracts, and compile boundaries      | `standard-structure`: confirm owners and dependency direction              |
| `docs`     | Guide page structure, bilingual content, demos, and documentation checks  | `docs-doc-principle`: base rules for every Docs change                     |
| `test`     | Define test contracts and how existing tests are reviewed                 | `test-contract`: observable behavior and the minimum test layer            |
| `theme`    | Constrain reference-theme design, implementation, and documentation       | `theme-academic`: shared rules for the Academic theme                      |
| `cross`    | Handle cross-work that needs independent perspectives                     | `cross-review`: fixed-snapshot multi-LLM review                            |
| `package`  | Organize pre-release audits, versioning, and release gates                | `package-publish`: contract and tag audit for a release group              |

When a task matches a category, AI loads the corresponding skill and works within its authorized scope. A simple task without a matching skill is not made complex by force; a new capability boundary, broader scope, or commit, push, tag, or publish returns to human decision and authorization.
