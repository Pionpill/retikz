Retikz 是一个声明式的通用绘图框架。你可以用代码或结构化数据描述图形，将基础图元、关系图、数据图表与表格组合成可复用的可视内容。

它适合那些需要随着内容、数据和产品一起演进的图：技术文档中的原理说明、应用中的关系视图、带注释的数据图表，以及由 AI 生成后还需要继续修改的图形。

## 描述图形，让表达可以复用

一张图不仅有颜色和坐标，也有内容与关系：哪个节点连接哪个节点，哪些元素属于同一组，哪个数据字段决定柱子的高度。Retikz 让这些意图成为图形描述的一部分。

例如，连接两个节点时，可以引用它们的名字，让框架计算线与节点边界的连接位置。修改节点文字或位置后，连线沿同一套规则重新计算。复用一张图，也就可以从替换内容和参数开始。

这种声明式表达把三个问题分开：

| 你要决定什么         | Retikz 的接入方式                                          |
| -------------------- | ---------------------------------------------------------- |
| 图里有什么、如何关联 | 用组件或结构化数据描述内容、关系与样式                     |
| 在什么应用中使用     | 核心绘图语义独立于 UI 框架，当前提供 React 与 Vanilla 入口 |
| 如何输出图形         | 由渲染层输出 SVG 或 Canvas，绘图语义与后端分离             |

框架无关意味着可以从适合应用的入口接入；渲染无关意味着同一套绘图语义不绑定某个绘制 API。具体输出能力仍以所选后端的文档为准。

## 从基础绘图到业务表达

Retikz 按场景提供四组能力。你可以从高层业务表达开始，也可以使用基础图元精细控制图形。

| 分组                     | 解决的问题                                           | 从哪里开始                                                    |
| ------------------------ | ---------------------------------------------------- | ------------------------------------------------------------- |
| **Kernel · 绘图内核**    | 节点、路径、文字与几何关系，以及共享的编译和渲染基础 | [基础绘图](/kernel/components/get-start)                      |
| **Library · 通用能力库** | 可复用图形组件、容器排版与布局能力                   | [Standard](/library/standard) · [Layout](/library/layout)     |
| **Schematic · 结构制图** | 实体、关系、分组与结构化图式                         | [Graph](/schematic/graph) · [Diagram](/schematic/diagram)     |
| **Viz · 数据可视化**     | 数据处理、视觉映射、图表与二维表格                   | [Plot](/viz/plot) · [Chart](/viz/chart) · [Table](/viz/table) |

这些分组共享底层绘图能力。业务组件把自身的语义转换为通用图形，再进入共同的编译与渲染过程。因此，排版、关系表达和数据图形可以围绕同一张图协作，不必各自维护一套画布与绘制规则。

这也给定制留出了空间：常见场景使用现成组件；需要特殊表达时，继续组合更底层的元素，或通过公开的 Definition 与注册机制扩展能力。

## 为 LLM 设计的图形表达

Retikz 的 AI 友好性不只在于“可以生成 JSON”，而在于让模型用紧凑的配置表达绘图意图，把必要的计算交给框架，并保留可继续修改的图形语义。

- **用较少配置描述图形**：节点引用、共享样式和高层组件承载可复用规则，不必为每个元素重复展开结构与坐标。对于包含关系、排版或重复图形的任务，相较于直接编写底层 HTML/SVG，这种表达可以减少需要生成和维护的细节；它并不意味着所有图形的配置或 token 数都更少。
- **生成后仍然可编辑**：Retikz 的 JSON 中间表示（IR）保留节点、关系、数据与样式。相较于位图中的像素，修改对象和修改意图是明确的；HTML/SVG 本身也可编辑，而 Retikz 进一步保留高层绘图语义，例如“连接这两个节点”，而不只是最终的线段坐标。
- **把必要算法封装在框架内**：几何计算、节点边界连接，以及所选布局组件的排版逻辑由相应能力处理。模型描述目标、关系和参数，不必自行展开每一步计算；内容变化后，框架按同一套规则重新求解。

为了让这些描述更容易被 LLM 理解和生成，Retikz 也在契约结构上做了针对性设计：

- **自描述的 Schema**：Zod schema 使用英文 `.describe()` 解释字段含义和使用规则。例如，间距配置不仅声明数值类型，还说明单边、轴向与默认值的优先级。模型读取契约时可以获得语义依据，程序则用 schema 检查结构与字段约束。
- **按语义组织属性**：例如 Node 将视觉覆盖放入 `style`，尺寸、间距与文字排版放入 `layout`，内容与引用仍留在各自的位置。分组让模型能按修改意图寻找字段，而不必面对一长串混合职责的属性。
- **控制判别分支的数量**：用 `kind` 区分真正不同的操作，用参数表达同类操作的变化。例如，正交折线统一使用 `kind: 'fold'`，通过 `via` 选择折线路径，不为每种方向另造一种操作。这样既保留明确的语义分支，也减少需要记忆的重复概念。

这些设计共同服务于一个目标：让模型专注于图里要表达什么，减少底层细节的生成负担，让结果保持可校验、可编辑和可复用。具体字段与约束可以查阅 [Schema Reference](/kernel/reference/schema)。

## 为什么选择 Retikz

当一张图同时需要业务语义、局部定制和长期维护时，统一的绘图基础尤其有价值。

- **从现成表达走向精细定制**：先用图表、关系与排版组件完成主体，再用通用图元补充细节。
- **把一次绘图变成可复用内容**：让内容、数据和配置驱动变化，将反复制作的图形纳入应用逻辑。
- **让不同入口共享语义**：React、Vanilla 与结构化数据围绕共同的绘图契约工作。
- **给 AI 生成结果留下修改空间**：保存可校验的描述，使生成、人工调整与后续更新能够衔接。

选择绘图工具时，可以先判断需求更接近哪一种工作方式：

| 工作方式                 | 选择时关注什么                                                                      |
| ------------------------ | ----------------------------------------------------------------------------------- |
| 直接编写 SVG / Canvas    | 适合需要直接控制绘制细节的场景；Retikz 在其上提供图元、引用与组合表达               |
| 使用专用图表或关系图工具 | 优先评估现成图型和交互是否满足需求；Retikz 值得关注的方向是通用绘图与业务表达的组合 |
| 将图形作为代码与数据维护 | 关注描述能否复用、校验和持续修改，这是 Retikz 的主要使用方式                        |

如果你需要的是完整的拖拽设计工具，还要评估选区、编辑操作与协作等产品能力。Retikz 提供的是可编程绘图框架，应用需要按自己的场景组织编辑体验。
