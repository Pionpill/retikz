Layout schemas persist container and item configuration. Definitions, capability presets, the Core compile context, and adapters are runtime objects. Standard owns generic layout solving, while Core proposes two-axis conditions to children, isolates probe candidates, replays selected candidates, and publishes typed artifacts.

> This page covers capability loading and execution rather than schema fields. See [Contract - Input](/standard/layout/reference/contract-input) for persisted configuration and [Contract - Artifact](/standard/layout/reference/contract-artifact) for solved results.

## Loading capability

| Granularity    | Public entry                                                              | Purpose                                                   |
| -------------- | ------------------------------------------------------------------------- | --------------------------------------------------------- |
| One definition | `FlexLayoutDefinition`, `GridLayoutDefinition`, `OverlayLayoutDefinition` | Register one layout composite with Core                   |
| One module     | `FlexLayoutModule`, `GridLayoutModule`, `OverlayLayoutModule`             | Load one member through the Standard capability system    |
| Layout preset  | `StandardLayoutPreset`                                                    | Load all three layout definitions                         |
| React          | `FlexLayout`, `GridLayout`, `OverlayLayout`, `LayoutItem`                 | Build canonical IR and contribute definitions to `Layout` |
| Vanilla        | `StandardLayoutVanillaAdapters`                                           | Recognize all three embeds in figure, mount, or SSR hosts |

`StandardLayoutPreset.compile.composites` is the Core definition array passed to `compileToScene()`. The preset does not introduce another compilation pipeline. React and Vanilla adapters produce the same Standard IR and contribute the same definitions.

## One layout transaction

A layout container is a Core layout-aware composite. One compilation proceeds through these deterministic stages:

1. **Parse input**: Core resolves the definition by `namespace` and `type`, then validates canonical IR with its schema.
2. **Probe children**: the container calls `layoutChild` for minimum, natural, ranged, or exact candidates. Results carry the parent-resolved `slotSize`, real `allocationBounds`, `visualBounds`, and available alignment guides.
3. **Solve the container**: Standard pure solvers use container rules, available space, and probe measurements to resolve tracks, lines, slots, and translations.
4. **Replay selected candidates**: each child replays only its selected candidate. Discarded probes publish no primitives, resources, namespaces, or artifacts.
5. **Publish results**: Core wraps the Standard value in an occurrence-aware composite artifact and returns it with the final Scene.

Fixed geometry may refuse a smaller slot, so `slotSize` and real `allocationBounds` remain distinct. Containers do not guess another main-axis distribution after refusal. Determinate undersizing is represented through overflow and visible bounds, while invalid or unsolvable configuration fails loudly.

Nested layouts remain in the same Core compilation. An inner container receives the outer proposal as an ordinary child. Every composite occurrence publishes an artifact with a local key space, without relying on a public id as an instance selector.

## Direct Core usage

```ts
import { compileToScene } from '@retikz/core';
import { FlexLayoutArtifactSchema, StandardLayoutPreset } from '@retikz/standard';

const output = compileToScene(scene, StandardLayoutPreset.compile);
const envelope = output.artifacts.find(
  artifact => artifact.kind === 'composite' && artifact.namespace === 'standard' && artifact.type === 'flexLayout',
);
const artifact = FlexLayoutArtifactSchema.parse(envelope?.value);
```

Hosts that need one container may put its definition in `compile.composites`; use `StandardLayoutPreset.compile` for the complete family. `occurrence.sourcePath` and `occurrence.expansionPath` distinguish nested or repeated instances. Parse `value` with the matching `XxxLayoutArtifactSchema`.

## React

The three `@retikz/standard-react` containers are embeddable Tier 2 components. Their direct children must be `LayoutItem` elements with the matching `kind`. Fragments and arrays flatten transparently, but ordinary JSX nodes cannot bypass item semantics.

Every `LayoutItem` requires exactly one of `children` or `ir` and must produce exactly one `IRChild`. React `itemKey` becomes canonical JSON `key`; it never reads React's reserved `key`. Nested Standard layouts may contribute the same family, while external datasets or foreign Tier 2 runtime contributions remain the outer host's responsibility.

React containers start no local compilation and perform no DOM measurement. They contribute IR and definitions to the outer `Layout`, which compiles and renders the complete tree. Observe artifacts through the outer host.

## Vanilla

`flexLayout()`, `gridLayout()`, and `overlayLayout()` return `VanillaEmbedSpec` values. Figure, mount, or SSR hosts need the matching adapter; use `StandardLayoutVanillaAdapters` for the complete family.

Each adapter calls the same `createXxxLayout()` factory as direct authoring and contributes a copy of `StandardLayoutPreset.compile.composites`. Vanilla therefore shares schemas, definitions, solvers, and artifact semantics with direct Core compilation and React.

## Layout Inspector

Layout Inspector is a runtime-only development overlay. It never enters Standard IR or changes typed layout artifacts. SVG appends a `pointer-events="none"` group after the primary figure. Canvas draws the overlay after the primary bitmap without adding its primitives to hit testing. Both backends derive viewBox, resources, animation, and normal interaction from the primary Scene only.

### Color, pattern, and line style

The overlay uses three independent visual channels instead of overloading color with both geometry class and nesting depth:

| Channel    | Meaning                 | Rule                                                                                                                                                                                                             |
| ---------- | ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Color      | Final layout occurrence | Core assigns `colorScope` in final entry order. Render cycles a nine-color palette, while warnings stay red                                                                                                      |
| Pattern    | Spacing semantics       | Margin and fixed gaps use `/`, while padding uses the opposite `\`. These three draw hatches without a base fill. Distributed space uses neither a pattern nor a background fill. Hatch spacing is 12 user units |
| Line style | Geometry class          | Container, content, item boxes, Flex lines, Grid tracks/cells/spans, Overlay placements, and alignment guides are dashed; anchor crosshairs are solid                                                            |

Regular primitives from one occurrence share a color. Nested containers receive colors from their own final occurrences. The palette repeats from the tenth occurrence, so color is a quick ownership cue; the occurrence locator remains the exact identity.

Paint order is spacing hatch / boundary underlay → family structure → box outline → overflow warning → guide/anchor → label. `bounds.content` and `bounds.slot` control only their outlines; `spacing.padding` and `spacing.margin` independently control both texture and boundary. Margin, padding, and fixed gaps use independent dashed lines for their boundaries. A ring outlines only its outer and inner perimeter, never the seams between its hatch pieces. `distributedSpace` shows only the dashed perimeter of unused content and keeps its interior transparent. If a spacing boundary is already fully covered by a content or slot outline, Flex line, or Grid track, that segment is painted once; enabling any category alone still keeps its complete visible boundary.

### Three activation scopes

| Scope            | React                                  | Vanilla                           | Cascade behavior                                            |
| ---------------- | -------------------------------------- | --------------------------------- | ----------------------------------------------------------- |
| Whole figure     | `<Layout inspect={{ layout: true }}>`  | `inspect` in mount or SSR options | Select every registered layout occurrence with an inspector |
| Authored subtree | `<Scope inspect={{ layout: true }}>`   | `VanillaScopeSpec.inspect`        | Select only authored descendants of that Scope              |
| One container    | `<FlexLayout inspect>` and equivalents | `flexLayout('id', input, true)`   | Select that occurrence only; nested layouts stay unchanged  |

Policies merge field by field from Layout to the nearest Scope and then the component. Object-valued `bounds` and `spacing` merge individual fields; switching between a boolean and an object replaces the whole group with the later value. `layout: false` only overrides the current cascaded value, so a deeper Scope or component may enable it again; only `enabled: false` creates a hard subtree barrier that descendants cannot cross. Component-level `inspect={false}` disables only that occurrence. With every `inspect` omitted, no inspector runs and `CompileResult.inspection` is `null`.

`layout: true` uses one full canonical profile: container, content, slot, allocation, padding, margin, overflow, and alignment guides are on; visual bounds and labels are off. Object values override only explicit fields, so `{ layout: { spacing: { padding: false } } }` disables only padding texture.

The docs playground “Recommended” profile is intentionally smaller: Flex shows the content outline, Flex line regions, and fixed gaps; Grid shows the content outline, track bounds, and fixed gaps; Overlay shows only the content outline. “All” enables every detail, “Off” changes only the master switch, and Reset returns to Recommended.

Flex enables `lines`, `gaps`, and `distributedSpace` by default. Grid enables `tracks`, `gaps`, `distributedSpace`, and `spans`, while `cells` stays off. Overlay enables `placements` and `anchors`, while `stacking` stays off.

For Flex and Grid, `gaps` controls resolved authored gaps and `distributedSpace` controls positive free space introduced by `justifyContent` or `alignContent`. Fixed gaps use `/`, opposite the padding hatch; distributed space keeps a transparent interior and contributes only uncovered dashed perimeter segments. The inspector consumes resolved `artifact.spacing` segments and does not classify every empty interval between slots or tracks as a gap.

`inspect` accepts sparse authoring values only; unknown keys or invalid types fail loudly. Core resolves the cascade exactly once, then a Standard inspector reads only the typed artifact from that same compilation. A retained update commits the primary frame, artifacts, and overlay atomically; a failure publishes no partial frame.
