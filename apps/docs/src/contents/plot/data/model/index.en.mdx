A chart has two halves: **config** (what to draw — marks / coordinate / scales) and **data** (which values). retikz keeps them apart — the data does **not** enter the chart config (the IR); it's supplied separately at compile time. That lets one config be reused across different datasets.

The simplest form: hand a row array to `<Plot data>` and have marks reference columns by field name.

```tsx
<Plot data={rows}>
  <LineMark x="month" y="revenue" order="month" />
</Plot>
```

A field name is a **path**, so nested data (MongoDB documents, JSON from an API) works directly: `x="user.address.city"` drills to the leaf. The leaf must be a scalar (string / number / boolean / time) — not an object or array.

## Declaring field types

With data alone, retikz can't tell whether `month` is a time or a plain string, or whether `revenue` is continuous or categorical. Give it a **model** and it knows the field contract — how to pick scales, format axes, derive legends, and validate — all driven by field type.

```tsx
<Plot data={sales} model={[
  { name: 'month',   type: 'temporal' },
  { name: 'revenue', type: 'continuous' },
]}>
  <LineMark x="month" y="revenue" order="month" />
</Plot>
```

Field types (three measurement kinds):

| Type | Meaning | Examples |
| --- | --- | --- |
| `continuous` | continuous measurable number | sales, price, temperature, share |
| `categorical` | discrete category | country, color name, rating |
| `temporal` | date / time | dates, timestamps |

Each field declaration can contain:

| Field | Purpose |
| --- | --- |
| `name` | logical field name, also the name referenced by marks / transforms |
| `type` | measurement type; omitted fields are inferred from data |
| `format` | declarative parsing format, such as `slashDate` / `percent`; see [Processing](/plot/data/processing) |
| `order` | category order for categorical fields |

**Declaring a model = strict mode**: every data field referenced by a mark / transform must be listed in the model; a misspelled field name **fails immediately** (instead of drawing an empty chart). References include not only `x` / `y`, but also `a` / `b` / `c`, `color`, `series`, a mark's `order`, point `size` / `opacity` / `shape`, and transform input fields. **No model**: retikz infers types by sampling the data (number → continuous, ISO date string / `Date` → temporal, other strings → categorical), which is handy for quick drafts.

**`type` is optional — partial models**: a field's type can be omitted, leaving just `{ name }`. The field still joins strict mode + the portable binding contract (by name), but its **type is left to inference**. Good for "most fields are obvious, only a few need pinning" — give `type` to numeric enums that need correcting, use `format` for non-default dates / percentages, and leave the rest bare:

```tsx
<Plot data={sales} model={[
  { name: 'createdAt',  format: 'slashDate' }, // '2024/01/01' → temporal
  { name: 'statusCode', type: 'categorical' }, // numeric enum pinned as category
  { name: 'revenue' },                         // name only → inferred continuous
]}>
  {/* … */}
</Plot>
```

Fields with `type` omitted need the data at lowering to determine their type; fields with `format` get their type from the format, so `format: 'percent'` is treated as `continuous`. To keep a spec fully self-describing without the data (LLM-friendly / fully portable), fill in `type` or `format`.

## Type-driven scales

With a model declared, positional channels (x / y, and ternary a / b / c) **no longer need an explicit scale** — retikz picks one from the field type: `continuous` → linear, `temporal` → time axis, `categorical` → band. Color channels are also affected by field type: fields with explicit continuous / temporal types derive continuous color ramps, while categorical fields derive discrete color. See [Scales](/plot/grammar/scale) for the full mapping and override rules.

## Category order: `order`

A `categorical` field orders its categories by **data appearance** by default (axes and legends follow that order). To control it — sizes should read `S → M → L → XL`, not whatever order they happen to appear in the data — give the field an `order`:

```tsx
<Plot data={rows} model={[
  { name: 'size',  type: 'categorical', order: ['S', 'M', 'L', 'XL'] }, // explicit order
  { name: 'grade', type: 'categorical', order: 'ascending' },           // sorted ascending
  { name: 'city',  type: 'categorical' },                               // default: appearance order
]}>{/* … */}</Plot>
```

| `order` | Effect |
| --- | --- |
| omitted / `'data'` | data appearance order (default) |
| `'ascending'` / `'descending'` | sort the categories: numeric when all numbers, else as strings |
| `Array` (e.g. `['S','M','L']`) | the array is the order; categories present in the data but absent from the array are appended at the end |

Rules:

- **It lives on the field, so position and color share the order**: when the same field drives both the x-axis (band) and color (ordinal), both use the same category order.
- **Only valid on `categorical`**: an `order` on a `continuous` / `temporal` field **throws** (order is meaningless for continuous values / time).
- **An explicit scale `domain` wins**: if the scale declares its own `domain`, that takes precedence and `order` is ignored.
- A **non-default** `order` (a sort or an explicit array) marks the field as ordered — retikz's three field types have no dedicated "ordered category" type; orderedness is expressed through this parameter.
