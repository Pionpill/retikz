---
title: Registry
description: Mark registration separates JSON-safe IR schemas from runtime lowering behavior; the built-in marks are implemented through the same mechanism.
---

A mark has two contracts: the IR schema describes which serializable fields the mark owns, while the lowering registry entry describes how that mark turns data, scales, and coordinates into core IR. The built-in `PointMark` / `PathMark` / `RegionMark` / `IntervalMark` / `ReferenceMark` / `LinkMark` are all registered entries in that mechanism.

That is also the shape of a custom mark: define a stable `type` and field contract, then implement a lowering function that turns data rows into core `Scope`, `Node`, `Path`, and related primitives.

## Two Contracts

| Layer | Contains | Enters IR | Purpose |
| --- | --- | --- | --- |
| schema | fields such as `type`, `encoding`, `bounds`, `series` | yes | persistence, validation, AI generation, cross-runtime transport |
| registry | behavior such as `lower(mark, rows, frame, channels)` | no | compile-time lowering into core IR |

Functions cannot be stored in the IR, so a custom mark cannot put drawing logic into JSON. Runtime functions live in registry entries; JSON stores only the fields needed to reconstruct the semantics.

## Entry Shape

The built-in registry entry can be read as:

```ts
type MarkDefinition<T extends Mark = Mark> = {
  type: PlotMarkValue;
  requiredRoles?: (frame: CoordinateFrame) => ReadonlyArray<DimensionRole>;
  buildCell?: (mark: T, row: ExternalRow, frame: CoordinateFrame, ctx?: IntervalContext) => Cell | null;
  lower: (mark: T, rows: Array<ExternalRow>, frame: CoordinateFrame, channels: MarkChannels, prov?: MarkProvenance) => IRChild | null;
};
```

`lowerMark` does not keep a long `if (mark.type === ...)` chain. It looks up `MARK_REGISTRY` by `mark.type`, then calls the matching `lower`. Adding a built-in mark means adding a registry entry while keeping dispatch stable.

## Custom Steps

When designing a custom mark, follow this order:

1. Pick an abstract semantic, not a chart name. Prefer "projected interval", "relational band", or "axis constraint" over "pie chart" or "heatmap".
2. Define a JSON-safe schema: fields, channels, defaults, and fail-loud rules must be serializable.
3. Implement the lowering entry: consume `rows`, `frame`, and channel resolvers, return a core `Scope`, and return `null` when there is nothing drawable.
4. If the mark depends on coordinate cells, turn each row into a `Cell` first, then call `frame.projectCell`. Cartesian coordinates can produce rectangles, polar coordinates can produce sectors, and curved coordinates can return contours.
5. Add the declaration layer for React / Vanilla. A React mark component only assembles flat props into IR; actual drawing still belongs to registry lowering.

## Example

The `CrossMark` example below shows which pieces an internal mark extension needs. Its semantics are simple: project one point per row, then draw two crossing line segments at that point. In the real codebase these pieces live in the IR schema, lowering, and React declaration layer; they are shown together here to make the mechanism visible.

The preview shows the declaration shape after a source extension is wired in: `CrossMark` sits under `<Plot>` like a built-in mark and only declares field channels; the rendered result comes from the registered `lowerCross` entry. The public API cannot register marks dynamically yet, so the demo uses a transparent `PointMark` as a scale anchor and overlays the core `Draw` output that lowering would produce.

First add a serializable IR schema. `type` is the discriminator, `encoding` still describes field-to-channel bindings, and `size` is a JSON-safe drawing parameter:

```ts
export const PlotMark = {
  // ...
  Cross: 'cross',
} as const;

export const CrossMarkSchema = z.object({
  type: z.literal(PlotMark.Cross),
  encoding: EncodingSchema,
  size: z.number().positive().optional(),
});

export const MarkSchema = z.discriminatedUnion('type', [
  PointMarkSchema,
  PathMarkSchema,
  RegionMarkSchema,
  IntervalMarkSchema,
  ReferenceMarkSchema,
  LinkMarkSchema,
  CrossMarkSchema,
]);
```

Then implement lowering. It consumes data rows and the coordinate frame, returns a core `Path` layer, and returns `null` when no point can be projected:

```ts
const lowerCross = (mark: CrossMark, rows: Array<ExternalRow>, frame: CoordinateFrame): IRChild | null => {
  const size = mark.size ?? 6;
  const children: Array<IRChild> = [];

  for (const row of rows) {
    const point = frame.projectRoles([channelValue(mark.encoding.x, row), channelValue(mark.encoding.y, row)]);
    if (!point) continue;

    const [x, y] = point;
    children.push({
      type: 'path',
      children: [
        { action: 'move', to: [x - size, y - size] },
        { action: 'line', to: [x + size, y + size] },
        { action: 'move', to: [x - size, y + size] },
        { action: 'line', to: [x + size, y - size] },
      ],
    });
  }

  return children.length === 0 ? null : { type: 'scope', children };
};
```

Finally register it and add a React declaration component that only assembles IR:

```ts
export const MARK_REGISTRY = {
  // ...
  [PlotMark.Cross]: { type: PlotMark.Cross, lower: lowerCross },
};

export type CrossMarkProps = {
  x: string;
  y: string;
  size?: number;
  id?: string;
};

export const CrossMark: FC<CrossMarkProps> = () => null;
```

The mark does not need to know whether the current coordinate is cartesian or polar. It asks `frame.projectRoles` for the projected point, and the coordinate layer decides how to interpret `x` / `y`.

## Current Boundary

<ComponentAlert type="warn" title="Runtime registration is not public yet" description="The built-in marks already use a registry table, but this version does not expose a registerMark API or a dynamic MarkSchema registry. Adding a brand-new mark is currently a source-extension / contribution path; application code should compose the six registered marks first." />

This differs from custom coordinates. A coordinate projection can be injected through `<Plot coordinates>` because the IR only stores a factory name and params. A mark `type` must also enter the `MarkSchema` discriminated union, so public runtime registration needs schema extension, React assembly, and lowering dispatch to be solved together.

## Built-Ins

| Mark | Registered behavior |
| --- | --- |
| `PointMark` | Lowers each row to a glyph or text Node |
| `PathMark` | Lowers ordered points into a Path |
| `RegionMark` | Fills the area enclosed by an outline and baseline |
| `IntervalMark` | Builds a Cell first, then projects it into a rectangle, sector, or contour |
| `ReferenceMark` | Lowers an axis constant into a line or band |
| `LinkMark` | Lowers source / target endpoints into a fillable cubic band |

Chart forms are just results of these registered marks under different coordinates, scales, and transforms. Before adding a new mark, first check whether the existing marks already express the geometry.
