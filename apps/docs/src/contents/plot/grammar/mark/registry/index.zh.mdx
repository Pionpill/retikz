---
title: 注册机制
description: mark 注册机制把 JSON-safe 的 IR schema、React 声明层和运行时 lowering 分开；内置 mark 也都通过同一套机制下沉到 core IR。
---

mark 注册机制解决的是“一个图元如何进入 plot 编译管线”。IR schema 只描述可序列化字段；React / Vanilla 声明层只把用户写法装配成 IR；registry 里的 lowering 函数才负责把数据行、比例尺和坐标系转换成 core `Scope` / `Node` / `Path`。

内置的 `PointMark` / `PathMark` / `RegionMark` / `IntervalMark` / `ReferenceMark` / `LinkMark` 都是这套机制里的注册项。自定义 mark 也要沿着同一条线：先定义稳定的 `type` 和字段契约，再把行为放进运行时注册项，而不是把函数塞进 JSON。

## 用法

对使用者来说，注册机制最终露出的形态仍是普通 mark 组件：

```tsx
import { Plot, PointMark } from '@retikz/plot-react';

<Plot data={rows}>
  <PointMark x="x" y="value" />
</Plot>;
```

新增一个源码级 mark 后，声明层也应该保持这个形态。下面的 `CrossMark` 是机制示例：它在 `<Plot>` 下声明字段通道，实际绘制由对应的 lowering 注册项完成。

```tsx
<Plot data={rows}>
  <CrossMark x="x" y="value" size={10} />
</Plot>
```

React 组件本身不画 DOM；`<Plot>` 收集它，生成 `type: 'cross'` 这类 mark IR，然后编译阶段按 `type` 查 registry。

## 机制层

一个 mark 需要三层协作：

| 层 | 放什么 | 是否进 IR | 职责 |
| --- | --- | --- | --- |
| schema | `type`、`encoding`、`bounds`、`series` 等字段 | 是 | 校验、持久化、AI 生成和跨端传输 |
| 声明层 | React props / Vanilla builder | 否 | 把用户写法装配成 JSON-safe mark IR |
| registry | `lower(mark, rows, frame, channels)` 行为 | 否 | 编译时下沉成 core IR |

这三层的边界很重要：IR 不能保存函数，所以 schema 只保留足够重建语义的字段；lowering 函数只存在于运行时注册项中。内置 mark 不是特殊分支，而是内置注册项。

当前内置 registry 项可以理解为：

```ts
type MarkDefinition<T extends Mark = Mark> = {
  type: PlotMarkValue;
  requiredRoles?: (frame: ResolvedCoordinate) => ReadonlyArray<DimensionRole>;
  buildCell?: (mark: T, row: ExternalRow, frame: ResolvedCoordinate, ctx?: IntervalContext) => Cell | null;
  lower: (mark: T, rows: Array<ExternalRow>, frame: ResolvedCoordinate, channels: MarkChannels, prov?: MarkProvenance) => IRChild | null;
};
```

`lowerMark` 不再维护一串 `if (mark.type === ...)`。它按 `mark.type` 查 `MARK_REGISTRY`，再调用对应的 `lower`。新增内置 mark 时，分发逻辑不变，只补 schema、声明层和注册项。

## 自定义步骤

设计新 mark 时按这个顺序收敛：

1. 先确定抽象语义，而不是图表名字。例如优先想“投影区间”“关系带”“轴向约束”，不要直接注册“饼图”“热图”。
2. 定义 JSON-safe schema：`type` 判别串、字段通道、默认值和 fail-loud 规则都必须可序列化。
3. 写 lowering 注册项：读取 `rows`、`frame` 和通道 resolver，返回 core `Scope`；没有可绘制内容时返回 `null`。
4. 如果图元依赖区间或网格，先把每行转换成 `Cell`，再交给 `frame.projectCell`。这样笛卡尔可以得到矩形，极坐标可以得到扇区，曲线坐标系也有机会返回 contour。
5. 补 React / Vanilla 声明层：组件或 builder 只负责装配 IR；绘制行为仍由 registry 的 lowering 负责。

当前公开 API 还不能动态注册 mark，所以这个 demo 只模拟“源码扩展接入后”的效果：本页局部定义的 `CrossMark` 是空声明组件；透明的 `PointMark` 负责让 plot 建立比例尺；core `Draw` 叠出 `lowerCross` 会生成的两条线。这个折中只服务文档预览，真实源码接入时应由 `buildPlotSpec` 收集 `CrossMark` 并交给 registry lowering。

第一步是扩展 IR schema。`type` 是判别字段，`encoding` 仍然只描述字段到通道的绑定，`size` 是 JSON-safe 的绘制参数：

```ts
export const PlotMark = {
  // ...
  Cross: 'cross',
} as const;

export const CrossMarkSchema = z.object({
  type: z.literal(PlotMark.Cross),
  encoding: EncodingSchema,
  size: z.number().positive().optional(),
});

export const MarkSchema = z.discriminatedUnion('type', [
  PointMarkSchema,
  PathMarkSchema,
  RegionMarkSchema,
  IntervalMarkSchema,
  ReferenceMarkSchema,
  LinkMarkSchema,
  CrossMarkSchema,
]);
```

第二步是写 lowering。它消费数据行和坐标系 frame，返回 core `Path` 图层；没有可投影的点时返回 `null`：

```ts
const lowerCross = (mark: CrossMark, rows: Array<ExternalRow>, frame: ResolvedCoordinate): IRChild | null => {
  const size = mark.size ?? 6;
  const children: Array<IRChild> = [];

  for (const row of rows) {
    const point = frame.projectRoles([channelValue(mark.encoding.x, row), channelValue(mark.encoding.y, row)]);
    if (!point) continue;

    const [x, y] = point;
    children.push({
      type: 'path',
      children: [
        { action: 'move', to: [x - size, y - size] },
        { action: 'line', to: [x + size, y + size] },
        { action: 'move', to: [x - size, y + size] },
        { action: 'line', to: [x + size, y - size] },
      ],
    });
  }

  return children.length === 0 ? null : { type: 'scope', children };
};
```

最后把它挂进注册表，并给 React 侧补一个只负责装配 IR 的声明组件：

```ts
export const MARK_REGISTRY = {
  // ...
  [PlotMark.Cross]: { type: PlotMark.Cross, lower: lowerCross },
};

export type CrossMarkProps = {
  x: string;
  y: string;
  size?: number;
  id?: string;
};

export const CrossMark: FC<CrossMarkProps> = () => null;
```

`CrossMark` 不需要自己理解“笛卡尔”或“极坐标”。它只向 `frame.projectRoles` 要投影点；坐标系如何解释 `x` / `y`，仍然由 coordinate 层决定。

## 接口说明

| 接口点 | 必填性 | 说明 |
| --- | --- | --- |
| `type` | 必填 | 注册键，必须等于 IR schema 的判别串 |
| `lower` | 必填 | 把当前 mark 和数据行下沉成 core IR；无内容返回 `null` |
| `requiredRoles` | 可选 | 声明当前坐标系下需要哪些位置角色；省略时由 lowering 自行 fail-loud |
| `buildCell` | 可选 | 区间类 mark 的 per-row cell 构造入口，通常供 `IntervalMark` 这类图元使用 |

声明层的 props 不等于 registry 接口。props 面向用户，通常是扁平字段名；schema 面向 IR，必须 JSON-safe；registry 面向编译期，拿到的是已经规范化后的 mark、数据行、通道 resolver 和坐标系 frame。

## 当前边界

<ComponentAlert type="warn" title="运行时注册尚未开放" description="当前版本已经把内置 mark 整理成注册表，但还没有公开 registerMark API，也没有动态扩展 MarkSchema 的 schema registry。应用层若要新增全新的 mark，需要走源码扩展 / 贡献路径；普通业务优先组合现有六个注册图元。" />

这和自定义坐标系不同：坐标系的投影可以通过 `<Plot coordinates>` 注入，因为 IR 只保存 `{ type: <customType>, ...config }`，角色和函数都在 `defineCoordinate` 定义里；mark 的 `type` 还要进入 `MarkSchema` 判别 union。公开运行时注册需要同时解决 schema 扩展、React / Vanilla 装配和 lowering 分发。

## 内置图元

| 图元 | 注册行为 |
| --- | --- |
| `PointMark` | 每行下沉成一个 glyph 或文本 Node |
| `PathMark` | 按顺序把点下沉成 core Path |
| `RegionMark` | 把上沿和基线围成可填充 Path |
| `IntervalMark` | 先构造 Cell，再投影成矩形、扇区或 contour |
| `ReferenceMark` | 把轴向常量下沉成线或带 |
| `LinkMark` | 把 source / target 端点下沉成可填充 cubic 曲带 |

图表形态只是这些注册图元在不同坐标系、比例尺和 transform 下的结果。新增 mark 前，先确认现有图元是否已经能表达该几何。
