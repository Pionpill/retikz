title: RelationMark
description: RelationMark lowers source / target relationships from data rows into core Paths, reusing Path targets, arrows, bends, folds, curves, and step labels.
---

`<RelationMark>` draws relationships between two targets. A target can be an existing core id, a stable id generated by `PointMark` / `IntervalMark` / `PathMark` through `anchorId`, or a coordinate projected from the current relation row.

It is not the older group / stack / dodge data-composition relation from early design notes. This relation is a drawable source-target mark: each relation row lowers to one core `Path` that starts at source, passes through optional waypoints, and ends at target.

## Usage

```tsx
import { Plot, PointMark, RelationMark } from '@retikz/plot-react';
```

```tsx
<Plot data={edges}>
  <PointMark x="sourceX" y="sourceY" anchorId={{ prefix: 'node', field: 'sourceId' }} />
  <PointMark x="targetX" y="targetY" anchorId={{ prefix: 'node', field: 'targetId' }} />
  <RelationMark
    source={{ anchorId: { prefix: 'node', field: 'sourceId' } }}
    target={{ anchorId: { prefix: 'node', field: 'targetId' } }}
    path={{ arrow: '->' }}
  />
</Plot>
```

`RelationMark` is usually paired with positional marks that define `anchorId`. The positional mark projects rows into core `Node` / `Coordinate` elements and gives them stable ids. The relation mark uses the same rule shape on its own rows to compute source / target ids, then lowers to a core `Path`. When the edge rows do not already exist, `transform` can derive relation rows locally for this mark.

## Presentation Layer

RelationMark is the low-level relationship path mark. It does not reinvent arrows, labels, or routed lines; it turns relationship data into a core `Path.children` step sequence. Dependency lines, flow lines, reference lines, and labeled connectors are all different configurations of the same source-target path.

| Presentation | Key props | Notes |
| --- | --- | --- |
| Point-to-point relation | `source` / `target` | Reference existing nodes by id or generated anchor rules, then connect with the default `move -> line` path |
| Waypoint path | `via` / `route[].to` | Projected waypoints generate core `Coordinate` elements, so later ids can reference them |
| Path label | `label` / `route[].label` | Lowers to core step label; explicit step labels win over shorthand |
| Core Path capabilities | `path` | Passes through arrows, bends, folds, marks, animations, color, and other Path top-level options |

## Examples

### Scatter Relations

Each scatter row declares both `id` and `target`. `PointMark` generates node ids with `anchorId`, and `RelationMark` joins those ids from the data fields. This example does not need `transform`: the relationship already exists in the raw rows, so RelationMark only resolves those fields into source / target paths.

### Bubble Relation

Bubble charts often need to highlight one business relationship inside a broader distribution. This example uses 20 bubbles for the distribution, and the bubble layer generates reusable Node ids with `anchorId`. The relation layer does not hand-write an edge row; its `transform` runs `relate`: source selects the bubble with the largest `value`, target selects the bubble with the highest `y`, and the transform emits `sourceId`, `targetId`, and the path label. Source / target then reference those derived ids with `boundary`, so the connector stops at the bubble boundary.

<ComponentPreview name="relation-bubble" sourceFiles={['relation-bubble.data.ts']} size="lg" />

### Path Extremes

The path mark draws 20 ordered points and registers each vertex with `anchorId`. This example also avoids a separate edge table: `RelationMark.transform` runs `relate` over the same points, selects the minimum `y` row as source and the maximum `y` row as target, then emits `sourceId`, `targetId`, and `deltaLabel`. Source / target connect to those derived vertex ids, and `routing={{ kind: 'bend' }}` draws the low-to-high relationship as a curve.

<ComponentPreview name="relation-path-extremes" sourceFiles={['relation-path-extremes.data.ts']} size="lg" />

### Interval Relation

In a bar or interval chart, a relation can connect the tops of two interval elements to explain a handoff or difference between stages. This example keeps only before / after interval rows, not five handwritten relation lines. Two `RelationMark.transform` pipelines split decrease and increase groups: the decrease layer reads `decreaseOrder`, the increase layer reads `increaseOrder`, and both group by `pair` to emit source / target coordinates, the `sourceViaY` waypoint height, and `deltaLabel`. `routing={{ kind: 'orthogonal' }}` consumes those derived fields to draw the upward right-angle connector; decreases are red, increases are green.

## How It Works

`<RelationMark>` does not render DOM directly. `<Plot>` collects it into mark IR with `type: 'relation'` while building the `PlotSpec`. During lowering, plot resolves `source`, `target`, `via`, and `route[].to`, then lowers each data row into one core `Path`, plus any required core `Coordinate` elements.

`transform` runs after the plot-level transform pipeline and only feeds the current relation mark. Derived fields such as `sourceId`, `targetId`, or `deltaLabel` can be consumed by `source`, `target`, `label`, and relation channels without adding them to the root data model.

Target references share the `PlotTargetRef` structure:

| Form | Use | Notes |
| --- | --- | --- |
| `{ id }` | Reference an existing core target directly | Can also carry `anchor` / `offset` / `boundary` |
| `{ anchorId }` | Generate the target id from the current relation row | Uses the same rule shape as positional mark `anchorId`; useful for joining by data fields |
| `{ project }` | Project a point from the current relation row | `project` maps coordinate roles to fields; add `anchorId` only when the point needs a reusable id |

Without `route`, the default path is `move(source) -> line(target)`. With `via`, intermediate points are inserted as `line(via)` in order. `routing` is a route strategy: `line` keeps straight segments, `bend` emits core bend steps, and `orthogonal` emits explicit right-angle line steps when the endpoints are projected coordinates. With `route`, route steps align with core path steps and support `line`, `fold`, `curve`, `cubic`, and `bend`. `route` and `routing` are mutually exclusive. `label` is shorthand: it lands on the default path, the selected routing segment, or the final drawable explicit route step. If a `route[].label` is already set, that explicit step label wins. Step labels generated by RelationMark default to `side: 'sloped'`, so they rotate along the path; an explicit `side` still takes priority.

When a relation uses generated `anchorId` and the target does not exist, lowering fails after the plot finishes and reports the relation mark id / index, data row index, and generated id. Duplicate generated anchor ids also fail loudly.

## API

`RelationMark` groups its API by targets, route, path, label, common props, and custom channels. `FieldName` means a data field name or field path, for example `sourceId` / `meta.to`.

### Mark API

| Group | Prop | Type | Default | Description |
| --- | --- | --- | --- | --- |
| Target | `source` | `PlotTargetRef` | Required | Start target of the relationship path: direct id, generated anchor id, or projected coordinate |
|  | `target` | `PlotTargetRef` | Required | End target of the relationship path, using the same structure as `source` |
|  | `via` | `Array<PlotTargetRef>` | - | Waypoints for the default route; each projected waypoint generates a core `Coordinate` |
| Data | `transform` | `Array<Transform>?` | - | Mark-local transform pipeline for deriving the current relation layer's rows from plot rows; see the transform table below for each type |
| Route | `route` | `Array<RelationRouteStep>` | - | Explicit step sequence; the last step may omit `to` and default to `target` |
|  | `routing` | `RelationRoutingSpec?` | `line` | Algorithmic route strategy: `line`, `bend`, or `orthogonal`; mutually exclusive with `route` |
|  | `route[].kind` | `'move' / 'line' / 'fold' / 'curve' / 'cubic' / 'bend'` | - | Core path step kind |
|  | `route[].to` | `PlotTargetRef?` | Last step uses `target` | Destination for the current step |
|  | `route[].label` | `RelationStepLabel?` | - | Label for the current step; higher priority than `label` shorthand |
| Label | `label` | `RelationStepLabel?` | - | Shorthand path label for the default path or the final drawable route step; defaults to `sloped` when `side` is omitted |
| Path | `path` | `RelationPathOptions?` | - | Core `Path` top-level passthrough, excluding `type` / `children` |
|  | `color` | `FieldName?` | - | Field-driven relation color channel |
| Common | `id` | `string?` | - | Optional mark handle for layer ids, errors, and runtime lookup |
| Custom | `channels` | `Record<string, Channel>` | - | Custom channel entry point, resolved by registered channel definitions |

`RelationPathOptions` is the place for constant Path capabilities such as `arrow`, `arrowDetail`, `marks`, `bend` / `fold` / `curve`, `animations`, `roundedCorners`, `strokeWidth`, and `color`. Field-driven visual styling should still use plot channels, for example `color="kind"`.

### Transform API

`transform` is the mark-local data entry shared by all marks, and it reuses the plot transform structure; see [Transform](/plot/grammar/transform) for common transform types. Inside `RelationMark`, it only feeds the current relation mark and does not rewrite the rows seen by sibling marks. This table lists the relation-oriented transform that is most often used here.

| Type | Row count | Meaning |
| --- | --- | --- |
| `relate` | N → relation rows | Reuses common selectors to choose source / target rows, usually for `RelationMark.transform`, and can also feed other marks |
