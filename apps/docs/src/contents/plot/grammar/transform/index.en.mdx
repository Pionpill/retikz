`transform` runs after data preparation and before scales and marks. It is independent of the final mark type: the same transformed rows can feed bars, lines, points, or regions.

## Responsibilities

| Category | Members | Row Count | Use It When |
| --- | --- | --- | --- |
| Row transforms | `sort` / `stack` / `normalize` / `derive-interval` / `jitter` | N rows → N rows | Reorder, derive fields, stack, compute shares, or spread overlapping points |
| Group transforms | `bin` / `aggregate` | N rows → M bins / groups | Build histograms, grouped summaries, or detail-to-summary views |

## Declaration

Declare a transform with `<Transform kind="...">`; `kind` is the discriminator and the remaining props map to that transform's fields. Multiple `<Transform>` children fold into a pipeline in **declaration order**:

```tsx
<Plot data={rows} model={model}>
  <Transform kind="aggregate" groupBy={['region']} reduce="sum" field="revenue" as="total" />
  <IntervalMark x="region" y="total" />
</Plot>
```

Transform outputs are **derived fields**, such as `binStart` / `binEnd` / `binValue`, `total`, or `y0` / `y1`. They are produced by the transform and do not need to appear in `model`; fields consumed by transforms still go through model and data validation.

For programmatic construction, `<Plot dataTransforms={[...]}>` can pass a transform array directly. It shares the same pipeline as `<Transform>` children; direct-pass entries come before child transforms.

> The prop is named `dataTransforms`, not `transforms`, to avoid colliding with core container geometric transforms such as translate / rotate.

## Custom Transforms

Beyond the built-in transforms, define your own data processor with `defineTransform`. The spec still stores only the JSON operation, such as `{ kind: 'double-x', field: 'x', as: 'x2' }`; the schema, field collection, and runtime function live in the definition passed through `<Plot transformDefinitions={[...]}>`.

```tsx
import { defineTransform } from '@retikz/plot';
import { z } from 'zod';

const doubleX = defineTransform({
  schema: z.object({
    kind: z.literal('double-x').describe('Discriminator: double one numeric field'),
    field: z.string().min(1).describe('Input field read from each row'),
    as: z.string().min(1).describe('Output field written to each row'),
  }),
  inputFields: operation => [operation.field],
  outputFields: operation => [operation.as],
  apply: (rows, operation) =>
    rows.map(row => ({
      ...row,
      [operation.as]: Number(row[operation.field]) * 2,
    })),
});

<Plot data={rows} model={model} transformDefinitions={[doubleX]}>
  <Transform kind="double-x" field="x" as="x2" />
  <PointMark x="x2" y="y" />
</Plot>;
```

`x2` is not declared in `model`, because it is derived by `double-x`. `outputFields` registers it as a transform output, so strict model validation checks only the real input fields `x` and `y`.

| Definition Field | Purpose |
| --- | --- |
| `schema` | Validates the `{ kind, ...config }` operation. `kind` must be a non-built-in `z.literal(...)`; all other fields must stay JSON-serializable. |
| `inputFields` | Returns the source fields read by the transform; these fields enter model validation and field resolution. |
| `outputFields` | Returns derived fields produced by the transform; downstream marks or transforms can consume them without declaring them in `model`. |
| `apply` | Runs the transform in pipeline order and returns the next row set. It must be deterministic so rendering and locators stay aligned. |

The third `apply` argument is a transform context. Row-preserving transforms usually keep row provenance by returning `{ ...row, newField }`; row-count-changing transforms can call `context.groupProvenance(out, members)` to attach `sourceIndices`. If a transform generates rows with no source rows, provenance naturally degrades to `transformedIndex` only.

## How It Works

During lowering, Plot collects source fields read by transforms and records output fields derived by transforms. Strict model validation then checks only real input fields and does not require derived fields to be declared ahead of time.

Transforms are applied in declaration order: the output rows from one transform become the input rows for the next. The final row set then feeds scale inference, mark lowering, and locators.
