A chart has two inputs: **config** (what to draw — marks / coordinate / scales) and **data** (which values). retikz keeps them apart: data does **not** enter the chart config (the IR); it is supplied separately at compile time. That lets one config be reused across different datasets.

<ComponentAlert title="Why data stays out of the IR" description="Data is usually much larger than the chart config. Embedding every row into the IR would make JSON and persisted artifacts bulky, hard to diff, and hard to maintain. Config and data are naturally separate: the IR describes how to draw, while data is supplied at compile time through the model; as long as the field contract lines up, the same config can run against another data source." />

The simplest form: hand a row array to `<Plot data>` and have marks reference columns by field name.

```tsx
<Plot data={rows}>
  <LineMark x="month" y="revenue" order="month" />
</Plot>
```

A field name is a **path**, so nested data (MongoDB documents, JSON from an API) works directly: `x="user.address.city"` drills to the leaf. The leaf must be a scalar (string / number / boolean / time) — not an object or array.

## Declaring field types

Declare field types through `<Plot model>`. The `model` is the field contract: whether `month` is time or a plain string, and whether `revenue` is continuous or categorical, affects scale selection, axis formatting, legend derivation, and validation. When `model` is omitted, retikz **infers field types** from data samples.

Field types and default inference:

| Type | Meaning | Examples | Default inference and explicit declarations |
| --- | --- | --- | --- |
| `continuous` | continuous measurable numbers | sales, price, temperature | Default: sample values are numbers<br />Declare: numeric enums, ids, or status codes should behave as categories |
| `temporal` | date / time values | dates, timestamps | Default: `Date` or unambiguous ISO date / datetime strings<br />Declare: non-default date formats or timezone-less times |
| `categorical` | discrete categories | countries, color names, ratings | Default: other strings / booleans and discrete values<br />Declare: category order, axes, or legends need fixed ordering |

Customize `model` when you need to override inference, parse non-default storage formats, or make the config self-describing without the data. Each field declaration can contain:

| Field | Purpose |
| --- | --- |
| `name` | logical field name, also the name referenced by marks / transforms |
| `type` | measurement type; omitted fields are inferred from data |
| `format` | declarative parsing format, such as `slashDate` / `percent`; see [Processing](/plot/grammar/data/processing) |
| `order` | category order for categorical fields |

**Declaring a model = strict mode**: every data field referenced by a mark / transform must be listed in the model; a misspelled field name **fails immediately** instead of drawing an empty chart. References include not only `x` / `y`, but also `a` / `b` / `c`, `color`, `series`, a mark's `order`, point `size` / `opacity` / `shape`, and transform input fields.

With no `model`, field types follow the default inference rules above, which is handy for quick drafts.

**`type` is optional — partial models**: a field's type can be omitted, leaving just `{ name }`. The field still joins strict mode and keeps a portable field contract; only its type is left to inference. This is useful when most fields are obvious and only a few need pinning: give `type` to numeric enums, use `format` for non-default dates / percentages, and leave the rest bare.

```tsx
<Plot data={sales} model={[
  { name: 'createdAt',  format: 'slashDate' }, // '2024/01/01' → temporal
  { name: 'statusCode', type: 'categorical' }, // numeric enum pinned as category
  { name: 'revenue' },                         // name only → inferred continuous
]}>
  {/* … */}
</Plot>
```

Fields with `type` omitted need the data at lowering to determine their type. Fields with `format` get their type from the format, so `format: 'percent'` is treated as `continuous`. To keep a spec fully self-describing without the data (LLM-friendly / fully portable), fill in `type` or `format`.

<ComponentAlert title="Inference is best-effort; the model is the contract" description="Without a model (or with a field's type / format omitted), types are guessed from samples: time is only recognized in unambiguous ISO form (YYYY-MM-DD, an ISO datetime with a timezone, including the space-separated SQL form like '2024-01-01 12:00:00Z') — '2024/01/01', timezone-less times, and bare numeric strings are not treated as time. Declare a model when you want precision, validation, or for an LLM to understand the fields without seeing the data; add format or resolveField for non-default storage formats." />

## Type-driven scales

Once field types are declared, positional channels (x / y, and ternary a / b / c) **no longer need an explicit scale**: retikz picks one from the field type, `continuous` → linear, `temporal` → time axis, `categorical` → band. Color channels follow the same field types: continuous / temporal fields derive continuous color ramps, while categorical fields derive discrete color. See [Scales](/plot/grammar/scale) for the full mapping and override rules.

## Category order: `order`

A `categorical` field orders its categories by **data appearance** by default; axes and legends follow that order. To control it — sizes should read `S → M → L → XL`, not whatever order they happen to appear in the data — give the field an `order`:

The two charts below use the same size data. The left chart follows data appearance order; the right chart fixes the business order `S → M → L → XL`.

<ComponentPreview name="data-model-order" sourceFiles={['data-model-order.data.ts']} />

| `order` | Effect |
| --- | --- |
| omitted / `'data'` | data appearance order (default) |
| `'ascending'` / `'descending'` | sort the categories: numeric when all numbers, else as strings |
| `Array` (e.g. `['S','M','L']`) | the array is the order; categories present in the data but absent from the array are appended at the end |

Rules:

- **It lives on the field, so position and color share the order**: when the same field drives both the x-axis (band) and color (ordinal), both use the same category order.
- **Only valid on `categorical`**: an `order` on a `continuous` / `temporal` field **throws** (order is meaningless for continuous values / time).
- **An explicit scale `domain` wins**: if the scale declares its own `domain`, that takes precedence and `order` is ignored.
- A **non-default** `order` (a sort or an explicit array) marks the field as ordered — retikz's three field types have no dedicated "ordered category" type; orderedness is expressed through this parameter.
