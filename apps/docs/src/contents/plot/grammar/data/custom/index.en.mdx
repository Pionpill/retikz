The data layer has two extension styles. Some extensions still persist with the PlotSpec, such as named `format` values. Others are runtime functions, such as `resolveField` and `defineVisualChannel`. Use the first when the config should serialize well; use the second when the behavior belongs to application code.

| Case | Recommended Entry | Enters IR |
| --- | --- | --- |
| Reusable field format | `defineFieldFormat` + `formatDefinitions` | Yes, only the format name |
| Arbitrary field parsing | `resolveField` | No, runtime function only |
| New visual channel | `defineVisualChannel` + `visualChannelDefinitions` | Binding enters IR; definition does not |

## Custom Named Formats

Beyond the built-in `format` vocabulary, common reusable formats such as currency strings, regional dates, or unit-suffixed numbers like `'1.2万'` can be registered with `defineFieldFormat`. The `model` still stores only a format-name string; the parser lives in a runtime definition.

<ComponentPreview name="processing-custom-format" sourceFiles={['processing-custom-format.data.ts']} />

Definition contract:

| Field | Purpose |
| --- | --- |
| `name` | Registration key = the `format` string in `model`; must be non-empty and must not collide with a built-in format. |
| `impliedType` | The single measurement type this format implies; fills in `type` when the field omits it. |
| `parse` | Raw value → canonical value; return `undefined` / `NaN` to mark the value invalid downstream. |

Custom and built-in formats share one registry: built-ins are always available, custom names cannot collide with built-ins or each other, and a `model` that names an unregistered format fails loud.

## Runtime Field Parsing

For arbitrary formats outside the vocabulary, such as a `'2026Q1'` quarter string, or when a field must be forced to a specific type, use `resolveField`. It is a function and never enters IR, so it is the escape hatch for hand-written application code.

<ComponentPreview name="processing-resolve" sourceFiles={['processing-resolve.data.ts']} />

Rules:

- Returning `{ type }` overrides the field type, ahead of the model and inference.
- Returning `{ parse }` overrides value parsing; with `parse` but no `type`, the type must come from the model.
- `resolveField` does not bypass strict mode: with a model declared, unlisted fields still error.
- The second argument provides `{ dataReference, physicalPath, declaredType }`, so one logical field can branch by data source or physical path.

## Custom Visual Channels

Common visual channels (`size`, `opacity`, `shape`, `strokeWidth`) have named props. To add your own visual channel, declare a runtime definition with `defineVisualChannel`, then bind a field or constant through `encoding.channels.<name>` in the spec.

```tsx
import { defineVisualChannel } from '@retikz/plot';

const intensity = defineVisualChannel<number>({
  channel: 'intensity',
  output: { outputKind: 'number', range: [0.3, 1], clamp: true },
  resolve: ctx => mark => {
    const binding = mark.type === 'point' ? mark.encoding.channels?.intensity : undefined;
    if (binding?.field === undefined) return undefined;
    const values = ctx.rows.map(row => Number(row[binding.field])).filter(Number.isFinite);
    const min = Math.min(...values);
    const max = Math.max(...values);
    return {
      of: row => {
        const value = Number(row[binding.field]);
        if (!Number.isFinite(value)) return undefined;
        return 0.3 + (max === min ? 0.5 : (value - min) / (max - min)) * 0.7;
      },
    };
  },
  deliver: (node, value) => {
    node.opacity = value;
  },
});
```

The binding remains JSON-safe PlotSpec:

```tsx
<Plot
  data={{ points }}
  spec={{
    namespace: 'plot',
    type: 'plot',
    data: { reference: 'points' },
    scales: [
      { type: 'linear', name: 'x' },
      { type: 'linear', name: 'y' },
    ],
    coordinate: { type: 'cartesian2D', x: 'x', y: 'y' },
    marks: [
      {
        type: 'point',
        encoding: {
          x: { field: 'x' },
          y: { field: 'y' },
          channels: { intensity: { field: 'score' } },
        },
      },
    ],
  }}
  visualChannelDefinitions={[intensity]}
/>;
```

The definition is runtime capability and does not enter PlotSpec; the spec stores only channel bindings. Built-in and custom visual channels are merged into one registry, then resolved and delivered to core node properties through the same path.

`encoding.channels` mainly serves the spec / programmatic entry today; React `<PointMark>` still exposes common channels as named props. A custom channel cannot override a built-in channel name, and binding an unregistered channel fails during lowering.

## Choosing One

| Need | Use |
| --- | --- |
| Enumerable format, persisted with the spec | `defineFieldFormat` |
| One-off parsing, application state, or data-source branching | `resolveField` |
| Only map logical fields to renamed source fields | `fieldMap`; see [Processing](/plot/grammar/data/processing) |
| Drive a new visual property from a field | `defineVisualChannel` |

Prefer declarative capability that can enter IR. Use runtime definitions or `resolveField` only when the behavior truly needs a function.
