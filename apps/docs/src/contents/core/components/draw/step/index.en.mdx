---
title: Step
description: Path's child node — one step = one action (move / line / fold / cycle close / curve / cubic / bend / smooth / arc / circlePath / ellipsePath / rectangle); `to` accepts node id / Cartesian / polar / offset / proportional placement / relative offsets; only valid as a direct child of `<Path>`.
---

`<Step>` describes a single path action: `move` lifts the pen, `line` draws a straight line, `fold` folds through a single right-angle corner, `cycle` closes the path, `curve` / `cubic` / `bend` draw curves of various shapes, `smooth` draws a smooth curve through a list of points, `arc` / `circlePath` / `ellipsePath` use the cursor as the center to draw an arc / full circle / full ellipse, and `rectangle` draws an axis-aligned rectangle from two opposite corners. It is **only** valid as a direct child of `<Path>`; placed elsewhere it is silently ignored.

Use this table to pick a `kind` first:

| kind | Needs `to` | Draws | Advances cursor | Supports label |
| --- | --- | --- | --- | --- |
| `move` | Yes | No | Yes | No |
| `line` / `fold` / `curve` / `cubic` / `bend` | Yes | Yes | Yes | Yes |
| `smooth` | No (uses `points`) | Yes | To the last `points` entry | Yes |
| `cycle` | No | Yes | Back to subpath start | No |
| `arc` | No | Yes | To arc endpoint | Yes |
| `circlePath` / `ellipsePath` | No | Yes | Back to circle / ellipse center | Yes |
| `rectangle` | Yes | Yes | To opposite corner | No |

## Usage

```tsx
import { Path, Step } from '@retikz/react';
```

```tsx
<Path>
  <Step kind="move" to="a" />
  <Step kind="line" to="b" />
</Path>
```

Use `<Step>` when you need exact control over Kernel path actions: multiple `move`s, mixed straight / folded / curved / arc segments, or debugging the structure produced by `<Draw>`. For everyday connections, prefer [Draw](/core/components/draw/overview).

### Closing (cycle)

`kind="cycle"` closes the current sub-path back to the most recent `move` target, matching SVG path `Z`. `cycle` carries **no** `to` field (the destination is implicit). Saves writing one explicit endpoint vs. drawing a `line` back to the start:

<ComponentPreview name="step-cycle" size="sm" />

### Quadratic curve

`kind="curve"` draws a quadratic Bezier with one control point, matching SVG path `Q`. A Bezier curve does not have to pass through the control point; the control point acts more like a handle that pulls the segment from start to end. The farther it is from the straight line, the stronger the bend. Control points currently use Cartesian `[x, y]`:

<ComponentPreview name="step-curve" size="xs" />

### Cubic curve

`kind="cubic"` draws a cubic Bezier with two control points, matching SVG path `C`. `control1` shapes the direction as the curve leaves the start; `control2` shapes the direction as it approaches the end. Because both ends can be controlled separately, this is useful for S-shaped curves and complex connectors:

<ComponentPreview name="step-cubic" size="xs" />

### Bend (arc shorthand)

`kind="bend"` is shorthand for an arced connection: say whether the segment bends left or right while looking from start to end, plus an angle. The compiler computes control points and lowers it to a cubic Bezier. `bendDirection` is the visual left/right relative to the from→to path; `bendAngle` defaults to 30:

<ComponentPreview name="step-bend" size="md" />

### Smooth curve through points (smooth)

`kind="smooth"` draws a smooth curve **through a list of points** — no need to hand-compute Bézier control points for each segment when drawing a data polyline, a streamline, or a free curve. It takes no `to`; instead it takes `points`: the current **cursor is the implicit first knot**, the curve starts at the cursor and passes through each point in `points` in order, and the cursor ends at the last point (so a preceding `move` or other step must set the cursor, otherwise the path is skipped with a `PATH_TOO_SHORT` warning, same as `line` / `curve` as the first step). It is compiled to a chain of cubic Béziers via centripetal Catmull-Rom. Below, the same set of points drawn as `smooth` (steelblue) versus a point-to-point `line` polyline (gray):

<ComponentPreview name="step-smooth" size="sm" />

`tension` tunes the curve's slackness (TikZ `tension`): the default 1 is the standard centripetal Catmull-Rom, `<1` pulls the curve tauter (closer to a polyline), and `>1` makes it loopier. Whatever the value, the curve always passes through every point — only the per-segment tangent length changes:

<ComponentPreview name="step-smooth-tension" size="sm" />

### Offset positioning

`to` also accepts the **`{ of, offset }`** form — a base point plus an arbitrary `(dx, dy)`. `of` has three shapes — node id, Cartesian literal, or PolarPosition (recursive polar) — symmetric with `<Node position>`'s offset form:

<ComponentPreview name="step-offset-target" size="sm" />

### Relative coordinates (relative / relativeAccumulate)

`to` also accepts relative-offset objects: `{ relative: [dx, dy] }` and `{ relativeAccumulate: [dx, dy] }` both resolve against the **previous step's endpoint** (`prevEnd`, falling back to `[0, 0]` when there is none). The only difference is **whether prevEnd advances**:

- `{ relative }` — chained offsets all anchor on the **same** point; prevEnd does **not** update
- `{ relativeAccumulate }` — each segment accumulates and prevEnd moves with it

You can also write the sugar strings `'+dx,dy'` / `'++dx,dy'` (e.g. `<Step to="+1,0" />`); the React adapter rewrites them in place to the matching IR objects. In the demo below, the two paths have identical step sequences and only the target form differs — the solid line (relative) traces an L, while the dashed line (relativeAccumulate) climbs a staircase:

<ComponentPreview name="step-relative" size="sm" />

### Arc

`kind="arc"` draws an arc by start / end angle and radius — centered on the **cursor** by default, or on an explicit `center` (anchored independently of the cursor). Radius is one of two forms: `radius` for a circular arc, `radiusX` + `radiusY` for an elliptical arc. It describes "sweep from this angle to that angle", needs no `to`, and is useful for angle marks, circle fragments, or geometric guides. Angles follow the retikz polar convention: 0° points to +x, 90° is visually downward. The pen ends at the arc's endpoint:

<ComponentPreview name="step-arc" size="sm" />

### Circle

`kind="circlePath"` uses the **cursor as center** and draws a circle by `radius`. Without angles it draws a fully closed circle — the pen returns to the center after closing, useful for endpoint dots, circular node borders, etc. With `startAngle` + `endAngle` it draws a **partial circle** (half circle / segment), closed per `closed`: `'chord'` (default) / `'sector'` (connect to the center into a wedge) / `'open'` (pure unclosed arc):

<ComponentPreview name="step-circle" size="xs" />

### Ellipse

`kind="ellipsePath"` uses the **cursor as center** and draws an ellipse by `radiusX` / `radiusY`. Without angles it draws a fully closed ellipse — the pen returns to the center, and when `radiusX === radiusY` it degenerates into a circle. As with circlePath, `startAngle` + `endAngle` draw a **partial ellipse**, closed per `closed` (`'chord'` default / `'sector'` / `'open'`):

<ComponentPreview name="step-ellipse" size="sm" />

### Rectangle

`kind="rectangle"` uses `from` and `to` as opposite corners of an axis-aligned rectangle; optional `cornerRadius` rounds the corners. Unlike `line`, it does not depend on the current cursor, which keeps it close to TikZ `(a) rectangle (b)`. For everyday rectangles prefer the `<Rectangle>` sugar in [Rectangle](/core/components/shapes/rectangle); use this low-level kind when authoring IR-like step sequences or mixing it with other step kinds.

<ComponentPreview name="step-rectangle" size="sm" />

### Edge label

Attach a `label` to a `<Step>` to drop a single line of text near the segment's start / middle / end. `label` is an object:

- `text`: required, single-line label content
- `position`: one of seven keywords `'at-start' | 'very-near-start' | 'near-start' | 'midway' | 'near-end' | 'very-near-end' | 'at-end'`, or a numeric t in `[0, 1]` for any fine position; default `'midway'` (t=0.5)
- `side`: `'above'` / `'below'` / `'left'` / `'right'` / `'sloped'`, default `'above'`; `'sloped'` rotates the label along the tangent so it sits on the line
- `textColor`: label text color; falls back to scope `labelDefault` → the owning path's master `color` → currentColor (follows the master color, not stroke)
- `opacity`: label-only opacity 0..1; multiplied with the owning path opacity (element-internal axis; does not compound across scopes)
- `font`: label font overrides (family / size / weight / style); per-field fallback to `labelDefault` → renderer default

Two equivalent forms — the prop form `<Step label={{...}} />`, or the sugar form `<Step><EdgeLabel>...</EdgeLabel></Step>` (needs `import { EdgeLabel } from '@retikz/react'`); **the prop wins when both are set**. `'move'` / `'cycle'` / `'rectangle'` cannot carry a label — move doesn't draw, cycle is a close marker, and rectangle has no label field, so any label on them is silently dropped:

<ComponentPreview name="step-label" />

#### Label color and font

An edge label's color follows the owning path's **master `color`** — with `<Path color>` the label is auto-colored to match; setting only `stroke` (no `color`) does not, so the label keeps its default color. Use `textColor` to override explicitly, and `font` / `opacity` for smaller / faded secondary labels:

<ComponentPreview name="step-label-color" size="sm" />

A scope `labelDefault` gives a whole group of labels a shared default (see [Scope style inheritance](/core/components/layout/scope)); inheritance order: label explicit > `labelDefault` > host path master color > currentColor.

#### label.position: 7 keywords + arbitrary numeric t

`position` accepts 7 keywords or a numeric t in `[0, 1]`. Keywords are sugar for the corresponding t:

| Keyword | t | Meaning |
| --- | --- | --- |
| `'at-start'` | `0` | Segment start |
| `'very-near-start'` | `0.125` | Very near start |
| `'near-start'` | `0.25` | Near start (1/4 in) |
| `'midway'` | `0.5` | Midpoint (default) |
| `'near-end'` | `0.75` | Near end (3/4 in) |
| `'very-near-end'` | `0.875` | Very near end |
| `'at-end'` | `1` | Segment end |

A numeric form like `position={0.3}` precisely places the label along the segment. **Values outside `[0, 1]` are rejected at schema validation, not clamped at compile time** (`position={-0.1}` / `position={1.2}` fail IR validation).

#### Geometric meaning of t per step kind

t is normalized along the whole segment; each kind has its own parametrization:

| Step kind | Parametrization | t=0.25 | t=0.5 | t=0.75 |
| --- | --- | --- | --- | --- |
| `'line'` | Normalized arc length | 1/4 in | Midpoint | 3/4 in |
| `'fold'` (N=2) | Each leg gets `1/N` of t — the corner is always at `t = j/N`, **independent of leg length** | Leg-1 midpoint | **Corner** | Leg-2 midpoint |
| `'curve'` / `'cubic'` | Bezier parameter t (**not arc length**) | Bezier t=0.25 | Bezier t=0.5 (usually **not** the visual midpoint) | Bezier t=0.75 |
| `'bend'` | Lowered to cubic, then Bezier t | Same as cubic | Same as cubic | Same as cubic |
| `'arc'` | t maps linearly across `startAngle..endAngle` (degrees) | Quarter of the angle sweep | Mid angle | Three-quarters of the sweep |
| `'circlePath'` | Full circle t∈[0, 1]: t=0 at angle 0 (+x), CCW growth | 90° (visually down) | 180° (−x) | 270° (visually up) |
| `'ellipsePath'` | Same as circlePath: t=0 at angle 0, CCW growth | Ellipse at 90° | Ellipse at 180° (**not** arc-length midpoint) | Ellipse at 270° |

## API Reference

| Prop | Type | Default | Description |
| --- | --- | --- | --- |
| `kind` | `'move' \| 'line' \| 'fold' \| 'cycle' \| 'curve' \| 'cubic' \| 'bend' \| 'smooth' \| 'arc' \| 'circlePath' \| 'ellipsePath' \| 'rectangle'` | `'line'` | See the "Twelve kinds" table below; IR also has `generator`, without React `<Step>` DSL |
| `via` | `'-\|' \| '\|-'` | — | Required for `kind="fold"`: `-\|` horizontal-then-vertical; `\|-` vertical-then-horizontal |
| `from` | `IRTarget` | — | Required only for `kind="rectangle"`: one rectangle corner |
| `to` | `IRTarget` | — | Not used for `kind="cycle"` / `'arc'` / `'circlePath'` / `'ellipsePath'`; required for `kind="rectangle"` and other cursor-advancing kinds. Target: node id, Cartesian `[x, y]`, polar object, offset object `{ of, offset }`, proportional placement `{ between, t }`, relative-offset object `{ relative }` / `{ relativeAccumulate }`, or sugar string `'+dx,dy'` / `'++dx,dy'` |
| `control` | `[number, number]` | — | Required for `kind="curve"`: single control point of the quadratic Bezier |
| `control1` | `[number, number]` | — | Required for `kind="cubic"`: first control point (shapes start tangent) |
| `control2` | `[number, number]` | — | Required for `kind="cubic"`: second control point (shapes end tangent) |
| `points` | `Array<IRTarget>` (≥1) | — | Required for `kind="smooth"`: the points the curve passes through after the cursor, in order. The cursor is the implicit first knot; a single point = one segment; the cursor ends at the last point. Element form is the same as `to` |
| `tension` | `number` (>0) | `1` | Optional for `kind="smooth"`: tangent-length multiplier (TikZ `tension`); default 1 (standard centripetal Catmull-Rom), `<1` tauter, `>1` loopier |
| `bendDirection` | `'left' \| 'right'` | — | Optional for `kind="bend"`: visual left / right relative to from→to direction; pairs with `bendAngle` for a symmetric bend. **`outAngle` / `inAngle` take precedence** and this is ignored when they are given |
| `bendAngle` | `number` | `30` | Optional for `kind="bend"`: bend angle in degrees, restricted to (-180, 180) |
| `outAngle` | `number` | — | Optional for `kind="bend"`: out-angle at the start (degrees, TikZ `out=`); pairs with `inAngle` for an asymmetric curve / self-loop, taking precedence over `bendDirection` / `bendAngle` |
| `inAngle` | `number` | — | Optional for `kind="bend"`: in-angle at the end (degrees, TikZ `in=`); pairs with `outAngle` |
| `looseness` | `number` | `≈1` | Optional for `kind="bend"`: control-point distance factor (TikZ `looseness=`); larger = slacker curve; also scales the default self-loop size when `from == to` |
| `startAngle` | `number` | — | Required for `kind="arc"`; optional for `'circlePath'` / `'ellipsePath'` (pair with `endAngle` for a partial circle / ellipse): start angle in degrees (0° → +x, 90° → visually down) |
| `endAngle` | `number` | — | Required for `kind="arc"`; optional for `'circlePath'` / `'ellipsePath'`: end angle in degrees; sweep direction inferred from start vs end |
| `radius` | `number` | — | Given for `kind="arc"` (circular) / `'circlePath'`: radius of the circle / arc. On arc, `radius` and `radiusX`+`radiusY` are **mutually exclusive** (one or the other); required on circlePath |
| `radiusX` | `number` | — | `kind="arc"` (elliptical) / `'ellipsePath'`: x-axis radius; required together with `radiusY` (mutually exclusive with `radius` on arc); required on ellipsePath |
| `radiusY` | `number` | — | `kind="arc"` (elliptical) / `'ellipsePath'`: y-axis radius; required together with `radiusX`; required on ellipsePath |
| `center` | `IRTarget` | cursor | Optional for `kind="arc"`: explicit arc center, defaults to the cursor (previous step endpoint); set it to anchor the arc independently of the cursor (used by `<Sector>` to draw a correct wedge) |
| `closed` | `'closed' \| 'chord' \| 'open' \| 'sector'` | see below | Optional for `kind="circlePath"` / `'ellipsePath'`: closing mode. Without angles `'closed'` (full circle / ellipse, default); with angles `'chord'` (chord between the two arc ends, default) / `'sector'` (connect both ends to the center, then close) / `'open'` (pure unclosed arc) |
| `cornerRadius` | `number` | — | Optional for `kind="rectangle"`: corner radius |
| `label` | `IRStepLabel` | — | Edge label (works on every kind except `'move'` / `'cycle'` / `'rectangle'`): `{ text, position?, side?, textColor?, opacity?, font? }`; equivalent sugar form `<Step><EdgeLabel>…</EdgeLabel></Step>`, prop wins on conflict |

### Twelve kinds

| kind | Behavior | Path analogue |
| --- | --- | --- |
| `'move'` | Move cursor, **no draw** | path "M" |
| `'line'` | Straight line from cursor to target | path "L" |
| `'fold'` | Right-angle fold through one corner | two path "L" segments |
| `'cycle'` | Close back to most recent `move` (no `to`) | path "Z" |
| `'curve'` | Quadratic Bezier (one control point) | path "Q" |
| `'cubic'` | Cubic Bezier (two control points) | path "C" |
| `'bend'` | Arc shorthand (direction + angle), lowered to cubic | path "C" |
| `'smooth'` | Smooth curve through cursor + `points`, lowered to a cubic chain | path "C"×N |
| `'arc'` | Cursor as center; arc by start / end angle + radius | path "A" |
| `'circlePath'` | Cursor as center; full circle, pen returns to center | path "A"×2 |
| `'ellipsePath'` | Cursor as center; full ellipse, pen returns to center | path "A"×2 |
| `'rectangle'` | Draw a rectangle using `from` and `to` as opposite corners | TikZ `(a) rectangle (b)` |

The IR schema also contains a `generator` step for external path-generator registries. It has no corresponding React `<Step kind="generator">` DSL and is usually supplied through direct IR or a higher-level package.

The first step of a `<Path>` must be `move` — if you write `'line'` / `'fold'` / `'cycle'`, the compiler coerces it to `move` (cycle has no `to`, so it falls back to origin `[0, 0]`).

### Two via values

Only meaningful when `kind="fold"`. Given cursor `(px, py)` and target `(tx, ty)`:

| via | Corner | Path |
| --- | --- | --- |
| `'-\|'` | `(tx, py)` | Horizontal to `tx`, then vertical to `ty` |
| `'\|-'` | `(px, ty)` | Vertical to `ty`, then horizontal to `tx` |

### Fields of `label`

`label` is a single object, applied uniformly across all kinds that accept it:

| Field | Type | Default | Description |
| --- | --- | --- | --- |
| `text` | `string` | — | Required label text (single line) |
| `position` | one of 7 keywords or `number` (0..1) | `'midway'` | Normalized position t along the segment — keywords are sugar for t (at-start=0 / very-near-start=0.125 / near-start=0.25 / midway=0.5 / near-end=0.75 / very-near-end=0.875 / at-end=1); values outside `[0, 1]` are rejected by the schema |
| `side` | `'above' \| 'below' \| 'left' \| 'right' \| 'sloped'` | `'above'` | Anchor + offset direction; `above` / `below` shift along y, `left` / `right` along x; `sloped` keeps the anchor and rotates the label along the tangent |
| `textColor` | `string` | — | Label text color; falls back to scope `labelDefault` → host path master `color` → currentColor (follows the master color, not stroke) |
| `opacity` | `number` | — | Label-only opacity 0..1; multiplied with the owning path opacity (does not compound across scopes) |
| `font` | `object` | — | Label font overrides (family / size / weight / style); per-field fallback to `labelDefault` → renderer default |

The geometric meaning of t per step kind is in the "[Geometric meaning of t per step kind](#geometric-meaning-of-t-per-step-kind)" table above. In short: line uses normalized arc length; fold splits the t interval evenly by polyline leg count (the corner is always at t=0.5); curve / cubic / bend use the Bezier parameter t (**not** arc length — t=0.5 is usually not the visual midpoint); arc uses angle parametrization; circlePath / ellipsePath traverse the full curve starting at angle 0 (+x), CCW.

### Forms of `to`

| Form | Example | Behavior |
| --- | --- | --- |
| Node id | `'a'` | Auto-attaches to Node border (see [Primitive Relations](/core/concepts/core/primitive-relations)) |
| Node + connection surface | `{ id: 'a', boundary: 'circle' }` | Per-edge override of the target node's [connection surface](/core/components/draw/path) (clip shape); never changes the node footprint |
| Cartesian | `[60, 0]` | Literal `[x, y]` |
| Polar | `{ origin: 'a', angle: 30, radius: 50 }` | Polar (see [Positioning](/core/concepts/basic/position)) |
| Offset | `{ of: 'a', offset: [10, 5] }` | Base + `(dx, dy)`; `of` accepts node id, Cartesian literal, or PolarPosition |
| Proportional placement | `{ between: [{ id: 'a' }, { id: 'b' }], t: 0.5 }` | Proportional point along A → B; endpoints must be independently resolvable absolute targets (`{ id, anchor? }` form, or Cartesian / polar) |
| Proportional placement (explicit anchor) | `{ between: [{ id: 'a', anchor: 'east' }, { id: 'b', anchor: 'west' }], t: 0.5 }` | Endpoints may carry an explicit `anchor`, resolved from that anchor instead of auto-attaching to the border |
| Relative (relative) | `{ relative: [10, 0] }` or `'+10,0'` | Previous step's endpoint + `[dx, dy]`; does **not** update prevEnd |
| Relative (relativeAccumulate) | `{ relativeAccumulate: [10, 0] }` or `'++10,0'` | Previous step's endpoint + `[dx, dy]`; **updates** prevEnd |
